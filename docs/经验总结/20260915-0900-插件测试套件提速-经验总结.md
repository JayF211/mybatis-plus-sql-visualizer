# 插件测试套件提速经验总结

> 分析基线：2026-09-13 ~ 2026-09-15 两轮提速（T-TestGuard/T-TestPerf 第一轮 + T-TestPerf2 第二轮），
> 末轮在 worktree `mpsv-testperf2` 实施、master `9e4a314` 合入，合并后主工作树 4081/0/0/6 绿。
> 本文沉淀「测试套件提速怎么做」的方法与实证结论，不重复开发计划里的逐行实现细节
> （见 `docs/开发计划/20260913-2330-测试守卫补全与全量提速-开发计划.md`、
> `docs/开发计划/20260915-0238-T-TestPerf2-全量测试一命令并行提速-开发计划.md`）。

## 一、结果

| 命令 | 定位 | 用例数 | warm 墙钟 |
|---|---|---|---|
| `./gradlew testShards` | **日常全量推荐（一命令真并行，默认 3 片）** | 4081~4103（随分支） | **2m05s ~ 2m07s** |
| `./gradlew test` | 串行权威对照（与并行口径 parity 核对用） | 同上 | 4m47s |

并行化把全量测试压掉 **56%（2.3 倍）**，且零用例删减、零断言改动、零测试代码改动——「测试效果不变」是硬前提，提速只能从调度层要。

## 二、先测量，再动手：耗时画像决定一切

动手前先聚合最近一次全量的 `build/test-results/test/*.xml`（每套件根属性带 `tests`/`time`），拿到逐类耗时，才能回答三个问题：能不能并行、并行度多少、瓶颈在哪。

本仓库 326 类 / 4083 用例 / 执行合计 251.6s 的画像特征：**头部高度集中**——前 5 类（ConvertSqlToJavaActionTest 27.5s / SqlToJavaPanelTest 13.4s / SqlPreviewPanelTest 11.5s / EntityClassFinderHeavyTest 10.6s / SqlPreviewSpecMatrixTest 7.9s）占 28%；大量 0.0~0.1s 的纯逻辑类。这个形态直接决定了下面两条结论：分区不能按类数均分，并行度在核数一半左右见顶。

同理，「用例数」与「耗时」没有强相关（`SqlPreviewSpecMatrixTest` 81 用例只要 7.9s，`ConvertSqlToJavaActionTest` 2 用例要 27.5s），按用例数或类数分片必然失衡。

## 三、边界：哪些并行路已被证伪，别再试

| 方案 | 结论 | 实证 |
|---|---|---|
| `./gradlew test -PtestForks=4`（默认 test 任务多 fork 并行） | **不可行** | 多 worker 共享默认 test 沙盒，PersistentFS 互踩成片 `PersistentFSConnector` 异常（2026-09-14 实测，191 失败+卡死永远的前例） |
| 纯逻辑测试单独分桶并行（`testFast`） | **不可行** | 技术上能跑通（classpath 复用默认 test 任务成品、排除统一走 `filter{}`——legacy exclude 被 filter 覆盖的坑也趟过），但 2246 个「纯逻辑」用例中 68 个隐性依赖同 worker JVM 里平台测试先建立的 Application/LaF 状态，脱离平台桶即红（forks=1 对照同败，排除并行争用）。作为快测任务会持续误报 |
| 分片任务各开多 fork | **不必要** | 分片已经用满核，片内再并行只会加剧 GC 与 IO 争用 |

结论：**能安全并行的单位是「独立沙盒的分片任务」，不是 fork，也不是用例分桶。**

## 四、可复用的做法

### 1. 一命令并行（任务级并发）

`org.gradle.parallel=true` 下，`./gradlew testShards`（聚合任务 dependsOn 各片）单命令即让各片任务真并发，无需双开终端——「同项目内任务不并行」的旧口径在很多文档里流传，实际被本仓库两轮实测证伪。给每个分片任务加起止毫秒时间戳日志（`doFirst`/`doLast` 打印 `System.currentTimeMillis()`），并发性可随时审计，出问题也不用猜。

分片任务必须各自独立沙盒目录（`testIde.register("testShardN") { sandboxDirectory.set(...) }`），这是前提不是优化——默认沙盒共享就是上面 PersistentFS 互踩的根源。

### 2. 分区算法：按历史耗时做贪心均衡

按类名哈希分区只保证「类数接近」，实测两片失衡 26%（157.9s / 93.7s），并行墙钟被重片拖死。改成：

- 权重 = 扫 `build/test-results/` 下全部结果目录（串行 `test/` 与各分片目录都要扫）的 `TEST-*.xml`，同类取 mtime 最新那份——**串行与分片互相喂养**，跑得越多权重越准；
- 无历史数据的类（新增测试）取已知权重的中位数，全新检出零数据时全体同权 → 退化为按类名字典序贪心，仍然确定性；
- 贪心：按 `(时长降序, 类名升序)` 排序，逐类放入当前最轻的片；
- 结果：两片 125.8s / 125.8s，三片 83.9s × 3（模拟值与实测吻合）。

两个附带事实：① 分片跑出的单类耗时因并发争用会比串行膨胀约 30%，但均衡度保持，不影响决策；② 分区在配置期计算，与配置缓存/类发现同语义——新增测试类、耗时变化在下一次配置失效后生效，短暂失衡可接受，不影响正确性。

### 3. 并行度取核数一半

6 核 12 线程实测：2 片 2m54s、3 片 2m06s、4 片未测（预计争用抵消）。**CPU 密集 + 每片 JVM 冷启动 + 沙盒索引开销**三者叠加，最优值在物理核数一半附近的 3 片。片数做成属性（`-PtestShardCount=N`）便于机器变化时重测。

### 4. 计数 parity 要能一眼看见

聚合任务 `doLast` 汇总各片 XML，打印每片与总数的 `tests/failures/errors/skipped`。没有这一行，「分片跑完到底跑全了没有」就得手工拼目录；有了它，`SHARD TOTAL: tests=4081 ...` 与串行口径对齐即可判绿。注意聚合报告里不要引用脚本顶层函数（`doLast` 引脚本对象会让整段不可序列化，配置缓存直接报错），把解析helper写在 `doLast` 体内。

### 5. 机器级全局资源要亲和到同一片

并行的新失败面来自「进程间争用全机唯一资源」。本仓库实例是 Windows 剪贴板（`WClipboard.openClipboard` 全机互斥）：并发分片时两片各自调 `Toolkit.getDefaultToolkit().systemClipboard` 互抢，报 `cannot open system clipboard`，表现为随机 1 例假失败（就是假失败清单里「剪贴板 flake」的并行放大版）。

对策不是改测试，而是**在分区阶段把碰这类资源的测试类固定到同一片**（片内串行天然无争用）：配置期扫测试源码，含 `CopyPasteManager` / `systemClipboard` 的类全部塞进第 1 片。同类待办清单：本地端口、临时文件固定路径、全局锁文件、系统输入法状态——凡「全机唯一」的资源都该进这张亲和清单。

## 五、提速之外的三个真问题（都值得单独记住）

1. **`org.gradle.caching=false` 写在项目 gradle.properties 里可能根本不生效**：Gradle 属性优先级是 `GRADLE_USER_HOME > 项目根`，用户级 `~/.gradle/gradle.properties` 里的 `org.gradle.caching=true` 会静默覆盖项目设置。本仓库「关闭 build cache」这项防假失败措施因此空转了整整一天（冷启动跑出 `5 from cache` 才暴露）。修复=把关闭动作落 `settings.gradle.kts` 的 `buildCache { local { isEnabled = false } }`（settings 配置优先级高于属性文件）。同理 `org.gradle.jvmargs` 也被用户级覆盖，daemon 实际只跑用户级那套参数。
2. **分片类发现不能假设「文件名 = 类名」**：Kotlin 允许文件名与类名不一致（本仓库 `CrudPreviewFlowAndTypesTest.kt` 里装的是 `class DbTypeQuoteHintTest`），按文件名推导 FQCN 会漏掉这些类——症状是分片跑完总数比串行少 3，非常难查。改为从源码内容提取列 0 的顶层 `class` 声明（带常见修饰符前缀），无声明时回退文件名。
3. **权重与计数依赖结果目录，要警惕陈旧 XML**：`build/test-results/` 是增量目录，上一次跑全量的 XML 会与本次混在一起（Gradle 不清理未执行的套件），手工聚合计数或取权重时会算进去。跑权威计数前先清目录，或按 mtime 过滤。

## 六、落地清单（新项目照抄）

1. 分片任务：`testIde.register("testShardN")` + 各自 `sandboxDirectory` + `filter { includeTestsMatching(...) }` + classpath 补 `sourceSets["test"].output`（IPGP 只给默认 test 任务配这个）。
2. 聚合任务：`dependsOn` 全部片 + `doLast` 打印各片与总数四元组。
3. 分区：内容扫描类名 → 历史 XML 权重 → 亲和类归位 → 贪心均衡；片数做成属性。
4. 开 `org.gradle.parallel=true`，并在 build cache 关闭这类「必须生效」的开关用 settings 层而非属性文件。
5. 计时方法：warm（至少第二次跑）对比，串行与并行同机同码各跑一轮落档；测试执行时间从 XML 聚合取，命令墙钟用 `time` 包。
