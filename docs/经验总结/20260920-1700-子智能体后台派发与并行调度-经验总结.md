# 子智能体后台派发与并行调度 — 经验总结

- 来源：2026-09-20 验收问题修复轮。用户连续两次指出「每次起多个子智能体都只启动了一个」，随后要求「子智能体不要阻塞主任务，等子智能体完成后反馈即可」。
- 结论：**并行靠后台派发，不靠一条消息塞多个调用**。本文件是可复用操作手册。

## 一、实测定位：为什么「只启动了一个」

我在一条 assistant 消息里写多个 `Agent` 调用（写了「同一条消息发三个」），**实际只产出一个**——连续三轮都是如此。工具文档说支持一条消息多个 tool use，但模型侧产出不可靠。

**可靠配方**：**每个 `Agent` 调用都加 `run_in_background: true`，逐条派发。**
- 后台 agent 派发后立即返回，主任务立刻继续；
- 第一条在跑的同时派第二条 → 两条**真正并发**；
- 完成时各自发 `<task-notification>`，不阻塞、无需轮询。

即：**并行度来自「后台」，与「一条消息塞几个调用」无关**。想并发就 background，别指望批处理。

## 二、派发前三条硬检查

### 1. 写集（write_set）必须显式声明并两两求交

- 交集为空 → 可并行；**交集非空 → 必须串行**（同一文件两个写者＝丢更新）。
- **本轮实例**：P1（预览恒降级）、P5（meta 行接通）、P6（tooltip 覆写）三个缺陷全落在 `ui/SqlPreviewPanel.kt` → 只能**一个 agent 一次改完**，派三个必然互相覆盖。
- 只读 agent（Explore、复核）write_set = `[]`，**永远可并行**。

### 2. 主任务要有一条不重叠的车道

派完不要空等。本轮派完三个后台 agent 后，主线程同时写了修复计划文件、回填了问题清单——零等待。

### 3. prompt 必须自包含

后台 agent **无法向你提问**。prompt 要写清：目标 / 输入 / write_set / 依赖 / 验收标准 / 返回格式 / 是否允许改码。
不确定的事先派**只读侦察**（Explore），拿到结论再派实施——本轮 P1 的根因就是先派只读调查拿到的（`SqlPreviewPanel.kt:2509` 用引用相等比较两个不同 `Pair` 实例，判定恒假 → 永远回落内存 PSI）。

## 三、收口协议

| 事项 | 做法 |
| --- | --- |
| 等结果 | **不轮询**；后台 agent 完成会自动通知。`TaskOutput` 会阻塞，只用于「用户要求等待」 |
| 读产物 | **不要读 local_agent 的 `output.txt`**——它是完整对话的符号链接，读它会爆上下文 |
| 回报格式 | 要求子代理压缩为「状态 / 产物 / 证据 / 是否通过」，禁止回传完整对话 |
| 独立复核 | **写与验分离**：另派只读 agent 复核「声称的修法是否真解决问题」「契约有没有被改坏」，复核结论回来才提交 |
| 门禁 | 主线程在复核回来后跑全量（`testShards` + 子项目），全绿才提交 |

## 四、反面清单（本轮踩到或差点踩到）

| 坑 | 现象 | 规避 |
| --- | --- | --- |
| 只发一个调用 | 以为在并行，实际串行 | 一律 `run_in_background: true` |
| 同文件多写者 | 两个 agent 改同一文件 → 丢更新 | 派发前求写集交集，非空即串行 |
| 主线程空等 | 派完就盯着等通知 | 先给自己排一条不重叠车道 |
| 后台 agent 提问 | 无人应答 → 自行发挥或卡住 | prompt 自包含；先只读侦察 |
| 拿自述当结论 | agent 说「已修好」未必真跑过测试 | 复核 agent + 主线程跑全量门禁 |
| 门禁盲区 | 子项目测试不在主门禁里，平时不跑 | 本轮发现 `:sql-visualizer-agent:test` 65 例不在 `testShards` 内，需单独补跑 |
