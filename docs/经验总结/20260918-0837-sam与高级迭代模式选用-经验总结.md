# sam 与 advanced-iterative-mode 选用经验总结

> 分析基线：2026-09-18，基于本仓库已加载的两个技能原文（`sam`：ZCode 原生 Subagents 多角色调度 v3；`advanced-iterative-mode`：ZCode 高级自迭代模式）。
> 本文沉淀「开发时何时该用哪个 / 何时该两个组合用」的判定方法，供后续任务开工前对号入座，不重复两个技能的原文机制（原文见各自 SKILL.md）。

## 一、一句话定位

**advanced-iterative-mode 是决策与统筹层（大脑），sam 是执行调度层（手脚）。**

- **sam 解决「任务怎么分派人去做」**：拆子任务、五维评分路由思考等级、按写集交集判定串并行、写验分离、失败回交。它假定「方向已清楚、验收标准已明确」，不负责「该不该做、方向对不对」。
- **advanced-iterative-mode 解决「为什么做、方向是什么、全局怎么布」**：金蝉脱壳·羽化成蝶消化分歧、先收集数据核实因果、失败信号转化、全局战略节点锁定、长期自迭代。它回答 sam 不回答的问题。

判断信号一句话：**有执行疑问（怎么分配/并行还是串行）→ 开 sam；有方向/因果/分歧疑问（该不该做/为什么/选哪条路）→ 开 advanced-iterative-mode。**

## 二、单独用 sam 的适用场景

同时满足就开 sam，不必开高级模式：

- 任务**边界清晰、验收标准明确**，不需要重新论证方向。
- 可拆成多个**写集可判定交集**的独立子任务，靠并行提效。
- 需要**独立复核**（写验分离防自嗨）。
- 目标是「把明确的活快速、可靠干完」。

典型：实现多个互不相关的功能模块、分片编码 + 交叉验证、一批独立的 bug 修复、按文档三处同步落地一批改动。此类任务开高级模式是浪费——没有方向分歧要消化，只有执行效率问题。

## 三、单独用 advanced-iterative-mode 的适用场景

满足这些就只开高级模式，别贸然派子代理：

- **方向不明 / 有分歧 / 有难点批评**，需要金蝉脱壳消化，而不是直接选边。
- **状态不明或数据不足**，必须先收集信息、追根因（如复杂 bug 的因果链）。
- **高风险不可逆决策**（核心模块上线、重构类 7-10 分的高危活）。
- **需要长期自迭代打磨到满意**、全局统筹布局。

共性：把「想清楚」作为前提。方向未定就并行，方向错了并行越多错得越多。高级模式自带智能体群编排（帝王/辅政级递进），需要多智能体的复杂战略任务它内部能管，不依赖 sam。

## 四、两个一起用的场景

任务「**大而复杂，既有方向决策、又有大量独立执行**」时，分阶段组合：

1. **先 advanced-iterative-mode 定方向**：金蝉脱壳处理分歧、核实因果、锁定战略节点、定下「做什么/为什么/验收标准」。
2. **再用 sam 拆包执行**：把消化好、验收已明确的子任务按写集判定并派子代理并行。
3. **每轮回 advanced-iterative-mode 复盘**：追凶闭环、失败转化、全局微调，再进下一轮。

即 advanced-iterative-mode 主持**总循环**（每轮定位—复盘—转失败），sam 在每一轮里负责**战术性并派与复核**。判断信号：任务同时含「需想清楚的方向问题」和「想清楚后有一大批可并行的执行块」。

## 五、本项目对 sam 并行的硬约束

AGENTS.md 里的并行铁律与 sam 默认并行上限（2 个活动子代理）要叠加理解，不能反向膨胀：

- **子代理并发上限 ≤3**：单会话 4 路 general-purpose 并行会触发账户 1302 限流（代理失败且可能零产出）。sam 默认上限 2 已在该红线内，实际派发不得超过 3。
- **跑 `./gradlew` 前先 `python C:\Users\USER\.zcode\cli\parallel_tasks.py check`**，有活跃任务先 `register --name ... --sandbox ...` 登记。sam 的派发前检查应把 parallel_tasks 登记纳入流程。
- **并发代理互读在途产物会报「生产 API 未落位」假告警**——基础件先落、依赖方后派，收口以最终编译门禁为准。
- **协作写集尽量扁平分支名**（不带 feature/ 前缀），本地独有分支尽快 push 留底。

因此本项目里 sam 的并行红利比纯通用环境打折扣，更依赖「先想清楚、减少迭代轮次」省 token。
