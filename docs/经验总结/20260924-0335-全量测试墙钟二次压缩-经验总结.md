# 全量测试墙钟二次压缩经验总结

> 基线：2026-09-24 T-TestPerf4（分支 t-testperf4，工作树 mpsv-testperf4）。
> 前情：2026-09-15 两轮提速（见 `20260915-0900-插件测试套件提速-经验总结.md`）把全量从串行 4m47s 压到一命令并行 2m05s（当时 326 类 4083 用例）。此后四周测试规模涨到 519 类 5902 用例，warm 全量回到 3m57s。本轮在**零用例删减、零断言改动、零测试源码改动**纪律下压回 3m16s~3m28s。
> 完整逐跑台账与裁决细节见 `docs/开发计划/20260924-0240-T-TestPerf4-全量测试墙钟二次压缩-开发计划.md` §六。

| 配置 | warm 墙钟 | 备注 |
| --- | --- | --- |

## 二、本轮最有价值的三个认知

### 1. 分片数的「定案」有保质期，过期判据是负载形态

2026-09-17「3 片最优、4 片反而慢」的复测结论，当时的边界是**片内执行 ~84s 量级**——每片一次的固定开销（测试 JVM 冷启+沙盒准备 ≈17s）占比高，片数越多固定开销×片数越亏。四周后片内执行涨到 210s 量级，固定开销占比从 ~17% 掉到 ~8%，同一个实验跑出了相反的拐点（4 片 3m16s vs 3 片 3m57s，5 片才回劣）。

教训：性能调参结论跟着当时的负载画像走，测试规模大幅增长后（本仓节奏约每月 +40% 用例）应当重测片数。判据不用背——「固定开销占片墙钟的比例」跌破两成就该把片数往上再探一档。

### 2. 配置缓存对配置期目录列举做输入追踪——「权重每轮生效」的机制被实证

分片权重的痛点之一是「配置缓存命中会不会冻结分区」。本轮用连续两跑直接裁决：run2 启动日志打出 `configuration cache cannot be reused because directory 'build\test-results\testShard1' has changed`——配置期 `listFiles` 枚举的结果目录被 Gradle 记为配置输入，目录内容一变（每轮测试结果落盘）就触发配置期重算，权重天然逐轮刷新。

推论两面：①依赖「配置期扫描结果目录」的方案默认是新鲜的，不需要手工 stamp；②反过来说，配置期扫大目录的写法有隐性重算代价——目录内容每次构建之间变一次，配置缓存就废一次，本项目此处只读几百个 XML 的头部 8 行，可忽略。

### 3. buildSrc 改动（连注释）会让下次构建付出约 2 分钟重编代价

计时实验期间改了一行 buildSrc 注释，下一跑立刻从 3m25s 变 5m21s（buildSrc 13 任务重编 + 主构建 classpath 变化连带 prepareSandbox 等 11 个任务重跑），与「新代码首跑」的形态完全一致。两跑台账（run6/run8）互为印证。

实操推论：改构建脚本（哪怕纯注释）与改生产代码一样是「会变冷」的操作；计时对照实验之间不要夹带任何 buildSrc 改动，注释补记集中在实验收尾一次性做。

## 三、本轮落地的三个编排增强（都在聚合报告层，零测试改动）

1. **预期 vs 实测对照行**：配置期把权重表算出的各片预期 execSum 经 `inputs.property` 固化成 String，聚合时与实测并排打印（`time=190.7s expected=162.8s`）。偏差持续偏向同一片=权重失准信号；±7% 内随机分布=并发膨胀噪声（分片跑出的单类耗时比串行膨胀且各片随机，均衡器追不动也不必追）。
2. **计划类并集 parity 校验**：各片结果 XML 的类名并集必须覆盖配置期扫描出的计划全集，缺失打 WARN 明细。T-TestPerf2 曾实证过类发现漏 3 类的形态（总数悄悄变少极难察觉），这道校验把「分片跑全了」从人眼对数变成自动断言。抽象基类/测试全在嵌套类的形态会误报，故 WARN 不 fail。
3. **权重平滑**：同类从「mtime 最新 1 份」改为「最新 K=2 份取中位数」（`-PtestShardWeightSamples`），削单轮膨胀毛刺。

传数据进 doLast 的固定套路（配置缓存约束）：配置期把值固化为 String 写进 `inputs.property`，doLast 从 `inputs.properties` 读回——doLast 引用脚本顶层对象/函数会让整段不可序列化（T-TestPerf2 实证），`testDatabase` 的 `mpProjectDirAbs` 与本轮两份计划数据走的是同一条通道。

## 四、已销账的维度（别再试）

| 维度 | 结论 | 出处 |
| --- | --- | --- |
| 测试堆加大（-PtestHeapSize=2g） | 无收益 | T-TestPerf2 |
| GC 换型（-PtestGc=parallel，开关保留） | 无收益（<5%） | T-TestPerf4 run7 |
| 5 片 | 回劣（并发膨胀 +25% 吃掉切分收益） | T-TestPerf4 run4 |
| 默认 test 多 fork / 纯逻辑桶进全量 / 片内再并行 / build cache | 不可行 | T-TestPerf/2/3（见 20260915 总结 §三） |

## 五、下一个自然瓶颈（未立项，登记备查）

warm 口径下墙钟 ≈ 关键路径片墙钟（前置段仅 ~10s），而 execSum 总和 601s 里最重类 SqlPreviewPanelTest 单类 42.6s（72 用例，占均片负载 22%）。类是分片的原子，单类内部无法切——这个量级再往下压只剩两条路：测试实现层（改测试代码，撞红线，不做）或方法级调度（平台测试框架不支持）。当前 3m16s~3m28s 就是调度层在不碰测试效果前提下的合理水位。
