# 全量测试墙钟九次压缩 经验总结（T-TestPerf11，2026-10-01）

> 前置说明：系列文档「二次~七次」对应 T4~T9；T10（八次）只有计划文档与实施记录、经验总结缺篇（dev 侧文档债，本轮代为点名）；本篇为第九次。任务出处：用户令「压缩全量测试时间、测试效果不能变、不能删减测试用例」，实施树 `mpsv-t11-perf` 分支 `t-testperf11`（基 dev `18ad110` 含批次 9）。计划=`docs/开发计划/20261001-0253-T-TestPerf11-全量测试墙钟九次压缩-开发计划.md`（§六为逐轮台账）。

## 一、结论先行

1. **墙钟没有可收割的大空间了——这句话本轮用数据再次确认**。dev tip +批次 9（6341 例，比 T10 多 156 例）今晚 off 带 2m38s~2m53s，落在 T10 历史带 2m38s~3m12s 的快端；批次 9 的增量成本被画像体系直接吸收，没有出现 20260929 那种 +13.7% 失衡破带。
2. 本轮真实交付的不是墙钟，而是三件防护性资产与两个 P1 交接：
   - **画像刷新闭环首次真实演练**：双告警首次触发（R1b/R2 shard2 超预期 +17%/+15%）→ weight-refresh 从干净轮刷库 → tsv 548→559 类（批次 9 全量入画像），顺带纠偏旧画像的 init 伪象条目（AcpTransportIsolationTest 17.511s→0.153s——单轮画像被「谁排在分片第一个谁吸收 bootstrap」污染的活标本）。
   - **组合旋钮证据补齐**：`testGcThreads=2 × testTieredStop=true` 同窗交错实测 execSum −5.7%（T9 两个单旋钮 −2.5%/−2.4% 确实可加），但墙钟 2m38s=2m38s 与关态完全打平——T9「线程面路线彻底销案」维持，组合证据行已补。
   - **协议升级**：轮前预检从「登记表+docker」扩为「登记表+docker+Commit 余量」（夜间 Commit 基线已达 63GB/74.7GB，冷跑的编译税+5 JVM 出生会顶破上限，R0 三 JVM 原生崩 + R1 一执行器出生冻结皆此因）。
   - P1 交接 A：**dev tip 既有红 ×3**（批次 9 未过全量门禁的遗留，含一个守卫没跟上菜单新项、一个死常量、一个被解析器骨架触发的标注断言）。
   - P1 交接 B：**SqlPreviewServiceBatchTest 顺序依赖隔离泄漏**（5 例 upsert/引用断言，隔离复绿 29s，权重变化改装箱顺序即间歇暴露）——**全量门禁的失败集合从此是顺序敏感的**，这比任何一个 P2 性能项都更值得先修。

## 三、新沉淀的机制认知（照抄给下一轮）

1. **「告警→刷新→自愈」的 attribution 要拆开说**：树内后续轮的均衡改善来自本地 K=2 数据覆盖（两轮即全覆），tsv 刷新对树内零增量；它的价值全部在**未来树**（新工作树冷启动、新批次合入时）。把闭环收益记在刷新头上是夸大，把刷新说成无用是短视——正确说法：告警体系负责「看见」，本地数据负责「本树自愈」，画像负责「别家树第一轮就位」。
2. **超预期告警在漂移窗会常态化误鸣**：execSum 夜间 689→726s（+5%）漂移下，临界片 +15~22% 超预期 WARN 连发 4 轮，但逐类偏差并无失准——告警判据（10%/12%）与窗口漂移带（±5~8%）的间距比设计时更窄，读告警先看 execSum 是否同向上漂。T10「六轮零误报」的口径要加上「漂移窗除外」。
3. **testShard2 结构性临界（开放观察，证据升级）**：连续 6 轮 shard2 恒任临界（+14~22%），类清单每轮全换、清空沙盒后依旧、五片 START 仅差 3ms——权重失准与容器毒化双双排除，指向按启动顺序的 OS 调度/核分配类因素。T10 曾记「shard2 连续临界 +18~22% 判为权重追尾」，本轮数据把「与权重无关」钉死。若未来可证并根除，墙钟预估 −15~20s（≈地板再下探 10%）；仓内合法杠杆暂无（改任务启动序属 hack）。**下一轮接手者第一件事可以是用「对调 shard1/shard2 类清单」的临时补丁做一次定向验证**——若临界跟着类清单走则权重问题，若留在 shard2 则环境问题，一轮就能定案。
4. **组合旋钮的诚实裁定路径**：execSum 显著（−5.7% 同窗交错可复现）+ 墙钟零增益 = 不转正。墙钟被临界片钉死的形态下，任何「总量降、临界不降」的优化都过不了墙钟判据——**先攻临界片构成，再谈总量**。
5. **失败证据生命周期纪律的两次兑现**：R0 崩溃轮先拷 hs_err 三件再清场；R3 泄漏轮先提失败报文再跑下一轮——两次都在「再跑一轮就没了」的边缘拿回了证据。
6. **官方聚合报告会被红任务压制**（testShards doLast 依赖分片全过）：既有红存在期间，聚合公式（mtime 闸+失衡/超预期判据+parity）要有一个仓外替身（本轮 python 聚合器，未入库）。这也是「守卫类工具的可用性不能依赖被测对象全绿」的一个注脚。

## 四、环境与协议账

- 夜间 Commit 基线 63GB/74.7GB（余量 10GB）时：冷跑必崩（编译税 ~2.5min + 5 JVM 出生），编译 warm 后可稳定跑完。**「跑全量前查 docker」之外再加「查 Commit 余量」**；余量 <12GB 时避免冷跑类重活。
- 僵死执行器（JVM 出生冻结、零 CPU、86MB WS）处置：杀 gradle 客户端→daemon 断连自动取消构建→执行器随构建回收；先核父子链再动手（本轮：执行器父进程=服务本树的 daemon）。
- gradle-gate.ps1 双槽闸门 + parallel_tasks 登记是两套互补信号量：登记表防「会话级撞车意图」，闸门防「机器级并发超额」，CPU 采样探针防「登记了但没跑/跑完没注销」的假信号——本轮 b9gate 会话占着登记条目 80 分钟实际零构建，全靠探针确认了真实空闲窗口。

## 五、留给后续的入口（按优先级）

1. **P1 修 dev tip 既有红 ×3 + 批次 9 全量门禁补跑**（b9gate 会话当时疑似正在做此事）。
2. **P1 SqlPreviewServiceBatchTest 隔离泄漏定位**（污染源疑经配置/缓存单例，本轮 grep 未命中显式写点；修法=前序类 @After 还原或泄漏点收口，属测试源码小改，需业主授权红线口径）。
3. **P2 shard2 结构性临界定案**（对调类清单的一轮定向验证，见 §三.3）。
4. **P2 超预期告警的漂移窗豁免**（execSum 环比上漂 >3% 时把判据从 10% 放宽到 15%，或改判据基准为「同轮各片相对散布」）。
5. **P3 线程面组合 exec 效应的用途**：墙钟判据下无用，但「execSum 峰值」若成为新指标（如 CI 计费/并发窗口）可复测转正——留证据不立项。
