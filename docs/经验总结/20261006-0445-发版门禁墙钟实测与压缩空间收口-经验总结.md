# 发版门禁墙钟实测与压缩空间收口（T-ReleasePerf6）经验总结

> 2026-10-06，分支 `t-releaseperf6`（基于 dev `1ce4472`）。计划与全量台账：`docs/开发计划/20261006-0244-T-ReleasePerf6-发版门禁墙钟压缩-开发计划.md`。
> 结论先行：**本轮零压缩落地——但把「为什么压不动」用读数钉死了**。releaseGate 13m11s 的构成里，testShards（T15 已至地板）、e2eFakeIde（24~45s）、verifyGate（verifier 进程内已并发三目标）全部排除后，唯一长杆是 verifyMarketplace 的在线解析（冷 873s / warm 589s），而它的一切缓存类提速都在动语义（在线 freshness 正是这道门禁的本体）。交付物＝门禁四环节 START/END 毫秒锚点（永久测量能力）+ 全环节分解台账 + 六项候选杠杆的证据化销案 + 语义锁定下的地板声明（**authority 终轮实测 683s=11m23s 全绿；常规争用窗 ≈13min**）。

## 六条认知

1. **「拆进程加并行」动手前要先证明被拆方真是串行**。L1（verifyGate 三目标拆三进程）立项于文档口径「一个串行 check-plugin 调用」，首轮实测即证伪：verifyGate 墙钟 252.9s，三目标完成时刻 169.7/239.9/246.1s——串行应合计 655.7s，verifier-cli 1.410 进程内本来就并发跑多目标。拆进程零增益，还白添 3× JVM 内存（当日窗口 Commit 已到 73GB）。文档注释描述的是写代码时的意图，不是运行时行为；耗时锚点读数才是权威。

2. **mustRunAfter 只钉任务名，不钉依赖闭包**。`testShards { mustRunAfter("verifyGate") }` 钉的是聚合任务，五个分片叶子任务无序约束、在 buildPlugin 动作还没结束时（START 424186 < END 424599）就被调度器放行。真实 DAG＝叶子浮动全并发，总墙钟 ≈ max(各长杆) + e2e——这解释了为什么 13m 里测试窗口只「出现」一次。按文档心智模型做编排推演会全错，锚点时序是唯一可信地图。

3. **在线门禁的 freshness 就是语义本体，压它=改语义**。verifyMarketplace（在线+无豁免+按 verdict 文本判）的 warm 588.7s 里，verifier 自带缓存只省三分之一（冷 873s）；剩余部分每次都要对 Marketplace 实时状态求值——可选依赖新发布会改变判定，这正是它区别于离线 verifyGate 的存在意义。按 commit 复用 verdict、缓存元数据 TTL、home 迁移共享，要么动判定语义要么收益为零。verifier-cli 旗标扫描确认无缓存/预取类参数。「压缩不了」的结论要靠排除法证据链钉死，不能凭感觉放行。

4. **两份全量门禁叠跑必然顶格 OOM**。R2（作废轮）Commit 冲到 74.69/74.7GB：测试执行器 OOM + 打不开平台发行文件 + 代理链路 SSL 断连成片失败。事后对协调登记表才发现与另一会话的 k2j 全量收口（t-synck2jm29）完全重叠。「构建并发上限 2 路」定例的适用面是 testFast 级双路，**两份 releaseGate 级全量互斥**；跑全量前不仅要查登记表，还要看活跃条目是什么类型的任务。

5. **管道吃退出码会伪造「绿」**（再次踩到）：`./gradlew releaseGate | grep …; echo $?` 取的是 grep 的退出码，R1 实为 BUILD FAILED 却读出 EXIT=0。长命令一律 `> log 2>&1; echo EXIT=$?` 全日志落文件，判定读日志不走管道。同族陷阱：grep 遇 verifier 输出里的二进制字节会静默按二进制文件处理，加 `-a`。

6. **冷树首轮的一次性税要拆账**：新工作树首轮 releaseGate 含 buildSrc 编译税 + verify-home idb 冷建 + marketplace 元数据全量下载（三项目标 873s vs warm 589s，税 ≈284s）；另 verifier 对多目标是并发分析，冷建的 idb 在三目标间摊薄。冷/暖、争用/独占是两个独立变量，对比读数必须同窗交错配对，混着读会把缓存效应误读成争用效应。

## 地板声明（供后续轮立项对照）

- releaseGate 语义锁定（五环节一个不少）下的地板：**authority 终轮实测 683s（11m23s）全绿**（暖窗低争用：marketplace 674.3s 长杆 + 门禁 238.2s/分片窗 209.5s 并行 + 编译链 ≈46s + e2e 28.5s）；常规争用窗 ≈13min（v2026.10.6 发行日 13m11s 同语义对读 −108s，差异全在 marketplace 争用窗）。同语义再往下压只有两条路：给 marketplace 减工作（=改语义）或给全链减环节（=删内容），均被红线封死。
- 操作面三条已知成本（非代码可解）：①两份全量门禁互斥（叠加即 OOM，R2 实证）；②clean/新工作树后的首轮多付 ~5min 冷启动税（marketplace 元数据 + idb 冷建），发版日复验前勿 clean；③agent 退避竞速 flake 家族一旦在门禁窗口命中，代价是整轮 12~15min（SenderLoopBackoffTest 本轮实证：隔离复跑 11s 绿）。
- 本轮反向验证留痕：S1 仪表化四锚点在 R1/R2/authority 三轮全数在场；`-PverifyOnly=true` 复用发行包路径可用（W1 即走此语义，39s 级 re-verify 能力在案）。
