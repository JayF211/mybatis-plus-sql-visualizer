# 子智能体测试分层与收口时序 — 经验总结

- 来源：2026-09-22 会话。用户点出多子智能体并行里的三个浪费点——「子智能体先定向再全量、有时候还构建测试、有时候还休眠等待几百秒」——要求改成：**子代理只跑定向测试，全量等所有子智能体完成后单独派一个智能体跑，主智能体同时写文档收尾，构建测试只有大改动或发版前才跑**。同轮追加两条：**实施过程中及时更新待办清单**，不许实际进度与清单进度脱节；**长命令一律用后台任务启（`run_in_background`），不要 sleep**。
- 结论：把「跑什么测试、谁来跑、什么时候跑」固化成**三档分层**，并把收口期从「空等门禁」改成「门禁 ∥ 写文档」。

## 一、三档分层

| 档 | 内容 | 谁跑 | 何时 |
|---|---|---|---|
| 定向 | `./gradlew test --tests "<FQCN>"`；纯逻辑改动用 `testFast`；触达 Database 链加该链定向类；agent 子项目改动加 `:sql-visualizer-agent:test` | 每个实施子代理自己 | 改完即跑，随实施报告交出 |
| 统一全量门禁 | `testShards` 打底；`testDatabase` 与 agent 子项目**按触达面加跑** | **全部子代理完成后单派一个只读收口代理**（write_set 为空、按并行登记表用独立沙盒） | 与主控写文档收尾**并行** |
| 构建校验 | `verifyGate` / `verifyPlugin` / `verifySmoke` / `buildPlugin` | 派活方统一跑一次 | **仅大改动或发版前** |

「大改动」判据写死为四条：动了 `build.gradle.kts` 或依赖版本、动了 `plugin.xml` 的 EP 或 since-build、引入新平台 API 面或反射入口、新增 MCP 工具声明。纯业务代码小修不跑第三档。

## 二、为什么子代理不该跑全量

- **并行期读数不可信**。多路共用一棵工作树时，别人在途的改动会让全量成片失败——本仓 2026-08-20 那批 11 项并行里，`#6 LogSmartGroup` 的「全量 30 个 NoSuchMethodError」就是 `#5 ParamBulk` 正在改 `SqlPreviewPanel.kt` 造成的，与 #6 毫无关系。这种读数既不能作为交付证据，又要花时间排障。
- **墙钟成倍拉长**。每路一次全量（`testShards` 三片约 2 分钟，加上集成与子项目更久），N 路就是 N 倍，而这些跑的其实是同一份代码的同一套用例。
- **构建校验的判别力不随次数增加**。`verifyGate` 要解包平台发行版跑三目标兼容检查，单次数分钟；各路文件面本来就不相交，校验是整体性的，放最后一次既省时又不丢覆盖（2026-09-20 第九轮七项批次的实测读数支撑这一点：全部并行结束后**唯一一次**收口跑出 testShards 5486/0/0/6 + testDatabase 10/0/0/0 + agent 58/0/0/0，verifyGate 三目标全 Compatible，未因省这几次而丢覆盖）。

## 三、收口时序：门禁与文档并行

```
所有实施子代理完成 → 派只读收口代理跑全量门禁（后台）
                      ↘ 主控同时写文档：验收文档 / 变更记录 / 计划 §实施记录回填 / CHANGELOG
                      ↘ 收口代理回报读数 → 主控填判定卡 → 提交
```

两条红线：

1. **收口代理只读**（不改码、不提交），并且按并行登记表 check/register 自己的独立沙盒。
2. **收口期间主控不得碰 `src/main`**——包括「回填计划时顺手改码」。只要动了生产代码，那道绿立刻过期，必须复跑；独立复核判出的 blocker 若修复落在 `src/main`，同样触发复跑。

## 四、长命令用后台任务启，不用 sleep 等

用户点名的「休眠几百秒」是负收益：子代理持有并发槽位，睡着的时候既解决不了锁，也堵着别的活儿。规则分两层：

- **命令层**：全量测试、构建（`testShards` / `buildPlugin` / `verifyGate`）、`runIde`、依赖安装这类长命令，一律用 Bash 工具的 `run_in_background: true` 启动；后台任务跑完会自动发通知，主线程立刻去干别的（写文档、读代码、改自己写集内的文件）。**不要前台跑完再 `sleep`，也不要用 `sleep` 轮询**；确实需要结果时才用 `TaskOutput` 等待。
- **冲突层**：撞上锁、或撞上并行会话的共享缓存与沙盒冲突时，处置是**记录证据并交回**——把现象与命令输出写进报告，由收口阶段统一复跑。主控派完收口代理也不空等，并行车道固定为写文档。

这条对主控和子代理同样适用（子代理也拿 Bash 工具）。

## 五、待办清单要与实际进度同步

用户同轮追加的要求。清单是用户看进度的唯一窗口，开工时写一次就再不动，等于给用户一个假读数：

- 每个阶段**开工时**就把该条标 `in_progress`，做完立刻标 `completed`；同一时刻只留一条 in_progress。
- 中途冒出的新活儿（用户插话加的要求、临时发现的前置修复）立即补进清单。
- 计划变更导致某条不再需要时，删掉或改写它，别留着充数。

### 改这个脚本的编译校验方法（可复用）

本机没有全局 `tsc`，`npx tsc` 会要求先 install。可靠路线：

```bash
mkdir -p "$TEMP/dwfcheck" && cd "$TEMP/dwfcheck"
npm install typescript --no-save
# 写 facade.d.ts 桩声明工作流全局：agent/phase/log/world/files/git/args/report/artifact + GrepMatch
./node_modules/.bin/tsc --noEmit --target es2022 --module esnext --moduleDetection force \
  --moduleResolution bundler --strict --skipLibCheck dev-flow.ts facade.d.ts
```

**用改前备份跑同一命令、比对错误集**——只该剩「顶层 return 需在函数体内」这类桩造成的噪声（两版一致即证明没改坏）。判别：`TS1xxx` 是语法被改坏，`TS2xxx`/`TS1108` 才是桩噪声。

**踩到的坑**：提示词在脚本里是模板字面量，往里直接写反引号会把字符串截断——本次给实施员提示词加「只跑 `--tests`」时就报了成串 `TS1005 ',' expected` 且都指向那一行；按文件既有写法转义（`` \`--tests\` ``）即可。这条正好说明「改完必须编译校验」，否则这类语法错误会以「整个工作流跑不起来」的形式暴露。
