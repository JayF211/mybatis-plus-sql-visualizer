## 一、「改了」不等于「改对了」——四类绿灯看不出的问题

这一批六路独立复核（sam 写验分离，只读验证者）抓出四处**绿灯状态下的真问题**。四处的共同点是：改动本身写得对、测试全绿、门禁全绿，但改动**在运行时不起作用或作用面被抹掉**。

### 1. 加了防护不等于防护有效：三道膨胀闸门被一个 6 字节诱饵整体绕过

**现象**。`xml/SecureXml.kt` 的膨胀预扫设了三道上限（可见字面量声明数 ≤64、引用路径深度 ≤16、单实体展开估算 ≤65,536 字符），并有 26 例用例。复核用同一载荷（4 层 × 10 引用 × 4000 字符）实测：**不加诱饵时预扫正确拒绝（chars=65537），加 6 字节诱饵后预扫 PASS，JDK 实际展开 40,000,016 字符**。

**为什么绿灯看不出**。子集切分用的是 `indexOf("]>")`——它不识别引号、注释、处理指令。诱饵 `<!ENTITY decoy "]>">` 置于子集首行时，切出的「子集」没有闭合引号 → 声明正则 0 命中 → `declarations.isEmpty()` **直接早退**，三道上限一条都没执行。用例全是「合规样本通过 / 超限样本拒绝」，而诱饵形态**不在任何用例的构造面里**——防护代码被执行了，只是被绕过去了。

**怎么发现的**。复核方构造了「同一载荷、只加诱饵」的对照实验，直接读 JDK 的真实展开量。

**判据/命令**。
- 判据：任何「静态预扫/估算」类防护，必须有一条**「防护被绕过」的反例用例**，而不只有「超限被拒」的正例。
- 本轮的落点：`SecureXmlTest` 的 `实体值里的子集结束符诱饵不放行` / `注释里的子集结束符诱饵不放行` / `处理指令里的子集结束符诱饵不放行`（`SecureXmlTest.kt:321-365`，诱饵构造器 `laughsWithDecoy` 在 `:585-587`）。
- 修复后处置扩为 **7 项**（计划 §九 T-XDH-07 逐条列出）：①子集切分改引号/注释/处理指令/条件段状态机 ②`] >`（`]` 与 `>` 之间带空白）此前完全不认结束符 ③`indexOf("<!DOCTYPE")` 被序言注释里的假 DOCTYPE 抢占 ④参数实体走私（`visibleSubset` 把 `%name;` 迭代替换为字面量）⑤非 ASCII 实体名不被 `[A-Za-z_]` 正则认下 ⑥⑦两条**方向相反的误报**（合法的头先声明 16 层链被 `visiting.size >= 16` 误拒；子集内处理指令里的 `<!ENTITY …>` 文本被误当声明）。
- 附带订正：实施方自己原先在计划里写的两条结论（「字符数上限不受影响」「对真实攻击判据充分」）**均被实测证伪**——三项判据只对**可见**声明有效，且不管文档总展开量（实测 `<!ENTITY big "y"×65,536>` 正文引用 100 次 → 展开 6,553,616 字符放行，兜底是 JDK `totalEntitySizeLimit`=50M）。

### 2. 加了透传不等于透传到达：30 处透传里 2 处被同函数外层 `runCatching` 立刻接住

**现象**。T-FatalPassthrough 在 3 个文件 30 处 `catch (…: Throwable)` 块首加了 `if (FatalErrors.isFatal(t)) throw t`。其中 `execute/DataSourceSelector.kt` 的 `writeConsoleOutput` 里**有 2 处**落在这个函数的**外层** `runCatching { … }.onFailure { LOG.info("[M36] writeConsoleOutput FAILED: …") }` 之内——fatal 抛出后被外层接住，转成一条 INFO 日志，执行链带病继续。**而捕获块上方新增的注释正声称「不得被吞成日志」**。

**为什么绿灯看不出**。守卫（源码扫描）只检查「`catch (…: Throwable)` 块体内是否含 `FatalErrors.isFatal(`」，2 处判定**字面存在**，守卫绿；行为用例只覆盖可注入的缝（`AgentSession.sendConfig` 站点），`writeConsoleOutput` 当时是 `private`，注入不进去。

**怎么发现的**。复核方逐处推演捕获块的**词法嵌套**，发现 2/30 属结构性无效透传。

**判据/命令**。
- 判据：`catch (…: Throwable)` 块内加判定后，必须向上找一层**同函数内的 `runCatching`/`onFailure`/`getOrElse`/`getOrNull`**——它是独立于捕获块的抵消面，捕获块级判定管不到它。
- 反例判据：**`runCatching` 单独包住无效**（仍会发起注定失败的创建/执行，只是吞掉结果），要拦必须在动作**之前**判。
- 修复落点：`DataSourceSelector.kt` 外层 `.onFailure` 块首解包 `InvocationTargetException.targetException` 再判 fatal（`:795-807`）；同批改 `:3813`、`:3874`、`AgentManager.kt:877`（`resolvePid` 的 `.getOrElse`）、`SqlPreviewService.kt:2121`（预热链唯一调用方，否则前面两处仍无效）。
- 先红后绿实录（`FatalPassthroughTest`）：改前 `6 tests completed, 2 failed`，报文 `expected same:<NoClassDefFoundError/StackOverflowError> was not:<null>`，日志侧同时实证被吞成 `[M36] writeConsoleOutput FAILED: …`；改后同命令 `6/0/0/0`。
- 计数口径：`catch (…: Throwable)` 全仓 74 处，落地 30 处 / 3 文件，豁免 44 处 / 18 文件 → 复核整改后 **43 处 / 17 文件**（`SqlPreviewService.kt:2100` 从豁免表移入已落地表，已落地 31 处 / 4 文件）。

### 3. 顺带吃掉另一条信息：120 字符 clip 让长 SQL 的错误文本整段消失

**现象**。T-McpAuditTrail 把审计行的入参从字面量 `"ok"` 改成真摘要 `args=<摘要>`，与错误文本拼成 `<摘要> error=<文本>` 后**对整串施加 120 字符 clip**。组合串长度 ≈ `33 + sqlLen + 7 + errLen`，于是 `sqlv_explain` 的 SQL 段 **>80 字符时错误文本开始被截、≥113 字符时整段消失**——而改造前该槽位只放错误文本（独占 120 字符）。长 SQL 恰是最需要看错误原因的场景。九个静态工具因 `ok ` 前缀只占 4 字符，实质信息不减。

**为什么绿灯看不出**。`McpAuditLogTest` 的断言是「摘要被截断到 ≤120」「`summarize` 不再是死代码」——都在验**新增的东西在不在**，没有一条断言**改造前就有的东西还在不在**。

**怎么发现的**。复核方算出组合串长度公式并实测长 SQL 样例，报文里审计槽位只剩 `dataSource=demo dialect=MySQL sql=…`，92 字符错误文本整段不在。

**判据/命令**。
- 判据：任何「在既有预算内追加字段」的改动，必须有一条断言钉住**被追加字段挤掉的那个字段仍然可见**（信息回退面），而不只是断言新字段可见。
- 修法取**两段分预算**（`McpAuditLog.kt` 新增顶层 `errorArgsSummary`）：错误文本优先占预算，入参摘要让位但保留 `ERROR_PATH_ARGS_FLOOR`=16 字符保底，错误文本短时余量全部还给摘要，总长仍 120 封顶。
- **不取「error 段前置」**：前置只是把饥饿方向翻个个儿（长错误文本会把入参摘要整段挤掉），分预算下两段都不会归零。
- 先红后绿：`mcp.*` 红 `104/6`（错误路径 6 例全红）→ 绿 `104/0/0/0`（`McpAuditLogTest` 11/0/0/0）。

### 4. 守卫的假绿：整文件子串检查把「回退格式化调用」放过去了

**现象**。`McpRowBudgetTest` 的接线守卫原断言是 `tool.contains("target.maxRows")`——**整文件子串检查**。而 `target.maxRows` 在 `executeQuery` 调用处（`ExplainTool.kt:132` 一带）本来就出现，所以把格式化调用回退成 `McpExplainFormatter.format(raw)`（丢掉生效预算），**守卫仍然绿**。

**为什么绿灯看不出**。子串检查不区分「这段串出现在哪一行、承担什么职责」；只要文件里有这个串，断言就成立。测试名与断言文案都写着「接线正确」，读起来毫无破绽。

**怎么发现的**。复核方做了**证伪对照**：临时把 `format(raw, target.maxRows)` 改回 `format(raw)`，跑守卫——必须红才算数。

**判据/命令**。
- 判据：接线/调用点类守卫必须匹配**调用点的精确串**，不能用整文件 `contains`。改法是 `tool.contains("McpExplainFormatter.format(raw, target.maxRows)")`（`McpRowBudgetTest.kt:160`），执行链调用点断言另立一条各管一段。
- 命令：`./gradlew test --tests "cn.song.mybatisplus.visualizer.mcp.*"` → 回退版本必红、还原后 7 例全绿。
- 这条与主题二同源：**守卫改动必须做「回退修复 → 必须变红」的反向验证**。

## 二、守卫类改动的自证盲区（本批最贵的一课）

`convention/BannedApiSourceScanTest.kt` 新增的「初始化入口改项目服务级状态须复位」规则（`c1af0a8`，**+436/-0，仅新增**）当时叠了**四层绿灯**：自证用例绿、既有 22 例绿（新增后 24 例）、豁免计数零漂移、仓内「0 处违规」。四条同时成立，看起来是一条已经焊死的护栏。

独立验证者（只读，用 Python 复刻规则逻辑跑真样本 + 全仓扫描）判它**对真正要防的那 5 个泄漏类完全不可见**：

- 规则的**名字绑定只认 `getService(`**，而那 5 个已修泄漏类统一走 `AlreadyDisposedDiagnostics.projectService(…)`（全仓 13 处）——更讽刺的是，**那个 wrapper 的文档正是要求测试类改用它**。
- 实证：**把真实泄漏类的 `restore` 行整行删掉（原样复现修复前的泄漏）→ 规则仍 `offenders=0` 绿**；仅改写成 `manager = project.getService(...)` 才红。
- 第二条阻断：4 条通用复位令牌（`.loadState(` / `.clearForTest(` / `.clearAll(` / `.resetForTest(`）在 `SqlLogManager` 上**不存在对应方法**，且复位判定是**文件级 `contains`、不与服务对象绑定** → 另一个对象的同名复位可以把真泄漏全部洗成绿。
- 验证者另纠正一处口径：**「仓内 0 处违规」是空绿**——写命中本身为 0，它不构成精度证据，不能拿来证明规则准。

修复（`df50fb5`，+315/−41）：①名字绑定令牌扩为 `["getService(", "projectService("]`（`BannedApiSourceScanTest.kt:1744`）；②复位判定改「绑定承接名」（`hasBoundServiceReset`：`<承接名>.<复位口>(…)` 或 `SqlLogManagerProjectState.restore(<承接名>, …)`），文件级 `contains` 整块移除。**验收用「能红」实证**：删 `restore` 行 → `命中 1 处：[…SqlConsoleBridgeFilterProviderTest.kt:31 → manager.entries.dedupeEnabled =]`；把复位换成另一对象的 `resetForTest()` → 仍报 1 处；反向不丢覆盖面（`RollbackSnapshotStore` + `store.clearForTest()` → 0，去掉复位行 → 1，证明该 0 非空绿）。

**方法论（可直接复用）**：

1. **守卫改动必须用真实站点做「删掉修复 → 必须变红」的反向验证**。删掉真实泄漏类的 `restore` 行，规则必须红——这是唯一能证明「规则看得见真实形态」的实验。
2. **合成样本只能证「规则看得见我造的形态」，证不了「规则看得见真实形态」**。本轮自证用例是把合成泄漏样本混进真实扫描面，命中清单里只有注入样本——所以它绿得毫无意义。**合成样本证明规则不空转，真实站点反向验证证明规则有判别力，两者不可互相替代。**
3. **「仓内 0 处违规」在写命中本身为 0 时是空绿**，不是精度证据。精度证据只能来自「能红」的实证。
4. **守卫的绑定面要覆盖仓内主流形态**——新规则上线前先 grep 一遍「我要防的那批真实站点，用的是哪种取服务写法」。本轮的 5 个泄漏类里 `getService(` 命中数为 **0**，这就是规则失明的直接原因。

## 三、「根治」的口径怎么被证伪的（一个可复用的方法论）

T-ST-02 分片顺序依赖的 `AlreadyDisposedException`：根因在生产代码 `config/SectionConfigurable.kt` 的 `apply()` 里 `project.getService(SqlLogManager)` 写在 `runCatching` 之外，项目处于 temporarily-disposed 窗口时首次创建服务，构造期 `messageBus.connect` 抛 `AlreadyDisposedException`（extends `CancellationException`）→ 归一成 "Container is already disposed" → 穿出 `apply()` 打断设置写回。修法（`648ddb1`，把取服务挪进同一 `runCatching`）落地后被写成「根治」。

复核**下到平台字节码**把它证伪了：

- `com/intellij/platform/instanceContainer/internal/LazyInstanceHolder$initialize$1$1` 的异常表是 `from 36 to 73 → 104 Class java/lang/Throwable` / `from 90 to 101 → 104 Class java/lang/Throwable`（**无 `CancellationException` 过滤**），handler 无条件 `new CannotInitialize(instanceClass, throwable)` + `access$complete`；`tryGetInstance()` 见 `_state instanceof CannotInitialize` 即 `throw getInitializationError()`。
- ⇒ **一次创建失败就把该服务在该项目实例上永久毒化**，此后每次 `getService` 都重抛同一个缓存异常。修法只是**吞掉结果、仍发起了那次创建**，阻止不了中毒。
- 旁证来自实施方自己的诊断日志：8 条 `[T-ST-02]` WARN **全部**打印 `project.isDisposed=false` 而消息是 "Container is already disposed"——抛时 `owner.isDisposed` 必真、catch 时同一对象为假，只有「缓存重抛」能自洽。
- 复核者还在测试所用平台 jar（`ideaIU-2024.3.7.1-win` / `lib/app-client.jar`）上用 `javap` 独立复核了异常表与 `ProjectImpl.isDisposed()`（= `super.isDisposed() || isTemporarilyDisposed`，窗口内确为 true），**未仅采信结论**。

随后补的第二修法（`bd54b9c`，取服务**之前**先判 `project.isDisposed`）在真窗口三组探针上端到端复验，结论**分两层**：

- **判据口径成立**：判据在位时窗口内 `getService` 调用数 = **0**，关窗后受害调用点成功建出 `SqlLogManager`；无判据基线则关窗后受害点仍重抛缓存异常——毒化机制**首次在真实窗口上被直接证实**（此前仅字节码推演）。
- **派生活动断言不成立**（「同窗口再现时那 3 例变绿」）：①受害点 `SectionConfigurableAutoCaptureLinkageTest#setUp:29` 不在守卫面内；②**判据分支对该窗口不可达**——`ProjectManagerImpl.closeProject` 的 light 分支在置 `setTemporarilyDisposed(true)` 的**同一写动作**里 `removeFromOpened(project)`（`ProjectManagerImpl.kt:347-350`），而 `apply()` 传的是 `openProjects` 快照（`ProjectManagerImpl.kt:245`），**窗口内该项目根本不在列表里**。

**同一轮还做了一次「先判可达性再决定覆盖面」的示范**（窗口可达性判定，只读调研）：用平台源码**穷举** `setTemporarilyDisposed(true)` 的**唯一调用点**（`ProjectManagerImpl.kt:348`，`closeProject` 的 light 分支），门是 `isLight = isUnitTestMode && 路径含 light_temp`，且方法标 `@TestOnly` → **真机 `isUnitTestMode==false` ⇒ 窗口永不出现**（三平台版本逐字同形）。结论：**6 处守卫不做**，改为定向治泄漏源（见主题四）。判定同时订正了原清单的两处错：`LogStartupCapture:26` 不需设防；**漏了** `ui/gutter/SqlGutterLineMarkerProvider.kt:174`。

**方法论**：

1. **声称「根治」前先问「我的改动是否触及机制本身」**。把结果吞掉 ≠ 阻止机制发生。判据：改动之后，「造成问题的那个动作」还会不会被执行？本轮第 ① 步的答案是「会」，所以它不是根治。
2. **平台内部状态的可达性要用源码穷举证明，不能靠推演**。`setTemporarilyDisposed(true)` 的唯一调用点 + `isUnitTestMode` 门 + `@TestOnly` 标注，三件套穷举完才敢说「真机不可达」。
3. **先判可达性再决定覆盖面**：不可达的面不加守卫（给生产代码加守卫＝让生产为测试让路，且守卫不治本——只挡传播，留下泄漏源本身），把力气花在治泄漏源上。
4. **交付口径与验证口径要分层写**：判据口径成立、派生活动断言不成立——两者必须分开表述，不能合并成一句「已验证」。

## 四、测试状态泄漏与分片顺序依赖（本仓高频坑，本轮出了两波）

### 1. 机制：light 测试项目在同片 JVM 内跨测试类复用同一个 `ProjectImpl`

`LightPlatformTestCase.ourProject` 片内只建一次（`doSetup` 每用例只 `setLightProjectName` 改名），因此 `project.getService(SqlLogManager::class.java)` 拿到的是**全片共享的单例**，仅在项目关闭时 `dispose`。**任何测试类改它的可变状态而不复位，都会串台到同片后续测试类**；是否发作取决于分片时长权重算出的邻居（**新增测试类即重排邻居**，潜伏的顺序依赖随之显隐）。

**判据**：红总是「本类隔离跑绿、分片跑红」，且失败集在两次全量跑之间**不同**。

### 2. 第一波：五个泄漏类的复位 + 治本

- 修法：新增 `testutil/SqlLogManagerProjectState.kt`（`capture`/`restore`，`SqlLogManagerProjectState.kt:57/80`）+ `SqlLogManager` 的 `internal fun restoreCaptureStateForTest(...)` 测试缝（`SqlLogManager.kt:90`——`userArmed`/`isWaitingForConsole` 只有 `private set`，公开路径改不回初值；`stopCapture()` 带应用级副作用不能代用），5 个泄漏类各自 setUp capture / tearDown restore，**未动用例语义与断言**。
- 泄漏清单：`SqlConsoleBridgeFilterProviderTest`（`dedupeEnabled=false` 只关不复位）、`EpBridgeSinglePathTest`、`McpHistoryIngestTest`、`SectionConfigurableAutoCaptureLinkageTest`、`AgentListenSyncTest`。
- **顺序无关的因果钉住**（临时探针，跑完即删未入库）：守卫短路 → 红「共享 buffer 应无残留条目 expected:<0> but was:<2>」（2 条正是 `McpHistoryIngestTest` 入队的）；守卫生效 → 绿。

### 3. 治本：把预热链的池线程绑到项目生命周期

窗口记录的大头是 `SqlPreviewPanel.prewarmPreviewTempFile` 派出的池线程在 temporarily-disposed 窗口内取服务。修法（`ec38d54`）：取消门挂 `ProjectEx.getEarlyDisposable()`——平台 KDoc 原文即「In unit test mode light project is not disposed, but **this disposable is disposed for each test**」，项目开始销毁即置 `previewDisposed`，池线程在下一个检查点放弃、**不取服务**；面板 dispose 时 `Disposer.dispose(gate)` 解除登记。**取消而非 join**（项目关闭路径上等待会把在途预热耗时加进用户可感的关闭时间）。

**读数**（同一命令 `./gradlew test` 全量，`idea.log` 按字节偏移取增量切片）：

| 口径 | 改动前 | 改动后 |
|---|---|---|
| `containerState=disposed temporarily` 行数 | 290（58 事件） | **0** |
| `Project is already disposed` 行数 | 290 | **0** |
| `[M36] prewarm FAILED: TestLoggerAssertionError` | 58 | **0** |
| `[M36] prewarm FAILED: AlreadyDisposedException` | 2 | **0** |
| `ui.SqlPreview*Test` + `CrudSqlPreviewPanelRenderTest` 子集窗口行数 | 25（5 事件） | **0**（382/0/0/0） |

分片那批 3971 行 = 795 事件，**795/795** 事件级首帧归因落在预热链（712 `prewarmPreviewTempFile$lambda$1$0$1` + 83 `lambda$0$0$1`）——「唯一来源」主张成立。复核另提四条条件，其中一条值得记：**「改动后同探针绿」的表述不实**（daemon 日志显示探针跑 5 次、2 次红，其中一次编的是比提交版多一行的源码变体），**不影响生产读数**，但说明「探针读数」这种一次性证据必须当场留档，否则事后不可复核。

### 4. 第二波：两路各自跑绿、合到一起红（判环境假失败的三步）

T-McpToolNaming 那路**首跑 shard3 出现 8 例失败**（`SqlConsoleBridgeFilterProviderTest` ×2、`SqlLogListFreezeGuardTest` ×1、`AgentListenSyncTest` ×3、`AgentManagerPremainTest` ×1，形态为 `AlreadyDisposedException` / 断言），三步证伪判定为既有的顺序/分片邻居依赖假失败：

1. 四个失败类**隔离复跑全绿**；
2. **全量复跑** 5378/0/0/6 绿；
3. 删迁移后全量复跑 5372/0/0/6 绿。

失败类**均不在 MCP 面**，与本次改名无关。该路最终读数为 **5372/0/0/6**；ACP 那路读数为 **5383/0/0/6**（两路各自的树、各自的时点，不可互比）。触发源是**分片组成变化**（类集变了 → 时长权重重排邻居），与既有规律「新增测试类即重排分片」一致。

**判据/命令**：
- 红总是「隔离绿、分片红」，且失败集两轮不同 → 先按三步证伪（隔离复跑 → 全量复跑 → 组成重跑），**不要先改代码**。
- 分片组成由 `build/test-results/**/*.xml` 的历史时长权重推导，**不宣称「分片顺序无关」**，也不把 `testShards` 总数当稳定常量。

### 5. 附带两种脆弱形态（登记，未修完）

- **脆弱前置**：`assertNull(getServiceIfCreated(X))` 断言的是**环境**而非被测行为。修法＝`assertSame(before, after)` 同一性比对。**边界**：`before != null` 时该断言**恒真**（项目服务是项目级单例），只对 `before == null` 有判别力——本轮可接受，是因为该用例的 `before` 恒为 null（已独立核实）。
- **反向形态**：`cacheSize() > 0` 一族**可能假绿**（`EntityResolver.cacheSize()` 是全局静态、片内跨类共享，邻居条目也能让它通过），属「弱而不脆」、**不可作承重证据**。

## 五、多智能体派活与掉线的实战教训

以下第 1–4 条有仓内出处（T-TailSweep2 批次），第 5–6 条仓内无产物，标注「未复核」。

1. **派活必须写死「每完成一件可提交的就立即提交」**。T-TailSweep2 六路实施代理中**四路在提交前掉线**（T-FS-05 / T-FS-06 / T-FS-07 三路的工作区改动未提交、G1 停在探针阶段），由派活方接手逐路评估完整度、补完并提交。
2. **接手掉线代理时先检查工作树是否停在中间态**。T-FS-05 那路掉线时工作树停在「先红」态——生产代码 `runWriteSafe` 被换成直写、源码留着 `RED PROBE` 注释。**照原样提交等于把写安全闸门摘掉上线**；派活方把它还原为与基线逐字符一致后才提交。命令：`git status` + `git diff` + 搜临时探针标记（本轮为 `RED PROBE`；搜法 `grep -rn "RED PROBE" src/`，当前仓内 0 命中）。
3. **派活给的路径要指向工作树副本，主仓只读**。同批多路把改动/回填写进了**主仓副本**（`docs/变更记录.md` 等共享文档），导致返工——T-PsiCaptureProtocol 计划 §八 记「同批多路已因误改主仓 `docs/变更记录.md` 返工」，T-DelimiterAware 计划 §九 记「同批三路已因误改主仓/共享文档返工」。T-PerfSweep5 的正确做法写在计划 §九：「报告 §5 回填写在**本工作树副本**，主仓副本待合流时同步」。
4. **写集碰撞判定要按「文件面」而非「目录」**。本轮实测两处「目录不同但文件相同」的假安全：①`mcp/` 下 T-McpRowBudget 与 T-McpAuditTrail 同改 `ExplainTool.kt` 与 `McpDbExecutor.kt`（合流时实际冲突 2 处，记录在 T-McpAuditTrail §八 T-MAT-07）；②`execute/` 下 T-FatalPassthrough / T-ErrorReportRedact / T-DelimiterAware **三份计划同改 `DataSourceSelector.kt`**，被排成串行链 A（全景盘点 §2.2 写集实测）。判据：排波前用 `grep -l "<文件名>" docs/开发计划/<本批>*.md` 对每份计划点名的文件求交，而不是按包名/目录名分组。
5. **并发上限的代价：多路并行 gradle 会共用同一个 Kotlin 编译 daemon**（JVM args 相同即复用）→ 编译串行化。**未复核**：仓内无「两路分别卡 70/20 分钟」的读数留档。可核实的是对策已被本批多份计划采用——验收命令统一加 `-Pkotlin.compiler.execution.strategy=in-process`（见 T-FatalPassthrough §十.6、T-ParamContract2 §门禁、T-PsiCaptureProtocol §验收）。
6. **收口脚本禁用 `&&` 串联**。**未复核**：仓内无产物。转述的问题是——本轮收口用 `merge A && merge B && … && gate`，第二个合并失败后**门禁静默未启动、日志为空**，被误读成「还在跑」。建议：多步收口用分号串联或显式检查每步退出码。
7. **计划文档的前提会被实测推翻，发现即当场更正并回填**。本批至少四处：
   - T-FS-06 点名的盲区形态 `invokeLater(ModalityState.any()) { }` **编译不过**（平台无 `(ModalityState, Runnable)` 重载），真正漏网的是 `invokeLater({ … }, ModalityState.defaultModalityState())`；
   - T-ST-01 的「light 共享 `ProjectImpl` 导致 `:140` 断言红」归因**对本类不成立**（该类是 `HeavyPlatformTestCase`，每测试方法独立 Project 实例，探针 hash 不同）；
   - T-ST-03 的「确认流另有一处 `generate(sql)` 在 `:734`」**落点不在确认流内**（它在 `showRollbackSql()` 工具栏按钮动作里）；
   - T-FS-09 的「平台有 `focusTarget` 机制」**不存在**（真实根因是自绘 `findComponent` 只认 JBLabel）。

## 六、判断「有没有用户受影响」要看产物，不看文档自述

本轮要把 MCP 工具前缀从 `mpsv_` 改成 `sqlv_`，用户判断「MCP 从未发布过，不需要迁移」。判断链条值得完整记下来，因为它**先被自述性记录误导过一次**：

**第一轮（被自述性记录误导）**：查 `CHANGELOG.md` 的**已发布段**——`[2026.9.18]` 段里有 **7 行**描述 MCP 工具集（T-McpToolset 三工具、T-McpToolset2 十工具 + 设置页门控）；查 `update/preview.update.json`——`"version": "2026.9.18"`，`downloadUrl` 指向 `…/releases/download/2026.9.18/….zip`。据此一度推翻用户口径、要求保留设置迁移（并按「旧禁用项静默复活」实现 + 6 例单测）。

**第二轮（看产物）**：去查 Gitee 公开 API + 本地 tag 树，结论相反——

- 本地 tag 共 23 个，去掉 2 个非版本 tag（`pre-dev-merge-20260918`、`r2-backup-pre-landing-20260915`）后是 **21 个发行版**，**没有 `2026.9.18` 正式版**（只有 `beta.1`~`beta.4`）；
- 命令：`git tag | wc -l`；`git ls-tree -r --name-only <tag> | grep -c "^src/main/kotlin/cn/song/mybatisplus/visualizer/mcp/"` → `2026.9.14` / `2026.9.18-beta.1` / `2026.9.18-beta.4` 三个 tag 全部为 **0**；同法 `grep -c "mcp-optional.xml"` → **0**；
- 发行 tag 是从**旁支**切的，MCP 只在 master 主线。

⇒ 迁移是死代码，连同 6 例单测一并移除。

**方法论**：

1. **「有没有用户受影响」的判据是「产物里有没有」（tag 树 / 发行物内容），不是「文档里写了什么」**。
2. `CHANGELOG` 的已发布段、`update` 清单这类**自述性记录可能与产物不一致**。本轮查出两处：CHANGELOG 已发布段描述了不含 MCP 的版本（条目由 dev 分支合并时被并入已发布段）；`update/preview.update.json` 的 `downloadUrl` 指向**从未创建**的发行版（必 404）。两处均按「本轮不改、登记」处理（不在写集）。
3. 判据命令固定为两条：`git ls-tree -r --name-only <tag> | grep -c "<路径前缀>"` + 发行版清单计数。**先跑产物侧，再读文档侧**——顺序反了就会被自述性记录带偏。

## 七、`@ApiStatus.Internal` API 的漂移没有自动化门禁

T-AcpMcpTransport 的绕行需要实现 ml-llm 的 `com.intellij.ml.llm.agents.acp.ideaMcpTransportProvider` EP，接口标 `@ApiStatus.Internal`。计划 R1 的应对栏写的是「版本升级时由既有 `verifyPlugin` 门禁暴露」——**实施方实测不成立**：verifier 对 `com.intellij.ml.llm` 走「optional 依赖不可用」分支（依赖树记 `(failed) com.intellij.ml.llm (optional): Unavailable`），**完全不做类型解析**；而三个目标平台都没有 AI Assistant 插件。**故这些 internal 类型的漂移没有任何自动化门禁会红**，本轮 `verifyGate` 三目标仍全 Compatible。

替代措施（可复用的取证手法）：

- **桩文件头逐条登记取证方法与出处**（`src/mcpStub/.../AcpIdeaMcpTransportProvider.kt` 头注释写清真类形态、EP 声明行号、消费逻辑的字节码出处）。
- **签名用 ClassFile API 导出，不用 javap**：JDK 8/17/21/24 的 `javap` 读不了 class major 69（ml-llm 模块 jar 正是 major 69），改走 gradle transforms 内 `idea-2026.2.1-win/jbr`（JBR-25.0.3）的 `javac` + `java.lang.classfile` API 写一次性导出器逐类导出签名。
- **编译产物与真接口逐字对齐的判据**：插件 jar 内实现类的 `interfaces=[…AcpIdeaMcpTransportProvider]`、方法描述符 `(Lcom/intellij/ml/llm/agents/acp/api/AcpAgentId;)Lcom/intellij/ml/llm/agents/acp/client/AcpIdeaMcpTransport;` 与真接口抽象方法逐字一致；桩类零命中（`unzip -l … | grep -c "com/intellij/mcpserver\|com/intellij/ml/llm"` → 0）。

**未复核**：`verifyGate` 三目标「各记 1 usage of internal API」这一具体读数在仓内无留档（计划 §8.5 只记了 243 `verifySmoke` 的 Compatible 与依赖树 `Unavailable`）。
