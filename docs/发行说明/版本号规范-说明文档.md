# 版本号规范说明文档

## 版本号

1. **版本号位置**: `gradle.properties` 文件的 `version` 属性（例如：`version=2026.8.13`）。
2. **命名格式**: `{年份}.{月份}.{日号}`
   - 年份格式：YYYY（例如：2026）
   - 月份格式：M，不补前导零（例如：8 表示 8 月，11 表示 11 月）
   - 日号格式：D，不补前导零（例如：13 表示 13 日，5 表示 5 日）
   - 示例：`2026.8.13`、`2026.11.5`、`2027.1.9`
3. **发布规则**: 一日一版
   - 一天最多发布一个版本号，版本号即发布当天的年月日。
   - 同日需再次发布（如热修）：并入下一个自然日，以次日日期作为版本号（示例：`2026.8.13` 当天发现缺陷，修复后次日以 `2026.8.14` 发布）。
   - 禁止使用同日递增后缀（如 `2026.8.13.1`）——四段数字不是合法 SemVer，上架会被拒绝。
4. **上架合规**: JetBrains Marketplace 对新插件默认开启 SemVer 校验
   - 版本号必须是三段纯数字，禁止字母（如 `2026.8.13.M19.4`）、禁止前导零（如 `2026.08.13`）、禁止预发布/构建后缀（`-SNAPSHOT` 仅限本地构建，发布版本不带）。
   - 日期版本号随时间自然单调递增，满足市场「新版本号必须大于旧版本号」的要求。
5. **注入方式**: `plugin.xml` 不手写 `<version>`，由 IntelliJ Platform Gradle Plugin 从 `gradle.properties` 自动注入。
6. **与里程碑解耦**: 内部迭代使用 M 里程碑编号（如 M19.4），仅记录于提交信息与 CHANGELOG，不进入对外版本号。
7. **发布时同步**: 发布当天将 CHANGELOG.md 的 `[Unreleased]` 分区改名为 `[{版本号}] - {YYYY-MM-DD}`（示例：`## [2026.8.13] - 2026-08-13`）。

## 内测版本号（Gitee 抢先体验通道）

Marketplace 稳定通道按上文规范走三段纯数字；Gitee 内测通道允许在基号后追加
`-beta.N` 后缀，解决「内测期一天发多轮」的序号问题（见
`开发计划/20260822-1200-更新机制改为内测版抢先体验-开发计划.md`）：

| 通道 | 格式 | 示例 |
|------|------|------|
| 内测（同日多版） | `YYYY.M.D-beta.N` | `2026.9.10-beta.1` → `beta.2` → `beta.3` |
| 正式（Marketplace） | `YYYY.M.D` | `2026.9.10` |

- 上架 Marketplace 的版本**必须去掉 `-beta.N` 后缀**（Stable 通道只展示纯数字版本）。
- 内测清单照常写 `update/update.json`，`writeUpdateManifest` 任务直接透传
  `gradle.properties` 的 version（含后缀），downloadUrl / 附件文件名自动拼接。

## 发行标签（git tag / Gitee 发行版）

- 标签名 = `gradle.properties` 完整版本号字符串，一字不差（含 `-beta.N` 后缀），
  **不带 `v` 前缀**。git 轻量标签与 Gitee 发行版标签同名建一套。
- 必须完全一致的原因：downloadUrl 按标签段拼接
  （`releases/download/{版本号}/mybatis-plus-sql-visualizer-{版本号}.zip`，
  见 `build.gradle.kts` 的 `writeUpdateManifest`），标签差一个字符，
  用户点「立即更新」就是 404。
- 创建时机：发行提交之后 `git tag {版本号}` → `git push origin {版本号}`；
  Gitee 建发行版填同名标签并上传 zip 附件。
- 同日第二轮内测：旧发行版附件不可改，直接打 `2026.9.11-beta.2` 新标签、
  新建发行版；beta 转正在 beta 发行版之外新建纯数字标签（如 `2026.9.11`），
  两发行版共存。
- beta 标签同样打 git 标签，使正式版发行的范围统计
  `git log {上一正式版tag}..HEAD` 自然包含期间 beta 提交，不漏算。

## 版本比较机制（T-VersionUtil，2026-09-10 起）

比较逻辑不再是插件自研的点分算法。`update/VersionComparator.kt` 的 `compare` 现委托
**IDEA 内置比较器** `com.intellij.util.text.VersionComparatorUtil`（`lib/util_rt.jar`），
与 IDE/Marketplace 自身判定「发现新版」用的是同一套规则——不存在「插件端认为有新版、
IDE 端认为没新版」的口径分叉。243 / 253 / 262 三平台 javap 实证
`compare(String, String)` 签名稳定；包装层保留 null 语义（null 小于非 null）与异常兜底
（比较异常降级为 0 = 不更新，不打扰用户）。

内置比较器对版本号的处理：逐段切分，数字段按**数值**比较，`-beta` 这类标识被识别为
**预发布标记**——同一基号下预发布永远小于正式版。用本机三平台 util_rt.jar 实测的行为表：

| 版本号 A | 版本号 B | 结果 | 对应场景 |
|----------|----------|------|----------|
| `2026.9.9` | `2026.9.10` | A < B | 隔日发版，正常提示升级 |
| `2026.9.10-beta.1` | `2026.9.10-beta.2` | A < B | 同日内测第二轮，正常推送 |
| `2026.9.10-beta.9` | `2026.9.10-beta.10` | A < B | 数字后缀按数值排，`beta.10` 大于 `beta.9` |
| `2026.9.10-beta.1` | `2026.9.10` | A < B | 同日内测版 **小于** 正式版：装了当天正式版的用户不会被内测清单「降级倒灌」 |
| `2026.9.11-beta.1` | `2026.9.10` | A > B | 次日内测版大于前一日正式版：内测用户继续收到抢先体验推送 |
| `2026.9.10` | `2026.9.10` | 相等 | 不提示（含用户已装正式版、清单仍挂着同号 beta 以外的场景） |

历史备注：旧自研点分比较把 `2026.9.10-beta.1` 的第三段切成 `10-beta` 走字符串兜底，
判其**大于** `2026.9.10`——「同日先 beta 后转正」时内测通道会出现提示倒挂。委托内置
比较器后此边界消除，`VersionComparatorTest` 已补 `betaPrereleaseLowerThanRelease` 用例锁定。
