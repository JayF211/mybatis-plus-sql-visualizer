# IService 内置 CRUD 方法预览——实体解析增强

**创建时间**：2026-08-19 23:50
**优先级**：P0（用户实测阻断：gutter 图标点击后报"未找到 Wrapper"）
**影响范围**：BatchOperationConverter 实体解析 + SqlPreviewService 兜底 + 测试

## 问题描述

用户代码：
```java
public R<User> selectOne(@PathVariable Serializable id) {
    return R.success(userService.getById(id));
}
```

点击 `userService.getById(id)` 行的 gutter 预览图标 → 提示"未在光标处找到MyBatis-Plus Wrapper 调用"。

**根因链路**：
1. `WrapperAnchorDetector` 场景 D 正确识别 `getById` 为批量操作锚点（gutter 图标正常显示）✅
2. `SqlPreviewService.preview()` 的 WrapperLocator 返回 null（非 Wrapper 链）→ 进入批量操作兜底分支 ✅
3. `BatchOperationConverter.convert()` → `resolveEntityTable()` 解析实体失败 → 返回 null ❌

**实体解析失败的具体原因**：
- `resolveEntityTable()` 对 `getById(id)` 走步骤 3（service qualifier 泛型）
- `resolveServiceEntityClass()` 步骤 3a 检查变量类型自身泛型参数 `varType.parameters` → 对 `UserService extends IService<User>`，变量 `userService` 的类型 `UserService` **自身无类型参数**（类型参数在父接口 `IService<User>` 上）→ 返回 null
- 步骤 3b 检查父类/接口泛型参数 → 找到 `IService<User>` → 解析出 `User` → **`User.name.endsWith("Entity")` = false** → 跳过
- 步骤 4（qualifier 实体类型）→ `UserService` 不是实体 → 返回 null
- 最终 `resolveEntityTable()` 返回 null → `convert()` 返回 null → 预览失败

**核心矛盾**：`resolveServiceEntityClass()` 步骤 3b 限定 `resolved.name?.endsWith(ENTITY_SUFFIX) == true`，导致 `User`、`Order`、`Account` 等不含 "Entity" 后缀的真实实体类全部被排除。

## 影响范围

所有 `BatchOperationConverter.batchOperationMethodNames` 中的方法，只要实体类不含 "Entity" 后缀且无 `@TableName` 注解：
- `getById` / `getOptById` / `listByIds` / `selectByIds` → 单主键/主键 IN 查询
- `removeById` / `deleteById` / `removeByIds` / `deleteByIds` / `removeBatchByIds` → 删除
- `updateById` / `updateBatchById` → 更新
- `save` / `saveBatch` / `insert` / `insertBatchSomeColumn` → 插入
- `saveOrUpdate` / `saveOrUpdateBatch` / `insertOrUpdate` → upsert
- `selectAll` → ActiveRecord 全列查询
- `selectByMap` / `listByMap` / `removeByMap` / `deleteByMap` → Map 条件

## 修复方案

### 方案概述：新增"方法返回类型"实体解析源 + 放宽 service 泛型后缀限定

**设计原则**：
- 新增实体解析路径，不破坏现有路径（`SpWorkflowVersionEntity` 等含后缀的实体继续走原有路径）
- 放宽 `resolveServiceEntityClass()` 的后缀限定，但保留 `isLikelyEntity` 的 JDK 基础类型排除（防 `List<String> list.selectAll()` 误判）
- 添加"方法返回类型"作为高置信度实体源（`getById` 返回 `User` → `User` 即实体）

### 改动点 1：BatchOperationConverter.resolveEntityTable() 新增返回类型解析

**文件**：`src/main/kotlin/.../psi/BatchOperationConverter.kt`

在 `resolveEntityTable()` 的步骤 3（service qualifier 泛型）之前，新增步骤 2.5：**方法返回类型解析**。

```kotlin
// 新增步骤：方法返回类型（getById 在 IService<User> 中返回 User → User 即实体）
val entityFromReturnType = resolveEntityFromReturnType(call)
if (entityFromReturnType != null) return EntityResolver().resolve(entityFromReturnType)
```

新增函数 `resolveEntityFromReturnType()`：
```kotlin
/**
 * 从方法调用返回类型解析实体（T-Mxx）：
 *  - `userService.getById(id)` 在 IService<User> 中返回 User → 解析 User
 *  - `userService.list()` 返回 List<User> → 解析泛型参数 User
 *  - `userService.save(entity)` 返回 boolean/void → 返回 null（无法从返回类型推断）
 *  - 返回类型不是 PsiClassType → null
 */
private fun resolveEntityFromReturnType(call: PsiMethodCallExpression): PsiClass? {
    val returnType = call.methodExpression.type ?: return null
    val classType = returnType as? PsiClassType ?: return null
    // List<User> → 取泛型参数
    val entityType = if (classType.className == "List" || classType.className == "Collection") {
        classType.parameters.firstOrNull() as? PsiClassType
    } else {
        classType
    }
    val resolved = entityType?.resolve() ?: return null
    // 排除 JDK 基础类型 + 仅接受有 @TableName 或类名含 Entity 的类（保守策略防误判）
    if (!isLikelyEntity(resolved)) return null
    return resolved
}
```

**注意**：返回类型解析使用 `isLikelyEntity` 保守策略（仍需 @TableName 或 Entity 后缀），因为返回类型可能是 `boolean`/`int` 等非实体类型。这一步对 `User` 类（无后缀无注解）仍然无法识别——需要改动 2 配合。

### 改动点 2：放宽 resolveServiceEntityClass() 后缀限定

**文件**：`src/main/kotlin/.../psi/BatchOperationConverter.kt`

将步骤 3b 的 `resolved.name?.endsWith(ENTITY_SUFFIX) == true` 限定移除，改为使用 `isLikelyEntity()`（已排除 JDK 基础类型 + 接受 @TableName 或 Entity 后缀）：

```kotlin
// 修改前：
if (resolved.name?.endsWith(ENTITY_SUFFIX) == true) return resolved

// 修改后：
if (isLikelyEntity(resolved)) return resolved
```

**影响分析**：
- `UserService extends IService<User>` → 解析出 `User` → `isLikelyEntity(User)` → 无 @TableName、无 Entity 后缀 → **仍然 false**
- 这意味着仅放宽后缀限定仍不够！

### 改动点 3（核心）：增强 isLikelyEntity() 或新增"方法返回类型"实体解析源

**方案 A（推荐）：新增"方法返回类型"实体解析源**

在 `resolveEntityTable()` 中新增一个高置信度源：**方法调用的返回类型**。对于 `getById(id)`，IService 定义中返回类型是 `T`（实体类型），在 `UserService extends IService<User>` 的上下文中，`getById` 的返回类型是 `User`。

```kotlin
// 新增步骤：方法返回类型 → 实体（高置信度：IService.getById/removeById 等方法签名中 T 即实体）
val entityFromReturnType = resolveEntityFromMethodReturn(call)
if (entityFromReturnType != null) return EntityResolver().resolve(entityFromReturnType)
```

新增函数：
```kotlin
/**
 * 从方法调用的返回类型解析实体（高置信度）：
 * 仅适用于 batchOperationMethodNames 中的方法——这些方法在 IService/BaseMapper 中
 * 的返回类型或泛型参数即为实体类型（如 getById 返回 T, list 返回 List<T>）。
 * 不对返回类型做 isLikelyEntity 限定（方法名已在白名单中，误判风险极低）。
 */
private fun resolveEntityFromMethodReturn(call: PsiMethodCallExpression): PsiClass? {
    val returnType = call.methodExpression.type ?: return null
    val classType = returnType as? PsiClassType ?: return null
    // List<User> / Page<User> → 取泛型首参
    val entityType = when (classType.className) {
        "List", "Collection", "ArrayList", "LinkedList" ->
            classType.parameters.firstOrNull() as? PsiClassType
        "Page" ->
            classType.parameters.firstOrNull() as? PsiClassType
        else -> classType
    } ?: classType
    val resolved = entityType.resolve() ?: return null
    // 排除 JDK 基础类型（防误判：boolean/int 等原始类型已被 PsiClassType 排除）
    val qualifiedName = resolved.qualifiedName ?: return null
    if (qualifiedName.startsWith("java.") || qualifiedName.startsWith("javax.")) return null
    return resolved
}
```

**关键设计决策**：
- `resolveEntityFromMethodReturn` **不做** `isLikelyEntity` 限定——因为方法名已在 `BATCH_OPERATIONS` 白名单中，且方法调用的返回类型在 IService 上下文中高置信度指向实体
- 排除 `java.`/`javax.` 包前缀 → 防 `boolean`/`int` 原始类型（但这些原始类型不是 PsiClassType，已被排除）
- 支持 `List<User>`、`Page<User>` 等集合/分页返回类型

**方案 B（备选）：放宽 isLikelyEntity() 为"排除 JDK 基础类型即接受"**

```kotlin
private fun isLikelyEntity(psiClass: PsiClass): Boolean {
    val qualifiedName = psiClass.qualifiedName ?: return false
    if (qualifiedName.startsWith("java.") || qualifiedName.startsWith("javax.")) return false
    if (psiClass.annotations.any { (it.qualifiedName ?: "").endsWith(".TableName") }) return true
    // 放宽：不再要求 Entity 后缀——只要不是 JDK 类就接受
    return true
}
```

**风险**：`selectAll` 等方法名可能与普通集合方法撞名（`List<String> list.selectAll()` 的 `String` 会被当实体）。但 `selectAll` 在 `BATCH_OPERATIONS` 中，且步骤 4（qualifier 实体类型）已有 `isLikelyEntity` 限定——如果放宽，`String` 会被误判为实体。

**决策**：采用方案 A（方法返回类型解析源），不做 isLikelyEntity 放宽。原因：
1. 方法返回类型在白名单方法名上下文下高置信度
2. 不影响现有路径（`SpWorkflowVersionEntity` 等继续走原有 service 泛型解析）
3. 不引入误判风险

### 改动点 4：resolveServiceEntityClass() 步骤 3b 同步放宽

**文件**：`src/main/kotlin/.../psi/BatchOperationConverter.kt`

```kotlin
// 修改前（步骤 3b）：
if (resolved.name?.endsWith(ENTITY_SUFFIX) == true) return resolved

// 修改后：
// 放宽：不再要求 Entity 后缀——IService<Entity> / ServiceImpl<M, Entity> 的泛型参数
// 在 service 上下文下高置信度指向实体（service 类不会用非实体类型作泛型参数）
if (isLikelyEntity(resolved)) return resolved
```

**影响**：步骤 3b 放宽后，`UserService extends IService<User>` → `User` 通过 `isLikelyEntity` → 无 @TableName、无 Entity 后缀 → **仍然 false**。所以步骤 3b 放宽对 `User` 无效，需要改动点 3 的方法返回类型源来覆盖。

**综合修复路径**：
1. 改动点 3（方法返回类型）→ 覆盖 `getById`/`removeById` 等方法的实体解析
2. 改动点 4（步骤 3b 放宽）→ 作为补充路径覆盖 service 泛型中有 @TableName 但无 Entity 后缀的实体
