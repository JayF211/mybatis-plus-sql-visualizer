## 一、背景与依据

一期 attach 路线的结构性代价是「挂载时机晚于应用启动」：用户点 Run 后，插件要等进程出现（`ExecutionListener.processStarted`）→ 3s 静默等待 → `VirtualMachine.attach` + `loadAgent` → agent 装载 transformer，期间应用已经跑起来了，启动阶段发出的 SQL（框架初始化、数据源探活、Flyway/Liquibase 迁移）全部落在 attach 完成之前，只能靠控制台桥补。此外 JEP 451 之后动态挂载会被 JVM 告警（`-XX:-EnableDynamicAgentLoading` 时可硬拒），而 `-javaagent` 启动加载被 JVM 视为「预期内」，既不告警也不受限——竞品 Cool Request 走 premain 正是为此。

本次补位要拿到的能力就一条：**Java 运行配置启动前把 `-javaagent` 写进 VM 参数**，让 agent 在目标 JVM 的 `premain` 阶段完成 transformer 装载，启动期 SQL 直接进增强通道；attach 链原样保留，作为未注入（未开启/未确认/端口协商失败/premain 未回连）时的既有通道。

agent 侧无需改动——`AgentMain.premain` 与 `agentmain` 共用同一个 `install`，`EventBus.start(port)` 与 `SenderLoop` 的无限退避重连对「IDE 先开端口、进程后启动」这一时序天然适配。

## 三、方案

### T-M56P2-01 端口前置协商入口（AgentManager）

把 `attachAndOffer` 里「开 loopback 端口」这一步抽成可独立调用的入口，供运行配置准备期使用；attach 链改走同一入口，不另起一套。

- 新增 `internal fun openPremainChannel(): Int?`：`ServerSocket(0, 1, loopback)` 取端口 → 登记为待连接通道 → 起守护线程 `accept()`（`soTimeout = PREMAIN_ACCEPT_TIMEOUT_MS = 120s`）→ 返回端口。绑定失败返回 null。
- 挂起通道上限 `MAX_PREMAIN_CHANNELS = 4`，超限拒绝（防重复准备泄漏 socket）；每次准备先 prune 过期/已认领通道。
- 回连到达后 `onPremainConnected(socket)`：读首帧 HELLO 取 agent 自报 pid（`SenderLoop.java:39` 的 `{"pid":n}`，非 HELLO/超时/畸形按 0 处理）→ 建 `AgentSession`（复用既有类，零改动）→ `attachedPids[pid] = now` → 初始 CONFIG 下发 → `updateOnline()` + 状态行广播。
- 增强已关闭/未确认时到达的回连直接丢弃（`isEnhancedActive()` 复核，覆盖「准备后用户关掉开关」的时序）。

### T-M56P2-02 premain 专用 jar 落盘

`-javaagent` 与 `loadAgent` 对文件的要求不同：后者在调用当次读文件，前者由**目标 JVM 在启动时**读，且**打不开 agent jar 时 JVM 直接终止启动**（`Error occurred during initialization of VM`）——所以既不能沿用 `deleteOnExit`（IDE 退出与目标 JVM 启动之间存在删除竞态），也不能用随机临时名（同会话重复 Run 每次新路径、旧文件堆积）。

- 新增 premain 专用落盘：目录 `PathManager.getPluginTempPath()/mpsv-agent`（不可用时回落 `java.io.tmpdir`），文件名按内容 CRC32 定名 `mps-sql-agent-<crc>.jar`——同一构建产物永远同一路径，重复 Run 复用不重写；写盘走「临时文件 + `ATOMIC_MOVE` 覆盖改名」，并发/多项目同时准备也只会收敛到同一份完整文件。
- 不登记 `deleteOnExit`。残留文件落在插件临时目录（单文件 ~500KB，OS 临时目录自行回收），换取「进程启动时文件必然在位」。
- attach 链的 `extractAgentJar()` 原样不动（`deleteOnExit` 语义对 attach 成立）。

### T-M56P2-03 RunConfigurationExtension 注入

新增 `PremainRunConfigurationExtension`（`src/main/kotlin/cn/song/mybatisplus/visualizer/log/agent/`），plugin.xml 在 `com.intellij` 扩展区注册 `<runConfigurationExtension implementation="…"/>`（`:92-94` 区块首部，紧邻既有 `consoleFilterProvider`）。

- `isApplicableFor` 恒 true（平台只在 Java 运行器链路上调用本扩展，非 Java 配置不会进入；登记理由写入注释）。
- `updateJavaParameters` 内：取 `configuration.project` 的 `AgentManager` → 问它要 `-javaagent` VM 选项 → 非空则 `params.getVMParametersList().add(option)`。全链 `runCatching` 包裹，任何异常只记 WARN——**注入失败绝不影响用户 Run**。
- VM 选项形态：`-javaagent:<jar 绝对路径>=port=<n>;logLevel=warn`，args 段由 `AgentProtocol.agentArgs(port)` 产出（`AgentProtocol.kt:31`），与 `AgentArgs.parse`（`AgentArgs.java:20-55`）逐字对齐。
- 注入结果**不写回运行配置**：`JavaParameters` 是每次执行现建的瞬时对象，用户保存的配置里不会留下 `-javaagent` 残留（attach 与 premain 都不需要「清理上一次注入」的额外逻辑）。

### T-M56P2-04 幂等与 attach 跳过

双保险沿用一期语义，新增的是「premain 在场时不重复走 attach」：

- `doAttachAsync` 开头判 `hasPendingPremainChannel()`（存在未认领且准备时刻在 `PREMAIN_SKIP_ATTACH_WINDOW_MS = 30s` 内的通道）→ 直接返回，不解析 pid、不入去抖表。
- 反方向由 `attachedPids` 兜底：premain 回连先到 → pid 已入表 → 随后 attach 请求被 `attachToPid` 的 `putIfAbsent` 挡下。
- premain 回连侧的去重判据是「**同 pid 是否有活动会话**」而非查 `attachedPids`：premain 是更强通道，先到者优先，且写入时覆盖（`attachedPids[pid] = now`）——避免 attach 先占表导致 premain 连接被误丢。
- 30s 窗口外的通道仍等回连（120s），但不再压制 attach：premain 失效（jar 被外部删除、目标 JVM 拒载）时 30s 后 attach 主路径自动恢复，零劣化。
- agent 侧 `sqlvis.agent.active`（`AgentMain.java:50`）作为最后一道：即便两条路径都发出 loadAgent，进程内也不会叠 transformer。

### T-M56P2-05 测试

- `PremainInjection` 抽成纯函数（决策 + VM 选项拼装），表驱动覆盖：未开启 / 未确认 / jar 不可用 / 端口协商失败 / 正常注入，以及 args 段字面量。
- `AgentManagerPremainTest`（headless，BasePlatformTestCase）：未确认不注入且不协商端口；已确认时注入并可从 VM 选项里取回端口；真连回环 + 写 HELLO 帧驱动「回连建会话 + pid 入幂等表 + 在线态 + 状态行」；同 pid 二次回连被丢弃；premain 通道在场时 attach 不排队；通道数上限。
- agent 子项目既有 `AgentArgsTest` 已锁定 args 解析（`AgentArgsTest.java` 标准形态/逗号分隔/非法端口三例），premain 复用同一 args 段，无需新增 agent 侧用例。

## 四、验收标准

1. 增强捕获开启且已确认时，Java 运行配置启动的进程 VM 参数含 `-javaagent:<jar>=port=<n>;logLevel=warn`，且 agent 在 `premain` 阶段完成装载——目标进程控制台**无** JEP 451 动态挂载告警（启动加载属预期内路径）。
2. 应用启动阶段（attach 3s 静默等待之前）发出的 SQL 进入增强通道，面板条目带增强角标。
3. 未开启增强捕获、或已开启但未确认注入时，`updateJavaParameters` 不产生任何 VM 参数、不协商端口、不提取 jar（`preparePremainVmOption()` 返回 null）。
4. premain 与 attach 不双挂：同一 pid 只有一条活动会话，`attachedPids` 只有一条记录。
5. 注入失败 / jar 落盘失败 / 端口协商失败 / 目标 JVM 未回连，四类失败均不阻断用户 Run，桥捕获照常（`SqlCaptureGate.paused` 不闭合）。
6. `./gradlew testFast`、`./gradlew testShards`、`./gradlew :sql-visualizer-agent:test` 全绿；新增用例含纯逻辑表驱动与 headless 分支两类。
7. 三处文档同步：`docs/变更记录.md` 顶部表格、`CHANGELOG.md` 的 `## [Unreleased]`、本计划 §八 实施记录。

## 五、真机走查清单（留人工）

1. **启动即捕获**：runIde 沙盒内打开任一带 MyBatis-Plus 的示例工程，设置页确认增强捕获已开启并同意注入 → Run 主配置 → 查看目标进程命令行（或 `jcmd <pid> VM.command_line`）含 `-javaagent:…`；应用启动阶段（数据源初始化/Flyway 迁移）的 SQL 出现在面板且为增强条目。
2. **无 JEP 451 告警**：目标 JDK 21+ 运行，控制台不应出现 `WARNING: A Java agent has been loaded dynamically`（premain 加载路径的预期结果）。
3. **不双挂**：同一次 Run 期间设置页状态行只显示一条 `已挂载 pid=x`；`jcmd <pid> VM.system_properties | grep sqlvis.agent.active` 为单值。
4. **回落零劣化**：手工把 `%TEMP%/mpsv-agent/` 下的 agent jar 改名后 Run（模拟 jar 不可用），应用应正常启动（若 JVM 因 `-javaagent` 打不开文件而拒绝启动，说明落盘稳定性不达标，按 §六 风险表处置）；恢复文件名后再 Run 应回到增强通道。
5. **关闭开关**：设置页关掉增强捕获 → 再 Run，VM 参数中不应出现 `-javaagent`，行为与一期关闭态逐字一致。
6. **慢启动窗口**：Run 后拖到 30s 以上再让进程真正起来（或先 Run 一个需长编译的配置），确认仍能挂上（attach 或 premain 二者之一），面板有增强条目。
7. **243 与 262 双平台**：本机 2026.2.3 与 243 沙盒各跑一遍走查 1/3。

## 六、风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 目标 JVM 因 agent jar 缺失而启动失败 | `-javaagent` 打开文件失败会让 JVM 初始化阶段终止（与 attach 的静默失败不同），这是本方案唯一「可能劣化用户 Run」的面 | 落盘用内容定名 + 原子改名 + **不登记 deleteOnExit**，路径在同一 IDE 会话内稳定；jar 提取在注入前同步完成，注入后不再有删除动作；走查 4 专项验证 |
| 落盘目录不可写 | `PathManager.getPluginTempPath()` 只读/不存在 | 回落 `java.io.tmpdir`；两者都失败则返回 null 不注入（零劣化） |
| premain 未回连时压制 attach | 通道在场 30s 内 attach 被跳过 | 窗口收敛到 30s（远小于 120s 的 accept 超时），窗口外自动回 attach；agent 侧 `SenderLoop` 无限退避重连，正常进程不会错过 |
| 重复准备堆积 ServerSocket | 同一配置多次 Run、预览执行等都可能触发 `updateJavaParameters` | 通道上限 4 + 过期 prune + `dispose`/`shutdownAll` 显式关闭 |
| 多项目/多 IDE 实例写同一 jar | 内容定名文件被并发写 | 写临时文件后 `ATOMIC_MOVE` 覆盖改名，读者只会看到完整文件；内容相同，最后写者胜出无差异 |
| EDT 上的落盘 IO | `updateJavaParameters` 可能在 EDT 调用 | 仅首次注入读一次资源（~500KB）写盘，后续复用缓存路径；失败路径全部 `runCatching`，不抛不弹 |
| 平台版本漂移 | `RunConfigurationExtension` 形态在 243/262 之外变化 | 已 javap 双版本核实；扩展实现只覆写两版本共有的抽象方法，注册形态与 JetBrains 自家十余处扩展同形 |
| Spring Boot 等第三方运行器未走该扩展 | 非 `BaseJavaApplicationCommandLineState` 链路的运行器可能不调用 `updateJavaParameters` | 本机 243 发行版实测覆盖 Java Application / JUnit / Gradle / Maven 四处；Spring Boot 走同一 state（该发行版 Spring 插件内无独立 command line state，实测）。真机走查 1 以 Spring Boot 工程为准，若未注入则回落 attach（零劣化），并在实施记录里如实登记 |

- 实施偏离（与 §三 方案的差异，均已在代码注释写明理由）：
  1. **端口前置协商没有复用 `attachAndOffer` 的内部实现**，而是并列新增 `openPremainChannel`——attach 路径的 ServerSocket 生命周期与 `VirtualMachine.attach` 强绑定（同一 `use` 块内开、accept、关），抽公共函数反而要把 attach 调用塞进端口管理，得不偿失；两处共用的是「`ServerSocket(0, 1, loopback)` 取端口」这一个思路而非代码。方案原文「复用既有实现思路，不要另起一套」按此理解落地。
  2. **premain 跳过 attach 的窗口从「与 accept 超时同长」收窄到 30s**（accept 仍等 120s）。原因是 120s 同窗会在 premain 失效时把 attach 压制两分钟，构成实质劣化；30s 窗口 + `attachedPids` 双向兜底后，「premain 先回连」与「attach 先成功」两种竞态都不会丢连接（前者压制 attach、后者由 premain 侧活动会话判据丢弃重复连接）。
  3. **premain 回连的去重判据是「同 pid 是否有活动会话」而非查 `attachedPids`**，且写表用覆盖写。方案原文写「accept 时校验即可」，实测按 `attachedPids` 校验会出现「attach 先占表 → premain 连接被误丢 → 唯一可用连接丢失」的坏路径，故改为会话级判据 + 覆盖写，使 premain 恒为胜者。
  4. **premain jar 落盘改为「内容 CRC32 定名 + 不登记 deleteOnExit」**（方案原文只说「按核实结论定案」）。核实结论：`-javaagent` 打不开文件时目标 JVM 在初始化阶段直接终止，`deleteOnExit` 与子 JVM 启动之间存在删除竞态，故不能沿用 attach 的随机临时名 + `deleteOnExit`。
