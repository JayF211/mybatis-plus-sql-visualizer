## 三、TranslationPlugin 方案分析

### 3.1 TranslationPlugin 的实现

```java
// PlatformUtil.java - openOnlineDoc
public static void openOnlineDoc(Project project, boolean useHtmlEditor) {
    String url = Urls.OVERVIEW;  // 在线 URL
    if (canBrowseInHTMLEditor() && useHtmlEditor) {
        String timeoutContent = loadText("html", "Timeout.html");
        if (Urls.isReachable()) {  // Apache HttpClient 检测（走系统代理）
            HTMLEditorProvider.openEditor(project, title, url, timeoutContent);
            return;
        }
    }
    BrowserUtil.browse(url);  // 降级系统浏览器
}
```

### 3.2 关键差异

| 维度 | TranslationPlugin | 本插件（当前） |
|------|-------------------|----------------|
| **打开目标** | 在线 URL（`json.memoryzy.cn`） | `data:` URL（本地 HTML） |
| **CSS 加载** | 正常（在线 URL 无 `file://` 限制） | 丢失（`data:` URL CSS 支持差） |
| **网络检测** | `Urls.isReachable()`（Apache HttpClient，走系统代理） | 无网络检测 |
| **降级条件** | JCEF 不可用 或 网络不可达 | JCEF 不可用 |

### 3.3 TranslationPlugin 为什么有效

1. **在线 URL 无 CSS 限制**：`https://json.memoryzy.cn` 是正常 HTTPS URL，JCEF 加载无 `file://` 安全问题
2. **网络检测准确**：`Urls.isReachable()` 使用 Apache HttpClient，走系统代理，检测结果与 JCEF 实际访问能力一致
3. **降级策略合理**：网络不可达时降级到 `BrowserUtil.browse()`（系统浏览器走代理）

## 四、根因分析

### 4.1 JCEF 网络访问机制（2026-08-31 字节码取证修正）

**旧结论（已推翻）**：JCEF 启动参数包含 `--no-proxy-server`（平台硬编码），不走任何代理。

**2024.3 平台实况**（反编译 `app-client.jar`）：
- `JBCefProxySettings.getInstance()` 从 `HttpConfigurable`（IDE 设置：Settings → System Settings → HTTP Proxy）读代理配置，生成 `--proxy-server` / PAC 配置传给 JCEF
- 配了手动代理（`USE_HTTP_PROXY=true`）→ **JCEF 只走该代理，不直连**
- 未配代理 → 直连（`--no-proxy-server` 语义）
- 代理认证由 `JBCefProxyAuthenticator` 弹窗处理，无需插件介入

**推论**：可达性检测必须与 JCEF 同栈（IDE 手动代理优先，其次直连），否则误判。

### 4.2 本插件目标 URL 的网络情况

```
nslookup plugins.jetbrains.com
→ 13.225.117.128 / 13.225.117.8 / 13.225.117.9  (CloudFront CDN)
```

- 本机直连（`Proxy.NO_PROXY`，curl 实测）→ HTTP 200 ✓
- JCEF（走 IDE 代理，代理不可用/规则拒绝时）→ 加载失败 ✗
- 用户实测：内嵌打开 10s 超时 → 显示超时页（见「九、第二轮修复」问题一）

### 4.3 data: URL 的问题（2026-08-31 修正）

`data:` URL 经 `loadURL` 加载时 CSS 渲染丢失（表格布局破碎）；但**同页面经 `loadHTML` 加载则内联 CSS 正常**（超时页截图实证）——根因是 `loadURL(data:)` 路径，不是 JCEF 渲染能力。本地兜底改用 3 参 `openEditor`（内部走 `loadHTML`）即可。

## 五、实施方案（2026-08-31 已实施）

### 方案：对齐 TranslationPlugin — 在线 URL + 代理降级

**核心思路**：
1. 检测目标 URL 是否可在 **无代理** 情况下访问（模拟 JCEF 实际能力）
2. 若可无代理访问 → `HTMLEditorProvider.openEditor` 打开在线 URL（CSS 正常）
3. 若需代理才能访问 → `BrowserUtil.browse()` 打开在线 URL（系统浏览器走代理）

**实施步骤**：

1. **添加无代理可达性检测**：
   ```kotlin
   fun isReachableWithoutProxy(url: String): Boolean {
       val connection = URL(url).openConnection(Proxy.NO_PROXY) as HttpURLConnection
       // 检测是否能直连
   }
   ```

2. **改造 HelpAction**：
   ```kotlin
   if (isReachableWithoutProxy(ONLINE_URL)) {
       // JCEF 可直连 → 编辑器标签页打开在线 URL
       HTMLEditorProvider.openEditor(project, title, ONLINE_URL, timeoutHtml)
   } else {
       // 需代理 → 降级系统浏览器（走代理）
       BrowserUtil.browse(ONLINE_URL)
   }
   ```

3. **保留本地 HTML 作为最终降级**：
   - 若在线 URL 完全不可访问（无网络），使用本地 HTML + `data:` URL

### 方案优势

- **CSS 正常**：在线 URL 无 `file://` / `data:` CSS 限制
- **网络自适应**：根据实际网络环境选择 JCEF 或系统浏览器
- **符合 TranslationPlugin 验证模式**：已在 TranslationPlugin 验证可行

### 方案风险

- **无代理检测可能不准确**：`HttpURLConnection` 的 `Proxy.NO_PROXY` 与 JCEF 的 `--no-proxy-server` 可能有差异
- **国内加速节点 IP 变化**：CloudFront IP 可能变化，需要实际验证

## 九、第二轮修复（2026-08-31 16:00）— 三个实测问题的根因与修复

### 问题一：内嵌浏览器显示超时页，未加载出在线文档

**现象**：点 ? → 内嵌标签页显示"页面加载失败"超时页（在线文档没加载出来）。

**根因**（字节码取证，app-client.jar）：
1. `HTMLFileEditor` 对 URL 请求：`loadURL(url)` + `Alarm.addRequest(显示超时页, Registry["html.editor.timeout"] 默认 10000ms)`——**10 秒没加载完就显示超时页**；
2. JCEF 请求走 **IDE 的 HTTP Proxy 设置**（`JBCefProxySettings` ← `HttpConfigurable`），配了手动代理就只走代理；
3. 第一轮修复用 `Proxy.NO_PROXY` 直连检测（本机直连 curl 200），与 JCEF 实际网络栈（IDE 代理）不一致 → 误判内嵌可行 → JCEF 走不可用的 IDE 代理 → 超时。

**修复**：检测栈对齐 JCEF——
- IDE 配了手动代理（`USE_HTTP_PROXY && !USE_PROXY_PAC`）→ 用 `HttpConfigurable` 的 host/port 构造 Proxy 检测（JCEF 同栈，结果一致）；
- 代理不可用 → `BrowserUtil.browse()` 系统浏览器（Windows 系统代理与 IDE 代理可能不同，仍有救）；
- IDE 未配手动代理（No proxy / PAC）→ `Proxy.NO_PROXY` 直连检测；直连不通 → 本地 HTML 兜底。

### 问题二：超时页"点击此处"无法跳转

**根因**：bundle key `help.html.timeout.action` 是纯文本（"点击此处用系统浏览器打开：{0}"），根本不是 `<a>` 链接。

**修复**：
- 文案改为 `<a href="{0}">点击此处用系统浏览器打开</a>`（中/英两个 bundle 同步）；
- `buildTimeoutHtml` 对 URL 做 HTML 转义（`&` → `&amp;`），防破坏 href 属性；
- 平台机制背书：`HTMLFileEditor` 的 `onBeforeBrowse` 把页内任何链接导航转成 `BrowserUtil.browse`（系统浏览器），所以超时页链接天然可点。

### 问题三：为什么 TranslationPlugin 可以，我们不行

**TranslationPlugin 逻辑**（开发计划 3.1 节已收录 `PlatformUtil.openOnlineDoc`）：
1. 文档 URL 是自建站点 `json.memoryzy.cn`（**国内直连可达**）——JCEF 无论走 IDE 代理还是直连，都能在 10s 内加载完成，内嵌天然成功；
2. `Urls.isReachable()` 用 Apache HttpClient **走系统代理** HEAD 检测，通过才开内嵌，否则 `BrowserUtil.browse()` 降级——检测与降级配套，不会"开了内嵌却白屏"；
3. 本质：**它选了一个 JCEF 不用代理也能访问的 URL**，代理问题被绕开了。

**我们的差异**：目标 `plugins.jetbrains.com` 在国内网络下 JCEF 加载超时；且第一轮检测栈（直连）与 JCEF 实际栈（IDE 代理）错位。

**我们的对策**（用户提示"可以使用本地代理"）：
- 检测栈对齐 JCEF：IDE 手动代理优先 → 代理可用时内嵌能加载成功；
- 代理不可用 → 系统浏览器（走 Windows 系统代理，可访问本地代理如 Clash）；
- 完全离线 → 本地 HTML 兜底（改为 3 参 `openEditor` 走 `loadHTML`，内联 CSS 正常，不再用 data: URL）。

**修复**：中英文案统一改为 `<a class="link" href="{0}">…</a>`，继承模板配色。

### 10.2 目标 URL 切换为自建站点

`HELP_DOCUMENTATION_URL` 改为
`https://mybatis-plus-sql-visualizer.jvtools.cn/features/wrapper-preview.html`（单常量改动，
检测与降级逻辑自动适配）。

**切换前后网络实测对比**（curl，同一台机器）：

| 目标 | 直连（`--noproxy`） | 系统代理 |
|------|-------------------|---------|
| `plugins.jetbrains.com`（旧） | HTTP 200，1.4s | — |
| `mybatis-plus-sql-visualizer.jvtools.cn`（新） | 超时 ✗ | 308 → 200，~2s ✓ |

**结论**：新域名当前**直连也不通**，与旧域名同属"国内需代理"特征，故未改变 JCEF 的加载
难度。切换的价值在于**站点自主可控**——后续接国内 CDN（腾讯云 COS / 阿里云 OSS 等）后，
JCEF 不配代理即可内嵌加载，从根本上绕开代理依赖。

### 10.3 网络方案可行性调研（ESA / jsDelivr / Gitee）

为"国内免代理可直连"评估了三类托管（全部本机 `--noproxy` 实测）：

| 方案 | 国内直连 | 耗时 | 门槛 | 结论 |
|------|---------|------|------|------|
| 阿里云 ESA「中国内地/全球」 | 未测 | — | **必须 ICP 备案** | 未备案不可用 |
| 阿里云 ESA「全球不含内地」+ 内地优化 | 未测 | — | 免备案但明文禁止内地请求访问内地节点 | 不解决国内可达 |
| jsDelivr（fastly/testingcf 镜像） | 200 ✓ | 0.5s | 免费免备案，但**仅支持 GitHub/npm/WordPress 源** | 需配合 GitHub |
| GitHub Pages | 200 ⚠️ | 5.1s | 免费免备案 | 逼近 JCEF 10s 超时，不可靠 |
| Gitee raw 直链 | 200 | 0.6s | 免费免备案 | **Content-Type=text/plain，不渲染 HTML**，致命 |
| Gitee Pages | 404/超时 | — | 实名+审核；2026 年有停服反馈 | 状态存疑 |
| 本地 HTML（loadHTML） | 不依赖网络 | 秒开 | 无 | **唯一零门槛零风险** |

结论：免备案前提下没有任何在线托管能同时满足"国内直连 + 渲染 HTML + 稳定"三条件
（jsDelivr 需 GitHub；Gitee raw 不渲染；Gitee Pages 状态存疑；ESA 需备案）。

### 10.4 定稿：本地 HTML 为主路径（2026-08-31 17:10）

**决策**：放弃在线文档作为内嵌主路径，本地 HTML 定稿为主方案。

理由：
1. IDE 插件帮助文档**本应随插件版本走**——用户装 vX 看到的就该是 vX 的说明；
   在线"最新文档"与旧版插件功能错位，反而误导；
2. `marketplace-custom-page.html` 为**纯内联 `<style>`**（15.8KB，零外部依赖：
   无 link/script/img/@import/url()），`loadHTML` 渲染样式 100% 完整，
   且不发起任何外部请求——不存在资源加载失败导致缺样式；
3. 零成本、零备案、零审核、零维护、100% 可用。

**代码落地**（`HelpAction` 重写为极简版）：
- JCEF 可用 → `openEditor(project, title, html)`（3 参，内部 `loadHTML`）直接开本地页；
- JCEF 不可用 / 资源缺失 / 异常 → `BrowserUtil.browse(HELP_DOCUMENTATION_URL)` 系统浏览器；
- **删除**：`checking` 防抖、`ProbeResult`、`probeJcefReachability`、`isReachable`、
  `openOnlineInEmbeddedBrowser`、`buildTimeoutHtml` 及全部网络探测逻辑；
- 保留：`Timeout.html` 资源与 `help.html.timeout.*` bundle key（零成本，未来在线方案可复用）。

**样式验证路径**：本地页与超时页同走 `loadHTML` 渲染，超时页样式早已截图实证正常，
故本地页样式完整性等同有实证背书。

**后续待办（可选）**：为 `jvtools.cn` 接入国内 CDN，届时移除/放宽代理检测即可全场景内嵌成功。

### 遗留观察

- 若 IDE 配了可用代理（如 `127.0.0.1:7890`），内嵌浏览器将能正常加载在线文档——这正是"本地代理访问"的落地路径；
- 更彻底的方案（可选）：把文档镜像到国内可达站点（如 Gitee Pages / 腾讯云 COS），让 JCEF 无代理也能加载，彻底绕开网络问题；若采纳需改文档托管与发布流程，另行立项。
