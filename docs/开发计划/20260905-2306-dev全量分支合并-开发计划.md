## 二、合并顺序与依据

固定顺序：**master → perf/redline-hardening → m39 → m44 → m37 → jdbc-template**。

依据：
1. master 最先：基线最新（含 v2026.9.4 发行与文档基线），且 dev 是其直接祖先，可快进。
2. perf 紧随：它完整包含 master 顶端（merge-base = 44e8eb2），master 合完后同样快进；性能红线版本是各热点文件的最新治理形态，先落位可让后续冲突尽量按"以 perf 为准"单向解决。
3. m39 → m44：同族 ORM 缺口补全，提交量小（3 / 5），冲突面集中在 ORM 覆盖矩阵文档与转换器注册，小步合并便于定位。
4. m37：体量最大（相对 master 28 提交），竞品融合横跨预览面板/设置页/EXPLAIN，放后面集中处理。
5. jdbc-template 最后：基线最旧且落后 dev 2 提交，必是真合并；其版本号（2026.9.2）是旧值，与 master 发行版冲突时以 master 为准。

## 三、冲突预判与解决原则

预判热点：
- **版本号**（gradle.properties / build.gradle 等）：master 2026.9.4 为准，jdbc 的 2026.9.2 与 m37 期中间值一律弃用。
- **CHANGELOG.md / 变更记录.md**：各分支条目全部保留，按既有条目格式合并。
- **docs/架构设计/ORM 覆盖矩阵**：m39 与 m44 都有勾行，逐行取并集。
- **docs/MEMORY.md / memory-archive**：master 已做第三次精简（大量归档移动），以 master 的精简后结构为基线，分支在旧结构上的新增条目迁移到新位置保留。
- **plugin.xml**：各分支扩展点声明（psource 预览、JOIN 图、AutoShowSuppress、perf 相关）按序全部保留。
- **源码重叠**：`ui/SqlPreviewPanel.kt`（perf 击键防抖 / jdbc 图标错位 / m37 AutoShowSuppress）、`log/*`（perf 流式重写 / jdbc 历史读回）、`ui/gutter/*`（两侧各自新增 marker）。此类冲突以 perf 治理版为底，把对方语义重新叠加，不允许整边取走。

解决原则：
1. 性能红线优先：与其他分支冲突时先采用 perf/redline-hardening 的实现，再把对方功能语义叠加进去。
2. 版本与发行信息以 master 为准。
3. 冲突两边都是独立交付的完整功能，禁止"顺手删一边"；静态判断不了的以测试定胜负。
4. 文档类冲突逐行合并，不整段取一边。
