# 插件自更新静默失败修复开发计划

> 状态：✅ 已修复（2026-08-20，全量测试全绿）
> 需求来源：用户日常 IDEA（2026.2.1 Windows）从 2026.8.18 更新到 2026.8.19，内置更新机制提示「更新成功」并重启，但实际版本仍为 2026.8.18。

## 1. 目标与范围

修复插件自更新（M28）在 Windows 上静默失败的缺陷——症状恒定为：`lib/` 下新旧两版本 JAR 共存、旧 JAR 不删除、重启后版本号仍是旧版。

本任务经多轮排查，最终定位为**三处叠加断点**。前两轮排查走了弯路（只修路径归一化），第三轮通过真实 IDE 诊断日志 + 反编译平台类彻底定位。

## 2. 症状与故障链路

用户已装 2026.8.18 → 内置更新下载 2026.8.19 → 通知「更新完成，重启生效」→ 重启 → **版本仍是 2026.8.18**。

故障链路：
1. 下载 zip 成功（`downloadAndInstall: downloaded … 1345749 bytes`）
2. `install()` 被调用
3. **DeleteCommand 未正确调度**（核心）
4. UnzipCommand 解压新版 JAR 到 `lib/`
5. 旧 JAR 未删 → `lib/` 两 JAR 共存
6. 两 JAR 内均有 plugin.xml，IDEA 从旧 JAR 加载 → 版本号旧版

## 3. 三处叠加断点

### 断点①：`codeSource.location` 在 2026.2 返回 null（第一根因）

`getPluginJarPath()` 用 `protectionDomain.codeSource.location` 拿插件 JAR 路径。**IDEA 2026.2.1 实证返回 null**（日志：`getPluginJarPath: codeSource.location is null`），`?.let` 短路 → 始终返回 null → DeleteCommand 永不调度。

> ⚠️ 弯路：最初假设是「路径未归一化」（`file:` 前缀 → `Path.of()` 抛异常的 `InvalidPathException`），为此加 `normalizeDescriptorPath()`——**但这无济于事**。因为 `location == null` 时 `?.` 链根本不进归一化分支。`getPath` 类工具对 null 无能为力，必须换路径来源。

### 断点②：`UnzipCommand` 执行了，但缺 DeleteCommand

即便修好①，`addActionCommand(UnzipCommand)` 只解压不删除 → 旧 JAR 残留。download/persist 均正常（补丁包已持久化到 `system/mpvs-update/`）。

### 断点③：DeleteCommand 目标目录名误用 `<id>` FQN（二次修复才暴露）

回退方案 `PathManager.getPluginsDir() / PLUGIN_ID`——但**插件 `<id>` 是 FQN `cn.song…mybatis-plus-sql-visualizer`，实际安装目录名是 zip 顶层短名 `mybatis-plus-sql-visualizer`**（Install from Disk 剥顶层，目录名取自 zip 顶层）。按 FQN 删除 → 目录不存在 → 扑空 → 旧 JAR 依旧不删。

## 4. 最终修复（PlatformPluginInstaller.kt + UpdateSource.kt）

1. **Fallback 到 `PathManager.getPluginsDir()`**：`codeSource.location` 为 null 时用平台目录 API（`PathManager.getPluginsDir()/INSTALL_DIR_NAME`）定位，三平台通用，不依赖 classloader 实现细节。
2. **目录名用 zip 顶层短名**：`UpdateSource.INSTALL_DIR_NAME = "mybatis-plus-sql-visualizer"`（新增常量），**不能直接用 `<id>` FQN**。
3. `DeleteCommand` 删除**整个插件目录**（`DeleteCommand.execute` 内部 `NioFiles.deleteRecursively` 递归删除，javap 实证），比删单个 JAR 更可靠。
4. 开发态守卫：`jarPath` 与 `pluginDir` 两个候选都检查构建特征段。
5. 全程诊断日志（`LOG.info/WARN` 打印 jarPath/pluginDir/DeleteCommand/UnzipCommand 目标），真实 IDE 断点定位——单元测试测不到真实路径形态。

```kotlin
// UpdateSource.kt
const val INSTALL_DIR_NAME = "mybatis-plus-sql-visualizer"  // zip 顶层目录名，非 <id>

// PlatformPluginInstaller.kt
internal fun pluginDirPath(): Path =
    PathManager.getPluginsDir().resolve(UpdateSource.INSTALL_DIR_NAME)
```

**验证关键信号**（真实 IDE 日志）：

## 7. 平台兼容与教训

| 平台 | 目录定位 | 说明 |
|---|---|---|
| Windows | `…\plugins\mybatis-plus-sql-visualizer` | `PathManager` 自动返回 Roaming 路径 |
| Mac | `/Users/…/Application Support/JetBrains/…/plugins/mybatis-plus-sql-visualizer` | 同上 |
| Linux | `~/.local/share/JetBrains/…/plugins/mybatis-plus-sql-visualizer` | 同上 |

**核心教训**：
- 代码里凡是重构「插件安装目录名」的路径，**直接查已安装 zip 顶层目录名**，不要臆断为 `<id>` FQN。
- `codeSource.location` 为 null 是平台差异（262 实证），优先用 `PathManager` 系 API 兜底；`getPath` 类工具对 null 无能为力。
- 自更新「重删旧装新」的链路断点（jarPath/pluginDir/DeleteCommand/UnzipCommand 目标）headless 测试测不到，须加诊断日志在真实 IDE 断点定位。
