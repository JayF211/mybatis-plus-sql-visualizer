## 一、本轮定位：T6 之后还剩什么

T6 的终局定案是「**浮动作结构已是语义锁定下的最优编排**」，但支撑该结论的证据等级是**定性推理**（"任何重排序都是串行化（更慢），任何缓存都是语义变化"），不是实测——L2（错峰编排）在 T6 内始终停留在「若读数支持」候选位，从未做过时间性错峰的实验；六项销案杠杆里也没有任何一项触碰过 verifier 进程自身的 JVM 参数或测试 JVM 堆大小。

本轮 = 把 T6 留下的三条窄缝做实测定案（转正或销案）。**即使全销案，产出同样成立**：把「地板声明」的证据等级从推理升格为进程级曲线实测背书（T6 先例：销案结论同样是产出）。

### 1.2 剩余理论空间的结构性来源

长杆 verifyMarketplace 的争用系数 +86s（588.7 solo → 674.3 同窗）与分片窗争用膨胀（209~236 争用窗 vs 165~186 solo 带，+50~70s）是**同一并发的两面**：5 JVM + 2 verifier 全并发互相拖累。理论回收上限 ≈86 + 50~70 ≈ **150s（-22%）**；实现它需要「marketplace 独占段 + 嵌入段」的时间性错峰成立，前提是 verifier 进程的 CPU 曲线存在低占用段（在线下载等待期）。**若曲线全程高位，则争用系数是纯 CPU 排队，任何错峰都只是串行化换皮，N1 当场销案**——这正是探针要回答的问题。

## 二、目标与非目标

**目标**：三条窄缝逐项读数定案。预期管理（诚实口径）：N1 上限 −150s、中位预期 −0~86s、下限 0（销案）；N2/N3 属关账型白捡实验，效应若无 ≥5% 即销案。转正项落构建脚本改动，销案项落台账证据。

**非目标（红线，继承 T6 全部）**：
- 门禁内容零删减：五环节（buildPlugin / verifyGate / verifyMarketplace / testShards / e2eFakeIde）一个不少；三目标 × 2 道兼容门禁口径不变；testExternal 护栏桶、agent 测试、e2e 探针不变；
- 不动 marketplace 在线语义（在线 freshness + 无豁免是 Marketplace 判定对齐的本体；verdict 按 commit 缓存 = 语义阉割，T6 W1 已否决勿再提）；
- 不动测试执行语义与分片算术（testHeapSize 是 T-TestPerf2 P9 立案的堆大小开关，不改测试逻辑，且「是否转正由实测收益定」本就是它的悬案——转正与否均不改任何测试的执行内容）；
- 不复活 T6 已销案的 L1（verifier 拆目标进程——进程内已并发）、L3（e2e 重叠）、L5（verify-home 迁出 build/）；
- dev 未经允许不合 master（用户明令），本分支不合 dev（合流待批）。

**验收判据（parity 三断言，对齐 T6 口径 + dev 新基线）**：终轮 releaseGate 全绿读数中，①testShards ≥6522 例 / failures=0 / skip=9（docker 离线口径）+ testExternal 40 例 + agent ≥112 例 0 失败；②verifyGate + verifyMarketplace 六判定全 Compatible，问题计数与 dev 基线读数逐字一致（0 未登记块）；③e2eFakeIde PASS=26 FAIL=0。

## 四、待验证前提（实施者先证伪再动手）

- **前提 A（N1 的生死线）**：verifyMarketplace 进程 CPU 曲线存在低占用段（均值 <40% 单核折算，持续 ≥60s）——在线下载/市场元数据等待期的存在性。探针 R1 直接回答；不存在则 N1 销案，同时把「争用系数 +86s 是纯 CPU 排队」写入台账，T6 地板声明的证据等级升格为实测。
- **前提 B（N2 的生死线）**：R1 曲线显示 verifier 进程 Commit 峰值 <3GB。满足则 GC 税大概率非瓶颈，N2 免跑 A/B 销案；不满足（堆压力大）才做 `-Xmx` A/B。
- **前提 C（N3 判据）**：512m → 2g 效应 <5%（机器窗口漂移 ±5~8% 量级以内）即销案维持缺省；≥5% 且两轮复现才转正（gradle.properties 写死 `testHeapSize=2g`）。
- **前提 D（实验窗资源）**：authority 对照基线是 T6 的 683s（夜间低争用暖窗）。本轮实验全部安排夜间单车道低争用窗（对表 parallel_tasks 登记表为空 + Commit 底噪 <60GB 才开轮）；任何与并行会话构建并窗的轮次一律弃样（T6 R2 教训：双车道顶格 74.69GB 成片 OOM）。
- **前提 E（warm 与弃样）**：rp7 新树首轮自带 buildSrc 编译税 + verify-home idb 冷建 + 权重表冷启动（T15 教训⑤），R0 冷跑只验链路通不进计时；计时轮全部 warm 且同窗交错（T5 定例）。
- **前提 F（环境前置在位）**：e2e 硬依赖本机 MySQL 127.0.0.1:3306（20261007 02:45 实测 LISTENING）+ demo 工程在位（已核）+ docker 离线（skip 9 口径正常）。轮前复验；MySQL 失联则 e2e 环节硬失败属既有语义，不静默跳过，登记后等恢复。
- **前提 G（错峰实现形态的可行性）**：若 N1 进入实验，时间性延迟在 Gradle 的落点 = 分片叶子任务的 `doFirst { Thread.sleep(...) }` 形态（配置期不可为、执行期延迟）或 shared build service 资源闸。先小样验证 sleep 形态与配置缓存/并行调度兼容（不破坏 up-to-date 与锚点），形态不可行即 N1 销案——不为 150s 上限引入脆弱编排；转正与否额外要求编排改动通过 `-PtestStagger=off` 一键回退且默认 off（终局默认形态见 D80 拍板）。
