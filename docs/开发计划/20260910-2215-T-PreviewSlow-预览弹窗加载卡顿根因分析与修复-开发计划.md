## 一、现象与日志证据

### 1.1 用户现象

SQL 日志列表双击某条 SQL → 弹出 SQL 预览弹窗，从点击到弹窗就绪有可感知的卡顿（用户定性「加载时间较长」），并非偶发，每次都会。

### 1.3 全链路时间钉死

| 阶段 | 时间戳 | 耗时 | 说明 |
|------|--------|------|------|
| 双击 → `createEditor` 起点 | 19.xxx → 23.169 | **约 3.07s** | 最大头。期间无任何插件日志，是纯阻塞（预热临时文件的**有界 EDT 自旋等待**） |
| `createEditor` → 临时文件降级 WARN | 23.169 → 25.233 | 2.06s | 同上（`awaitPrewarmedTempFile` 的 `Thread.sleep` 自旋） |
| 降级 → 控制台准备启动 | 25.233 → 25.252 | 19ms | 快速 |
| 控制台准备段 | 25.252 → 25.258 | 6ms | 极快，但**失败**（挂载链踩平台断言） |

**结论**：卡顿的绝对大头不是控制台准备，也不是 DB 连接，而是 `createEditor` 里「预览临时文件」支链的 **EDT 上同步自旋等待**（`Thread.sleep` 轮询预热线程产物），单次预览耗掉约 3 秒。控制台挂载失败是**伴随的第二个 bug**，不占耗时但让「预览即 DBN 控制台」这一设计在真机上从未生效。

## 二、根因（两个独立问题）

### 根因一（耗时主因）：`awaitPrewarmedTempFile` 在 EDT 上 `Thread.sleep` 自旋轮询

位置 `SqlPreviewPanel.createEditor` → `awaitPrewarmedTempFile()`（`SqlPreviewPanel.kt:372`）：

```kotlin
private fun awaitPrewarmedTempFile(): Pair<VirtualFile, PsiFile>? {
    var waited = 0L
    while (true) {
        val ready = prewarmedTempFile?.also { prewarmedTempFile = null }
        if (ready != null) return ready
        if (waited >= PREWARM_WAIT_MS) return null          // 2000ms 上限
        Thread.sleep(PREWARM_POLL_MS)                        // 20ms 间隔
        waited += PREWARM_POLL_MS
    }
}
```

预热线程（`prewarmPreviewTempFile`）干的是 `File.createTempFile` + `LocalFileSystem.refreshAndFindFileByIoFile` + `ReadAction.compute { PsiManager.findFile }`——一次**同步 VFS refresh + PSI 解析**，冷态下几百毫秒到数秒不等。而 `createEditor` 在 **EDT 鼠标事件**里调用上面的自旋等待，等于把整个预热延迟同步烧进 UI 线程：

- 冷启动（首个临时文件）时 `refreshAndFindFileByIoFile` 慢，EDT 卡 3 秒等它；
- 即使预热失败/超时（`PREWARM_WAIT_MS=2000` 触顶），`createEditor` 也已经白卡了 2 秒才走降级分支（日志里 `fall back to in-memory editor` 直接坐实了这条路径——降级也救不回已烧掉的那 2 秒）。

> 注：这段自旋是早期「预热线程抢在 createEditor 前就绪」的产物，把「后台预热」用「前台死等」兑现了，与 T-PreviewFlash 想把慢操作移出 EDT 的初衷相悖。

### 根因二（伴随缺陷）：`prepareInConsole` 用 `ReadAction` 包 `attachConsole`，触发「ReadAction 内不能再开 WriteIntentReadAction」硬抛

位置 `DataSourceSelector.prepareInConsole`（`DataSourceSelector.kt:1119`）：

```kotlin
val console = ReadAction.compute<Any?, Throwable> {
    attach.invoke(null, project, session, vf)   // DBN 内部 EditorImpl.<init> → setHighlighter → WriteIntentReadAction
}
```

真机日志完整链（`idea.log` 里唯一一条 `Caused by`）：

```
Caused by: java.lang.IllegalStateException: WriteIntentReadAction can not be called from ReadAction
    at NestedLocksThreadingSupport.runWriteIntentReadAction(...:704)
    at WriteIntentReadAction.computeThrowable(WriteIntentReadAction.java:55)
    at EditorImpl.setHighlighter(EditorImpl.java:1832)          // ← EditorImpl 构造里要开 WIRA
    at EditorImpl.<init>(EditorImpl.java:639)
    at ConsoleExecutionEditor.<init>(ConsoleExecutionEditor.java:55)
    at LanguageConsoleImpl.<init>(LanguageConsoleImpl.kt:74)
    at DatabaseSessionViewServiceImpl$MyLanguageConsoleImpl.<init>
    ... MessageBusSession.attach → JdbcConsoleProvider.attachConsole
    at cn.song...DataSourceSelector.prepareInConsole(DataSourceSelector.kt:1120)
```

说明：T-PreviewDocLock2 的 F1 为了让 attachConsole 满足读权限，用 `ReadAction.compute` 把整段 attachConsole 包了起来；但 DBN 的 `attachConsole` 底层要 `new EditorImpl`（建控制台编辑器），而 `EditorImpl` 构造里 `setHighlighter` 走 `WriteIntentReadAction`，平台锁层 **明文禁止在 read-action 内再开 write-intent-read-action**，于是 `IllegalStateException` 被 `runCatching` 吞掉 → `prepareInConsole FAILED: InvocationTargetException`，控制台**从未真正挂载成功**。

后果：
- 预览面板里「原生 DBN 控制台」在这台 262 真机上每次准备都失败，静默回落到纯自研编辑器（用户看到的是无 DBN 工具栏的退化预览）；
- 平台在 `read-action + WIRA` 双重锁叠加下虽然不炸 UI，但每次预览都白跑一趟失败的挂载链。
- 与耗时：这条失败链本身只烧 6ms（不占大头），但它是「预览即 DBN 控制台」从未生效的根因，也顺带解释了为什么日志里 `attachConsole -> $console` 永远 null / 后续 `editor$` 一段从不打印。

**为什么 T-PreviewDocLock2 当时没发现**：F1 的验收标准是「262 真机 `grep` 读权限 `SEVERE` 零增量」，靠的是「读权限断言日志是否新增」。这个 WIRA-in-ReadAction 是**写意图锁**的一类，且被 `runCatching` 吞成 `InvocationTargetException: null`（不带 `Read access` 关键词），不落在「读权限断言」的 grep 面内 → 修复引入了新的、更难发现的锁嵌套冲突，且因为静默降级，沙盒测试（243，Database 插件链路不会真跑 attachConsole）也测不出来。这正是「平台加固型缺陷是 243 测试沙盒固有盲区，判定只能靠 262 反编译 + 真机日志」的又一实例。

## 三、修复方案

### F1（耗时主因）：预热产物「事件等待」替换「EDT 自旋」，超时后不烧 EDT

不在 EDT 上 `Thread.sleep` 等预热线程。改为：

1. **预热产物改为一次性计数/信号**：预热线程完成后 `invokeLater` 通知；`createEditor` 若产物未就绪，**立即**走纯内存降级分支（不等待），由预热完成的回调在后续重建时自然补上 PSI 路径。
2. 或最小改动：`awaitPrewarmedTempFile` 的等待预算从 2000ms 砍到经验值的几十毫秒（若预热线程还没跑完，说明首次冷启动，直接降级避开本次卡顿，下次打开面板时预热已就绪、走 PSI 主路径）。

> 取舍：方案 2 改动最小、语义最贴近现状（主路径仍尽力走 PSI），且首次冷启动的「降级态无补全」在一次预热完成后立即自愈（第二次打开即走 PSI）。推荐方案 2 作为落地，方案 1 作为其后更彻底的演进（跨会话不重复烧 EDT）。
>
> 不变的约束：`project==null` 与降级分支的纯内存模板已存在（`EditorFactory.createDocument(sql)`），复用即可；预热线程/`releaseEditor` 清理逻辑零改动。

### F2（伴随缺陷）：`prepareInConsole` 去掉 `ReadAction` 包 attachConsole，改为真正的平台入口语义

DBN 的 `attachConsole` 是「平台自带读权限 + 内部自行 `invokeLaterIfNeeded` 切 EDT」的第三方链入口，它自己会在需要时开 `WriteIntentReadAction`（`EditorImpl.setHighlighter`）。我们**不该**用 `ReadAction` 把它整个包死。修复：

1. 把 `:1109` 的 `ReadAction.compute { attach.invoke(...) }` 还原为直接 `attach.invoke(...)`（去掉外层 ReadAction）。
2. `:1116` 的 `console.getDocument()` 反射同样去掉 `ReadAction` 包裹（它踩的是 `FileDocumentManager.getDocument` 的读断言，但该调用点在 attachConsole 成功返回、console 已建好的前提下，其内部已由 DBN 的正常挂载链在合法线程/锁上下文执行）。

**读权限回归风险**与验证：T-PreviewDocLock2 当初加 ReadAction 是为压 `LanguageConsoleImpl$Helper.getDocument` 的 `softAssertReadAccess` 刷屏；去掉后若读权限 `SEVERE` 重新冒头，正确处置是把「真正需要读权限的最小读模型段」包 ReadAction，而不是把会新开 WIRA 的 `EditorImpl` 构造/高亮链也吞进去。即：**从「整段包」改为「按需最小包」**——attachConsole 交给 DBN 内部自行处理读权限，我们只对「我们自己触发的纯读模型访问」包 ReadAction；`console.getDocument` 若实测仍刷断，单独为这一句包 ReadAction（它不触发 WIRA）。

## 四、验收标准

- 全量 `./gradlew test` 绿（243 沙盒，量级与既有基线比对，零回归）。
- 262 真机日志：
  - 双击预览 `showSql` 出现时间相对点击时间，从约 3s 降到可感知以下（冷启动首次 ≤ 几百毫秒，热态近瞬时）；
  - `prepareInConsole FAILED: InvocationTargetException` 归零（`grep -c` 字面量）；
  - `WriteIntentReadAction can not be called from ReadAction` 归零；
  - 「读权限 `SEVERE`」相对修复前**零增量**（`grep -c "c.i.u.ThreadingAssertions" 或 Read access` 增量校验，防 F2 回退引入）。
- 真机走查「双击预览 → 点执行」链路，确认原生 DBN 控制台正常挂载（预览面板出现 DBN ▶ 工具栏，而非退化自研编辑器）。

## 五、风险与边界

| 风险 | 评估 | 处置 |
|------|------|------|
| F1 砍等待预算后，首次冷启动走降级态（无补全/自建高亮） | 低（仅首开一次，预热完成后自愈） | 日志 WARN 定位；确保第二次打开走 PSI 主路径 |
| F2 还原 attachConsole 后读权限 SEVERE 回归 | 中 | 真机 grep 零增量校验；若回归按「最小包」只包纯读段，不包会开 WIRA 的高亮链 |
| F2 改动触及 T-PreviewDocLock2 已交付修复 | 中 | 保留「读权限协议」护栏结论，仅把「整段 ReadAction」改为「按需最小包」，同步更新其计划文档的 F1 结论 |
| 243 沙盒测不出 attachConsole 真实链路 | 高（固有） | 262 反编译 + 真机日志交叉验证为本计划主要证据；沙盒只做编译/单测回归 |

## 六、后续项

2. 沉淀全局 pitfall（候选）：**「write-intent-read-action 不能在 read-action 内再开」** —— 平台锁层明文禁止（`NestedLocksThreadingSupport.runWriteIntentReadAction:704`），`EditorImpl` 构造等平台链内部会开 WIRA，故包 ReadAction 的边界不能吞到这类链；被 `runCatching` 吞成 `InvocationTargetException: null`，极难归因。
