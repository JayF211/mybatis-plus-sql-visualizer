## 一、根因（真机日志逐行实证，不是推理）

同一秒内的四条日志锁死了整条链（13:43:12）：

```
12,589 WARN  [M36] exec doc write EDT dispatch timeout after 2000ms (EDT busy?)
12,590 WARN  [M36] exec file doc-write FAILED, fallback to raw write (no loaded document)
12,609 INFO  MemoryDiskConflictResolver - reload mpsql-exec.sql from disk?
12,609 INFO  MemoryDiskConflictResolver -   documentStamp:3903 / oldFileStamp:0
12,613 INFO  [M36] exec file updated via document+save (disk synced in-critical-section)
12,621 INFO  DumbServiceImpl - enter dumb mode [mybatis-plus-sql-visualizer-demo]
```

链：**冷启动 EDT 忙（随后即见 DumbService 进入 dumb）** → `dispatchDocWriteOnEdt` 有界等待
2000ms 超时返回 false → T-EC-02 兜底守卫查 `getCachedDocument(vf)` 得 **null**（此刻排队中的
EDT 写任务尚未执行、document 也还没建）→ **放行裸写盘** → 排队的 EDT 任务随后才跑，
`getDocument(vf)` **新建** document 并 setText 标脏（`oldFileStamp:0` 正是「文档建于磁盘写入
之前」的指纹）→ 裸写引发的 VFS 变更落到这个刚建出的文档上 → MemoryDiskConflictResolver
弹「重载 mpsql-exec.sql？」→ 23ms 后文档写入自己完成落盘。

**结论：插件与自己的排队写在赛跑，与外部改盘无关。** 该判据（`getCachedDocument == null`
= 无冲突面）在 EDT 繁忙时不成立，因此 T-EC-02 的「裸写兜底」不是兜底，而是**本链唯一的
制造者**——它是全链中唯一能让磁盘背着 document 变更的动作。

## 二、方案

**F1（唯一改动）：VFS 已有该文件即绝不裸写。** `projectExecFile` 中删掉「doc 写失败 → 查
守卫 → 裸写」整段；doc 写未完成（超时或 WriteAction 失败）时记录 warn 并**原样返回文件路径**
（调用方仍需 ioFile 做 refresh/方言映射）。VFS 无该条目（首次创建，不可能有 document 挂载）
维持裸写。

**F2：T-EC-02 守卫退役。** `canFallBackToRawWrite` 删除（判据已被实机证伪）。

语义守恒：「宁内容旧一拍」为既有裁定（T-EC-02 注释即此语义）——排队任务/later 的
console doc 同步链（`prepareAfterEditorResolved` 的 F2 同步、`executeOnConsole` 执行前同步）
都会重写并落盘；执行内容取自编辑器文档（用户所见），不受磁盘陈旧影响。

## 三、测试

| 用例 | 断言 |

## 五、风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 磁盘内容短暂陈旧 | 超时后本次不写盘 | 既有裁定（T-EC-02 起即「宁旧一拍」）；console doc 同步链在 attach/执行前都重写落盘；执行内容取编辑器文档 |
| 极端情况下排队任务永不执行 | EDT 长时间占用 | 下次预览/执行链重写；F5 防抖自动落盘仍守用户手改 |
