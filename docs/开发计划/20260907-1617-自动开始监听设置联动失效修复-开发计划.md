## 1. 问题现象

用户开启设置「项目启动时自动开始监听」（`settings.log.autoCapture`）后，项目（Spring Boot）启动运行，日志监听没有生效：图标不变、无 SQL 捕获。复现路径为「项目已打开 → 开启设置 → 运行项目」。

### 2.2 直接根因：边沿联动代码挂在未注册的死类上

「设置在项目已打开后才开启 → apply 时检测关→开边沿 → 遍历 openProjects 调 startCapture + 清 suppressed」这一修复是踩坑记录第九轮（2026-08-20，`pitfall-log-startup-capture-regression.md` §第九轮）的产物，代码现在完整存在于 `PluginSettingsConfigurable.apply()`（`config/PluginSettingsConfigurable.kt:45-63`）。

但设置页后来重构为「文件夹 + 分区子页」架构：plugin.xml（`src/main/resources/META-INF/plugin.xml:88-132`）注册的是 `PluginSettingsFolderConfigurable` + 五个 `SectionConfigurable` 子类（UiActions / SqlPreview / TableMapping / **SqlLog** / About）。`PluginSettingsConfigurable` **未注册**——从未实例化，apply 中的边沿联动是死代码。

用户实际勾选开关的位置是「SQL 日志」子页 → `SqlLogConfigurable` → `SectionConfigurable.apply()`（`SectionConfigurable.kt:31-35`），它只透传 `panel.apply()`（写状态、发 `SETTINGS_CHANGE_TOPIC`），没有边沿检测。`SqlLogManager` 对 `SETTINGS_CHANGE_TOPIC` 的订阅（`SqlLogManager.kt:115`）也只做 `applySettings()` + `refreshConsoleContexts()` + autoShow 逻辑，刻意不启动捕捉。

于是：`LogStartupCapture`（postStartupActivity）已随项目打开以 `false` 跑过一次不再触发；设置 apply 又无人调 `startCapture()`；运行控制台出现时无桥无监听，`onConsoleAppeared` 无从产生。这正是踩坑记录第九轮修的问题在设置页架构改造后的回归——**修复代码还在，挂载点死了**。

## 3. 修复方案

### 3.1 方案对比

| 方案 | 内容 | 结论 |
|------|------|------|
| A（采纳） | 边沿联动迁到 `SectionConfigurable.apply()` 基类：apply 前读旧值 → `panel.apply()` → 读新值 → 关→开则清 suppressed + 遍历 openProjects 调 `startCapture()` | 最小改动；覆盖任意承载该开关的子页；与原修复语义完全一致 |
| B | `SqlLogManager` 的 SETTINGS_CHANGE_TOPIC 订阅里做边沿 | 回调拿不到「变更前值」需新增 lastSeen 字段；且服务是 project 级、无项目时不存在，遍历 openProjects 的原语义反而别扭 |
| C | 恢复注册 `PluginSettingsConfigurable` | 与 Folder+Section 架构重复整页设置，不可行 |

### 3.2 行为语义（对齐踩坑第八/九/十/十一轮结论）

- 「关→开」边沿成立：`logAutoCaptureSuppressed = false`（重新表达诉求）+ `openProjects.forEach { startCapture() }`（`startCapture` 自带幂等守卫与无控制台 armed 态）。
- 非「关→开」apply（如改前缀后 Apply）：不做任何捕捉联动。
- `onConsoleAppeared` 现行守卫不动（`suppressed && !userArmed` 拦截、不清零语义维持 dev 现状）。

### 7.2 第二轮根因

`stopCapture()` 在 `logAutoCaptureOnStart=true` 时把 `logAutoCaptureSuppressed=true` **持久化**（第八轮语义：用户"停止"跨重启尊重），同时拆除轮询 + contentListener + Filter（全部检测链）。

此后自动捕捉的三个入口全部失效：
1. `LogStartupCapture`——postStartupActivity 只在项目打开时跑一次，两次 armed 已消费；
2. `SectionConfigurable.apply` 边沿——设置未再变更，不触发；
3. `onConsoleAppeared`——被第十一轮补的守卫 `suppressed && !userArmed` 拦截（该守卫防的是"重启后 armed 态复现"，但这里 suppressed 只该抑制**项目未运行期间**的 armed，不该永久封死项目启动）。

**矛盾点**：踩坑第十一轮已确立"设置优先——项目启动应始终自动捕捉"，但该轮修复只清了 armed 态复现，没有给"手动停止后再 Run 项目"留任何恢复入口。用户点击面板捕捉（manual）本来是恢复入口，但一旦点击后停止/或未点，自动链路就永久沉没——`Run x3` 后应用真跑起来，`capturing=false + suppressed=true`，无人应答。

（两次 stopCapture 均来自面板 CaptureAction 点击：工厂侧两个调用点各有守卫 `logStopOnToolWindowClose`（=false）+ 必有 INFO 日志，日志均无；ActionsLocalSummary 不记录无 action-id 的 inner class 按钮，故摘要无痕。）

### 7.3 第二轮修复（T-B1~B4）

- **T-B1** `SqlLogManager.onProjectProcessStarted()`：进程级启动回调——autoStart=true 时无条件清 suppressed（对齐踩坑第十一轮"设置优先"）+ `startCapture()`（幂等：已捕捉态 no-op、armed 且轮询活跃时跳过重复 attach）；autoStart=false 时 no-op 不动状态。
- **T-B2** `RunConfigurationProcessListener`（新文件，log 包）：反射订阅 `ExecutionManager.EXECUTION_TOPIC` 的 `processStarted`——`app-client.jar` javap 核验 243 平台接口签名（`processStarted(String, ExecutionEnvironment, ProcessHandler)` 三参版）；`Class.forName(…, platformClassLoader)` 显式平台 classloader（243 execution API 域，262 裁剪同样兼容）；任一环节异常静默降级 false（RCM 轮询兜底仍在）。**不处理 `processTerminated`**——对所有 RunProfile 触发（HTTP/profiler 均为进程），项目停止语义仍由 `onConsoleRemoved` 承担（踩坑第九轮 v2 误停教训）。
- **T-B3** `SqlLogManager.init` 末尾接线 `RunConfigurationProcessListener.subscribe(project, this)`（messageBus connect 挂 project 服务 Disposable，随项目关闭自动断开）。
- **T-B4** 测试 4 例（SqlLogManagerBehaviorTest T23~T26）：T23 suppressed 清除 + armed 进入（20:41 会话根因回归）；T24 autoStart=false 完全 no-op；T25 armed+轮询活跃时幂等（不重复 attach）；T26 控制台已存在时直接完整捕捉态。

### 7.5 第三轮修正（22:53 会话日志实证）——subscribe 反射踩泛型桥方法

22:53 会话日志：`RunConfigurationProcessListener: EXECUTION_TOPIC 不可用——降级为 RCM 轮询兜底`，异常为
`IllegalArgumentException: argument type mismatch`，栈指向 `subscribe(RunConfigurationProcessListener.kt:61)`。

**根因**：`connection.javaClass.methods.first { name=="subscribe" && parameterCount==2 }` 在运行时类上
拿到的是泛型擦除/协变桥方法（`SimpleMessageBusConnection.subscribe(Topic<L>, L)` 编译为
`subscribe(Topic, Object)` + 泛型签名方法并存），`javaClass.methods` 顺序不定——invoke 时 Topic 实参
落到非预期形参即抛 mismatch。`connect(disposable)` 同样是碰运气（实现类上可能有重载）。

**修正（T-B5）**：订阅链拆两半——
- messageBus/MessageBusConnection 是 `util.jar` 全平台稳定接口 → **编译期直调**
  `project.messageBus.connect(manager)` + `connection.subscribe(topic, listener)`，零反射；
- 只对 execution 域（可能被 IPGP 裁剪/移位）保留反射：`ExecutionListener` 与 `EXECUTION_TOPIC`
  两个 `Class.forName` 独立 try，任一失败单独降级日志。

**教训**：反射调平台 API 前先查该类是否本就在插件编译类路径上且全平台稳定——`javap` 确认
`MessageBusConnection`/`SimpleMessageBusConnection` 在 `util.jar`（非 app-client execution 域），
编译期直引合法且 Marketplace 安全；**反射方法选择绝不用 `methods.first { name==… }`**，
桥方法/重载序不定，必须用 `getMethod(精确签名)` 或干脆不反射。

### 7.6 第四轮（2026-09-08 08:29 会话日志实证）——被动模式：开启设置不再立即 armed

第三轮修复后进程级入口已生效（08:32:44 `已订阅 EXECUTION_TOPIC`；08:33:15/08:35:46 两次 Run 均由
`onProjectProcessStarted` 驱动捕捉成功）。用户随后反馈新问题：**开启「项目启动时自动开始监听」后，
还没 Run 项目，监听（按钮 ⏸）就自动开启了**——08:33:01 边沿联动按第九轮历史设计立即 `startCapture`
进入 armed 态，用户 2.4 秒后点了停止（08:33:03）。

该 armed 边沿是历史产物：当时（无进程级事件）armed 是唯一能让"项目已打开后开启设置 → 下次 Run 自动捕捉"
生效的机制。进程级入口接管后机制冗余，且与用户语义冲突——**「开启设置 ≠ 监听已开启」**。

**修正（T-C1~C3）**：被动模式分流——
- `SqlLogManager.processListenerActive`（订阅结果落属性，internal set 供测试）；
- `SqlLogManager.onAutoStartSettingEnabled()`：清 suppressed 后分流——进程级可用=被动（不预 armed、
  不挂轮询，按钮保持原状，Run 事件驱动捕捉）；不可用=降级进 armed（RCM 轮询为唯一检测通道，原语义）；
- `SectionConfigurable.apply` 边沿改调 `onAutoStartSettingEnabled()`（原直调 startCapture）；
- `LogStartupCapture.execute`：`processListenerActive=true` 时项目打开**完全被动**（既不 armed 也不
  startListeningOnly——恢复链由 Run 事件自洽：清 suppressed + startCapture）；降级时维持原分支。

测试：T27（被动不 armed+不挂轮询+清 suppressed）、T28（降级维持 armed 原语义防回归）；原 T23~T26
（进程级恢复链）不变。

**边界说明**：被动模式下，设置开启前已在运行的项目不会被立即捕捉（设置语义=「项目启动时」，
运行事件未发生）；重启/再次 Run 即捕获。
