## 一、背景与依据

弹窗本体是平台 `MemoryDiskConflictResolver` 的原生冲突裁决：VFS refresh 检测到磁盘文件被**绕过 document** 外部改写，而该文件的内存 Document 同时处于**已修改未保存**状态——两边各自偏离最近同步点，平台只能弹窗让用户二选一。M36.5.13 曾实证此模态弹窗期间默认 modality 的 invokeLater 全部冻结，执行链换入/重试挂起——不只是烦人，会直接把执行链卡死在「执行中」。

插件在 M36.5.43 已把写法改成 document 驱动（`setText + commitDocument`），但本次真机弹窗说明**冲突窗口没有闭合，只收窄了**：document 驱动分支从不落盘（磁盘靠 IDE 自动保存追赶），且 WriteAction 失败时的兜底路径仍是裸写盘。两个洞叠出真机弹窗。

## 二、现状核实（master 实测，DataSourceSelector.kt）

| 面 | 现状 | 位置 |
|---|---|---|
| 执行文件写入 | `<projectBase>/.idea/sql-visualizer/exec/mpsql-exec.sql`，路径稳定每次覆盖；写入方两条链：BGT 预热 + EDT 冷路径 | `projectExecFile` `execute/DataSourceSelector.kt:3052-3100` |
| document 分支（VFS 已知文件） | `setText + commitDocument` 后**不落盘**——磁盘依赖 IDE 自动保存（帧失活/空闲触发）追赶；期间 document 恒为「已修改未保存」态；日志 `exec file updated via VFS (no cache conflict)` 名不副实（只更新了内存） | `DataSourceSelector.kt:3077-3093` |
| WriteAction 失败兜底 | `runCatching{WriteAction}.getOrDefault(false)` → **无条件裸 `FileUtil.writeToFile` 写盘**（注释自认「可能 conflict」）；失败原因（Throwable）被吞，日志只剩阶段名 | `DataSourceSelector.kt:3068-3098` |
| 双写方并发 | `execPrewarmInFlight` 只串行化预热真实链，EDT 冷路径（`chooseAndPrepare → createTempPsiFile:279`）不持标记——BGT setText 与 EDT 裸写可交错 | `DataSourceSelector.kt:105、279、3191` |
| 执行前 console 同步 | `executeOnConsole` 把 console document 同步进 console vf：同款 `setText + commitDocument` **不落盘**——执行前一刻又造出一个「已修改未保存」窗口 | `DataSourceSelector.kt:2277-2303` |
| 外部改写面 | demo 项目若把 `.idea` 文件入 git（checkout/stash/pull 重写工作区）、或用户在 IDE 外碰文件，都构成「绕过 document 的磁盘改写」 | 环境因素，无法穷举 |

**冲突成因链（弹窗复现的最小序列）**：任一预览/执行 → document 分支 `setText` → document 转入「已修改未保存」→ 磁盘被绕过 document 改写（插件自身裸写兜底 / git / 外部）→ 下一次 VFS refresh 判定两边各自有变 → 弹窗。

修复方向因此不是「再换一种写法」，而是**同时消灭两个条件**：① document 改完立刻同临界区落盘（不再留「已修改未保存」窗口）；② 只要该文件还有已加载 document，就禁止任何绕过 document 的裸写。二者齐备后，无论外部怎么改盘，插件侧都不再制造冲突面。

## 三、方案

**T-EC-01（document 分支同临界区落盘）**：`projectExecFile` 的 doc 分支在同一个 `WriteAction` 内补 `FileDocumentManager.getInstance().saveDocument(fileDoc)`（`setText → commitDocument → saveDocument`，磁盘=VFS=内存三方同步收口，VFS stamp 随保存原地更新，无需额外 refresh）；`executeOnConsole` 的 console-vf 同步块（2277-2303）同款补——执行前用户未保存的手动编辑一并落盘，磁盘与内存一致。日志文案改为如实的 `exec file updated via document+save`。scratch 语义不变（用户未保存手改被新 SQL 覆盖，与现状一致）。

**T-EC-02（裸写兜底守卫）**：WriteAction 失败后不再无条件裸写。新增判定 `canFallBackToRawWrite(vf): Boolean = FileDocumentManager.getInstance().getCachedDocument(vf) == null`（internal 纯函数供表驱动测试）：
- 有已加载 document → **放弃本次写盘**，`lastTempFileFailure` 带阶段标识（如 `writeConflictGuard`），失败原因 Throwable 一并进日志（现状被 `getOrDefault(false)` 吞掉）；链路按既有失败路径降级——下游 console doc 同步（T-EC-01 已落盘版）会在执行前把内容收敛，宁内容旧一拍，不弹模态窗。
- 无已加载 document → 裸写合法（document 不存在就无所谓冲突），维持 `FileUtil.writeToFile`。

**T-EC-03（单写方串行化）**：`projectExecFile` 加对象锁（synchronized，临界区毫秒级），BGT 预热与 EDT 冷路径不再并发写同一文件；不改 `execPrewarmInFlight` 既有语义。

**T-EC-04（VFS 缺条目路径加固 + 测试 + 文档）**：`existing == null` 裸写 + refresh 路径保留（无 VFS 条目即不可能有 document）；refresh 返回 vf 后防御性比对 `getDocument(vf).text` 与 sql，不一致补一次 doc 分支同步。测试照 `ExecTempFileFixTest`（BasePlatformTestCase）惯例：
- doc 分支落盘断言：写文件 → 换 SQL 重写 → **磁盘内容 == 新 SQL**（修复前磁盘滞留旧值，靠自动保存追赶）；
- `canFallBackToRawWrite` 表驱动：cached document 有/无两态；
- 兜底守卫断言：document 已加载 + 强制 WriteAction 失败（测试缝注入失败标记）→ 磁盘内容不变、`lastTempFileFailure` 携带守卫阶段；
- `existing == null` 路径：裸写后 refresh 可见、内容一致。
- CHANGELOG [Unreleased] Fixed、变更记录行；无新 bundle 键（`lastTempFileFailure` 阶段串为内部标识，用户文案复用 `execute.tempFile.failed` 模板）。

## 四、验收标准

1. doc 分支写后磁盘立即可见新 SQL，不依赖 IDE 自动保存；「已修改未保存」窗口在插件写入路径上不复存在。
2. document 已加载时插件任何路径都不裸写盘（守卫测试全绿）；WriteAction 失败原因必达日志。
3. 两条写入链并发不交错（锁语义 + 既有 `execPrewarmInFlight` 不回归）。
4. 全量 test 绿，跑前按铁律并行登记。

2. 关闭 IDE 自动保存（Settings 关两处 autosave）复跑第 1 条——依旧无弹窗（证明不依赖自动保存）。

## 六、风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| `saveDocument` 在 WriteAction 内的线程语境 | BGT 预热路径 WriteAction 内 saveDocument 属平台常用形态，但 262 断言面需实证 | 沙盒先行 + 真机走查 §五-1；异常落入 T-EC-02 守卫（不再裸写），最坏降级为内容旧一拍 |
| 覆盖用户未保存编辑 | setText 本就覆盖，saveDocument 把覆盖同步到盘——语义不变但后果更即时 | scratch 文件定位（每次覆盖生成），现状语义保持；弹窗二选一本来也让用户丢一边 |
| 放弃写盘导致 console 内容滞后 | 守卫拒绝写盘后，弹窗打开时文件可能是旧 SQL | 执行前 console doc 同步（T-EC-01）必然重写并落盘，执行内容不受影响；预览渲染不读该文件 |
| 锁引入的线程阻塞 | synchronized 临界区含 VFS 写，两链争锁至多毫秒级 | 临界区无用户交互依赖，阻塞可忽略 |

- **四子任务全数落地，方案有两处实施期升级**：
  1. **T-EC-01 升级为「document 写统一派 EDT」**（`dispatchDocWriteOnEdt`，DialectPreMapping.ensureMapped 两段式同款：EDT 直调同步、BGT invokeLater+有界 latch 2s）：实施期关键发现——262 平台文件 document（非 FREE_THREADED）的 `setText` 包 `CommandProcessor.executeCommand`，**BGT 直调硬抛 EDT-only 断言**（javap 反汇编 + 沙盒堆栈双实证）。这意味着旧实现 BGT 预热的 document 分支**每次必炸**、runCatching 吞掉后静默掉进裸写兜底——裸写兜底不是「低概率失败路径」而是 262 上的**确定性主路径**，即真机 File Cache Conflict 链本体。仅做计划原方案的「同临界区落盘」会被这个断言在预热线程上炸穿，故 document 写必须统一派 EDT（`writeVfTextViaDocument` 仅 EDT；`docWriteOnce` 失败原因必达日志）。

- T-EC-02 守卫：`canFallBackToRawWrite`（getCachedDocument 判定）+ writeConflictGuard 拒写异常（携带阶段标识，`lastTempFileFailure`/onError 文案自然携带）；表驱动 + 注入缝（`execWriteActionFailureInjection`）双测。

- T-EC-04：`syncExecVfContentIfNeeded`（getCachedDocument+VFS 内容双探测，写侧经 EDT 派发）挂入冷路径与预热线程 refresh 之后；`existing==null` 裸写路径保留。
