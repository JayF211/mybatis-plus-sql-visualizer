## 一、问题描述

### 当前现象

SQL 日志监听功能已正常工作（自动监听、自动停止、手动启停均正常），但**工具栏「捕捉/停止」按钮的图标和文案不能实时反映监听状态**：

| 场景 | capturing 实际值 | 按钮显示 | 用户操作后 |
|------|-----------------|---------|-----------|
| 项目启动后 | `true`（正在监听） | ▶ 开始（错误） | 点击面板后变为 ■ 停止 |
| 手动停止后 | `false`（已停止） | ■ 停止（错误） | 点击面板后变为 ▶ 开始 |
| 项目停止后 | `false`（已停止） | ■ 停止（错误） | 点击面板后变为 ▶ 开始 |
| 手动开始后 | `true`（正在监听） | ▶ 开始（错误） | 点击面板后变为 ■ 停止 |

**总结**：按钮状态总是「慢一拍」，需要用户点击或悬停工具面板后才会刷新到正确状态。

---

## 二、根因分析

### 2.1 IntelliJ 动作系统更新机制

工具栏按钮由 `CaptureAction`（`AnAction` 子类）渲染，其图标/文案由 `update(AnActionEvent)` 方法决定：

```kotlin
override fun update(e: AnActionEvent) {
    e.presentation.icon = if (manager.capturing) AllIcons.Actions.Suspend else AllIcons.Actions.Execute
    e.presentation.text = MpSqlVisualizerBundle.message(
        if (manager.capturing) "log.panel.stop" else "log.panel.capture",
    )
}
```

**关键**：`update()` 由 IntelliJ 动作系统调度，**仅在以下时机触发**：
1. 工具栏首次渲染时
2. 用户与工具栏交互时（点击、悬停、键盘焦点）
3. 显式调用 `ActionToolbarImpl.updateActionsAll()` 时

`capturing` 由 `SqlLogManager` 在后台线程/协程中变更（`startCapture/stopCapture`），动作系统不会感知这一变化，因此不会主动调用 `update()`。

### 2.2 已尝试的失败方案（沙盒日志实证）

| 方案 | 结果 | 原因 |
|------|------|------|
| 反射调用 `ActionToolbarImpl.updateActionsAll()` | ❌ 失败 | 243 平台无此方法（idea.log 实证 `NoSuchMethodException`） |
| 反射调用 `toolbar.updateActions()` | ❌ 失败 | 243 平台 ActionToolbarImpl 无 `updateActions()` （idea.log 实证 `NoSuchMethodException`） |

### 2.3 根因：用了错误的方法名

243 平台 `ActionToolbarImpl`（app-client.jar `javap` 实证）存在的是**接口公开方法 `updateActionsImmediately()`** 与 `updateActionsAsync()`，并非 `updateActions`/`updateActionsAll`。反射按错误名字找方法必然抛 `NoSuchMethodException`，导致刷新调用从未真正执行——按钮状态于是永远「慢一拍」，只有动作系统自行调度 `update()` 时（点击/悬停）才纠正。

### 2.4 核心矛盾

- `capturing` 是 `SqlLogManager` 的内态，变更时机不可预测
- 动作系统是被动调度，无法感知内态变化
- <del>没有合法的公开 API 可以「从外部」强制刷新特定工具栏的 action 状态</del>（已否定：`ActionToolbar.updateActionsImmediately()` 就是公开 API）

## 三、预期效果

| 场景 | 预期行为 |
|------|---------|
| 项目启动后 | 按钮**立即**显示 ■ 停止（红色方块） |
| 手动点击「停止」 | 按钮**立即**显示 ▶ 开始（绿色三角） |
| 项目停止后 | 按钮**立即**显示 ▶ 开始 |
| 手动点击「开始」 | 按钮**立即**显示 ■ 停止 |

**核心指标**：从 `capturing` 变化到按钮刷新之间的延迟 **< 200ms**，用户无需主动交互。

## 四、约束条件

1. **兼容性**：须同时兼容 IDEA 2024.3 / 2025.3 / 2026.2 三个平台版本
2. **性能**：不能引入高频轮询（如 Timer 每 500ms），避免 CPU 空转
3. **不侵入**：不能修改 `CaptureAction` 的 `update()` 逻辑（正确性已验证）
4. **可测试**：核心逻辑须可脱离 `BasePlatformTestCase` 测试（单元测试覆盖）

## 五、待选方案

> 以下为候选方向，不包含具体实现，待评估后选择。

### 方向 A：利用 `DumbAware` + 后台会话变更
- 利用 IntelliJ 的 `ApplicationManager.getApplication().getMessageBus()` 发布自定义事件
- 动作系统监听事件并触发 `update()`

### 方向 B：替换 `ActionToolbar` 为自定义 `JPanel`
- 放弃 IntelliJ ActionToolbar，改用 `JButton` + `AbstractAction`
- 通过 `PropertyChangeListener` 监听 `capturing` 变化
- 自行控制按钮图标/文案刷新

### 方向 C：利用 `presentation` 的 `fireEvent` 机制
- 通过反射或其他方式触发 `Presentation.firePropertyChange()`
- 间接通知动作系统刷新

### 方向 D：轮询 + 脏标记
- 在 `CaptureAction.update()` 中增加时间戳判断
- 通过 `javax.swing.Timer` 周期性触发 `updateAll`
- 有性能开销，但实现简单

### 方向 E：调用接口公开 API `ActionToolbar.updateActionsImmediately()`（✅ 已实施）
- `SqlLogManager` 的 `capturingListeners` 已就位（startCapture/stopCapture 时通知）
- 面板监听回调在 ED `invokeLater` 内对 `_toolbarRef` 直接调用 `toolbar.updateActionsImmediately()`
- 该方法是 `ActionToolbar` 接口公开抽象方法（243/253/262 皆有），无需反射
- 事件驱动、无轮询、无反射；`javap` 核实三平台签名一致
