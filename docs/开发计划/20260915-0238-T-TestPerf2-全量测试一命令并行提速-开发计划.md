# T-TestPerf2：全量测试一命令并行提速（分片时长均衡）

> 立项：2026-09-15。用户需求原话：「目前插件全量测试花费时间较长，现在你需要想办法压缩全量测试时间但是测试效果不能变，不能删减测试用例」。
> 前作：T-TestPerf-01~04（docs/开发计划/20260913-2330-测试守卫补全与全量提速-开发计划.md），本计划接续其编号。

## 一、背景与现状

- 现行权威全量 = 串行 `./gradlew test`：4083 用例 / 326 类，2026-09-14 22:58 全量 XML 聚合执行时间合计 **251.6s**，命令墙钟约 4.5~5 分钟。
- 前作已收割：build cache 关闭（根除假失败整轮重跑）、configuration cache 复活、分片包含清单自动分区。两条并行路已证据否决：平台测试 `maxParallelForks`（多 fork 共享默认沙盒 PersistentFS 互踩）、纯逻辑分桶 task（68 例隐性依赖同 JVM 平台状态）。
- 现存真并行路径 testShard1/2 有三个缺口：
  1. **用法口径要「双开终端」**：一命令 `./gradlew testShards` 是否真并行存在矛盾口径——gradle.properties 注释称历史 4 片「无依赖任务同时执行」（2026-08-15 起 `org.gradle.parallel=true` 已开），测试约定记忆却称「同项目内任务不并行」——未经实证定案；
  2. **分区算法对耗时无感知**：类名哈希只保证用例数接近，实测 26% 失衡（见 §二），并行墙钟被重片拖死；
  3. **结果聚合口径缺位**：分片结果散在 build/test-results/testShard1|2/ 两个目录，现行计数聚合惯例只扫 test/，分片跑完总数要手工拼。

## 二、实测数据（2026-09-14 22:58 全量 XML，326 类 / 4083 用例）

头部耗时高度集中，前 5 类占 28%：ConvertSqlToJavaActionTest 27.5s（2 例）、SqlToJavaPanelTest 13.4s（55 例）、SqlPreviewPanelTest 11.5s（60 例）、EntityClassFinderHeavyTest 10.6s（17 例）、SqlPreviewSpecMatrixTest 7.9s（81 例）。

对同一份真实逐类耗时模拟分区（Java String.hashCode + floorMod 复算现行算法；贪心 = 按时长降序逐类放入当前最轻片）：

| 分区算法 | 片数 | 各片负载 | 失衡度 |
|---|---|---|---|
| 现行：类名哈希 | 2 | 157.9s / 93.7s | 26% |
| 本计划：时长贪心均衡 | 2 | 125.8s / 125.8s | ≈0% |
| 现行：类名哈希 | 3 | 70.9s / 97.3s / 83.3s | 16% |
| 本计划：时长贪心均衡 | 3 | 83.9s × 3 | ≈0% |

结论：**只换分区算法，并行墙钟理论上限即从 158s 压到 126s（2 片）或 84s（3 片）**，不含任何用例删减或断言改动。机器 i5-10400F（6C12T）/ 32GB：2 片为保守默认，3 片由实测定去留。

## 三、方案设计

**P5 一命令并行定案与收编**：实证 `./gradlew testShards`（单命令）两片任务是否并发执行（看任务起止时间戳）。并发成立 → 收编为推荐用法，串行 `./gradlew test` 保留为权威对照口径；不成立 → 查根因（多任务点名 / 双终端兜底），实测结论落注释。

**P6 时长均衡自动分区**：分区权重来自 build/test-results 下历史 XML（test/ 与 testShardN/ 全扫，同类取 mtime 最新——串行与分片跑出的数据互相喂养）；无数据类取全体中位权重（全新检出零数据时全体同权，退化为按类名字典序贪心均分，仍确定性）。贪心排序键 = (时长降序, 类名升序)，同输入必得同分区——双开终端两进程、配置缓存复用前后的多次配置期计算结果一致。配置缓存语义与现行类发现一致：新增测试类 / 时长变化在下一次配置失效后生效，短暂失衡可接受、不影响正确性。

**P7 片数可配**：`-PtestShardCount=N` 动态注册 testShard1..N（默认 2），聚合任务与报告任务随之伸缩；testShard1/2 既有名称不变。

**P8 分片结果聚合报告**：`testShards` 聚合任务 doLast 汇总各片 XML 的 tests/failures/errors/skipped 与执行时间，打印分片表 + 总数——分片口径与串行口径的计数 parity 目测即得（配置缓存约束：doLast 只引用配置期解析好的 File，不触达 Project/layout）。

**P9 test JVM 堆参数实验（可选，按实测取舍）**：Test 任务未显式配 maxHeapSize（Gradle 默认 512m）。实验 `maxHeapSize=2g` 对照，>5% 收益才转正，否则不动。

**清理项**：gradle.properties 里 testForks 死注释删除（属性无任何读取点，T-TestPerf-03 已否决）；「同项目内任务不并行」「双开终端」两处口径按实证结论修正（build.gradle.kts 注释）。

## 五、范围边界（明确不做）

- **不删减、不改写任何测试用例与断言**；不动被测生产代码；不动测试内 sleep/轮询时序（「测试效果不能变」红线）。
- 不重启 maxParallelForks（PersistentFS 互踩已否决）与纯逻辑分桶（68 例隐性平台依赖已否决）两条路。
- 串行 `./gradlew test` 任务定义零改动，权威对照地位保留；分片任务用例集合口径不变（DB 集成三类仍只在 testDatabase）。
- 不引入新测试框架、不动 Gradle 版本与 IPGP 版本。

### T-TestPerf-05 一命令并行实证

「同项目内任务不并行」旧口径**证伪**：`org.gradle.parallel=true` 下单命令 `./gradlew testShards` 各片任务真并发（Run B/F 两片 END 仅差 0.9~1s；Run D/E/F 三片同样重叠）。旧「双开终端」用法仍可用但已非必需。各分片任务留了 START/END 毫秒时间戳锚点便于日后并发审计。

### T-TestPerf-06/07 分区与发现

- 时长均衡分区：贪心（时长降序、类名升序确定序，逐类入最轻片）替换类名哈希——哈希 2 片实测 157.9s/93.7s 失衡 26%，均衡后 125.8s/125.8s。权重源=build/test-results 全目录（test/ 与 testShardN/）历史 XML 同类取 mtime 最新，串行与分片互相喂养；无数据类取已知中位数，全新检出退化为字典序贪心，仍确定性。
- **类发现修正（捡到真雷）**：发现逻辑原按「文件名=FQCN」推导，而 Kotlin 文件名≠类名合法——`generator/CrudPreviewFlowAndTypesTest.kt` 文件内是 `class DbTypeQuoteHintTest`（3 用例），旧法漏发现致分片并集 4080 < 串行 4083。改为内容提取顶层 class 声明（列 0，含 Kotlin/Java 常见修饰符），全库扫描仅此一处错位，修复后 parity 4083 达成。该文件命名与类名错位未动（不改测试文件红线），建议后续顺手把文件改名 DbTypeQuoteHintTest.kt。
- 机器级资源亲和：Run A 实证 Windows 剪贴板全机互斥在并发分片下放大（`cannot open system clipboard`，假失败清单「剪贴板 flake」的并行版）——源码含 `CopyPasteManager/systemClipboard` 的 5 个测试类固定进第 1 片，片内串行无争用；后续 D/E/F 三轮零 flake 验证生效。
- 聚合报告：`testShards` doLast 打印各片与总数 tests/failures/errors/skipped 四元组，计数 parity 目测即得。

### 额外收获：build cache 关闭自落地起在本机空转（已根治）

Run A 出现「5 from cache」+ daemon 元空间耗尽（256m）双异常信号，溯源实锤：**用户级 `~/.gradle/gradle.properties` 的 `org.gradle.caching=true` 与 `jvmargs` 按 Gradle 属性优先级（GRADLE_USER_HOME > 项目根）覆盖项目内 `org.gradle.caching=false` 与 `jvmargs`**——T-TestPerf-01 的「关闭」从未真正生效。修复=关闭落 `settings.gradle.kts` 的 `buildCache { local { isEnabled = false } }`（settings 配置优先级高于属性文件），历史三次成片 NoSuchMethodError 假失败的根源才真正关死。jvmargs 覆盖（daemon 实际跑在用户级 -Xmx2g/MaxMetaspace 256m）项目侧无法从属性层压制，留给用户环境自行取舍：若修 ~/.gradle/gradle.properties，项目注释（gradle.properties T-TestPerf2 补记）已写明。
