>

## 2. 方案设计

### 2.1 服务链式 wrapper 定位（T-M15-01）

**现状**：`WrapperAnchorDetector`/`WrapperLocator` 的工厂识别硬编码 `Wrappers.` 静态工厂（qualifier resolve 为 `Wrappers` 类）；`service.lambdaQuery()` 的 qualifier 是 service 引用 → 锚点、类型、链收集三个入口全部落空。`detectWrapperType` 无 ChainWrapper 类型。

**方案**：
- `WrapperAnchorDetector`：新增锚点形态——方法名匹配 `lambdaQuery`/`lambdaUpdate` 的调用点（快速路径，qualifier 文本匹配，零 resolve，与 `Wrappers.` 工厂共用逻辑，保持 gutter 图标 O(1) 红线）；
- `WrapperLocator.isWrapperFactoryCall` 放宽容纳 `lambdaQuery`/`lambdaUpdate`；`factoryWrapperType` 映射 → LQ/LU；
- 链式收集：从链起点收集后续 `.set/.eq/...` 调用，按**终结点全集**截断——查询：`.one()/.oneOpt()/.list()/.count()/.exists()/.page()/.last()/.getOne()/.remove()`；更新：`.update()/.remove()`；
- 消费语义：`lambdaUpdate()...remove()` → **DELETE**（U11-⑤ 唯一真实用例）；`lambdaQuery()...exists()` → EXISTS 语句（Q14-③）；`lambdaQuery()...page(Page)` → 分页 SELECT；
- `detectWrapperType` 增加 `LambdaQueryChainWrapper`/`LambdaUpdateChainWrapper` 显式声明（modules/CarDevicePortInfoServiceImpl 唯一 1 处，先 count 后 getOne 复用）。

**验收**：真实语料样例转换正确（`consumer/UserInvoiceAppService`、`admin/MerchantWalletWithdrawAppService`、`merchant/SubAccountAppService#doConfigStation` 的 `lambdaUpdate().remove()`）；新测试全绿。

### 2.2 字符串版 QueryWrapper / UpdateWrapper 转换器（T-M15-02）

**现状**：`ConverterRegistry` 仅 6 个转换器（LQ/LU/LD/MPJL/MPJQ/MPJLQ），无 QUERY/UPDATE；`columnArgs`/`orderItems`/`groupBy` 只收 `ColumnArg`，字符串列（ValueArg）丢失。

**方案**：
- 新增 `QueryWrapperConverter`（基于 `QueryWrapperParser`：字符串列 → `ColumnRef(columnName = 原样)` + 未知列提示）与 `UpdateWrapperConverter`（复用 `LambdaUpdateConverter.parseSet` 逻辑 + 字符串列 eq/setSql/apply）；
- `QueryWrapperParser` 的列/排序/分组解析接受 ValueArg 字符串：`select("DATE(create_time)::timestamp as ...")`、`eq("merchant_id", v)`、`groupBy("DATE(create_time), amount_direction")` 原样透传；
- `WrapperLocator.buildChain`：支持 `wrapper.lambda()` 调用转换（`lambda()` 返回的续链并入原链，U09-④）。

**验收**：`merchant/AccountManagementAppService#queryDayAmountSummary`（Q03/Q09/Q18 聚合链）、U09 四形态（含 `wrapper.lambda()`）用例全绿。

### 2.3 exists 三形态（T-M15-03）

**现状**：`parseInternal` 无 `exists` 分支 → 链内 `exists(boolean, "SELECT ... {0}", v)` 静默丢弃；消费集合只有 delete/count 两组，`service.exists(wrapper)` 渲染成普通 SELECT。

**方案**：
- `QueryWrapperParser.parseInternal` 新增 `exists`/`notExists` 分支：`EXISTS (...)` 条件透传 + `{0}` 参数替换（复用 apply 的替换逻辑）+ boolean 首参剥离；
- 消费识别：`service.exists(wrapper)` / `mapper.exists(wrapper)` → 输出形态对齐 MP 语义（`SELECT EXISTS (SELECT ...)` 或 EXISTS 条件查询，文档化输出形态）；
- 链式 `lambdaQuery()...exists()` 依赖 T-M15-01 的终结点支持。

**验收**：Q14 三种形态（`CarStationPriceTaskRecordAppService#page` SQL 子查询、`MerchantAppService` wrapper 子查询、`UserInvoiceAppService` 链式）用例全绿。

### 2.4 更新链路补强（T-M15-04）

**现状**：`set(boolean, col, val)` 首参不剥离（U03，25 处）；`setSql("...{0}", val)` 的 `{0}` 不替换（U04-③）；`last("AND ...")` 非 limit 形态被 `parseLimit` 丢弃（U05）；`update(entity, wrapper)` 双参无 SET（U07-②）；`Wrappers.lambdaUpdate()` 无泛型 → table null（U01-③）。

**方案**：
- `LambdaUpdateConverter.parseSet`：SET 分支复用 `analyzeFlag` 剥离首参布尔（对齐 eq 等条件方法的处理）；SET_SQL 分支取 `args.drop(1)` 按 `{i}` 替换（复用 selectFunc/apply 的参数替换）；
- `UpdateStatement` 模型新增 `rawTail` 字段：`last` 非 limit 内容原样追加到 UPDATE 语句末尾（`StoreCouponServiceImpl#deduction` 防超发模式）；
- `parseSet` 新增 entity 分支：`update(entity, wrapper)` 时用 `EntityResolver` 展开实体**非 null 字段**为 SET 列（upsert 场景；标注与全局 `update-strategy: always` 的差异）；
- `WrapperLocator.buildChainFromFactory`：`Wrappers.lambdaUpdate()`/`Wrappers.<T>lambdaUpdate()` 类型实参缺失时，从链内首个 `set(SFunction, ...)` 的方法引用推断实体类（兜底：无法推断时输出 SQL 模板 + 表名未知提示，不再静默返回 null）。

**验收**：U03/U04-③/U05/U07-②/U01-③ 用例全绿；`GiftFundPayService` 余额保护链（setSql {0} + apply 配对）、`StoreCouponServiceImpl#deduction`（setSql + last AND）样例正确。

### 2.5 跨方法追踪补全（T-M15-05）

**现状**：`expandFactoryCalls` 只展开 1 级且仅链首；if/else 互斥分支的两个调用按源码序合并 → `WHERE id = ? AND id IN (...)` 语义错误；`update(null, wrapper)`/`selectCount(wrapper)` 行的实参锚点不可预览。

**方案**：
- `expandFactoryCalls` 递归展开**实参位置**的工厂/构造调用（`PsiExpressionList` 内的 wrapper 前置链），支持 P03 的 3 级链（`baseWithdrawQueryWrapper → baseWithdrawJoinWrapper → applyWithdrawFilters → 续链`）；
- `buildChain` 的 `ReferencesSearch` 收集按 `PsiIfStatement` 分支归属分组：if/else 互斥分支 → 渲染 if 分支条件 + 提示（tooltip「存在互斥分支条件」），或 OR 合并（需按分支语义决定，默认取 if 分支 + 提示，与 M12 动态条件机制交互）；
- `findWrapperVariable` 扩展：方法调用实参位置的 wrapper（`update(null, wrapper)`/`selectCount(wrapper)`/`remove(wrapper)`）→ 回查变量声明与初始链（U08 双锚点）。

**验收**：P03 3 级链（`MerchantWalletWithdrawAppService#createExportTask`）、P15 if/else（`bridge/PlatformService#findCarDeviceInfoByStationIds`）、U08 count 预检复用（`modules/CouponUserQueryServiceImpl#overdueTask`）样例正确。

### 2.6 selectCollection ON 修复 + MPJ 输出对照（T-M15-06）

**现状**：`parseCollection` 的 ON 复用只匹配 `on(col1, col2)`（`OnConditionArg`），清单 P06 主形态是**三参 leftJoin** → filter 判空失败 → LEFT JOIN 子查询无 ON（笛卡尔积）；嵌套 collection 外键按约定推断（`孙表.父表名_id = 父表.id`，R7 未对照）；现有测试断言固化无 ON 输出。

**方案**：
- `parseCollection` ON 复用匹配扩展到四种 join 形态（三参 ColumnArg 对 / 四参带别名 / `on(...)` / lambda ON），复用 `parseJoin` 的解析结果（按子表类名匹配）；
- 嵌套 collection 外键语义对照 MPJ 1.5.6 官方输出：用真实语料 `modules/CarStationPriceTaskRecordServiceImpl#getExecutionDetailById`（P07 三层）与 `admin/CarOccupyRecordAppService#detail`（P06）验证，去除纯约定推断；
- 修正既有测试断言（`mpjLambda_selectCollection子查询`、`mpjLambda_selectCollection嵌套collection` 输出含 ON）。

**验收**：P06/P07 样例输出含 ON 且与 MPJ 官方输出对照一致（无真实数据库验证的项标注 R7 风险）。

### 2.7 逻辑删除与实体注解补强（T-M15-07）

**现状**：`EntityResolver` 只读 `@TableName value`/`@TableField value`/`exist=false`/`@TableId`；`@TableLogic`、fill/updateStrategy/select 属性不读；查询/删除不自动追加 `deleted = 0`；批量插入不填充。

**方案**：
- `EntityResolver`：读取 `@TableLogic`（标记 `TableInfo.logicDeleteColumn`）、`@TableField(fill/updateStrategy/select)`；
- `SqlGenerator`/preview：查询与删除自动追加 `AND deleted = 0`（对齐真实项目全局 `logic-delete-field: deleted`；**新增配置开关 `injectLogicDelete`（默认开）**，关闭时保持纯 wrapper 语义）；
- 插入/批量模板：`FieldFill.INSERT` 字段（createTime/updateTime/deleted）标注填充（对齐 MetaObjectHandler，X10 降级为「填充标注」而非真实求值）；
- `updateById` 预览：按 `update-strategy: always`（项目全局配置）渲染全列 SET，标注与字段级注解（NEVER/NOT_NULL）的差异。

**验收**：@TableLogic 实体查询自动追加 deleted 条件用例全绿；开关关闭不追加；既有测试断言更新（行为变更记录 CHANGELOG）。

### 2.8 单实体批量方法补齐（T-M15-08）

**现状**：`BatchOperationConverter` 覆盖 saveBatch/updateBatchById/insertBatchSomeColumn/removeByIds；`removeById(id)`（约 26 处）、`updateById(entity)`、`saveOrUpdate/saveOrUpdateBatch` 无处理。

**方案**：
- `removeById(id)` → `DELETE FROM t WHERE id = ?`（主键列来自 @TableId / 实体字段）；
- `updateById(entity)` → 全列 SET 模板（对齐 `update-strategy: always`）；
- `saveOrUpdate(entity)`/`saveOrUpdateBatch(list)` → 按方言渲染 upsert（真实项目 PostgreSQL：`INSERT ... ON CONFLICT (id) DO UPDATE SET ...`；MySQL 方言 `ON DUPLICATE KEY UPDATE`）；
- `insertBatchSomeColumn` 模板补强：`FieldFill.UPDATE` 字段排除 + 空字段 `DEFAULT` 标注（对齐自定义 SqlInjector 语义，X09）。

**验收**：U11/U12 用例全绿；PG/MySQL 方言 upsert 各一用例。

### 2.9 语料回归测试与验收（T-M15-09）

- 测试基座：以清单 §4 模式编号（P/Q/U）命名测试方法，未覆盖的已支持模式补齐回归测试（清单 §6.2 的 18 条高风险用例逐条有测试）；

## 4. 风险与应对

| 编号 | 风险 | 影响 | 应对 |
|------|------|------|------|
| M15-R1 | service 链定位破坏 gutter 图标性能红线（快速路径要求 O(1)、零 resolve） | 编辑器卡顿 | 锚点判定仅做方法名/qualifier 文本匹配（零 resolve，与 `Wrappers.` 工厂同路径）；`lambdaQuery()` 方法名匹配优先级低于 `new` 关键字锚点 |
