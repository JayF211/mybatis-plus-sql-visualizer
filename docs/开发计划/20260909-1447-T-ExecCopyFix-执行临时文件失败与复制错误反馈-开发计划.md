## 一、症状与定位

### 1.1 问题一：复制错误信息无点击反馈

截图圈选的「复制错误信息」按钮是 `SqlResultPanel` 的行内按钮（错误文本居左 `infoLabel`、按钮居右 EAST，与截图布局吻合），顶部工具栏还有一个同 bundle key（`panel.copyError`）的按钮，两处行为相同：点击后静默写入剪贴板，无任何 UI 反馈。

- `SqlResultPanel.errorCopyButton`（SqlResultPanel.kt:40-51）：actionListener 只调 `copyToClipboard`（:221-224），`setContents` 后即返回。
- `SqlPreviewPanel` 顶部工具栏 `errorCopyButton`（SqlPreviewPanel.kt:376-379）→ `copyError()`（:2220-2225），同样静默（本场景 `currentWarning == null` 时不可见，一并修）。

对照组即用户指定的参考交互：SQL 日志面板单击预览弹窗的复制按钮 `SqlClickPreview.flashCopied`（SqlClickPreview.kt:242-252）——图标短暂换成 `AllIcons.Actions.Checked`，一次性 `Timer(1500)` 恢复，T-ClickPreview-05 已交付实证可用。两处错误复制按钮均未接入此语义。

### 1.2 问题二：执行 SQL 报 Failed to create temporary SQL file

链路：执行 SQL → `SqlPreviewPanel.executeSql`（SqlPreviewPanel.kt:407）→ `isPrepared()` false 或 `executePrepared` 返回 false → `SqlExecutor.execute` → `DataSourceSelector.chooseAndPrepare` → `createTempPsiFile` 返回 null → `onError("Failed to create temporary SQL file")`（DataSourceSelector.kt:240-246，硬编码英文）→ `resultPanel.showError`（bundle `execute.result.error`，即截图文案）。

`createTempPsiFile`（DataSourceSelector.kt:2609-2644）整段 `runCatching { ... }.getOrNull()`——**异常被整体吞掉，无任何日志**；`chooseAndPrepare` 侧只有一条不含原因的通用 warn（:242）。这直接导致真机失败无法归因，只能列候选：

| 候选 | 机理 | 可能性依据 |
|---|---|---|
| R1 262 平台硬抛被吞 | 用户 IDE 为 2026.2.1。① `refreshAndFindFileByIoFile` 同步 VFS refresh 的 write-safe 语境要求（T-PreviewWiLock 27ccfcf 同类硬抛先例）；② `PsiManager.findFile` 在 EDT ReadAction 内触发 `WorkspaceFileIndex.ensureIsUpToDate` 慢操作断言（T-PreviewFlash 计划 §2.1 沙盒实证该调用点必触发；243 仅 SEVERE 记录，262 平台违规家族有升级硬抛先例）。且 `allowSlowOperations(GENERIC)` 逃生舱在 EDT 上是空壳（T-PreviewFlash §3.1 反编译：`startSection` 只在非 EDT 压栈） | 高——与 262 硬抛先例群吻合，且此路径从未做过 262 安全化（SqlPreviewPanel 侧同源代码 T-PreviewFlash/T-PreviewWiLock 已两轮加固，DataSourceSelector 侧只有 vf 缓存在途改动） |
| R2 projectExecFile IO 失败 | `project.basePath == null`（:2661 直接返回 null）；`.idea/sql-visualizer/exec` 的 `mkdirs()` 返回值被忽略（:2663），失败后 `FileUtil.writeToFile` 抛 IOException → 吞。Windows 真机 杀软/OneDrive/权限均可触发 | 中——真机环境因素常见，补日志后可一锤定音 |
| R3 refresh 后 vf 不可见 | `refreshAndFindFileByIoFile` 返回 null（不抛异常，无日志），Windows 文件刚写盘被占用时可能发生 | 低——但它是「无异常的 null」，现有代码连 onFailure 都进不去 |
| R4 WriteAction 分支异常 | 既有文件分支 `WriteAction.compute` 抛（写入竞争等）→ 兜底写盘（:2695-2698），仅兜底也抛时才 null | 低 |

注意：生产 IDE 上 `LOG.error` 只记录不抛，因此「SEVERE 断言」本身在真机不构成失败；真正的 null 必来自**显式抛出的异常或显式 return null**。R1① 与 R2/R3 是显式来源，R1② 在 262 是否抛需真机日志裁决。**结论：修复的第一步是把失败原因暴露出来（F2a），同时按已知先例把整段调用 262 安全化（F2b/F2c），两步合流后真机复验收口。**

## 二、修复方案

### 2.1 F1：复制反馈（问题一，SqlResultPanel 为主 + 顶部工具栏对齐）

1. 新增 `ui/CopyFeedback.kt`：`internal fun flashCopied(button: JButton, durationMs: Int = 1500)`——文本按钮适配版：保存原文案与图标 → 文案换 bundle `panel.copied` + 图标 `AllIcons.Actions.Checked` → 一次性 `Timer(durationMs)` 恢复两者。语义与 `SqlClickPreview.flashCopied` 对齐（1500ms 一次性 Timer，无常驻定时器、无 Disposer 负担）。
2. `SqlResultPanel.errorCopyButton` 的 actionListener 在 `copyToClipboard` 后调 `flashCopied(this)`。
3. `SqlPreviewPanel` 顶部工具栏 `errorCopyButton` 回调在 `copyError()` 成功后调 `flashCopied(this)`（`copyError()` 返回 false 即无警示时不闪）。
4. bundle zh/en 各加一行 `panel.copied`（zh「已复制」/ en "Copied"）。

范围外说明：弹窗底部「复制 SQL」走 toast 既有反馈不动；`SqlClickPreview.flashCopied` 图标版保留原样；两处实现不强求合并（图标版与文本版形态不同）。

### 2.2 F2：createTempPsiFile 失败可见 + 冷路径 262 安全化（问题二）

**F2a 失败可见（先行，独立成立）**：

- `runCatching` 链补 `.onFailure { LOG.warn("[M36] createTempPsiFile FAILED", it) }`；
- 三个显式 `return null` 站点（ioFile/vf/psi）各自补一条 stage 级 warn（标明在哪一步、ioFile 绝对路径与 exists 状态）——覆盖 R3 这类「无异常的 null」；
- `projectExecFile` 的 `mkdirs()` 失败记 warn；`basePath == null` 记 warn；
- `chooseAndPrepare` 的 onError 文案本地化并携带原因：新 bundle key `execute.tempFile.failed`（zh「创建临时 SQL 文件失败：{0}」/ en "Failed to create temporary SQL file: {0}"），{0} 取异常 message 或阶段标识。复制按钮（F1）复制到的也是带原因的完整文本。

**F2b 冷路径后台化**（对齐 T-PreviewFlash 已定的预热模式，线程语义复刻 `SqlPreviewPanel.prewarmPreviewTempFile` 主体——BGT 上 refresh + ReadAction findFile 合法且安静，SqlPreviewPanel.kt:298-320 在用先例）：

- `projectExecFile`（纯 IO 写盘；既有文件分支的 document 同步 WriteAction 留 EDT）保持现状；
- 冷路径（缓存未命中/失效）拆三拍：refresh（BGT）→ `mapDialectBeforePsi`（EDT，`setMapping` 线程语义未验证的既定约束不变，方言短路后仅首次真实执行）→ findFile（BGT + ReadAction）；EDT 以既有 `awaitPrewarmedTempFile` 口径有界等待（PREWARM_WAIT_MS=2000 / POLL=20），超时按失败回调并带原因；
- 缓存命中路径零改动（现状直返）。

**F2c 缓存存续修正**（对在途 T-PreviewFlash 改动的修正）：`clearPrepared()` 不再清 `cachedTempPsiFile`——vf 失效守卫已兜底，内容覆盖写走 document 驱动不破坏 vf↔psi 配对；现状每次预览切换清缓存，导致执行必走冷路径，击穿 T-PreviewFlash「跨点击吸收」的本意。实施时与该会话协调（同文件在途改动，基于最新工作树实施）。

### 2.3 API 权威核实清单（铁律：本地 jar 反编译为准）

```
WriteIntentReadAction.compute(Computable)     # 243~262 交集重载（T-Wia262 已核；若 F2b 编排降级为 EDT 包装变体时使用）
com/intellij/util/SlowOperations              # 复核 production LOG.error 不抛语义（§1.2 判定依据）
com/intellij/workspaceModel/.../WorkspaceFileIndexDataImpl.ensureIsUpToDate   # 262 是否抛，真机日志裁决
AllIcons.Actions.Checked                      # SqlClickPreview 在用，无需重核
LocalFileSystem.refreshAndFindFileByIoFile    # BGT 合法性：prewarmPreviewTempFile 在用先例
```

## 五、风险与回滚

- **F2b 编排复杂度**：三拍跨线程若在 runIde 复现新竞态，回退变体 = 维持 EDT 全路径，但整段换 `WriteIntentReadAction.compute`（Computable 单类型重载，243~262 交集）包装 + 保留 allowSlowOperations——修掉 R1① 写安全项，慢操作 SEVERE 噪音回到 T-PreviewFlash 前水平（生产不抛，可接受回退）。

- **回滚**：单提交 revert；bundle 仅新增键，无迁移面。
