## 二、提效方案（数据定案，先测后议）

### 2.1 基线实测（2026-09-17，本机 warm，配置缓存复用）

| 口径 | 结果 | 备注 |
|---|---|---|
| 串行 `./gradlew test` | **4m06s**，4321/0/0/6（350 类），测试执行 234.7s | 对照第一轮交付时 3968/4m03s——用例 +353 时间持平（配置缓存红利） |
| `./gradlew testShards`（默认 3 片） | **2m03s** | T-TestPerf2 时代 4081/2m05s，权重表自动喂养下依然稳 |
| `./gradlew testShards -PtestShardCount=4` | **3m02s** | T-TP3-02 实测：4 片并发超出物理核（6C12T）竞争反而比 3 片慢 ~1m——**默认 3 片定案维持**，勿再调大 |
| 平台型 vs 纯逻辑 | **平台型 1790 用例 222.1s（94.7%）｜纯逻辑 2531 用例 12.5s（5.3%）** | 决定性数据，见 2.2 |

### 2.2 「纯逻辑分桶提速全量」正式证伪销账（第一轮 T-TestPerf-03 的数据闭环）

第一轮否决纯逻辑分桶的实验结论（68 例隐性依赖）本轮拿到占比数据后彻底闭环：**2531 个纯逻辑用例总共 12.5s**——即使清偿 68 例债务并 4-fork 并行，理论收益 <10s，而清偿本身要逐例补平台引导。结论：**「纯逻辑分桶给全量提速」永久销账**，68 例隐性依赖债务不再追讨（它们在平台桶里跑得好好的），buildSrc 注释同步钉死这一条，防止后人再立项。

### 2.3 落地：testFast 秒级反馈通道（价值重定位）

分桶不给「全量」提速，但给「日常反馈」提速：改纯逻辑面（parser/converter/tokenizer/守卫测试）时，`./gradlew testFast` 秒级~半分钟拿到反馈，不必等 4 分钟全量。设计：

- **划桶规则增强**（第一轮 68 例误报的根因修复）：配置期扫描 src/test，源码含 `BasePlatformTestCase|HeavyPlatformTestCase` **或平台运行时特征符号**（ApplicationManager、UIUtil、JBColor、CopyPasteManager、ActionManager、TransactionGuard、DocumentUtil 等名单）的类一律留平台桶；其余进 testFast。特征名单保守起步，宁可漏进桶不可错进桶。
- testFast 为独立 Test 任务：classpath 复用默认 test 任务成品（IPGP 平台 jar 直配任务不进 sourceSets.runtimeClasspath——第一轮趟过的坑）、排除统一走 filter（DB 集成四类天然被特征规则拦在桶外，仍显式排除双保险）、`maxParallelForks=1` 起步（12.5s 总量无并行收益，fork 只引入新假失败形态）。
- **默认 `test` 任务保持全量不动**（权威口径不变），testFast 纯增量快通道。
- 验收：testFast 全量绿（证伪隐性依赖误报；红则逐类加排除并记录）+ 计时落档。

### 2.4 testShards 片数复测（数据说话）

上轮「6C12T 3 片最优」的对照只有 2 片（慢 40%），4 片无记录；4321 用例时代权重表已演化。实测 `-PtestShardCount=4` 对比，数据决定是否改默认。

### 2.5 慢类治理：抽查证伪，无病可治

Top 慢类 SqlToJavaPanelTest 13.7s/55t、SqlPreviewPanelTest 10.8s/62t 人均正常；ConvertSqlToJavaActionTest 2 例 6s 是**类级平台 bootstrap 固定开销**（平台型地板），非病态。平台型 222s = 350 类 bootstrap 的结构成本，串行/fork/分桶均已证伪，唯一并行形态就是 testShards（已是）。诚实记录，不硬治。

### T-TP3-01 testFast 秒级反馈通道（2236 用例 / 161 类 / 0 失败，执行 13.7s）

三段 classpath 构造（两轮实测校准定案，见 mpv-testing.gradle.kts 注释）：

1. **首跑**（classpath 直接复用默认 test 成品）：2280 例 28 失败分两类——①4 类隐性平台依赖（Diagram 两类 NoClassDefFoundError UIUtil / CrudSqlPreviewFlow 与 ErrorReportDialogLayout「Must be precomputed」，测试源码零 `com.intellij` 字面但被测生产类内部走平台状态——划桶规则的盲区，**显式排除名单**解决）；②PluginBuildInfoTest 读出真实构建时间戳——**插件自身 jar 在 classpath 且类解析可达**，打破「测试形态类从 classes 目录加载」前提。
2. **二跑**（剔除插件 jar）：成片 NoClassDefFoundError WrapperCall——默认 test 的类解析靠 Gradle worker 的类路径顺序，成品 classpath 里 build/classes 不在可达位，**剔除 jar 断了生产类供给**。
3. **三跑定案**：`main output + test output 前置 + 成品 classpath 续后（剔除插件 jar）`——类解析必从 classes 目录起（PluginBuildInfo 前提恢复），平台类从平台 jar 解析（Logger 等静态初始化可用），全绿。
4. 计时：全量 testFast 带 test 编译 1m34s；执行本身 13.7s；日常场景（增量编译）≈1 分钟内，对照全量 test 4m06s。warm 无改动 up-to-date 秒级跳过。
