# T-DynUpdate 自更新免重启：动态安装改造开发计划

> 立项 2026-09-11，未实施。
> 结论先行：插件描述文件已完全满足平台动态插件要求（9/9 扩展点 `dynamic="true"` 逐条实证）；「更新后必须重启」的直接根因是 M28 自研安装器 `PlatformPluginInstaller` 绕过平台动态安装链路、无条件调度「下次启动替换」。当年据此定论的 T-M23.10「环境 Performance Testing 插件否决动态卸载」经 262 反编译证实为误判——该 vetoer 只否决 performanceTesting 插件自身、且仅在其命令回放执行期间生效。

## 1. 背景与现象

用户在 IDE 2026.2.1（IU-262.10315.125，本机实证环境）更新插件后必须重启 IDE 才生效。插件侧已遵守官方动态插件的全部静态要求，期望更新免重启热生效。本计划基于官方文档、262 平台反编译与本仓现状的三重交叉核实，定位根因并给出改造方案。

## 2. 调查结论（2026-09-11 实证）

### 2.1 平台判定链（262 反编译，`intellij.platform.ide.impl.jar`）

Settings→Plugins 更新与 Install from Disk 同源，核心在 `PluginInstallOperation.prepareToInstall`：

1. `myAllowInstallWithoutRestart` 为真时，调用 `DynamicPlugins.allowLoadUnloadWithoutRestart(descriptor, context)`（262 新管线为 `DynamicPluginsSupport.checkCanReconfigureWithoutRestart`，带 `PluginStateValidator` 预演新插件集状态）。
2. 判定通过 → 收进 `PendingDynamicPluginInstall`；随后 `PluginInstaller.installFromDisk` 对每个待装项调 `installAndLoadDynamicPlugin(file, parent, descriptor)` 热替换——内部 `installWithoutRestart` 解包到插件目录 → `PluginDescriptorLoader.loadDescriptor` → 确认旧版已不在加载态 → `DynamicPlugins.loadPlugin`。任一步失败才落 `installAfterRestart` 启动脚本并置 `isRestartRequired = true`。
3. 判定不通过 → `myRestartRequired = true` + `downloader.install()` 直接落启动脚本，重启生效。

`allowLoadUnloadWithoutRestart`（旧式实现 `DynamicPluginsLegacyImpl`）的否决项：

- 插件用到的每个扩展点在平台定义中必须 `dynamic="true"`；旧式 `<components>` 直接否决。
- `ide.dynamicPluginVetoer` 扩展逐个询问 `vetoPluginUnload/pluginLoad`（平台内置 `FallbackPluginVetoer` 走 app + 各 project messageBus 二次查询）。
- 依赖插件图检查（其他插件 optional depends 本插件且无独立 classloader 等情形）。
- 运行期兜底：卸载阶段 `doUnloadPluginWithProgress` 失败（典型为 classloader 泄漏）→ `InstalledPluginsState.setRestartRequired(true)`，与官方文档「卸载失败时询问重启」一致。

官方文档（Dynamic Plugins 页）其余要点：`require-restart="true"` 显式退出才强制重启；第三方付费插件不允许免重启安装更新；Plugin DevKit「Plugin.xml dynamic plugin verification」 inspection 与 Marketplace Verifier 会自动核这些规则。

### 2.3 T-M23.10 定论误判的澄清（反编译实锤）

`plugins/performanceTesting/lib/performanceTesting.jar` 中 `PlaybackRunnerExtended$PlaybackRunnerExtendedPluginUnloadVetoer`：

```java
public String vetoPluginUnload(IdeaPluginDescriptor pluginDescriptor) {
    return activeExecutionCount.get() > 0
        && PluginId.getId("com.jetbrains.performancePlugin").equals(pluginDescriptor.getPluginId())
        ? PerformanceTestingBundle.message("performancePlugin.can.not.be.unloaded") : null;
}
```

否决对象硬编码为 performanceTesting 插件自身，且仅当其命令回放执行中（`activeExecutionCount > 0`）。它从不否决第三方插件的动态卸载。T-M23.10 当年「环境 vetoer 否决 → 覆盖更新必重启 → 不做动态加载」的全局结论不成立；M28 安装器在该结论下被固化成无条件重启路径。

### 2.4 直接根因（本仓现状）

更新链路：`StartupUpdateCheck`（启动检查/通知 [立即更新]）→ `PluginUpdateRunner.downloadAndInstall`（下载+校验）→ `PlatformPluginInstaller.install`——`StartupActionScriptManager.DeleteCommand + UnzipCommand` 调度下次启动删旧解新 → 调用方弹 `RestartDialogImpl.restartWithConfirmation()`「更新完成，重启生效」。全程从未尝试平台动态安装；`PluginUpdateRunner.InstallResult.Installed` 的 KDoc「下次重启生效——T-M23.10 定论」随之过期。

附带说明：若用户经 Settings→Plugins（自定义仓库）更新，平台本就走 2.1 的动态尝试——插件现状合规后该通道理论已可免重启，卡死的只有自研通知链。

## 2.5 F0 核验定论（2026-09-11 实施首日补记）

F0 已按 javap 243（`ideaIU-2024.3.7.1-win.zip` 内 lib/app-client.jar，ms-21 javap）+ 反编译 262 双端完成，原 §4 路线选型**修订**：

- **路线 A（复用 `installFromDisk`）否决**：243 该方法包私有、`File` 参数、6 参；262 public、`Path`、7 参（多 `BiConsumer`）——跨版本签名漂移；且两条平台流程都不卸载已加载旧版（`installAndLoadDynamicPlugin` 在旧版仍加载时直接返回 false），对覆盖更新场景热替换必失败。
- **路线 B 定稿**，五入口双端实证（签名与语义一致）：`PluginDescriptorLoader.loadDescriptorFromArtifact(Path, BuildNumber)`、`PluginManagerCore.findPlugin(PluginId)`、`DynamicPlugins.allowLoadUnloadWithoutRestart(descriptor)`、`DynamicPlugins.unloadPlugin(descriptor)`、`PluginInstaller.installAndLoadDynamicPlugin(Path, JComponent?, descriptor)`。关键澄清：双端反编译实证 `installWithoutRestart` 的 descriptor 参数仅用于进度标题/日志/`fireState`，解包布局由 zip 顶层目录名（`rootEntryName`）决定——传新版描述即可，无需复杂预接线。
- 失败恢复统一回退 `PlatformPluginInstaller.installRestartScript`（原 install 改名，M28 行为保底），无中间死态：卸载失败→插件继续运行原版；卸载成功装载失败→脚本路径重启修复。
- 253 无本地发行版（gradle 缓存仅 243），以反射探测 + runCatching 整体降级覆盖：签名漂移即回退脚本路径（最劣=现状），发版前 verifyPlugin 门禁再硬核。

## 3. 目标与非目标

目标：

1. 自研更新链（启动检查通知 [立即更新]、设置页手动更新）在环境允许时免重启热生效；
2. 平台否决或运行期卸载失败时，自动回退现有启动脚本路径并提示重启，不劣化现状；
3. 三目标平台 243/253/262 兼容，平台 API 签名逐个 javap 核验。

非目标：Marketplace 官方通道更新（平台自管，本就动态尝试）；卸载/禁用免重启（设置页自管）；Gitee 通道接入平台 custom release repository（另行评估，不并入本任务）。

## 4. 方案设计

### F0 技术核验（实施第一步，javap 三平台定签名）

243/253/262 平台 jar 逐个核对以下入口（T-Wia262 教训：javap 权威须覆盖全部目标平台）：

- `PluginInstaller.installFromDisk(model, pluginEnabler, file, project?, callback, pluginUpdateSourceCallback)`（262 反编译 d2 签名如引，@RequiresEdt；243/253 参数序与可见性待核）；
- `PluginInstaller.installAndLoadDynamicPlugin(Path, JComponent?, IdeaPluginDescriptorImpl)`（262 已核：@JvmStatic @Internal @RequiresEdt，返回 boolean；243/253 待核）；
- `PluginDescriptorLoader.loadDescriptor(Path, boolean, PluginXmlPathResolver)` 可访问性；
- `DynamicPlugins.checkCanUnloadWithoutRestart / checkCanLoadWithoutRestart`（262 新 API；243 只有 `allowLoadUnloadWithoutRestart(descriptor, baseDescriptor)` 旧签名）；
- `PluginInstallCallbackData` 的 needRestart getter 名（反编译实证第三构造参即 `!allowNoRestart`）；
- `InstalledPluginsTableModel` 构造与 `PluginEnabler.HEADLESS` 可访问性（路线 A 依赖）。

缺失或签名不兼容时按任务惯例：能力探测（runCatching + 版本分支）降级，262 直调、243/253 反射桥或直接走回退路径，不在低版本硬抛。

### F1 安装主路径改造（核心）

- 路线 A（推荐）：下载 zip 校验通过后整包交给官方 Install from Disk 实现 `PluginInstaller.installFromDisk`——内部即 `PluginInstallOperation(allowNoRestart=true)` 动态尝试 + 热替换 + 失败自动 `installAfterRestart`，回调里按 needRestart 分叉 UX。zip 顶层目录剥离由平台处理（顺带消除 T-M28.5 自剥顶层的特判面）。
- 路线 B（备选，A 不可用时）：手工两段——`checkCanUnloadWithoutRestart(current)` + `checkCanLoadWithoutRestart(PluginDescriptorLoader.loadDescriptor(zip))` 预检 → 通过则 `DynamicPlugins.unloadPlugin(current)` 后 `installAndLoadDynamicPlugin(zipPath, newDescriptor)`；否则走现有 `PlatformPluginInstaller` 脚本路径。
- 安装前置校验收紧：动态安装前校验 zip 内 plugin.xml 的 `<id>`/`<version>` 与 manifest 声明一致，防半截包热替换进插件目录。

### F2 结果 UX 分叉

- 热生效：BALLOON 通知「已更新至 vX.Y.Z，已立即生效」（复用 preview 通知组，bundle 新增键 + `_zh`），不再弹重启对话框。
- 回退重启：保留现「更新完成，重启生效」+ `RestartDialogImpl.restartWithConfirmation()`（脚本已由平台 `installAfterRestart` 或旧 `PlatformPluginInstaller` 落好）。
- `InstallResult` 密封类扩容：`Installed（热生效）` / `InstalledRestartRequired（回退重启）` / `Failed`；编排层与两处 UI（StartupUpdateCheck、AboutConfigurable）同源消费。

### F3 卸载成功率加固（8-20 计划 P1/P2 遗留清收）

热更新成败在运行期：classloader 能否干净释放取决于平台侧是否仍持我们对象。按引用方向排雷（平台持我们对象才算硬屏障；插件内静态 map 持 PsiFile 是内存卫生问题，不阻止卸载但纳入清理）：

- `EntityResolver` companion `cache`（`ConcurrentHashMap<EntityCacheKey, Entry>`，持 PsiFile）——按 8-20 方案改 project 级 Disposable，或最低成本接 `DynamicPluginListener.pluginUnloaded` 清空；
- `PluginCacheManager`、`JoinFkRegistry` 两个 object 与 `SqlPreviewService` 非 Disposable 的生命周期接线；
- 监听/Disposer 审计：`messageBus.connect` 一律以 pluginDescriptor 或服务为 parent；控制台监听、轮询 Timer、弹窗单例（T-RefreshDbSteal 既有治理面）在卸载场景复核一遍；
- 订阅 `DynamicPluginListener` 注册进程内清理钩子（控制台 attach 状态、虚拟外键注册表）。

### F4 验证方案

- 单测：`PluginUpdateRunner` seam 注入扩三分支（热生效/回退/失败），安装编排 fake 断言不触达平台 API（沿用既有约定）；`DynamicInstallSupport` 能力探测纯函数化可测。
- runIde 沙盒 e2e：旧版插件 → 新版 zip 更新演练，观测 `idea.log` 中 `com.intellij.ide.plugins.DynamicPlugins` 判定行与「已立即生效」通知；对照安装/卸载 Performance Testing 插件验证无影响（2.3 结论复核）。
- 真机（人工）：Gitee 内测通道 [立即更新] 全链 + 更新后旧实例功能回归（预览、日志窗口、控制台捕获）。
- 回归：全量测试计数口径照旧；发版前 verifyPlugin 三版本门禁另按定例执行。

## 5. 风险与对策

- 自更新卸载自身：[立即更新] 回调运行在将被卸载的旧 classloader 上——编排层把善后动作限定为平台 API 与通知（通知组 id 是平台侧注册字符串，安全），不得再触达自身服务单例；热替换后旧线程随孤儿 classloader 自然结束。
- 243 管线差异：243 无 `DynamicPluginsSupport` 新管线，路线 A 依赖若在 243 缺失则 243 走回退路径（现状等价，不劣化），262 全功能。
- 热更新后常驻状态跨版本残留：设置常驻实例、工具窗内容按 `DynamicPluginListener` 清理；平台保证插件装载/卸载发生在 EDT write action 下并自动清 CachedValue 缓存。
- 卸载失败兜底：平台 `unloadPlugins` 失败即自动置重启必需，回退 UX 覆盖，无死局。
