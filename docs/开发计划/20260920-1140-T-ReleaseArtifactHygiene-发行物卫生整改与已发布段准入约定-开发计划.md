## 决策定案补充——beta.4 转正式版路线口径（2026-09-22 用户转向；2026-09-23 O-62 落档）

> 背景：beta.4 转正三选一的完整口径此前只存在于本地会话记忆，仓库 docs 零条目（第三轮全景审计 §8.1 登记缺口）；本节按 T-BranchHygiene3（O-62）§三.7 要求落档。**后续事实**：该路线最终未被走完——2026-09-23 发行火车直接开出 `v2026.9.23`（Gitee tag + 发行版 + 附件已上线），`2026.9.18-beta.4` 保持 beta 状态停在历史 tag 列表；本节保留作口径存档与将来同类决策的先例。

**技术口径**：版本号焊在 6 处——外层 zip 名 / 内层 jar 名 / `plugin.xml` `<version>` / MANIFEST `Version` / change-notes 标题块 / `update.json`；因此**转正不可能只改名**，必须用 beta 的树按新版本号重打全量产物。自报 `beta` 的包在已装用户处更新提示永不收敛（IDE 对 pre-release 版本串的排序），拖着不转正等于断供。

**三选项与各自代价**：
- **A 原样转正**（beta.4 树直接换号重打）：带着当时已知的 SenderLoop P0 缺陷出门，不建议；
- **B 摘取重打**（从 beta.4 树摘取 P0 修复后按新号重打）：保留 beta 线内容基线，摘取面需逐项核对；
- **C 用 master 重打**（以当时 master 为基线换号重打）：基线最新最干净，但需重验 beta 线特有改动是否全部在 master。

**复核倾向**：B 或 C；A 不建议。实际走向＝C 的变体（master 火车直接开新版本号），验证路径由 `releaseGate` 承担。

### 1.5 版本号规范（**本轮新读，原为待验证前提**）

`docs/发行说明/版本号规范-说明文档.md` 明文三条，直接决定 D2：

1. **命名格式** `{年}.{月}.{日}`（不补前导零）；**一日一版**——一天最多发布一个版本号，版本号即发布当天的年月日；
2. **同日需再发（如热修）→ 并入下一个自然日**，以次日日期作为版本号；**禁止同日递增后缀**（如 `2026.8.13.1`，四段数字不是合法 SemVer，上架会被拒）；
3. **标签名 = `gradle.properties` 完整版本号字符串，一字不差、不带 `v` 前缀**——downloadUrl 按标签段拼接，标签差一个字符用户点「立即更新」就是 404；**创建时机 = 发行提交之后**。

→ **口径修正 5**：不存在「回头补打 `2026.9.18` tag」这个选项。要发就用**发行当日**的日期号（见 §三 T-RAH-02）。

## 二、目标与非目标

**目标**：发行窗口打开时，让「已发布段的文字」与「发行产物里真有的东西」一致、让自更新链接指向真实存在的包体；并把「已发布段只写已交付内容」变成文档里的明文约定。**同时清掉一个从未存在过的版本块。**

**非目标**：不改产品代码（本任务零 `src/` 改动）；**不在本计划内决定发行日期**（发行窗口由用户测试进度决定）；不重写 CHANGELOG 历史段（只处理 `[2026.9.18]` 这个幽灵段 + 消重标题）；不动 `update/update.json`（用户明示只能手改）；不把 `2026.9.18` 当作要补打的目标 tag。
