### 1.5 版本号规范（**本轮新读，原为待验证前提**）

`docs/发行说明/版本号规范-说明文档.md` 明文三条，直接决定 D2：

1. **命名格式** `{年}.{月}.{日}`（不补前导零）；**一日一版**——一天最多发布一个版本号，版本号即发布当天的年月日；
2. **同日需再发（如热修）→ 并入下一个自然日**，以次日日期作为版本号；**禁止同日递增后缀**（如 `2026.8.13.1`，四段数字不是合法 SemVer，上架会被拒）；
3. **标签名 = `gradle.properties` 完整版本号字符串，一字不差、不带 `v` 前缀**——downloadUrl 按标签段拼接，标签差一个字符用户点「立即更新」就是 404；**创建时机 = 发行提交之后**。

→ **口径修正 5**：不存在「回头补打 `2026.9.18` tag」这个选项。要发就用**发行当日**的日期号（见 §三 T-RAH-02）。

### 1.6 决策 B 让整改形态显著简化（**口径修正 6，最重要**）

原计划 §三 要求「逐条归属、不得按行号区间盲搬」——那是建立在「`2026.9.18` 是个已发布版本，只能把未交付条目摘出来」的假设上。但 §1.3 证明**该版本从未发布**：`[2026.9.18]` 段描述的其实是一个**从未存在的版本**，而段内内容全部来自 master 主线（`f44cf0a` 折入的 dev 块也早已在 master 上）。

→ 因此从当前 master 发一版，段内每一条都会变成真的。整改简化为：

- **把 `[2026.9.18] - 2026-09-18` 段整体并入 `[Unreleased]`**（或按规范在发行当天把 `[Unreleased]` 改名为 `[{发行日}] - {发行日}`），**消除这个从未存在的版本块**；
- **不必做「5 行搬、5 行留」的精细切分**，只需一次**轻量核对**：段内条目对应的能力是否仍在当前 master 上（防「条目描述的功能后来被回退」），核对手段是 grep 关键符号而非逐行归属。

**口径修正 7（并行会话口径分歧，以实测为准）**：并行会话的第二轮全景审计报告记「CHANGELOG 已发布段 12 行 MCP 条目**现为 11 行**（a3cc6e1 改走 1 行）」。**本计划实测仍为 12 行**，且 `git show --stat a3cc6e1` 显示该提交只动了验收文档、**未碰 CHANGELOG**。以实测 12 行为准；分歧登记备查。

## 二、目标与非目标

**目标**：发行窗口打开时，让「已发布段的文字」与「发行产物里真有的东西」一致、让自更新链接指向真实存在的包体；并把「已发布段只写已交付内容」变成文档里的明文约定。**同时清掉一个从未存在过的版本块。**

**非目标**：不改产品代码（本任务零 `src/` 改动）；**不在本计划内决定发行日期**（发行窗口由用户测试进度决定）；不重写 CHANGELOG 历史段（只处理 `[2026.9.18]` 这个幽灵段 + 消重标题）；不动 `update/update.json`（用户明示只能手改）；不把 `2026.9.18` 当作要补打的目标 tag。

## 三、方案

> **分两段执行**：T-RAH-01/03/04 属**文档侧整改，现在可做**（不依赖发行窗口）；T-RAH-02 属**发行动作，挂起至用户测试完成**。

**T-RAH-01（消除幽灵版本段，现在可做）**：
- 把 `[2026.9.18] - 2026-09-18` 段（92–220 行）整体并入 `## [Unreleased]`，并消掉重复的 `### Added` 小节标题（`[2026.9.18]` 段内 96/102；`[Unreleased]` 段内 Added 7/82 与 Changed 18/87）。
- **轻量核对（替代原「逐条归属」）**：对段内提及 MCP/`sqlv_` 的 12 行 + 其余条目，grep 关键符号确认对应能力仍在当前 master 上（重点核对 5 行纯 MCP 条目的工具名是否已全部改名 `sqlv_*`、能力是否仍在）。产出**核对表**（不是逐行归属表）。
- **保留**段内 IDE 功能条目（它们描述的能力已真实交付，只是所属版本块要改）。
- 若发行窗口在整改后打开，则按规范 43 行在发行当天把 `[Unreleased]` 改名为 `[{发行日}] - {发行日}`（**这一步属 T-RAH-02**）。

**T-RAH-02（发行动作，挂起至用户测试完成）**：以**发行当日日期号**发一版真正含 MCP 的版本：

- 按八处同步清单走完整发行；`update/preview.update.json` 的 `version`/`downloadUrl`/`changeNotes`/`publishDate` 与之一致；
- **回读校验**（130–138 行约定 + T-ReleaseChecklist 的 T-RC-03）：附件 `browser_download_url` 与 `downloadUrl` 逐字一致、直取 200；

- **不选路线 A 的理由**（登记备查）：A 只把 `preview.update.json` 指回 `beta.4`，会留下「CHANGELOG 有正式版块、产物里没有正式版」的永久不一致，且 Marketplace 继续断供。

**T-RAH-04（补明文约定，现在可做）**：在 `docs/发行说明/Gitee自动发行工作流-说明文档.md` 补一节「已发布段的准入约定」：
- **已发布段只写该版本产物里真实存在的内容**；晚于 tag 的提交移入本版块（既有 33–35 行约定的镜像）；
- 合并把 dev 的 `[Unreleased]` 折入已发布段时须逐条核对产物，核对手段示例 `git ls-tree -r <tag> | grep -c "^src/main/kotlin/.*/mcp/"`；
- **发行前必须确认 tag 真的建了**（本次事故的根因之一：把发行提交当成发行）。

**T-RAH-05（可选，防复发守卫）**：候选是「已发布段条目 ↔ 产物」的机器核对脚本。**默认只登记为候选**——判据难以泛化（并非每条条目都有可机器核对的路径特征），收益低于 T-RAH-04 的明文约定。

## 四、验收标准

1. `[2026.9.18]` 幽灵版本块消失（内容并入 `[Unreleased]`），`### Added` 等重复小节标题在两段内均消除。
2. 产出**核对表**：12 行 MCP/`sqlv_` 命中行 + 其余条目的「对应能力是否仍在 master」逐项结论。
3. `Gitee自动发行工作流-说明文档.md` 补入「已发布段准入约定」节，含「发行前确认 tag 已建」一条。
4. **（发行窗口打开后）** 新版本号 = 发行当日日期号；`update/preview.update.json` 的 `downloadUrl` 直取返回 **200** 且与 Gitee 发行版附件 `browser_download_url` 逐字一致。
5. 本任务不改 `src/`（零产品代码改动），全量门禁不受影响；若触及 `src/` 须跑 testShards 并说明理由。
6. 第七~九轮流传的「Gitee 已发 v2026.9.18」失实口径在**盘点与报告**中订正（历史报告不改写，只加订正注记）。

## 五、真机走查清单（留人工）

1. **（发行窗口打开后）** 走一次完整发行：门禁 → tag → Gitee 发行版 → 附件 URL 与 `downloadUrl` 逐字一致 → **回读断言**（直取 200 + updates 端点）。
2. 老版本用户更新提示：从 `2026.9.14` 触发一次「检查更新」，确认提示版本号与下载链接可用（自更新通道端到端）。
3. Marketplace 上传后核对：在售版本页的 changeNotes 与整改后的版本段一致（不再含未交付描述）。

## 六、风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **发行前用户测试未完成** | 本计划发行动作的前置是用户测试；若提前发行会把未验证的改动推给用户 | 时序定案：发行动作挂起，文档侧整改先做；发行窗口由用户明示打开 |
| **核对遗漏** | 轻量核对若只看 MCP 12 行，可能漏掉「描述的能力已被回退」的非 MCP 条目 | 核对表覆盖段内全部条目，不只 MCP 行 |
| **版本号取错** | 若沿用 `2026.9.18` 会与 beta 系列同 base、且违反「一日一版」 | D2 已定案用发行当日日期号；规范 1.5 三条为判据 |
| 与上传动作的时序 | 若发行窗口打开后先上传再整改，失实条目会随 changeNotes 公开 | 实施顺序：整改（T-RAH-01/04）先于发行（T-RAH-02） |
| 自更新通道二次断裂 | 只改 `preview.update.json` 而不建 tag 会造成与产物不一致 | 严格按规范「先 tag 后发行版」，回读校验为硬步骤 |
| 判据不可泛化 | T-RAH-05 想机器化核对，但多数条目无路径特征 | 默认不实施，只补 T-RAH-04 明文约定 |
