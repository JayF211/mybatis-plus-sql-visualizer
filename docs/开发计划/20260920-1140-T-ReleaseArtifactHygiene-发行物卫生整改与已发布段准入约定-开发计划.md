## 二、目标与非目标

**目标**：Marketplace 上传之前，让「已发布段的文字」与「发行产物里真有的东西」一致，让自更新链接指向真实存在的包体；并把「已发布段只写已交付内容」变成文档里的明文约定。

**非目标**：不改产品代码（本任务零 `src/` 改动）；不决定 Marketplace 上传动作本身（属 T-ReleaseChecklist N-28 与 §9.1 出场清账）；不重写 CHANGELOG 历史段（只搬被折入的块 + 消重标题）；不动 `update/update.json`（用户明示只能手改）。

## 三、方案

- **5 行纯 MCP 条目**（110/124/159/165/167）整条搬回 `[Unreleased]`。
- **5 行 IDE 功能 + MCP 子句**（126/140/142/144/146）**保留在已发布段**，但须逐行复核：若该行的 MCP 子句描述的能力未随该版本交付，则**只删子句、保留主体功能描述**（主体功能已真实交付，整行移出会造成新的失实）。
- **2 行顺带提及**（105/214）：105（T-IncludeCrossNs 的「含 MCP 片段直渲…逐字节不变」）与 214（T-DmlAliasGuard 测试条目的「MCP crud 出口」子句）按同法只删子句。

**T-RAH-02（自更新链接与产物对齐）**：二选一，**须用户定案（决策点 D1）**：
- **路线 A（对齐文档，最小改动）**：`update/preview.update.json` 的 `version`/`downloadUrl` 改回**当前真实存在的最新发行版**（`2026.9.18-beta.4`，与 `update/update.json` 对齐），消除 404；代价=已发布段的 `2026.9.18` 字样与自更新通道再次错位，且**未解决 MCP 未交付**这一根因。
- **路线 B（推荐，补发行版）**：按八处同步清单走一次**真发行**，产出一个**真正含 MCP** 的版本（tag 名与版本号须定案，见 §六 风险表 D2），使 `downloadUrl` 有对应 tag 与附件；同时按 130–138 行约定回读校验附件 URL 与 `downloadUrl` 逐字一致。**证据可行性**：`2026.9.18` 这个 tag 名从未被占用（本地 23 tag 与远端 21 tag 均无），技术上可创建；但会与 beta 系列共用同一 base 版本号，需版本号规范裁决（`docs/发行说明/版本号规范-说明文档.md`，本计划未读，**列为待验证前提**）。
- 无论走哪条，`update/preview.update.json → update/update.json` 的收尾按 20 行既有约定执行。

**T-RAH-03（销账登记）**：ACP 计划 §9.2 旧名已由 `b9aeeba` 闭合，在第九轮报告与盘点中标注销账即可，本任务不做代码/文档改动；全仓 `mpsv_` 残留 6 文件 11 处逐处性质判定后，**只保留决策/记录/引述性质的 10 处**（`docs/memory-archive` 1 处属归档不改）。

**T-RAH-04（补明文约定）**：在 `docs/发行说明/Gitee自动发行工作流-说明文档.md` 补一节「已发布段的准入约定」——**已发布段只写该版本产物里真实存在的内容**；晚于 tag 的提交移入本版块（既有 33–35 行约定的镜像）；合并把 dev 的 `[Unreleased]` 折入已发布段时须逐条核对产物（`git ls-tree -r <tag> | grep -c "^src/main/kotlin/.*/mcp/"` 这类产物级判据作为核对手段示例）。

**T-RAH-05（可选，防复发守卫）**：候选是「已发布段条目 ↔ 产物」的机器核对脚本（读 tag 树与 CHANGELOG 段，对 MCP 这类有明确路径特征的条目做交叉校验）。**本计划默认只登记为候选**，因为判据难以泛化（并非每条 CHANGELOG 条目都有可机器核对的路径特征），收益低于 T-RAH-04 的明文约定。

## 四、验收标准

1. `[2026.9.18]` 段内不再有条目描述该版本产物中不存在的 MCP 能力；`[Unreleased]` 段接管被折入的未发行内容。

3. `### Added` 等重复小节标题在 `[Unreleased]` 与 `[2026.9.18]` 两段内均消除。
4. `update/preview.update.json` 的 `downloadUrl` 直取返回 **200**（不再 404），且与 Gitee 发行版附件 `browser_download_url` **逐字一致**（130–138 行约定）。
5. `Gitee自动发行工作流-说明文档.md` 补入「已发布段准入约定」节；`scripts/push-all.sh` 类失真引用不在本任务范围（属 T-ReleaseChecklist）。
6. 本任务不改 `src/`（零产品代码改动），全量门禁不受影响；若触及 `src/` 须跑 testShards 并说明理由。

## 五、真机走查清单（留人工）

1. 整改后走一次真发行（路线 B 时）：门禁 → Gitee 建 tag 与发行版 → 附件 URL 与 `downloadUrl` 逐字一致 → **回读断言**（`curl` updates 端点 / 直取 downloadUrl 得 200）。
2. 老版本用户的更新提示：从 `2026.9.14` 版本触发一次「检查更新」，确认提示的版本号与下载链接可用（自更新通道端到端）。
3. Marketplace 上传后核对：在售版本页的 changeNotes 与整改后的已发布段一致（不再含未交付的 MCP 描述）。
