## 一、背景与目标

**现状**：全量门禁 `testShards` 为 6395 例/566 计划类、5 片时长均衡栈。warm 稳态墙钟带 165~196s（BUILD 2m38s~3m12s），物理面（片数/均衡/拆分/JVM 参数/bootstrap/固定 sleep）经 T9~T13 五轮全部销案，地板声明 2m30s~3m00s。T14 交付的机制面杠杆 auto-handicap（同槽恒临界自动补偿）A/B 实测 −7.7%（off 中位 183s vs auto 169s），但 auto 轮 3 轮中 2 轮踩响 SqlPreviewService 族顺序依赖竞态（O-97 形态），D45 定案**缺省关**，并留案「O-97 根因修复后可翻默认开」。

**关于「测试效果不能变」与两条实施面的关系**：auto-handicap 改变的是用例在片间的分配，用例全集、每例断言、门禁判据全部不变；T14 之所以定案缺省关，是因为分区变化会踩响隐藏的测试间状态泄漏，把确定性门禁变成概率性门禁。本轮治理正是把这个隐藏耦合修掉——修掉之后分区变化对结果的影响归零，auto-handicap 才能以「测试效果不变」的语义翻回默认开。两条实施面是同一件事的前后半。

**目标**：
1. O-97/O-93 族顺序依赖竞态根因治理（测试间全局设置态泄漏，两层：堵源+受害自净）；
2. 修成后 auto-handicap 翻默认开，失衡窗口自动兑现 −7%（绝对值约 13s，非失衡窗口零行为）；
3. 继承 t13/t14 在途资产（画像 566/auto-handicap 机制/testDatabase 五任务并行 warm 2m44s vs 串行 ~356s）；
4. 加分件：冷树首轮编译税的 build cache 验证（`org.gradle.caching=false` 现为显式关闭，证伪即弃）。

**预期**：默认态临界片 165~173s 带 → ~156s（T14 A/B 实测先例复现，判据 ≥−5%）；testDatabase 命令墙钟 2m44s（t14 已落，本轮仅验证）。

## 二、红线

1. 零删例：门禁计数恒 6395/0/0/9 + parity 566。
2. 零断言语义改动：`src/test` 只增「状态快照/恢复」行，不改任何期望值、断言逻辑、测试结构。
3. `src/main` 原则零改动：若审计发现 src/main 真缺陷（O-93 型 effective 劫持残留），单列决策点请示，不擅动。
4. 已销案面不重开：T9~T14 物理面清单（片数/均衡/S3 拆分/外部分离桶/JVM 参数/AppCDS/bootstrap/固定 sleep）全部维持原判。
5. `dev→master` 不动；t13/t14/t15 三支链并 dev 的时机留用户拍板（关联在册 D50），本轮收口停分支 push 留底，不自动并。
6. 构建纪律：跑 gradle 前 `parallel_tasks check/register/done`；构建并发 ≤2 路；计时对照实验全机只跑一路 test；长命令后台启不 sleep 等待。

## 三、O-97 证据链与根因假设

**证据链**：T13 R0 冷轮 OfficialApiTest 18/39 单行 ComparisonFailure（同序 warm 未复现）；T14 R2 补偿分区 shard4 117 类爆 20 例（OfficialApi 18 例单行形态 + TenantTest 2 例，其一为「ON 条件不应含 tenant_id」租户注入残值），同注入历史复跑 R2b 零失败；R6 auto 重触发轮 BatchTest 1 例定向 31s 复绿。失败 XML 归档 `t14-perf` 树 `build/fail-evidence/r2|/r6`。

**T13 排除结论勘误**：T13 §七.6 曾排除「formatSql 开关（仅设置 UI/IO 消费，渲染链不读）」——该结论被源码证伪：`SqlPreviewService.kt:1704` 的 `formatSql()` 直读 `effective({ settings?.state?.formatSql ?: true }, { projectSettings?.effectiveFormatSql() })`，渲染链真实消费此全局态，泄漏通道存在。这是本轮能立案推进的前提修正。

**根因假设**：某测试类把 `PluginSettings` 全局态（formatSql、injectTenantLine 等渲染链消费键）改写后不恢复；固定分区下污染源与受害类的相对执行顺序恰好无害，分区变化（补偿/画像刷新/新类进片）随机翻转先后即概率性炸。嫌疑面（实施 S1 精确定位）：

- `PluginSettingsPanelBindingTest.kt:313` 设 `injectTenantLine = true` 且类内**无 tearDown**——租户残值头号嫌疑；
- `SettingsIOTest` 多处 `formatSql = false`——需分辨局部构造对象与单例写入两种形态；
- `ProjectPluginSettingsConfigurableTest` 已有完整的 setUp 快照 `copy()` + tearDown `loadState()` 恢复范式（治理先例），但 UI 点击路径是否全覆盖待核；
- SqlPreviewService 族 7 类（OfficialApi/Tenant/Batch/XmlInline/JpaCrud 等）tearDown 只恢复租户键、不恢复 formatSql——受害面无防御；
- `SqlPreviewServiceBatchTest.kt:640/687` 设 `injectTenantLine = true`，恢复纪律待核。

**待验证前提**：
- **V68**：O-97 根因 = 测试间全局设置态泄漏（formatSql + 租户键），非 src/main 缺陷、非平台/JVM 时序。证伪手段：S1 审计 + S3 复现实验；若两层治理后复现实验仍红，则升级 src/main 嫌疑重查（触发 D54 备选路径）。
- **V69**：受害族 setUp 快照 + tearDown 恢复（照 ProjectPluginSettingsConfigurableTest 范式推广）足以消除该族概率性失败，且不引入新失败——个别类若依赖「前面类留下的非默认态」则属隐藏耦合，逐案登记处置而非回退治理。
- **V70**：两层治理后 auto-handicap 缺省开在强制触发轮（借权重注入 3 连历史）连续多轮零失败。
- **V71**：`org.gradle.caching` 翻 true 后 Test 任务（Gradle 默认不可缓存，需全仓 grep `cacheIf` 复核）执行语义零变化，仅编译/jar 类任务命中缓存，冷树首轮 BUILD 收益可辨。证伪即弃（D56）。
