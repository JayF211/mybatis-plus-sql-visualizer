# 动态卸载问题分析与修复计划

> 创建日期：2026-08-20
> 状态：**部分实施（P1 静态缓存修复已完成，P0 自定义语言阻塞待解决）**
> 优先级：P0（用户反馈卸载后插件仍存在，需重启才生效）

## 问题描述

插件安装/更新/卸载设计为免重启生效（动态加载），但实际卸载后 IDEA 仍显示插件存在，必须重启才能完全移除。

## 根因分析

动态卸载的核心约束：IntelliJ Platform 在卸载插件时执行 dispose 所有服务 → 移除 EP 注册 → 释放 classloader。任何阻止 classloader GC 或平台无法动态移除的注册都会导致卸载失败。

按严重程度排序，共发现 4 处阻塞点：

---

### P0（阻塞级）：自定义语言 + 自定义文件类型注册

**位置**：`plugin.xml` L104~109

```xml
<lang.parserDefinition language="MP_SQL_Preview" .../>
<completion.contributor language="MP_SQL_Preview" .../>
<fileType name="MP_SQL_Preview" extensions="mpsql" language="MP_SQL_Preview" .../>
```

**问题**：`lang.parserDefinition` 和 `fileType` 属于平台**结构性注册**——写入全局 `Language` 和 `FileTypeManager` 注册表，这些注册表不支持运行时移除。即使服务全部 dispose、classloader 释放，平台仍持有这些注册项的引用，插件 JAR 无法被卸载。

这是当前卸载失败的**首要原因**。

**影响范围**：
- `SqlParserDefinition` — MP_SQL_Preview 语言解析器
- `SqlCompletionContributor` — 语言级补全
- `SqlPreviewFileType` — 自定义文件类型
- `SqlPreviewPanel` / `SqlInputEditor` 中的语法高亮依赖此语言注册

**修复方案**（二选一）：

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A：移除自定义语言 | 去掉 `lang.parserDefinition` + `fileType`，预览面板改用纯文本或 Language Injection | 彻底解决动态卸载 | 丢失预览区 SQL 语法高亮 |
| B：保留但接受限制 | 保持现状，在文档/设置页标注「卸载需重启」 | 零改动 | 不满足用户预期 |

若选方案 A，替代高亮思路：
- 使用 `LanguageInjection` 将 SQL 注入已有 `SQL` 语言（需 Ultimate + Database 插件）
- 使用 `EditorCustomElementRenderer` 或自定义 `LayeredLexerEditorHighlighter` 做局部分词高亮（不注册全局语言）
- 简单方案：预览区用 `JTextArea` + 自绘高亮（不依赖 PSI）

### P1（高危）：EntityResolver 静态缓存持有 PsiFile 引用

**位置**：`EntityResolver.kt` L390

```kotlin
companion object {
    private val cache = ConcurrentHashMap<EntityCacheKey, Entry>()
}
```

**问题**：`cache` 是 companion object（类级别静态），持有 `EntityCacheKey.file: PsiFile` 引用。即使所有 Project 服务 dispose，静态 Map 仍被 EntityResolver 类（由插件 classloader 加载）持有，PSI 文件无法 GC → classloader 无法释放 → 插件无法卸载。

`clearCache()` 方法存在但仅在 `PluginCacheManager.clearAll()` 中调用（设置页手动点「清除缓存」），没有接入服务生命周期。

**修复方案**：

将 `cache` 从静态改为项目级实例：

```kotlin
// 改为 PluginSettings 或新建 EntityCacheService 的实例字段
@Service(Service.Level.PROJECT)
class EntityCacheService(private val project: Project) : Disposable {
    private val cache = ConcurrentHashMap<EntityCacheKey, Entry>()
    
    fun getOrCompute(key: EntityCacheKey, stamp: Long, compute: () -> TableInfo): TableInfo { ... }
    
    override fun dispose() {
        cache.clear()
    }
}
```

EntityResolver 不再持有缓存，改为从 `project.getService(EntityCacheService::class.java)` 获取。

涉及文件：
- `EntityResolver.kt`（移除 companion cache，改为委托）
- 新增 `EntityCacheService.kt`（或合并到 `PluginCacheManager`）
- `PluginCacheManager.kt`（调整 clearAll 逻辑）

### P1（高危）：PluginCacheManager 未接入服务生命周期

**位置**：`PluginCacheManager.kt`、`EntityClassFinder.kt`

**问题**：`PluginCacheManager.clearAll(project)` 清除 `EntityClassFinder` 和 `EntityResolver` 的缓存，但仅在设置页「清除缓存」按钮触发。项目关闭或插件卸载时没有自动触发缓存清理。

`EntityClassFinder` 的 `REVERSE_LOOKUP_CACHE_KEY` 用 `Project.putUserData` 存储——Project 关闭时 userData 自动释放，这部分问题不大。但 `EntityResolver` 的静态 cache（见上条）是主因。

**修复方案**：

将 `PluginCacheManager` 升级为 project 级 Disposable 服务：

```kotlin
@Service(Service.Level.PROJECT)
class PluginCacheManager(private val project: Project) : Disposable {
    fun clearAll() {
        EntityClassFinder.clearReverseLookupCache(project)
        EntityResolver.clearCache()
    }
    
    override fun dispose() {
        clearAll()
    }
}
```

设置页「清除缓存」改为调用 `project.getService(PluginCacheManager::class.java).clearAll()`。

### P2（中等）：SqlPreviewService 未实现 Disposable

**位置**：`SqlPreviewService.kt` L55~59

```kotlin
@Service(Service.Level.PROJECT)
class SqlPreviewService(private val project: Project) {
    private val cache = WrapperCache()
```

**问题**：`WrapperCache` 持有 `PsiFile` 引用（通过 `CacheKey.file`）。`SqlPreviewService` 未实现 `Disposable`，项目关闭时 cache 不会显式清空。虽然服务实例最终会被 GC，但显式清理更安全。

**修复方案**：

```kotlin
@Service(Service.Level.PROJECT)
class SqlPreviewService(private val project: Project) : Disposable {
    private val cache = WrapperCache()
    
    override fun dispose() {
        cache.clear()
    }
}
```

## 风险与权衡

1. **移除自定义语言的代价**：预览区 SQL 语法高亮能力减弱。Language Injection 依赖 Database 插件（Ultimate），Community 降级为纯文本。
2. **EntityCacheService 引入的复杂度**：新增一个轻服务，但缓存逻辑更清晰、生命周期可控。
3. **向后兼容**：不涉及 API 突破，仅内部重构 + EP 注册变更。已安装用户首次升级后需重启一次（移除自定义语言注册），之后即可免重启。

## 实施尝试记录（2026-08-20）

### 尝试方案：移除 lang.parserDefinition + 编程注册

**改动内容**：
1. `plugin.xml` 删除 `lang.parserDefinition` 和 `fileType`，`completion.contributor` 从 `MP_SQL_Preview` 改为 `SQL`
2. `SqlInputEditor` 新增 `resolveSqlFileType()` 动态获取内置 SQL 语言（Ultimate 用 `SqlFileType`，Community 用 `PlainTextFileType.INSTANCE`）
3. `SqlPreviewPanel` 同上
4. `SqlCompletionContributor` 移除关键字补全，仅保留实体感知补全

**结果**：编译通过，但 101 个测试失败。

**根因分析**：
- 移除 `lang.parserDefinition` 后，`SqlPreviewLanguage` 无注册解析器 → `PsiFileFactory.createFileFromText` 返回 null → PSI 文件创建失败
- 编程注册 `SqlParserDefinition`（`LanguageParserDefinitions.INSTANCE.addExplicitExtension`）干扰平台测试基础设施 → 大面积测试失败
- `completion.contributor language="PlainText"` 注册后，贡献器未被平台正确调度（可能因 PlainText 语言在测试环境未注册或调度机制不同）
- Community 环境编辑器使用 `PlainTextFileType.INSTANCE`，贡献器注册在 `SQL` 语言上 → 补全不触发

**结论**：自定义语言（`lang.parserDefinition`）是平台结构性注册，移除后无法通过编程方式等效替代（会导致 PSI 文件创建和补全调度全线失效）。动态卸载与自定义语言注册存在根本冲突。

### 可行替代方案

**方案 A：接受现状，文档标注限制**
- plugin.xml 保留 `lang.parserDefinition` 和 `fileType`
- 在 README 和设置页标注「卸载需重启」
- 优点：零风险，功能完整
- 缺点：不满足用户动态卸载预期

**方案 B：分离预览语言到独立插件**
- 将 `MP_SQL_Preview` 语言和补全功能拆分为独立插件（可选依赖）
- 主插件不注册自定义语言 → 支持动态卸载
- 预览插件单独安装/卸载
- 优点：主插件可动态卸载
- 缺点：架构复杂，用户需额外安装预览插件

**方案 C：使用 Language Injection 替代自定义语言**
- 移除自定义语言，改用 `LanguageInjection` 将 SQL 注入内置 `SQL` 语言
- 优点：保留语法高亮
- 缺点：依赖 Database 插件（仅 Ultimate），Community 无高亮

**推荐**：短期选 A（文档标注），中期选 C（Language Injection + Community 纯文本降级）。
