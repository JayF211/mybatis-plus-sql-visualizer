# T-ExplainIndex 执行计划索引缺失建议 — 开发计划

- 日期：2026-09-16 06:47
- 任务编号：T-ExplainIndex（全分支功能全景审计报告 §7 N-23）
- 来源：一键 EXPLAIN 现输出原始计划文本，普通用户读不出行动项；把「SQL 调试闭环」推进半步到「优化建议」，Log 系/Ultra 均无此能力
- 性质：新功能（EXPLAIN 结果结构化识别与建议呈现）
- 实施方式：任务分支 t-explainindex
- 前置：**T-MergeDev2Master 合流**（底层识别函数须与 dev 侧 perf_advice 工具共用，避免两套口径）

---

## 一、背景与依据

EXPLAIN 是「真实计划诊断」环的入口能力（7 方言含信创），但原始计划文本（MySQL 表格行 / PG 文本树）对非 DBA 用户是只读天书。竞品与本插件的差距不在有无 EXPLAIN，而在读完之后用户能不能行动。本任务把高频可判定模式（索引缺失类）提炼为一条可点击的建议提示。

## 二、现状核实（实测）

| 面 | 现状 | 位置/证据 |
|---|---|---|
| EXPLAIN 执行链 | 一键 EXPLAIN 经内嵌原生控制台执行，结果由原生控制台呈现（Ultimate） | master 执行链 + database-optional.xml |
| MCP 侧性能建议 | dev 侧 perf_advice 工具已产性能建议文本（七工具二期交付） | dev f6533f7 |
| 需核实的落点 | 原生控制台结果集的程序化读取面（能否在结果旁挂建议）**实施前必须核实**，不得臆断平台 API | 实施第一步 T-EI-01 |
| 备选落点 | O-16 T-NoticeChannel 立项的「结果/错误/notices 三元组」消息区可作建议承载位（协同不重复建设） | 第五轮 O-16 计划 |

## 三、方案

**T-EI-01（落点核实）**：核实原生控制台执行结果的程序化读取与附加呈现能力（结果集行数据可否插件侧读取）；两落点定案——A：原生控制台消息区/notices 位追加建议行（随 T-NoticeChannel 基建）；B：EXPLAIN 结果快照进插件面板侧自渲染（重，备选）。

**T-EI-02（识别器纯函数）**：`ExplainIndexHint` 纯函数族，两方言先行：MySQL 表格式（`key=NULL` 且 `rows` 超阈值、`type=ALL` 全表扫、`Extra` 含 Using filesort/Using temporary）；PG 文本树（`Seq Scan` 于大表、无匹配索引行）。产出结构化建议（命中规则、涉及表与列、建议文案），只提示不执行不改 SQL。规则集放 util 供 perf_advice 复用（合流后接线，MCP 输出同源）。

**T-EI-03（呈现接线）**：按 T-EI-01 定案落点接线；建议条含「展开依据」（命中的计划行原文），无命中零输出（不噪音）；方言不支持静默降级（保持现状）。

## 四、验收标准

1. 识别器纯函数测试覆盖两方言各正反例（有索引/无索引/阈值边界/格式变异），零平台依赖。
2. EXPLAIN 大表全扫场景真机（或 Lab 容器）出建议条，命中依据可展开；小表/命中索引不出条。
3. 不支持方言（信创系）行为与现状逐字节一致。
4. 全量 testShards 绿；perf_advice 接线后其测试同步绿（同一规则集单源）。

## 五、真机走查清单（留人工）

MySQL 与 PG 各跑一条无索引大表查询核对建议文案与展开依据；确认原生控制台内呈现不破坏既有结果页。

## 六、风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 原生控制台读取面不可达 | 平台 API 不开放结果集程序化读取 | T-EI-01 前置核实，不可达则走 T-NoticeChannel 承载位或备选 B |
| 误报建议 | 阈值一刀切在小表/临时表噪音 | 阈值可配 + 无命中零输出 + 依据可展开可证伪 |
| 双口径漂移 | UI 与 MCP 各一套规则 | 单一规则集 util，两侧消费 |

## 七、实施顺序

```
T-EI-01（落点核实）→ T-EI-02（识别器纯函数+测试）→ T-EI-03（呈现接线+perf_advice 接线）→ 全量门禁 → 真机走查
```
