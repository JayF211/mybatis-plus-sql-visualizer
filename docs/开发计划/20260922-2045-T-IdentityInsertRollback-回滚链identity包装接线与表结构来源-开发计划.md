## 一、背景与依据

O-52（T-IdentityInsertWrap，`docs/开发计划/20260921-2330`）把「可回放 INSERT 的 identity 包装」从**生成物缺陷**升级为**执行缺陷**，依据是回滚弹窗真的会把生成的 INSERT 提交执行——SQL Server 上把带 identity 列的整行 INSERT 直接提交会报 **544**，须用 `SET IDENTITY_INSERT <表> ON/OFF` 成对包裹。

该批交付的判定落在共用渲染点 `BatchModel.renderSql` 的 INSERT 分支（`model/BatchModel.kt:128-133`）：

```kotlin
if (active.none { it.autoGenerated }) base
else dialect.renderInsertWrapper(tableName, base, identifierCaseSource) ?: base
```

即包装要成立，**两个输入必须同时到位**：`active` 里有列带 `autoGenerated=true`，且 `model.dialect` 是需要包装的方言（SQL Server）。

独立复核发现：**回滚链上这两个输入都是空的**，故 `wrapper` 恒为 null、产品侧永不包装（blocker②）。同族的另两条链已收口——CRUD 链由 O-52 本体接线，PSI/实体批量链由 `7f21949` 补齐 `autoGenerated`——**只剩回滚链**。

## 二、目标与非目标

**目标**

- DELETE → 粘贴快照 → 生成回填 INSERT 这条链上，SQL Server 方言产出**带 `SET IDENTITY_INSERT … ON/OFF` 成对包装**的语句（改前报 544）。
- 包装所需的两项输入（`dialect` / `identityColumns`）在**生产登记点**真实到位，而不是只在单测里到位。
- 默认路径逐字节不变：不需要包装的方言（PG/MySQL/Oracle/DM/KingBase/H2/SQLite/MariaDB）产物与改前完全相同。

**非目标**

- 不改 CRUD 链与 PSI/实体批量链（已由 O-52 本体与 `7f21949` 收口）。
- 不为 SQL Server 以外的方言造包装（`renderInsertWrapper` 默认 null 的口径不变）。
- 不引入「执行态 → 源 SQL」的位置/列换算。
- 不改 `RollbackSnapshotStore` 的字段语义（O-52 已定 D1=A，字段缺失 = 不包装）。

## 五、真机走查清单（留人工 / 环境依赖）

1. **SQL Server 端到端（决定性）**：在真实 SQL Server 上 DELETE 一张含 identity 列的表 → 粘贴快照 → 回填 INSERT **执行成功**（改前报 544）。
   **2026-09-23 已取得引擎级真机读数（本机 Docker 起了 SQL Server 2022 16.0.4295.3 一次性容器）**：建 `t_identity(id INT IDENTITY(1,1) PRIMARY KEY, name)` → 插两行 → `DELETE` → **不加包装**的回填 `INSERT INTO t_identity (id, name) VALUES (1, 'a')` 报
   `Msg 544, Level 16, State 1 … Cannot insert explicit value for identity column in table 't_identity' when IDENTITY_INSERT is set to OFF.`（与报障同码同文案）；
   **按本插件产物形态**（逐条 `SET IDENTITY_INSERT … ON;` + INSERT + `SET … OFF;`）执行 → 两行均**成功**、id 1/2 原值恢复；对照「不指定自增列」的 INSERT 无需包装即成功（自增出 id 3）。
   容器为一次性（库/表已 drop，`sys.databases` 仅 4 个系统库、无残留表）；DBX 侧已登记连接「本地 | SQL Server 2022 (mpsv 探针容器)」（127.0.0.1:14333，MCP 作用域默认不含新连接，故读数走容器内 sqlcmd）。
   **仍未验（用户侧）**：§五-1 的 **GUI 半边**——在 runIde 沙盒里配 DBN 数据源、走预览面板的 DELETE→粘贴快照→回填流程（本次验的是该流程产出的 SQL 文本在真引擎上的行为）。
2. **同场景回归**：同一 DELETE 流程换 MySQL / PG 执行回填 INSERT，产物与改前逐字节一致（不因接线引入多余包装）。
3. **解析不到表结构时的形态**：在无数据源/无表模型的工程里走同一流程 → 不包装、不报错（fail-safe 分支的真机确认）。
4. **DM8（对照）**：~~显式插入自增列是否需要包装……建议本轮补一次读数~~ → **2026-09-23 已实测并证伪为「需要」**：DM8 报 `dm.jdbc.driver.DMException: 仅当指定列列表，且SET IDENTITY_INSERT为ON时，才能对自增列赋值`（vendorCode -2723），加包装后成功 ⇒ **我们只给 SQL Server 造包装是缺陷**，已按 O-52 §五-3「另立增量」落地（`DmDialect` 覆写 `renderInsertWrapper` + 共用形态抽取 + 解冻三处契约断言；反向验证 3 例红）。

## 六、风险与缓解

| 风险 | 缓解 |
|---|---|
| **自省路径引入 EDT/PSI 开销或慢操作断言** | 登记点在执行前调用链上；解析必须走后台或既有缓存面（`DatabaseSchemaResolver` 已有负缓存），禁止在 EDT 直读 PSI；必要时把解析结果随会话缓存 |
| **无数据源工程下解析抛异常** | 一律 `runCatching` + 空清单降级（不包装），并由 §五-3 真机确认 |
| **表名匹配歧义（同名表/模式前缀）** | 解析不到就空清单，**不猜**（与 O-52「未知不臆造」同口径） |
| **改 `SqlPreviewPanel.kt` 与并行会话冲突** | 该文件是热点（O-48/O-49/T-PerfSweep6 都动过）；开工前 `git fetch` 并 rebase 到最新 master，冲突按「本任务只加参数实参」最小面处理 |
| **既有断言反转遗漏** | §四-6 列为独立验收项；T-IIR-04 与 T-IIR-01 同批提交 |
