### G2 write-unsafe 族收口（P2，同族缺陷再犯面）

**T-TS-03 四处真实 write-unsafe 站点过闸**（`BannedApiSourceScanTest` 现有规则看不见它们，因全是尾随 lambda 形态）
- `ui/SqlInputEditor.kt:142` — 自动补全 `commitDocument`（用户键入触发，常态 write-safe，但需显式过闸或标注）
- `ui/SqlPreviewPanel.kt:2486` — 同型 `commitDocument`
- `log/SqlToJavaPanel.kt:881` — `setResultText(code)` → `WriteCommandAction` 写结果区文档（**WriteCommandAction 不赋予 write-safe 资格**）
- `log/SqlToJavaPanel.kt:820` — `render(...)` 内部调 `setResultText`，且投递拍里还 `SqlSelectionDialog(...).show()`（模态），间接同族
- 统一做法：写体过 `execute/DocWriteContext` 既有闸门（`runWriteSafe` / `invokeLaterWriteSafe`），或按平台语义显式声明 write-safe 模态 + `// write-safe: <理由>` 标注（仓库既有豁免惯例）。

**T-TS-04 守卫提取器扩到尾随 lambda 形态**
- 现状：`convention/BannedApiSourceScanTest` 的调用提取用 `indexOf("invokeLater(")`（`:326-346`），**看不见** `invokeLater {` → 只收紧谓词会新增 0 处红（复核实证）。
- 要做：提取器支持花括号形态 + 增加「闸门感知豁免」（识别 body 内 `DocWriteContext.runWriteSafe` / `invokeLaterWriteSafe`，避免把已过闸的 `DataSourceSelector.kt:3387` 误判）+ 标注豁免白名单。
- 收紧后应恰好命中 T-TS-03 处置后的残留（预期 0，或仅剩已标注豁免项）。
