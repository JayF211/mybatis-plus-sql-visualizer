## 一、背景与依据

第九轮复查的基调是「新功能面首审 + 上轮立项验收」：T-PerfSweep5 十六项全部收口（系列连续两轮无在册遗留），心跳计时改造根治「增强捕获 30 秒必掉线」，设置页导航改 EP id 消除 EDT 慢操作。但本轮引入了一个新的高频面——**预览插入列 inlay 以 `language="SQL"` 注册到 IDE 全部 SQL 编辑器**：provider 内虽有双锚点过滤，但命中后每次 daemon pass 全文重新词法且无缓存，一次性闸门 `collected` 还是非线程安全的普通 `var`，而平台 `InlayHintsPass.doCollectInformation` 用 `JobLauncher.invokeConcurrentlyUnderProgress` 分片并行（平台源码实证）——这是全篇唯一「中」级发现，也是唯一带正确性（不只是一次性成本）的发现。另有两条可省的重复工作：`schema_context` 每次调用重建全量索引、XML 一次预览解析两遍；一条资源面代价：预览临时文件唯一命名后异常路径残留无兜底。

本计划 9 项任务 + 1 项定案不改（发现 17 AgentProxyCL loader 不缓存是刻意取舍：避免强引用驱动类钉住旧 RestartClassLoader，量级与 `newProxyInstance` 同阶，留档不改），一次收口、一道门禁。

## 三、方案

**T-PS6-01（inlay 规划缓存 + 闸门线程安全，中·本轮头号）**：两件组合——
1. 闸门改 `java.util.concurrent.atomic.AtomicBoolean`（`compareAndSet(false, true)` 后才执行收集），消除平台分片并发下「同 collector 被两线程各跑一遍、提示二次投进同一 sink」的通道；平台侧依据 = `InlayHintsPass.doCollectInformation` 的 `JobLauncher.invokeConcurrentlyUnderProgress`（第九轮报告 §4.2 平台源码实证），本任务的守卫测试用「同一 collector 并发调 collect 两次」断言只投递一次（模拟分片竞态，无需真起 daemon）。
2. 规划结果按 `document.modificationStamp` 单槽缓存：`InsertColumnInlayPlanner.plan` 的产物（hint 列表）按「文本指纹 + 时刻」缓存，stamp 未变直接复用；注意 `collect` 每次取 `editor.document.text` 本身就是 O(文档) 拷贝，缓存键取 stamp 可顺带省掉未变时的 `text` 读取。planner 侧 `wordUpper` 的 `substring + uppercase` 双分配可在同一任务顺手收敛（`locale` 明确的 `uppercase()` + 只在需要时构造）。
测试：并发 collect 只投递一次（先红后绿：退回普通 var 断言红）/ stamp 未变不重算（planner 调用计数探针）/ stamp 变更后结果正确 / 越界防御与既有提示文案回归。

**T-PS6-02（schema 索引跨调用缓存，中低）**：`McpSchemaContextService.collectEntries` 的调用内索引改为跨调用持有（按数据源键缓存，键口径沿用既有 `IdentityHashMap`/身份键纪律），失效双保险：接 `MetadataInvalidator` 登记表（DDL 执行后失效，基建已有——`MetadataInvalidator` 的 `register` 机制就是为此设计）+ TTL 上界（实施定案，建议 30s，与 `DatabaseSchemaResolver` 负缓存同量级）；同时把「所有表所有列」改为**惰性建列**：索引只记表对象，列在命中输出时才构建（`readModelTables` 的列循环下移到输出路径）。测试：同调用/跨调用命中不重扫（反射计数探针）/ DDL 失效后重扫 / 输出结果与既有逐字节一致。

**T-PS6-03（XML 解析链收敛，中低）**：两件组合——
1. `XmlPreviewService.preview` 的 `XmlCrossNsFragmentResolver.resolve` 与 `XmlMapperParser().parse` 共用一次解析：给 resolver 加「已解析 Document 入参」重载（或让 resolve 返回其 Document 供 parse 复用），消除同一文本两遍 DOM（实测 225KB ≈1.6ms×2）。
2. `SecureXml` 工厂/构建器 ThreadLocal 缓存：`DocumentBuilderFactory` 配置一次后按线程复用（`DocumentBuilder` 同样非线程安全，一并 ThreadLocal）；失效面简单（安全配置是常量），测试用「同线程两次 parse 复用同一工厂」探针 + 跨线程各自建。
约束：**预扫（`checkEntityExpansion`）语义不得削弱**——它拦的是内联 DTD 膨胀，与工厂缓存无关，两条路径都要保留；`SecureXml` 是无状态 object 的既有形态改为持有 ThreadLocal 属结构性变更，KDoc 须同步。

**T-PS6-04（预览临时文件兜底回收，中低）**：目录级兜底三件（按性价比取二）——
1. 预热目录启动清扫：首次建面板时扫 `preview/` 目录，删除「年龄 > 7 天」（实施定案）的残留文件；
2. 单目录条数上限：超过 N（建议 200）按 mtime 删最旧；
3. `dispose()` 路径补一次 `releaseEditor` 同款回收（当前清理实际依赖 `removeNotify`，三种宿主下 dispose/removeNotify 先后未穷尽）。
约束：只动插件自有预热目录（`.idea/sql-visualizer/preview/`），不得碰用户文件（照 `SqlLogAutoSaver` 裁剪的「宁漏删不误删」定案精神：先按文件名模式过滤再删）。测试：残留文件按年龄/条数回收 / 非本插件文件零删除 / 正常路径行为不变。

**T-PS6-05（attach 链重连 + 退避语义，中低·功能面）**：两件组合——
1. attach 链照 premain 改循环 accept：保留监听 socket 至运行结束（复用 premain 通道的「循环 accept + 收口三点」形态），使 attach 启动的应用掉线后 agent 能重连（现场根因形态在 attach 路径的补齐）。
2. 退避语义修正：`SenderLoop` 的 `backoffMs = 1000` 从「连接成功处」后移——改为「连接存活超过阈值（如首帧交换完成 / 存活 > N 秒）才复位」，或增加「同端口连续快速失败计数」独立退避；同修发现 9 的端口复用面（agent 对「连上即被关」连续 N 次后放弃该端口，退出重试）。
测试（agent 通道）：连上即被关的模拟服务下退避确实增长（先红后绿）/ attach 链重连端到端（照 `ConnectWeaveEndToEndTest` 形态）/ 正常连接不受影响。

**T-PS6-06（premain 通道三处边界，中低）**：
1. 去重判据改 `isSessionHealthy`（半死会话不再挡同 pid 重连一次，`AgentManager.kt:820-824`）；
2. 通道上限语义变更（并发服役数 ≤4）与 pid 未知去重失效（峰值 32）登记为已知边界，注释写清取舍与自愈路径；
3. 顺带核对 `:660-663` 上限判定与 `:720-732` 超时判定的注释一致性。
测试：半死会话语境下同 pid 重连放行（构造 alive 但心跳过期的会话）/ 既有通道上限用例回归。

**T-PS6-07（N6 建边日志降频，中低）**：`JoinVirtualFkProvider` 的每表 INFO 降 DEBUG；保留「本次建图首行 INFO」（`(all refs)` 形态出现一次即证明 EP 被建边链触达——诊断价值所在，注释里写清为何只留首行）。测试：日志形态断言（首图一行 INFO + 后续 DEBUG）或按既有探针口径回归。

**T-PS6-08（低危快件批 A·代码治理，低）**：写集无交集，可并行——
- `AgentManager.shutdownAll` 补 monitor 复位（发现 8）；

- `bailAfterTraversal` 加短 TTL「扫描失败」标记（发现 11）；
- `withScanBudget`/`ScanBudget` 死代码删除或补消费方说明（发现 12）；
- `SqlHookCallbacks.fallbackCount()` 接出口（发现 13）；
- `LogToSqlPanel.kt:381` 计数缓存或条目上限（发现 16）；
- `JoinFkRefTables` 登记处补「登记数 == 清理数」守卫或注释（发现 18）。

## 六、风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 陈旧产物劫持 | internal 新函数/字段首跑 NoSuchMethodError（多犯实录） | 首跑前清 build/classes + build/kotlin（+ agent 子项目 build） |
| inlay 缓存正确性（T-PS6-01） | stamp 复用判据若漏（如文档内容变但 stamp 未变），提示与文本错位 | stamp 是平台文档变更的权威标记；命中仍做越界防御；真机走查项 1 |

### 8.2 计划前提被证伪 / 就地更正

1. **「collector 内缓存」是死代码**（计划 §三 T-PS6-01② 字面实现）：平台**每个 highlighting pass 都新建 collector**——`InlayHintsPassFactoryInternal.createHighlightingPass` 里 `InlayHintsSinkImpl(editor)` 与 `getProviders(...).mapNotNull { it.getCollectorWrapperFor(...) }` 逐 pass 执行（**243 装机版源码实证**，与报告引的 262 同形）。故缓存必须落进程级（`InsertColumnInlayPlanCache`），且键须含文档身份——`modificationStamp` 是**全局** 24 位计数器（`LocalTimeCounter.MOD_COUNTER_MASK = 0x00ff_ffff`），跨文档可碰撞。
