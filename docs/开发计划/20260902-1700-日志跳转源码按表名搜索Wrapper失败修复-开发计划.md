# 日志「跳转到源码」按表名搜索 Wrapper 失败修复

> **创建日期**：2026-09-02
> **优先级**：P1（用户反馈）
> **状态**：待开发

---

## 1. 问题描述

SQL 日志列表右键 SQL → 「跳转到源码」，提示：`未找到表 "user" 对应的 Wrapper。`

### 1.1 用户场景

用户在 SQL 日志面板看到一条 `SELECT * FROM user WHERE id = 1`，右键选择「跳转到源码」，期望定位到产生该 SQL 的代码位置（如 `UserService.java` 第 42 行的 `lambdaQuery()` 调用处）。实际弹出提示「未找到表 "user" 对应的 Wrapper」。

### 1.2 触发条件

- 实时 SQL 日志条目**不携带 `sourceFile`**（未配置 `SqlSourceInterceptor` 或拦截器未生效）
- 插件回退到「按表名搜索 Wrapper」的启发式路径
- `WrapperSearchService.search(project, "user")` 返回 `WrapperSearchResult.None`

---

## 2. 根因分析

### 2.1 设计缺陷：事后搜索 vs 执行时记录

**当前架构有两个跳转路径**：

| 路径 | 触发条件 | 可靠性 |
|------|---------|--------|
| 精确跳转（file:line） | 条目携带 `sourceFile`（由 `SqlSourceInterceptor` 注入） | ✅ 可靠 |
| 表名搜索 Wrapper（回退） | `sourceFile == null` | ❌ 不可靠 |

**核心问题**：表名搜索 Wrapper 是一种**事后猜测**——从 SQL 中提取表名，再到项目代码中搜索引用该表的 Wrapper 链。这种方法：

1. **搜索范围过窄**：只搜索 `Wrappers.lambdaQuery()` 等 5 个静态工厂类的引用，不覆盖 `service.lambdaQuery()` / `service.getById()` 等 IService 链式写法（绝大多数 MP 项目的实际写法）
2. **实体类解析失败时静默跳过**：字符串参数链式调用（`.eq("name", "John")`）无法解析实体类，候选被丢弃
3. **本质不可靠**：即使搜索成功，找到的 Wrapper 链也不一定是产生该 SQL 的那条——同一表可能有多处 Wrapper 链

**正确方案**：SQL 日志的源码跳转**必须依赖执行时记录的源码位置**（`SqlSourceInterceptor`），而非事后搜索。

### 2.2 现有源码位置记录机制

```
应用 JVM（SQL 执行线程）
  └─ SqlSourceInterceptor.beforeQuery/beforeUpdate
    └─ CallerSourceLocator.locate()  ← 沿线程栈取第一个用户代码帧
    └─ println("SQLVIS-SOURCE|path|line")  ← 打印标记到 stdout

IDE 控制台（轮询捕获）
  └─ SqlLogConsoleBridge.processConsoleLine
    └─ SqlSourceMarker.parse(line)  ← 解析标记行
    └─ ctx.pendingSource = marker   ← 暂存源码位置
    └─ 下一行 SQL 解析时附加到 LogSqlEntry
```

**此机制已完整实现**（F-44-6），但**需要用户手动部署 `SqlSourceInterceptor`**。

### 2.3 问题本质

| 问题 | 根因 | 影响 |
|------|------|------|
| 用户未配置 `SqlSourceInterceptor` | 拦截器是可选示例，需手动复制到项目并注册 | 所有实时日志无源码位置 |
| 回退路径（表名搜索）不可靠 | 设计缺陷：事后搜索本质无法保证准确性 | 用户看到「未找到 Wrapper」 |
| 错误提示不友好 | 直接显示技术细节，无配置引导 | 用户不知道需要做什么 |

---

## 3. 修复方案

### 3.1 总体策略

**核心原则**：日志源码跳转**必须依赖执行时记录的源码位置**，移除不可靠的表名搜索回退，改为引导用户配置 `SqlSourceInterceptor`。

```
改造前：
  sourceFile != null → 精确跳转
  sourceFile == null → 表名搜索 Wrapper（不可靠）→ 失败 → 「未找到」

改造后：
  sourceFile != null → 精确跳转
  sourceFile == null → 提示配置 SqlSourceInterceptor（引导部署）
```

### 3.2 改动 1：移除表名搜索回退，改为配置引导

**改动文件**：`src/main/kotlin/.../log/SqlLogPanel.kt`


**新增配置引导弹窗**：


## 6. 风险评估

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 移除表名搜索后，未配置拦截器的用户无法跳转 | 用户体验下降（从「不可靠跳转」变为「不跳转」） | 通过配置引导弹窗明确告知用户原因和解决方案 |
| 配置代码生成可能不匹配项目实际结构 | 用户需要手动调整 | 提供多种模板（Spring Boot / 原生 MyBatis / 手动注册） |
| `WrapperSearchService` 被移除调用后成为死代码 | 代码冗余 | 保留类但标记为 `@Unused`，后续其他功能可复用 |
