## 一、现状核实（实测 2026-09-24 02:20~02:40）

### 1.1 执行链路（buildSrc/src/main/kotlin/mpv-testing.gradle.kts）

- 权威全量＝`./gradlew testShards`：聚合任务 dependsOn 三件事——`testShard1~3`（IPGP `testIde.register`，Platform 测试框架，各片独立沙盒 `build/test-sandbox/shardN`）、`:sql-visualizer-agent:test`（独立构建通道，连带构建 agent fat jar 与 attach 子 JVM）。`org.gradle.parallel=true` 下三片与 agent 通道并发。
- 分区算法：配置期扫描 `src/test/kotlin` 提取顶层测试类 FQCN 全集（DB 集成 5 类只归 testDatabase），权重来自 `build/test-results/{test,testShard1..3}` 历史 XML（同类取 mtime 最新），无数据类取已知中位数；贪心均衡（时长降序、类名升序）；剪贴板亲和类（源码含 CopyPasteManager/systemClipboard）固定第 1 片。配置缓存语义：分区在下一次配置失效后重算。
- 聚合报告：doLast 汇总各片 `tests/failures/errors/skipped` 四元组，与串行 `./gradlew test` 口径 parity 对账。
- 片数 `-PtestShardCount=N` 默认 3：2026-09-17 T-TestPerf3 复测定案（4 片 3m02s vs 3 片 2m03s），当时片内执行量约 84s 量级。
- `-PtestHeapSize` 堆覆盖开关已存在，T-TestPerf2 实测 2g 无明确收益，缺省不开。

### 1.3 已排除的方向（历史实证，不再立项）

- 默认 test 任务多 fork 并行：PersistentFS 互踩成片失败（191 失败先例）。
- 纯逻辑用例独立分桶进全量：68 例隐性平台依赖脱离平台 JVM 即红（testFast 作为**日常快测**通道保留，不进全量）。
- 片内再开多 fork：分片已用满核，只加剧争用。
- 测试堆加大：`-PtestHeapSize=2g` 已实测无明确收益。
- build cache：三次实证复用陈旧产物造成成片假失败，已在 settings 层关死，不开倒车。
- 测试源码 sleep 拖尾：本轮扫描全量 `Thread.sleep` 单处最大 720ms、绝大多数 ≤300ms，无优化价值。

## 二、瓶颈画像与空间分析

当前 warm 全量墙钟由四段叠加：配置期（配置缓存命中时秒级）→ 编译段（主源集+测试源集 Kotlin 增量编译）→ 沙盒准备与测试 JVM 启动（每片一次 IPGP Platform 启动）→ 片内类执行（最重片 ≈ 3.5 分钟）。以 1.2 数据推算，**片内执行已重新成为墙钟大头**（9-15 那轮片执行 84s 占墙钟 2m05s 的 67%；现在最重片 210s，占比更高）。空间按预期收益排序：

1. **S1 分片均衡治理**：三片实测 168.0 / 202.9 / 210.6，若均衡到 ≈194s×3，最重片少 ~17s。失衡根因有三个待裁决假说（见 §三前提 1），对应三种修法，实施时用数据选。
2. **S2 测试 JVM GC 换型实验**：JBR（JDK21）默认 G1；本套件是「类多、单类短、UI 重类长跑」混合负载，ParallelGC 在批处理型负载常有 10%~20% 收益，本机未测过。零代码风险（Test 任务 jvmArgs 开关），对照实验定去留。注意与已否决的堆参数实验是两回事。
3. **S3 片数重测**：2026-09-17「4 片更慢」定案时的负载是片执行 ~84s（固定开销占比高，片数越多固定开销×片数越亏）；现在片执行 210s，固定开销占比大幅下降，边界条件已变，值得 3 vs 4 重测。纯调参（现有属性），默认维持 3 片除非明确收益。
4. **S4 关键路径时序审计**（一次性，顺带完成）：从各任务 START/END 时间戳确认三片并发重叠度、agent 通道是否拖尾、prepareSandbox/编译段实际占比。若发现编译段占比异常（Kotlin 增量失效形态），转编译链健康度诊断并如实登记。

## 三、待验证前提（实施者先证伪再动手）

1. **片失衡根因未裁决**：假说 a＝配置缓存命中冻结分区（权重 XML 已更新但配置期未重跑，`listFiles` 目录列举是否触发配置缓存失效未验证）；假说 b＝权重数据本身带并发膨胀噪声（分片单类耗时比串行膨胀约 30% 且各片膨胀不均，均衡器追噪声）；假说 c＝新增/变重类权重滞后一轮（新类取中位数，实际偏重）。三假说可并存，修法不同（a→stamp 显式失效；b→同类近 K 份取中位数平滑；c→不可消除，靠聚合报告的预期 vs 实测对照持续暴露）。
2. **「片内执行是墙钟大头」是外推**：依据是 1.2 的 XML 执行合计与 9-15 墙钟结构，但当前命令**总墙钟无实测读数**。若阶段 A 实测显示编译段/沙盒准备占大头，本计划方案重心转向编译链诊断（S4），S1~S3 降级。
3. **GC 换型收益存在性未验证**：JDK21/JBR 环境无本仓实测数据；若 C1 对照两跑收益 <5%，不落地，仅保留开关与结论。
4. **4 片可能仍劣于 3 片**：与 2026-09-17 定案相反的只是边界条件推理，不是结论；C2 对照无收益即维持 3 片定案不动。
5. **agent 通道不拖尾**：37.5s 执行量级推断不会晚于最重片结束，但任务图时序（agent fat jar 构建→agent:test 与三片的相对起止）未实测；若实测拖尾成关键路径，再议编排调整（本计划不预设改任务依赖图）。

- 跑前 `parallel_tasks.py check` + `timeout 10 docker info` 验 daemon 活性；全量**单路收口**（有其他构建活跃则等待），分片沙盒在各工作树自己的 `build/` 下天然隔离。

### 阶段 B：分片均衡治理（S1，改 mpv-testing.gradle.kts）

- B1 聚合报告加「预期 vs 实测」对照行：各片配置期预期 execSum 与实测 execSum 并排打印，此后权重失准一眼可见。

- B3 若 A3 实锤配置缓存冻结分区：给分区计算加显式失效源（结果目录最新 mtime 作为配置输入读入），保证权重更新能触发重算；未实锤则不动。
- B4 聚合报告加分片并集 parity 校验：各片 XML 类名并集必须等于配置期 discoveredTestClasses 全集，缺失即打 ERROR 行（防类发现回归，T-TestPerf2 曾实证漏 3 类形态）。纯报告层，不改测试。

- 落地纪律：单项收益 <5% 不落默认值，结论写进注释与经验总结；两项同时有效时再跑一次组合验证。

## 七、实施中的新坑（计划外发现）

1. **buildSrc 任何改动（连注释）都会触发下次构建的 buildSrc 重编链**：run6/run8 两次实测，代价约 +2 分钟（buildSrc 13 任务重编 + 主构建 classpath 变化连带 prepareSandbox 等 11 个任务重跑）。构建脚本的「顺手改注释」应与生产代码改动一样按「会变冷」预期安排时序，不要夹在计时实验中间。
2. 配置缓存对配置期**目录列举**（`listFiles`）做输入追踪——目录内文件变化即触发配置期重算。这既是「权重每轮生效」的机制，也意味着扫大目录的配置期写法有隐性重算代价，本项目此处规模（几百个 XML 头部 8 行）可忽略。
