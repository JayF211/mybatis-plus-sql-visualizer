# 开发计划

> 本文档是 **MyBatis-Plus SQL Visualizer** 的分阶段开发计划，任务编号（`T-xx`）稳定，供后续开发跟进与验收。
> 配套文档：[项目介绍](../项目介绍.md)、[功能概览](../需求文档/20260812-1058-MP-SQL可视化-需求文档.md)（功能编号 `F-xx` 在本计划中被引用）、[MPJ 用法收集与兼容性测试清单](../MPJ用法收集与兼容性测试清单.md)（模式编号 `P-xx`/构造编号 `C-xx` 在 M7 中被引用）。
> 当前项目基线：Kotlin 2.3.20 + IntelliJ Platform Gradle Plugin 2.18.1 + IDEA 2025.3.5，基础包 `cn.song.mybatisplus.visualizer`，v1.0.0（M0~M6）已交付。

## 1. 目标与原则

- **目标**：交付一个稳定、可发布到 JetBrains Marketplace 的 MP SQL 可视化插件；首个可用版本 v0.1 覆盖"查询类"闭环，v1.0 覆盖 CRUD + 联表 + 配置。
- **原则**：
  1. **核心先行**：转换引擎（纯逻辑）先于 UI 完成，保证可单测。
  2. **PSI 解析为主**：不依赖目标项目 classpath 动态加载 MyBatis-Plus，通过解析源码调用链 + 实体注解生成 SQL；若后续需精确对齐 MPJ 行为，再评估引入 MPJ 依赖做对照测试（见风险 R2）。
  3. **每里程碑可验收**：每个里程碑结束都有可运行的产物与通过的命令。
  4. **增量演进**：一个 Wrapper 类型跑通全链路后，再横向扩展其他类型。

### M7 MPJ 真实语料兼容（4~5 天，v1.1）

**目标**：以《MPJ 用法收集与兼容性测试清单》为验收语料，**消除现有 MPJ 兼容缺口，使清单中 P01~P20 全部 20 个模式、C1~C6 全部构造形式可正确转出 SQL**。配套完成「清单模式 → 支持状态矩阵」并回写清单 6.3 待补充项。

**现状差距分析（对照清单逐项比对代码结论）**：

| 清单模式 | 当前插件现状 | 差距 |
|----------|--------------|------|
| P01/P02/P04 `selectAs(Entity::getX, VO::getY)` | 仅支持第二参为字符串别名（`MpjLambdaConverter.parseSelectAs` 取 `SqlValue.Literal.unquoted`） | 方法引用别名解析缺失，**该列被丢弃** |
| P01/P02 `selectAll(Class)` | `QueryWrapperParser` 无 `selectAll` 分支 | 未识别 |
| P11 `selectAs("alias.col", VO::getY)` | 同上 | 字符串列 + 方法引用别名未识别 |
| P06/P07 `selectCollection`（含子映射 `id/result/collection` 三层嵌套） | 无对应模型与解析 | 全部缺失 |
| P08 `selectAssociation` | 无 | 缺失 |
| P09 `selectFunc`（`%s`/`{0}` 占位、`func.accept/values`） | 无 | 缺失 |
| P18 `selectMax` / `selectCount` | 无 | 缺失 |
| P05 `distinct` | `SelectStatement` 无 distinct 字段 | 缺失 |
| C4/P11 表别名构造 `new MPJLambdaWrapper<>(Class, "alias")` | `WrapperLocator` 仅解析泛型实体；`MpjLambdaConverter` 主表别名**固定 `t`** | 构造第二参（表别名）未解析 |
| P11 四参 join `leftJoin(Class, "alias", col1, col2)` | `parseJoin` 仅支持 `OnConditionArg`（`on(col1,col2)` 两参调用） | 四参重载未支持，on 条件与别名丢失 |
| P13 lambda ON `leftJoin(Class, on -> on.eq(...))` | `ArgResolver` 将 lambda 解析为 `NestedArg`，`parseJoin` 忽略 | 生成**无 ON 的 JOIN**（语义错误） |
| P11 `orderByAsc("alias", col)` | `orderItems` 仅取 `ColumnArg` | 字符串别名排序未支持 |
| P02 布尔条件重载 `eq(boolean, col, val)` | `QueryWrapperParser.simple` 取 arg0 为列 → 布尔实参解析失败 | 三参重载未支持，**条件被静默丢弃** |

## 7. 跟进说明

- 每个任务完成时：更新本文件对应行状态（`[ ]` → `[x]`）+ 在 CHANGELOG 记录。
- 每里程碑结束：跑验收命令并截图留存（README/验收脚本）。
- **增量验证约定（M13 起，解决全量 `clean test + verifyPlugin` 过慢问题）**：
  - **日常迭代**：只跑**定向增量**——`./gradlew test --tests "*XxxTest"`（受影响测试类），**不加 `clean`、不加 `--no-build-cache`**（复用增量编译与已编译产物），反馈秒级~1 分钟；M13 实测：定向 3 类 50s、全量增量 41s（165 用例全绿）。
  - **里程碑验收**：增量全量 `./gradlew test` 通过即视为回归绿；发布前最终确认才跑 `./gradlew clean test --no-build-cache` + `./gradlew verifyPlugin buildPlugin`（该组合数分钟级，日常迭代不要跑）。
  - **慢的根因（M13 分析）**：① `clean` 触发对整个 IDEA 平台 classpath（数百 MB jar + bundled 插件）的全量 Kotlin 重编译；② `--no-build-cache` 关闭构建缓存（规避"缓存恢复旧编译产物 → NoSuchMethodError"，见 CHANGELOG 持续记录）；③ 15 个 `BasePlatformTestCase`（LightPlatform）测试类每类启动 IDE 平台 fixture，默认单 fork 串行；④ `verifyPlugin` 依赖 `buildPlugin` 打包链（打 zip、复制依赖、校验 plugin.xml）。
  - **可选优化**（如仍嫌慢）：`gradle.properties` 加 `org.gradle.parallel=true`；test task 配置 `maxHeapSize("2g")`（LightPlatform 测试内存偏小会频繁 GC 拖慢）。
