## 一、背景与依据（锚点核实已完成，缺口实锤）

本计划立案前已完成锚点核实（2026-09-24，对 master `e85916e` 实测），与 O-60「核实后头号风险证伪为已覆盖」不同，本任务**缺口确认存在**：

### 1.1 核实事实

| # | 事实 | 证据 |
|---|------|------|
| 1 | 切分器括号深度只认 ASCII：`c == '('` 抬深度、`c == ')'` 降深度（钳 0） | `SqlStatementSplitter.kt:230-241` |
| 2 | 全角 `（`/`）` 不命中任何括号分支，落入普通字符处理，**不参与 `parenDepth`** | 同上（U+FF08/09 非 `isLetterOrDigit`，走 else 词终结分支） |
| 3 | `parenDepth` 全仓仅此一处（三套切分已收敛为单一状态机），一处修复全覆盖 | 全仓 grep `parenDepth` 仅命中 `SqlStatementSplitter.kt` |
| 4 | 字符串态安全：`inSingle`/`inDouble` 是主循环 when 链**最前两支**（:150~171），字符串内字符（含全角括号）到不了括号分支 | `:150-171`（已核实，非推演） |
| 5 | `;` 切分点重置 `caseDepth` 但**不重置 `parenDepth`**（正常流程下切分只发生在 depth==0，故无需重置；深度泄漏只可能来自括号失配） | `:214-228` |

### 1.2 缺陷推演（两个混对形态，均为代码走查推演、实施首步实测钉住）

**形态 A（`（…)` 混对，误切）**：`INSERT INTO t VALUES （1, 2; 3)`
- `（` 不抬深度 → `;` 在 depth 0 被**误切**，一条坏语句变两条坏片段（`VALUES （1, 2` / `3)`），报错拆散在两条上，可诊断性变差。

**形态 B（`(…）` 混对，吞并——主危害）**：`SELECT * FROM t WHERE id IN (1; 2）` 后随 `; SELECT 3; UPDATE …`
- ASCII `(` 抬深度至 1 后，闭合符是全角 `）` 不被认 → `parenDepth` 泄漏为正且**永不归零**（`;` 切分点要求 depth==0）→ **后续整段脚本被吞并成一条语句**送执行/确认流。与 O-47 治理的「批次吞并」同族危害，且一个坏字符的放大面是「其后全部内容」。

**无危害对照（纯全角对 `（…）`）**：深度恒 0，`;` 正常切分，切分边界与无括号一致——每段都是坏 SQL 但边界正确。**修复不得改变此形态的段数**（防过度修复的正对照）。

### 1.3 危害论证前提（决定优先级 P2 的依据）

全角括号出现在 SQL 里 ⇒ 该 SQL 本身不可执行（主流数据库词法拒绝 U+FF08/09；七方言逐一举证未做，见待验证前提 2）。本任务因此**不是**让坏 SQL 变可执行，而是「坏输入的可诊断性」修复：形态 B 把「一条坏语句」放大成「其后全部语句不可执行」，修复后退化回「一条坏语句」。这与 DBX #81 的编辑器补全场景动机不同（他们保的是输入中的编辑辅助），落地形态同形（深度栈双匹配、不改写字节）。

### 1.4 消费方与既有测试

- 消费方（与 O-60 计划 §1.4 同表，无新增）：`log/LogToSqlPanel.kt`（逐条执行）、`execute/SqlTypeClassifier.kt`（逐条分类→免确认门）、`reverse/SqlToJavaConverter.kt`（批量转换）、`mcp/SqlVisualizerCheckSqlTool.kt`（语句数+分类）。

## 二、目标与非目标

**目标**：全角 `（`(U+FF08) / `）`(U+FF09) 与 ASCII `(`/`)` **同栈计数**——形态 B 吞并消除（退化为一条坏语句）、形态 A 误切消除；纯全角对照形态段数不变；ASCII 既有语义逐字节不变（回归门）。

**非目标**：不做全角→半角规范化改写（产物必须保留原字符，让数据库报错指到用户写错的原位——切分器的逐字节契约）；不做全角分号 `；`(U+FF1B) 语句边界（挂 D1 决策）；不做其他全角标点（全角逗号/引号等——引号形态全角 `‘’“”` 不进字符串态判定，登记不做：把全角引号当字符串定界是语义扩张，坏输入放大面小）；不改渲染链与执行链语义。
