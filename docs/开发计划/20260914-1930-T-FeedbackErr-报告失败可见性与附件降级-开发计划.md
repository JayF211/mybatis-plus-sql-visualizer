# T-FeedbackErr：报告提交失败不可见与附件失败连坐 开发计划

> **创建日期**：2026-09-14
> **分支**：master（当前 HEAD `82bf32c`）
> **优先级**：P0（用户在手边报错时提交失败，**唯一可见反馈只有一个 toast**，原因与内容双双丢失；官网需求池其实收得到，白白流失线索）
> **来源**：用户真机（日常 IDEA，非 runIde 沙盒）反馈——「我通过 idea 上报问题失败了，并且没有弹框反馈，只有 idea 的通知不太够」，通知内容为 `Server returned HTTP response code: 400 for URL: https://sql-visualizer.jvtools.cn/api/v1/feedback/posts`

---

## 一、现场与结论摘要

用户点「报告到 SQL Visualizer 需求池」提交后，看到的是平台通道级异常文本 `Server returned HTTP response code: 400 for URL: …`——**没有服务端给出的具体原因，也没有可重试的对话框**。用户以为功能坏了，实际是服务端明确拒绝（400）而插件把拒绝理由丢了。

根因两条，都在插件侧（服务端按设计返回中文 `message`）：

1. **错误响应正文被丢弃**：`HttpRequestsSender` 走 `HttpRequests.request(url).throwStatusCodeException(true).connect { it.readString() }`，非 2xx 时平台抛出的是 `Server returned HTTP response code: 400 for URL: …`，而服务端写在**响应体**里的 `{"code":400,"message":"标题长度需在 5-200 字符之间"}` 从未被读取（`readString()` 只认成功流）。
2. **结果落点只有 toast，且对话框先关了**：`ErrorReportDialog.doOKAction()` 先 `super.doOKAction()` 关窗，再调 `onSubmit(submission)`；提交结果只经 `FeedbackReporting.notifyResult` 发通知。失败 = 窗口已关 + 一个 toast = 用户「没有弹框反馈」，改内容重试也无门。

外加一条连坐缺陷：**附件上传失败会连坐整帖**——`FeedbackApi.submit` 在附件分支直接 `return SubmitResult.Failure(...)`，用户填好的标题/描述连同堆栈一起丢失（线上 `fb_attachments` 至今 0 行，此路径从未成功过，属未被覆盖的高风险分支）。

线上库直查（`sql-visualizer-admin` 仓库，`CLOUDFLARE_API_TOKEN` + `wrangler d1 execute --remote`）：

| 证据 | 结论 |
|------|------|
| `fb_posts` 最新 id=22（`FR-0021`），无本次失败记录；唯一 `source=ide` 的帖子是 `FR-0017`（2026-09-11 07:20，插件 `2026.9.11-dev`） | 失败提交**根本没入库**，服务端在写库前拒绝 |
| `sys_alert_events` 中本机 IP 仅有一条 `submit_flood`（11:11:43，即本次排查的探针所触发） | 用户那次失败**不是限流**（限流也会入库告警） |
| 前一日 11:03:36 有 `login_success` 审计（用户本人） | 官网站点当下正常，非全站故障 |
| 提交探针：`pluginVersion=2026.9.14` → 200；`ideVersion="IntelliJ IDEA 2026.2.1 Ultimate"`（35 字符）→ 200 | **「版本字段形状/长度被 400」假设被证伪**——服务端 `validateVersionValue` 只拦 >32 字符与含 \uFFFD/控制字符的值，用户所见 400 另有出处（客户端校验只挡 title/description，其余字段的可读原因当时不可见） |
| `fb_attachments` 全表 0 行 | 堆栈附件上传链路自上线以来从未成功落库 |

服务端 400 分支（`src/modules/feedback/routes.ts` POST `/posts`）明确且可读：UTF-8 非法字节、非 JSON、标题 5~200、描述 ≥10、类型 1~4、邮箱格式、附件数/字段完整性、版本字段长度与控制字符——**每一条都带中文说明**。也就是说：**只要把这句 message 带回插件，用户当场就知道该改什么**。这就是本次修复的主线。

## 三、技术方案

### 3.1 错误正文回传（服务端原因优先）

`HttpRequestsSender` 两条链路（JSON / multipart）改为手写 POST，自己判状态码、自己读 errorStream：

- 请求方式与 multipart 同款手法——`RequestBuilder.tuner` 内设 `HttpURLConnection.requestMethod = "POST"`、`doOutput = true`（该手法在生产 multipart 路径上已验证过；`RequestBuilder.post(String)` 是 2023.3+ 新名，243 基线不依赖）。
- 连接成功后取 `request.connection as HttpURLConnection`，`responseCode` 非 2xx 时读 `errorStream`（成功流 `inputStream` 在错误码下不可用，直接读会抛）。
- 非 2xx 抛新类型 `HttpFailure(status, body)`（`IOException` 子类，`message` 保留平台同款 `Server returned HTTP response code: N for URL …` 形态并附正文摘要，便于排查）。
- `FeedbackApi.describeHttpFailure(error)`（纯函数）：`HttpFailure.body` 里的 `message` 优先 → `cause.message` → `message` → null。**服务端人写的文案永远压过通道文案。**

### 3.2 附件失败降级（不连坐整帖）

`FeedbackApi.submit` 返回类型由 `SubmitResult` 升格为 `SubmissionOutcome(result, warning)`：

- 附件上传失败 → 记 `warning`（取服务端原因），**丢掉附件继续提交正文**；
- 正文提交失败仍是 `SubmitResult.Failure`；
- 调用方对 `warning` 单独提示（对话框状态行 + 一条 WARNING toast）。

理由：用户填的标题/描述是主诉求，一个 txt 附件上传失败没道理把主诉求一起吞掉；附件可事后补。

### 3.3 提交状态机落进对话框（「没有弹框反馈」的正解）

`ErrorReportDialog` 从「确认即关窗」改为「结果驱动关窗」：

- 构造回调签名 `onSubmit: (Submission, (SubmissionOutcome) -> Unit) -> Unit`——调用方**必须**在提交结束（成功或失败）时回调结果；
- `doOKAction()` 不再 `super.doOKAction()`：校验不过仍交框架弹错；通过则 `beginSubmitting()` 后触发回调；
- `beginSubmitting()`：按钮文案转「提交中…」并禁用（`isOKActionEnabled=false`，`isSubmitting` 防重入），状态行显示「正在提交到需求池…」；
- `finishSubmitting(outcome)`：**成功** → `close(OK_EXIT_CODE)`（通知路径不变：FR 编号 + 查看详情）；**失败** → 窗口保留，按钮恢复「提交」，状态行红字显示「提交失败：{服务端原因}」+ 一行「可修改内容后重试，或点下方『转浏览器填写』」，附件降级时追加一行说明；
- headless / 无 peer（异常路径、单测）时按钮与关窗 API 全部 `runCatching` 跳过，状态行赋值照常——保证 `beginSubmitting/finishSubmitting` 可单测；
- 状态行常驻最底部（`fullRow(statusLabel)`，weighty=0，不参与纵向伸缩，不影响 T-FeedbackDlg2 的高度补偿逻辑）。

### 3.4 通知层

`FeedbackReporting`：`submitInBackground(submission, onProgress, onResult)`（进度可选）；新增 `notifyAttachmentWarning`（WARNING）与 `notifyOutcome`（warning + 结果）。错误通道（`IdeErrorReportSubmitter`）流程：先回对话框（失败留窗可改可重试），再 `consumer.consume(reportInfo(result))` 与通知——平台 Internal Errors 侧语义不变。

## 六、风险与边界

- **改动落在 HTTP 层**：`HttpRequestsSender` 由平台封装改手写 POST。已复用的手法（tuner 设 method/body）在生产 multipart 路径上跑过；单测不覆盖网络层，靠真机与线上灰度确认。
- **未证伪的疑点**：附件上传链路从未成功过（`fb_attachments` 0 行），本次只做了「失败不再连坐」的兜底，**并未证明上传本身可用**；真机走查需专门验证一次带附件的提交是否能落 `fb_attachments`。另外探针过程中观察到服务端计数异常（连续 200 后同连接上起 429），怀疑 keep-alive 复用与请求体写出存在细微问题，一并列入真机排查项。
- **请求体本身若是 400 根因**（如用户描述里含异常控制字符、附件元数据不齐），本次修复不改变结果**但让原因可见**——这正是本次目标；后续若真机复现，按状态行文案定位。
- **限流文案**：429 由限流中间件在 handler 之前返回，正文「请求过于频繁，请稍后再试」现在会原样进状态行，无额外处理。

## 八、追加：批量报告与限流规避（T-FeedbackBatch，同日用户追加定案）

> 用户原话：「目前通过 idea 报告问题，需要考虑不能被轻易限流，因为有时候用户报错很多，选择了全部报告，要么就把信息合到一起，以免出现 429」。
> 结论：两条一起做——先把信息合并成一条帖子，超出一轮额度的部分再错峰补发；单纯合并会丢现场，单纯排队会让首条帖子失焦。

### 8.1 约束事实

- 服务端 `POST /api/v1/feedback/posts` 限流 **5 次/小时/IP**（`src/middleware/rate-limit.ts` 的 `RATE_LIMITS`，
  在 handler 之前计数、超限直接 429 并落 `submit_flood` 告警）——这是防御规则，插件侧只能绕开而不是改掉。
- 平台 Internal Errors 对话框支持**多选**错误，`ErrorReportSubmitter.submit(events, …)` 拿到的是数组：
  旧实现只取 `events.firstOrNull()`，用户「选择了全部报告」时其余条目被静默丢弃（既没报上去，用户也不知道）。

### 8.2 分流策略

| 条目数 n | 行为 | 服务端请求数 |
|---------|------|-------------|
| 1 | 原样单帖（堆栈 txt 附件） | ≤2（附件 + 帖子） |
| 2 ~ 5（`BATCH_MERGE_MAX`） | **合并成一条帖子**：标题 `首条摘要（等 N 条异常）`、描述逐条 `#N [类] 消息` 清单、附件换多节全文（`----- #N -----`） | ≤2 |
| ≥ 6 | 首发仍是**合并帖**（附件含全部条目），第 2..n 条各成独立帖子交 [PendingReportScheduler] **每 12 分钟补发一条** | ≤2 + (n-1) 错峰 |

12 分钟取自服务端窗口 3600s ÷ 5 次 = 720s 再留余量——同一出口 IP 往往还有浏览器/其他会话共用这个桶。

### 8.3 实现

- `ErrorReportComposer`：`BatchEntry`、`buildBatchTitle`（≤200，含「等 N 条异常」）、
  `buildBatchDescription`（条目清单 + 超 20 条截断注明 + 保留用户补充）、
  `buildStackAttachment(stacks)` 多节重载（`异常条数: N`，总量仍 ≤60_000）、`shouldMerge` 阈值。
- `BatchSubmitter`：`BatchItem`（条目级 `attachStack` 勾选）、`composeFirstSubmission`（首发载荷重写）、
  `followUpSubmissions`（补发列表）、`submissionFor`（条目 → 独立帖子）。
- `PendingReportScheduler`（APP 级 service，守护线程单线程池）：首发**成功后**才排队；
  逐条 12 分钟发出、失败不重试；内存队列不落盘，IDE 退出即丢弃（要补发得用户再点一次）。
- `ErrorReportDialog`：错误形态新增「其他 N 条异常」分节（逐条复选框、默认全勾、取消即不报该条），
  提交前经 `composeSubmission` 纯函数重写标题/描述/附件；手动形态不受影响。
- `IdeErrorReportSubmitter`：`events` 全部组装为批次条目（`batchItemsOf`）随对话框展示。
- 新键 2×2：`error.report.dialog.batchHeader` / `error.report.dialog.batchItem.tip`。

### 8.4 边界与取舍

- 补发内容早已在对话框里展示并由用户确认，不是静默替用户发东西；但**关窗后仍在进行**——有意如此（否则用户白等），
  队列不跨进程持久化，避免变成「重启后后台偷偷发」。
- 首发失败（额度已满/断网）不排补发：首发都失败时排队只会连环失败；此时状态行已给服务端原因 + 转浏览器兜底。
- 合并附件只用一个 txt（多节），不占服务端「每帖 ≤3 附件」配额，也不碰 ≤5MB 上限（总量截断 60_000 字符）。

  （`Unclosed comment`）——KDoc 里别让 `/` 紧邻 `*`。

## 九、真机第二轮（2026-09-14 晚，用户日常 IDEA 实测截图反馈）

### 9.1 现场

用户在手动形态提交（标题/描述随意输入、勾选堆栈并粘贴占位内容），对话框同屏出现两行矛盾文案：
「提交失败：响应解析失败：java.lang.IllegalStateException: Expected BEGIN_OBJECT but was STRING
at line 1 column 1 path $（Gson 排障链接）」+「帖子已提交，但异常堆栈附件未能上传：Expected BEGIN_…」，
且整个对话框被撑到 ~1900px 宽。

### 9.2 根因（字节码级实锤）

- **假失败真相**：线上 D1 实查 **FR-0023（`ddesdds忒`，source=ide，id=23）已完整入库**——请求与服务端处理全部成功，MAX(id) 编号同步验证生效；「失败」是客户端读响应的锅。
- **gzip 链**：`javap` 反编译 app-client.jar `HttpRequests$RequestBuilderImpl`——构造器 `iconst_1 → putfield myGzip`（**gzip 默认 true**），connect 时 `if (myGzip) setRequestProperty("Accept-Encoding", "gzip")`；CF 实测对带该头的响应返回 `Content-Encoding: gzip`。平台自己的 `readString()` 会解压，而 T-FeedbackErr 手写的 `readBody` 直接把原始字节按 UTF-8 解码——gzip 二进制乱码在 Gson lenient 模式下即「was STRING at line 1 column 1」。util-8.jar 全量扫描佐证：Accept-Encoding 字面量只存在于 HttpRequests.class。
- **窗口过宽**：状态行是 `JBLabel`（不换行），Gson 英文异常 + 排障链接的单行渲染把 GridBag 整行（进而整个对话框）撑到 ~1900px。
- **文案矛盾**：状态行只在失败时出现，而附件降级行写死「帖子已提交，但…」——失败现场自相矛盾；`notifyOutcome` 在失败时也会发「反馈已提交（未附堆栈）」toast，同病。

### 9.3 修复

1. `HttpRequestsSender.readBody` 按 `Content-Encoding: gzip` 用 `GZIPInputStream` 解压；tuner 显式设 `Accept-Encoding: gzip`（与平台默认值一致，协商与解压配套、不依赖平台隐式行为）。
2. `nonJsonHint` 纯函数：正文不以 `{` 开头（HTML 拦截页/网关错误页/空响应）→ 可读归类并截取正文片段；`parsePostResponse`/`parseUploadResponse`/`describeHttpFailure`（附 HTTP 状态）全部接入，Gson 英文原文不再透给用户。
3. `HttpFailure` 记录 `status`；`describeHttpFailure` 归类文案带 `（HTTP 403）` 形态。
4. 状态行 `JBLabel` → `JBTextArea(2,40)`（lineWrap + wrapStyleWord + 透明背景），preferred 宽 40 列封顶；新增 `buildStatusRow` 纯函数（文本区居中 + 按钮居东）。
