## 一、结论先行

**不建议现在接入 MyBatis-Flex。** 不满足立项门槛「FlexConverter 增量维护 < 现有 MP 系 15%」——两段式条件 API 与 MP 单段式**结构性不同**，条件提取器无法复用，实际边际成本接近新做一个并列解析器（估算为 MP 系工作量的 60~80%）。另有一个必须先解决的**同名锚点冲突**问题。重启条件见第五节。

## 二、Flex API 结构（jar 反编译事实）

`com.mybatisflex.core.query.QueryWrapper`（extends BaseQueryWrapper\<QueryWrapper\>）核心 API：

| 环节 | Flex 形态 | 反编译依据 |
|------|-----------|-----------|
| 工厂 | `QueryWrapper.create()`（5 个重载）/ `new QueryWrapper<>()` | `public static QueryWrapper create()` |
| 列选择 | `select(QueryColumn... / LambdaGetter<T>... / String...)` | QueryWrapper.select 重载 6 个 |
| 表 | `from(Class<?>... / String... / QueryTable...)` | QueryWrapper.from 重载 4 个 |
| **条件** | **两段式**：`where(QueryColumn)` 返回 `QueryConditionBuilder`，谓词在 Builder 上（`eq(Object)` / `eq(Object, boolean)` / `eq(LambdaGetter)` 等）；或 `where(QueryCondition)`——条件由 `QueryColumn.eq(Object)` 预先构造 | QueryConditionBuilder 实现 `Conditional<Wrapper>`，谓词 4 类重载；QueryColumn 同样全量谓词返回 QueryCondition |
| 连接词 | `and(...)` / `or(...)` 与 where 同构（也走 Builder/Condition 双形态） | QueryWrapper.and/or 重载 |
| 布尔控制 | 谓词尾参 `boolean` / `BooleanSupplier` / `Predicate<T>`（**值在左，条件在右**） | Builder.eq 4 重载 |
| JOIN | `leftJoin(QueryTable/Class/Wrapper)` 返回 `Joiner<Q>`（第三段式） | QueryWrapper.leftJoin 重载 6 个 |

典型写法：`QueryWrapper.create().where(USER.AGE).ge(18).and(USER.NAME).like("x")` 或 `USER.AGE.ge(18).and(USER.NAME.like("x"))` 挂 `where(...)`。

## 三、与本项目解析器的结构性差异

本项目 Wrapper 解析链（`psi/WrapperAnchorDetector.kt` + `converter/QueryWrapperParser.kt` 等 12 个 converter）建立在两条设计约束上：

1. **零 resolve 纯语法判定**：锚点按类型名/工厂方法名 O(1) 判定，条件提取直接从「谓词调用」的参数表达式拿列与值——`eq(User::getName, "x")` 一次调用携带全部信息。
2. **谓词单段式模型**：`WrapperArg/Condition` 模型假定「方法名=谓词，参数表=(列, 值[, 布尔条件])」。

Flex 的三处不兼容：

| 差异点 | MP（现支持） | Flex 1.11.8 | 解析器影响 |
|--------|-------------|-------------|-----------|
| 条件携带 | 谓词调用内 `(列, 值)` | 列在 `where()`/QueryColumn 上，谓词只带值；跨**两个调用**的信息合并 | 需要**跨调用状态机**（where 记列 → 下个 eq 消费），现有单调用提取模型整体不适用 |
| 列来源 | Lambda（方法引用名）/ 字符串，纯语法可解 | 静态字段引用 `USER.NAME`（QueryColumn 常量）——列名在**字段初始化表达式**里，语法可解但字段名≠列名，准确列名需 resolve 字段定义（TableDef 生成类） | 精确列名解析破坏零 resolve 红线；降级方案（用字段名）输出有偏差 |
| 布尔重载 | `eq(boolean, col, val)`（条件在首参） | `eq(value, boolean)`（条件在尾参） | 参数序不同，提取规则需独立维护 |

另有 **同名类冲突**：Flex 与 MP 的主类都叫 `QueryWrapper`。`WrapperAnchorDetector` 场景 A/B 按类型名判定——Flex 用户的 `new QueryWrapper<X>()` 会命中现有锚点并被 `QueryWrapperConverter` 按 MP 语义解析出**错误 SQL**。要区分两者必须引入 import/类型 resolve，直接触碰性能红线（M10 开发计划 §2.4 硬性约束）。

## 四、成本评估

- **可复用部分**：方言渲染、预览面板、日志捕获、执行链——全部可复用（这是好消息，占产品体验的大头）。
- **不可复用部分**：锚点判定（需 resolve 或限定工厂形态）、条件提取（新状态机）、Joiner 三段式（新 parser）、WrapperArg/Condition 模型适配（新模型或加 Flex 分支）。
- **工作量估计**：与 MP 系 12 个 converter 的总量同量级（MP 系积累了 20+ 里程碑的迭代），即边际成本 ~60-80%，远超 15% 门槛。
- **生态对照**：Marketplace 已有 Mybatis-Flex-Helper（id 22165，1.8 万下载，4.32 分）占位 Flex SQL 预览；Flex 用户基数（GitHub star 量级远小于 MP）叠加已有人占位，预期获客有限。

## 五、结论与重启条件

**暂缓。** 理由：结构性改造成本高 + 同名锚点冲突触碰性能红线 + 生态已有占位 + 与「守住 MP 主战场」的窗口期策略冲突（M37.0~M37.4 资源应集中于独家壁垒）。

满足以下任一条件可重启调研：

1. 用户侧出现明确需求信号（本插件 issue/Gitee 反馈中 Flex 支持请求 ≥ 3 例）；
2. Flex 生态明显增长（Mybatis-Flex-Helper 下载量年增 > 5 万，或 Flex 官方路线图出现破坏性变更导致其 Helper 断更）;
3. 项目决定引入轻量 Flex 支持**只做锚点提示**——检测到 `QueryWrapper.create()`（MP 没有的工厂方法名，零 resolve 可判）时提示「检测到 MyBatis-Flex 链，本插件暂不支持 Flex 解析」，避免同名类误解析出错误 SQL。此低成本兜底建议作为独立小项评估（半天工作量）。
