## 1. M30：SQL 诊断平台核心（P0）

### 1.1 包含项

| # | 项名 | 对应子计划 | 核心依赖 | 现状 |
|---|------|-----------|----------|:----:|
| F-1 | JOIN 关系可视化图 | `20260822-1601-F1-JOIN可视化图-开发计划.md` | PlantUML 8059（MVP）/ Mermaid+JCEF（v2） | ✅ 已落地（`sql/JoinDiagramGenerator.kt` + `ui/diagram/`） |
| F-2 | SQL 性能分析建议 | `20260822-1602-F2-SQL性能分析-开发计划.md` | JSqlParser 5.3 | ✅ 已落地（`sql/SqlPerfAnalyzer.kt` + `sql/perf/` 三批 20 条规则） |
| F-3 | Wrapper 链复杂度评分 | `20260822-1603-F3-复杂度评分-开发计划.md` | JSqlParser 5.3（与 F-2 共享） | ✅ 已落地（`sql/ComplexityScorer.kt`，387 行完整实现） |

### 1.2 优先级判定

**P0 依据**：这三项构成从"SQL 预览工具"到"SQL 诊断平台"的质变，是竞品完全空白的增量市场。

- **F-2 SQL 性能分析**：用户写完 Wrapper 链后立即获得性能反馈，不需要连接数据库。JSqlParser 5.3（1.26MB 零依赖）可解析 MySQL 方言，20+ 静态规则可实施。
- **F-3 复杂度评分**：sql-visualizer 已验证需求，COMPLEXITY_WEIGHTS 矩阵可直接移植。与 F-2 共享 JSqlParser 依赖。
- **F-1 JOIN 可视化**：Web 端 sql-visualizer 用 ReactFlow 验证了需求，IDEA 内无同类产品。MVP 用 PlantUML（纯 Java 渲染，+5MB），v2 用 Mermaid+JCEF（+300KB，交互更佳）。

### 1.3 依赖与实施顺序

```
F-2 SQL 性能分析 ──┐
                   ├── 共享 JSqlParser 依赖 + SqlPerfAnalyzer 基础
F-3 复杂度评分 ────┘
                   
F-1 JOIN 可视化 ─── 独立，依赖 SelectStatement/JoinClause 模型（已有）
```

**推荐实施顺序**：F-2 → F-3 → F-1（F-2 产出基础设施，F-3 复用，F-1 独立）

三项互相独立，可并行。推荐：O-4（最快产出）→ O-1 → F-5（需 CompletionContributor 注册）

## 3. M32：拦截器模拟与 Kotlin（P1）

### 3.1 包含项

| # | 项名 | 对应子计划 | 核心依赖 | 现状 |
|---|------|-----------|----------|:----:|
| F-6 | 拦截器模拟增强 | `20260822-1607-F6-拦截器模拟增强-开发计划.md` | 无新依赖 | ✅ 已落地（`sql/interceptor/TenantLineEnhancer.kt` + `DataPermissionPlaceholder.kt` + `DynamicTableNameProcessor.kt`） |
| F-4 | Kotlin KtWrapper 支持 | `20260822-1608-F4-Kotlin支持-开发计划.md` | Kotlin PSI API | ✅ 已落地 MVP（`psi/KtWrapperDetector.kt`，基于方法名模式匹配的 O(n) 检测） |

### 3.2 优先级判定

**P1 依据**：真实项目几乎必用拦截器，不含拦截器的预览与运行时 SQL 差异大。Kotlin+MP 用户持续增长。

- **F-6 拦截器模拟**：
  - TenantLine：PluginSettings 已有 `injectTenantLine` + `tenantColumnName`，需完善到 INSERT 也追加 tenant_id 列
  - DynamicTableName：新增设置项允许用户指定表名映射规则（正则 → 替换）
  - DataPermission：运行时无法静态模拟，提供占位提示
  - BlockAttack：UPDATE/DELETE 无 WHERE 已有警示，加 BlockAttack 风格标记
- **F-4 Kotlin**：MP 的 `mybatis-plus-kotlin` 模块提供 `ktQuery()`/`ktUpdate()` 扩展函数，不是独立 KtQueryWrapper 类。需 Kotlin PSI 基础设施（KtCallExpression、KtLambdaArgument）。

### 3.3 依赖与实施顺序

两项独立。推荐：F-6（价值高，成本低）→ F-4（Kotlin PSI 工作量大）

### 5.2 全局约束

- **性能红线**：gutter 快速路径 O(1) 纯语法不 resolve（新增入口同样遵守）
- **测试先行**：每项遵循 fixture 先于实现 → 增量验证 → 全量验证
- **插件体积**：JSqlParser +1.26MB，PlantUML +5MB（MVP），Mermaid +300KB（v2）
- **兼容性**：所有新 API 需通过 verifyPlugin 三版本（243/253/262）
- **优雅降级**：新功能的近似实现不得抛异常，必须可读占位

## 6. 全局实施规范

### 6.1 测试先行
每项遵循既有惯例：fixture 先于实现 → 增量验证（定向测试）→ 全量验证（`./gradlew clean test --no-build-cache` 全绿 + `buildPlugin`）→ 提交 git。

### 6.2 并行测试铁律
跑任何 `./gradlew` 命令前，先 `python C:\Users\USER\.zcode\cli\parallel_tasks.py check`。

### 6.3 文档同步
每项完成后同步更新：README 功能特性、CHANGELOG、需求文档覆盖矩阵。

### 6.4 提交节奏
每个子计划独立提交，commit message 格式对齐既有约定（`feat:` / `fix:` / `docs:` 前缀）。
