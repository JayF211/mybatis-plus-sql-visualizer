## 二、根因分析

### 问题一：项目打开即自动监听（无运行控制台）

自动启动有三条路径，全部**只检查 `logAutoCaptureOnStart` 设置，不检查是否已有运行中的主控制台**：

1. `LogStartupCapture.execute()`（postStartupActivity，`src/main/kotlin/cn/song/mybatisplus/visualizer/log/LogStartupCapture.kt:26-28`）——设置开启 → `tryStartCapture` → `manager.startCapture()`；
2. `ProjectListenerRegistrar.registerIfNeeded()` 的 `projectOpened` 回调（`ProjectListenerRegistrar.kt:35-40`）——同上直接 `tryStartCapture`；
3. `ProjectListenerRegistrar.registerIfNeeded()` 的「已打开项目兜底遍历」（`ProjectListenerRegistrar.kt:46-51`）——注册时项目已打开（热加载等）→ 直接 `startCapture`。

这三条路径在项目打开时（无任何运行进程）就直接挂载监听，于是按钮显示「监听中」但实际无控制台可捕获——即使后续从未启动项目运行，也一直处于捕捉态。

对照：设置页 `PluginSettingsConfigurable.apply()`（`config/PluginSettingsConfigurable.kt:51-61`）已有正确模式——「关→开」时先查 `manager.hasConsoles()`，有运行控制台才 `startCapture`，无则跳过并打日志。

另注意：`SqlLogManager.startCapture()` 无控制台守卫（`SqlLogManager.kt:65-82`），它只做幂等与 attach 成功判断——attach 成功即置 capturing=true（`bridge.attach` 对缺失 console 的场景返回 true，仅当 execution API 不可用时才 false）。

### 问题二：关闭面板不触发 `contentRemoved`

现有实现靠 `ContentManagerListener.contentRemoved`（`SqlLogToolWindowFactory.kt:77-87`）。但关闭侧边栏面板（stripe 隐藏）时 content 并不移除——工具窗口只是隐藏，content 仍在，`contentRemoved` 不触发。旧 UI 关闭按钮可能走 content 移除；新 UI 折叠/隐藏则完全是 ToolWindow 可见性变化，与 content 生命周期无关。

因此「关闭面板即停止监听」需要监听的是 **ToolWindow 可见性**，而非 content 生命周期。平台提供 `com.intellij.openapi.wm.ex.ToolWindowManagerListener`（243 jar javap 实证，接口含多个 `stateChanged` 重载、`toolWindowShown` 等；`ToolWindow.isVisible()` 存在）。该主题经 `project.messageBus.connect()` 订阅，消息总线编程注册（plugin.xml 不支持 `<listener topic>`，见既有 pitfall 记录）。

### 问题三：日志倒序

`SqlLogEntryBuffer.addEntry` 用 `entries.addFirst(entry)`（`SqlLogEntryBuffer.kt:42`），越晚加入越靠前 = 最新在前；裁剪超限时 `removeLast()`（丢最旧）。`snapshot()` 原样 `toList()`。面板 `refreshList()` 按 snapshot 顺序填充 `DefaultListModel`（`SqlLogToolWindowFactory.kt:291-295`）——故列表显示为倒序。

改正序需翻转入队方向：`addEntry` → `addLast`（新条目追加到队尾）、超限裁剪 → `removeFirst()`（丢最旧）；`snapshot()` 仍 `toList()` 即得最早在前。去重检测 `isDuplicate` 用 `entries.firstOrNull` 扫全队（顺序无关，去重语义不变，仍丢弃窗口内重复的**后到者**）；去重/过滤/暂停语义不受影响。

## 三、方案设计

### 问题一：自动监听加「主运行控制台存在」守卫

统一在 `SqlLogManager.startCapture()` 内部加守卫最干净——三条启动路径（StartupCapture / projectOpened / 兜底遍历）以及未来的任何调用点自动获得正确行为，且手动点击「捕捉」不受影响（手动意图明确，无需控制台前置）。

方案：`startCapture()` 开头（`SqlLogManager.kt:66`，`if (capturing) return` 之后）增加：

```kotlin
// 自动启动路径守卫：项目尚无运行中的主控制台时不进入捕捉态
// （projectOpened / postStartupActivity 兜底遍历等调用点不区分自动/手动，
//  统一在此拦截——无控制台时挂载 filter 也无 SQL 可捕获，按钮显示「监听中」是假象）
if (!hasConsoles()) {
    LOG.info("startCapture: 无运行中的主控制台，跳过（捕获将等待项目启动运行）")
    return
}
```

注意：`hasConsoles()`（`SqlLogManager.kt:85-98`）当前语义是「任意 run 控制台 tab 存在」（含已终止进程残留 tab 与 HTTP 请求工具窗口）。对照业务期望「仅当项目实际开始运行」，应把守卫条件收紧为 `hasMainConsole()`（`SqlLogConsoleBridge` 已有：`getAllDescriptors → ConsoleViewImpl + ProcessHandler.isProcessTerminated/isProcessTerminating` 存活检查，`SqlLogConsoleBridge.kt:149-174`）。`hasMainConsole()` 未在桥外暴露——需在 `SqlLogManager` 增加转发方法 `hasMainConsole()`（可同时让 `hasConsoles()` 语义保持原样供设置页沿用）。

守卫放置优先在 `startCapture()` 门口（单一收敛点）；若担心手动场景也不该被拦（无控制台时手动点捕捉无意义但用户可能有预挂载诉求），可改为只在自动启动路径（LogStartupCapture/projectOpened/兜底遍历）加检查——实施时二选一，倾向收敛点方案（手动 `startCapture` 前 UI 已有「先跑项目」的心智，且 `onConsoleAppeared` 会在控制台出现时自动重启捕捉）。

补充：`onConsoleAppeared()`（`SqlLogManager.kt:134-139`）在「控制台出现 + 设置开启 + 未捕捉」时自动 `startCapture()`——该路径天然有控制台（触发者即控制台出现事件），不受守卫影响，正好构成「打开项目不监听 → 启动运行才监听」的完整闭环。

### 问题二：隐藏面板停止监听

新增成员变量 `toolWindow` 引用，并在 `createToolWindowContent` 中经 `project.messageBus.connect(content.disposer)` 订阅 `ToolWindowManagerListener`。关键点：

1. **平衡语义**：「关闭面板后自动停止监听」不应在**新建**窗口时误停（如 `log.setContentUiType`、隐藏后重显的中间态）；只在「可见 → 不可见」的转换沿上 stop。做法是记录上一个可见状态（init 时为 false），`stateChanged` 时读取 `toolWindow.isVisible()`：可见变不可见 → 按设置 stopCapture。
2. **消息总线注册**：`project.messageBus.connect(content.disposer)`——disposer 为 content 的 disposer，窗口关闭（真正移除）时连接自动断开，无需手动 unsubscribe。
3. **手动停止 vs 自动停止**：复用 `manager.stopCapture()` 本身（幂等，`capturing=false` 时直接返回），无需新增状态。
4. **不重复叠加**：保留现有 `contentRemoved` 监听作为「真正移除 content」的兜底（产生于某些平台把关闭实现为移除），新监听只补「隐藏」场景——两者都调 `stopCapture()`，幂等无冲突。

监听方法选择（243 jar javap 实证）：接口含 3 参 `stateChanged(ToolWindowManager, ToolWindow, ToolWindowManagerEventType)`，多个缺省实参便捷变体。最稳写法：

```kotlin
val manager = project.getService(SqlLogManager::class.java)
var wasVisible = false
project.messageBus.connect(content.disposer).subscribe(
    ToolWindowManagerListener.TOPIC,
    object : ToolWindowManagerListener {
        override fun stateChanged(toolWindowManager: ToolWindowManager, toolWindow: ToolWindow, type: ToolWindowManagerListener.ToolWindowManagerEventType) {
            if (toolWindow != tw) return
            val visible = tw.isVisible
            if (wasVisible && !visible) {
                val settings = PluginSettings.getInstance()
                if (settings.state.logStopOnToolWindowClose && manager.capturing) {
                    manager.stopCapture()
                    LOG.info("ToolWindow 隐藏：已停止捕捉（project=${project.name}, type=$type）")
                }
            }
            wasVisible = visible
        }
    },
)
```

由于接口方法签名较宽（多个 stateChanged 重载且非默认实现，实现类须覆写平台会调用的那个），实施前需在目标运行时验证实际回调签名；若不稳，退路是 4 支路分别覆写并且各自执行同一可见性比较逻辑。`toolWindow.isVisible` 为接口公开方法（243 javap 实证）。

### 问题三：日志正序

`SqlLogEntryBuffer`（`src/main/kotlin/cn/song/mybatisplus/visualizer/log/SqlLogEntryBuffer.kt`）：

| 行 | 现状 | 改后 | 说明 |
|----|------|------|------|
| 42 | `entries.addFirst(entry)` | `entries.addLast(entry)` | 新条目追加到队尾 |
| 43 | `while (size > max) removeLast()` | `while (size > max) removeFirst()` | 超限裁掉最旧（队头） |
| 57 | `/** 最新在前的快照。 */` | `/** 最早在前的快照（正序）。 */` | 注释同步 |
| 36-37 | KDoc（最新在前） | 改为（最早在前，正序） | 类头/方法 KDoc |
| 7-9 | 类 KDoc（最新在前） | 改为（最早在前，正序） | 类头 KDoc |

测试 `SqlLogEntryBufferTest.kt` 三处断言方向翻转：

- `新增条目最新在前`（25-32）→ 改名 `新增条目最早在前`，断言 `snap[0]=="SELECT 1"`、`snap[1]=="SELECT 2"`；
- `超过上限裁掉最旧`（34-44）→ 断言 `snap[0]=="SELECT 2"`（原 SELECT 1 最旧被裁），余两条按序 `SELECT 2, SELECT 3, SELECT 4` 正序；
- `清空与删除单条`（55-65）`removeEntry(e1)` 后应为 `listOf("SELECT 2")`——不受顺序影响（e1 是 SELECT 1，删后剩 SELECT 2，单元素）。

UI 层（`SqlLogToolWindowFactory.kt:291-295`）按 snapshot 顺序填 `DefaultListModel`，无需改动即得正序。首条出现时自动打开窗口的 `maybeAutoOpenWindow`（`SqlLogManager.kt:176-187`）只判空，不受影响。
