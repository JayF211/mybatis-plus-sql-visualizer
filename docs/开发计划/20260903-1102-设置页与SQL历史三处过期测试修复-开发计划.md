## 问题分析

### 失败 1：PluginSettingsPanelBuildInfoTest.testSettingsPanelSectionsTitles

```
expected: [SQL Preview, Table Name Mapping, Code Generation, MyBatis Core,
           ORM Frameworks, Auto-save, UI and Actions, Update and Diagnostics]
actual:   [SQL Preview, Table Name Mapping, Code Generation, MyBatis Core,
           ORM Frameworks, Auto-save, 源码位置捕获, UI and Actions,
           Update and Diagnostics]
```

| 失败位置 | 期望 | 实际 |
|----------|------|------|
| `PluginSettingsPanelBuildInfoTest.kt:85` | 8 个 TitledSeparator | 9 个（多 `源码位置捕获`） |

**根因**：生产代码 `PluginSettingsPanel.kt:529` 新增
`sectionGroup("settings.log.tab.sourceCapture")`（F-44-7：SqlSourceInterceptor 自动注入 /
源码位置捕获，bundle 键 `settings.log.tab.sourceCapture` = "Source Location Capture" /
"源码位置捕获"）。测试 `expected` 列表（`PluginSettingsPanelBuildInfoTest.kt:74-84`）仍沿用旧版 8 分区，未追加第 9 区。

**结论**：测试过期。生产新增分区正确，测试预期列表需追加
`settings.log.tab.sourceCapture`。

### 失败 2：PluginSettingsPersistenceTest.testLanguageWriteThroughRefreshesCheckboxTexts

```
expected: 18  but was: 20
```

| 失败位置 | 期望 | 实际 |
|----------|------|------|
| `PluginSettingsPersistenceTest.kt:147` | 18 个 JCheckBox | 20 个 |

**根因**：生产代码随功能演进新增复选框，测试计数未同步。当前生产实际 20 个：
`PluginSettingsPanel.kt` 内 19 个 `JBCheckBox`（`replaceParamsCheck` /
`formatCheck` / `gutterIconCheck` / `injectLogicDeleteCheck` / `injectTenantLineCheck` /
`injectTenantOnInsertCheck` / `dataPermissionHintCheck` / `manualEntityCheck` /
`logMixedPrefixCheck` / `logAutoCaptureCheck` / `logAutoOpenCheck` /
`logStopOnToolWindowCloseCheck` / `logTimestampCheck` / `logFormatSqlCheck` /
`logHibernateEnabledCheck` / `logJdbcEnabledCheck` / `logAutoSaveCheck` /
`autoInjectInterceptorCheck` / `logShowDurationCheck`）+ `updateSection.autoCheckCheck`（更新分区"启动时自动检查更新"）。

测试注释（`PluginSettingsPersistenceTest.kt:140-146`）自身追溯了计数演变
（4→5→…→18），但 `autoInjectInterceptorCheck`（F-44-7 源码位置捕获）与
`logShowDurationCheck`（执行耗时显示）两个复选框在注释定稿后加入，未计入。

**结论**：测试过期。生产新增复选框正确，测试预期计数需改为 20，
注释追溯段同步补正。

### 失败 3：SqlLogHistoryRoundTripTest.真实链路_捕获条目自动保存后读取回环_字段全一致

```
expected: ...OM user WHERE id = 1[]   (无分号)
actual:   ...OM user WHERE id = 1[;]  (有分号)
```

| 失败位置 | 期望 | 实际 |
|----------|------|------|
| `SqlLogHistoryRoundTripTest.kt:72` | `captured.restoredSql`（无 `;`） | `read.restoredSql`（有 `;`） |

**根因**：生产代码 `SqlLogAutoSaver.writeEntry`（`SqlLogAutoSaver.kt:141`）写入时调用
`withTerminator(entry.restoredSql)`（`SqlLogPanel.kt:74-75`，无分号结尾自动追加 `;`，
已以 `;` 结尾或空串不重复），保证历史 `.sql` 文件可直接在数据库工具中执行。

测试夹具 `capturedEntry(sql = "SELECT ... WHERE id = 1")` 设 `restoredSql = sql`（无 `;`），
经 write→read 回环后读取端得到带 `;` 文本；断言 `assertEquals(captured.restoredSql, read.restoredSql)`
两端不一致。测试未把 `withTerminator` 纳入预期。

**结论**：测试过期。生产 `withTerminator` 行为正确（有意为之，便于直接执行），
测试断言应改为比较 `withTerminator(captured.restoredSql)`，或夹具设 `restoredSql = withTerminator(sql)`。

### 为什么判定为"测试过期"而非"生产 bug"

三处失败均经 dev 分支干净基线（`git stash`）复现，确认在改动前即存在；
且三处对应的生产行为均有明确功能意图：
- 失败 1/2：新分区与复选框对应 F-44-7（源码位置捕获）、执行耗时显示等已交付功能；
- 失败 3：`withTerminator` 保证历史 SQL 文件可执行，属有意设计。

生产代码全部正确，**仅需修订测试**。
