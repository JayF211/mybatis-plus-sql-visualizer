## 第一部分：T-M31.9 RegionUrlMapper setContextClassLoader 噪音修复

### 1.1 需求分析（用户视角）

runIde 沙盒启动时，日志刷 3+ 屏 `SecurityException: setContextClassLoader` 堆栈（见附录 A），视觉上像严重错误，实际是 IDEA 2024.3 + JDK 21 组合的已知噪音。目标：**消除该噪音**，同时不破坏启动时序（不禁用 SecurityManager）。

### 1.2 根因分析

**两层因果链**：

1. **SecurityManager 来源**：发行版 vmoptions（`ideaIU-2024.3.7.1-win/bin/jetbrains_client64.exe.vmoptions` 末行）设了 `-Djava.security.manager=com.intellij.platform.core.nio.fs.CoreBootstrapSecurityManager` → JVM 启动早期（initLevel 2）自动安装 SM。

2. **innocuous 线程诞生**：JDK 21 的 `ForkJoinPool.commonPool()` 在 SecurityManager 存在时改用 `InnocuousForkJoinWorkerThread`（`ForkJoinPool.makeCommonPool` 源码逻辑）。该类 `setContextClassLoader` **无条件硬抛 SecurityException**（`ForkJoinWorkerThread.java:230`，源码写死不查任何策略）。

3. **撞击点**：`RegionUrlMapper`（插件市场/CDN 区域 URL 映射）由 Caffeine 异步加载，恰跑在 common pool 上；`HttpRequests.process` 发请求前设 context class loader → 撞上硬抛 → 映射加载失败回退默认 URL（功能无害，纯噪音）。

**关键发现（JDK 21 initLevel 时序实证）**：

反编译 JBR 21.0.7 的 `System.initPhase3` / `ClassLoader.getSystemClassLoader` / `ForkJoinPool.makeCommonPool` 后，完整时序如下：

| initLevel | 阶段 | getSystemClassLoader() 行为 |
|-----------|------|---------------------------|
| 0/1/2 | initPhase1/2 + SM 安装 | 返回 AppClassLoader（**不抛**） |
| 3 | PathClassLoader 构造中 | **硬抛 IllegalStateException** |
| 4 | 完全初始化后 | 返回 scl |

- `System.initPhase3` 先装 SM（initLevel 2，此时 `getSystemClassLoader()` 返回 AppClassLoader **不抛**）→ `implSetSecurityManager` 首次安装时调 `DefaultFileSystemProvider.theFileSystem()` + `sm.checkPackageAccess` → CoreBootstrapSecurityManager.checkPermission 里 `FileSystems.getDefault()` **预初始化文件系统并卸载自己**（`setSecurityManager(null)`，日志的"has been called"警告即卸载调用）→ 然后 `VM.initLevel(3)` → PathClassLoader 构造（initLevel 3 时 getSystemClassLoader **硬抛**）→ Paths.get 依赖已就绪的 FileSystems。
- **即 CoreBootstrapSecurityManager 是 FileSystems 预初始化的触发者，缺失即崩**。

**尝试过的失败路径**：`-Djava.security.manager=allow` 直接关掉 SM → JVM 启动崩溃（`Error occurred during initialization of VM: getSystemClassLoader cannot be called during the system class loader instantiation`）。因为 allow 值在 initPhase3 直接短路不触发预初始化 → PathClassLoader 构造时 FileSystems 未就绪 → 崩。**SM 不可禁**。

### 1.3 技术方案

**核心思路**：绕开 innocuous 线程——通过 JDK 21 官方属性 `java.util.concurrent.ForkJoinPool.common.threadFactory` 指定普通线程工厂（common pool 构造用 `ClassLoader.getSystemClassLoader()` 加载它，无视 SM 状态 → common pool 恒为普通线程）。

**改动清单**：

| 文件 | 改动 |
|------|------|
| `dev-support/plain-fjpf/src/.../PlainForkJoinWorkerThreadFactory.java` | 新增：普通线程工厂（`ForkJoinPool.ForkJoinWorkerThreadFactory` 实现，`newThread` 返回 `new ForkJoinWorkerThread(pool){}`） |
| `build.gradle.kts` | 新增 `compilePlainFjpf`（JavaCompile，release 17，UTF-8）+ `plainFjpfJar`（Jar）任务；`runIde` 追加 `dependsOn(plainFjpfJar)` + `classpath += files(...)` + `jvmArgumentProviders.add(...)` 注入属性 |

**关键代码**（`build.gradle.kts:127-156`）：

```kotlin
val compilePlainFjpf = register<JavaCompile>("compilePlainFjpf") {
    source = fileTree("dev-support/plain-fjpf/src")
    classpath = files()
    destinationDirectory.set(layout.buildDirectory.dir("plain-fjpf/classes"))
    options.release.set(17)
    options.encoding = "UTF-8"
}
val plainFjpfJar = register<Jar>("plainFjpfJar") {
    from(compilePlainFjpf.map { it.destinationDirectory })
    destinationDirectory.set(layout.buildDirectory.dir("plain-fjpf"))
    archiveFileName.set("plain-fjpf.jar")
}

    autoReload = true
    dependsOn(plainFjpfJar)
    classpath += files(layout.buildDirectory.file("plain-fjpf/plain-fjpf.jar"))
    jvmArgumentProviders.add(CommandLineArgumentProvider {
        listOf("-Djava.util.concurrent.ForkJoinPool.common.threadFactory=" +
            "cn.song.mybatisplus.visualizer.support.PlainForkJoinWorkerThreadFactory")
    })
}
```

**设计要点**：
- 工厂 jar 是**独立 Java 源**（不进入插件产物），仅 runIde 沙盒启动 classpath 提供
- 属性在 `jvmArgumentProviders` 追加（IPGP 会把它放在 vmoptions 参数**之后**，同名 -D 后者覆盖前者，实测生效）
- 不动 SecurityManager → FileSystems 预初始化时序不受影响 → 不崩

### 1.4 验证

**独立 JVM 对照实证**（jbr 21.0.7 + 同样的 SM 参数 + nio-fs.jar）：

| 实验 | 参数 | 结果 |

| 实验1（有属性） | `-Djava.security.manager=CoreBootstrapSecurityManager -D...threadFactory=PlainForkJoinWorkerThreadFactory` | `setContextClassLoader OK (普通线程)` ✓ |
| 实验2（对照，无属性） | `-Djava.security.manager=CoreBootstrapSecurityManager` | `SecurityException (innocuous)` ✓（复现原状） |

## 第二部分：invocationHasMpj 接口继承误判修复

### 2.1 需求分析（用户视角）

真机使用 `BikeDeviceInfoService`（源码 `interface BikeDeviceInfoService extends MPJBaseService<BikeDeviceInfoEntity>`）作调用类时，多表 JOIN 生成报：

```
SqlReverseException: reverse.error.unsupported: 多表 JOIN 需要 MyBatis-Plus-Join（MPJ）依赖，但调用类 BikeDeviceInfoService 无 MPJ 能力
```

该接口**确实具备 MPJ 能力**（直接 extends MPJBaseService），属误判。

### 2.2 根因分析

**逻辑本身是对的**——`hasMpjInterface`（`SqlToJavaConverter.kt:65`）接口递归（`:68`）+ 父类递归（`:69`）都有，且既有测试 `testDirectMpjInterfaceMatch` 覆盖了 `interface UserService extends MPJBaseService<User>` 并断言为 true。

**但真机失败**。差异只有一点：测试里 `MPJBaseService` 是**测试项目内的源文件**，而真实项目里 `MPJBaseService` 来自 **MPJ 库的编译 jar**，且带泛型参数 `MPJBaseService<BikeDeviceInfoEntity>`。

**最可能的 bug 机制**：`clazz.interfaces`（`:68`）解析 `BikeDeviceInfoService` 的父类型时，需要完整解析泛型超类型 `MPJBaseService<BikeDeviceInfoEntity>`——这要求类型实参 `BikeDeviceInfoEntity` 也能解析。一旦类型实参解析因任何原因失败（跨模块、stub 不完整、循环依赖等），**整个超类型解析失败 → `getInterfaces()` 返回空数组** → 继承链在第一层就断了，MPJBaseService 根本没被检查到。

而源文件→源文件解析总是成功，所以测试通过但真机翻车。

**调用链**（`SqlToJavaPanel.kt:666` → `SqlToJavaConverter.kt:53` → `:65`）：

```
SqlToJavaPanel.callerField$lambda$0(:149) → setPicked(:568) → pickPsiClassForTest(:478)
→ elementChosen(:460) → regenerateWithNewFormat(:852) → render(:902) → generateCode(:950)
→ SqlToJavaConverter.generateCode(:171) → JavaCodeGenerator.generate(:83) → generateSelect(:110)
→ 判定 isJoin && invocation!=null && !invocation.mpj → throw SqlReverseException(:113)
```

`invocation.mpj` 在 `SqlToJavaPanel.kt:886` 由 `SqlToJavaConverter.invocationHasMpj(project, callerField.text)` 赋值。

### 2.3 技术方案

**核心思路**：把 `hasMpjInterface` 的遍历从"依赖 `getInterfaces()` 完整解析泛型超类型"改为**不依赖类型实参解析**的方式——用 `clazz.superTypes`（`PsiClassType[]`，同时覆盖超类和超接口）+ `PsiClassType.resolve()` 取 qualifiedName。

**改动清单**：

| 文件 | 改动 |
|------|------|
| `SqlToJavaConverter.kt`（`hasMpjInterface`，:65-70） | 改用 `superTypes` 遍历 + `seen` 改 `MutableSet<String>` |
| `InvocationMpjHeavyTest.kt` | +2 用例（jar-loaded 泛型超类型 + 接口直接 extends MPJ） |
| `JavaCodeGeneratorTest.kt` | +1 用例（JOIN 场景端到端：caller 选真实 MPJ 能力接口不报错） |

**关键代码**（`SqlToJavaConverter.kt:65-70`）：

```kotlin
internal fun hasMpjInterface(clazz: PsiClass, seen: MutableSet<String> = mutableSetOf()): Boolean {
    val qn = clazz.qualifiedName ?: return false
    if (!seen.add(qn)) return false
    if (qn in MPJ_INTERFACES) return true
    // superTypes = 超类 + 超接口（PsiClassType[]），比 getInterfaces() 更稳——
    // 即使泛型实参未完全解析，仍可通过 PsiClassType.resolve() 取 raw qualifiedName
    return clazz.superTypes.any { superType ->
        superType.resolve()?.let { hasMpjInterface(it, seen) } ?: false
    }
}
```

**改动要点**：
- `clazz.superTypes`（`PsiClassType[]`）替代 `getInterfaces()` + `getSuperClass()` 分开写——同时覆盖超类和超接口，且 `PsiClassType` 对 jar-loaded 类型解析更稳
- `seen` 从 `MutableSet<PsiClass>` 改为 `MutableSet<String>`（qualifiedName）——避免 PsiClass 对象在 stub 环境下 equals 不稳定
- 如果 `PsiClassType.resolve()` 仍因泛型实参失败，再加一层 fallback：从 `superType.canonicalText` 提取 raw 类名匹配（兜底，可选）

### 2.5 边界与风险

- **诊断优先**：先写复现用例锁定是"jar-loaded 泛型超类型解析失败"还是其他原因（如 `getClassesByName` 取到错误类），再动手改——避免修错地方
- **`superTypes` vs `getInterfaces()`**：`superTypes` 对接口返回超接口、对类返回超类+实现接口，语义覆盖完整；但需确认对**接口的接口**（interface extends interface）也适用（JDK PSI 文档确认 `PsiClass.superTypes` 对接口返回扩展的接口）
- **`seen` 改 String**：qualifiedName 在 jar-loaded 类上稳定返回（不受 stub 状态影响），比 PsiClass 对象更安全
- **fallback 可选**：如果 `PsiClassType.resolve()` 在极端场景仍失败，从 `canonicalText`（如 `com.github.yulichang.base.MPJBaseService<Entity>`）提取 `<` 前的 raw 全限定名匹配——但先不加，看 P0 测试是否足够
- **不动 `JavaCodeGenerator` / `SqlToJavaPanel` / `MPJ_INTERFACES` 常量**：判定逻辑收敛在 `hasMpjInterface` 一处
