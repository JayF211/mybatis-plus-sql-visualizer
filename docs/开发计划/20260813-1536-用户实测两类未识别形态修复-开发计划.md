# 用户实测两类未识别形态修复——分析与开发计划（M19.5）

> 本文档记录 **MyBatis-Plus SQL Visualizer** 的 M19.5 增量修复：用户实测报告的两类真实代码**无法识别**——
> **① 服务链赋值形态**（`service.lambdaQuery()...one()` / `service.lambdaUpdate()...update()` 结果变量接收，gutter 无图标）；
> **② 实体单条 CRUD**（`service.getById(id)` 单主键查询、`service.save(entity)` 单实体插入）。
>
> **M19.5 同时与《[低频复杂 API 后期实现计划](./20260813-0829-低频复杂API后期实现计划.md)》一起开工**：P1-01~06 全部 + P2-08（`selectByIds`/`deleteByIds` 与 T-M19.5-03 的 `Operation.SELECT` 同一修改点，`selectByIds`/`listByIds` 模板合并实现）并入本批。
>
> 当前基线：M19.4（282 测试全绿，2026-08-13）。

---

## 1. 问题与根因（2026-08-13，证据驱动）

### 1.1 问题①：服务链赋值形态锚点丢失（实体名/列名已占位）

```java
// 失败用例 1（清单 Q17：service.lambdaQuery() 链）
BikeDeviceInfoEntity onlineVersion = bikeDeviceInfoService.lambdaQuery()
        .eq(BikeDeviceInfoEntity::getStationId, 1)
        .orderByDesc(BikeDeviceInfoEntity::getDicStatus)
        .last("LIMIT 1")
        .one();
// 失败用例 2（清单 U13：service.lambdaUpdate() 链）
boolean updated = spWorkflowService.lambdaUpdate()
        .eq(SpWorkflow::getId, dto.getWorkflowId())
        .set(SpWorkflow::getShelveStatus, ShelveStatusEnum.NOT_SHELVED.getCode())
        .update();
```

**症状**：两处代码行左侧均**无 SQL 预览图标**（gutter 入口是 M10 起的主入口），图标点击/快捷键均提示
"未找到可转换的 Wrapper"；用户修改语句形态后仍失败。

**根因**：`WrapperAnchorDetector.isInsideWrapperVariableInitializer`（`WrapperAnchorDetector.kt:114-124`）
对**任意变量**初始化一律去重——沿父链上溯**遇到任意 `PsiVariable` 即返回 true**，未检查变量是否为
**Wrapper 类型**。当链被**结果变量**接收（实体 / boolean / long）时，场景 B 不会给变量标锚点
（变量类型非 Wrapper），场景 C 的链起点锚点又被去重抑制 → **整条语句无任何锚点 → 无图标**。

**实证（2026-08-13，临时回归测试已移除）**：`WrapperAnchorDetectorTest` 临时新增用户用例 1 原样测试
（结果变量赋值 + eq/orderByDesc/last/one）→ `anchorElement(lambdaQuery 方法名)` 断言失败（返回 null）→ **复现成功**；
移除后测试全绿。

**既有测试未暴露的原因**：anchor 路径测试全用 standalone 形态（`testServiceChainCallAnchors`）；
唯一赋值形态（`testServiceLambdaQueryChainCountRendersCountStar` 的 `long total = ...count()`）走
**locator 路径**（`preview(anchor())`），不经 anchor 路径——locator/转换链路本身正常（standalone 的
SELECT/UPDATE/DELETE 测试全绿）。

**影响面**：Q17 `lambdaQuery()` 链（35 文件约 177 处）与 U13 `lambdaUpdate()` 链（20 文件约 87 处）中
**结果变量赋值形态**——`XxxEntity e = ...one()/.oneOpt()`、`long n = ...count()`、
`boolean b = ...update()/.remove()`、`List<T> l = ...list()`——全部受影响（真实项目最常见书写形态）。

### 1.2 问题②：实体单条 CRUD 未识别

```java
// 失败用例 3（实体单主键查询，无 wrapper）
spWorkflowVersionService.getById(workflowVersionUpdateDTO.getVersionId());
// 失败用例 4（实体单条插入，无 wrapper）
carDeviceInfoService.save(new CarDeviceInfoEntity());
```

**症状**：同①——无 gutter 图标、预览提示"未找到可转换的 Wrapper"。

**根因**（代码核查，`BatchOperationConverter.kt`）：

- `service.save(entity)`：`BATCH_OPERATIONS` 注册表（35-44 行）**没有 `save` 条目**——但类注释（17 行）
  声称 "saveBatch(list) / insertBatchSomeColumn(list) / save(entity)：INSERT"——**注释与实现不一致**，
  `save` 单实体形态从未注册（实体解析链路本身已具备：`resolveEntityTable` 步骤 2 实体参数类型
  `new CarDeviceInfoEntity()` 可解析）；
- `service.getById(id)`：插件**无 SELECT 类实体单查操作类型**（`Operation` 枚举仅有
  UPDATE/INSERT/DELETE/UPSERT）——`getById` 未注册、无对应生成模板；
- 锚点（`WrapperAnchorDetector` 场景 D）与预览回退路径（`SqlPreviewService.preview` 批量分支）
  均依赖 `batchOperationMethodNames` 集合——注册表补齐后**自动生效**，无额外改动。

**影响面**：`getById(id)`（实体单查，真实项目高频）、`save(entity)`（单实体插入）及其同族
`listByIds(ids)`（主键 IN 查询）——均无 wrapper 形态，属 F-15 批量/实体操作预览的自然延伸。

## 2. 修复方案

| 编号 | 修改点 | 说明 |
|------|--------|------|
| T-M19.5-01 | `WrapperAnchorDetector.kt` `isInsideWrapperVariableInitializer` | 去重条件加"变量是 Wrapper 变量"：`PsiVariable -> return WrapperLocator.isWrapperVariable(cursor)`——仅当变量为 Wrapper 类型（或 Wrapper 基类型 + initializer 链首为 wrapper 构造/工厂）才去重；结果变量（实体/boolean/long 等）不再抑制场景 C 锚点 |
| T-M19.5-01a | `WrapperLocator.kt` `isWrapperVariable` | 由 `private` 提升为 `internal` 供 AnchorDetector 复用。其判定为 O(1) 纯语法（`detectWrapperType` 文本匹配 + 基类型时 initializer 链首回溯），**无 resolve**，符合 M10 性能红线 |
| T-M19.5-02（P2 可选） | `WrapperLocator.kt` `findWrapperFactoryCall` | 快捷键路径光标停在**变量名/类型**上时定位失败（链位于 initializer 子树内、非变量标识符的祖先）：anchor 上溯到 `PsiVariable` 时检查其 initializer 子树。非本次用户路径（光标在链上即可定位），评估后决定是否纳入 |
| T-M19.5-03 | `BatchOperationConverter.kt` | ① `BATCH_OPERATIONS` 注册 `save` → `Operation.INSERT`（单实体形态复用 `buildInsertBatch` 全列模板，与类注释一致化）；② 新增 `Operation.SELECT` + 注册 `getById`（主键等值：`SELECT 全列 FROM 表 WHERE 主键 = ?`）、`listByIds`/`selectByIds`（主键 IN：`... WHERE 主键 IN (?, ?, ...)`，**低频计划 P1-02/P2-08 同点合并**）、`deleteByIds`（DELETE 主键 IN，与 `removeByIds` 同族）；③ 实体解析沿用 `resolveEntityTable`（getById 单参走步骤 3 service qualifier 泛型，T-M15-08 的 removeById 链路已具备；save 走步骤 2 实体参数类型）；④ 类注释同步补齐 |
| T-M19.5-04 | 锚点/预览回退验证 | `save`/`getById`/`listByIds` 注册后经 `batchOperationMethodNames` 集合（`WrapperAnchorDetector` 场景 D + `SqlPreviewService.preview` 批量分支同一来源）gutter 图标与预览**自动生效**——仅验证，不改代码 |

**边界行为确认（修复后）**：

- 问题①：`LambdaQueryWrapper<X> w = Wrappers.lambdaQuery()...` → 变量是 Wrapper → 仍去重、只标变量名（既有测试不变）；
  `Wrapper<X> w = new LambdaQueryWrapper<X>()...` 基类型声明 → 基类型降级命中 → 仍去重；
  `XxxEntity e = service.lambdaQuery()...one()` → 变量非 Wrapper → `lambdaQuery` 方法名成为锚点；
  罕见形态 `Object o = new LambdaQueryWrapper<>()...` → 变量非 Wrapper → new 关键字成为锚点（比现状更正确）；
- 问题②：`save(entity)` 与 `updateById(entity)`/`saveBatch(list)` 模板同族（全列 INSERT）；
  `getById(id)` 与 `removeById(id)` 对称（同主键等值解析链路，SELECT 而非 DELETE）；
  `listByIds(ids)` 与 `removeByIds(list)` 对称（主键 IN）。

## 4. 验收

- `./gradlew clean test` 全绿（282 + 新增用例）+ `buildPlugin` 成功；
- 手动清单（真实 IDE）：
  1. 真实工程四条用户用例原样打开 → gutter 图标出现，点击弹窗 SQL 正确
     （`SELECT ... LIMIT 1` / `UPDATE ... WHERE id = ?` / `SELECT ... WHERE id = ?` / `INSERT INTO ... VALUES (...)`）；
  2. 问题①变体逐一验证：`long total = service.lambdaQuery()...count()`、`List<X> l = service.lambdaQuery()...list()`、
     `boolean b = service.lambdaUpdate()...remove()` 均有图标且 SQL 正确（COUNT(*)/SELECT/DELETE）；
  3. 问题②变体：`removeById(id)`（既有）与 `getById(id)`（新增）图标与 SQL 对称正确；
  4. `LambdaQueryWrapper<X> w = Wrappers.lambdaQuery()...` 仍只标变量名（无同行双图标）；
  5. standalone 形态（终结点直接作为语句）图标与 SQL 不受影响。
