## 1. 问题描述

用户真实代码（预览缺失 `EXISTS` 子查询条件）：

```java
Page<CarStationPriceTaskRecordEntity> page = taskRecordService.page(
        new Page<>(dto.getPageNum(), dto.getPageSize()),
        Wrappers.<CarStationPriceTaskRecordEntity>lambdaQuery()
                .like(StringUtils.hasText(dto.getName()), Entity::getName, dto.getName())
                .exists(dto.getStationId() != null,
                        "SELECT 1 FROM biz_car_station_price_task_station_rel rel " +
                                "WHERE rel.car_station_price_task_id = biz_car_station_price_task_record.id " +
                                "AND rel.station_id = {0}",
                        dto.getStationId())
                .eq(dto.getDicStatus() != null, Entity::getDicStatus, dto.getDicStatus())
                .orderByDesc(Entity::getCreateTime)
                .orderByDesc(Entity::getId));
```

实际预览：

```sql
SELECT ...
FROM biz_car_station_price_task_record
WHERE name LIKE ?
    AND dic_status = ?
    AND deleted = 0
ORDER BY create_time DESC, id DESC
-- 缺少：AND EXISTS (SELECT 1 FROM ... WHERE ... AND rel.station_id = ?)
```

## 2. 根因（已复现确认）

**不是**解析器不支持 `exists(condition, sql, v)`——`QueryWrapperParser.parseExists`（T-M15-03）已支持，
字符串拼接模板（`"a" + "b" + "c"`）经 `ExpressionEvaluator.evaluatePolyadic` 也能正确求值为字面量。

真正根因在 **PSI 定位层的链式终结点误判**：

- `WrapperLocator.kt:452`（`buildChainFromFactory`）以「链内最后一个方法名 ∈ `chainTerminalMethodNames`
  （one/list/count/**exists**/page/...，T-M15-01 为 `service.lambdaQuery()...exists()` 无参终结点形态加入）」
  识别链式消费终结点，命中即从链中剔除并记录消费语义；
- `exists` 同时是 MP 官方**条件方法**（`exists(boolean, String, Object...)`，AbstractWrapper）；
- 本用例的 wrapper 是裸工厂链直接作 `service.page(page, wrapper)` 实参，链内**没有**真正的终结点
  （one/list/page 等），于是链中间的 `.exists(...)` 被 `lastOrNull` 选中为终结点：
  - 该调用被剔除 → `EXISTS (...)` 条件丢失；
  - `chainExistsConsumed = true` → 整条链被包成 `SELECT EXISTS (...)`（当前构建行为；
    用户安装的旧构建无包裹逻辑、只剔除，即截图所见「纯 SELECT 缺条件」——同一根因两种表现）。

**复现证据**（临时测试，已删除）：复刻用户代码跑 `SqlPreviewService.preview`，实际输出为

```sql
SELECT EXISTS (SELECT id, name, dic_status, create_time
FROM car_station_price_task_record_entity
WHERE name LIKE ?
    AND dic_status = ?
ORDER BY create_time DESC, id DESC)
```

**现有测试未暴露原因**：Q14-① 用例（`testExistsSqlSubqueryCondition`）链尾带 `.page(new Page<>(1,10))`——
`page` 是真正的终结点（`lastOrNull` 先命中），中间的 `exists` 条件得以保留；「wrapper 直接作
service 方法实参的裸链」形态恰好无覆盖。

## 3. 修复方案

**主修复（一处）**：`WrapperLocator.kt` 终结点判定加 exists 双语义守卫——

```kotlin
// T-M25.2：exists 双语义——带参 exists(condition, sql, values) 是条件方法（Q14-①），
// 仅无参 exists() 是 Q14-③ 链式终结点（service.lambdaQuery()...exists()）。
// 带参 exists 误判为终结点 → 条件被剔除 + 整链误包 SELECT EXISTS（裸链实参场景）。
val terminal = clearedCalls.lastOrNull {
    it.methodExpression.referenceName in chainTerminalMethodNames &&
        !(it.methodExpression.referenceName == EXISTS_TERMINAL &&
            it.argumentList.expressions.isNotEmpty())
}
```

**不受影响路径核对**（无需改动）：
- `service.exists(wrapper)`（Q14-②）：外层消费方法判定（`EXISTS_CONSUMER`），不走终结点剔除；
- 无参 `exists()` 终结点（Q14-③）：仍正常剔除并触发 `SELECT EXISTS` 包裹；
- 其余终结点（one/list/count/page/update/remove 等）无同名 wrapper 条件方法，无歧义。
