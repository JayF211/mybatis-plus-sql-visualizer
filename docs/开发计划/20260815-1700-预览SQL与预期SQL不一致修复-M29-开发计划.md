## 1. 差异分析（预览 SQL vs MP 实际生成的 SQL）

用户代码：

```java
LambdaQueryWrapper<BikeOrderRecordEntity> wrapper = Wrappers.<BikeOrderRecordEntity>lambdaQuery()
        .in(CollUtil.isNotEmpty(stationIds), BikeOrderRecordEntity::getStationId, stationIds)
        .eq(ObjUtil.isNotNull(dto.getDicStatus()), BikeOrderRecordEntity::getDicStatus, dto.getDicStatus())
        .in(BikeOrderRecordEntity::getDicPayStatus, DicConstants.DIC_VALUE_PAY_WAIT, DicConstants.DIC_VALUE_PAY_COMPLETE)
        .and(StrUtil.isNotBlank(dto.getKeyword()), w ->
                w.likeRight(BikeOrderRecordEntity::getCode, dto.getKeyword())
                        .or().likeRight(BikeOrderRecordEntity::getUserPhone, dto.getKeyword())
        )
        .between(BikeOrderRecordEntity::getCreateTime, dto.getStartTime(), dto.getEndTime())
        .orderByDesc(BikeOrderRecordEntity::getCreateTime);
Page<BikeOrderRecordEntity> page = bikeOrderRecordService.page(new Page<>(pageNum, pageSize), wrapper);
```

面板复制出的预览 SQL：

```sql
SELECT ... FROM biz_bike_order_record
WHERE station_id IN (?)
    AND dic_status = ?
    AND dic_pay_status IN (1, 2)
    AND create_time BETWEEN ? AND ?
    AND deleted = 0
ORDER BY create_time DESC
```

对照 MP 运行时（keyword 非空时）应生成的 SQL：

```sql
SELECT ... FROM biz_bike_order_record
WHERE station_id IN (?,?,?)                    -- 集合每个元素一个占位符
    AND dic_status = ?
    AND dic_pay_status IN (?, ?)               -- 运行时绑定常量值 1、2
    AND (code LIKE CONCAT(?, '%') OR user_phone LIKE CONCAT(?, '%'))   -- ← 预览缺失
    AND create_time BETWEEN ? AND ?
    AND deleted = 0
ORDER BY create_time DESC
LIMIT ?,?                                      -- ← 预览缺失（IService.page 分页）
```

### 差异清单

| # | 差异 | 性质 | 根因 |
|---|------|------|------|
| D1 | `AND (code LIKE ? OR user_phone LIKE ?)` 整个 and 组缺失（动态条件面板也无该开关） | **Bug（P0）** | QueryWrapperParser 的 and/or/nested/not/func 分支未剥离布尔条件首参，parseGroup/parseNot/func 取 `args.firstOrNull()` 当 NestedArg 失败 → 组静默丢弃 |
| D2 | `LIMIT ?,?` 缺失（service.page 分页） | **缺口（P1）** | WrapperLocator 消费识别只有 count/delete/exists/updateEntity 四类，page/selectPage 不识别；即使识别也无 Page 参数解析与 LIMIT 生成（LimitClause 仅由 `last("limit ...")` 填充） |
| D3 | `dic_pay_status IN (1, 2)`（预览内联常量）vs `IN (?, ?)`（运行时绑定） | 设计特性，**语义等价** | ExpressionEvaluator 静态求值 static final 常量（M14.6「字面量恒内联」同一机制；XML 引擎 @class@field 同语义）。无需修复，建议文档说明 |
| D4 | `station_id IN (?)` 单占位符 vs `IN (?,?,?)` 逐元素 | 设计特性（近似） | 集合变量运行时大小不可静态展开 → 单占位符 + inList 回填提示（面板输入 `1,2,3` 回填 `(1, 2, 3)`，M19.6 已文档化）。无需修复 |

## 2. 目标

1. **P0-1 and/or/nested/not/func 布尔条件重载修复**：`.and(condition, w -> ...)` 等带布尔首参的分组调用不再被丢弃——剥离标志、嵌套组照常解析、组挂动态条件开关（默认勾选语义与 M13 一致：字面量 false 默认不勾选、运行时布尔默认勾选）。修复后预览含 `AND (code LIKE ? OR user_phone LIKE ?)`，面板「动态条件」出现该组开关。
2. **P1-1 分页消费识别与渲染**：`service.page(Page, wrapper)` / `mapper.selectPage(Page, wrapper)` / 链式 `lambdaQuery()...page(...)` 识别为分页消费，解析 `new Page<>(pageNum, pageSize)` 实参生成分页子句——字面量 pageNum/pageSize 直接算 `LIMIT offset, count`（如 `LIMIT 0, 10`），运行时变量渲染 `LIMIT ?, ?`（占位符进参数区可回填）；按方言渲染（MySQL `LIMIT ?,?`、PG `LIMIT ? OFFSET ?` 等）。

**非目标**：D3/D4（设计特性，仅文档说明）；`last("limit ...")` 既有路径行为不变；分页拦截器未配置时 MP 实际不追加 LIMIT 的运行环境差异（预览恒按配置方言渲染分页，与 MP 拦截器配置解耦——文档化边界）。

## 3. 根因（代码级定位）

### 3.1 D1：分组方法布尔重载被静默丢弃

调用链实证：

- `ArgResolver.resolve`（ArgResolver.kt:52-89）：`.and(StrUtil.isNotBlank(dto.getKeyword()), w -> ...)` 首参是 `PsiMethodCallExpression` → `resolveMethodCallArg` → 非 `on` 方法 → `resolveValueArg` → **ValueArg（占位符）**；第二参 lambda → **NestedArg**。故 `WrapperCall.args = [ValueArg, NestedArg]`。
- `QueryWrapperParser.analyzeFlag`（QueryWrapperParser.kt:571-593）的 `CONDITION_METHODS` 只含 eq/ne/gt/ge/lt/le/like/in/between/isNull/allEq 等，**不含 and/or/nested/not/func** → 标志不被剥离。
- 分派 `"and"`/`"nested"` → `parseGroup(call)`（QueryWrapperParser.kt:465-475）：`call.args.firstOrNull() as? WrapperArg.NestedArg` —— 首参是 ValueArg → **null → 整个组静默丢弃**（`addConditionFlagged` 对 null 条件仅保持 orPending）。`"or"` 同（parseGroup 共用）。`"not"` → `parseNot`（kt:451-456）首参取法相同 → 丢弃。`"func"`（kt:209-214）→ 首参取法相同 → 丢弃。
- 无布尔首参的形态（`and(w -> ...)` / `or(w -> ...)` / `nested(w -> ...)` / `not(w -> ...)`）args[0] 即 NestedArg，正常——所以既有测试全绿、长期未暴露。
- 组内 `w.likeRight(...).or().likeRight(...)` 由 `parseInternal` 的 no-arg `or()` 处理（orPending → Group(OR, ...)），本身无问题——只是外层组已丢。

影响面：MP 的 `and(boolean, Consumer)` / `or(boolean, Consumer)` / `nested(boolean, Consumer)` / `not(boolean, Consumer)` / `func(boolean, Consumer)` 五个官方重载全部命中（真实项目最常见写法，用户实测即此）。

### 3.2 D2：page 消费未识别、无分页渲染

- `WrapperLocator.isConsumerArgument` 消费集合仅三类（WrapperLocator.kt:1008-1020）：`deleteConsumerMethodNames`（remove/delete/deleteJoin）、`countConsumerMethodNames`（count/selectJoinCount/selectCount）、`EXISTS_CONSUMER`（exists）。**`page` 不在其中** → `WrapperChain` 无 pageConsumed 标记，`SqlPreviewService.preview` 无对应分支。
- `chainTerminalMethodNames`（kt:995-1000）虽含 `page`（链式 `lambdaQuery()...page()` 终结点剔除），但剔除后**不产生任何 LIMIT**。
- `SelectStatement.limit` 仅由 `parseLimit`（QueryWrapperParser.kt:512-524）填充（`last("limit 10")` 文本解析）；`LimitClause`（ColumnRef.kt:56-59）只承载 Long 字面量，无占位符能力；`SqlGenerator.generateSelect`（SqlGenerator.kt:193）渲染 LIMIT 时不收集参数。
- MP 运行时：`IService.page(Page, Wrapper)` → `selectPage` → PaginationInnerInterceptor，MySQL 渲染 `LIMIT ?,?`（两个绑定参数 offset=(pageNum-1)*pageSize、size=pageSize）。

## 4. 方案设计

### 4.1 Fix-1：分组方法布尔重载（P0）

复用既有 `analyzeFlag` / `bindToggle` / `flagged` 模式，扩展 GROUP 方法族：

1. 新增 `GROUP_FLAG_METHODS = setOf("and", "or", "nested", "not", "func")`；分派分支统一走新辅助：
   - `stripGroupFlag(call)`：args >= 2 且首参不是 NestedArg，且首参为 true/false 字面量或占位符（运行时布尔）→ 返回 `FlagAnalysis`（剥离后 call + flagSource + defaultEnabled，判定规则与 `analyzeFlag` 一致：字面量 false → 默认不勾选，其余默认勾选）；否则返回 null（无标志，走原逻辑，回归不变）。
   - `parseGroupFlagged`：无标志 → 原 `parseGroup`；有标志 → `parseGroup(stripped).flagged(analysis)`（组挂 toggle，id 延续 `c${toggleSeq++}`，label = 渲染后的组文本，如 `(code LIKE ? OR user_phone LIKE ?)`）。
2. `not` 分支：`parseNot` 同样先剥离标志再取 NestedArg，结果 `flagged(analysis)`（negated 组挂 toggle）。
3. `func` 分支：有标志时把展开的子条件包成 `Group(AND, children).flagged(analysis)`（func 语义=condition ? 追加子条件 : 跳过；组化后开关可控），无标志保持展平（回归不变）。
4. 面板零改动：组 toggle 经 `Condition.toConditionViews` 扁平化自然出现（组自身开关 + 组内子条件开关，与既有 or() 组一致）；组文本超宽由既有 checkBoxText 截断 + tooltip。

### 4.2 Fix-2：分页消费识别与渲染（P1）

1. **消费识别**：`WrapperLocator` 新增 `pageConsumerMethodNames = setOf("page", "selectPage")`（IService.page / BaseMapper.selectPage / Db.page）；`WrapperChain` 增加 `pageConsumed: Boolean` 与 `pageCall`（或直接存解析产物），`buildChain` 中 `isConsumerArgument(ref, pageConsumerMethodNames)` 置位；链式终结点 `page`（chainTerminalMethodNames 已有）同步置位。Service 层与 chain 两入口的构造调用点同步加参。
2. **Page 参数解析**（psi 层）：定位消费调用的 Page 实参（`new Page<>(pageNum, pageSize[, searchCount[, optimizeCountSql]])`）：
   - 两参/三参/四参构造：第 1 参 = 页码、第 2 参 = 每页条数；`new Page<>()` 空构造 → 默认 1、10（MP 默认）；
   - 实参经 ExpressionEvaluator：字面量 int → `SqlValue.Literal`；变量 → `SqlValue.Placeholder(source)`；
   - 语义：offset = (pageNum-1)*pageSize、count = pageSize（对齐 MP `getOffet()`：`getCurrent()>0 ? (getCurrent()-1)*getSize() : 0`）。
3. **模型**：`LimitClause.offset/count` 由 Long 改为 `SqlValue`（Literal 保留 `last("limit 10")` 解析产物为 Literal，`renderLimit` 渲染不变；Placeholder 渲染 `?`）。`Dialect.renderLimit` 全部实现适配（MySQL/PG/Oracle/SQLServer/DM 等共 10 个方言点，抽公共辅助避免重复）。
4. **参数收集**：`SqlGenerator.generateSelect` 渲染 LIMIT 时把 Placeholder 的 source 收集进 paramSink + hintSink（numeric 无引号 hint），面板参数区自动出现 `#pageNum`/`#pageSize` 输入行，回填后 `LIMIT 20, 10`。
5. **方言**：MySQL 形态 `LIMIT ?, ?`；PG 形态 `LIMIT ? OFFSET ?`；其余方言沿用各自 renderLimit 现有形态（占位符随值渲染）。

### 4.3 D3/D4：文档说明（不实现）

变更记录/项目介绍「已知差异」补充：静态常量引用内联（`IN (1, 2)`）与集合单占位符（`IN (?)`）均为插件静态求值特性，与 MP 运行时文本不同但语义等价。

## 7. 风险与边界

- Fix-1 的 stripGroupFlag 判定必须与 analyzeFlag 同一套「仅 true/false 字面量或占位符」守卫——字符串版列名首参（如 `nested("col", ...)` 非法形态）不可误剥离；无标志形态零回归。
- Fix-2 的 Page 实参解析失败（非 `new Page<>` 形态，如变量传入 Page 实例）→ 不渲染 LIMIT（维持现状），不降级猜测；`page` 方法名下非分页语义的调用（自定义同名方法）由既有守卫（消费集合只认实参引用归属调用名）天然隔离。
- MP 分页拦截器实际是否生效取决于运行环境配置，预览恒按配置方言渲染分页子句（文档化边界，不探测运行时拦截器）。
