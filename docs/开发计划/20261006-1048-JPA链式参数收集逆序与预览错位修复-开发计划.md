# JPA 链式参数收集逆序与 SQL 预览错位修复 — 开发计划

> 2026-10-06 立项（T-JpaParamOrder，占号 O-111/R56/D65/D66/V83）。来源：用户在日常 IDE 反馈「setParameter 参数写重后 SQL 预览的参数不正确了」，附截图（`occupyEmptyTcLocation` 方法，`setParameter("locationStatus","E")` 出现两次，预览渲染五个条件的值全部错位）。
> 本计划基于「截图数值逐位反推 + 代码链路走查」双线结论，问题链路四文件 master 与 dev 零实质差异（SqlPreviewService 的 dev 增量仅在 MP 分页 COUNT 包裹，不触及 JPA 参数链），实施分支建议 dev。

## 1. 问题现象与证据（截图逐位对照）

用户代码：`entityManager.createQuery(hql, Long.class).setParameter(...)` **链式**调用，共 6 次 setParameter、5 个唯一参数名，其中 `locationStatus` 写重两次。代码调用顺序：warehouseId → locationStatus → zoneCode → locationStatus(重复) → emptyFullDegree → positionType。

**参数面板本身是对的**——5 行参数、每行的默认值与代码一致（positionType=TC、emptyFullDegree=0、locationStatus=E、zoneCode=KQ13、warehouseId=1）。

**渲染出的 SQL 全错**，且错位模式与「参数面板行序 × SQL 占位符序」的错切完全吻合：

| SQL 条件（`?` 序） | 配到的参数名 | 值 | 渲染结果 | 正确应为 |
|---|---|---|---|---|
| `warehouse_id`（第1个） | positionType | TC | `'TC'` | 1 |
| `status`（第2个） | emptyFullDegree | 0 | `'0'` | `'E'` |
| `code`（第3个） | locationStatus | E | `'E'` | `'KQ13'` |
| `full_degree`（第4个） | zoneCode | KQ13 | `'KQ13'` | 0 |
| `agv_position_type`（第5个） | locationStatus（重复项） | E | `'E'` | `'TC'` |
| （无第6个 `?`） | warehouseId | 1 | 值被丢弃 | — |

引号规则同样吻合：每位的引号提示按「配到的参数名」判定（如 `status='0'` 带引号是因为 emptyFullDegree 非宿主方法数值参数；若配对正确 warehouseId 是 `Long` 形参，`warehouse_id=1` 应不带引号）。连第 6 项 warehouseId=1 在 SQL 中无处渲染这一细节都对上——**机制链条无剩余疑点**。

附带缺陷（同截图在场）：面板头部显示「表： long」——`createQuery(hql, Long.class)` 的结果类型 `Long.class` 被当成实体类解析，表名显示为 `long`；而 HQL `FROM WmsLocation` 的表名替换反而因 HqlConverter 内部的 project 级实体映射蒙对了（`WMS_LOCATION`）。

## 2. 根因分析

### 根因 1（核心）：链式调用下参数收集顺序 = 代码顺序的逆序

`HqlQueryLocator.locateFromCall`（`psi/jpa/HqlQueryLocator.kt:218-236`）用 `PsiTreeUtil.collectElementsOfType(method.body, PsiMethodCallExpression)` 收集 setParameter 调用。PSI 前序遍历先访问外层节点——而链式写法 `em.createQuery(...).setParameter(a).setParameter(b)...` 的 PSI 是**嵌套**结构：越靠近链尾的调用越在外层。于是收集顺序恰好是代码书写顺序的**逆序**。

本例收集结果：`[positionType, emptyFullDegree, locationStatus(重复), zoneCode, locationStatus, warehouseId]`——参数面板的行序（去重后）正是这个序列，截图即证。

非链式写法（`Query q = em.createQuery(...); q.setParameter(...);` 分语句）各调用在 PSI 中平铺，收集序=文档序=调用序，**不受影响**。单参数链式逆序后仍是自己，也不暴露——这就是既有测试全绿的原因：`PreviewEndToEndTest.testNamedParam_tableNameResolved` 是唯一的链式场景，断言只查「`unresolvedParams.contains("username")`」与表名，从不断言「第 i 个 `?` 配第 i 个参数」。

### 根因 2（放大器）：占位符与参数名纯位置配对，且重复名不撑位

渲染链路：`SqlPreviewService.previewHql`（`ui/SqlPreviewService.kt:896`）把 `info.parameters` 原样 map 成 paramNames（**不去重、6 项**）→ `buildJpaPreviewResult` 透传为 `unresolvedParams` → `SqlPreviewPanel.backfillParamsBySource`（`ui/SqlPreviewPanel.kt:4220`）把**第 i 个 `?` 配 `sources[i]`**，值再按名字查 `paramValues` map（`SqlPreviewPanel.kt:1870` 播种，按名一份）。`ParameterReplacer.buildExecutableSql`（`sql/ParameterReplacer.kt:71`，「复制可执行 SQL」共用）同机制。

位置配对在 MP wrapper / 日志通道上是安全的（sources 与 `?` 天然一一对应）；配上根因 1 的逆序后整体镜像错位，重复参数名再把 sources 撑到 6 项（SQL 只有 5 个 `?`），错位又多滑一格、尾参丢失。面板行数因 `.distinct()`（`SqlPreviewPanel.kt:3354,3380`）显示 5 行正常，进一步掩盖了 sources 实为 6 项的事实。

**推论**：参数「写重」只是放大器，不是必要条件——链式多参数（即使不重复、顺序规范）在现状下渲染也**必然整体错位**。用户这次因为写了重名才注意到。

### 既有兜底为何没接住

T-PSG-04 的 `placeholderReconciliation`（`SqlPreviewPanel.kt:4223`）只对账「`?` 数 vs 参数条数」并在执行前 `warnOnPlaceholderMismatch` 提示、不阻断——预览正文照样渲染错值，且多数用户不会点执行。

## 3. 待验证前提（实施者先证伪再动手）

- **前提 A**：链式下 `PsiTreeUtil.collectElementsOfType` 前序遍历先外后内、收集序=调用序逆序。截图数值反推已强吻合，但需阶段 0 用链式双参数 fixture 直接断言收集序坐实（一行 `assertEquals` 的事）。
- **前提 B**：PSI 元素 `textOffset` 在链式嵌套下严格递增（外层链起点 < 内层各 setParameter 起点），`sortedBy { it.textOffset }` 可无损恢复文档序。条件参数（if 分支内 setParameter）文档序可能与运行时序不同，但静态预览本就无法定运行时序，文档序与现状非链式行为一致，属最合理近似。
- **前提 C**：HqlConverter 转换后 `?` 序 = HQL `:name` 首现序。截图吻合（warehouse_id → status → code → full_degree → agv_position_type 与 HQL 一致），需守卫钉住 JOIN ON 内参数先于 WHERE 的场景。
- **前提 D**：`namedParamHints` 按名替换通道（`ParameterReplacer.replaceNamedParams`，NamedParameterJdbcTemplate 在用）对 HqlConverter 产物兼容（格式化后 `: name` 空格形态 pattern 已容忍）——仅阶段 2 D65 拍板做 F3 时需先验。
- **前提 E**：JPA 规范对同名重复 setParameter 是覆盖语义（后值胜）。面板提示（F5）与文档口径引用该语义时，以 Hibernate 本地 jar 反编译/官方文档为准，不凭印象写。

## 4. 实施方案（分阶段，每步达标即提交）

### 阶段 0：先红复现 + 根因实证（半天）

1. 新建 `HqlQueryLocatorChainOrderTest`（psi/jpa 目录，照 HqlQueryLocatorTest 夹具风格）：链式双参数 fixture 断言 `info.parameters` 收集序（预期现状=逆序，红证前提 A）；非链式分语句 fixture 断言文档序（现绿，F1 后须保持）。
2. 渲染层先红：链式双参数 + 同名写重两用例，经 previewHql → backfillParamsBySource 断言渲染 SQL 中各 `?` 的值（现状必红，作为 F1/F2 的摘修复对照锚）。
3. 产物：读数贴本计划实施记录；两个先红用例即阶段 1 的验收锚。

### 阶段 1：F1+F2 修复（治本，常规改动）

1. **F1 收集序归位**：`locateFromCall` 参数收集循环前对 calls 按文本偏移升序排序（`sortedBy { it.textOffset }`），一处改动、所有出口（previewHql / previewNativeSql / namedQuery / JPQL 常量）一起受益；非链式场景排序幂等。摘掉排序 → 阶段 0 红用例复红（反向验证）。
2. **F2 参数列表去重保序**：JPA 出口 `paramNames + extraParams` 后做保序 distinct，`paramHints` 与之平行，必须同步切分对齐（inClauseParams 是 Set 不受影响）。落点建议 `buildJpaPreviewResult` 入口统一处理，防各出口漏改。
3. 验收：阶段 0 全部红用例转绿；既有 JPA 集成测试（PreviewEndToEndTest / JpaDemoIntegrationTest / HqlQueryLocator 系）零回潮；`warehouseId` 之类的尾参不再被丢弃。

### 阶段 2：可选加固（两处，停等拍板后实施）

1. **F3 渲染改按名配对（D65，推荐做）**：HqlConverter 在 `:name`→`?` 替换点透出「每个 `?` 对应的原始参数名」序列（`inClauseParams` 已有透传先例），`backfillParamsBySource` 优先按名替换（同名 `?` 复用同值，JPA 命名参数语义），缺省回退位置配对——MP wrapper 的合成 param1..N 场景语义不变。这是对「setParameter 顺序 ≠ 占位符顺序」这类非常规代码的语义正解；F1+F2 只保证常规书写习惯下正确。
2. **F5 写重提示（D66）**：面板对「同名参数多次 set」加一行轻提示（JPA 覆盖语义、以最后一次为准），帮用户发现自身代码 bug；不做弹窗、不发新通知组。
3. **F4 表名误判修复（随批）**：`extractEntityInfo` 路径 1（`HqlQueryLocator.kt:356-363`）取得第二参 PsiClass 后校验 @Entity，非实体（Long/Tuple/DTO 投影）不作为实体类返回，让 `resolveHqlTable` 落到按 HQL 实体名解析的既有路径，修「表： long」。注意 DTO 投影类同样命中此路径，校验只影响表名/列信息显示，不触及 SQL 转换。

### 阶段 3：收口

- 定向测试：HqlQueryLocatorTest / HqlQueryLocatorComprehensiveTest / HqlQueryLocatorChainOrderTest（新）/ PreviewEndToEndTest / JpaDemoIntegrationTest / CopyExecutableSqlAction 与 ExecutableSqlFormatter 相关（buildExecutableSql 同源机制断言）。
- 新增守卫：链式收集序守卫（F1 摘除必红）+ 重复名去重守卫（F2 摘除必红），均用真实站点形态做样本，防「守卫看不见要防的站点」。
- 门禁：本计划不触 build.gradle.kts / plugin.xml EP，属常规改动——testFast + 定向即可，全量随下轮收口批。

## 6. 风险与边界

- F1 是行为修正：过去「恰好顺序对」的非链式场景排序幂等不受影响；但若有依赖旧逆序行为的测试断言（理论上不该有，它们只会一直错着），跑定向时暴露后按正确语义修断言，不为保绿回改产品码。
- F3 动渲染配对语义，必须保底「按名失败回退位置」不破既有通道；MP wrapper / foreach / IN 列表等位置语义场景全量走查定向。
- 修复落 dev；在售 v2026.10.6 用户要吃到修复需随下版发行回流 master，窗口与批次归用户拍板（D38 回流批一机制顺路搭载）。
