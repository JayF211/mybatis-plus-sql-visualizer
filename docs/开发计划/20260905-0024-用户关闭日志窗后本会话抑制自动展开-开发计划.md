# 用户手动关闭日志窗后本会话抑制自动展开 开发计划

- **任务ID**：T-AutoShowSuppress
- **立项时间**：2026-09-05 00:24
- **分支**：`feature/m37-competitive-fusion`
- **前置**：M37.3 首条 SQL 自动展开日志工具窗（logAutoOpenOnCapture，默认开，60s 防抖）

## 1. 问题

自动展开决策只看「设置开启 + 距上次展开超 60s」两条件（`SqlLogManager.shouldAutoShow`），没有「用户手动关闭窗口」的记忆。用户嫌占编辑器空间把日志窗关掉后，应用继续跑、SQL 继续捕获，60 秒防抖一过窗口又弹回来，往复循环——典型的「这插件老自己弹窗」差评源，正是 M37.3 想避免的评价类型。

## 2. 方案

用户手动关闭日志工具窗后，**本次项目会话内不再自动展开**；恢复途径两条：重新开启设置开关（显式表达「我要这个行为」），或重启 IDE/重新打开项目（会话自然重置）。

不做的取舍：

- **开始捕捉不解除抑制**：开始捕捉是关于捕获的动作，不是关于窗口可见性的诉求；用户刚关过窗口、知道怎么打开，重新点开始捕捉时窗口又自动弹出反而违背「本会话抑制」的承诺。
- **不改默认值、不动 60s 防抖**：默认开的发现性收益保留（见合并验收讨论），本方案只消灭「关了又弹」循环。

### 2.1 手动关闭检测——平台坑与实证方案

全局记忆 `pitfall-toolwindow-manager-listener`（243 jar 反编译 + joinfw 分支真机实证）：

- 新 UI 关闭/折叠面板时 `ContentManagerListener.contentRemoved` 不触发，必须监听 ToolWindow 可见性；
- `plugin.xml` 不支持 `<listener topic>`，必须 `project.messageBus.connect(...).subscribe(...)` 编程注册；
- 三参 `stateChanged(TWM, ToolWindow, EventType)` 标记 `@Experimental + @Internal`，覆写触发 Marketplace Internal API 违规；
- **两参 `stateChanged(ToolWindowManager)` 是公开 API**，在任何 ToolWindow 状态变化时回调，需自行过滤目标窗口。

本次实现沿用两参方案 + 可见性「转换沿」检测：只在「上次可见 → 本次不可见」沿上认定手动关闭。自动展开自身只调 `show()`（不可见→可见沿），不会造成误判；初值 false，启动布局恢复等中间态不误停。

**243 反编译核实（本次 javap app-client.jar）**：接口 9 个方法全部为 default（无 ACC_ABSTRACT），Kotlin 侧仅需覆写两参 `stateChanged`，其余继承默认实现——与记忆方案一致，可直接落地。

### 2.2 具体改动

| 文件 | 改动 |
|------|------|
| `log/SqlLogManager.kt` | ① `autoShowSuppressedByUserClose` 会话级抑制标志（@Volatile，项目级服务实例字段，重启自然重置）；② `logWindowWasVisible` 可见性沿基准；③ `maybeAutoShow` 传入抑制标志；④ `shouldAutoShow` 纯函数加第三参；⑤ `isUserCloseTransition(was, now)` 纯函数（转换沿判定）；⑥ init 订阅两参 `stateChanged`，沿命中置抑制 + INFO 日志；⑦ SettingsChangeListener 里检测 `logAutoOpenOnCapture` false→true 重启用沿，清除抑制（防止「重开设置不生效」观感缺陷） |

## 5. 风险

- `stateChanged` 在任何 ToolWindow 状态变化时高频回调：回体只有一次 `getToolWindow` + 一次 `isVisible`，O(1)，无性能顾虑（logStopOnToolWindowClose 在 joinfw 分支同模式真机实证）。
- 罕见误判：IDE 布局重排造成瞬时 可见→不可见→可见，会被记一次抑制——后果仅是本会话不再自动弹，用户重开设置即恢复，可接受。
