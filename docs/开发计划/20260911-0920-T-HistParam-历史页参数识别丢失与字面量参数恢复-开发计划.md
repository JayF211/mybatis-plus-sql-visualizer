# T-HistParam 历史页参数识别丢失与字面量参数恢复 开发计划

> 立项：2026-09-11。基线 master 7b4b906。用户报障两个现象：SQL 历史 tab 的 SQL 双击预览永远显示「无未解析参数」，与 SQL 日志 tab 同一条目行为不一致；且一条参数值已内联为字面量的 SQL（附录 A）在 SQL 日志页也不出参数行。本文先给根因的代码级实证，再给改造方案与子任务拆解。

## 1. 问题现象

现象一：SQL 日志 tab 双击条目，预览左栏出现 param1..N 参数行（值预填、可改值重渲染）；同一条目在「SQL 历史」tab 双击，左栏永远是「无未解析参数」。

现象二：附录 A 这类 SQL（`WHERE ("id" = '3254...ba1')`，参数值以字符串字面量内联在 SQL 文本里）在 SQL 日志页双击，同样只显示「无未解析参数」。用户预期是值可以被识别为参数、可编辑后重渲染。

## 2. 根因分析（2026-09-11 代码锚点实测）

### 2.1 现象一：历史页参数识别在三层逐级丢失

日志页的识别管线是这样的：SqlLogPanel.openPreview（SqlLogPanel.kt:1167）调 `LogSqlEntry.toRecognizedPreview()`（LogEntryPreviewRecognizer.kt:36），以「rawSql 中 `?` 占位符数（string-aware 计数）== params.size 且 > 0」为识别条件；识别成功则 unresolvedParams 填 param1..N、initialValues 填日志参数值、paramHints 带引号提示，预览面板据此重建参数行（SqlPreviewPanel.kt:1801 buildParamRow）。

历史页在同一条管线上三层断裂：

- L1 写入端：SqlLogAutoSaver.writeEntry（SqlLogAutoSaver.kt:131）落盘格式为头部注释行加 `withTerminator(entry.restoredSql)` 正文，rawSql 与 params 完全不落盘，只存值已内联的最终 SQL。
- L2 读取端：SqlLogFileReader.parseBlock（SqlLogFileReader.kt:113）重建条目时硬置 `rawSql = sql, restoredSql = sql, params = emptyList()`（130 行与 145 行两个分支同病）。文件格式本身没有参数位。
- L3 展示端：HistorySqlLogPanel.openPreview（HistorySqlLogPanel.kt:271）硬编码 `unresolvedParams = emptyList()`、`warning = null`，从头到尾没碰过 toRecognizedPreview。

也就是说，即使 L1/L2 存下了参数，L3 也不会用；反过来只修 L3，读回的条目 params 恒空，识别照样失败。三层必须一起修。

### 2.2 现象二：字面量 SQL 没有任何识别通道

用户那条 SQL 进入日志页的路径：rawSql 全文不含一个 `?`。捕获侧完全可能如此——HibernateLogParser 开了 `recognizeBareSql = true`（HibernateLogParser.kt:36），行首即 SELECT/INSERT/UPDATE/DELETE/MERGE/WITH 的裸 SQL 行直接进收集态建条目，参数绑定行是唯一 params 来源；上游日志若本身已把值内联进 SQL 文本（裸 SQL 形态输出、MyBatis `${}` 字面量替换后 Preparing 行带值且无 Parameters 行等），产出的条目就是 rawSql 带字面量、params 空。

识别侧随后整体失活：countPlaceholders(rawSql) == 0 导致 recognized=false（LogEntryPreviewRecognizer.kt:38），走回退分支展示 restoredSql；警告分支只在 `countPlaceholders(restoredSql) > 0` 时给文案（SqlLogPanel.kt:1187），零 `?` 连警告都没有；最终 unresolvedParams 为空，预览面板落到 panel.param.none「无未解析参数」（SqlPreviewPanel.kt:1740）。

这也解释了用户截图的形态：预览里既没有 `?` 残留也没有警告横幅——若是「数量不匹配」回退，restoredSql 必然残留 `?` 且带 unresolvedWarning 警告；零警告加零占位符，唯一的解释就是捕获原文本身没有占位符。字面量值明明就写在 SQL 里，插件却没有任何一条通道把它当成参数。

### 2.3 一点判别上的澄清

两个现象不是同一个 bug。现象一是「有参数信息但层层丢弃」，现象二是「条目本身就无参数信息且无恢复手段」。但修复后两者汇聚到同一条体验：日志页与历史页的参数识别行为一致。字面量恢复（§3.3）做成识别层的公共通道后，历史页读回的字面量条目自动同样受益。

## 3. 技术方案

### 3.1 F1 历史文件格式 v2：参数持久化

历史文件（.idea/sql-visualizer/sql-history/*.sql）保持 F-43 初心——正文是可直接在数据库工具打开执行的可执行 SQL。v2 在头部注释行之下新增一行机器读的注释行：

```
-- source: src/.../UserMapper.java:42 | time: 3ms | 2026-09-11 09:00:00.123 --
-- pd: <base64> --
<withTerminator(restoredSql)>
```

payload 为 UTF-8 JSON `{r: rawSql, p: [[value, type], ...]}`（value 可为 null）的 Base64 编码，项目已有 Gson 可直接复用。选 Base64 加单行注释的理由：参数值可能含 `|`、逗号、`--`、括号甚至换行等任意文本，明文分隔符方案必然引入转义歧义；Base64 字符集与现有解析正则零冲突，单行形态不会破坏 countInFile 的头部行计数判据（SqlLogFileReader.kt:58 只看头部行）。写入条件：`params.isNotEmpty() || countPlaceholders(rawSql) > 0`，纯静态 SQL 条目维持现状两行形态。

前向兼容是选这个形态的决定性理由：已发行旧版本插件的 Reader 正则锚定行尾（SqlLogFileReader.kt:26 `--+$`），遇到带 pd 行的文件会把 pd 行并进 SQL 正文——结果只是 SQL 前多一行注释，展示冗余但可执行性不破坏，回滚场景安全。若把参数塞进头部行本体，旧正则整条解析失败会直接丢条目，不可接受。

### 3.2 F2 读取端重建完整条目

parseBlock 在识别头部行后探测紧随其后的 pd 行（严格 `-- pd: ` 前缀加 ` --` 结尾），解码出 rawSql 与 params 填入条目；restoredSql 继续用正文原文而不重新计算——restorer 的引号规则可能随版本演进，重算会让正文漂移，写入什么读回就是什么。解码或 JSON 解析任何一步失败，pd 行按普通正文行处理（后果仅多一行注释，且需同时满足头部行后紧跟合法 pd 前缀才可能触发，误判面趋近于零）。旧格式文件无 pd 行，行为与现状完全一致。

### 3.3 F3 展示端识别通道统一

SqlLogPanel.openPreview 的双分支逻辑（识别成功填参数、回退分支按零参数与数量不匹配分流 unresolvedNoBinding/unresolvedWarning 文案，SqlLogPanel.kt:1172-1197）整体抽为公共函数，建议落位 LogEntryPreviewRecognizer：`LogSqlEntry.toPreviewResult(formatSql: Boolean)`。SqlLogPanel 传现状的 `state.logFormatSql`，行为零变化；HistorySqlLogPanel.openPreview 删掉硬编码改调此函数，传 false 保持历史页现状不格式化。

v2 条目读回后 params 与 rawSql 齐全，toRecognizedPreview 自然识别成功，历史页参数行与日志页对齐。单击轻量预览（SqlClickPreview）是纯文本弹窗，不在本次范围。

### 3.4 F4 字面量参数恢复：识别层的第二通道

核心思路是把字面量 SQL 在预览识别时改写成等价的占位符形态，从而整体复用现有参数管线——面板的参数行、值编辑、ParameterReplacer 回填、重渲染一行都不用动。

识别器建议新文件 log/LiteralParamRecovery.kt：string-aware 扫描 rawSql（状态机形态与 placeholderPositions 一致，LogSqlRestorer.kt:97，跳过 `--` 行注释、块注释与字符串内容），定位全部单引号字符串字面量；把每个字面量原位改写为 `?` 得到占位符化 SQL，param1..N 对应，initialValues 存字面量原文（`''` 转义还原为单引号），paramHints 全部 quote=true。字面量场景下值天然是字符串，与 paramHints 机制对齐。

接线点：toPreviewResult 的回退分支内，当 `countPlaceholders(rawSql) == 0` 时先尝试字面量恢复，命中则按识别成功形态产出；数量不匹配（残留 `?`）场景维持现状警告，不做两套占位符的混合恢复。捕获侧已有 params 但零占位符的条目同样走字面量恢复，被捕获的绑定参数不参与（现状回退里它们本来也无处可用）。

逐字符一致性校验作为运行期熔断，不只是测试断言：改写后用初值经 replacer 引号规则渲染，结果必须与 rawSql 原文逐字符一致，不一致则整条放弃恢复维持现状。这一条兜住扫描器的方言盲区——比如现有状态机只认 `''` 转义不认 MySQL 反斜杠转义（`'a\'b'` 会错切），与其扩方言不如让一致性校验统一兜底。

范围控制三条：

- 上限熔断：字面量数超过阈值（建议 32，实施可调）不启用，防止 IN 大列表生成上百参数行。
- 只识别单引号字符串字面量。双引号标识符（`"id"`）走的是另一套引号体系天然不误伤；数值与布尔裸字面量噪音大（LIMIT/OFFSET/投影常量），一期不做。
- 设置开关 PluginSettings.literalParamRecovery 默认开启。新增复选框必须同步 PluginSettingsPersistenceTest 计数（复选框总数台账教训）。

### 3.5 与「模型派生视图」语义的相容性

预览编辑器是模型派生视图（T-PreviewDisplayMode 已确立：showSql 全量重建）。字面量恢复改写的是 PreviewResult.sql 模型，初值回填后初始显示与原字面量逐字符一致（T-M42 同款要求），用户改值即重渲染，与既有语义完全一致；日志列表条目本身不动——识别发生在预览时，restoredSql、去重指纹、摘要都不受影响。

同一捕获条目在 SQL 日志 tab 与 SQL 历史 tab 双击预览，参数行数量、预填值、改值重渲染行为一致。附录 A 的 SQL 在两页均出现参数行，值默认 `3254...ba1`，改值后 SQL 同步替换。旧格式历史文件读取行为不变。全量测试绿，设置计数同步。

## 8. 风险总表

- pd 行被旧版插件并进 SQL 正文（回滚场景）：展示多一行注释、可执行性不破坏，接受并记录。
- 字面量改写后初始渲染与原文漂移（方言转义盲区）：运行期逐字符一致性熔断兜底，不一致即放弃恢复。
- 空串字面量 `''` 与 M12 空值输入语义的边界：实施时核实空串初值能否渲染回 `''`，冲突则跳过空串字面量。
- IN 大列表参数行爆炸：上限熔断。
- 历史文件体积增大：仅带参条目多一行 Base64（约 1.33 倍 rawSql 加 params 长度），可接受。
- 识别通道统一误伤日志页现状行为：公共函数参数化格式开关，日志页传现状值，既有 SqlLogPanel 测试守护。

## 9. 不做清单

- 数值字面量的全量识别（LIMIT/OFFSET/投影常量噪音大）与布尔裸字面量识别——数值已二轮扩面为谓词语境限定（见变更记录），布尔仍不做。
- IN 列表参数折叠合并。
- 残留 `?`（数量不匹配）场景的字面量混合恢复。
- 单击轻量预览的参数行。
- F-7 SqlHistoryPanel 的参数化：其独立工具窗注册已注释下线（plugin.xml「SQL 历史记录已合并到主侧边栏 tab」），SqlPreviewService 仍在写快照数据但无用户可见入口，不投入。
- 历史文件格式的对外契约承诺（.idea 内部数据文件，发行说明可提一句，不作兼容承诺）。

## 变更记录

- 2026-09-11：立项。根因实证三层丢失链（SqlLogAutoSaver.kt:131 / SqlLogFileReader.kt:130 / HistorySqlLogPanel.kt:271）与字面量识别通道缺失（LogEntryPreviewRecognizer.kt:38 零占位符失活），方案定稿格式 v2 加识别通道统一加字面量恢复。
- 2026-09-11 实施期 refinement（反斜杠歧义片段）：原方案假设「逐字符往返熔断」能兜住 MySQL 反斜杠转义盲区，实测证伪——`'don\'t'` 被扫描器错切出尾反斜杠片段 `don\` 后，引号渲染（`'don\'`）恰能逐字符重组原文，熔断通过但畸形值进了参数模型，改值即产出坏 SQL。修正为识别器显式跳过以反斜杠结尾的歧义片段（LiteralParamRecovery candidates 过滤），逐字符熔断保留为纵深防御（防其他未知盲区）。另实施中发现两处方案未覆盖的坑已修：Reader 的 countInFile 与 parseContent 旧头部判据（`-- ` 起始无 source:）会把 pd 行误判为 F-43 头部，块被劈开且计数翻倍，须显式排除；预览面板回填按 `?` 字符朴素替换（backfillParamsBySource），改写后 SQL 若残留非参数 `?`（注释内）回填必错位，恢复前加 naive `?` 计数守卫。
- 2026-09-11 二轮扩面（数值字面量）：用户追加反馈 `WHERE (t.id = 1)` 数值谓词仍无参数行——一期只认单引号字符串的口径漏掉数值。扩面为谓词语境限定的数值识别：前一 token 是比较运算符（`= != <> > < >= <=`，`= -1` 负号保留比较上下文、负号留原文随 `-?` 往返无损）、IN 列表与 VALUES 列表括号内、BETWEEN 双界。LIMIT/OFFSET/SELECT 投影/函数实参/EXISTS 子查询常量仍不识别——MP 分页查询 LIMIT 恒为字面量，全量识别会给每条分页查询加噪音参数行（这是不做全量数值的根因）。非纯数字 token（`1abc`/`0x1F`/`1E5` 后随词字符）不识别；多行 VALUES 第二行起不识别（列表闭合不重臂，保守）。布尔裸字面量仍不做。
