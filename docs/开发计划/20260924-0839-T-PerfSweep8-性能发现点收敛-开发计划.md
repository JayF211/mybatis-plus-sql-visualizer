## 一、背景与依据

第十一轮报告 §5 交出 **4 低 + 2 文档缺口**，全部为登记性质，无中低头号——本轮动态代理化整改（Marketplace 审核响应）的成本形态经审计确认健康（启动期一次性 + 会话/清单刷新级微秒），无需救火。本计划只收：**零风险快件包 1 个任务（2 件）** + **两个维持/观察决议的决策点（D1/D2）** + **4 项登记不做**（§五）。计划规模小于 PS7。

## 二、现状核实（立项前形态核实，2026-09-24 实测，一路只读子代理 + 主控复核）

1. **【成本高估修正】发现 1 的补缓存是十分钟级**：测试缝现成——`AcpTransportRegistrarProxyTest.kt:33` 注入自有 sseProvider，生产侧缓存零触面；仓内有同款先例（`SqlLogConsoleBridge.kt:674-687` `methodCache` ConcurrentHashMap 找不到也缓存 null，T-LogPerf-02；`:467-484`「挂载时解析一次」F1）；我方支持免重启热替换（T-DynUpdate），热卸载时旧 loader 连 companion 缓存整体丢弃，**我方更新不产生陈旧 Class**；ml-llm 自身动态卸载/更新的滞留风险为理论残余（仓内既无论述也无反例，插件更新通常重启）。
2. **【口径修正】发现 2 的调用频率证据出处**：「平台每次清单刷新重走 applyFilters」的原文在桥 KDoc `McpGateFilterEpBridge.kt:28-29`，不在 mcpStub 桩（桩只有设置页以 clientInfo=null 调用的路径证据 `:31-36`）——报告 §4.2 原出处标注不准，已随本批订正。**核实补充**：谓词代理无状态（`:81-89` 只引用参数与静态目标，不捕获 context）→ 谓词代理/Function1 Class/updateState Method 三者可提 companion 单例，且缓存不冻结门控设置状态（谓词每次 invoke 现查 `McpToolGate` 决策核）；但桥有 20260923 空源性 NPE 前科（`:33-40` 全路径判空纪律），「首次查找失败是否缓存 null」是新增决策面。
3. **【新事实，报告 §5-4 已随本批订正】发现 4 的「改单触发」被证伪**：EP 主捕获通道 `SqlConsoleBridgeFilterProvider.EpLineFilter` 持有**私有** BridgeLineContext（`:43-62`），不在桥的 consoleContexts 注册表（注册点仅 `SqlLogConsoleBridge.kt:341`），而 `flushSettledEntries` 只遍历 consoleContexts（`:445`）——**EP 通道的静默冲刷今天只有逐行触发这一条路**，「逐行只 touch、冲刷只靠每拍」会让 M56 后的主通道在应用安静后退回「已扫描 N 行/产出 0 条」，O-70 的用户可见收益在主通道归零；单触发的隐藏前置「EP ctx 入可轮询注册表」是跨线程改造（须引入 `:386`/`:393`/`:447` 同款 synchronized 互斥）。
4. **【4b 改动面钉死】mcp-filter-optional.xml 全仓引用三处**：`McpToolGate.kt:16`、`McpConfigurable.kt:31` 两处**注释失实**须改；`McpGateFilterRegistrationGuardTest.kt:29` 是「断言该文件不存在（改走探测式注册）」的**防回流守卫，不是残留，不动**。
5. **T-PS8 代号无占用**（`git log --all --grep T-PS8` 零命中、计划目录无同名件）；写集四文件均无在册任务碰撞。

## 三、方案

### T-PS8-01 低危快件包（2 件）

- **4a AcpTransportRegistrar 反射缓存与注释对齐（报告发现 1）**
  - **落点**：`AcpTransportRegistrar.kt:80`（sseProvider 每次 `Class.forName(TRANSPORT_ENUM_FQN).getField("SSE").get(null)`）、`:99`（`getMethod("getFullId")` 现查）、`:25`（KDoc「首次 getTransport 时解析并缓存」失实）。
  - **方案**：companion 加 `@Volatile private var cachedSse: Any?`——首次解析成功缓存枚举常量（`getField(...).get(null)` 返回 static final 枚举常量，JVM 语义每类加载器单实例，缓存即缓存天然单例）；解析失败不缓存、维持现有 runCatching→throw 路径；`getFullId` 的 Method **保留现查**（上游两条发行线的 agentId 运行时类可能不同，按类键单槽的复杂度不值当，频率会话级）；`:25` 注释改为如实描述（SSE 常量已缓存 / getFullId 现查）。
  - **验收**：新增缓存命中用例，先红后绿——缓存实现退回（恢复每次现查）时解析计数=2 即红，有缓存则=1；`AcpTransportRegistrarProxyTest`/`AcpTransportIsolationTest` 保持绿。测试缝设计见 §八-1。
- **4b 门控注册注释残留修正（报告发现 3）**
  - **落点**：`McpToolGate.kt:16`、`McpConfigurable.kt:31`。
  - **方案**：两处注释的「mcp-filter-optional.xml 以 since-build=262 门控」改为如实形态——「注册走 `mcp-optional.xml` 的 postStartupActivity 探测式（262+ 命中 / 253 静默跳过，见 `McpGateFilterRegistrar`）」；守卫测试 `:29` 不动。
  - **验收**：纯注释，编译绿 + `McpGateFilterRegistrationGuardTest` 绿；收口时全仓 grep `mcp-filter-optional` 仅剩守卫断言与历史叙述文档（判别法见 §六-3）。

**D1（报告发现 2）：McpGateFilterEpBridge 反射是否现在补缓存？——待定案**

## 六、风险

1. **4a 的可选依赖边界**：ml-llm 动态更新而本插件未重启时，缓存的枚举常量属旧 loader——理论残余（仓内既无论述也无反例）；失败路径 runCatching→warn 与现查行为一致，可接受。
2. **4a 新增测试缝面**：`cachedSse` 的 clearForTest/解析计数是新 internal 面，仓内自用（沿 `InsertColumnInlayPlanCache` 的 `clearForTest`/`planInvocationCount` 先例），不涉跨版本签名护栏。
3. **4b 是活文档修正，有判别法**：`McpToolGate.kt:16`/`McpConfigurable.kt:31` 描述注册机制现状＝功能性引用，须改净；`McpGateFilterRegistrationGuardTest:29` 守卫断言与历史计划文档（T-McpGateDynamicFilter 计划、全景盘点）里的叙述性引用**不改**（改掉反而失真）。
