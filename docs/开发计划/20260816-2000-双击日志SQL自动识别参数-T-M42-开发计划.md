## 2. 现状代码分析（已逐行核实）

### 2.1 数据源：日志条目本就带完整参数信息

`log/LogSqlModels.kt` 的 `LogSqlEntry` 同时持有三份数据：

```kotlin
data class LogSqlEntry(
    val rawSql: String,          // Preparing 原文：WHERE (username = ?)
    val restoredSql: String,     // 还原后可执行 SQL：WHERE (username = 'admin')
    val params: List<LogSqlParam>, // [LogSqlParam(value="admin", type="String")]，与 `?` 按序对应
    ...
)
```

**结论：不需要从 SQL 文本反猜字面值**——值、类型、位置全部来自日志 Parameters 行（`log/LogSqlRestorer.kt` 已实现 `?` 按序替换，`PLAIN_TYPES` 集已定义数值/布尔直出、其余引号的类型判定）。双击链路 `SqlLogToolWindowFactory.openPreview`（259-280 行）只用了 `restoredSql`，把 `params` 丢弃了。

### 2.2 面板回填机制（可完全复用）

`ui/SqlPreviewPanel.kt` 旧文本渲染路径（356-360 行）：

```kotlin
val base = if (compactMode) result.compactSql else result.sql
showSql(backfillParamsBySource(base, result.unresolvedParams, result.paramHints))
```

`backfillParamsBySource` 按 `?` 出现顺序替换为 `paramValues[source]` 渲染值（`renderParamValue`：String 恒引号 / 数值启发式 / LIKE 拼 % / IN 逗号分割）。**只要给出 `unresolvedParams` + `paramHints` + 预填 `paramValues`，识别即完成**。

### 2.3 参数行初始值缺口

`showResult`（248-288 行）初始化参数值：

```kotlin
result.unresolvedParams.forEach { source -> paramValues.putIfAbsent(source, "") }
```

初始值恒为空字符串——日志路径要预填日志值，需要一个初始值载体。`PreviewResult` 目前无此字段（`model/PreviewResult.kt` 已读，字段清单见 KDoc）。

### 2.4 匹配判定：与还原器语义天然自洽

`LogSqlRestorer.restore` 内部就是 `indexOf('?')` 顺序替换（参数多则忽略、参数少则残留 `?`）→ **`rawSql` 中 `?` 数 == `params.size` ⇔ `restoredSql` 无残留 `?`**（等价于现有 warning 条件 `'?' in entry.restoredSql`）。匹配即识别、不匹配即回退，无需新判定机制。

### 2.5 列表 Ctrl+C 复制 HTML 的机制（已反编译实证，243 jar）

JBList（`com.intellij.ui.components.JBList`）**内置 Ctrl+C 复制**：`installDefaultCopyAction()` 注册的复制动作 → `protected doCopyToClipboardAction()` → 遍历选中项调 **`protected String itemToText(int index, E element)`** → `StringUtil.join("\n")` → `CopyPasteManager.setContents(StringSelection)`（javap 字节码实证 243.28141.41）。

`itemToText` 默认实现返回 **cellRenderer 的渲染文本**——本面板 cellRenderer（`SqlLogToolWindowFactory.kt:187-208`）输出 `<html>...` 着色片段 → 复制的就是 HTML 源码（用户粘贴实证）。

**修复点：继承 `JBList<LogSqlEntry>` 覆写 `itemToText(index, element)` 返回 `withTerminator(element.restoredSql)`**——protected 钩子即官方扩展点，其余复制链路（多选换行拼接、CopyPasteManager 写入、Ctrl+C 快捷键注册）零改动复用；且与右键菜单「复制」（`log.panel.copy`，复制 `withTerminator(restoredSql)`）内容一致。`withTerminator` 提为伴生/模块级函数供两处共用。

### 2.7 调用类形态机制（需求 4，已逐行核实）

`SqlToJavaPanel.kt:141 callerField`（ClassPickerField，弹 Goto Class 选择器选 PsiClass；`text` property 公开，测试 `pickForTest` 直写）→ `callerField.text` 进 `InvocationTarget(callerClass, voClass, mpj)`（JavaCodeGenerator.kt:45）→ 生成器三处消费：
- `callerVar`（214 行）= 类名首字母小写（`UserService` → `userService`）——调用对象变量名；
- `isMapper`（608 行）= `endsWith("Mapper")`——mapper 形态（`selectList/selectPage/insert/update(null,…)/delete`）vs service 形态（`list/page/save/update(wrapper)/remove/saveBatch`）；
- `invocationHasMpj`（SqlToJavaConverter.kt:52）= 类名经 `PsiShortNamesCache` 反查 + 继承链匹配 MPJ 接口（`MPJBaseService/JoinService/MPJBaseMapper/JoinMapper`，1.5.6 jar javap 实证）——false 时 JOIN 直接报错（98 行）、VO 回落实体查询。

### 2.8 serialVersionUID 问题定位（需求 5，已逐行核实）

- `psi/EntityResolver.kt` `resolveColumn`（92-129 行）：**不过滤 static 字段**——实体的 `serialVersionUID` 被当作普通列（`columnName = NamingStrategy.toSnakeCase("serialVersionUID")` = `serial_version_uid`），进入 `TableInfo.columns` → `columnToField`（SqlToJavaConverter.kt:108/139、SqlToJavaPanel.kt:681 三处构建点全部源于此）；
- 用户 SQL 列名 `serial_version_u_i_d`（UID 逐字母拆分形态）与 `serial_version_uid`/`serialVersionUID`/`SERIAL_VERSION_UID` 归一化（小写+去下划线）后**都等于 `serialversionuid`**——单一匹配规则全覆盖；
- 生成路径：有实体（Lambda 模式）→ `columnToField` 命中 → `User::getSerialVersionUID`（renderColumnRef 622 行）→ **编译失败**（serialVersionUID 无 getter）；无实体 → 回落字符串列名（不炸但语义为序列化 ID，查询无意义）；
- 正向链路同样问题：实体 SELECT 全列展开（`table.columns`）含 `serial_version_uid` 列（MP 官方跳过 static 字段——对齐修复）；
- 用户示例 SQL 的反引号表名（`` FROM `user` ``）已支持（SqlTokenizer.kt:54-55 标识符词形）——无需处理。

## 3. 方案设计

### 3.1 核心：识别器（新文件 `log/LogEntryPreviewRecognizer.kt`，纯逻辑可纯测）

```kotlin
data class RecognizedLogPreview(
    val sql: String,                 // rawSql + ';'（格式化由 openPreview 按设置做）
    val compactSql: String,          // rawSql + ';'
    val unresolvedParams: List<String>,   // ["param1", "param2", ...] 按 `?` 出现顺序；未识别为空
    val initialValues: Map<String, String>, // "paramN" -> 日志值（null 参数预填空串）
    val paramHints: List<ParamHint>,       // 与 unresolvedParams 并行
    val recognized: Boolean,         // true=匹配识别；false=回退现状
)

fun LogSqlEntry.toRecognizedPreview(): RecognizedLogPreview
```

判定与装配规则：

1. `placeholderCount = rawSql.count { it == '?' }`（裸计数，与 `LogSqlRestorer` 的 indexOf 语义一致——字符串字面量内的 `?` 同语义对待，不额外解析）；
2. `recognized = placeholderCount > 0 && placeholderCount == params.size`；
3. 识别时：`unresolvedParams = (1..n).map { "param$it" }`（日志无参数名，用序号命名，对齐 MP 生成器 `param1` 风格）；`initialValues` = 按序取值（`LogSqlParam.value`，null → `""`，回填显示 `?`——边界见 §7）；`paramHints` = 类型映射（见 3.2）；
4. 未识别（params 空 / 数量不匹配 / 无 `?`）：`sql`/`compactSql` 由调用方回退 `restoredSql`（现状），`recognized = false`。

### 3.2 类型 → ParamHint 映射（`log/LogSqlRestorer.kt` 内新增）

复用 `LogSqlRestorer` 的 `PLAIN_TYPES`（提为 `internal` 单源，不复制）：

```kotlin
/** 日志参数 → 回填提示：数值/布尔原样，其余引号（对齐 LogSqlRestorer 还原语义）；无类型标注走面板启发式。 */
internal fun LogSqlParam.toHint(): ParamHint = when {
    type == null -> ParamHint()
    type in PLAIN_TYPES -> ParamHint(quote = false)
    else -> ParamHint(quote = true)
}
```

回填后初始显示与 `restoredSql` 逐字符一致（`'admin'`、`10`、`true`、`'2026-08-01'`），用户无感变化；改值才生效。

### 3.8 需求 4：调用类支持 `this` / `baseMapper`

**4.1 生成器（`reverse/JavaCodeGenerator.kt`）**：

```kotlin
/** 特殊调用值直出（this=service 内调用、baseMapper=ServiceImpl 字段），普通类名首字母小写。 */
private fun callerVar(invocation: InvocationTarget): String = when (invocation.callerClass) {
    "this", "baseMapper" -> invocation.callerClass
    else -> invocation.callerClass.replaceFirstChar { it.lowercaseChar() }
}

private fun isMapper(invocation: InvocationTarget): Boolean = when (invocation.callerClass) {
    "baseMapper" -> true
    "this" -> false

}
```

### 3.9 需求 5：serialVersionUID 默认忽略（两层过滤）

**层 1 源头（`psi/EntityResolver.kt` resolveColumn）**：字段名归一化匹配跳过——与 `@TableField(exist=false)`/ignoredFields 同级（返回 null）：

```kotlin
// serialVersionUID（static final 序列化字段，无 getter/setter，MP 官方不映射为列）默认忽略——
// 归一化匹配覆盖 serial_version_uid / serial_version_u_i_d / serialVersionUID 等全部形态
if (fieldName.lowercase().replace("_", "") == "serialversionuid") return null
```

正向（SELECT 全列展开/批量面板/补全）与反向（columnToField）统一受益。

**层 2 生成兜底（`reverse/JavaCodeGenerator.kt`）**：无实体/未映射路径仍可能遇到该列名——渲染入口统一过滤（剥反引号与别名前缀后归一化匹配）：

```kotlin
/** serialVersionUID 系列列名（归一化：小写+去下划线）默认忽略——序列化字段非业务列。 */
private fun isIgnoredColumn(expr: String): Boolean =
    expr.substringAfterLast('.').trim('`').lowercase().replace("_", "") == "serialversionuid"
```

过滤点（跳过，不生成引用）：
- SELECT 列清单（generateSelect 的 isJoin 与单表两分支的 `selectColumns` 渲染，`renderSelectColumn` 调用前）；
- WHERE 条件列（renderCondition 的 Simple/In/Between/Like/Unary——列名命中即跳过该条件）；
- ORDER BY 列（renderOrderBy 前过滤）；
- INSERT 列（generateInsert 的 `insertColumns` 渲染前过滤）；
- UPDATE SET 列（generateUpdate 的 `sets` 渲染前过滤）。
全部列被过滤（SELECT 仅含该列）→ `selectColumns` 空 → 现有 `isNotEmpty()` 分支自然回落（不生成 select 调用，MP 全列语义）。

**边界（文档化）**：不扩展 static/transient 通用过滤（超出本次反馈范围，EntityResolver 其余 static 字段行为不变，留待后续）；无实体场景该列同样跳过（字符串列名虽可编译但查询序列化 ID 无业务意义，用户明确要求默认忽略）。

## 7. 风险与实证注意

- **null 参数边界**：日志 `null` 参数（还原为 `NULL`）在识别路径预填空串 → 回填显示 `?`（与还原 `NULL` 不一致）——MyBatis 日志 null 绑定罕见且运行语义本就无行返回，接受并文档化，不特殊处理；
- **字符串内 `?`**：计数用裸 `count { '?' }`，与 `LogSqlRestorer` 替换语义一致（现存行为，不做 SQL 词法解析）；
- **`itemToText` 跨版本**：243 jar 已 javap 实证 protected 签名；实施时对 253/262 实证，缺失则回退覆写 `doCopyToClipboardAction()`（同为 protected 钩子，263 平台亦稳定存在多年）；
- **`withTerminator` 提级**：从 `SqlLogPanel` 私有方法提为伴生 internal，三处共用（openPreview / 右键复制 / itemToText），行为不变（空串与已有 `;` 不重复追加）；
- **createEditor ReadAction**：EDT 上 ReadAction.compute 同步执行、语义不变；Light 测试环境路径一致（现有 SqlPreviewPanelTest 回归即验证）；
- **特殊值 MPJ 能力**：`this`/`baseMapper` 恒视为具备 MPJ 能力（无法反查类）——单表查询生成普通方法不受影响；JOIN/VO 生成 MPJ 方法族，无 MPJ 依赖的项目编译不过属用户显式选择边界（文档化，与普通类无 MPJ 时 JOIN 报错策略并列说明）；
- **serialVersionUID 过滤影响面**：`EntityResolver.resolveColumn` 加过滤后，`SqlPreviewServiceTest`（fixture 含 serialVersionUID，grep 实证）等既有断言可能需同步；过滤为默认忽略语义（用户要求），不提供开关（后续如需可加设置项）；static/transient 通用过滤不在本次范围；
- **并行合并风险**：C（需求 5）与 B（需求 4）共享 `JavaCodeGenerator.kt`——两 worktree 各自独立开发，主控合并时按「先 B 后 C」应用 patch，函数级不重叠（B 改 callerVar/isMapper、C 改渲染过滤），冲突时手工合并；
