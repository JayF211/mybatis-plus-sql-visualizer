# HQL/JPA SQL 日志捕获支持

> 创建日期：2026-08-21
> 状态：**计划中**
> 优先级：**P0**（功能缺失——用户运行 Hibernate/JPA 项目时 SQL 面板完全无法捕获）

## 1. 问题描述

### 1.1 现象

用户项目使用 Hibernate/JPA（Spring Data JPA / 原生 Hibernate）时，SQL 日志面板**无法捕获任何 SQL**。仅 MyBatis-Plus 项目能正常捕获。

### 1.2 根因分析

当前 SQL 捕获管线**完全围绕 MyBatis 日志格式设计**：

```
Console Output → SqlLogConsoleBridge（Filter 代理）
  → MyBatisLogParser（配对 Preparing: / Parameters: 行）
  → LogSqlRestorer（还原 ? 占位符）
  → SqlLogEntryBuffer → SqlLogPanel
```

Hibernate/JPA 的日志格式与 MyBatis 截然不同，整个管线无法识别：

| 维度 | MyBatis（当前支持） | Hibernate/JPA（不支持） |
|------|---------------------|------------------------|
| SQL 行格式 | `==> Preparing: SELECT ...` | `Hibernate: select ...` 或 `/* load Entity */ select ...` |
| 参数行格式 | `==> Parameters: 1(Long), abc(String)` | `binding parameter [1] as [BIGINT] - [1]` |
| 参数聚合 | 单行内全部参数 | 每参数一行，带索引 `[N]` |
| 类型标注 | Java 类型名（Long, String） | JDBC 类型名（BIGINT, VARCHAR） |

### 1.3 Hibernate 日志格式详解

用户需在 `application.yml` / `logback-spring.xml` 中配置以下日志级别：

```yaml
# 必要：输出 SQL
spring.jpa.show-sql: true
# 或
logging.level.org.hibernate.SQL: DEBUG

# 可选：输出参数绑定（TRACE 级）
logging.level.org.hibernate.type.descriptor.sql.BasicBinder: TRACE
```

**实际输出示例：**

```text
// 场景 1：show-sql=true（仅 SQL，无参数）
Hibernate: select user0_.id as id1_0_0_, user0_.name as name2_0_0_ from users user0_ where user0_.id=?

// 场景 2：SQL + BasicBinder TRACE（SQL + 参数）
/* load com.example.User */ select user0_.id as id1_0_0_, user0_.name as name2_0_0_ from users user0_ where user0_.id=?
binding parameter [1] as [BIGINT] - [1]

// 场景 3：更新语句
/* update com.example.User */ update users set name=? where id=?
binding parameter [1] as [VARCHAR] - [John Smith]
binding parameter [2] as [BIGINT] - [1]

// 场景 4：批量插入
insert into users (name, email, id) values (?, ?, ?)
binding parameter [1] as [VARCHAR] - [Alice]
binding parameter [2] as [VARCHAR] - [alice@example.com]
binding parameter [3] as [BIGINT] - [100]

// 场景 5：Criteria 查询
/* criteria query */ select ... from ... where ...
binding parameter [1] as [INTEGER] - [18]
binding parameter [2] as [INTEGER] - [60]

// 场景 6：JOIN 查询
/* load com.example.Order */ select ... from orders o0_ left join users u1_ on o0_.user_id=u1_.id where o0_.id=?
```

### 1.4 核心差距

| 差距 | 说明 |
|------|------|
| **无 Hibernate 日志解析器** | `MyBatisLogParser` 硬编码 MyBatis 前缀，无法识别 Hibernate 格式 |
| **参数格式不匹配** | Hibernate 使用 `binding parameter [N] as [TYPE] - [VALUE]` 单参数单行格式，与 MyBatis 的 `Parameters: v1(Type1), v2(Type2)` 完全不同 |
| **类型系统差异** | Hibernate 使用 JDBC 类型名（BIGINT, VARCHAR, TIMESTAMP），`LogSqlRestorer.PLAIN_TYPES` 仅有 Java 类型名 |
| **SQL 行前缀多样** | `Hibernate:` 前缀、`/* comment */` 注释前缀、或无前缀（纯 SQL 行） |

## 2. 技术方案

### 2.1 设计决策

**决策 A：独立解析器 vs 扩展现有解析器**

选择**独立 `HibernateLogParser` 类**，与 `MyBatisLogParser` 并列：
- 理由：两种日志格式的解析逻辑差异显著（参数聚合方式、类型系统、前缀模式），强行合并会引入大量分支条件，降低可读性
- 复用：共享 `LogSqlEntry` 数据模型和 `SqlLogEntryBuffer` 缓冲区
- 扩展性：未来可支持更多 ORM 框架（jOOQ、Spring JDBC 等）

**决策 B：双解析器并行喂行**

在 `SqlLogConsoleBridge.attachFilter()` 中创建**两个解析器实例**，每行输出同时喂入两个：
- MyBatis 解析器忽略 Hibernate 行（无 `Preparing:` 前缀）
- Hibernate 解析器忽略 MyBatis 行（无 `Hibernate:` / `binding parameter` 前缀）
- 两者独立产出 `LogSqlEntry`，汇入同一 buffer
- 零耦合：互不干扰，任一方解析失败不影响另一方

**决策 C：Hibernate 类型映射**

扩展 `LogSqlRestorer.PLAIN_TYPES`，追加 JDBC 类型名：
- 数值型：`BIGINT`, `INTEGER`, `SMALLINT`, `TINYINT`, `FLOAT`, `DOUBLE`, `NUMERIC`, `DECIMAL`, `BOOLEAN`, `BIT`
- 字符串/时间型：`VARCHAR`, `CHAR`, `DATE`, `TIME`, `TIMESTAMP` → 保持引号
- 未知类型：走启发式（数值原样，其余引号）

**决策 D：SQL 行识别策略**

Hibernate SQL 行的三种前缀模式，按优先级匹配：
1. `Hibernate:` 显式前缀（`show-sql=true`）
2. `/* ... */` 注释前缀 + SQL 关键字（`load Entity` / `criteria query` / `update Entity`）
3. 纯 SQL 行（行首即为 SELECT/INSERT/UPDATE/DELETE）——仅当启用严格模式时

**决策 E：条目来源标记**

`LogSqlEntry` 新增 `source: SqlSource` 枚举字段（MYBATIS / HIBERNATE / UNKNOWN）：
- 列表单元格显示来源徽章（可选，默认关）
- 筛选条增加「来源」过滤（可选，P2）
- 预览弹窗标题显示来源

### 2.3 详细改动

#### 2.3.1 `HibernateLogParser.kt` — 新增

```kotlin
/**
 * Hibernate/JPA 控制台日志解析器。
 *
 * 支持的日志形态：
 * - SQL 行（Hibernate: 前缀）：`Hibernate: select ...`
 * - SQL 行（注释前缀）：`/* load com.example.User */ select ...`
 * - SQL 行（纯 SQL）：`select ...`（行首即 SQL 关键字）
 * - 参数行：`binding parameter [1] as [BIGINT] - [1]`
 *
 * 解析策略：
 * - SQL 行触发新条目开启（闭合上一条未完成的条目）
 * - 参数行追加到当前 pending 条目（按索引排序）
 * - 下一条 SQL 行到来时自动闭合当前条目
 *
 * 与 [MyBatisLogParser] 并列运行，互不干扰。共享 [LogSqlEntry] 数据模型。
 */
class HibernateLogParser(
    private val restorer: LogSqlRestorer = LogSqlRestorer(),
    var sqlPrefix: String = DEFAULT_SQL_PREFIX,
    var paramPrefix: String = DEFAULT_PARAM_PREFIX,
    var mixedPrefix: Boolean = true,
    var maxParseLength: Int = DEFAULT_MAX_PARSE_LENGTH,
    /** 是否识别无前缀的纯 SQL 行（行首即 SELECT/INSERT/UPDATE/DELETE）。 */
    var recognizeBareSql: Boolean = true,
) {
    private val entries = mutableListOf<LogSqlEntry>()
    private var pendingSql: String? = null
    private val pendingParams = mutableListOf<LogSqlParam>()

    fun feed(line: String) {
        // 分支 1：SQL 行（Hibernate: 前缀 / 注释前缀 / 纯 SQL）
        val sql = extractSql(line)
        if (sql != null) {
            closePending()
            pendingSql = sql.take(maxParseLength)
            pendingParams.clear()
            return
        }

        // 分支 2：参数绑定行
        val param = extractBindingParam(line)
        if (param != null) {
            if (pendingSql == null) return // 无 SQL 上下文，忽略
            pendingParams += param
            return
        }

        // 分支 3：噪声行
    }

    fun closePending(): LogSqlEntry? { /* 同 MyBatis 逻辑，source = HIBERNATE */ }
    fun takeEntries(): List<LogSqlEntry> { /* 同 MyBatis 逻辑 */ }

    private fun extractSql(line: String): String? {
        // 1. Hibernate: 前缀
        // 2. /* ... */ 前缀 + SQL 关键字
        // 3. 纯 SQL 行（recognizeBareSql=true 时）
    }

    private fun extractBindingParam(line: String): LogSqlParam? {
        // 匹配：binding parameter [N] as [TYPE] - [VALUE]
    }

    companion object {
        const val DEFAULT_SQL_PREFIX = "Hibernate:"
        const val DEFAULT_PARAM_PREFIX = "binding parameter"
        const val DEFAULT_MAX_PARSE_LENGTH = 20000

        // 注释前缀模式：/* load Entity */ 或 /* criteria query */ 或 /* update Entity */
        private val COMMENT_PREFIX_PATTERN = Regex(
            """^\s*/\*.*?\*/\s*(select|insert|update|delete)\b""",
            RegexOption.IGNORE_CASE,
        )

        // 纯 SQL 行模式
        private val BARE_SQL_PATTERN = Regex(
            """^\s*(select|insert|update|delete)\b""",
            RegexOption.IGNORE_CASE,
        )

        // 参数绑定行模式
        private val BINDING_PARAM_PATTERN = Regex(
            """binding parameter\s+\[(\d+)\]\s+\[(\w+)\]\s+-\s+\[(.*)\]""",
            RegexOption.IGNORE_CASE,
        )
    }
}
```

#### 2.3.4 `SqlLogConsoleBridge.kt` — 修改

在 `attachFilter()` 中，将单解析器改为双解析器：

```kotlin
private fun attachFilter(console: Any) {
    if (attachedConsoles.containsKey(console)) { ... }
    attachedConsoles[console] = true
    for (filterIfaceName in FILTER_IFACE_CANDIDATES) {
        try {
            val filterIface = Class.forName(filterIfaceName, true, platformClassLoader)

            // 双解析器：MyBatis + Hibernate
            val myBatisParser = MyBatisLogParser(...)
            val hibernateParser = HibernateLogParser(...)

            val filter = Proxy.newProxyInstance(
                filterIface.classLoader,
                arrayOf(filterIface),
                LogFilterProxyHandler { line ->
                    val cfg = parserConfig()
                    // 同步 MyBatis 解析器配置
                    myBatisParser.sqlPrefix = cfg.mybatisSqlPrefix
                    myBatisParser.paramPrefix = cfg.mybatisParamPrefix
                    // 同步 Hibernate 解析器配置
                    hibernateParser.sqlPrefix = cfg.hibernateSqlPrefix
                    hibernateParser.paramPrefix = cfg.hibernateParamPrefix

                    // 喂行到两个解析器
                    myBatisParser.feed(line)
                    hibernateParser.feed(line)

                    syncBufferConfig()

                    // 收集两个解析器的产出
                    val taken = myBatisParser.takeEntries() + hibernateParser.takeEntries()
                    taken.forEach { buffer.addEntry(it) }
                },
            )
            console.javaClass.getMethod("addMessageFilter", filterIface).invoke(console, filter)
            ...
        }
    }
}
```

## 4. 风险点

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| **纯 SQL 行误识别** | 业务日志/输出恰好以 SELECT 开头 → 误判为 SQL | `recognizeBareSql` 默认关，仅用户显式开启；Hibernate 前缀和注释前缀优先匹配 |
| **Hibernate 格式版本差异** | 不同 Hibernate 版本日志格式微调 | 前缀可配置（`logHibernateSqlPrefix` / `logHibernateParamPrefix`）；注释前缀正则兼容多种注释内容 |
| **参数行出现在 SQL 行之前** | 极罕见日志乱序 | 无 SQL 上下文的参数行直接忽略 |
| **PLAIN_TYPES 扩展影响既有测试** | 新增类型名可能改变既有参数的还原行为 | 仅追加数值型类型（BIGINT 等），不修改既有 Java 类型的判定；全量测试覆盖 |
| **双解析器性能** | 每行喂入两个解析器 | 解析器是纯字符串操作（O(行长度)），两个解析器开销可忽略；实测控制台行长度通常 < 1000 字符 |
