> 来源：2026-09-21 用户报告（沙盒运行，附截图）+ 沙盒日志（`.intellijPlatform/sandbox/mybatis-plus-sql-visualizer/IU-2024.3.7.1/log/idea.log`，2026-09-21 16:06~16:11 段）。

## 一、现象与影响

用户描述的两个状态互为对照：

| 状态 | 字段注释 | JOIN 连接线 | 走的渲染路径 |
|---|---|---|---|
| 未配置数据源 | 无 | **有** | A 路径（自实现 Provider）/ 自绘 |
| 配置数据源后 | 有（DB 真实注释） | **无** | **B 路径（Database 原生显示图）** |

截图左下角 `Powered by yFiles` 是 Database 原生图的内核水印，与日志中 `Native Database diagram (B path) taking over: tables=[car_device_info, station_info]` 一致——用户看到的正是 B 路径。

影响面：**配置了数据源的用户（即主要使用场景）在 JOIN 图上看不到任何连线**。JOIN 图的核心价值（看清表间关联）在这条路径上完全丢失；表盒、字段注释、`int(11)` 类型全部正常，所以现象是「一半好一半坏」，容易被误读成样式问题。

性质：既有缺陷。B 路径连线自 T-Embed-04 起依赖虚拟外键注入，本次定位的守卫行（`JoinVirtualFkProvider.kt:35`）自该实现写下时就存在，属「从未真正生效」而非「新引入」。

## 二、分流：为什么「配了数据源反而没线」

两条路径的连线来源**完全不同**，这是现象反直觉的原因。

`SqlPreviewPanel.showJoinDiagram`（`src/main/kotlin/cn/song/mybatisplus/visualizer/ui/SqlPreviewPanel.kt:1912-1930`）的降级链：

```kotlin
clearNativeDiagram()                       // :1912  T-EmbedFkOrder F1：先清旧图
val native = if (nativeEnabled) {          // :1913
    (project?.let { … })                   // :1916-1919  B 路径
        ?: NativeJoinDiagramSupport.buildTabComponent(...)   // :1920  A 路径
} else null
if (native != null) { … add(native, …) }                            // :1925-1927
else { … add(diagramPanel, …); diagramPanel.showDiagram(model) }    // :1928-1930 自绘
```

- **A 路径 / 自绘**：连线直接来自 `DiagramModel.relationships`（`DiagramRenderer.drawOrthoLines`），与数据源无关——所以「没配数据源也有线」。
- **B 路径**：节点是真实 `DbTable`（所以注释/类型是 DB 真实值），连线**只能**来自 `JoinFkRegistry` 虚拟外键经 `JoinVirtualFkProvider`（EP `com.intellij.database.modelRelationProvider`，注册于 `src/main/resources/META-INF/database-optional.xml:13`）注入。

B 路径的前置条件是「模型里所有表都能在数据源中定位」（`NativeDatabaseDiagramSupport.kt:69-85`）。没配数据源时定位必失败 → 回落 A 路径 → 有线无注释；配上数据源 → 定位成功 → B 路径接管 → 有注释但连线断在平台侧。**两条路径各自的缺口恰好互补，才形成这个「切换数据源就丢线」的观感。**

## 三、根因（平台字节码级，243 / 253 / 262.1 / 262.3 四版本一致）

### 1. 建边入口只走两参重载

`DbDiagramDataModel.refreshDataModel()` 是唯一的建边触发点（`calculateElementToNodeMap` → `calculateEdges` → `myEdges`），而我们显式调用了它（`NativeDatabaseDiagramSupport.kt:266`）。`calculateEdges` 字节码（ideaIU-2024.3.7.1 的 `plugins/DatabaseTools/lib/database-plugin.jar`）：

```
18: getstatic  DbDiagramProvider$Holder.VIRTUAL_FOREIGN_KEYS
21: invokeinterface DiagramNodeContentManager.isCategoryEnabled     ← 我们已强制置 true（:306-317）
69: iload_3 / 70: ifeq 85
79: invokestatic ModelRelationManager.getForeignKeys:(Project; DasTable;)JBIterable   ← 两参重载
87: (else) DasUtil.getForeignKeys(DasTable)
130: invokeinterface DasForeignKey.getRefTable
135: invokevirtual   asDbElement(DasTable) → DbTable
138: invokeinterface Map.get → DbDiagramNode    ← 找不到 ref 节点则丢边
```

即：分类开关打开后，平台用 **`ModelRelationManager.getForeignKeys(project, table)`（两参）** 取外键，而**不是**三参（带 refTable）的那一个。

### 2. 两参重载把 refTable 传成 null

`ModelRelationManager.lambda$getForeignKeys$1`（243 与 253.5 / 262.1 / 262.3 的字节码逐字节相同）：

```
0: aload_2                 // provider
1: aload_0                 // project
2: aload_1                 // table
3: aconst_null             // refTable = null   ← 关键
4: invokeinterface ModelRelationProvider.getForeignKeys(Project, DasTable, DasTable)
```

### 3. 我们的 provider 见到 null 就返回空

`src/main/kotlin/cn/song/mybatisplus/visualizer/ui/diagram/nativefw/db/JoinVirtualFkProvider.kt:30-44`：

```kotlin
override fun getForeignKeys(project: Project?, table: DasTable, refTable: DasTable?): JBIterable<DasForeignKey> {
    if (refTable == null) return JBIterable.empty()          // :35  ← 平台建边路径恒定命中这一行
    val entries = JoinFkRegistry.find(table.name, refTable.name)
    LOG.info("JoinVirtualFkProvider: ${table.name} -> ${refTable.name}, hits=${entries.size}")   // :38-40
    ...
}
```

平台契约里 `refTable == null` 的含义是「不做引用表过滤，返回该表的全部外键」——平台自己的内置 provider 就是这么实现的（`ModelRelationManager$DasForeignKeys.getForeignKeys` 字节码）：

```
8: aload_2 / 9: invokestatic DasUtil.getForeignKeys(DasTable)      // 该表全部 FK
14: aload_3 / 15: ifnonnull 23
18: aload 4 / 20: goto 34                                          // refTable == null → 直接返回全集
23: ... JBIterable.filter(isReferenceTo(fk, refTable))              // 非 null 才过滤
```

我们把「无过滤」误读成「无关系」，于是平台建边时拿到的永远是空迭代器 → 节点全在（注释/类型正常）、`myEdges` 恒空 → 一条线都没有。

### 4. 为什么日志看起来是「健康」的，以及 T-EmbedFkOrder 为何没修好它

沙盒日志里确实有命中记录：

```
16:11:25,182  JoinVirtualFkProvider: car_device_info -> station_info, hits=1
16:11:28,001  JoinVirtualFkProvider: station_info -> car_device_info, hits=1
```

但这些**全是三参重载的调用**（打印出的 refTable 名非空即为证），来自 `ModelRelationManager.getExportedKeys` → `computeExported` 按候选表对逐个回问 provider 的那条链（"显示引用表"用的）。两参建边链在 `:35` 就返回了，**日志打在守卫之后，所以建边路径一次都没留痕**——这正是本条躺了多个里程碑的排障障因。

同时这组日志反证了两件事，把嫌疑面收窄到唯一一点：

- `hits=1` 说明 `JoinFkRegistry` 里**登记是好的**、`columnPairs` 非空、表名匹配也对——所以 `registerJoinForeignKeys`（`NativeDatabaseDiagramSupport.kt:134-144`）与 T-EmbedFkOrder F1/F2 修的「登记被旧图 dispose 抹掉」**都不是本条的原因**；
- 于是唯一没被验证过的环节就是 `refTable == null` 那个分支。

### 5. 为什么「9 例 JUnit 绿」没有拦住它

`src/test/kotlin/cn/song/mybatisplus/visualizer/execute/HeavyNativeDatabaseDiagramJoinChainTest.kt:226` 确实写了 `assertTrue("期望 ≥1 条连接线…", edges.isNotEmpty())`，但该用例有三级软返回（`:187-190` introspect 失败、`:196-205` `component == null`、`:209-219` 编辑器/Builder 未挂接），命中任一即 `println + return` 记绿、五组断言一组都不执行。产物实证（`build/test-results/testDatabase/TEST-…HeavyNativeDatabaseDiagramJoinChainTest.xml`）：

```
[DB-IT] SKIP: B 路径链路不可用（表定位失败或框架异常，应降级 A 路径）——注意：本用例记绿但 B 路径**未验证**（五组断言未执行）
```

即本环境走的是 `component == null` 那条，**B 路径在这台机器上从未被真跑过**，`edges.isNotEmpty()` 从未执行。类注释（`:33-45`）已自陈此事，本轮把「未验证」变成了「确证失效」。

## 四、修法

### F1 注册表增「按 child 表查」入口（纯 JVM）

`JoinFkRegistry` 现在只有方向无关的成对查询 `find(child, ref)`（`JoinFkRegistry.kt:50-58`），无法回答「这张表作为 child 的全部外键」——而两参契约要的正是这个。新增：

```kotlin
/** 该表作为 child（FK 起点）的全部登记；大小写不敏感，无则空列表。 */
fun entriesForChild(childTable: String): List<Entry>
```

实现为遍历 `map` 各桶、按 `entry.childTable == child.trim().lowercase()` 过滤（保持返回方向即登记方向，不做翻转——翻转是 `find` 的成对语义）。纯字符串逻辑，`test` 任务（无 database jar）可直接测。

### F2 新增 ref 表实例持有者（platform-typed，独立于注册表）

两参路径下我们没有 `refTable` 参数，只有表名；而 `calculateEdges` 的 `nodeMap.get(asDbElement(fk.getRefTable()))` 要求 `getRefTable()` 返回**图里那个 `DbTable` 实例**（`asDbElement` 对已是 `DbTable` 的对象走 `ObjectUtils.tryCast` 原样返回；`addElementInner` 字节码实证 `myTablesAddedByUser.put(name, (DbTable) element)` 存的就是传入实例，`calculateElementToNodeMap` 直接拿它当 map 键）。所以必须由登记方把定位到的实例交出来——`registerJoinForeignKeys` 手上正好有 `located: Map<String, DbElement>`。

新增 `src/main/kotlin/…/nativefw/db/JoinFkRefTables.kt`（与 `JoinFkRegistry` 同包，可 import `com.intellij.database.*`）：

```kotlin
/** 表名（小写）→ 已定位的 DasTable 实例。仅供 JoinVirtualFkProvider 在无 refTable 参数时还原引用表。 */
object JoinFkRefTables {
    fun put(tableName: String, table: DasTable)
    fun get(tableName: String): DasTable?
    fun clear()
}
```

**为什么单开一个持有者而不是塞进 `JoinFkRegistry.Entry`**：`JoinFkRegistry` 是「纯 JVM 零平台依赖」的会话数据（类注释 `JoinFkRegistry.kt:6`），`JoinFkRegistryTest` 在 `test` 任务下无 database jar 运行。若把 `DasTable` 放进 `Entry`，注册表类就带上平台类型引用，测试与 Community 侧的类加载边界都被污染。职责上「ON 条件语义」与「平台对象实例」也确实是两件事。

### F3 provider 补齐空 refTable 分支（含诊断）

`JoinVirtualFkProvider.getForeignKeys` 改为：

```kotlin
if (refTable == null) {
    val entries = JoinFkRegistry.entriesForChild(table.name)
    val fks = entries.mapNotNull { e ->
        val ref = JoinFkRefTables.get(e.refTable) ?: run {
            LOG.warn("JoinVirtualFk: ref table '${e.refTable}' not located, skip edge for ${table.name}")
            null
        }
        ref?.let { JoinVirtualFk(table, it, e) }
    }
    LOG.info("JoinVirtualFkProvider(no-refTable): ${table.name} entries=${entries.size} edges=${fks.size}")
    return JBIterable.of(*fks.toTypedArray())
}
// 原三参路径保持不变（getExportedKeys / computeExported 仍在用）
```

要点：
- 语义与平台内置 `DasForeignKeys` 对齐：只返回「该表作为 FK child」的边，不返回反向，避免同一关系画两条线；
- `JoinVirtualFk` 的 child 参数直接用平台传进来的 `table`（它就是图节点实例），ref 用 F2 的实例；
- 诊断行必须打（这是本轮排障的最大缺口）：空 refTable 分支的入参、登记数、成边数三者同时留痕；「登记有、实例缺」单独 WARN，避免又出现「日志一片正常、画布没有线」。

### F4 抽出可测的纯选择逻辑

把「给定 child 表名 + 登记集合 + ref 实例可用性 → 应成边的关系描述」抽成不依赖平台类型的纯函数（返回 `List<Entry>` 或轻量数据类），provider 只负责把描述翻译成 `JoinVirtualFk`。目的是让 F3 的分支逻辑在 `test` 任务（无 database jar）下也能被断言——与项目既有做法一致（`applyTableMeta`、`joinTitleText` 等纯函数注入缝）。

### F5 测试与守卫

| 层 | 用例 | 断言 |
|---|---|---|
| 纯 JVM（`test`） | `JoinFkRegistryTest` 扩 | `entriesForChild` 大小写不敏感、返回登记方向、未知表空、跨多个 ref 表全返回 |
| 纯 JVM（`test`） | 新增 F4 纯函数用例 | 给定登记 + ref 实例齐全 → 描述非空；ref 实例缺失 → 该条被跳过且其余保留（**这条是 N6 的直接回归守卫**） |
| `testDatabase` | `HeavyNativeDatabaseDiagramJoinChainTest` 增 | 直接调 `JoinVirtualFkProvider().getForeignKeys(project, childDasTable, null)`，断言**非空**且 `getRefTable()` 与 `located` 里的实例同一（把「两参契约」钉死在测试里，不依赖画布/布局） |
| `testDatabase` | 同文件软返回收紧 | 内省成功、数据源存在、`located` 齐全时 `component == null` 应**判失败**而非记绿；确需跳过时打印可区分的原因串 |

软返回收紧是必须项：本轮的核心教训不是「断言写错了」，而是「断言所在的用例可以整条静默跳过」。若评估后认定本环境确实无法让 B 路径跑起来（表定位失败），则把 `component == null` 分支的判定从「跳过」改为「失败」会红掉 `testDatabase`——那就退一步，在**该分支内加一条对 `locateDbTables` 四段计数（`roots`/`dasTables`/`nameHits`/`registryMiss`）的断言**，把「为什么跑不起来」变成可失败的门禁，而不是注释里的说明。

## 五、待验证前提（动手前先证伪）

1. **两参重载传 null 在全部目标平台成立**——已在 243.28141.41 / 253.5 / 262.1 / 262.3 四个 `intellij.database.core.impl.jar` 上反编译确认（`lambda$getForeignKeys$1` 第 3 参数 `aconst_null`，四份字节码相同），且四版本的 `DbDiagramDataModel.calculateEdges` 都是「VIRTUAL_FOREIGN_KEYS 门 → 两参重载 → `asDbElement(getRefTable())` 查 nodeMap」同构。**仍需在实现时复跑一次**（改平台版本后该结论会漂）。
2. **`located` 的 `DbElement` 与图节点是同一实例**——字节码链已证（`addElementInner` 原样存实例、`calculateElementToNodeMap` 以之为键、`asDbElement` 对 `DbTable` 原样返回），但 `findDbElement(DasObject)` 返回对象是否 `is DbTable`（可 `as? DasTable` 成功）需在 `testDatabase` 或真机用 F5 的「同实例」断言实测。若该前提不成立，F2 的实例持有路线要改为按名称从父 schema 反查，届时连边可能因实例不等而仍不显示。
3. **`columnPairs` 非空**——用户这条 SQL 由日志 `hits=1` 反证成立；但 `extractOnColumnPairs`（`JoinDiagramGenerator.kt:188-214`）只接受 `Condition.ColumnComparison` 且两侧归属可判，rawSql / 子查询 / 函数表达式 ON 条件不产生配对 → 那类 SQL 即使修好本 bug 也仍然没有连线。属既有已知边界，见 §十。
4. **`refreshDataModel` 是唯一建边时机**——字节码已证 `myEdges` 只在该方法内被赋值；若实现中发现平台另有增量建边入口，F3 之外还需补登记时机。

## 六、验收标准

1. 沙盒（IU-2024.3.7.1）配置数据源后预览用户那条 SQL（`car_device_info t LEFT JOIN station_info t1 ON t1.station_id = t.station_id`）→ JOIN 图**同时**有 DB 注释**和**连线，连线为 `station_info → car_device_info`，标签显示 ON 列对。

3. 关闭预览 / 切到无 JOIN 语句 → `JoinFkRegistry` 与 `JoinFkRefTables` 均清空（无跨图残留、无平台对象泄漏）。
4. 无数据源时行为不变：A 路径/自绘仍有连线（本次改动不触碰 A 路径）。
5. 日志可诊断：两参建边链每次调用留 `JoinVirtualFkProvider(no-refTable): …` 一行；`refTable` 名无法还原实例时留 WARN。**排障时只 grep 这一行即可判定「建边链是否被触达 / 成边数」。**
6. `test` 全量绿 + `testDatabase` 绿；`testDatabase` 中 F5 的直接 provider 断言与「同实例」断言真实执行（以 XML `system-out` 无 SKIP 行为证）。

## 七、反向验证（必做，不接受只跑绿灯）

1. 临时把 `JoinVirtualFkProvider` 的 `refTable == null` 分支改回 `return JBIterable.empty()` → F5 的纯函数守卫用例**必须变红**；贴两次读数（红/绿）。
2. 若本环境能让 B 路径真跑：同上还原后 `HeavyNativeDatabaseDiagramJoinChainTest` 的边断言**必须变红**。
3. 若本环境不能真跑 B 路径：如实登记「画布级反向验证环境受限未做」，**不得**用纯函数用例的红绿冒充画布已验；同时按 §四 F5 末段把「跑不起来」本身变成可失败门禁。
4. 真机走查（§八）作为最终证据层级——按项目纪律，画布真实可见性以真机截图为准，不以数据模型断言代替。

## 九、风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| ref 实例与节点实例不等 | 若前提 2 不成立，边仍会被 `nodeMap.get` 丢掉，症状不变 | F5 的「同实例」断言在实现期即暴露；备选路线见 §五.2 |
| 重复连线 | 平台内置 `DasForeignKeys` 与 `NameBasedRelationProvider` 也在贡献边；若该库真存在 DDL 外键，同一关系可能出现两条线 | 走查项 2 观察；若出现，按 providerId 去重（只保留 `SqlVisualizerJoin`） |
| 反向边 | 两参路径若同时返回 child 侧与 ref 侧会画两条 | F3 明确只返回 child 侧；F5 用例覆盖 |
| 注册表与实例表生命周期不一致 | 两处清理点漏一个 → 残留实例引用 | 同一处调用点成对清理；验收项 3 覆盖 |
| 平台版本漂移 | 253/262 已证同构，但后续版本可能改回三参或改门控 | 复用 `PlatformSignatureCrossVersionTest` 的跨版本护栏思路，对两参重载的 null 语义加一条签名/契约断言 |

### 实施中的两处偏离（相对 §四，均已论证）

1. **null 语义下沉到纯函数，而不是留在 provider 里做分支**。原计划 F3 把分支写在 provider、F4 用纯函数覆盖选择逻辑——但那样纯 JVM 守卫**看不见它要防的那一行**（回归点仍在引用平台类型的文件里），正是本仓守卫已三次失效的形态。改为：provider 内不再出现任何 `refTable == null` 判断，语义全部由 `JoinFkRegistry.selectForCall` 承载（该文件纯 JVM，`test` 分片可直测）。代价是仍需一条源码级守卫兜住「provider 有没有绕过纯函数」（见下）。
2. **新增源码级守卫 `JoinVirtualFkProviderContractTest`**（计划外，为补 §七 的覆盖缺口）。理由：provider 引用 `com.intellij.database.*`，plain `test` 分片无 database jar，无法行为级验证「null 分支是否被绕过」。该守卫的覆盖边界已在类注释里诚实标注（只认 `if (refTable == null)` 形态，改写成 `?.let{} ?: return` 会漏），并在 §反向验证 里实测有效。

### 顺手修掉的一处同族缺陷

`registerJoinForeignKeys` 原以 `located[mainTable]` 直查，而 `locateDbTables` 的键是**小写表名**——表名含大写时命中失败、整条 JOIN 被静默跳过（登记为空 → 无边，日志只显示 `entries=0`）。已改为 `located[...trim().lowercase()]`。属同族「登记静默跳过」缺陷，一行修正、无行为回归风险（`located` 键恒为小写）。
