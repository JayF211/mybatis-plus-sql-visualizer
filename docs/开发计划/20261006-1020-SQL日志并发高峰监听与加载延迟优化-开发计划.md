# SQL 日志并发高峰监听与加载延迟优化 — 开发计划

> 2026-10-06 立项。来源：用户在日常 IDE（IntelliJ IDEA 2026.2.1，262.10968.63，装发行版 v2026.10.6）并发压测 easy-code-demo 时反馈「并发情况下大量 SQL 日志导致 SQL 日志监听加载有延迟、加载较慢」。
> 本计划基于「idea.log 实测取证 + 代码链路走查」双线结论，实施分支建议 dev（生产码主干；master 仅文档）。

## 1. 实测证据（日常 IDE idea.log + 磁盘产物，20261006 上午）

### 1.1 用户压测画像

- 09:30:03 运行 EasyCodeDemoApplication，premain agent 注入成功（pid=5180），增强捕获在线。
- 09:30:39 首条 SQL 条目到达 → 09:32:40 累计 4600+ 条：`AgentSession` 的「日志时间戳命中累计 N 条」INFO 每 200 条一行，折算**稳定约 65 条/秒、持续 2 分钟以上**——这就是「并发情况下大量 SQL 日志」的量化形态。
- 09:56:12 第一轮结束；09:59:26 第二轮（pid=9760）。当日历史文件随之膨胀。

### 1.2 历史加载延迟（「加载较慢」的直接证据）

磁盘产物：`easy-code-demo/.idea/sql-visualizer/sql-history/sql-history-2026-10-06.sql` = **19,043,758 字节（约 19MB）**。

| 时点 | 日志证据 | 耗时 |
|---|---|---|
| 09:31:52.335 → 09:31:54.929 | refresh → showFileContent「共 2370 条」 | ≈ 2.6s |
| 10:13:14.050 / 10:13:15.726（两次 refresh）→ 10:13:30.660 | showFileContent「共 8708 条」 | **≈ 15~16.6s** |

条目数 ×3.7，耗时 ×6+——**超线性劣化**。且 10:13 窗口内 refresh 与 showFileContent 各自独立全量读盘（见 §2 P1），实际发生了 3 次左右 19MB 全文解析。

### 1.3 EDT 争用旁证

- `ActionUpdater - N ms to grab EDT for SqlLogPanel$*Action`（工具栏 6 动作整体等待）多次出现，单次 358~1110ms——EDT 有明显排队压力，与日志面板同窗。
- 09:12:20/09:12:28 两份 IDE 冻结转储（7s/6s）经查 EDT 栈在平台 VFS 名称缓存读取（`MRUFileNameCache`/`ExternalAnnotationsManagerImpl`），**与本插件无关，已排除**。

### 1.4 配置核验

`mp-sql-visualizer.xml`：`logAutoSaveEnabled=true`、`logAutoCaptureOnStart=true`，`logMaxCount` 未写=默认 200。实时列表本身条目量有界，**大文件只在历史侧**。

## 2. 代码链路与嫌疑点（按嫌疑度排序，行号为主干 20261006 时点）

捕获链路：三条通道（EP 控制台 Filter / 反射桥 Filter / agent 会话读线程）→ `SqlLogEntryBuffer.addEntryInternal` → 节流通知（20 条/200ms）→ `SqlLogManager.notifyUi` 单个 invokeLater → `SqlLogPanel.refreshList`（EDT）。历史侧：`HistorySqlLogPanel.refresh()/showFileContent()`（均已后台化）→ `SqlLogFileReader.readFromFile` → `fillSqlList` 分批填充。

| # | 嫌疑点 | 位置 | 说明 |
|---|---|---|---|
| P1 | refresh 浏览态全量重读 keepFile | `HistorySqlLogPanel.kt:363,376` | 用户停在二级浏览某文件时，**每次 refresh 都把当前文件全文重读+重解析一遍**（仅为了「保持二级视图」）；19MB 文件下每次刷新都是一次全量解析 |
| P2 | readFromFile/parseContent 多次全量拷贝 + 每块 Base64+gson 解码 | `SqlLogFileReader.kt:134,168-195`、`SqlLogParamCodec` | 每块 `joinToString`→`lines()`→再 `joinToString` 至少三份拷贝；8708 块逐块 Base64+JSON 解码；整体实测仅约 1.1~2MB/s |
| P3 | fillSqlList 分批链后续批次未包 ignoreRepaint | `HistorySqlLogPanel.kt:461-484` | 首屏 30 条包了，剩余 290 个 EDT 跳（8708/30）每跳裸 `addAll`+布局失效 |
| P4 | 历史二级列表无条数上限 | `fillSqlList` 全量入 `DefaultListModel` | 8708 条全量进模型，后续搜索过滤、重绘都在全量上做 |
| P5 | EDT 刷新全量重活 | `SqlLogPanel.kt:1414-1455` | 每次 refreshList：全量 snapshot 拷贝 + 4 层过滤 + 排序 + slowQueryCounter.report 遍历 + dedupeCountsSnapshot 全 map 拷贝；风暴期每 200ms 一轮 |
| P6 | 缓冲锁内 O(n) 去重扫描 | `SqlLogEntryBuffer.kt:168,258-261` | `isDuplicate` 在 `synchronized(entries)` 内 `firstOrNull` 全表扫；三通道写线程与 EDT snapshot 抢同一把锁，缓冲越大锁越久 |
| P7 | agent 接管期桥侧空转 | `SqlLogConsoleBridge.kt:925-933`、`:388-404` | 短路行仍喂 3 个解析器构造即弃 + 计数；且桥是 EDT Swing Timer 轮询（2s），`synchronized(context)` 与控制台输出线程互卡 |
| P8 | 热路径零耗时埋点 | log 包整体 | 无任何 nanoTime 耗时打点，延迟无法从 idea.log 直接归因——本计划第一步先补 |

## 3. 待验证前提（实施者先证伪再动手）

- **前提 A**：16.6s 的大头在后台 `readFromFile` 解析本身，而非 EDT apply 端。若打点证伪（大头在 apply/EDT 调度），则 P3/P4 升为主修、P2 降级。
- **前提 B**：P1 的 keepFile 全量重读确实发生在用户浏览二级视图期间（10:13 窗口推算出约 3 次全读与此吻合，但无逐次打点）。需阶段 0 打点坐实单次解析耗时分布。
- **前提 C**：实时监听「有延迟」的主因是 EDT 拥塞（P5/P7），不是缓冲节流（20 条/200ms 的节流上限本身不构成秒级延迟）。需在压测复现时以打点/thread dump 佐证。
- **前提 D**：gson 逐块解码在 P2 中占比可观（若占比微小，P2 只做拷贝合并即可，不必动编解码格式）。

## 4. 实施方案（分阶段，每步达标即提交）

### 阶段 0：耗时埋点先行（不改行为，半天）

- `SqlLogFileReader.readFromFile` / `parseContent`、`HistorySqlLogPanel.applyRefresh` / `fillSqlList`、`SqlLogPanel.refreshList`、`SqlLogEntryBuffer.addEntryInternal`（批次级）加 `System.nanoTime` 差值打点，**阈值触发**（单次 >100ms 才打 INFO），避免风暴期日志刷屏。
- 用户日常 IDE 复现一轮压测，拿打点读数裁决 §3 前提 A/B/C/D，据实调整后续阶段权重。
- 产物：读数贴进本计划「实施记录」节；埋点转正保留（阈值门槛使其常态零噪音）。

### 阶段 1：历史 tab 加载（低风险高收益，预计大头）

1. **refresh 不再全量重读 keepFile**（P1）：浏览态刷新只做 `countInFile`（已有 lastModified+length 缓存）更新计数徽标；二级内容标记「文件已变化」惰性重载——用户实际查看时才重读，或文件 length 未变直接复用现有 `currentEntries`。
2. **解析单遍化**（P2）：`parseContent` 块累积改直接传递行序列，砍掉 `joinToString`/`lines()` 双拷贝；按前提 D 实测占比决定是否推迟 gson 解码（如参数载荷延到条目真正展示时再解码）。
3. **二级列表按需加载**（P3/P4）：fillSqlList 分批链整链包 `ignoreRepaint`；对超大批量（如 >3000 条）改「虚拟化/滚动到底再追加」或加显式上限 + 尾部提示行——**两种口径涉及产品行为，实施前与用户确认**（默认推荐滚动追加）。
4. 验收：8708 条文件从点开到首屏可见 <2s，全量就绪 <5s（以打点读数为准回填）。

### 阶段 2：实时监听热路径（并发期延迟）

1. **去重索引化**（P6）：`isDuplicate` 的 O(n) 全表扫改 `HashMap<dedupeKey, 最近时间戳>` 侧索引（60s 窗口内有效），入队/淘汰/手动裁剪/清空同步维护；补等价性测试（与现语义逐用例对齐：窗口内指纹判重、淘汰出窗失效、disableDedupe 清账）。
2. **agent 接管期桥侧最小化**（P7）：`SqlCaptureGate.paused` 短路分支不再喂 3 解析器（时间戳嗅探改最小前缀判定）；先红后绿摘修复验证。
3. **EDT 刷新减负**（P5）：`slowQueryCounter.report` 与 `dedupeCountsSnapshot` 增量化/按脏标记跳过；确保风暴期单次 refreshList 摊薄 <10ms。
4. 验收：65 条/秒持续灌入下，新条目从到达缓冲到列表可见 <1s；压测期间工具栏动作无 >500ms 的 grab-EDT 记录。

### 阶段 3：收口

- 定向测试：`SqlLogConsoleBridgePerfTest`、`LogRouterHotPathRegexGuardTest`、`SqlLogStreamingDiffTest`、`SqlLogListFreeze*`、`ConsoleSettleFlushTest`、`SqlLogAutoSaver*`、`log/agent/AgentListenSyncTest` 等（见 §5）。
- 新增守卫：`SqlLogFileReader` 大文件解析耗时上限断言（用相对基准防 CI 波动）；去重索引等价性测试；fillSqlList 链 ignoreRepaint 行为钉。
- 全量门禁按验证三档分层走（本计划改动不触 build.gradle.kts/plugin.xml EP，属常规改动，testFast + 定向即可，全量随下轮收口批）。

## 5. 测试与验证载体

- 单测：`src/test/kotlin/.../log/` 下既有并发/性能/守卫族（SqlLogConsoleBridgePerfTest、LogParseConcurrencyTest、HibernateLogParseConcurrencyTest、SqlLogCaptureRealtimeScenarioTest、SqlLogEntryBufferTest 系、HistorySqlLogPanel 相关 UI headless 测试）。
- 真机复现：日常 IDE 2026.2 + easy-code-demo 并发压测脚本（两轮并发流水，65+ 条/秒），idea.log 打点对账；runIde 沙盒侧可复用同 demo 工程。

## 6. 风险与边界

- 历史二级列表「上限/虚拟化」是可见行为变化：默认走滚动追加方案，如需硬上限须用户拍板。
- 去重索引化动了捕获语义热点路径，必须「摘掉索引维护 → 等价性测试必红」反向验证，防假绿。
- agent 接管期短路分支有版本兼容面（旧版 agent 混合双通道），改动后跑 `EpBridgeSinglePathTest`/`ConsoleReplayGuardTest` 防回潮。
- 埋点打点只走阈值 INFO，不发新通知组，不触设置页。

### 前提裁决（阶段 0 前置复核 + 实施中判定）

- **前提 A/B（历史加载大头在哪）**：未先跑真机打点即实施——理由：P1（refresh 全量重读）与 P2（三份拷贝）属**结构性浪费**（无论大头占比多少都该修），滚动追加（P3/P4）把 8708 条的全量成本改为按需，四项合取后 P1/P2 单项占比不再关键。打点已转正（阶段 0），用户下次真机压测的 idea.log `[T-SqlLogPerf]` 行可直接复核修复后读数。
- **前提 C（实时延迟主因）**：实施中实锤一个**计划未列的实态**——实时列表全量重建链会被 200ms 一次的新刷新反复抢占重启（`listModel.size != lastRendered.size` 拒绝增量 → 每次刷新都重启链），风暴期列表卡在首屏 30 条；已修（进差分前同步补完在途链，`1f92f80`）。另发现 log 包**原本就没有任何滚动控制**（新条目只进模型视口不动）——用户「监听加载有延迟」体感的最直接形态，随「滚动到底部+尾部跟随」一并解决（用户点名）。
- **前提 D（gson 逐块解码占比）**：未单独测——单遍化后每块只剩一次必要拷贝，参数载荷推迟解码如需要可随后续打点读数再立项。
- **P7（agent 接管期桥侧嗅探最小化）推翻不动**：与 T-AgentLogTime 既有定案冲突（日志时间是数据、采集不受显示开关控制、零开关判断是刻意设计），最小化会破坏增强模式下的日志时间回填；如实记录于 CHANGELOG。
