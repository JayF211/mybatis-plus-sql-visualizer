## 1. 依据

### 1.1 为什么 agent：捕获层级的代差

控制台桥捕获链（`SqlLogConsoleBridge` → 三解析器 → `SqlLogEntryBuffer`）存在三个结构性局限：

| 局限 | 具体表现 | agent 通道的解法 |
|------|---------|-----------------|
| 依赖日志格式 | MyBatis/Hibernate/JdbcTemplate 各自日志形态，格式变（p6spy/日志级别/框架版本）即断；`processConsoleLine` 逐行正则+状态机 | 字节码层直接 hook 执行点，与日志格式完全解耦 |
| 数据不完整 | 参数从 `Parameters:` 文本行反解析（类型推断有失败面）；拿不到影响行数；报错信息要另行识别异常行（M55-02 的时序反向关联） | PreparedStatement setter 实参直取；execute 前后时间戳；getUpdateCount；异常对象直捕 |
| 拿不到执行上下文 | 调用栈靠「向用户项目注入拦截器源码」回传（F-44-6/7）；请求边界无来源 | agent 在应用 JVM 内，调用栈/线程上下文天然在手 |

覆盖范围差异是决定性的：**JDBC 层一个 hook 即全覆盖 9 框架族**（MyBatis/MP/MPJ/Hibernate/JPA/JdbcTemplate/裸 JDBC 底层全是 JDBC），而现有桥需要为每框架族各配解析器。

### 1.2 本机实测证据（2026-09-07，Windows）

- attach 端到端跑通：JBR25（IDE 运行时）/JDK17/JDK8 三种附加器 × JDK8/JDK17 两种目标交叉 attach + `loadAgent` 成功，agentmain 内 `retransformSupported=true`、`redefineSupported=true`。
- Windows 走命名管道 `\\.\pipe\javatool*`（tools.jar 反汇编证实）；`VirtualMachine.list()` 仅列同用户可 attach JVM——IDE 启动的用户应用天然满足同用户条件。
- 附加方 API：JDK8 在 tools.jar、JDK9+ 在 jdk.attach 模块（IDE 用 JBR 恒在）；`loadAgent(磁盘jar路径)` 是唯一挂载途径（javap 逐字实证，无公开 prependAgentJar）。
- 幂等坑实证：JDK8 目标二次 loadAgent 抛 `AgentLoadException: 0`——必须做 attach 幂等防重（§2.6）。
- 探针工程 `C:/Users/USER/AppData/Local/Temp/attach-probe/`（AttachProbe/TargetSleep/Agent + agent.jar）可作 PoC 基线直接复用。

### 1.3 拿 pid 的公开 API（javap 实证，IDEA 2026.2）

`RunContentDescriptor.getProcessHandler()` → `ProcessHandler.getNativePid(): CompletableFuture<Long>`（243 基线可能缺失，回退 `BaseProcessHandler.getProcess().pid()`）；或 `ExecutionManager.EXECUTION_TOPIC`（ExecutionListener.processStarted 直接给 ProcessHandler）。**本项目桥已有反射访问 execution API 的现成模式**（`SqlLogConsoleBridge.kt:442-498` 双包名候选 + platformClassLoader 反射），attach 模块直接复用，零新增编译期依赖。

### 1.4 字节码工具选型

| 选项 | 包体 | 结论 |
|------|------|------|
| 裸 ASM 9.8+（asm/commons/tree/util） | ~380KB | **首选**：拦截点固定（6~10 个方法）、包体最小、Arthas 已验证（ByteKit=ASM 系）；按目标 JVM 指定 `Opcodes.V1_8` 生成即可覆盖 JDK8~25 |
| ByteBuddy（1.12.x / 1.17.x） | 3.9MB / 9.0MB | 备选：高层 API 快，但须整 jar 自包含 + shade（插件与 IDE 平台 ASM 已 relocate 到 `org.jetbrains.org.objectweb.asm`，撞类风险） |
| Javassist | ~0.8MB | 不建议：现代 JVM 栈映射劣势 |

### 1.5 拦截层级矩阵（决策依据）

| 维度 | JDBC 层 | MyBatis 层（Executor/StatementHandler） |
|------|---------|----------------------------------------|
| SQL 文本 | ✅（含 ? 占位符） | ✅（BoundSql，含参数对象） |
| 绑定实参 | ✅ 跟踪 setXxx | 复刻 MyBatis 参数映射（成本高） |
| 耗时/行数/报错 | ✅ 最精确（execute 前后/getUpdateCount/异常直捕） | 含 MyBatis 内处理 |
| 调用栈跳转 | ✅ 栈顶即 Mapper/Service 帧 | ✅ |
| MappedStatement id | ❌ | ✅ Executor 首参天然 |
| 框架覆盖 | **全家族** | 仅 MyBatis 族 |

**决策**：主体 JDBC 层（框架无关、字段全、最精确）+ 叠加 MyBatis 层小 hook 补 `ms.getId()`（拿不到即降级，不影响主链）。注意 MyBatis 的 Interceptor 本身就是 Executor 的动态代理包装——**与 agent hook 同一处，两条通道是冗余可选关系，agent 生效时禁止与现有「注入 InnerInterceptor 源码」方案双写**（agent 在线即跳过注入）。

### 1.6 与 M55 的协同关系（代码链路调研结论）

agent 通道与现有控制台桥**并存、agent 在线优先**：agent 事件适配器复用 `SqlLogEntryBuffer.addEntry` 唯一汇聚点（`SqlLogConsoleBridge.kt:325`，全仓唯一生产调用），去重/过滤/暂停/淘汰/自动保存对两通道零成本统一生效。M55 四任务处置：

| M55 任务 | agent 通道下 | 处置 |
|---------|-------------|------|
| T-M55-01 跳转双目标 | statementId 由 agent 事件直供（MyBatis 层 hook），发射端简化；MapperXmlLocator/双菜单 UI 完全复用 | 不受影响，发射端升级 |
| T-M55-02 执行报错同列 | 异常对象结构化直供，**「异常行→已入列条目」时序反向关联风险被结构性消除** | agent 下被替代；识别器保留为桥路径组件（降级通道用） |
| T-M55-03 方法级聚焦 | 调用栈给出真实方法边界（`{Class}#{method}`），消除静态行号区间近似的全部风险 | 简化（近似→精确） |
| T-M55-04 请求级聚合 | per-thread 请求栈比 RequestContextHolder 可靠 | 替代/简化 |

M55 §2 的标记行 3~5 段兼容约定**照常实施**——控制台桥是降级主路径，存量已注入拦截器用户必须继续工作。实施顺序：M55 消费端先行（两通道共用），M56 落地后 M55 发射端按本计划升级。

### 1.7 实施后的用户体验优化清单（用户视角）

从插件使用者的视角，M56 落地后最直接可感知的变化（现状 → agent 后，对应子任务见 §3）：

| # | 场景 | 现状（控制台桥） | agent 后 |
|---|------|-----------------|----------|
| 1 | 开启捕获 | 依赖工程日志输出形态（p6spy/日志级别/框架版本），格式一变就断；Hibernate 需要特定绑定参数行 | 开启即捕获，与日志格式、框架版本完全解耦；JDBC 层一个 hook 全覆盖 MyBatis/MP/MPJ/Hibernate/JPA/JdbcTemplate/裸 JDBC 九框架族 |
| 2 | 参数回填 | 从 `Parameters:` 文本行反解析，复杂类型（LocalDate 等）有推断失败面 | PreparedStatement setter 实参直取，类型即真实类型，回填零解析失败 |
| 3 | SQL 报错定位 | 报错散在控制台堆栈里靠人工对应；M55-02 异常行识别存在「异常晚于 SQL 打印」的时序歧义 | 执行异常与 SQL 条目同列展示，含参数绑定报错（Ultra 4.0.14 自述不支持的边界）——不需要人工对位 |
| 4 | 跳转源码 | 精确跳转需先注入拦截器（改用户工程 + 重启生效）；未注入时回退按表名猜 | attach 热挂载即时生效、零工程改动；调用栈直取更精确，XML 双目标可达 |
| 5 | 执行信息 | 无影响行数；耗时从控制台文本解析（不精确） | 每条 SQL 带影响行数 + 精确耗时（execute 前后计时），慢查询判断更准 |
| 6 | 方法级聚焦 | M55-03 静态行号区间近似（lambda/匿名类边界模糊） | 真实方法执行边界，`{Class}#{method}` 页签精确过滤 |
| 7 | 请求级聚合 | M55-04 依赖 RequestContextHolder（异步子线程拿不到） | per-thread 请求栈（一期可选项），同请求 SQL 归组更可靠 |
| 8 | 使用门槛 | 精确跳转要先配置注入拦截器（Spring Boot 专用，MyBatis 原生项目注入是 TODO） | 纯 IDE 侧操作：确认一次 + 开启开关即用；Spring Boot / MyBatis 原生 / 非 Spring 项目形态一致 |
| 9 | 数据隐私 | 无 agent，全在 IDE 内解析控制台文本 | 采集留在本机 loopback 通道，默认对敏感参数（密码/token 形态）脱敏，可开关；注入前显式确认 |

边界说明（防过度承诺，与 §2.6/§8 呼应）：

- **本功能定位为「增强捕获」（对用户不出现 agent 字样）**：默认关闭，未开启的用户体验与现状逐字一致（控制台捕获链零改动）；开启增强后 agent 为捕获源，attach 不可用（远程/容器/SSH/失败）自动回落控制台捕获，零劣化。
- 首次启用需确认，采集留本机、敏感参数默认脱敏；关闭增强即回到默认捕获，不打扰用户。
- 实施后对外文案（随下次发行）：默认能力不变，新增「增强捕获」开关——打开后捕获所有框架的 SQL、参数、报错、耗时与调用点，与 N-10 §3.3 建议的「免费 + 精确跳转 + 静态预览」话术合并使用。

## 2. 技术方案

### 2.1 总体架构

```
IDE JVM（插件）                          用户应用 JVM（runIde 启动）
┌─────────────────────────┐              ┌──────────────────────────┐
│ AgentManager (project)  │ attach+load  │ agent.jar（ASM 增强）    │
│  ├ attach 生命周期/幂等  │◄────────────►│  ├ JDBC 层 hook（主）    │
│  ├ ServerSocket 收流     │  loopback     │  │   Connection/Stmt/    │
│  └ AgentEventAdapter ──►│  Socket       │  │   PreparedStatement   │
│      │ 事件→LogSqlEntry │              │  ├ MyBatis 层 hook（补） │
│      ▼                  │              │  │   ms.getId()          │
│ SqlLogEntryBuffer       │              │  ├ 采集队列（不阻塞）    │
│   （与桥共用唯一入口）    │              │  └ Socket 客户端推送    │
└─────────────────────────┘              └──────────────────────────┘
```

### 2.2 attach 挂载（T-M56-01 核心）

1. **进程发现**：复用桥的反射骨架（`descriptorsOf/cachedMethod` 模式）取 RunContentDescriptor → `getProcessHandler()` → `getNativePid()`（反射，243 缺失回退 `getProcess().pid()`）；或订阅 `EXECUTION_TOPIC` processStarted。
2. **agent jar 落盘**：插件内嵌 agent jar（独立自包含、无 Kotlin stdlib、manifest 含 `Agent-Class` + `Can-Redefine-Classes/Can-Retransform-Classes: true`）解压到临时文件 + `deleteOnExit`（loadAgent 参数是磁盘路径，目标 JVM system classloader 加载，插件 classpath 不可见——ByteBuddyAgent 同款机制，探针实证）。
3. **挂载**：`Class.forName("com.sun.tools.attach.VirtualMachine", …, platformClassLoader)` 反射 `attach(pid)` + `loadAgent(path, "port=xxxx")` + `detach()`；同 pid 幂等记录（插件侧 pid 表 + agent 侧 system property 标记）。
4. **失败降级**：attach 异常/远程 SSH/容器/`DisableAttachMechanism` → 记日志回退控制台桥，功能不劣化（桥链路零改动）。

### 2.3 agent 字节码增强（agent 侧，Java 编写）

- **JDBC 层 hook 点**（6~10 个固定方法）：`Connection.prepareStatement/prepareCall`（记语句）、`PreparedStatement.setXxx`（记实参）、`Statement.execute/executeQuery/executeUpdate/executeBatch`（执行前取调用栈/起始时间，执行后取耗时与 getUpdateCount，异常直捕）、`Connection` 关闭清理。回调类经 `ClassInjector.UsingInstrumentation` 注入到目标可见 classloader（java.sql.* 是 bootstrap 类）。
- **MyBatis 层 hook**（补 `ms.getId()`）：`Executor.query/update` 首参 MappedStatement 取 id；与 JDBC 事件按线程+时序关联（实施期以关联可靠度为验收点，不可靠则降级为仅 JDBC 事件）。
- **协议与约束**：事件字段（见 §2.4）经队列（有界、丢事件不丢线程）推送 loopback Socket；agent 内异常不得泄漏/不得阻塞应用线程/热路径零分配；全局禁用开关（§2.6 的「禁用不卸载」）。

### 2.4 数据通道与事件协议

IDE 侧 `AgentManager` 起 loopback ServerSocket（随机端口传参给 loadAgent），agent 建连后推结构化事件（JSON 或紧凑自定义文本，实施期定）。事件字段：

| 字段 | 来源 | 对应条目 |
|------|------|---------|
| sql | execute 前 SQL 文本（含 ? 占位） | rawSql |
| params | setXxx 实参（含类型） | params → restoredSql |
| durationMs | execute 前后时间戳 | executionTimeMs |
| updateCount | getUpdateCount | （扩展字段，M56 可选） |
| error | 异常类名+消息+堆栈（截断） | errorText（M55-02 字段） |
| callerFile/callerLine | 执行点调用栈帧（框架帧过滤同 `CallerSourceLocator` 规则） | sourceFile/sourceLine |
| statementId | MyBatis 层 ms.getId() | mapperStatement（M55-01 字段） |
| requestTag | per-thread 请求栈（一期可空） | requestTag（M55-04 字段） |
| source | 固定 AGENT | SqlSource 扩展值 |

### 2.5 事件→条目适配（T-M56-02）

`AgentEventAdapter`（纯函数，可单测）：`AgentEvent` → `LogSqlEntry` 字段映射 → `SqlLogEntryBuffer.addEntry`。来源标记 `SqlSource.AGENT` 新增枚举值（渲染沿用现有高亮体系，可加轻微角标区分通道）。去重/过滤/暂停/淘汰/自动保存全部复用 buffer 层——两条通道零重复接入成本（代码调研实证 addEntry 为唯一生产调用点）。

### 2.6 双通道降级与信任流程（产品化约束，不随技术简化而放宽）

1. **定位为增强模式、默认关**：对用户不叫「agent」，设置页显示「增强捕获」（技术内部名 `enhancedCaptureEnabled`，`PluginSettings.State` 新增，默认 false；plugin.xml 无需新 EP，project service 注解注册沿 M16.1 规范；开关变化走既有 `SETTINGS_CHANGE_TOPIC` 订阅模式）。未开启增强的用户，体验与现状逐字一致（控制台捕获链零改动）。
2. **注入确认**：首次启用时弹确认（说明目的/采集范围/回退路径/数据留在本机不回传），确认后记忆；取消则维持控制台桥。
3. **数据脱敏**：默认不采集参数值中疑似敏感形态（密码/token 等关键词），脱敏开关供用户开启完整采集。
4. **禁用不卸载**：Instrumentation 不可逆——「禁用」= agent 内全局开关短路（简单可靠），不做卸载还原承诺（尽力而为的 retransform 还原列为可选）。
5. **幂等**：同 pid 只挂一次（实测 JDK8 二次挂载抛异常）。
6. **生命周期**：AgentManager 为 project 级服务（与 `SqlLogManager` 并列），随 project dispose 摘除；进程终止（复用桥 `isProcessAlive` 检测）自动清理 agent 会话；与 capturing 状态机（startCapture/stopCapture/onConsoleRemoved）联动。
7. **增强接管、失败回落**：增强开启且 attach 成功 → agent 为捕获源（桥暂停挂载避免重复采集）；attach 失败/会话结束/关闭增强 → 自动回落控制台桥，零劣化。切换边界以实施期实测确认（两通道同源同 SQL，dedupeKey 指纹天然一致）。

## 3. 子任务

### T-M56-01 agent 基座（P0）
attach 挂载（§2.2 全链）+ agent.jar 骨架（§2.3 JDBC hook 最小集：prepareStatement/setXxx/execute 三族）+ Socket 通道 + 幂等/降级/禁用开关 + 最小注入确认流程。**内置 PoC 门禁**：复用 `attach-probe` 探针思路，runIde 启动 demo 应用 → attach → 事件流到达 IDE 侧并打印（面板集成见 02）。验收：demo 应用 JDBC SQL 事件结构化到达；JDK8 与 JDK17 目标各一次实证；二次挂载幂等；禁用开关生效；attach 失败回退桥零劣化。

### T-M56-02 事件→条目适配与面板集成（P0）

### T-M56-03 跳转精确化（P1，消费端复用 M55-01）

## 8. 不做清单（防范围蔓延）

- **不内嵌 Arthas**（Ultra 59.7MB 路线；本插件 ASM 轻量、无 Arthas telnet/http 服务端面）。
- **不做远程/生产环境 attach**（Arthas 式远程排障超出「IDE 内调试闭环」定位；远程场景即降级桥通道）。
- **不承诺 agent 卸载**（Instrumentation 不可逆，提供禁用语义；还原为尽力而为）。
- **一期不 hook Web 层做请求边界**（T-M56-06 标注可选项；请求上下文一期允许为空）。
- **不做 agent 内 SQL 格式化/高亮**（agent 只采集传输，展示复用 IDE 侧渲染）。
- **不替代模板注入方案**（F-44-6/7 保留为「用户项目零依赖、代码可见」的信任底座与无 attach 环境通道，仅 agent 在线时跳过注入）。
