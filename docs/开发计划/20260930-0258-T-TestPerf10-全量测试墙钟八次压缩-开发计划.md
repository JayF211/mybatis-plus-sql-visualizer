## 三、方案

### S1 权重画像入库（核心件）

**机制缺口**：均衡器权重只来自本树 `build/test-results` 历史 XML（`mpv-testing.gradle.kts:285-307`），缺数据类按「已知权重中位数」插值。新落地的重类（如批次 8 的 UI 类）首轮必然被按 1~2s 量级中位数误判为轻类，所在片被实际超重 10~20s；新工作树首轮更退化为全体同权的类数均分（26% 级失衡先例，`mpv-testing.gradle.kts:260-261`）。历代对策是「冷跑+两轮 warm」人工仪式和跨树借 XML（教训⑥），均为手工且每树每批次重复付费。

**方案**：把「干净一轮的逐类时长画像」作为生成物入库，均衡器在本地数据缺类时回填画像值：

1. 新增 `dev-support/test-shard-weights.tsv`：`FQCN<TAB>秒` 两列，头两部 `#` 注释行记录生成来源（轮次日期、execSum、生成器版本）。由脚本从 clean 轮 XML 生成，**入库的是派生画像，不是原始 XML**——「本地构建数据不入 git」针对的是易污染、机器相关的原始结果；画像值只被均衡器用作相对权重（贪心装箱只需要相对量级，绝对刻度机器间差异不影响均衡），且本地有数据时画像永不覆盖本地值，陈旧画像的退化面=回到现状。
2. `mpv-testing.gradle.kts` 的 `durationWeights` 块加三级回填：`smoothed[it] ?: profile[it] ?: median(known)`。配置期读文件，配置缓存自动追踪该文件输入。
3. 新增 `dev-support/weight-refresh.ps1`：扫 `build/test-results/{test,testShard1..N}` 的 `TEST-*.xml`，同类取 mtime 最新 K=2 份中位数（与均衡器同语义），写 tsv。内置污染闸：本轮分片 execSum 超过阈值（参数，默认 900s）时拒绝生成并提示先鉴别该轮是否被并发构建污染（教训②：clean ≈600s 量级、翻倍即污染），`-Force` 可越过。
4. 本批次 8 后的首份画像：在实施树 S0 干净 warm 轮的 XML 上生成后随本任务入库。

### S2 聚合报告失衡/缺权告警

`testShards` 聚合 doLast（`mpv-testing.gradle.kts:668-737`，纯读 XML 的报告层，不触执行面）追加两条 WARN：

- **失衡告警**：各片实测 exec 的 max/avg 偏差 >12% → WARN 提示权重失准或新类缺权，指向 weight-refresh.ps1；
- **漂移告警**：各片「实测 − 预期」差持续同向且临界片超预期 >10% → WARN 提示权重画像过期或本地样本被污染。

预期 vs 实测对照行已存在（T-TestPerf4），本件只是把「人眼比对日志」固化为机器判据，防止 dev 树 3m07s 这类漂移再次静默发生。

### S3 拆分候选复测（数据件，预期零扩容）

S3 巨类方法级拆分的门槛 = ≥20s 且 ≥30 例。按 20260929 轮实测复测：唯一达标者仍是 SqlPreviewPanelTest（已拆分在役），#2 原子山 ConvertToSqlActionTest 22.2s 只有 3 例，#3 GenerateCrudSqlFromEntityActionTest 20.0s/4 例、PluginSettingsPanelUiTest 19.5s/4 例均不可达——T9「路线死」结论维持，新增批次 8 类无一改变格局。结论入档，零代码。

### S4 AppCDS 尾注执行（时间盒实验，预期销案）

T7 留尾注「动态 archive 对 IPGP classpath 可用性验证一次，<3s 收益即弃」（`20260927-0250-T-TestPerf7-开发计划.md:48,113`），一直未执行。本件时间盒一个窗口内闭环：

- 形态：`-PtestCds=true` 旋钮（缺省不动），分片 JVM 首轮 `-XX:ArchiveClassesAtExit=build/test-cds/shardN.jsa` 落 archive，后续轮 `-XX:SharedArchiveFile` 复用；per-shard 独立 jsa 防五 JVM 并发写同一文件。
- **预登记销案判据（先于实验写死）**：① 插件 jar 因 MPV-Build 时间戳每轮恒重建 → classpath 身份每轮变化，CDS 校验拒绝即静默回退（-Xshare:auto 默认）→ 第二轮读不到命中收益；② 收益 <3s/片；③ 任何一轮出现 CDS 相关失败。命中任一即销案，旋钮按系列惯例保留缺省不动并留注释，不再重试。
- 底线预期：T7 算术否决已给过 2~3s/片上限，本实验大概率销案归档；价值在于把系列最后一个「未实测仅算术否决」的口子用数据关掉。

## 四、待验证前提（实施者先证伪再动手）

1. **失衡根因假说**：临界片超重主因是新类零历史被中位数插值（而非窗口漂移或权重污染）。证伪法：S0 基线轮起跑前打印各片预期 loads 与片内新类（无本地 XML 的类）清单，若预期临界片本就最高且新类确实落在其中，假说成立；若预期均衡而实测仍失衡超 10%，则另有主因（并发膨胀/GC 抖动），S1 仍交付（回填机制独立成立）但 G3 目标下调。
2. **画像回填不改判分片结果集**：回填只动权重、不动类清单与 filter 结构，`discoveredTestClasses` 与 parity 口径零变化——实施时以「回填前后计划类并集相等」断言自证。
3. **tsv 读取与配置缓存兼容**：配置期读文件若引发配置缓存失效风暴或序列化报错，回退为 `providers.fileContents`/inputs 通道（实施时先单跑两轮验证 CC 复用日志）。
4. **AppCDS 在 JBR 17（243 平台测试 JVM runtime）上可用**：`-XX:ArchiveClassesAtExit` 是 JDK 13+ 特性，JBR 17 应具备，未实测——实验第一步先 `-version` 级冒烟，flag 不识别即当场销案。
5. **S0 冷基线可测**：实施树首轮即冷轮（新树无 XML），天然是冷基线；「挪走 test-results 再冷跑」的 A/B 会同时失去 S3 拆分数据（新树同态），对比双方均无拆分，公平性在案。
