## 一、需求背景

当前插件捕获控制台 SQL 日志时，`LogSqlEntry.timestamp` 记录的是**捕获时间**（`System.currentTimeMillis()`，即插件收到日志行的时刻）。用户希望：

1. 同时记录日志行中携带的**原始时间戳**（日志框架打印时的时间）
2. 列表默认显示**日志时间**而非捕获时间
3. 可在设置中切换显示**日志时间**或**捕获时间**
4. 时间戳格式设置（`logTimestampFormat`）同时作用于两种时间的显示
5. 需兼容日志中可能出现的不同时间格式

### 2.4 日志来源与时间格式

不同框架的日志行可能携带不同格式的时间戳：

| 来源 | 典型格式 | 示例 |
|------|----------|------|
| Logback 默认 | `yyyy-MM-dd HH:mm:ss.SSS` | `2024-01-15 10:30:45.123 [thread] DEBUG ...` |
| Log4j2 默认 | `yyyy-MM-dd HH:mm:ss.SSS` | 同上 |
| Spring Boot 默认 | `yyyy-MM-dd HH:mm:ss.SSS` | 同上 |
| p6spy | `yyyy-MM-dd HH:mm:ss.SSS` 或自定义 | 同上 |
| MyBatis-Plus | 通常不带时间（依赖日志框架） | `==> Preparing: SELECT ...` |
| 自定义格式 | 任意 | 用户可配置日志框架输出格式 |

**关键认知**：时间戳是否出现在日志行中、以什么格式出现，取决于用户的日志框架配置。插件无法控制，只能尽力解析。

## 三、技术方案

### 3.1 数据模型扩展

[LogSqlModels.kt](src/main/kotlin/cn/song/mybatisplus/visualizer/log/LogSqlModels.kt) 新增字段：

```kotlin
/** 日志原始时间戳（从日志行中解析，未解析到则为 null）。 */
val logTimestamp: Long? = null,
```

- `timestamp`（捕获时间）保持不变，始终有值
- `logTimestamp`（日志时间）可空，解析失败时为 null
- 历史文件读写需兼容新字段（见 3.4）

### 3.2 日志时间解析

新增 `LogTimestampParser.kt`（log 包内），职责：从日志行中提取时间戳。

**解析策略**（按优先级）：

1. **正则预定义格式匹配**：维护一组常见时间格式的正则 + 对应 `SimpleDateFormat` pattern：
   - `yyyy-MM-dd HH:mm:ss.SSS`（Logback/Log4j2/Spring Boot 默认）
   - `yyyy-MM-dd HH:mm:ss`（无毫秒）
   - `yyyy-MM-dd'T'HH:mm:ss.SSSZ`（ISO 8601，如 `2024-01-15T10:30:45.123+0800`）
   - `yyyy-MM-dd'T'HH:mm:ss.SSSXXX`（ISO 8601 带冒号时区）
   - `dd/MMM/yyyy:HH:mm:ss Z`（Nginx 风格，低优先级）

2. **提取位置**：时间戳通常在日志行**行首**（level 之前），但部分框架可能在其他位置。策略：
   - 先尝试行首匹配
   - 行首未命中时，尝试在 level 关键词（DEBUG/INFO/TRACE/ERROR/WARN）之前匹配
   - 均未命中返回 null

3. **容错**：
   - 解析失败返回 null（不影响现有捕获流程）
   - 不抛异常，不中断日志处理
   - 性能：每条日志行最多尝试 N 个正则（N 为预定义格式数，约 5 个），失败即停

4. **线程安全**：`SimpleDateFormat` 非线程安全，使用 `ThreadLocal<SimpleDateFormat>` 或每次 new（与现有 `formatTimestampFragment` 同范式）

### 3.3 解析器接线

在各日志解析器产出 `LogSqlEntry` 时，调用 `LogTimestampParser.parse(line)` 提取日志时间：

- **MyBatisLogParser**：从 `Preparing:` 行或 `Parameters:` 行解析（取 SQL 行的时间）
- **JdbcTemplateLogParser**：从 `Executing prepared SQL statement` 行解析
- **HibernateLogParser**：从 `Hibernate:` 行解析
- **通用 fallback**：从触发捕获的首行解析

解析时机：在 `closePending()` / `feedIdle()` 产出条目时，将解析出的时间写入 `entry.logTimestamp`。

### 3.4 历史文件兼容

[SqlLogAutoSaver.kt](src/main/kotlin/cn/song/mybatisplus/visualizer/log/SqlLogAutoSaver.kt) 写入文件时：
- 文件头时间戳格式保持 `yyyy-MM-dd HH:mm:ss.SSS` 不变（Reader/正则锚定）
- 条目行新增日志时间字段（若解析到）：格式 `|logTime=<timestamp_ms>`，与现有 `|time=<ms>` 并列
- 未解析到日志时间时，该字段省略（向后兼容）

[SqlLogFileReader.kt](src/main/kotlin/cn/song/mybatisplus/visualizer/log/SqlLogFileReader.kt) 读取时：
- 解析新字段 `logTime`，写入 `SqlHistoryEntry.logTimestamp`
- 旧文件无该字段时，`logTimestamp` 回退为 `timestamp`（捕获时间）

internal fun formatTimestampFragment(entry: LogSqlEntry): Pair<String, SimpleTextAttributes>? {
    val state = PluginSettings.getInstance().state
    if (!state.logTimestampEnabled) return null

        LOG_TIMESTAMP_SOURCE_LOG -> entry.logTimestamp ?: entry.timestamp

    return "[$formatted] " to LIST_META_GRAY
}

## 七、风险与注意事项

1. **时间格式多样性**：无法穷举所有格式。策略：覆盖常见格式 + 解析失败回退捕获时间（fail-open）。用户如有特殊格式，可后续按需扩展。
2. **性能**：每条日志行增加正则匹配开销。预定义格式数量控制在 5 个以内，匹配失败即停，影响可忽略。
3. **历史文件兼容**：新字段需向后兼容旧文件。Reader 遇到无 `logTime` 字段的条目时，`logTimestamp` 回退为 `timestamp`。
4. **与 F3 修复合并**：本计划实施时，F3（历史页时间戳硬编码）应一并修复，避免重复改动 `HistorySqlLogPanel`。
5. **并发场景**：JdbcTemplate 并发日志交错时，时间戳解析应在分桶后按线程独立解析（与 F1 分桶修复配合）。
