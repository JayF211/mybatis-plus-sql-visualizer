## 2. Bug 清单与根因分析

### 2.1 SQL 重复显示

**现象**：`jpqlQuery` 方法预览显示 `SELECT u SELECT u FROM...WHERE d.name = ? uLEFT JOIN...WHERE d.name = ?`（SQL 被重复）。

**根因链**：
1. `HqlConverter.mapFallbackEntityToTable()` 使用 `Regex.replace()` 遍历所有匹配
2. 每次匹配都在**原始字符串**上调用 `replaceFirst()`，而非在累积结果上操作
3. 导致多次替换产生重复输出

**修复**：改用 `find()` + `replaceFirst()` 仅替换第一个匹配。

```kotlin
// 修复前（bug）
private fun mapFallbackEntityToTable(hql: String, table: TableInfo): String {
    val fromPattern = Regex("""\bFROM\s+([A-Z][a-zA-Z0-9_]*)\b""", RegexOption.IGNORE_CASE)
    return fromPattern.replace(hql) { matchResult ->
        val entityName = matchResult.groupValues[1]
        hql.replaceFirst(entityName, table.tableName)  // ← 在原始 hql 上替换，导致重复
    }
}

// 修复后
private fun mapFallbackEntityToTable(hql: String, tableName: String): String {
    val fromPattern = Regex("""\bFROM\s+([A-Z][a-zA-Z0-9_]*)\b""", RegexOption.IGNORE_CASE)
    val match = fromPattern.find(hql) ?: return hql
    val entityName = match.groupValues[1]
    return hql.replaceFirst(entityName, tableName)  // ← 仅替换一次
}
```

**教训**：`Regex.replace()` + 回调内操作原始字符串 = 重复替换。应使用 `find()` + `replaceFirst()`。

### 2.2 字符串拼接表达式被当作字面量

**现象**：`"%" + username + "%"` 被当作字符串字面量，SQL 显示 `LIKE '%"+ username + "%'`。

**根因**：`CriteriaQueryConverter.sqlValue()` 检查 `trimmed.startsWith("\"") && trimmed.endsWith("\"")`，而字符串拼接表达式以 `"` 开头和结尾，被误判为字面量。

**修复**：增加 `!trimmed.contains("+")` 前置条件。

```kotlin
// 修复后
if (!trimmed.contains("+") &&
    ((trimmed.startsWith("'") && trimmed.endsWith("'")) ||
        (trimmed.startsWith("\"") && trimmed.endsWith("\"")))
) {
    // 字符串字面量处理
}
```

**教训**：正则/字符串匹配前，先排除运行时表达式（含 `+`、变量引用等）。

---

### 2.3 多行 HQL 字符串拼接

**现象**：`orderStat` 方法预览显示 Java 代码（`"SELECT..." + "FROM..."`），而非干净 SQL。

**根因**：`HqlQueryLocator.extractHqlString()` 对 `PsiBinaryExpression` 的处理是直接返回 `firstArg.text`（包含 `+` 和引号）。

**修复**：新增 `PsiBinaryExpression` 处理分支 + `collectStringLiterals()` 递归收集所有字符串字面量。

```kotlin
is PsiBinaryExpression -> {
    val parts = collectStringLiterals(firstArg)
    if (parts.isNotEmpty()) parts.joinToString("") to true
    else firstArg.text to false
}
```

**教训**：PSI 树中字符串拼接是 `PsiBinaryExpression`，必须递归收集子节点。

---

### 2.4 参数名显示 `#param1/#param2`

**现象**：位置参数显示 `#param1`、`#param2`，而非实际变量名 `username`、`minAge`。

**根因**：`previewHql()` 使用 `info.parameters.map { it.paramName }`，而位置参数的 `paramName` 是索引（"1"、"2"）。

**修复**：`info.parameters.map { if (it.isPositional) it.valueExpr else it.paramName }`。

**教训**：位置参数的 `paramName` 是索引，`valueExpr` 才是变量名。

---

### 2.5 String 参数不加引号

**现象**：`deptName`（String 类型）输入 `11` 后 SQL 显示 `WHERE d.name = 11`（无引号）。

**根因**：`buildJpaPreviewResult()` 仅在 `inClauseParams.isNotEmpty()` 时生成 `paramHints`，导致非 IN 参数无类型信息。

**修复**：始终根据方法签名参数类型生成 `paramHints`。

```kotlin
val paramHints = if (paramNames.isNotEmpty()) {
    paramNames.map { name ->
        val inList = name in inClauseParams
        val isNumeric = isNumericParam(method, name)
        ParamHint(quote = !isNumeric, inList = inList)
    }
} else emptyList()
```

**教训**：参数类型推断不应仅限于 IN 子句参数。

---

### 2.6 表名显示 `unknown_table`

**现象**：`nativeQuery` 方法预览显示 `FROM unknown_table`。

**根因链**：
1. `createNativeQuery` 不在 `CREATE_QUERY_METHODS` 中 → 完全不识别
2. 即使加入后，`HqlGutterLineMarkerProvider` 的过滤条件 `element.text !in setOf("createQuery", "createNamedQuery")` 不包含 `createNativeQuery`
3. 即使加入后，`CustomDaoHqlGutterLineMarkerProvider` 也会匹配（方法名含 `Query`），导致双图标

**修复**：
- `CREATE_QUERY_METHODS` 加入 `createNativeQuery`
- `HqlGutterLineMarkerProvider` 加入 `createNativeQuery` 匹配
- `CustomDaoHqlGutterLineMarkerProvider` 排除 `createNativeQuery`
- 新增 `previewNativeSql()` 处理原生 SQL（不做实体→表名映射）
- `previewHql()` 双重检测 `isNativeQuery`（标志+方法名 fallback）

**教训**：添加新功能时，必须检查所有相关 provider 的过滤条件，避免遗漏或冲突。

---

### 2.7 gutter 图标重复

**现象**：`createNativeQuery` 行有两个 gutter 图标。

**根因**：`HqlGutterLineMarkerProvider` 和 `CustomDaoHqlGutterLineMarkerProvider` 都匹配了 `createNativeQuery`。

**修复**：`CustomDaoHqlGutterLineMarkerProvider` 排除列表加入 `createNativeQuery`。

**教训**：多个 provider 可能匹配同一元素，必须确保互斥。

---

### 2.8 CriteriaQuery WHERE 出现 Java 代码

**现象**：`cq.where(predicates.toArray(new Predicate[0]))` 导致 WHERE 子句出现 `AND predicates.toArray (new Predicate [0])`。

**根因**：`CriteriaQueryLocator.extractPredicate()` 对非方法调用表达式返回 `PredicateModel.Raw(expr.text)`，而 `predicates.toArray(...)` 是方法调用但不在 `CB_CONDITION_METHODS` 中。

**修复**：
1. `extractPredicate()` 仅处理 `CB_CONDITION_METHODS` 中的方法，其他返回 `null`
2. 新增 `isNestedInParentPredicate()` 检查，避免 `cb.equal()` 在 `cb.not()` 内被重复提取

**教训**：
- PSI 遍历方法体时，中间变量声明（`Predicate p = cb.equal(...)`）也会被当作独立调用提取
- 必须检查调用的父级是否是另一个 CriteriaBuilder 分组方法

---

### 2.9 `status IN ()` 无法输入值

**现象**：`cb.in(root.get("status")).value(statuses)` 渲染为 `IN ()`，面板无法输入。

**根因**：`buildIn()` 只提取 `cb.in(...)` 的直接参数，不处理链式调用 `.value()`。

**修复**：新增 `extractInValuesFromChain()` 提取链式调用参数；无值时添加 `__IN_PLACEHOLDER__` 标记。

**教训**：JPA Criteria API 的链式调用（`cb.in(...).value(...)`）需要特殊处理。

---

### 2.10 单元测试无法覆盖的 Bug

**现象**：多个 bug 在单元测试中通过，但在 IDE 环境中复现。

**根因**：

| Bug | 单元测试场景 | IDE 实际场景 |
|-----|-------------|-------------|
| 表名 `unknown_table` | fixture 类有 `@Table` 注解 | 实体类可能跨模块、注解解析失败 |
| `createNativeQuery` 不识别 | 测试覆盖不全 | 实际代码使用 `createNativeQuery` |
| gutter 图标重复 | 不涉及 PSI gutter 框架 | 实际 PSI 树结构 |
| 参数类型不推断 | 测试只测 `isNumericParam()` | `buildJpaPreviewResult()` 完整链路 |

**教训**：单元测试（测单个函数）≠ 集成测试（测完整链路）。必须补充端到端测试（`PreviewEndToEndTest`）。

```kotlin
fun locate(anchor: PsiElement): HqlQueryInfo? {
    // 路径 1：anchor 是 PsiMethodCallExpression → 精确匹配
    if (anchor is PsiMethodCallExpression) {

```

**关键点**：支持 `PsiMethodCallExpression` 作为 anchor（gutter 导航 handler 传入的是方法调用表达式）。

### 3.3 智能参数类型检查

```kotlin
private fun hasStringHqlArgument(call: PsiMethodCallExpression): Boolean {
    val firstArg = call.argumentList.expressions.firstOrNull() ?: return false
    return when (firstArg) {
        is PsiLiteralExpression -> firstArg.value is String
        is PsiBinaryExpression -> true  // 字符串拼接
        is PsiReferenceExpression -> {
            // 变量引用：仅 String 类型视为有效 HQL 参数
            val resolved = firstArg.resolve()
            if (resolved is PsiVariable) {
                val typeName = resolved.type.canonicalText
                typeName == "java.lang.String" || typeName == "String"
            } else false
        }
        else false  // Class 字面量等
    }
}
```

**关键点**：变量引用时解析其声明类型，仅 String 类型视为有效 HQL 参数，排除 `cb.createQuery(Class)` 和 `em.createQuery(cq)`。

## 4. 踩坑记录

### 4.1 正则替换 + 操作原始字符串 = 重复

```kotlin
// ❌ 错误：在 replace 回调中操作原始字符串
regex.replace(hql) { hql.replaceFirst(old, new) }

// ✅ 正确：find + replaceFirst（仅替换一次）
regex.find(hql)?.let { hql.replaceFirst(old, new) } ?: hql
```

### 4.2 PSI BinaryExpression 的 text 包含 `+` 和引号

```java
"SELECT..." + "FROM..."
```
```kotlin
// ❌ 错误：直接返回 text
else -> firstArg.text to false  // 返回 "SELECT..." + "FROM..."

// ✅ 正确：递归收集字符串字面als
is PsiBinaryExpression -> {
    val parts = collectStringLiterals(firstArg)
    parts.joinToString("") to true
}
```

### 4.3 多个 LineMarkerProvider 的互斥

添加 `createNativeQuery` 支持时，必须同时修改：
1. `HqlQueryLocator.CREATE_QUERY_METHODS`
2. `HqlGutterLineMarkerProvider` 匹配条件
3. `CustomDaoHqlGutterLineMarkerProvider` 排除条件
4. `SqlPreviewService` 新增 `previewNativeSql` 路径

遗漏任何一个都会导致功能异常或双图标。

### 4.4 单元测试通过 ≠ IDE 环境正常

单元测试使用简单的 fixture 类，无法模拟：
- 跨模块实体类解析
- PSI gutter 框架的完整行为
- 多个 provider 的交互

**必须补充端到端测试**：`PreviewEndToEndTest`。

### 4.5 Kotlin `when` 表达式的返回类型

```kotlin
// ❌ 错误：when 表达式分支返回不同类型
return when (firstArg) {
    is PsiLiteralExpression -> firstArg.value is String  // Boolean
    is PsiBinaryExpression -> true  // Boolean
    is PsiReferenceExpression -> { ... }  // Boolean
    else -> false  // Boolean
}
// 编译错误：分支类型不一致

// ✅ 正确：使用 if-else 或统一返回类型
if (firstArg is PsiLiteralExpression) return firstArg.value is String
if (firstArg is PsiBinaryExpression) return true
...
```

### 4.6 链式方法调用的 PSI 结构

```java
cb.in(root.get("status")).value(statuses)
```
```
PsiMethodCallExpression (.value)
  └── qualifier: PsiMethodCallExpression (cb.in)
       └── arguments: [root.get("status")]
  └── arguments: [statuses]
```

提取 IN 值时，需要检查父级是否是 `.value()` 方法调用。
