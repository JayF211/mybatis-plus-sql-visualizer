## 1. 问题与动机（用户反馈，证据驱动）

**用户反馈**：识别生成 SQL 时父类字段顺序需要考虑。用户 BaseEntity 如下（`@TableId` +
两个 `@TableField(fill = ...)` + `@TableLogic`）：

```java
@Data
public abstract class BaseEntity implements Serializable {
    @TableId(type = IdType.AUTO) private Long id;
    @TableField(fill = FieldFill.INSERT, updateStrategy = FieldStrategy.NEVER) private LocalDateTime createTime;
    @TableField(fill = FieldFill.INSERT_UPDATE) private LocalDateTime updateTime;
    @TableLogic private Integer deleted;
}
```

**现状盘点**（M23.2 交付后）：
- `EntityResolver.collectFieldsIncludingSuper`（T-M16.2-02）**父类字段整体前置**（`EntityResolver.kt:74-78`），
  对齐 MP 声明顺序语义——继承实体的 SELECT 全列展开为 `id, create_time, update_time, deleted, <业务字段…>`；
- `TableInfo.columns` 是**单一数据源**，被三处消费：SELECT 全列展开（`SqlGenerator.generateSelect`，
  `SqlGenerator.kt:131-133`）、批量 INSERT/UPDATE/UPSERT 勾选面板与参数行（`BatchOperationConverter`
  → `BatchModel`）、补全/参数对照（`SqlCompletionProvider`）——顺序在哪定义，三处同时生效；
- `ColumnInfo` 现有标记：`isId` / `idTypeAuto` / `fill` / `fieldType` / `comment`；**缺**逐列的角色标记
  （`@TableLogic`/`@Version` 只在 `TableInfo` 侧有列名 `logicDeleteColumn`/`versionColumn`，非逐列标记）。

**方案确认**（AskUserQuestion，2026-08-14）：**A 角色分组固定规则**——`@TableId` 置顶、
`fill ≠ null` 字段与 `@TableLogic`/`@Version` 沉底、业务字段居中，组内保持声明顺序；
零配置、不依赖继承结构、对所有实体统一生效；排除「父类非主键沉底」（规则由字段位置而非
性质决定，不可预期）与「设置项可切换」（多配置面，现状用户默认不变无收益）。

## 2. 设计方案（T-M23.3）

### 2.1 排序规则（角色分组，稳定排序）

新增角色枚举，排序键 `PRIMARY(0) < BUSINESS(1) < AUDIT(2) < SYSTEM(3)`，**组内保持声明顺序**：

| 角色 | 判定 | 位置 |
|------|------|------|
| `PRIMARY` | `@TableId` | 置顶 |
| `BUSINESS` | 其余（默认） | 居中 |
| `AUDIT` | `@TableField(fill = ...)` 非空（T-M15-08 既有提取语义） | 沉底组 1 |
| `SYSTEM` | `@TableLogic` / `@Version` | 沉底组 2 |

用户场景效果：

```sql
-- 现状                                    -- T-M23.3 后
SELECT id, create_time, update_time,      SELECT id, station_id, scheme_name,
       deleted, station_id, scheme_name          create_time, update_time, deleted
FROM biz_bike_station_share_scheme_info   FROM biz_bike_station_share_scheme_info
```

### 2.2 模型（`model/TableInfo.kt`）

- `ColumnInfo` 增加 `role: ColumnRole = ColumnRole.BUSINESS`（默认 BUSINESS——存量构造零影响）；
- 新增 `enum class ColumnRole { PRIMARY, BUSINESS, AUDIT, SYSTEM }`（同文件，data class 之上）。

### 2.3 解析（`psi/EntityResolver.kt`）

- `resolveColumn` 计算 role：`isId` → `PRIMARY`；`fill != null` → `AUDIT`；`@TableLogic`/`@Version`
  标注 → `SYSTEM`（`hasAnnotation` 既有短名兜底复用）；其余 `BUSINESS`；
- `resolve` 收集后稳定排序：`columns.sortedWith(compareBy { it.role })`——Kotlin `sortedWith`
  基于 TimSort **稳定**，组内保持声明顺序（父类在前语义在组内保留）；
- **排序点唯一**（`resolve` 列清单构建处），三处消费点零改动自动统一生效；
- 注释更新：T-M16.2-02「父类字段在前」→ T-M23.3「父类字段在组内保持声明顺序，整体顺序按角色分组」。

### 2.4 影响面与边界（文档化）

- **零影响场景**：无继承/无审计字段实体（组内声明顺序 = 现状）；审计字段本就声明在业务字段之后的实体；
- **统一生效**：SELECT 全列展开、批量勾选面板与参数行、补全——同一 `columns` 数据源；
- **语义零变化**：只影响显示顺序，列集合不变（批量 INSERT 排除 UPDATE 填充列、`@TableLogic`
  自动过滤、`@Version` 乐观锁等逻辑不依赖顺序）；
- fill 判定沿用既有提取语义（T-M15-08：属性文本须含 `FieldFill`）——**字符串形态 fixture**
  （`fill = "INSERT"`）不沉底、真实 MP 注解形态（`FieldFill.INSERT`）沉底，与既有 fill 行为一致，不引入新规则。
