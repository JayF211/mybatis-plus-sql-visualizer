# @Embedded 注解识别补全 — 开发计划

> 来源：2026-09-28 用户要求调研 `@Embedded` 注解（用户反馈插件不能正常识别）。调研结论与证据
> 见同批 `docs/调研报告/20260928-1219-Embedded注解识别-调研报告.md`（下称「调研报告」，
> 缺口编号 G1~G4 与本计划 D1~D4 一一对应）。
> 定位一句话：JPA 基础展平（T-J18）已在库，本计划补三块真实缺口——JPA 规范强制要求的
> 嵌套点路径 `@AttributeOverride`、Spring Data `@Embedded` 专属形态（`@Embedded.Nullable/Empty`
> 与 `prefix`）、MP 路径对混合注解实体的嵌入识别；嵌套 fieldName 降级边界维持登记不改。
> 本计划只动实体解析层（`psi/` 与 `psi/jpa/`），不动转换器、不动 UI、不动数据源校正。

## 一、背景与目标

`@Embedded` 属 JPA（jakarta/javax）与 Spring Data JDBC 两族注解，MyBatis-Plus 无此注解（调研报告 §二）。
插件 JPA 路径已有完整展平实现（T-J18），但存在三处真实缺口：

1. **G1（SD 形态）**：`FQN_RELATIONAL_EMBEDDED` 声明即弃用。裸 `@Embedded` 被 `findFlex`
   短名轨误打误撞命中（行为可用但无测试钉住、`prefix` 丢失）；`@Embedded.Nullable` /
   `@Embedded.Empty` 因 PSI 短名是 `Nullable`/`Empty` 根本不命中，落入伪单列。
2. **G2（点路径覆写）**：规范要求嵌套嵌入的覆写用 `name="zipcode.zip"` 点路径
   （jakarta sources `AttributeOverride.java` Example 2），当前 `overrides[fieldName]`
   只按裸名查找，覆写静默丢失。
3. **G3（MP 路径）**：`EntityResolver` 无嵌入分支，混合注解实体（`@TableName` + `@Embedded`）
   在 Wrapper 预览/批量模板/CRUD 生成里产出 `update_info` 伪列。

目标：三处缺口闭合后，`@Embedded` 在插件全部消费链（HQL/JPQL/Criteria/Querydsl、
Spring Data 派生方法与 Specification、MP Wrapper/批量/CRUD）上按各框架官方语义正确展平。

## 二、待验证前提（实施前先证伪，再动刀）

以下判断来自本轮代码实读与规范文本，但**未经运行验证**，实施者每条先写探针或最小测试证实/证伪，
证伪结论回填本节，推翻的事实要改方案而不是硬做。

1. **SD 链路可达性**：Spring Data Repository 实体（`org.springframework.data.relational...Table`
   标注）经 `JpaGutterLineMarkerProvider` / `ConvertToSqlAction` / `SpecificationQueryConverter`
   到达 `JpaEntityResolver.resolve` 的完整链路未亲证。`JpaMetadataReader.readClassMeta:539`
   已认 `FQN_RELATIONAL_TABLE`，推断链路通。证法：测试夹具建 SD Repository + 嵌入值对象，
   断言 resolve 产物展平列在场。
   → **实施回填：证实**。五形态测试经 `JpaEntityResolver.resolve` 全链路产出展平列（SD Table
   实体注解短名轨命中、嵌入字段展平在场），元数据层可达即下游转换器共链可达（同消费 `TableInfo`）。
2. **`@Embedded.Nullable` 的 PSI 形态**：推断 `annotation.nameReferenceElement?.referenceName`
   对 `@Embedded.Nullable` 取末段 `Nullable`、无法用 `findAnnotation(FQN)` 命中（组合注解不展开）。
   证法：fixture 里打印注解的 `qualifiedName` / `text` / `nameReferenceElement`，据实定匹配策略
   （候选：注解 text 以 `Embedded.Nullable` 结尾，或注解类型的 FQN 匹配 `*.Embedded.Nullable`）。
   → **实施回填：证实（附平台订正）**。262 平台 `PsiAnnotation.qualifiedName`/`getText()` 声明为
   可空（首版实现直接链调编译失败即为证）；夹具无 SD jar 时注解不可解析，匹配落地为双轨——
   可解析按全名 startsWith（真实项目有 SD jar 走此轨）、不可解析按注解文本三形态
   （`@全限定.` / `@全限定(` / `@Embedded.` 短名捷径，jakarta 无点号形态不误伤）。
   可解析轨无夹具直测：`JavaCodeInsightTestFixture` 不在 262 测试 classpath（`addClass` 不可达），
   SD 注解桩注入不可行、测试 classpath 补 SD 依赖=build 脚本改动超出本计划「只动 psi/」边界——登记，
   该轨逻辑简单（两行 startsWith）且与文本轨同函数共用出口。
3. **短名误命中的既有行为**：裸 SD `@Embedded` 目前被 jakarta 轨命中并按 JPA 语义展平——
   这是代码可判的事实（`findFlex:147-154` 第三轨），但零测试钉住。D2 改动必须保证该行为不回归
   （新增显式识别后，裸 `@Embedded` 语义不变，只是 prefix 语义补上）。
   → **实施回填：钉住**。SD 不可解析时裸 `@Embedded` 不认 SD、交 jakarta 短名轨展平（前缀空串），
   五形态测试形态 1 显式断言（`embedded=true` + `embeddedParent` + 展平列名）。
4. **MP 运行时对对象字段的列化行为**：调研报告 §2.3 的口径（平铺为列、不展平）来自官方文档与
   社区共识，未对 `mybatis-plus-core-3.5.17.jar` 反编译逐字节核验。D3 的展平决策不依赖 MP 运行时
   行为（插件口径=跟真实数据库），但验收文档引用该口径前建议 javap `TableInfoHelper` 补硬证据。
   → **实施回填：已补 javap 硬证据**。`TableInfoHelper` 与 `TableFieldInfo` 方法面 embed 字样
   **零命中**（javap 全方法清单 grep，2026-09-28 实测）——MP 元数据层确无嵌入概念，列化只能平铺；
   字节级行为证伪未做（口径引用降为「注解包全清单 + 元数据类方法面」双证据）。
5. **用户具体报障场景未知**：本轮按代码证据定缺口排序（G1/G2 影响列名正确性、G3 影响面最广），
   若用户后续给出具体复现（框架/注解形态/功能入口），以复现场景为最高优先调整实施顺序。
   → **实施回填：维持**。未获用户复现，按 G1/G2（P0）→ G3（P1）顺序全量实施完毕。
6. **Kotlin 实体可用性**：展平递归走 `PsiClassType.resolve()`，对 Kotlin data class（KtLightClass）
   的可用性未验证。既有 T-J18 测试是否覆盖 Kotlin 夹具待查；若未覆盖，D1/D2 的测试补一个
   Kotlin 嵌入夹具（不作为阻塞项，出问题单独登记）。
   → **实施回填：未覆盖，登记**。既有 T-J18 测试同为 Java 夹具，KtLightClass 展平路径改前改后
   风险面等同（递归入口未变）；Kotlin 夹具未补，出问题单独立项。

## 四、任务分解

### D1 JPA 嵌套点路径 @AttributeOverride（对应 G2，P0）

**落点**：`psi/jpa/JpaMetadataReader.kt`（`attributeOverrides:590-606`、`flattenEmbeddableClass:637-668`）、
`psi/jpa/JpaEntityResolver.kt`（`flattenEmbeddedColumns:287-299`）。

**改法**：
1. `flattenEmbeddableClass` 增加 `pathPrefix: String` 参数（实体根起算的点路径，顶层为空串）。
2. 每层查找覆写键两级尝试：`overrides[prefix + fieldName]` → `overrides[fieldName]`（裸名兜底，
   保证既有用例不回归；两级都命中时点路径优先）。
3. 嵌套递归时传 `prefix + field.name + "."`；同时保留「嵌套字段自身 `@AttributeOverride(s)`」的
   相对键查找（现状 `:652`），与类级点路径键**并存**——字段级覆写 name 相对该嵌入对象、类级覆写
   name 相对实体根，两个键空间都要能查。
4. `key.` / `value.` 前缀形态本轮不解析（Map 元素集合展平不在此列，登记）。

**验收**：规范 Example 2（Customer/Address/Zipcode，类级 `zipcode.zip` → `ADDR_ZIP`）夹具绿；
字段级点路径覆写绿；既有裸名覆写用例（`JpaEntityResolverMappingDeepTest.kt:122`）不回归。

### D2 Spring Data @Embedded 形态与 prefix（对应 G1，P0）

**落点**：`psi/jpa/JpaMetadataReader.kt`（`isEmbeddedField:567-573` 附近新增 SD 判定与 prefix 读取、
`flattenEmbeddedColumns:632` 加 prefix 参数）、`psi/jpa/JpaEntityResolver.kt`（`resolveColumns:232-234`
传参）。

**改法**：
1. 新增 SD 嵌入判定：字段注解命中 `FQN_RELATIONAL_EMBEDDED`，或注解 FQN 以
   `.Embedded.Nullable` / `.Embedded.Empty` 结尾（匹配策略以前提 2 证伪结论为准），或
   （保留现状）短名轨兜底。
2. prefix 读取：`attrString(annotation, "prefix")`，展平列名 = `prefix + 内列名`（拼在每一列之前，
   与官方文档一致）；覆写（`@AttributeOverride`）在本轮 SD 轨不展开（SD JDBC 用 `@Column`
   在值对象内部定名，规范与 JPA 覆写不同，登记差异）。
3. 展平复用既有 `flattenEmbeddableClass`（prefix 只在最外层拼一次，嵌套 SD 值对象罕见，嵌套时
   prefix 同样按层传递可留待实测再定）。
4. `onEmpty` 不处理（前提已在 §三范围声明）。

**验收**：SD 夹具五形态——裸 `@Embedded`、`@Embedded.Nullable`、`@Embedded.Empty`、
`prefix` 双嵌入同值对象、无注解嵌套对象（应保持一对一语义不展平，现有 `isNestedEntityOrEntityCollectionField`
行为不动）——全部按官方语义产出列清单；**反向验证**：临时摘掉 SD 识别分支，前四例必红（贴两次读数）。

### D3 MP 路径嵌入识别（对应 G3，P1）

**落点**：`psi/EntityResolver.kt`（`resolveColumn:139-186`；`resolveInternal:106` 的列收集链）。

**改法**：
1. `resolveColumn` 在既有跳过判定（`@TableField(exist=false)`、忽略字段名、serialVersionUID——
   **MP 语义优先，顺序不变**）之后，加嵌入分支：字段类型可解析为 PsiClass 且
   （有 `@Embedded`/`@EmbeddedId` 标注【jakarta/javax/短名，与既有 `findAnnotation` 同模式】
   或类型类有 `@Embeddable`）→ 展平。
2. 展平调用复用 `JpaMetadataReader.flattenEmbeddedColumns`（psi 包可引 psi.jpa，`ColumnNameCalibrator`
   已有跨包先例）；覆写链天然继承 D1/D2 语义。列名兜底 `NamingStrategy.toSnakeCase`，与 JPA 轨一致。
3. 产物 `ColumnInfo` 填 `embedded = true`、`embeddedParent = 字段名`；`@EmbeddedId` 展平列
   `isId = true` 并回填 `TableInfo.compositeIdColumns`。
4. 简单类型字段（String/数值/时间等）零影响——嵌入分支只对 POJO 类型 + 嵌入注解生效，普通字段
   与 MP 注解字段行为逐字节不变；`EntityResolver` 缓存键不用动（PSI 修改戳天然失效）。

**决策记录（推荐 A）**：MP 路径展平跟**真实数据库**而不是 MP 运行时（MP 运行时本身不展平，
写 `@Embedded` 的实体在 DB 侧就是展平列；与 O-58 校正层哲学一致）。若用户认为应严格跟 MP 运行时，
替代方案 B=识别后按非表字段剔除（不出伪列也不出展平列）——实施前如用户未表态，按 A 做。

**验收**：混合注解实体（`@TableName` + jakarta `@Embedded` + `@Embeddable` 值对象 + 嵌套点路径覆写）
夹具：Wrapper 渲染消费的列清单、批量 INSERT 模板列、补全候选均无 `update_info` 伪列且含展平列；
无嵌入注解的 POJO 字段（裸 POJO）行为不变（仍按现状产出单列，不在本计划收窄）；既有 `EntityResolver`
相关测试全绿。

### D4 嵌套 fieldName 完整路径 — 登记不改

维持 `EmbeddedColumnSpec.fieldName` 内名语义与 `embeddedParent` 首段判据（调研报告 §3.3 G4）。
若后续有真实报障指向此处（如某消费链按完整路径反查），单独立项。

### D5 测试与守卫

1. 新增/扩充（全部走定向测试，`--tests "<FQCN>"`，不跑全量、不跑构建校验）：
   - `JpaEntityResolverMappingDeepTest`：SD 五形态（D2 验收清单）、类级/字段级点路径覆写（D1）。
   - `EntityResolver` 侧新建混合注解实体测试类（或就近扩既有）：D3 验收清单。
   - HQL 链加一条「点路径覆写后的列名在属性映射产物中出现」的用例（`HqlAliasColumnMappingTest`）。
2. 守卫：既有 16 处 `Embedded` 断言全绿（防 D1 改递归参数时回归）；裸 SD `@Embedded` 展平行为
   用显式断言钉住（前提 3）。
3. 反向验证：D2 的 SD 识别分支摘除必红（§D2 验收）；D1 的点路径查找摘除（只留裸名）必红。

## 六、风险与回退

- **D1 两级键查找的歧义**：同一内名在裸名与点路径两键同时存在且指向不同列时，点路径优先——
  规范语义下类级点路径更具体，实测若发现真实项目冲突形态，登记后按「最内层覆写优先」再校。
- **D3 对既有消费方的行为面**：展平只新增列、不改既有列；最大风险是补全候选变多（展平列进入
  候选集）与批量 INSERT 模板列数变化——都是修正而非回归，验收用例里显式覆盖。
- **回退**：三处改动均可用摘除新分支回退到现状（D1 留裸名兜底、D2 保留短名轨、D3 嵌入分支
  独立成段），无数据迁移与配置项。
