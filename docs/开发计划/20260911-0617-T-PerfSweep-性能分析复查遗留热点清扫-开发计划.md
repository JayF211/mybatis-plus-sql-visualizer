## 二、改动点

### F1 重放守卫惰性化（P1-2，dev 最高优先）

**现状**（`SqlLogConsoleBridge.kt:331-338`、`ConsoleReplayGuard.kt:52`）：

- `decide(endOffset, docStamp, lineText, line0Text: String?)` 的行 0 参数在调用点以 `context.line0Reader?.invoke()` **急切求值**——每行输出无条件付一次 `doc.getText()`（O(文档大小) 字符串拷贝）+ `lineSequence().firstOrNull()`；
- `docStampReader` lambda 体内每行 `doc.javaClass.getMethod("getModificationStamp")` 重新反射查找（`attachReplayGuard` 挂载时解析一次即可）；`line0Reader` 内的 `getMethod("getText")` 同款。

而 `decide` 只在「endOffset 落回 watermark 之内 **且** stamp 变化」这一罕见混合态分支才需要行 0 文本——重放风暴（长控制台回滚）时每行都在烧这个成本，恰是最热路径。

**方案**：

1. `decide` 签名：`line0Text: String?` → `line0TextProvider: (() -> String?)?`，仅混合态分支内调用；
2. `attachReplayGuard`：`getModificationStamp`/`getText` 两个 `Method` 提到挂载时解析一次，闭包捕获 `Method` 实例（解析失败降级语义不变：读取器为 null，守卫恒 Process）；
3. 行 0 文本按 stamp 失效缓存（闭包内 `lastStamp`/`lastLine0` 两个 var）：重放风暴中同一 stamp 的连续行只做一次全文档拷贝。

**验收**：`ConsoleReplayGuardTest` 全绿且新增「惰性」断言——正常推进（Process）与纯重放（Replay）路径下行 0 提供者**零调用**；混合态路径调用且值正确。

### F2 捕捉热路径 Regex 残留两处

**现状**：

- `JdbcTemplateLogParser.kt:192`：`paramsText.split(Regex("""\s*,\s*(?=\w+\s*=)"""))` 在每条 named 参数条目解析时内联新建 Regex（`T-Perf-23` 提常量时的漏点）；
- `ExecutionTimeParser.kt:77`：配置自定义 timePrefix 时每条 SQL `Regex("""(?i)$escaped\s*(\d+)\s*ms?\b""")` 动态拼接编译。

**方案**：前者提为 companion 常量；后者加 `ConcurrentHashMap<String, Regex>` 按 timePrefix 缓存（键为用户配置串，天然有界；默认前缀路径不经过此处，无影响）。

**验收**：`JdbcTemplateLogParser`/`ExecutionTimeParser` 既有测试全绿（纯等价替换，无行为变化）。

### F3 dedupeCounts 有界化

**现状**（`SqlLogEntryBuffer.kt:46`）：`ConcurrentHashMap<String, Int>` 无上限，条目淘汰后计数不随移除——分析实测十万级去重会话可累积百万级键（键为 16 字符指纹，单键内存小但无界即风险）。

**方案**：换 `LinkedHashMap`（插入序）+ `synchronized` 访问，容量上限 `MAX_DEDUPE_COUNT_KEYS = 4096`，插入超限淘汰最旧键。徽章「本次去重开启以来的总丢弃量」语义在 4096 个不同 SQL 窗口内保持不变；超限淘汰最旧属极端会话（>4096 种不同 SQL 且都发生过重复）的软降级，徽章最多丢最旧键的计数，列表内容不受影响。热点路径锁开销：去重丢弃分支本身低频（重复才计数），EDT 读侧 `dedupeCount`/`dedupeCountsSnapshot` 临界区仅 O(1)/O(n 拷贝)，可接受。

**验收**：`SqlLogEntryBufferTest` 既有计数断言全绿；新增超限测试——插入超过上限个不同键后 `dedupeCountsSnapshot().size == 4096` 且最新键保留、最旧键被淘汰。

### F4 CriteriaQuery gutter 文件级门控

**现状**（`CriteriaQueryGutterLineMarkerProvider.kt`）：provider 已有 `PsiIdentifier` 早退与方法名锚定（`method.nameIdentifier !== element` 早退），循环 `setOf` 已提常量；但对每个**方法定义**仍直调 `locate` 全代码块扫描（daemon 每趟 × 每方法 × 全块 PSI 遍历），且 locate 路径上 `extractEntityClass` 含 `.resolve()`。T-Perf-02 给 CustomDaoHql 做的名字预筛在这里不可复制——CriteriaQuery 构建方法名无特征（任意方法都可能构建）。

**方案**：文件级门控 + 单条目缓存——方法名锚定后先查 `(containingFile, modificationStamp)` 的单条目缓存（`@Volatile` 三个字段，零泄漏），未命中时以 `file.text.contains("riteria")` 判定（覆盖 CriteriaBuilder/CriteriaQuery/criteria 变量名与 import，大小写敏感子串一次匹配）；不含该子串的文件（绝大多数）整体跳过 locate。误放行（字符串/注释里恰好出现）只是回落到现状路径，正确性无损。

**验收**：`CriteriaQueryGutterLineMarkerProviderTest` 与 `CriteriaQueryLocatorTest` 全绿（门控对含 criteria 的文件零行为差异）；无 criteria 文件的跳过路径以单条目缓存命中数（internal 缝）或纯代码评审验证。

## 四、风险与回退

- F1 改 `decide` 公开签名：唯一外部调用方是 Bridge 调用点与 `ConsoleReplayGuardTest` 的 helper，一次改净；降级路径（读取器 null）语义不变。
- F3 换存储结构：`dedupeCountsSnapshot` 的快照语义（返回拷贝）保持；`disableDedupe`/`clear` 的 `resetDedupeCounts` 路径不变。
- F4 单条目缓存非线程安全（daemon 线程模型下单消费者）——最坏情况重复计算一次子串匹配，无正确性影响。
- 每个改动点独立可回退：任一项引发回归即单独 revert 该项，不影响其余。
