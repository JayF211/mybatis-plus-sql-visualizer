## 二、根因（按收益排序）

**R1（主要·2 秒台阶）`projectExecFile` 无差量快路径，且派发有 2 秒有界等待。**
`writeVfTextViaDocument` 只对 `setText` 做了等值判断，`commitDocument + saveDocument` **无条件执行**；
调用侧 `dispatchDocWriteOnEdt` 又是"派发 + 等 2 秒"。于是**内容与磁盘完全一致时也要派发、也要等、也要落盘**——
连续预览同一 SQL（日志 14:17-14:18 五连预览）每次都白付 2 秒 + 一次落盘 + 一次索引噪音。

**R2（我方缺陷）F2 判据失效：`content refresh SKIPPED` 计数为 0。**
`isConsoleAttachedToVf` 依赖 `console.getVirtualFile() === vf`，实机日志里该对象 `toString()={}`（非 vf），
判据从未成立 → 预热每次都按"缓存命中刷内容"改写 exec 文件（写「预览原文」），与 F1 的回填互相覆盖一轮。
**正确判据应为「该 vf 的文档当前正被编辑器打开」**（`EditorFactory.getEditors(doc).isNotEmpty()`）——直接对应
"别改用户眼前的内容"这一意图，且不依赖 DBN 内部方法。

**R3（我方新增开销）F1 回填写入把文档标脏 → 触发 F5 防抖落盘。**
每次预览因此多一次磁盘写 + VFS 事件（`exec doc autosaved` 8 次）。程序性写入不应触发自动落盘，
自动落盘只为**用户手改**（控制台键入）兜底。

**R4（次要）同一内容多路径重复写。** 一次预览里 `prewarm`（BGT）与 `createTempPsiFile`（EDT 冷路径）
都调 `projectExecFile`，内容相同时仍各走一遍 commit+save；`saveDocument` 也未先判 `isDocumentUnsaved`。

**R5（放大项·非本轮引入）文件写入 → 方言 push/PSI 重建 → 进入 dumb 索引。**
每次预览 1~2 次 `enter dumb mode`；减少无效写入（R1/R3/R4）即可连带削减。

## 三、方案

| # | 项 | 改动 | 预期收益 |
|---|----|------|----------|
| P1 | 差量快路径 | `projectExecFile` 派发前先读当前内容（document 文本 / vf 内容）与目标比对，**相同即直接返回，不派发、不落盘**；比对逻辑复用 `syncExecVfContentIfNeeded` 的探测实现 | 连续预览同一 SQL：2 秒台阶归零、落盘 0 次（主要收益） |
| P2 | 预热不阻塞 | `prewarm` 侧派发改 fire-and-forget（或预算降至 200ms）——T-ExecDocSync3 后超时已无副作用；面板侧冷路径保留同步语义 | 即便内容真的变化，BGT 不再白等 2 秒 |
| P3 | F2 判据修正 | `isConsoleAttachedToVf` 改用「该 vf 文档正被编辑器打开」判据（`EditorFactory.getEditors`），修掉计数为 0 的实现缺陷 | 预热不再与回填互相覆盖，减一次写入+索引 |
| P4 | 抑制程序性自动落盘 | F1 回填/插件写入期间置 `suppressExecAutosave` 标志（时间窗或显式开关），仅用户手改才排防抖落盘 | 每次预览少一次落盘 |
| P5 | 落盘去重 | `saveDocument` 前判 `isDocumentUnsaved`；同一内容短时间多次写入合并（P1 落地后基本无重复写） | 减少写盘与 VFS 事件 |
| P6 | 渲染去抖 | F1 回填渲染与 DBN attach 后的 DBN 自身刷新合并（同内容短路，避免 2.2s / 4.3s 两次 showSql） | EDT 上少一次全量渲染 |
| P7 | 度量 | 新增统一耗时埋点：`preview click → dialog → console visible` 三段耗时落日志（现只有零散阶段日志） | 验收可量化 + 后续回归可视 |

## 四、验收标准

1. **量化**（新构建真机日志，10 次连续预览）：
   - `exec doc write EDT dispatch timeout` 出现次数 **0**；
   - 同内容预览的 `exec file updated via document+save` 次数 **0**（内容变化时 1）；
   - `exec doc autosaved` 仅在用户手改控制台后出现；
   - 点击 → 控制台 SQL 可见 ≤ **500ms**（冷启动首帧索引期除外，且不得出现固定 2 秒台阶）。
2. 功能不回归：预览仍显格式化（T-PreviewConsoleFmt 守护用例）、File Cache Conflict 仍零复发（T-ExecDocSync3 行为）、
   执行内容仍取编辑器所见。
3. 门禁：全量 `test` 绿 + `testDatabase` 绿（DB 链改动双跑口径）。

## 六、风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 差量快路径误判导致内容陈旧 | P1 跳过写盘后，若判据把"分叉"当"一致"，控制台/执行会拿到旧 SQL | 判据复用 `syncExecVfContentIfNeeded` 同款探测（doc 文本 + vf 内容双源）；执行前 `executeOnConsole` 仍有同步兜底；用例覆盖分叉场景 |
| P2 改 fire-and-forget 后内容更新延迟 | BGT 不再等 EDT —— 内容最终由排队任务落盘 | T-ExecDocSync3 已使超时无害；面板渲染链（F1）与执行前同步是内容权威 |
| P3 判据换新引入误判 | 「文档被编辑器打开」在控制台隐藏时可能为真 | 目标是"别改用户眼前内容"，保守即为安全方向（宁可少刷新） |
| P4 抑制过度 | 用户手改未被自动落盘 → 回到"已修改未保存"窗口 | suppress 只覆盖程序性写入的调用栈（显式开关 + finally 复位），用户键入路径不置位 |
| 陈旧产物劫持 | 新增 internal 函数首跑 NoSuchMethodError | 首跑前清 `build/classes` + `build/kotlin` |

## 八、附：本轮已定位但不在本计划范围

- `content refresh SKIPPED` = 0 说明 T-PreviewConsoleFmt 的 F2 **未生效**（判据错），
  但 F1 回填已使显示正确——F2 修正（P3）属本计划范围，避免预热与回填互相覆盖。
- 预热写「预览原文」而面板渲染格式化文本这一"双文本源"结构是 R2/R3 的土壤；
  根治方向（二期议题）：统一由面板渲染文本作为 exec 文件内容的唯一权威。
