## 一、背景与目标

Mybatis-Flex-Helper（Marketplace 1.8 万下载）证明 Flex 生态存在与本项目同构的「QueryWrapper → SQL 预览」需求。若本项目解析器抽象层可低成本接入 Flex，边际获客可观；若需大改 converter 层，则放弃。

**产出**：一份独立调研报告（`docs/开发计划/{时间戳}-MyBatis-Flex支持可行性-调研报告.md`）。**门槛**：结论为「可低成本复用」（FlexConverter 增量维护 < 现有 MP 系 15%）才立项子计划，否则记录放弃理由归档。

---

## 二、调研项

### 2.1 API 结构差异（方法名以本地 jar 反编译为唯一权威）

- Maven Central 拉取 mybatis-flex-core 最新版 jar → javap 反编译 `QueryWrapper/QueryCondition/Joiner` 全量方法签名。
- 与 MP `AbstractWrapper/QueryWrapper/LambdaQueryWrapper` 逐方法对照：链式语义、条件组合方式（and/or 的 API 形态）、join 写法、函数列/原生片段。

### 2.2 解析器抽象层改造点

- 现有 converter SPI（`WrapperType/WrapperArg/Condition` 模型 + 9 个 converter）中，哪些环节硬编码了 MP 概念（`AbstractWrapper` 类型判定、Lambda 取列名的 SerializedLambda 解析等）。
- 评估：FlexConverter 是新增实现即可，还是需先抽 `WrapperDialect` 中间层（后者成本陡增）。

### 2.3 生态与用户重叠

- Marketplace：Mybatis-Flex-Helper 功能边界（它做到哪、缺哪）。
- Flex GitHub star 数/issue 活跃度，与本插件目标用户（MP 用户）重叠估计。
- Flex 官方是否已有内置预览路线（MyBatis-Flex-Helper 是否社区官方背书）。

### 2.4 风险项

- Flex 生态规模是否足以覆盖维护成本；双框架支持对「MyBatis-Plus 专属」定位描述的影响（更名后为 SQL Visualizer，定位冲突小，但描述需调整）。
