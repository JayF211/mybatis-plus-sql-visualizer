# M38 Flex 精华吸收体验优化开发计划

> **创建日期**：2026-09-02
> **归属**：P-立项-06 N-5 的延续——M37.5 结论「不做 Flex 用户支持」仍然成立（报告 `20260902-0120-MyBatis-Flex支持可行性-调研报告.md`）；本计划是**反向吸收**：把 Flex 生态验证过的好设计拿来服务现有 MP 用户。
> **调研来源**：Mybatis-Flex-Helper（Marketplace 18116 下载/4.32 分，Gitee djxchi/mybatis-flex-code-gen）功能与迭代史 + mybatis-flex.com 文档语义对照表 + flex-core 1.11.8 jar 反编译。
> **优先级**：P0 两项均为低成本高确定性（其中 M38.1 直接对应竞品真实差评）。

---

## 一、吸收逻辑：相似且可吸收的判定

Flex 精华很多，但只有与「Wrapper→SQL 静态预览 + 日志还原 + 执行」定位**相似**的才吸收。排除项先行：

- 逻辑删除/多租户/脱敏/多数据源等**运行时能力**——MP 自有体系，本插件已有拦截器模拟覆盖展示面，不再扩展。
- TableDef/APT 静态列补全——MP 无对应概念，Flex-Helper 的 APT 链路（mvn clean 失效、多模块误扫）恰是其维护负担，不学。
- Db+Row 弱类型模式——MP 无对应，跳过。

留下的五个吸收点及来源：

| # | 吸收点 | 来源 | 性质 |
|---|--------|------|------|
| A1 | gutter 锚点**误报回归集** | Flex-Helper 真实差评（import 行也弹 icon） | 质量 |
| A2 | **语义对照金样矩阵**（Wrapper API × 期望 SQL） | Flex 文档逐 API 标注生成 SQL 的做法——业界最完整的 Wrapper→SQL 规格表 | 质量/营销 |
| A3 | 原生片段（apply {i} 绑定）参数链路查漏 | Flex toSQL()「一步完整 SQL」体验 | 体验 |
| A4 | 触发面（表达式入口）资产化 | Flex-Helper 被"只支持 QueryWrapper"追加需求拖着走的迭代史 | 架构 |
| A5 | 描述页能力对照话术 | Flex-Helper 没做完的"日志还原+预览闭环"正是本插件强项 | 营销 |

## 三、各里程碑要点

### M38.1 gutter 锚点负例回归集（A1）

**现状**：9 个 lineMarkerProvider 共用 `WrapperAnchorDetector.anchorElement()` O(1) 语法判定；Flex-Helper 的教训是误报（import 行弹图标）直接变成差评，而锚点误报**没有任何现有测试锁定**。

**做法**：
- 新增 `WrapperAnchorDetectorNegativeTest`：负例矩阵——import/import static 语句、行注释/块注释/Javadoc、字符串字面量内的方法名文本、字段**声明类型位**（`QueryWrapper<User> w;` 的类型名）、泛型实参位、方法参数列表类型位、纯 lambda 体内部、switch/case 标签。
- 9 个 provider 的锚点入口各过一遍矩阵（Wrapper/XML/注解/JPA 各族的判定入口不同，负例共性抽 helper）。
- 不改实现——若矩阵暴露真实误报，单独立 bug 修复项（与 M37.0 参数回归同策略）。

**验收**：负例矩阵全绿（无误报）；矩阵内每场景有注释说明"为什么这里不该有锚点"。

### M38.2 语义对照金样矩阵（A2）

**现状**：解析器测试按类组织（各 converter 自己的用例），没有一张「Wrapper API 全集 × 期望 SQL」的对照规格。Flex 文档把每个 API 的生成 SQL 写死在文档里——证明这种转换可作纯函数规格化，本插件缺这张表。

**做法**：
- 新增 `sql/spec/` 测试包 + 一张驱动表（数据驱动用例）：`api | 场景代码片段 | 期望 SQL 快照`。
- 覆盖维度（对齐 MP API 全集，参照 Flex 语义表结构分面）：条件族（eq/ne/gt/ge/lt/le/like 系列/in/notIn/between/isNull/isNotNull/exists/apply/applyFunc/last）、连接词（and/or 嵌套/括号）、select 投影（lambda/字符串/聚合/别名）、分页/排序/分组、批量（saveBatch/updateById）按方言。
- 快照断言（期望 SQL 为字面常量）+ 9 方言只对代表性子集展开（复用 M37.0 真机通道做抽样背书）。
- **滚动提交**：按条件族→投影→分批，每批独立可绿，避免一次大提交。

**验收**：矩阵 ≥ 80 个场景；`gradlew test` 全绿；金样文件注释标注来源（MP 版本 3.5.17 语义）。

### M38.3 apply {i} 绑定参数链路查漏（A3）

**现状**：`apply("…{0}…", val)` 已解析且挂复选框（T-M15-03 布尔前缀 + {i} 绑定）。
**查漏点**：{i} 参数在预览面板**参数回填/内联链路**是否与普通 ? 参数一致（Flex toSQL() 的体验标准是"一步拿到完整可执行 SQL"）；多 {i} 与布尔 toggle 组合、{i} 值含引号的转义。
**做法**：先写现状用例探路，缺什么补什么（预计是小修），不做架构改动。

### M38.4 触发面资产化（A4）

**做法**：
- `docs/架构设计/` 新增「预览触发面清单」：9 个 provider 的入口场景矩阵（链式/变量/工厂/服务链/测试类内/Kotlin），每行标注判定入口与测试类。
- 现有测试按该矩阵对号入座（只组织，不改逻辑），新增入口时按清单登记——把 Flex-Helper 的教训变成流程资产。

### M38.5 描述页对照话术（A5）

- README/marketplace 描述加"能力对照"小节：静态预览、日志还原、SQL→Java、原生执行、预览↔源码互跳、历史面板——只列自己能力，不点名对比竞品。
- 覆盖"编码期预览 + 运行期回看"两个刚需场景的表述（Flex-Helper 1.4 加日志功能验证了双刚需同源）。

## 四、验证策略

- M38.1/M38.2 产出全部为测试，随常规分片跑；金样矩阵新测试类加入最小编号分片（build.gradle.kts 分片清单维护）。

## 五、风险

1. **金样矩阵维护成本**——期望 SQL 是手工快照，MP 升级语义变化时会批量翻红；对策：矩阵标注 MP 版本基线（3.5.17），升级时按 diff 审阅而非直接重生成。
2. **负例矩阵误伤**——某些"看似不该有锚点"的位置实际是合法入口（如测试类内的 wrapper 链）；矩阵先于实现冻结期望，红了走讨论不直接改判定。
3. Flex-Helper 4.32 分的教训本身是风险提示：**工程细节决定口碑**——本里程碑全是细节项，不为凑数扩面。

## 六、不做清单

- 不做 Flex 语法/锚点支持（M37.5 结论不变）。
- 不做 APT/TableDef 类生成物依赖（MP 生态无此概念，且是其维护负担来源）。
- 不做描述页对竞品的点名对比（合规与口碑风险）。
