# HQL 自定义 DAO「拼接变量」无预览图标 修复开发计划

> 源自 2026-09-03 用户反馈（微信截图 5 张）：`String hql = "select" + " ..."` 拼接初始化后传给自定义 DAO 方法 `commonDao.findByQueryUniqueResult(hql, ...)`，gutter 不显示 SQL 预览图标；手动触发插件动作弹"未在光标处找到 MyBatis-Plus Wrapper 调用或 IService/BaseMapper 内置方法"。

## 背景与现状

用户代码形态（老式 Spring DAO 统计查询，截图 1/3）：

```java
String hql = "select count(case when booking.status = 'F' then 0 end)" +
             " ... from WmsDockBooking booking" +
             " left join WmsAsn asn on asn.id = booking.relatedBillId" +
             " where booking.warehouseId = :warehouseId and ...";
Object[] stats = (Object[]) commonDao.findByQueryUniqueResult(hql,
    new String[]{"warehouseId", "startTime", "endTime"},
    new Object[]{warehouseId, startTime, endTime});
```

相关链路（已逐行核实）：

| 环节 | 代码位置 | 现状 |
|------|---------|------|
| gutter 图标 | `CustomDaoHqlGutterLineMarkerProvider.getLineMarkerInfo` | 锚调用方法名 identifier，`CustomDaoHqlLocator.locate(call) == null` 则不出图标 |
| 三重启发 | `CustomDaoHqlLocator.isCustomDaoHqlCall` | qualifier `commonDao` 尾缀 `Dao` ✓；方法名含 `Query` ✓；**内容启发 ✗** |
| 内容启发 | `matchesHqlContent` → `extractArgumentText` | PsiReferenceExpression 分支只认 `PsiLiteralExpression` 初始化式，拼接初始化式回退变量名 |
| 字符串提取 | `extractHqlFromCall` → `extractHqlString` | **已递归**（PsiReferenceExpression → `extractHqlString(initializer)` → Binary/Polyadic → `collectStringLiterals`）✓ |
| 标准 createQuery 对照 | `HqlQueryLocator.extractHqlString` | 2026-09-02 T-HqlVarResolve-01 已修复同款缺口（0e9f0aa）✓ |

## 根因

`CustomDaoHqlLocator` 内部两个字符串提取函数逻辑分叉：

- `extractHqlString`（供 locate 后提取 HQL 用）已递归处理变量引用的拼接初始化式——2026-09-02 计划 T-HqlVarResolve-03 复核结论"无需改动"正确；
- `extractArgumentText`（供**内容启发**判定用）仍停留在只认字面量初始化式：
  `resolve()` 后 `initializer is PsiLiteralExpression` 才取值，否则回退 `expression.referenceName`（即 `"hql"`）。

结果：`matchesHqlContent` 拿到的文本是 `"hql"`，与 `HQL_CONTENT_PATTERNS`（SELECT…FROM / UPDATE…SET 等）全部不匹配 → `isCustomDaoHqlCall = false` → `locate() = null`。同一根因双出口：

1. **gutter 图标**：`CustomDaoHqlGutterLineMarkerProvider` 判定 null，不出图标（截图 1 无图标）；
2. **手动触发**：action → `SqlPreviewService.previewCustomDaoHql`（SqlPreviewService.kt:534）`locate` 返回 null → 弹通用"未找到 Wrapper/IService/BaseMapper"提示（截图 3 的弹窗）。

即：T-HqlVarResolve 复查时只看了提取函数，**漏了与它并行的内容启发函数**，同源缺口在自定义 DAO 路径上仍然生效。

次要问题（同截图代码）：参数以「名字数组 + 值数组」两参传递（`new String[]{...}` + `new Object[]{...}`），`detectParamSource` 判为 `POSITIONAL`，参数面板 valueExpr 会显示 `new String[]{...}` 整体文本而非 `warehouseId` 实际变量——修复图标后需一并处理，否则预览面板参数对照错误。

## 目标

1. 拼接变量（`String hql = "a" + "b"`）作为自定义 DAO HQL 调用首参时，gutter 图标正常显示、点击预览展开完整 HQL（主任务）。
2. 名字数组+值数组参数模式正确解析进参数面板（同场景联动修复）。
3. 标准 `createQuery(hql)` 路径回归确认不受影响（0e9f0aa 已覆盖，验证为主）。

## 任务

### T-HQLGutter-01 内容启发与提取单一来源对齐（核心修复）

- `CustomDaoHqlLocator.extractArgumentText` 改为直接委托 `extractHqlString(expression).first`：
  两个函数的字面量/拼接/变量分支语义逐条核对一致（literal 取 value 否则 text；拼接递归 `collectStringLiterals`；变量 resolve 有 initializer 递归、无则变量名；其余取 text），委托后消除双逻辑再次分叉。
- 若委托后 `extractArgumentText` 无独立调用点之外的用途，删除该函数体保留委托壳（调用点：`matchesHqlContent` 一处），改签名注释说明与 `extractHqlString` 共享逻辑。
- `extractHqlString` 保持不变（已有递归）。

### T-HQLGutter-02 名字数组+值数组参数模式（ParamSource 扩展）

- `detectParamSource` 新增分支：`extraParams.size == 2` 且第一个是字符串数组创建（`PsiNewExpression` 的数组初始化元素全部为字符串字面量）→ `ParamSource.NAME_VALUE_ARRAYS`。
- `resolveParameters` 新增 NAME_VALUE_ARRAYS 处理：从名字数组取名字序列，值数组按索引取元素文本作 `valueExpr`（`isPositional=false`），与 HQL `:paramName` 按名匹配。
- 枚举注释补该模式说明；`customDaoHql` 预览链路无需改动（参数表由 `info.parameters` 驱动）。
- 数组元素取文本统一走 `expression.text`（变量引用/方法调用/字面量均可）。
