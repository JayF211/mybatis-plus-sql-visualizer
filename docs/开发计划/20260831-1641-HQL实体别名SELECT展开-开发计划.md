> **创建日期**：2026-08-31 16:41
> **触发**：用户实测 HQL 预览生成的 SQL 在 MySQL 控制台执行失败（`[42S22][1054] Unknown column 'u' in 'field list'`）
> **前置**：M36.6 系列（`20260830-0038-M36.6-SQL预览原生控制台收尾-开发计划.md`）

## 一、问题复现

### 1.1 输入代码

```java
public List<UserEntity> hibernateHql(String username) {
    Session session = entityManager.unwrap(Session.class);
    Query<UserEntity> query = session.createQuery(
        "SELECT u FROM UserEntity u WHERE u.username = :username", UserEntity.class);
    query.setParameter("username", username);
    return query.getResultList();
}
```

### 1.2 面板生成 + 控制台执行结果

```
mpj_demo> SELECT u FROM user u WHERE u.username = 1
[2026-08-31 16:39:43] [42S22][1054] Unknown column 'u' in 'field list'
```

### 1.3 期望结果（Hibernate 真实行为）

```sql
SELECT u.id, u.username, u.password, u.create_time, ...
FROM user u
WHERE u.username = 'admin'
```

Hibernate 对 `SELECT u` 的处理是**取整个实体**，即展开为该实体映射的全部列；同时（若有 `@TableLogic`）隐式追加 `deleted = 0`。

## 二、根因分析

### 2.1 根因 A（P0，必现，直接致错）：HqlConverter 缺失 SELECT 子句展开步骤

**证据（grep 实证）**：`HqlConverter.kt` 全文 **0 处** `SELECT`/`select` 处理。

`convert()` 现有十步流水线：

| 步骤 | 处理 | 状态 |
|------|------|------|
| 1 | 命名参数 `:param` → `?` | 已实现 |
| 2 | 位置参数 `?1` → `?` | 已实现 |
| 3 | `IN ?` → `IN (?)` | 已实现 |
| 4 | `NEW DTO(...)` 提取构造参数 | 已实现 |
| 5 | `JOIN FETCH` → `LEFT JOIN` | 已实现 |
| 6 | `MEMBER OF` 降级注释 | 已实现 |
| 7 | 实体名 → 表名 | 已实现 |
| 8 | 关联字段路径 `alias.field.id` → 外键列 | 已实现 |
| 9 | 属性名 → 列名 | 已实现 |
| 10 | DELETE 检测 | 已实现 |
| **—** | **`SELECT <实体别名>` → 列清单展开** | **缺失** |

**机制**：步骤 7 把 `UserEntity` → `user`（正确），步骤 9 把 `.username` → 列名（正确），
但 `SELECT u` 中的别名 `u` 无人处理，原样输出。MySQL 解析器在 `SELECT` 后的字段列表中
遇到裸标识符 `u`，按列名解析 → 报 `Unknown column 'u' in 'field list'`。

**影响面**：所有「`SELECT 别名`」形态的 HQL 全军覆没——这是 HQL 最常见的写法
（`session.createQuery("FROM Xxx x WHERE ...")` 与 `SELECT x FROM Xxx x` 占绝大多数）。
`SELECT x.id, x.name` 这种显式列写法不受影响。

### 2.2 根因 B（P1，需沙盒取证）：String 参数回填未加引号

现象：`WHERE u.username = 1`，而 `username` 是 `String` 类型参数，应为 `= '1'`。

按代码推理**本不该发生**——`buildJpaPreviewResult`（`SqlPreviewService.kt:590-597`）
对 `String username` 应算出 `ParamHint(quote = true)`，面板 `renderSingleValue`
（`SqlPreviewPanel.kt:2056`）会输出 `'1'`。因此实际断点需在沙盒取证，候选三处：

| # | 候选断点 | 取证方式 |
|---|---------|---------|
| B1 | `paramNames` 解析为空 → `paramHints` 为空 → 走 `NUMBER_REGEX` 数字启发式，`1` 判为数值裸渲染 | 面板「参数」区是否出现 `username` 输入行；无输入行即命中 |
| B2 | `info.method` 为 `null`（`HqlQueryLocator` 未解析出 `PsiMethod`）→ `isNumericParam` 返回 false → quote 应为 true，**与现象矛盾**，可先排除 | 日志打 `method=` |
| B3 | 用户直接在原生控制台编辑器里手改 SQL 把 `?` 替换成 `1`（控制台可编辑），非插件路径 | 复现时先不改编辑器内容，直接执行 |

**处置**：B1/B2 在根因 A 修复后同轮取证（面板能打出可执行 SQL 才有意义）；B3 属使用方式问题，
不计入缺陷但应在文档中说明「参数请在参数区填写」。

### 2.3 根因 C（P2，保真度）：HQL 隐式逻辑删除条件未追加

实体带 `@TableLogic` 时，Hibernate 对 `SELECT u FROM UserEntity u` 的真实 SQL 会追加
`WHERE u.deleted = 0`。当前转换器完全不知道 `TableInfo.logicDeleteColumn` 的存在，
生成的 SQL 会查出已逻辑删除的数据——**不报错但结果集偏大**，属于「静默失真」，比报错更隐蔽。

### 2.4 根因 D（P2，边界）：HQL 无 SELECT 子句时的隐式查询

`FROM UserEntity u WHERE u.username = :username` 是合法 HQL（Hibernate 隐式 `SELECT u`），
当前转换器输出 `FROM user u WHERE ...`，缺 `SELECT` 子句 → MySQL 语法错误。
注：`HqlConverterTest` 现有用例 `from UserEntity u where u.username = :username`
只断言 `contains("from")`，未断言可执行性，故该缺陷被漏过。

## 三、目标与非目标

### 3.1 目标

1. `SELECT <别名>` / 无 SELECT 子句 → 展开为带别名前缀的列清单，生成的 SQL 可直接在 MySQL 执行。
2. 有 `@TableLogic` 时追加逻辑删除条件，使结果集与 Hibernate 真实行为一致。
3. 实体元数据不可解析时降级为 `<alias>.*`，保证 SQL 至少语法正确。
4. 全量单测无回归，新增用例覆盖各类 SELECT 形态。

### 3.2 非目标

- 不重构为「条件树 + SqlGenerator」架构。现有设计注释已明确：HQL 转换器不做条件树解析，
  WHERE 子句是自由文本，必须走字符串级变换（`HqlConverter` 类注释第 21-22 行）。
  本次继续沿用字符串级方案，与既有设计一致。
- 不处理 HQL 聚合函数之外的复杂投影语义（如 `SELECT new map(...)` 的多态展开）。
- 不处理继承映射（`@Inheritance` 的 JOINED/SINGLE_TABLE 歧义），保持现状不加支持也不加提示。

## 四、任务详单

### T-01 SELECT 子句展开引擎（P0）

**位置**：`HqlConverter.kt` 新增 `expandSelectClause(sql, table)`，插入 `convert()` 流水线
**步骤 9 之后、步骤 10（DELETE 检测）之前**。

#### 4.1 识别：哪些 SELECT 项需要展开

先定位 SELECT 子句范围（从 `SELECT` 到最近的一个顶层 `FROM`，大小写不敏感，
用括号计数跳过函数嵌套）。取出 SELECT 项列表（按顶层逗号切分），逐项判定：

| SELECT 项形态 | 是否展开 | 说明 |
|--------------|---------|------|
| `u`（裸别名，无点号、非函数、非字面量） | **展开** | 核心场景 |
| `u.id`、`u.name` | 否 | 已是列引用 |
| `count(u)`、`count(*)`、`sum(u.age)` 等函数调用 | 否 | 含 `(` |
| `u.id + 1`、`u.name || 'x'` 等表达式 | 否 | 含运算符 |
| `'literal'`、`123`、`null` | 否 | 字面量 |
| `u.department.name`（关联路径） | 否 | 步骤 8 已加注释提示 |

判定规则（保守优先）：
**仅当该项匹配 `^[a-zA-Z_][a-zA-Z0-9_]*$`（纯标识符）且该标识符是本次查询的实体别名时展开。**

#### 4.2 别名来源

优先从 `FROM` 子句解析：`FROM <table> <alias>`（可选 `AS`）。
多表 JOIN 场景按 `JOIN <table> <alias>` 逐个收集别名→实体的映射。
若某别名找不到对应实体（如子查询别名），跳过不展开。

#### 4.3 展开规则

| 条件 | 输出 |
|------|------|
| 别名对应实体有 `columns` | `u.col1, u.col2, ...`（属性→列名已由步骤 9 之前的 `columns` 提供；注意此处取 `columnName` 而非 `fieldName`） |
| 别名对应实体 `columns` 为空（元数据不可解析） | `u.*` |

**列顺序**：沿用 `TableInfo.columns` 声明顺序（与 `SqlGenerator.kt:135` 的
`SELECT *` 展开一致），主键已在实体解析阶段置顶（`ColumnRole.PRIMARY` 排序），无需重复处理。

**多别名展开**：`SELECT u, d FROM ... JOIN FETCH u.department d` →
`SELECT u.id, u.username, ..., d.id, d.name, ...`。

**执行顺序注意**：步骤 5（`handleJoinFetch`）已把 `JOIN FETCH u.department d` 改写成
`LEFT JOIN department d ON ...`，所以展开在步骤 9 之后执行时，FROM/JOIN 子句的别名已是最终形态，
解析别名应基于**步骤 9 之后的 SQL**，而不是原始 HQL。这一点必须在实现时确认，否则 JOIN 别名取不到。

#### 4.4 边界用例（全部进单测）

| # | 输入 HQL | 期望输出 SQL |
|---|---------|-------------|
| 1 | `SELECT u FROM UserEntity u WHERE u.username = :username` | `SELECT u.id, u.username, ... FROM user u WHERE u.username = ?` |
| 2 | `FROM UserEntity u WHERE u.username = :username` | `SELECT u.id, u.username, ... FROM user u WHERE ...` |
| 3 | `SELECT DISTINCT u FROM UserEntity u` | `SELECT DISTINCT u.id, u.username, ... FROM user u` |
| 4 | `SELECT u.id, u.username FROM UserEntity u` | 原样不展开 |
| 5 | `SELECT count(u) FROM UserEntity u` | 原样不展开 |
| 6 | `SELECT u FROM UserEntity u JOIN FETCH u.department d` | `SELECT u.id, ..., d.id, ... FROM user u LEFT JOIN department d ON ...` |
| 7 | `SELECT u, d FROM UserEntity u JOIN FETCH u.department d` | 两个别名均展开 |
| 8 | 实体 `columns` 为空 + `SELECT u` | `SELECT u.* FROM user u` |
| 9 | `DELETE FROM UserEntity u WHERE u.id = :id` | **不展开**（DELETE 无 SELECT 子句，步骤 10 前必须跳过） |
| 10 | `SELECT u FROM UserEntity u WHERE u.id IN :ids` | 展开 + `IN (?)` 保持 |

**验收**：用例 1 的输出贴入 MySQL 可直接执行返回结果集。

### T-02 参数引号取证与修复（P1）

**前置**：T-01 完成（否则 SQL 本身跑不通，引号问题被 1054 掩盖）。

**步骤**：

1. 沙盒打开该 HQL 预览，观察面板「参数」区是否出现 `username` 输入行：
   - **无输入行** → 命中 B1：`paramNames` 为空。查 `HqlQueryLocator` 为何未解析出
     `query.setParameter("username", username)`（疑点：`Query` 对象经局部变量 `query`
     中转，`locate` 的变量追踪可能未回溯到 `session.createQuery(...)`）。
     修复方向：`setParameter` 回溯支持局部变量链式赋值；或保证
     `extractParamNamesFromHql` 兜底恒生效。
   - **有输入行但输入 `1` 后仍输出裸 `1`** → 查 `isNumericParam` 与 `info.method`，
     必要时对 JPA 路径改为「以实体字段 `fieldType` 判定引号」（`ColumnInfo.fieldType`
     已有该信息，比方法参数类型更准，可参考 XML 路径的 `XmlParamTypeResolver` 做法）。
2. 修复后回归 `HqlConverterParamTest` 与 `SqlPreviewServiceJpaTest`。

**验收**：`String` 参数输入 `1` → `= '1'`；`Long/Integer` 参数输入 `1` → `= 1`。

### T-03 隐式逻辑删除条件追加（P2）

**步骤**：

1. `convert()` 末尾（展开之后、返回之前）检测 `table.logicDeleteColumn != null`：
   - 生成的 SQL 已有 `WHERE` → 追加 ` AND <alias>.<logicDeleteColumn> = 0`
   - 无 `WHERE` → 追加 ` WHERE <alias>.<logicDeleteColumn> = 0`
2. 追加时带注释标记 `/* @TableLogic 隐式条件 */`，与 `handleJoinFetch` 的
   `/* 推断的ON条件，请验证 */` 风格一致，让用户知道这是插件补的。
3. DELETE 语句默认**不加**（Hibernate 的 `delete` HQL 不加逻辑删除条件，而是转 UPDATE）。

**验收**：带 `@TableLogic` 的实体 HQL 预览出现 `deleted = 0`；不带的不出现。

### T-04 无 SELECT 子句兜底（P2，与 T-01 同批实现）

`FROM`/`from` 开头的 HQL 在 SELECT 位置插入展开后的列清单。与 T-01 共用
`expandSelectClause`，只是「插入」而非「替换」。

同时**补强现有测试**：`HqlConverterTest` 中 `namedParameter_replacedWithPlaceholder`
等用例只断言 `contains(...)`，太弱，改为断言完整 SQL 或以「可执行性」为判据
（至少断言 `SELECT` 子句首项不是裸别名）。

### T-05 回归与沙盒验证（P0，收尾）

1. `./gradlew test --no-build-cache --no-configuration-cache` 全量（当前基线 2656 全绿）。
2. 新增测试类 `HqlConverterSelectExpandTest`（放 `src/test/kotlin/.../converter/jpa/`，
   与既有 `HqlConverter*Test` 同目录同风格），覆盖 T-01 的 10 个边界用例。
3. bump `BUILD_STAMP`（`DataSourceSelector.kt:50`，改动前为 `M36.5.79-polyadic-chain-fix`）

## 五、风险与边界

| 风险 | 等级 | 缓解 |
|------|------|------|
| 展开在 JOIN FETCH 改写前执行 → JOIN 别名取不到 | **高** | 实现时强制确认调用点位于步骤 9 之后；单测用例 6/7 锁定 |
| 别名与真实列名同名导致误展开（极端场景） | 中 | 判定加约束：裸标识符必须是 FROM/JOIN 中出现的别名才展开 |
| 巨宽表（100+ 列）展开后 SQL 冗长，编辑器性能 | 低 | 与 MP 路径 `SELECT *` 展开行为一致，已有先例；必要时受「SQL 格式化输出」设置控制换行 |
| `u.*` 降级掩盖元数据解析失败 | 中 | 降级时追加 `/* 实体列信息未解析，已降级为 <alias>.* */` 注释 |
| DELETE 路径被误展开破坏 | 中 | 单测用例 9 锁定；实现里在展开前先判 `startsWith("DELETE")` 直接短路 |
| T-02 若走「按实体字段类型判定引号」改动面扩大 | 中 | 先取证再改；仅在 B1 命中时才考虑，否则只修 locator |
