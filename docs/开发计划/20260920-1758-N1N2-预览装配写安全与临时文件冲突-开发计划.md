## 一、范围与背景

两条缺陷都由真机走查发现、并在第二轮复核（提交 `c269fbd`，独立沙盒 `MPSV-P10Reverify`）确认**仍复现**：

| # | 一句话 | 触发频率 | 用户可见性 |
|---|--------|---------|-----------|
| N1 | 预览装配在**写不安全语境**下改文档，平台记 SEVERE `Write-unsafe context!` | **必现**（重开预览即触发；第 2 次已被平台 `Suppressed a frequent exception` 计数） | 日志可见；界面表现正常，但**平台测试断言下会升格为失败** |
| N2 | 预览临时文件触发平台 **File Cache Conflict** 模态弹窗并抢焦点 | 3 次预览装配出现 3 次冲突询问、2 次实际弹窗 | **直接可见**：模态框抢焦点，其后连续三次悬停取不到 tooltip；疑似还会丢预览内容（见 §三.3） |

两条的共同诱因是同一处设计：预热在**池线程**写项目内临时文件、装配在**回调**里改文档，而两侧都没有把「写」放在平台认可的写安全语境里。

## 二、N1 写不安全语境改文档

### 2.1 根因（代码实证）

- 派发通道：`SqlPreviewPanel.kt:523-524` 构造 `PrewarmAwait` 时传 `{ runnable -> ApplicationManager.getApplication().invokeLater(runnable, ModalityState.any()) }`；
- 消费链：`PrewarmAwait.scheduleOnce$lambda$0$0`（`PrewarmAwait.kt:57`）→ `resolvePreviewEditorSource$lambda$0`（`SqlPreviewPanel.kt:754`）→ `assemblePreviewEditor`（`:2579`）→ `WriteCommandAction.runWriteCommandAction` → `DocumentImpl.setText` → `assertWriteAccess` 抛；
- 平台判词：`Model changes are allowed from write-safe contexts only. Please ensure you're using invokeLater/invokeAndWait with a correct modality state (not "any")`，`current modality=ModalityState.NON_MODAL`。

即：**`ModalityState.any()` 不是写安全模态**，而回调里做了文档写。

### 2.2 为什么当初用了 any()（已查清，见下）

`PrewarmAwait` 由 `92d67a5`（T-PerfTail #2）引入，该提交信息对派发通道的原话是：「冷态 scheduleOnce 注册完成回调经 **invokeLater(any modality)** 回 EDT 装配（**EDT 零阻塞**）」。

即 `any()` 是**为「派发不被模态挡住、尽快回 EDT」而选**，提交信息里**没有**给出「必须在模态对话框挂起期间完成装配」的具体场景。这个事实把候选路线收敛了：

- 平台判词要求的是**写安全模态**——`any()` 明确不是，而 `ModalityState.defaultModalityState()` 是（模态期间它会推迟到模态关闭，这正是「写安全」的定义）；
- 而面板在模态对话框挂起时**本来就在模态框后面**（用户看不见），把装配推迟到模态关闭**观感代价接近零**；
- 故 **路线 B（dispatcher 换成 `ModalityState.defaultModalityState()`）从「有代价的取舍」降级为「大概率一行改动」**，A/C 两路退为备选（若真机发现某场景必须在模态期间装配，再上 A 的事务闸门）。

| 路线 | 做法 | 代价 / 风险 |
|------|------|------------|
| **B（首选）** | dispatcher 由 `ModalityState.any()` 换成 `ModalityState.defaultModalityState()`（写安全；模态期间自动推迟） | 模态挂起时装配延后——面板在模态框后面，观感代价接近零；仍需真机确认无场景依赖「模态期间装配」 |
| A. 写动作改走事务闸门 | 保持 `any()`，把 `document.setText` 换 `TransactionGuard.getInstance().submitTransaction(...)` | 写被平台推迟到写安全时刻，装配时序要重新核对；实现面比 B 大 |
| C. 拆两段 | 文档写走 A、编辑器挂载保持 `any()` | 实现最细，要防「编辑器已挂载、文档还是旧内容」的中间态 |

**改前必做**：`git log -S "ModalityState.any()" -- SqlPreviewPanel.kt` 的另几个提交（`ae0c56d` T-PreviewConsoleFmt「预热不越权改写」、`f68372e`/`fd25c84` M36.5 原生控制台嵌入）里 `any()` 用于控制台挂载/回填链路，**那些是另一条链路，别顺手一起改**——本项只动 `PrewarmAwait` 的 dispatcher 这一处。

### 2.3 护栏缺口（本项必须一并补）

`BannedApiSourceScanTest` 已有「`ModalityState.any()` 排出的回调里做文档写」的**词法**规则，但本例写入在回调**间接调用**的方法里（回调 → `assemblePreviewEditor` → … → `setText`），静态扫描看不到。补法二选一：

- 扩规则：对「回调体内调用的方法」做一层浅调用图（易误报，需谨慎）；
- **加运行期断言（倾向）**：测试环境里让装配走一次回调路径，断言无 `Write-unsafe context!`（平台在测试模式下会把该告警升格为失败，天然可断言）。

## 三、N2 预览临时文件冲突

### 3.1 根因

- 临时文件名**固定**：`projectPreviewFile()` → `<project>/.idea/sql-visualizer/preview/mpsql-preview.sql`；
- 每次预热都**重写同一文件**，而编辑器仍持有该文件的**内存文档** → 平台 `MemoryDiskConflictResolver` 判定「内存与磁盘均变」→ 弹模态「File Cache Conflict」（Load File System Changes / Keep Memory Changes / Show Difference）。

### 3.2 证据（第二轮复核）

- 冲突询问 3 次：idea.log `1828 / 2180 / 2194` 行 `MemoryDiskConflictResolver - reload mpsql-preview.sql from disk?`（伴随 `documentStamp`/`oldFileStamp`）；
- 实际弹窗 2 次（截图 `_p6_more_menu.png` 把「更多」点击整个吃掉、`_p6_step4_tt4.png`）；
- **抢焦点的因果实证**：弹窗后连续三次悬停 meta 行取不到 tooltip，改用「Keep Memory Changes」关掉后**同一次悬停立刻出 tooltip**。

### 3.3 疑似连带后果（必须先复现确认）

复核中出现一次「新预览打开后 SQL 编辑区只剩占位文案、点【刷新】恢复」，时机紧跟 N2 的冲突询问。**假设**：冲突解析若选「从磁盘重载」，会把内存里的真 SQL 换成预热文件里的**占位内容**（预热写的是空壳，真 SQL 由装配期写入文档）。

若成立，N2 就不只是弹窗骚扰，而是**会丢预览内容**——优先级从「观感」升到「功能」，本计划的第一件事就是**专门复现确认**（连续预览 ≥3 次 + 主动选 Load File System Changes，看编辑区内容）。

### 3.4 候选修法

| 路线 | 做法 | 代价 / 风险 |
|------|------|------------|
| A. 唯一文件名 | 每次预热用唯一名（如 `mpsql-preview-<n>.sql`） | 冲突根治；但文件名被 `DialectPreMapping.ensureMapped`（按文件做方言映射）与清理逻辑使用，且**文件数变多**——需补清理（现逻辑只删 `previewTempFile` 一个），否则 `preview/` 目录只增不减 |
| B. 走文档 API 写 | 该文件已有文档时，改写文档（写动作）而非裸文件 IO，使 VFS 与文档同步 | 不新增文件；但写文档需写动作 + EDT，**与预热「池线程零 EDT 阻塞」的设计冲突**（这正是 T-PreviewFlash 要消掉的东西） |
| C. 写前对齐时间戳 | 写文件前先让平台文档与磁盘 stamp 一致（如 `FileDocumentManager.saveDocument` 或 reload） | 最轻；但「让谁覆盖谁」要定义清楚，且仍可能在竞态窗口内被判冲突 |

**倾向 A + 补清理**（把冲突从根上消掉，不把写搬回 EDT），但需先做 §3.3 的复现确认，再定是否顺带修内容丢失。

## 五、风险与顺序

1. **N1 的 `any()` 之问已答**（见 §2.2）：它是 T-PerfTail #2 为「派发不被模态挡住、尽快回 EDT」选的，提交信息里没有「必须在模态期间装配」的具体场景，故路线 B（换写安全模态）代价接近零；改前仍需真机确认无场景依赖模态期间的装配。
2. **N2 先做 §3.3 复现确认**，修法边界取决于「是否真丢内容」；
3. 两条都动预热/装配链，**不要与其它改该文件的任务并行**（写集交集：`SqlPreviewPanel.kt`、`PrewarmAwait.kt`）；
4. 顺序建议：**N2 先行**（根因单一、修法独立、用户可见），N1 随后（一行 dispatcher 改动 + 运行期断言）。

## 六、验收口径

- N1：真机连续重开预览 ≥3 次，idea.log 中 `Write-unsafe context!` 计数 **0**；
- N2：真机连续预览 ≥3 次，`MemoryDiskConflictResolver` 询问计数 **0**、模态弹窗 **0**、编辑区内容不丢；`preview/` 目录文件数不随预览次数增长；
