## 一、需求分析

### 1.1 需求一：搜索支持行号与时间信息

**现状**（[SqlLogPanel.kt:143-153](src/main/kotlin/cn/song/mybatisplus/visualizer/log/SqlLogPanel.kt)）：

```kotlin
internal fun filterBySearch(entries: List<LogSqlEntry>, query: String): List<LogSqlEntry> {
    val q = query.trim()
    if (q.isEmpty()) return entries
    return entries.filter {
        it.restoredSql.contains(q, ignoreCase = true) || it.summary.contains(q, ignoreCase = true)
    }
}
```

只匹配**还原 SQL**与**摘要**两个字段。而列表条目实际展示的元信息行（渲染于 SqlLogPanel.kt:1628-1640）包含：

```
#123 [2024-01-15 10:30:45] 230ms [UserMapper.java:42]
```

- `#123` 行号（`sequenceNumber`，T-LogRowNumber）
- `[2024-01-15 10:30:45]` 时间戳（`formatTimestampFragment`，跟随 `logTimestampSource` 来源与 `logTimestampFormat` 格式设置）

**用户在列表里看得见行号和时间，却搜不到**——违背「所见即可搜」直觉。搜 `#5` 找第 5 行、搜 `10:30` 找那个时间段的 SQL，是高频定位诉求（条目多时按行号/时间定位比翻滚动条快得多）。

### 1.2 需求二：右键菜单新增复制时间

**现状**（[SqlLogPanel.kt:1231-1278](src/main/kotlin/cn/song/mybatisplus/visualizer/log/SqlLogPanel.kt) `showContextMenu`）：菜单项为复制 SQL（多选批量）→ 删除 → 发送到 SQL→Java → 发送到日志转 SQL → 跳转源码。复制走 `Toolkit.systemClipboard + StringSelection`。

用户想把某条 SQL 的执行时间复制出去（贴到聊天/工单/文档说明「这个查询是几点跑的」），目前只能手动照着屏幕敲。

**按钮命名**：用户明确要求取一个比「复制时间」更合适的名字。推荐 **「复制时间戳」/ Copy Timestamp**：

- 「时间」含糊（相对时间？耗时？）；「时间戳」准确对应列表 `[yyyy-MM-dd HH:mm:ss]` 形态
- 与现有「复制 SQL / Copy SQL」菜单命名范式对齐（单选 `log.panel.copy` / 多选 `log.panel.copySelected`）

### 1.3 复制内容的形态决策

**核心原则（用户定调）：当前页面显示什么就复制出什么**——所见即所复制。

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 文本形态 | 与列表渲染的时间戳片段**逐字节一致**：`[2024-01-15 10:30:45]`（含方括号，仅去掉段间距用的尾随空格） | 用户明确要求所见即所复制；粘贴出来与页面看到的完全一样 |
| 时间来源 | 跟随 `logTimestampSource` 设置（日志时间优先，回退捕获时间），**与显示语义完全一致** | 所见即所复制的自然推论 |
| 格式 | 跟随 `logTimestampFormat`，非法回退默认 | 与显示同源 |
| 显示开关 | **受 `logTimestampEnabled` 限制**：开关关闭时页面上没有时间戳片段，菜单项置灰禁用 | 所见即所复制的完整语义——没有显示就没有可复制的时间戳 |
| 多选 | 支持：逐行拼接（每行一条带方括号的时间戳），与 `batchCopySql` 同构 | 右键菜单已有多选语义（`resolveContextMenuSelection`） |

## 二、技术方案

### 2.1 时间文本获取（单一真源，零格式化新逻辑）

**所见即所搜 / 所见即所复制**语义下，搜索与复制的文本源就是现有 `formatTimestampFragment`（SqlLogPanel.kt:1480-1494）的产出片段——**不需要抽取新函数，不新增格式化逻辑**：

```kotlin
/** 显示片段文本（去段间距尾随空格）：[2024-01-15 10:30:45]；显示开关关闭时为 null。 */
internal fun timestampDisplayText(entry: LogSqlEntry): String? =
    formatTimestampFragment(entry)?.first?.trim()
```

`formatTimestampFragment` 本身不动（显示行为逐字节不变）。来源选择（`logTimestampSource`）、格式跟随（`logTimestampFormat` + 非法回退）、开关语义（关闭返回 null）全部由现有函数天然承载——单一真源就是它。

### 2.2 搜索匹配扩展（可注入时间文本，保纯逻辑可测）

`filterBySearch` 增加时间文本提供器参数（默认实现读设置取显示片段，测试注入 stub 绕开平台依赖）：

```kotlin
internal fun filterBySearch(
    entries: List<LogSqlEntry>,
    query: String,
    timestampTextOf: (LogSqlEntry) -> String? = ::timestampDisplayText,
): List<LogSqlEntry> {
    val q = query.trim()
    if (q.isEmpty()) return entries

    // 行号形态：#5 / 5 → 精确匹配 sequenceNumber（0 = 无行号条目不参与）。
    // 精确而非 contains：搜 "1" 不应命中全部 1xx 行。
    val rowNumber = q.removePrefix("#").toLongOrNull()

    return entries.filter { entry ->
        entry.restoredSql.contains(q, ignoreCase = true)
            || entry.summary.contains(q, ignoreCase = true)
            || (rowNumber != null && entry.sequenceNumber == rowNumber)
            || timestampTextOf(entry)?.contains(q, ignoreCase = true) == true
    }
}
```

**行号匹配语义决策**：

- 支持 `#5` 与 `5` 两种输入（`#` 为渲染形态，直接敲数字更顺手）
- **精确 equals** 而非 contains/前缀：搜 `1` 命中全部 1xx 行是误命中灾难；用户搜行号就是要找那一行
- `sequenceNumber == 0`（历史文件/round-trip 条目）不渲染行号，且 equals 语义下搜 `0` 天然不命中，无需额外 guard

**时间匹配语义决策（所见即所搜）**：

- 对**显示片段文本**（含方括号 `[2024-01-15 10:30:45]`）做 `contains`——搜 `10:30`、搜 `2024-01-15`、甚至搜 `[2024` 都命中，与页面所见完全一致
- **跟随显示开关**：`logTimestampEnabled=false` 时页面上没有时间戳，`timestampDisplayText` 返回 null，时间分支天然不参与匹配——没有显示就没有可搜索的时间
- 格式跟随当前设置：改格式后匹配面随显示收窄是预期行为（所见即所搜）

**性能**：`timestampTextOf` 对每条过滤条目调用一次（new SimpleDateFormat）。条目上限 `logMaxCount`（默认 200）+ 200ms 防抖，开销与渲染路径同范式，可忽略。不做按需格式化等微优化。

**调用处**：`refreshList()`（SqlLogPanel.kt:1035）零改动——默认参数承接。

### 2.3 右键菜单新增「复制时间戳」

`showContextMenu`（SqlLogPanel.kt:1231-1278）在「复制 SQL」项之后插入。**显示开关关闭时菜单项置灰禁用**（所见即所复制——页面上没有时间戳就没有可复制的）：

```kotlin
// 所见即所复制：片段文本与页面渲染逐字节一致（含方括号）；显示关闭时无片段可复制
val timestampClip = batchCopyTimestamps(selectedEntries)
menu.add(
    JMenuItem(copyMenuText("log.panel.copyTimestamp", "log.panel.copyTimestampSelected", selectedEntries.size)).apply {
        isEnabled = timestampClip.isNotEmpty()
        addActionListener {
            if (timestampClip.isNotEmpty()) {
                Toolkit.getDefaultToolkit().systemClipboard.setContents(StringSelection(timestampClip), null)
            }
        }
    },
)
```

配套顶层函数（与 `batchCopySql` 同范式，SqlLogPanel.kt:93-94）：

```kotlin
/** 批量复制时间戳：取显示片段去尾随空格逐行拼接（按选择序）；显示开关关闭时为空串。
 *  与 batchCopySql 同构。 */
internal fun batchCopyTimestamps(entries: List<LogSqlEntry>): String =
    entries.mapNotNull { timestampDisplayText(it) }.joinToString("\n")
```

**实现细节**：时间片段在菜单构建时计算一次（右键是低频交互，无性能顾虑）；单选时一条片段即复制文本；多选逐行。`isEnabled` 由片段是否非空驱动，开关/来源/格式全走 `formatTimestampFragment` 单一真源。

- 搜索框输入行号（`#5` 或 `5`）精确命中第 5 行条目；输入时间片段（如 `10:30`）命中显示时间含该片段的条目；输入 SQL 片段行为不变

- 历史 tab 搜索与复制能力与日志页一致
- 全量测试绿，bundle parity 绿

## 六、风险与注意事项

1. **行号精确匹配的边界**：用户输入非纯数字（如 `abc#1`）时 `removePrefix("#")` 后 `toLongOrNull()` 为 null，行号分支跳过，纯 SQL 匹配兜底——无异常路径。
2. **filterBySearch 签名变化**：新增带默认值的第三参数，既有调用处（refreshList）与既有测试零改动；测试若直接以两参调用仍编译通过。
3. **时间匹配与格式设置耦合**：改格式后旧搜索词可能失效（如格式改成 `HH:mm` 后搜 `2024` 不再命中时间）——预期行为（所见即所搜），文档提示即可。
4. **显示开关关闭时复制不可用**：用户定调所见即所复制（页面上没有时间戳就没有可复制的内容），非缺陷——若后续有"显示关但仍要复制"诉求再立项（须重新拍板形态语义）。
5. **历史页 bundle 命名**：接线时确认历史页菜单文案 key 的命名空间（`log.history.*` 或复用 `log.panel.*`），避免 parity 测试失败。
6. **性能**：每条过滤条目一次 SimpleDateFormat new，200 条上限内可忽略；不引入缓存（与渲染路径同范式，避免 ThreadLocal 复杂化）。
