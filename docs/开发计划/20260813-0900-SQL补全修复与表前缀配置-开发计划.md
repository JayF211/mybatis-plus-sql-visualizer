# SQL 补全修复 + 实体父类字段 + 表前缀/后缀配置——开发计划（M16.2）

> 本文档是 **MyBatis-Plus SQL Visualizer** 的 M16.2 增量计划：① 修复 **SQL 补全不生效且无提示**（M16 引入的回归）；② 实体**父类字段**纳入全列展开（查询全部时含继承字段）；③ 设置中新增**表前缀/表后缀**配置（可添加/清除）。
>
> 当前基线：v1.10（M16 + M16.1 已提交，239 测试全绿）。

## 1. 问题分析与证据（2026-08-13）

### 1.1 SQL 补全不生效（M16 回归，证据驱动）

**补全链路**（M9 建立，M16 改动前可用）：
```
SqlPreviewPanel.createEditor(sql)
  └─ PsiFileFactory.createFileFromText("preview.mpsql", SqlPreviewLanguage, sql)
      └─ psi.putUserData(SqlCompletionContext.KEY, ctx)      ← PSI userData 绑定
          └─ SqlCompletionContributor（plugin.xml language="MP_SQL_Preview" 注册）
              └─ M9：ctx==null 时关键字仍补全（if (ctx != null) 包裹）
              └─ M16：ctx==null 时直接 return（关键字也丢失）  ← 回归点 A
```

**回归点 A（关键）**：M16 重写 Contributor 时 `val ctx = ...getUserData(KEY) ?: return` ——**ctx 为 null 时整个补全（含关键字）静默失效**。而 M9 用 `if (ctx != null)` 包裹——ctx 丢失时关键字仍在。用户"没有相关提示"（连关键字都没有）与此完全吻合。

**userData 丢失根因（回归点 B）**：上下文绑在 **PSI 文件**的 userData 上。嵌入式编辑器（`EditorFactory.createEditor`）中用户输入后，`PsiDocumentManager` 在补全前强制 commit——**非项目文件（createFileFromText 产物）的 PSI 在 commit 时可能重建**（FileViewProvider 重建 → 新 PSI 对象 → userData 丢失）。**Editor 对象在编辑过程中稳定不重建**——改用 **`parameters.editor.getUserData(KEY)`**（CompletionParameters 提供 getEditor()）作为主要载体，PSI userData 作兜底。

**回归点 C（异常风险）**：M16 的 `detectClause` 执行 `file.text.substring(0, position.textRange.startOffset)`——**旧 PSI（未随编辑更新）的 offset 与新文档文本长度不一致时抛 StringIndexOutOfBounds** → CompletionContributor 异常 → IDE 吞掉异常 → **补全无提示**。需防御（clamp offset / try-catch 回退 UNKNOWN）。

**其他确认**：
- `completion.contributor` 注册的 `language="MP_SQL_Preview"` 与 `SqlPreviewLanguage.id` 一致（`forLanguage(SqlPreviewLanguage)` 测试通过 ✓）；
- 关键字补全在 Contributor 内（M16 后因 return 连带失效）。

### 1.2 实体父类字段缺失

`EntityResolver.resolve` 用 `entityClass.fields`——**只含本类字段**。真实项目实体普遍继承基类（如 `BaseEntity {id, createTime, updateTime, deleted}`，80 个实体 extends BaseEntity），`table.allColumnNames`（SELECT 全列展开）**缺失父类字段**——查询全部时 SQL 列清单不完整。

### 1.3 表前缀/表后缀配置（新需求）

用户要求设置中支持**表前缀/表后缀**（可添加/清除）：如添加 `sys_` 前缀（`device_info` → `sys_device_info`）；清除已配置的后缀（设为空即原样）。当前表名来源：`@TableName` 注解或类名 snake_case 推断——无全局修饰能力。

## 2. 方案设计

### 2.1 补全修复（T-M16.2-01）

`SqlCompletionContributor` 三处修改：
1. **上下文载体改 Editor userData**：`SqlPreviewPanel.createEditor` 同时 `editor.putUserData(SqlCompletionContext.KEY, ctx)`（Editor 稳定，编辑后不丢）；Contributor 读取顺序：`parameters.editor.getUserData(KEY) ?: parameters.position.containingFile.getUserData(KEY)`（Editor 优先、PSI 兜底）；
2. **ctx 为 null 时不 return**：关键字补全不受影响（恢复 M9 语义）；实体表/列/别名补全在 ctx != null 时执行；
3. **detectClause 防御**：offset clamp 到文本长度（`min(offset, text.length)`）+ 空文本返回 UNKNOWN。

**测试**：`SqlCompletionContributorTest` 增补——detectClause 边界（空文本/offset 越界 clamp 不抛异常）；上下文读取双载体逻辑（Editor userData 优先）抽为可测函数。

### 2.2 实体父类字段（T-M16.2-02）

`EntityResolver.resolve` 收集字段改为**递归父类**：

```kotlin
private fun collectFieldsIncludingSuper(clazz: PsiClass, seen: MutableSet<PsiClass> = mutableSetOf()): List<PsiField> {
    if (!seen.add(clazz)) return emptyList()               // 防循环继承
    val superFields = clazz.superClass?.let { collectFieldsIncludingSuper(it, seen) } ?: emptyList()
    return superFields + clazz.fields.toList()              // 父类字段在前（MP 声明顺序语义）
}
```

- `resolveColumn` 对父类字段同样生效（`@TableField(exist=false)` 跳过、`@TableId` 主键标记、`@TableLogic` 逻辑删除、注释提取）✓ 通用；
- `@TableLogic` 检测与 `logicDeleteColumn` 计算同样基于全量字段（父类 deleted 字段被识别——**真实项目 BaseEntity.deleted 即父类字段，M15 逻辑删除注入对继承实体当前失效，本任务一并修复**）；
- 多级继承递归、循环继承防重（seen 集合）；
- **影响面**：`table.allColumnNames`（SELECT 全列）与批量模板列、逻辑删除注入、注释——现有 fixture 测试实体无父类（断言不变）✓。

**测试**：`EntityResolverCommentTest`/新增用例——子类继承 `BaseEntity {id, @TableLogic deleted, createTime}` 的实体：`allColumnNames` 含父类列、`logicDeleteColumn == "deleted"`、主键 `isId`。

### 2.3 表前缀/表后缀配置（T-M16.2-03）

- `PluginSettings.State` 新增 `tablePrefix: String = ""`、`tableSuffix: String = ""`；
- `EntityResolver.resolve` 末尾应用：`tableName = prefix + tableName + suffix`（`runCatching { PluginSettings.getInstance().state }` 兜底空——测试环境与未配置时零影响）；
- 设置页新增两行文本输入（`JTextField`）：「表前缀」「表后缀」，写入/读取 State（沿用现有 apply/reset/isModified 模式）；
- bundle 中英文案（`settings.tablePrefix` / `settings.tableSuffix`）；
- 影响面：所有表名渲染（SELECT/UPDATE/DELETE/MPJ join 关联表/批量模板——统一经 TableInfo，一处生效）；
- **边界**：`@TableName` 显式表名同样被修饰（全局语义，文档说明）；"清除"= 输入框清空。

**测试**：`SqlPreviewServiceTest`——settings.tablePrefix="sys_" 时预览 SQL 表名为 `sys_device_info`；suffix 同理；清空恢复原样（finally 恢复配置）。

### 2.4 验收（T-M16.2-04）

- `./gradlew clean test` 全绿 + `buildPlugin`；
- 手动验收：真实 IDE 打开预览面板 Ctrl+Space——关键字/表名/列名/注释补全全部出现；继承实体 SELECT 全列含父类字段；设置前缀后 SQL 表名变化；
- CHANGELOG/README 更新。

## 4. 风险与应对

| 编号 | 风险 | 影响 | 应对 |
|------|------|------|------|
| M16.2-R1 | Editor userData 在嵌入式编辑器中仍不可靠（某些场景 editor 也重建） | 补全仍无实体上下文 | Contributor 双载体（Editor 优先 + PSI 兜底）；仍有问题则退化为「面板持有关联 Map<Project, context>」静态注册表方案 |
| M16.2-R2 | 父类递归引入**接口字段/非实体父类**（如 Object） | 列清单污染 | 仅沿 `superClass`（类继承），跳过接口；`Object` 无字段天然过滤；seen 集合防循环 |
| M16.2-R3 | 表前缀应用于 `@TableName` 显式表名造成意外（用户只想要实体推断表名加前缀） | 表名错乱 | 全局语义（文档说明）——前缀对显式表名同样生效；如用户需要区分可后续加「仅推断表名」开关 |
| M16.2-R4 | 补全真实 IDE 复测时仍有其他原因（如嵌入式编辑器补全 action 未绑定） | 修复无效 | 手动验收第一步验证「关键字补全」是否出现——区分「Contributor 未调用」（注册/编辑器层）与「实体上下文缺失」（载体层） |
