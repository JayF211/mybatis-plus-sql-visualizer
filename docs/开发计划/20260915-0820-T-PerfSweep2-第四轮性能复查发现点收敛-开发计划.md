## 现状核实（出证见调研报告，此处列实施相关事实）

1. **01**：`extractConsoleError` 用反射 `doc.getText()` 整串拷贝后才按 `consoleErrorBaseline` substring 截断（`:578,582-587`）；600ms 结果刷新定时器（`:776`）与 400ms 结果 Tab 重试定时器（`:2695`，常规 40 拍/dumb 100 拍）**每拍**调用，`:2755` 另有一次单发调用。当前**无任何测试覆盖**（src/test grep 实证）。附带病灶：`:2708-2714` 的 debug 日志列表（contents.map/ids）在 debug 关闭时也照建。
2. **02**：`readBody` 为 `HttpRequestsSender` 私有（`:297`），`stream.use { it.readBytes() }` 与 gzip 解压 `readBytes()` 均无字节数上限，仅 10s 连接/读超时（`:251-252`）。`FeedbackApi.sender` 是测试 seam（`:136` internal var，fake 不触网）；超限截断后的非法 JSON 会自然落入既有 `nonJsonHint` 归类路径。
3. **03**：`buildStackAttachment(List)` 先全文 append 全部堆栈、末尾 `take(60_000)`（`ErrorReportComposer.kt:124`），逐条不先截断且附件节数不受 `BATCH_MAX_ITEMS`（仅限描述清单）约束；组装发生在调用线程 = EDT（`doOKAction` → `composeSubmission`/`composeFirstSubmission` 后才交 pooled）。
4. **04**：`cachedTempPsiFile` 为 object 级单槽 `@Volatile Pair<VirtualFile, PsiFile>`（`:86`），写点 `:2986,:3219`、清点 `:3009,:3237` 全在消费侧惰性路径（`isCacheUsable` `:3020` internal 已可测），项目关闭无钩子。
5. **05**：`enqueue` 在 `scheduled?.isDone == false` 时直接 return（`:38`）；`drain` 循环内 `Thread.sleep(720s)` 逐条间隔（`:62-67`）。现有测试在 `BatchSubmitterTest`（覆盖 scheduleQuietly 触发），调度器本体无独立测试。
6. **06**：plugin.xml:204 注释「开关默认开」与 `PluginSettings.kt:151` `autoCheckUpdate=false` 漂移，上轮已提未修。

## 任务分解

### T-PerfSweep2-01 错误提取改基线片段读取（中低）

**方案**（DataSourceSelector.kt，单文件收口）：

1. `extractConsoleError` 反射读取从 `getText` 改 `getCharsSequence`（同属 `Document` 接口，DBN 包装类可达性与 getText 一致，无 BadLocationException 面）；`baseline > 0 && length > baseline` 时只 `subSequence(baseline, length).toString()` 物化新增段，`baseline == 0` 保持全文（首次执行语义不变），`baseline >= length` 返 null 不变。
2. `:2708-2714` debug 列表构建包 `LOG.isDebugEnabled` 守卫。
3. `extractConsoleError` 提升为 internal 供测试（house 惯例）。

**测试**：新增 `ConsoleErrorExtractTest`（动态代理 ConsoleView/Document 桩，沿用 ResultTabSelectionTest 的动态代理复现手法）：①baseline 截断后只分析新增段（用记录 subSequence 范围的计数 CharSequence 断言未触碰全史）；②baseline==0 全文分析检出错误行；③baseline≥length 返 null；④新增段内错误签名照常检出。debug 守卫为纯防御改动不单测。

### T-PerfSweep2-02 响应体有界读取（低）

**方案**（FeedbackApi.kt）：

1. 新增 `internal fun readBounded(input: InputStream, maxBytes: Int = RESPONSE_MAX_BYTES): ByteArray`：循环读入缓冲、累计达 maxBytes 即停（后续字节不再消费），`RESPONSE_MAX_BYTES = 2MB` 常量。
2. `readBody` 成功流/errorStream 两路统一走 `readBounded`；gzip 分支对 `GZIPInputStream` 直接 `readBounded`（限解压后字节数，gzip 炸弹面消除）。
3. 截断产物为非法 JSON → 既有 `nonJsonHint` 路径接管，用户侧可见失败原因，不新增 bundle 键（「响应超限截断」文案是否透出记为观察项，本轮不做）。

**测试**：`FeedbackApiTest` 增 4 例：小响应原样、明文超限截断（3MB→2MB）、gzip 解压超限截断（高压缩比构造）、空响应。`readBounded` 直测 InputStream，无需网络。

### T-PerfSweep2-03 批量附件 per-item 截断（低）

**方案**（ErrorReportComposer.kt）：

1. `buildStackAttachment(List)` append 前对每条堆栈先截断：单条路径上限 60_000（现状不变，存量行为 byte 级兼容）；多条路径按条数**半幅均分**（60_000/(N*2)，下限 1_000/条保诊断上下文），截断尾注 `（已截断，原 N 字符）`（发帖内容纯文本，不走 bundle）。【实施修订 2026-09-15：原定固定 8k/条，自测实证 20×8k=160k 仍触发 take(60_000) 终裁、第 8 节起整节丢失——均分方案同时修复内存面与丢节面】
2. 末尾 `take(60_000)` 保留为最后防线；瞬时分配上界从「所选堆栈总量」降到 max(60k, 20×8k)=160KB，EDT 组装回到毫秒级。

**测试**：`ErrorReportComposerTest` 增 3 例：单条 60k 内逐字节不变（存量断言保持）、批量 20 条×50k 每节 ≤8k+尾注且总量 ≤60k、小堆栈批量逐字节不变。

### T-PerfSweep2-04 cachedTempPsiFile 项目关闭钩子（低）

**方案**（DataSourceSelector.kt）：

1. object 内加 `hookedProjects`（`ConcurrentHashMap.newKeySet<Project>()`）；缓存写入路径（`:2986`、`:3219` 两处）调用 `hookProjectClose(project)`：首次 add 成功才 `Disposer.register(project) { hookedProjects.remove(project); if (cachedTempPsiFile?.second?.project == project) cachedTempPsiFile = null }`。
2. 回调内 `PsiFile.getProject()` 为字段级访问无需读锁；单槽 `@Volatile` 写线程安全。`Disposer.register(project)` 是平台公开 API，非反射入口，不涉签名护栏登记；注册的是回调非资源，不构成 ObjectTree 泄漏面。

**测试**：新增 `CachedTempPsiFileTest`（平台 fixture）：写缓存 → dispose project → 断言单槽清空；B 项目缓存不被 A 项目关闭误清；`isCacheUsable` 惰性校验兜底保持（存量语义）。

### T-PerfSweep2-05 调度器 drain 链式化（低，含一处行为增强）

**方案**（PendingReportScheduler.kt）：

1. 队列从 drain 局部捕获改为字段 `pending: ArrayDeque<Submission>`；`enqueue` synchronized 内 append，若无在途 tick 则 `schedule(::tick, INTERVAL_SECONDS)`。
2. `tick`：取队首发送（成功与否都不重试，语义不变）→ 队列非空再 schedule 下一拍、为空清 `scheduled`。`Thread.sleep` 消失，线程在两拍间归还池；12 分钟间隔、首发成功才排后续（BatchSubmitter 调用点保证）、内存队列退出即弃，均不变。
3. **行为增强**：drain 期间新 enqueue 从「静默丢弃」变「并入队尾顺延补发」——KDoc 语义约定同步更新（「不静默替用户发东西」红线不破：内容均经对话框确认）。
4. `describeQueue` 的 queued/idle 两态语义保持。
5. `enqueue` 增可参数化延时 `delaySeconds`（默认 `INTERVAL_SECONDS`，internal），测试用极短间隔走真实单线程池。

**测试**：新增 `PendingReportSchedulerTest`（fake sender seam 注入）：空列表 no-op、按序发送、两拍间隔、drain 中新 enqueue 并入不丢（本轮行为变更点）、describeQueue 两态、应用退出不阻塞（daemon 断言）。`BatchSubmitterTest` 既有断言保持。

plugin.xml:204 「开关默认开」改为「开关默认关（`PluginSettings.autoCheckUpdate=false`，稳定版由 Marketplace 推送，内测期手动开启）」，与代码权威一致。零行为变化。

## 风险与兼容性

1. **01 反射面变化**：`getCharsSequence` 与 `getText` 同属 Document 接口，代理可达性一致；用例④（新增段检出）兜住功能等价。243/262 双版行为一致（接口方法，非实现类方法）。
2. **03 附件内容变化**：仅批量路径超长单节出现截断尾注，服务端纯文本存储无需变更；单条路径 byte 级不变。
3. **05 行为变更**：drain 中新批次从丢弃变排队——属用户可感的语义增强，CHANGELOG 条目按 Changed 记。
4. **04**：项目关闭回调与消费侧惰性校验并存，双保险不冲突（钩子清空后 `isCacheUsable` 走重建路径）。
