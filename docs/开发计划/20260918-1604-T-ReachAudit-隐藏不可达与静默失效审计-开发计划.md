## 二、发现清单（全部实测，附出处）

### F1（P1）增强捕获在线态缺心跳窗口 → 半死会话永久封口，静默零捕获

- 协议与文档都写了心跳语义，实现里没有：
  - `log/agent/AgentProtocol.kt:24-25`：`/** 在线态判定：最近 N 毫秒内有心跳或事件。 */ const val ONLINE_WINDOW_MS = 30_000L` —— **全仓零消费**；
  - `log/agent/AgentManager.kt:43`：类 KDoc「在线态：最近 [AgentProtocol.ONLINE_WINDOW_MS] 内有心跳/事件（§4.3）」；
  - `AgentSession.lastSeen`（`AgentManager.kt:658`）有写（读循环每帧刷新，`:683`）**无读**；
  - 真正判定在线的是 `updateOnline()`（`:431`）`sessions.any { it.alive }`，而 `alive`（`:654`）只在读循环退出/异常时置 false（`:688/:749`），类 KDoc `:642` 自述「alive = socket 未断」。
- **后果**：agent 侧停止产出（织入未生效、事件解析持续失败、应用侧卡死）但 TCP 连接仍在 → `alive` 恒 true → `online` 恒 true → `SqlCaptureGate.paused` 恒 true → **控制台桥保持封口、agent 又没产出 = 两条通道同时零产出**，且没有任何超时恢复路径；与此同时设置页状态行（T-CaptureTruth T-CT-01 五态）显示「已挂载 pid=…」——**看起来一切正常**。这正是用户两次报障的同一症状形态（静默零捕获 + 状态显示正常），区别只在于触发原因。
- **修法**：`updateOnline()` 与 `sweepOffline()` 纳入心跳窗口（`alive && now - lastSeen <= ONLINE_WINDOW_MS`），过期会话走既有摘除链路（`sweepOffline` 5s 巡检 → 摘除 → `updateOnline` → 桥回落）；状态行在「挂载但心跳过期」时给出区分文案；补测试（假时钟 + 不刷心跳的会话 → 一个巡检窗后应摘除并回落）。
- **注**：`sweepOffline` 目前只摘 `!alive`，所以半死会话连「连接中断，已回落控制台捕获」都不会显示。

### F2（P2）JOIN 图错误态从未接线（死 UI + KDoc 与实现不符）

- `ui/diagram/DiagramPanel.kt:63-71`：`errorTextArea`（JTextArea，带完整样式）与 `errorScroll`（JBScrollPane）**全仓（含测试）除声明处零引用**；
- 换页入口 `swapContent` 只有两个实参：`placeholderLabel`（`:91/:148`）与 `scrollPane`（`:128`）——**没有错误页**；
- 而类 KDoc 两处声称有错误态：`:44`「『无 JOIN』占位与错误态保留原样」、`:53`「占位/画布/错误态都在其内容层换页」；
- 唯一调用点 `ui/SqlPreviewPanel.kt:1187` `diagramPanel.showDiagram(model)` 无 try/catch，`showDiagram`（`:125`）只分「空模型→占位」与「有模型→画布」两支。
- **后果**：图渲染失败时面板无错误出口（用户看到的是上一态或空画布），KDoc 却宣称有错误页——与 T-SettingsTruth P2「死 UI 行」同族。需实施时判定：若错误已由调用方以通知形式呈现（如 `showExportError` 的 ERROR 轻通知口径），则删两字段并把 KDoc 与实现对齐；否则把 `errorScroll` 接到内容层错误页并补 `showError`。
- **同族（P3）**：`ui/SqlResultPanel.kt:33` `statusLabel`（JBLabel）声明后零引用（同面板真正在用的是 `infoLabel`）——死字段，判定接线或删除。

### F5（P3）初始化顺序陷阱的**通用**守卫（把 T-CT-07 从 DialogWrapper 推广到全类）

- 全类扫描命中 5 处「init 块 → 被调方法 → 引用后声明属性」：
  - `SqlLogPanel.historyPanelRegistered`（`log/SqlLogPanel.kt:886`，`addHistoryTab`/`updateHistoryTabVisibility` 引用）——**当前无害**：其声明初值 `false` 与 JVM 默认值一致，构造期读到 false 正是守卫想要的语义；
  - `AnnotationSqlCompletionContributor.TAG_NAME_AT_CARET`、`SqlCompletionContributor.AGGREGATE_FUNCTIONS`、`XmlSqlCompletionContributor.DYNAMIC_TAGS`——三处均为 **companion 侧常量**，JVM 伴生对象整体初始化语义使其安全（除非构成循环初始化）。
- **结论**：T-CT-07 的 `disableCaptureAction` 之所以真出事，是因为它是**对象类型**（构造期为 null 而非「声明初值」）。守卫应从「DialogWrapper 子类 + 声明顺序」推广为「全类 + 声明顺序 + 初值与 JVM 默认值不等」——这样上述 5 处不再误报，真陷阱照抓。

### F6（P4）枚举可达性：`DiffType.CHANGE` 声明了但从不产出

- `ui/diff/SqlDiffer.kt:16` `enum class DiffType { INSERT, DELETE, CHANGE, EQUAL }`；
- 产出点只有三处（`:74/:80/:85`）：EQUAL/INSERT/DELETE——**CHANGE 既无产出也无渲染分支**（全仓无 `DiffType.CHANGE` 的代码引用）。
- 影响：SQL 差异视图里「某行被修改」只能表现为「删一行 + 加一行」，无法表达"修改"语义。判定=实现（LCS 后处理把相邻 删+增 合并为 CHANGE 并给渲染样式）或删除该常量。
- 其余 45 个枚举全部常量在 src/main 有产出点；`CommentSource`（`psi/EntityResolver.kt:186`）的 SCHEMA 等为 **KDoc 明示的预留位**（「当前实现 schema 返回 null，未来方案 B 接入」），非缺陷。
