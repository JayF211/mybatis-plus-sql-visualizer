## 二、根因详述

### 2.1 预设名全局（缺陷 1）

存储模型 `schemes: 预设名 → (SQL键 → 参数快照)`——快照**已**按 SQL/方法分桶，缺的只是「名」的作用域：名单、激活指针、查重三处都是全局的。故任何方法的下拉都列出全部预设名，切方法时激活指针也不跟着走。

### 2.2 文案（缺陷 2）

键值直改；引用处一律经 bundle 取文案，测试无需动。

### 2.3 NPE（缺陷 3）

```kotlin
class SqlSuppressManagerDialog(...) : DialogWrapper(...) {
    private val ruleManager = SqlSuppressRuleManager.getInstance()
    init { …; refreshRuleList(select = null) }        // :113-122 构造期
    …
    private val createdAtFormat = ThreadLocal.withInitial { SimpleDateFormat(…) }  // :412 声明在后
}
```
构造期 `refreshRuleList` → `setSelectedValue` → 渲染器 `getListCellRendererComponent` → `createdAtText` → `createdAtFormat.get()` = **null.get()** → NPE。Kotlin 对「init 块引用后声明属性」不报编译错（引用类型默认 null），属静默陷阱。

### 2.4 EXPLAIN 直送的 EDT 读盘（缺陷 4）

`projectExecFile` 的「差量快路径」在 `document` 未加载时回落 `vf.inputStream.readBytes()`（DataSourceSelector.kt:4302）——EDT 上做 VFS 文件 IO，命中平台 SlowOperations 断言（`Logger.error`，表现为 IDE 内部错误）。该调用发生在点击处理器（EDT）里，属**线程归位**问题；项目定例禁止 `allowSlowOperations` 逃生舱（243+262 双重证伪）。

### 2.5 增强捕获零产出（缺陷 5）

沙盒日志（`.intellijPlatform/sandbox/.../log/idea.log`，2026-10-06 14:24–14:26，pid=33448）事实链：

1. 14:24:20 premain 注入成功、会话建立（`premain 会话建立：pid=33448`），**当时 CONFIG 为 `disabled=true`**（用户尚未开始捕获）；
2. 14:25:01 用户开启捕获 → CONFIG `disabled=false` 已 ACK（#2/#3）；
3. 14:25:12 发 HTTP 请求 `http://localhost:8086/selfdev/tool/directory-builder`；
4. 14:26:23–24 运行结束 → `SocketException: Connection reset` + 在线态 true→false（**正常关闭，非故障**）。

结论：挂载层与会话层健康，缺的是「事件有没有被产出、有没有到达 IDE」这一环——两条通道（proxy 包装 / 语句织入）在停采态不打点、收事件也不打点，日志侧无法判别。需本机复现（§3.6）并把事件计数补进诊断行（§3.5）。

## 三、方案设计

### S1 预设按方法隔离（键作用域）

存储格式不动、老数据零迁移，只改作用域语义：

1. **名单**：新增 `schemeNamesFor(key: String?): List<String>`（按创建序返回「在该键下有快照」的名；key 空 → 空表）。面板 `syncSchemeCombo()` 与对话框 `schemeNamesWithDefault()` 改用它。
2. **激活指针**：`activeScheme`（全局单值）改为按键记录 `activeSchemeFor(key)`（无记录 / 名字在该键无条目 → `DEFAULT_SCHEME`）；`switchScheme(name, key)` 只写该键指针（保 F49 轻量落盘语义）。
3. **查重**：`saveAsScheme(name, key, params)` 的 DUPLICATE 判定改为「**该键下**是否已有同名条目」——同名预设可在不同方法各自存在、各存各值。
4. **重命名/删除**：维持**名字级**（改一次，各方法同名条目同步变），对话框加一行说明（D71 已按推荐定案）。
5. **持久化**：`PluginSettings.State` 新增 `paramActiveSchemeByKey: String`（`{"key":"name"}` 最小 JSON，复用 ParamHistoryCache 既有转义/切分工具）；旧 `paramActiveScheme` 作为「未记录键的回落值」，仅当该名字在当前键下确有条目时生效（迁移安全）。
6. **对话框**：条目数显示从「全局缓存键数」改为「本方法：已存 / 未存」；上限 `MAX_SCHEME_COUNT` 维持全局（内存界），文案不变。
7. **面板**：`switchToScheme(name)` 内部取当前键传给 cache；combo listener 的「是否变化」判定改用 `activeSchemeFor(key)`。

### S2 文案

`panel.bindstate.associated` 中文改「数据源（上次使用）：{0}」、英文改 `DataSource (last used): {0}`。

### S3 NPE

`createdAtFormat` 声明上移到 `init` 之前（属性区首位，紧随 `ruleManager`）；顺带核对本类无其它「init 期引用后声明属性」。

### S4 EDT 慢操作归位（线程归位两段式）

去掉 EDT 上的 VFS 读：`projectExecFile` 的差量判据改为**不碰 VFS IO**——

- 已有 document → `doc.text == sql`（现状保留，纯内存）；
- 无 document → 用**「本进程最近写入内容」内存标记**（按文件路径记录最后写入的 SQL；写入点唯一=本类的写盘路径）替代 `vf.inputStream` 读取；
- 标记缺失/不匹配 → 视为「不一致」走正常写入路径（宁可多写一次，绝不在 EDT 读盘）；
- 测试缝保留：`execFileContentMatches` 语义改为「doc 或内存标记」，新增单测钉住「EDT 调用零 VFS IO」（可用探针计数 `vf.inputStream` 调用——测试里传桩 vf）。

### S5 诊断面补「增强捕获已收事件数」

`CaptureDiagnostics` 增 `agentEventsReceived: Long`（取数点=agent 事件消费入口，即事件进入 `SqlLogManager` 之处）；文案在增强通道片段后追加「已收事件 N 条」（>0 才显示？——**不**：此计数是判「事件到没到」的关键判别量，**恒显示**，与重放/短路计数的「非零才显示」口径不同，理由写进注释）。

demo 工程本机已有（`F:\code\Java\Gitee\SongRenShuo\mybatis-plus-sql-visualizer-demo`，启动类 `SelfDevFrameworkDemoApplication`，MySQL/8086 端口）：

## 七、实施记录（2026-10-06 当轮）

### 7.1 增强捕获零产出：本机复现定根因（子代理车道）

按 S6 协议本机跑通（假接收端按 `AgentProtocol.kt` 帧格式解码；帧 = `[4B 大端 len][1B cmd][len B UTF-8 body]`，agent 是 TCP 客户端、IDE 侧是 ServerSocket）：

| 轮 | 注入 jar | 结果 |
|---|---|---|
| Run A | 当前 `build/dist/mps-sql-agent.jar`（含 `afb62e4`） | 握手全通（HELLO/CONFIG_ACK 到）/ **零事件** / 宿主崩：`VerifyError: Stack map does not match the one at exception handler`（`com.mysql.cj.jdbc.StatementImpl.execute(String,String[]) @46`，Spring `schema.sql` 第一条建 Statement 即引爆，应用从未打印 Started） |
| Run B | 对照 pre-`afb62e4` jar | 应用正常起、**9 条 EVENT**（含请求线程 `http-nio-8086-exec-*` 的 SQL）——事件产出与到达链路本身没问题 |

**最近根因**：`afb62e4` 的帧补丁给每个 FrameNode 的 locals **直接追加 LONG**，前提「token 槽恰起于原 info 数末尾」不成立——原帧 locals 项数可小于 `maxLocals`（javac 未用尾槽在帧里不出现）。实证 `StatementImpl.execute(String,String[])`：`stack=3, locals=4, args_size=3` 而原帧 locals 仅 3 项 ⇒ 追加 LONG 后帧声称 long 在 slot 3-4、头插 `LSTORE` 用 tokenSlot=4（写 slot 4-5）→ 错一槽 ⇒ 首次加载即 VerifyError ⇒ 宿主起不来 ⇒ 无 SQL ⇒ 「已挂载但产出 0 条」。

### 7.2 修复与验证层（主控）

- **帧补丁修正**（`StatementWeaver.patchFramesWithTokenSlot(mn, tokenSlot)`）：按**槽数**（long/double 占 2）补齐 `TOP` 到 tokenSlot 再追加 LONG，与头插写入位置逐槽对齐；javadoc 原错误前提同步订正为勘误段。
- **补上被漏掉的验证层**（新增 `StatementWeaverFramePatchVerifyTest`）：既有 `ZeroLoadClassWriterWeaveTest` 刻意「只织入不定义」（防污染增量判别式），于是「产物非法字节码」无人守——新类把产物在**隔离子 ClassLoader** 里 `defineClass + Class.forName(initialize=true)`（触发链接期校验）并实际调用，覆盖三形态：①合成「未用尾槽」夹具（`maxLocals=4` 而帧只列 2 项）②真实 h2 驱动类三面（JdbcStatement/JdbcPreparedStatement/JdbcConnection）③帧槽位对齐直证。
- **红/绿读数**：旧补丁态该套 3/3 必红（红读数：帧槽数 `expected:<6> but was:<4>` + VerifyError）→ 修正后 **agent 子项目 112/0 全绿**。
