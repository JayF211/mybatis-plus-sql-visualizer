# SQL 预览 CASE 关键字选择粘连修复 - 开发计划

> **创建日期**：2026-09-03
> **优先级**：P1（用户体验缺陷）
> **状态**：待实施

---

## 一、问题描述

在 XML 预览（及所有 SQL 预览）中，双击/点击 `CASE` 关键字时，选中范围包含 `CASE` 及其后的字段名（如 `CASE use_status` 整体被选中），而非仅选中 `CASE` 关键字本身。

**复现路径**：
1. 打开含 `<choose>/<when>` 或 `<if>` 动态条件的 MyBatis XML
2. 点击预览按钮 → 右侧 SQL 编辑器显示含 `CASE use_status WHEN ...` 的 SQL
3. 双击 `CASE` → 选中范围为 `CASE use_status`（错误），期望仅选中 `CASE`

---

## 二、根因分析

### 2.1 编辑器高亮链路

`SqlPreviewPanel.createEditor()`（约 L1258-L1267）设置编辑器高亮器：

```kotlin
val sqlHighlighter = SyntaxHighlighterFactory
    .getSyntaxHighlighter(sqlFileType, project, null)
if (sqlHighlighter != null) {
    highlighter = LexerEditorHighlighter(sqlHighlighter, EditorColorsManager.getInstance().globalScheme)
}
```

编辑器使用**平台原生 SQL 高亮器**（Database 插件提供），而非插件自研 `SqlLexer`。

### 2.2 词选择机制

IntelliJ 编辑器的双击词选择由 `SelectWordHandler` 驱动，其 `getRange()` 方法：
1. 取光标处 token 类型（`Lexer.getTokenType()`）
2. 向左右扩展至同类型 token 边界
3. 若 token 类型为 `WHITE_SPACE`，跳过至下一个非空白 token

**关键**：词选择的边界判定依赖高亮器内部 lexer 的 token 切分。

### 2.3 根因推断

平台原生 SQL lexer（`com.intellij.sql.parser.SqlLexer`）在处理 `CASE` 后的标识符时，可能将 `CASE use_status` 视为同一 token 或相邻同类型 token（均为 `IDENTIFIER` 类型），导致选择器将二者合并。

**可能原因**：
- **A. 原生 SQL lexer 的 CASE 上下文处理**：SQL 标准中 `CASE <expr> WHEN ...` 的 `<expr>` 可以是列引用，原生 lexer 可能将 `CASE` 后的标识符标记为与 `CASE` 关联的表达式片段
- **B. 高亮器未正确安装**：`getSyntaxHighlighter` 返回 null 时，编辑器无高亮器，词选择回退到默认字符级判定（按空格/标点分词），此时 `CASE` 和 `use_status` 应被空格分隔——若仍粘连，说明有高亮器但 token 切分异常
- **C. LexerEditorHighlighter 的 token 类型映射**：`LexerEditorHighlighter` 包装原生高亮器时，token 类型可能被统一映射为少数几种，导致选择器无法区分关键字与标识符

### 2.4 验证优先级

| 假设 | 验证方式 | 概率 |
|------|----------|------|
| A. 原生 lexer CASE 上下文处理 | 在独立 SQL 文件（非预览）中双击 CASE 观察选择范围 | 高 |
| B. 高亮器未安装 | 日志输出 `sqlHighlighter` 是否为 null | 中 |
| C. LexerEditorHighlighter 映射 | 调试查看 token 类型序列 | 中 |

## 三、调查步骤

### Step 1：确认原生行为
- 在项目中新建独立 `.sql` 文件，写入 `SELECT CASE use_status WHEN 1 THEN 'a' END FROM t`
- 双击 `CASE` → 观察选择范围
- **若独立 SQL 文件同样粘连** → 问题在平台原生 lexer，非插件 bug → 需绕行方案
- **若独立 SQL 文件正常** → 问题在预览编辑器的高亮器安装/配置

### Step 2：检查高亮器安装
- 在 `createEditor()` 中加日志：`Logger.getInstance(...).info("[CASE] highlighter: ${sqlHighlighter?.javaClass?.name}")`
- 沙盒 runIde 打开预览，查日志确认高亮器类型

### Step 3：Dump token 序列
- 在 `createEditor()` 创建编辑器后，用 `sqlHighlighter` 对当前 SQL 跑一遍分词，输出每个 token 的 (type, text, start, end)
- 确认 `CASE` 和 `use_status` 是否为独立 token、各自类型

## 四、修复方案

### 方案 1：自研 SqlLexer 接管高亮（推荐）

将编辑器高亮器从平台原生 SQL 高亮器切换为基于自研 `SqlLexer` 的 `SyntaxHighlighter`：

**改动点**：
1. 新建 `SqlSyntaxHighlighter`（包装 `SqlLexer`，实现 `SyntaxHighlighter` 接口）
2. `SqlPreviewPanel.createEditor()` 中改用 `SqlSyntaxHighlighter` 替代 `SyntaxHighlighterFactory.getSyntaxHighlighter`

**优势**：
- 自研 `SqlLexer` 已正确将 `CASE` 标记为 `KEYWORD`、`use_status` 标记为 `IDENTIFIER`（不同类型 → 选择器不会跨 token 合并）
- 词选择边界与高亮 token 完全一致
- 不依赖 Database 插件（Community 版也能正确高亮+选择）

**风险**：
- 自研 `SqlLexer` 覆盖面不如原生 lexer（复杂 SQL 可能分词不准）
- 需确保 `SqlSyntaxHighlighter` 正确实现 `getTokenHighlights()` 返回高亮颜色

### 方案 2：保留原生高亮器 + 自定义 SelectWordHandler

若 Step 1 验证原生 SQL 文件也存在粘连（平台 bug），则：
- 保留原生高亮器（高亮正确）
- 为预览编辑器注册自定义 `SelectWordHandler`，在 `getRange()` 中强制按空格+关键字边界切分

**劣势**：侵入性强，维护成本高，且需处理大量边界情况。

### 方案 3：仅修复高亮器安装（若 Step 2 确认未安装）

若 `sqlHighlighter` 为 null（Database 插件未安装），回退到自研 `SqlSyntaxHighlighter`。

## 五、实施计划

### Phase 1：调查验证
1. 新建独立 SQL 文件验证原生 lexer 行为（Step 1）
2. 加日志确认高亮器安装状态（Step 2）
3. Dump token 序列确认切分（Step 3）

### Phase 2：实施修复
4. 新建 `SqlSyntaxHighlighter` 类（包装 `SqlLexer`）
5. 修改 `SqlPreviewPanel.createEditor()` 使用自研高亮器
6. 确保高亮颜色方案与原生一致（关键字蓝、字符串绿、注释灰等）

### Phase 3：测试验证
7. 新增 `SqlSyntaxHighlighterTest`：验证 CASE/WHEN/ELSE/END 分词正确
8. 真机验证：预览含 CASE 的 SQL → 双击 CASE → 仅选中 CASE
9. 回归测试：其他关键字（SELECT/FROM/WHERE/JOIN）选择正常

- [ ] 预览含 `CASE expr WHEN ...` 的 SQL，双击 `CASE` 仅选中 `CASE`
