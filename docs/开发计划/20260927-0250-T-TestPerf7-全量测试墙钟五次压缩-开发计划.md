## 二、改动方案

### S1 testExternal 外部桶扩容（结构性，预期片 execSum −19s 档、墙钟 −4~6s）

`testExternalClasses` 名单（mpv-testing.gradle.kts）追加四类，逐类非沙盒验证后落名单：

| 类 | T6 树残量 | 非沙盒可行性现状 |
| --- | --- | --- |
| acp.AcpSignatureCrossVersionTest | 3.8s | 纯 JUnit 声明；源文本含 10 处 com.intellij（按 T6 §二为字符串字面量非 import），testFast 划桶规则按全文匹配故**不在 testFast 桶**——须 testExternal 直接行为验证（V1） |
| config.SettingsRealityGuardTest | 4.8s | 纯 JUnit 声明；com.intellij 文本命中数待查（V2），命中即须行为验证 |
| convention.BannedApiSourceScanTest | 2.9s | 纯 JUnit 声明；`com.intellij.util.ui.IconUtil` 系封禁规则字符串（:121）非 import，testFast 划桶按全文匹配故不在桶——须行为验证（V2） |
| convention.EnumReachabilityGuardTest | 7.5s | 纯 JUnit 声明且零 com.intellij 文本=**testFast 桶成员**，日常非沙盒绿即行为已证（V2 预通过） |

- 验证方法：四类加入名单后单跑 `./gradlew testExternal`，全绿即落名单提交；某类红=隐性平台依赖，该类回退留分片并登记（68 例教训口径）。
- testExternal 桶 `maxParallelForks` 维持 1（签名类起外部 JBR JVM，桶内串行总时长 ~35s ≪ 片墙钟 130s 档，不拖尾）。
- parity 与权重表零维护：聚合报告已扫 testExternal 目录（T6 S3 落的）；`discoveredTestClasses` 排除名单自动生效。

### S2 新重类固有成本复核（登记件，预期零改动）

09-26 主树画像的新增重类按 T6「重复劳动 vs 固有成本」分型复核。2026-09-27 静态预审计（walkTopDown/readText/Thread.sleep 形态 grep + 单例耗时分布）：SqlToJavaPanelTest（55 例 338ms/例）、SqlPreviewSpecMatrixTest（91 例 194ms/例）、SqlPreviewPanelImportTest（18 例 782ms/例）、EntityClassFinderHeavyTest（17 例 708ms/例）、HeavyXmlParamTypeResolverTest（16 例 745ms/例）、PluginSettingsFolderConfigurableTest（9 例 1.3s/例）、EnhancedCaptureConsentDialogTest（2 例 7.8s/例，headless 直调 doOKAction 的对话框构造固有成本）、XmlPreviewPanelTest（16 例 695ms/例）——全部呈「均匀小用例分布、无重复扫描形态」=固有成本。实施轮跑一轮逐类定向核对读数分布即可登记销账；仅当发现异常重复劳动才动手（同 companion-lazy 模式，断言零改动）。

### S3 片数保质期复测 4/5/6（实验件，预期 0 或 −10~25s）

- 触发依据＝mpv-testing 脚本内置规则「固定开销占片墙钟比例跌破两成就该把片数往上重测」：合流树片执行 ~135s 档、固定开销 ~17s/片 → 占比 ~12% < 20%；且 T4/T5 的 5 片否决是在 execSum 600s+、testExternal 尚未分桶的旧负载形态下做出的，负载已变。
- 方法：同窗交错 A/B/A/B（4/5/6 片各 ≥2 轮 warm，`-PtestShardCount`），全程 PowerShell 每 3s 采 Commit 提交量（资源定例 R6）。判据＝中位数差 >5% 且 Commit 峰值留 >8GB 余量、无换页；不达标维持 4 片并销账（脚本上限 6 已在）。

### S4 固定开销构成拆账（测量件，时间盒 0.5 天，预期 0 或 −2~5s）

现无「17s/片」的构成拆解（JVM 起动/平台 bootstrap/sandbox 任务链/Gradle 任务开销各占多少）。方法：分片 doFirst/doLast 时间戳 + gradle --profile + 测试结果 XML 首类时间差拆账；发现可消除项（重复 prepare、可关报告组件）才动手。AppCDS/JBR CDS 路线放本项可选尾注：动态 archive 对 IPGP classpath 的可用性验证一次，<3s 收益即弃。

### S5 环境盘点（报告件，产出＝用户决策点）

Windows Defender 实时保护排除项盘点（`Get-MpPreference`，只读）。项目目录/F:\gradle-home/JBR 无排除＝候选优化（Windows 实时扫描对 class/jar 高频读的经典 10~30% 税），但系统配置变更须用户授权——本任务只交盘点报告与建议，不动系统配置。

## 三、基线与验收

- **基线策略**：新树冷跑 1 轮 + 两轮 warm 起手（权重表冷启动滞后一轮教训）；对照实验全部同窗交错 A/B（窗口漂移 ±5~8% 与 <10% 效应同量级的定例）；计时跑前查 `parallel_tasks.py check`（本会话开工时有活跃车道 t-synck2j187，计时轮避让或登记独立沙盒后择空窗跑）；资源定例：全量单路收口、跑前 `timeout 10 docker info` 验 daemon。
- **红线**（沿用 T6）：零用例删减、零断言改动、测试效果不变；S1 只挪桶不删不改任何测试；S3/S4 只动构建参数且逐项可回退。
- **验收门禁**：①parity 全绿——聚合报告口径（分片+testExternal）计划类全集均有结果 XML，计数与基线轮逐轮一致、0F/0E；②同窗交错对照：T7 收口墙钟 ≤ 合流树基线，S1+S3 合力改善 ≥5%，或逐项销账的诚实台账；③master 侧零触碰（本任务写集=buildSrc/gradle.properties/文档，全在 T7 树）。
- **预期（诚实口径）**：合流树基线 ~2m50s±10s（T6 execSum 收割在干净窗口的首次兑现）→ T7 收口 2m30s~2m45s 档；若 S3 命中 6 片可再 −15~20s。若 S3/S4 全销账，净改善 −5~10s + 护栏族扩容解耦的结构性收益，同样如实交付。相对 master 现状（3m10s+ 档且无 T6 栈），合流后总收益 −12% 档起步。
