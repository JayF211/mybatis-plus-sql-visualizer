## 2. 各立项项详述

### P-立项-01：fill 关联填充（T-M22-01，原 P3-02）

**背景**：MPJ 1.5.1+ 官方 API，6 形态（`fill(field, tagField)` / 带 consumer / 带 oneClass / 带 oneField 等组合）。语义为**主查询后**收集关联键 → 关联表 `IN` 附加查询（可带 consumer 条件）→ 内存 groupingBy 回填（非 join，FillUtils 源码核实）。真实项目 0 使用、文档低频。

**实现思路（定位）**：
1. `MpjLambdaConverter`：新增 `fill` 调用解析（新 `WrapperArg.FillArg` 或复用 NestedArg）——提取 `field`（主查询字段，决定关联键来源）与 `tagField`（关联表字段）、可选 oneClass（关联实体）与 consumer（附加查询条件）；
2. 渲染：主 SELECT 段（现有）后追加第二段 `SELECT <关联表列> FROM <关联表> WHERE <tagField> IN (关联键列表)`（关联键列表静态不可得 → 占位 `?` + 参数对照说明）；
3. 复用 T-M21-02 的子查询渲染抽象与 `QueryWrapperParser`（consumer 条件链）；
4. 分页形态（fill 后主查询）与一对一/一对多差异仅影响回填语义，预览 SQL 形态一致。

**难点**：`field`/`tagField` 的实体归属判定（主表 vs 关联表）；与 selectCollection 现有子查询渲染的耦合避免。

**验收**：6 形态各一 fixture（模型构造测试 + 1 个端到端），SQL 对照 MPJ 官方输出结构；矩阵行 ⬜ → ✅。

### P-立项-02：拦截器改写模拟（T-M22-02 剩余）

**背景**：MP 拦截器族对最终 SQL 的改写面——真实项目（测试清单 X08）仅 `PaginationInnerInterceptor`（插件已按方言等价模拟）。其余拦截器真实项目 0 使用，但 MP 官方高频生态面（尤其 TenantLine）。

**实现思路（定位）**：
1. **TenantLineInnerInterceptor**：设置页新增「租户模拟」配置组（开关 + 租户列名，默认 `tenant_id`）→ 中央注入（仿 `injectLogicDeleteCondition` / `injectOptimisticLockCondition`）：SELECT/UPDATE/DELETE 条件追加 `tenant_id = ?`；INSERT 列清单补 `tenant_id`；
2. **DataPermissionInterceptor**（3.5.9+）：handler 注入片段静态不可得 → 追加可读占位条件（`AND <数据权限片段: 运行时注入>`），文档化近似；
3. **DynamicTableNameInnerInterceptor / setTableName(Function)**：表名函数静态不可求值 → 预览表名标注占位提示（与 T-M21-09 setTableName no-op 策略一致，仅提示层差异）；
4. **@InterceptorIgnore**：mapper 方法级注解（tenantLine/dataPermission/blockAttack 等成员）→ 定位消费方法 PsiMethod 读注解，命中成员则跳过对应注入；
5. **@KeySequence**：Oracle/PG 序列取主键 → INSERT 主键列渲染 `序列.NEXTVAL` 占位（设置页可配序列名格式，默认 `SEQ_表名`）。

**依赖**：`PluginSettings` + `PluginSettingsPanel` 配置面扩展（模拟开关与参数，沿用既有持久化与中英文 bundle）。

**难点**：拦截器组合时的注入顺序与去重（tenant + logicDelete + version 三层）；@InterceptorIgnore 的 PSI 定位成本。

**验收**：每拦截器开关开/关两态 fixture；组合注入顺序断言；矩阵行 ⬜ → ✅。

### P-立项-03：XML `${ew.customSqlSegment}` 面（T-M22-05）

**背景**：自定义 Mapper XML 中 `${ew.customSqlSegment}`（及 `${ew.sqlSelect}`/`${ew.sqlSet}`）展开 `Wrapper.getCustomSqlSegment()`（`WHERE ...` 片段），配套 `@Param(Constants.WRAPPER)`（`"ew"`）。测试清单 X01~X04 已收录真实项目 XML 语料面（20 个 XML，69 条语句，**全项目无 `${ew.customSqlSegment}` 使用**——纯生态面）。插件当前无任何 XML 处理。

**实现思路（定位）**：
1. **XML PSI 基础设施**：以 XML 文件轻量解析（DOM/IntelliJ XmlPsiFile）读取 `<select|update|delete|insert>` 语句文本，识别 `${ew.customSqlSegment}` 占位；
2. **wrapper 关联**：`@Param("ew")` 的 Mapper 方法名 ↔ XML 语句 id 匹配（`namespace + methodName`）；该方法签名的 wrapper 参数即展开源；
3. **预览**：在 XML 语句行提供 gutter/悬停入口——用同方法名 Java 侧 wrapper 调用链（经 `WrapperLocator` 复用）展开为完整 SQL（`SELECT ... FROM t WHERE <wrapper 片段>`）；
4. `${ew.sqlSelect}`/`${ew.sqlSet}` 同理（SELECT 列 / SET 片段展开）。

**难点**：wrapper 定义与 XML 语句的跨文件关联（可能无 Java 调用点，需从 `@Param` 类型推断）；XML 高亮/行号渲染成本。

**验收**：典型 XML fixture（含 `<if>` 动态标签 + `${ew.customSqlSegment}`）端到端预览；矩阵行 ⬜ → ✅。

### P-立项-04：Kotlin 侧（T-M22-06，原 P3-05）

**背景**：MP 官方 `KtQueryWrapper`/`KtUpdateWrapper`/`KtQueryChainWrapper`/`KtUpdateChainWrapper`、`IService.ktQuery()/ktUpdate()`、`ChainWrappers.ktQueryChain()` 等（列引用为 `KProperty1` 方法引用）；MPJ Kotlin 扩展（`com.github.yulichang.extension.kt`）。真实项目 0 使用、插件当前聚焦 Java PSI（`WrapperLocator` 注释已声明边界）。

**实现思路（定位）**：
1. **Kotlin PSI 基础设施**：`KtCallExpression` 链解析（与 Java 路径平行的 `WrapperLocator` 变体）；`KProperty1<Entity, *>` 引用 → 属性名 → 列名（`Entity::name` 语法）；
2. `detectWrapperType` 类名映射加 `KtQueryWrapper`/`KtUpdateWrapper`（复用既有 converter——SQL 生成与列解析语义相同）；
3. `service.ktQuery()/ktUpdate()` 链起点收录（复用 `serviceChainMethodNames` 机制）；
4. 测试：Kotlin fixture（`.kt` 文件）全链路。

**难点**：Kotlin PSI 依赖与解析成本；Java/Kotlin 双路径的架构收敛（避免逻辑分叉）；LightPlatform Kotlin 测试夹具配置。

**验收**：Kotlin fixture 全链路（构造/链/消费/锚点）；矩阵行 ⬜ → ✅。

### P-立项-05：方言输出真实验证（F-14 实测对比）

**背景**：9 种方言（MySQL/PG/Oracle/SQL Server/H2/SQLite/MariaDB/DM/KingBase）的 renderLimit 与引用形态基于官方文档/源码推导（DM/KingBase 为兼容性假设，见 Dialect.kt KDoc）。测试清单 §6.3 明确标注"多数据库方言实测 SQL 输出对比需连接真实数据库验证"。

**实现思路**：搭建方言验证环境（可 docker-compose 或本机实例）——对每方言执行代表性 SELECT（分页/标识符引用/参数占位），与插件输出逐字节比对；产出验证报告并修正假设性形态。

**依赖**：数据库实例可用性（DM/KingBase 需商业许可实例）。

**验收**：9 方言验证报告；DM/KingBase 假设修正或标注确认。

## 3. 立项流程与验收标准

1. **立项触发**：用户提出需求 / 真实项目语料出现该 API 使用 / 生态面需要（任一即可立项）；
2. **实施流程**（沿用既有惯例）：测试先行（fixture 先于实现）→ 增量验证（定向测试）→ 全量验证（`./gradlew clean test --no-build-cache` 全绿 + `buildPlugin`）→ 提交 git（每关键节点）→ 矩阵/清单 §5.6 状态同步（⬜ → ✅ 或标注文档化边界）；
3. **性能红线不变**：gutter 快速路径 O(1) 纯语法、不 resolve（新增入口同样遵守）；
4. **不支持面优雅降级**：任何立项项的近似实现不得抛异常，必须可读占位。
