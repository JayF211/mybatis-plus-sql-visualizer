## 一、归因（两 URL 逐一钉死，2026-09-18 实测）

第一轮（2026-09-11）归因是 `SqlLogPanel.HelpAction` 的 `BrowserUtil.browse(HELP_DOCUMENTATION_URL)` 降级分支在测试沙盒里 ShellExecute 拉起真机 Edge，已实施 `isUnitTestMode` 短路修复（master f955d85）。本轮弹的两个页面**都不在那条链上**，是第二轮残余：

### URL 2：`https://example.invalid/never-opened` —— SafeBrowserTest 直接触发

`src/test/kotlin/cn/song/mybatisplus/visualizer/util/SafeBrowserTest.kt:19`：

```kotlin
SafeBrowser.browse("https://example.invalid/never-opened")
```

该测试的**意图**是「纯 JUnit 无平台 Application 时短路生效，不会真弹浏览器」。但 `SafeBrowser.browse` 的守卫条件是：

```kotlin
val app = ApplicationManager.getApplication()
if (app != null && app.isUnitTestMode) return
```

两个漏洞叠加导致短路失效：

1. **守卫写法是「有 Application 且 isUnitTestMode 才短路」**。定时回归任务若通过 IntelliJ 平台测试框架跑（存在 Application 且 isUnitTestMode=true）短路确实生效；但任何**非平台形态的测试进程**（如 `ApplicationManager.getApplication()` 返回 null，或经 Gradle test runner 直跑 JUnit3/4 时 Application 为 mock/真实实例而 isUnitTestMode=false）会**放行**，`BrowserUtil.browse` 直接 ShellExecute 打开真机浏览器。测试注释自述「本测试环境恰好就是『无 Application』形态」——即该测试跑的时候 Application 为 null，`app != null &&` 条件不成立，**守卫必然放行**，只要这条链真执行到 `BrowserUtil.browse` 就弹浏览器。
2. **`BrowserUtil.browse` 在无平台 Application 的纯 JUnit 进程里**：IntelliJ 的 `BrowserUtil` 会沿 `BrowserUtilImpl` → `SystemBrowser` 链降级为 `Desktop.browse`/ShellExecute，不因缺 Application 抛异常——所以「不抛异常」这个断言**根本证明不了短路生效**，反而每次定时任务跑全量测试都会真开一次 `example.invalid`。

结论：这个测试**每次运行都会打开一次浏览器**（当守卫放行时），`never-opened` 这个 URL 名字成了反向flag——它就是被打开的那个。

### URL 1：`https://sql-visualizer.jvtools.cn/about/feedback` —— 两条候选链，须实施前先 grep 钉死

同文件 `SafeBrowserTest.kt:18` 也调 `SafeBrowser.browse("https://sql-visualizer.jvtools.cn/about/feedback")`，与用户所见 URL 1 完全一致——**首要嫌疑仍是同一个测试**（同一时刻连开两个 URL，Edge 会按调用顺序开两个标签，用户感知为「每隔一段时间弹这两个页面」）。

次要候选（实施前核实，不先行认定）：

- `FeedbackApiTest.kt:297` 虽出现该 URL，但那是字符串比较断言（`FeedbackApi.detailUrl("FR-0042")` 的期望值），不触达浏览器，基本排除。
- `ErrorReportDialog`/`FeedbackReporting` 的 `SafeBrowser.browse` 调用点若有测试走到 submit 成功回调路径（`FeedbackReporting.kt:66`），也可能触发；grep `[SafeBrowser]` 沙盒日志可证伪/证实。

### 触发时机吻合

ZCode 定时自动化任务每天跑全量测试（runIde/测试沙盒），与 2026-09-11 第一轮「帮助页周期性弹出」同一触发源。Edge 弹出窗口时间点 = 定时任务运行窗口。

## 二、根因本质

第一轮修复收口了 **src/main 生产代码**的所有 `BrowserUtil.browse` 出口（SafeBrowser 收口 + HelpAction 短路），但**漏了测试代码这个「守卫的消费者」**：SafeBrowserTest 的设计前提「测试环境 Application 必为 null」与守卫条件「`app != null && isUnitTestMode` 才短路」**语义不匹配**——Application 为 null 时守卫反而放行。守卫逻辑与消费方对环境形态的假设互相矛盾，测试自身成了浏览器弹出的直接触发者。

## 三、方案

**T-BL2-01（SafeBrowser 守卫语义反转，改为 fail-safe 默认短路）**：`SafeBrowser.kt` 守卫从「白名单放行」改为「黑名单/默认拦」：

```kotlin
fun browse(url: String) {
    val app = ApplicationManager.getApplication()
    if (app == null || app.isUnitTestMode) return   // 无平台环境默认视为测试，静默跳过
    BrowserUtil.browse(url)
}
```

真机（IDEA 插件宿主）Application 恒非 null 且 isUnitTestMode=false，行为零变化；所有「Application 缺失的边缘形态」（纯 JUnit、Gradle test runner、未来新测试形态）一律静默短路。这是根治——测试代码不用改 URL 也不会再弹。

**T-BL2-02（SafeBrowserTest 断言换形，消除真开浏览器的可能）**：测试不再依赖「跑下去没弹」这种不可观测副作用做验证，改为可断言的形态：

- 方案 A（优先）：给 SafeBrowser 增加可测试的判定函数（如 `internal fun shouldSkip(): Boolean` 或 `browse` 拆出 `isTestEnvironment()` 判定），测试直接断言判定结果，`browse` 主函数只做 `if (isTestEnvironment()) return; BrowserUtil.browse(url)`。
- 方案 B：测试内注入 mock Application 设 isUnitTestMode=true/false 两态，断言短路/放行分支覆盖（依赖 IntelliJ 测试框架形态，实施时按现有 headless 测试惯例择优）。
- 无论哪种，`example.invalid/never-opened` 与 `/about/feedback` 这两个真实 URL 从测试调用中移除或仅用于字符串断言，杜绝「守卫失效就真开浏览器」的测试形态。

**T-BL2-03（守卫测试补位）**：`BannedApiSourceScanTest` 既有「src/main 中 `BrowserUtil.browse(` 文件须自带短路」的扫描约定，本轮扩展两点：

- 扫描范围确认覆盖 `src/test`（测试代码同样禁止直调 `BrowserUtil.browse`，统一走 SafeBrowser）。
- SafeBrowser 自身守卫语义（null Application 必短路）加守卫测试，防未来重构回退。

**T-BL2-04（文档与记忆收口）**：

- `pitfall-test-sandbox-browser-leak.md` 追加第二轮实录（URL 2 钉死 SafeBrowserTest、守卫语义反转定案）。

## 四、验收标准

1. 定时回归任务（全量 testShards）跑完后，Edge 零弹出——以连续两个定时任务窗口无复发为准（真机人工观察，测试无法自动断言）。
2. `SafeBrowserTest` 运行期间不再有 ShellExecute/`Desktop.browse` 触达（可临时在 browse 内打日志证伪一次后移除）。
3. 全量测试绿，计数口径按 testFast 秒级通道 + 全量守卫两轮惯例。
4. `grep -rn "BrowserUtil.browse" src/test` 零命中（SafeBrowser 生产文件除外）。

## 五、风险与边界

- 守卫语义反转对真机 IDE 宿主零影响（Application 恒非 null 且非 unit test mode），不需要真机回归。
- `shouldSkip`/`isTestEnvironment` 若做成 internal，注意 Kotlin internal 对同模块测试可见即可，不需要 public API。
- 第一轮修复（HelpAction 短路）保持不动，本轮只动 SafeBrowser 与测试。
