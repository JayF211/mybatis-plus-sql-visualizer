# T-IntrUpg：旧生成拦截器自位污染残留——解析防线 + 拦截器文件自动升级

- 立项日期：2026-09-14
- 任务性质：用户真机缺陷反馈（T-JumpPath 交付同项目的后续现象）
- 反馈来源：用户截图——SQL 日志三条条目位置仍全显示 `[SqlSourceInterceptor.java:62]`（2026-09-14 14:29 捕获），期望位置=SQL 执行处业务代码行
- 上游：T-JumpPath（merge 50a9cc7）§七 留观「已注入旧模板的用户工程不会自动更新 isSelf……是否提供升级能力未在本期范围，视用户反馈另行立项」——本反馈即触发点

## 一、取证（沙盒日志 + demo 工程磁盘实锤）

1. **条目时间 14:29:06~08**（截图）对应沙盒日志 14:29:05~09 三次进程 attach 与「首条 SQL 自动展开日志工具窗」（idea.log:7690-7699），捕获链正常。
2. **污染源 = join-demo 手工拷贝旧件**：`mybatis-plus-join-demo/src/main/java/cn/song/mpjdemo/config/SqlSourceInterceptor.java`（文件时间 12:41:19，早于插件模板修复）第 79 行 isSelf 常量为 `cn.equals("cn.song.mybatisplusdemo.config.SqlSourceInterceptor")`——拷贝件漏改包名常量，与实际类 `cn.song.mpjdemo.config.SqlSourceInterceptor` 分叉 → 自跳过失效 → 自身 locateSource for 循环行（该拷贝件第 **62** 行，`sed` 实读吻合）被当调用点。
3. mybatis-plus-demo 原件（12:40 注入，常量=mpdemo 与类一致）行为正确，被污染仅 join-demo——拷贝件数量决定污染面。
4. 插件侧 `processConsoleLine` 对标记行照收（SqlLogConsoleBridge.kt:642-646 暂存直写条目），无「自帧污染形态」识别——位置错也照展示、照跳转，用户见错。

## 二、根因定性（与 T-JumpPath 的关系）

T-JumpPath-01 修的是**生成期**（新注入文件不再产生自位）；本缺陷是**存量**：旧生成文件不会被触碰（AlreadyExists 短路），且插件解析侧对污染标记无防线。两个缺口：

- RC-A（存量升级缺口）：无「升级已生成文件」能力，用户删除旧文件重注入无引导（且手改过的文件用户不敢删）。
- RC-B（解析防线缺口）：已知污染形态（标记路径文件名 = SqlSourceInterceptor.java）插件可确定性识别却照收，错位置进列表/反查/跳转全链路。

## 四、修复设计

### 4.1 防线（01）

`SqlSourceMarker` 新增：

```kotlin
/** 标记路径是否指向拦截器模板文件本身（旧模板 isSelf 分叉时自帧污染形态）。 */
fun isInterceptorSelfPath(relativePath: String): Boolean =
    EntrySourceMatcher.normalize(relativePath).substringAfterLast('/') == "SqlSourceInterceptor.java"
```

`processConsoleLine` 第 1) 步：marker 解析成功且 `isInterceptorSelfPath` → 不暂存（打 LOG.info 一行，含原路径便于远程排障），返回空列表。效果：旧件环境条目=无位置 → 跳转弹 MissingSource 引导 → 用户点「立即注入」触发升级（4.3）→ 重启应用自愈。文件名判定误伤面=用户业务类恰名 SqlSourceInterceptor.java（模板注入文件名常量，可忽略级；即便误伤也只丢位置不丢条目）。

### 4.2 升级判定（02）

```kotlin
internal fun needsInterceptorUpgrade(text: String): Boolean =
    text.contains("自动生成于 SQL Visualizer 插件") &&      // 仅模板产物可被覆盖（用户手改文件不动）
        text.contains("cn.equals(\"") &&                    // 旧 isSelf 常量拼接形态
        !text.contains("getClass().getName()")              // 已是运行时比对形态则跳过
```

判定基于运行时行为缺陷形态而非模板全文比对：模板其他部分后续演进不误判。

### 4.3 升级执行（03）

- `detectForInject`：对 existed 结构逐个 `VfsUtil.loadText`（读权限内合法）读拦截器文件，needsInterceptorUpgrade 命中 → 转入 `upgradable` 清单（与 ready 同型 `ProjectStructure`），`PrepareOutcome.Ready` 增 `upgradable` 分量。
- `createFiles`：upgradable 项不建新文件，EDT 中对既有文件 `VfsUtil.saveText(vf, generateInterceptorClass(basePackage))`（VfsUtil.saveText 243 javap 实证存在）——内容重写为本模块正确包名+运行时 isSelf；包路径若与模块 basePackage 不符（拷贝件场景），旧文件保留不动、新包路径另生成一对（避免跨包移动破坏引用）。实现从简：升级仅重写文件内容；拷贝件位于 `<mpjdemo>/config/` 而 basePackage 检测取该模块实际包（mpjdemo）→ 生成内容与所在包一致，重写即修复常量，文件位置不动。
- 消息聚合：upgraded 模块并入 injected 清单（对用户统一为「注入/更新成功」），成功消息多模块形态沿用 successMulti；全部为升级且无新建时走新键 `log.inject.upgraded`（{0}=模块数 {1}=模块清单，说明「已更新旧版拦截器文件」）。
- AlreadyExists 语义不变：全部文件均为新版模板时才提示已存在。

### 4.4 用户侧恢复步骤（写入交付说明）

升级仅改源码，**join-demo 应用须重启**后新标记才生效；重启前旧进程仍打污染标记，由 4.1 防线保证 UI 不再显示错位置。
