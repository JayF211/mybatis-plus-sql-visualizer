## 1. 优先级判定依据

### 🔴 P0 —— 用户高频痛点，预览 ≠ 运行时

**判定标准**：真实项目几乎必用，且当前预览输出与运行时 SQL 存在**语义差异**（不是格式差异，是条件缺失）。

- **#1 多租户**：`TenantLineInnerInterceptor` 是 MP 生态最高频拦截器。用户开了它，预览的 SELECT/UPDATE/DELETE **缺少 `tenant_id = ?` 条件**、INSERT **缺少 `tenant_id` 列**——这是"预览看起来对、执行结果错"的最危险情况。
- **#2 XML `${ew.customSqlSegment}`**：XML + Wrapper 混用是 MP 最常见的写法（动态 SQL 在 XML、条件在 Java）。当前 `${ew.customSqlSegment}` 被当普通 `${}` 求值为空串，**整个混合形态完全没覆盖**。

### 🟡 P1 —— 明显体验缺口，成本可控

- **#3 fill**：P-立项-01，6 形态，真实项目低频但官方 API。
- **#4 SQL 性能分析**：新增价值点，`SqlTextAnalysis` 已有基础，边际成本低。
- **#5 参数批量导入**：预览面板逐个填 `?` 效率低，剪贴板导入是自然延伸。
- **#6 日志智能分组**：日志工具窗口目前平铺，高频 SQL 无折叠。
- **#7 批量 SQL→Java**：当前一次一条，多语句需反复粘贴。

### 🟢 P2 —— 完善性 / 效率，不阻塞核心

- **#8 暗色主题**：插件图标有 `_dark` 版，但预览弹窗 UI 无主题感知。
- **#9 实体缓存**：性能优化，大项目收益。
- **#10 gutter 防抖**：交互体验微调。
- **#11 verifyPlugin 提速**：构建效率，发布前全量、日常 smoke。

## 3. 全局实施规范（与既有约定对齐）

### 3.1 测试先行
每项遵循既有惯例：**fixture 先于实现** → 增量验证（定向测试）→ 全量验证（`./gradlew clean test --no-build-cache` 全绿 + `buildPlugin`）→ 提交 git。

### 3.2 性能红线（不变）
- gutter 快速路径 **O(1) 纯语法、不 resolve**（新增入口同样遵守）。
- 任何立项项的近似实现**不得抛异常**，必须可读占位（对齐既有"优雅降级"原则）。

### 3.3 不支持面优雅降级
- 拦截器组合注入顺序与去重（tenant + logicDelete + version 三层）需明确优先级。
- 无法静态求值的（如 `DynamicTableName` 表名函数、`DataPermission` handler 片段）→ 追加可读占位 + warning，不抛异常。

### 3.4 文档三处同步（既有约定）
每项交付后同步更新：
1. `docs/变更记录.md`（变更摘要）
2. `docs/MP-MPJ官方API覆盖矩阵.md`（矩阵行 ⬜ → ✅ 或标注文档化边界）
3. `CHANGELOG.md`（发布时合并入版本条目）

### 3.5 i18n 中英双语同步
任何新增 UI 文案必须同时写入：
- `src/main/resources/messages/MpSqlVisualizerBundle.properties`（英文默认）
- `src/main/resources/messages/MpSqlVisualizerBundle_zh.properties`（中文）

### 3.6 注释风格
中文 KDoc + 任务 ID（如 `T-Mxx-yy`），与既有代码一致。

### 3.7 提交信息格式
`fix:` / `docs:` / `feat:` 前缀，描述具体改动，必要时附 `Co-Authored-By`。
