### R48 MetaObjectHandler 自动填充仿真（本轮首推）

- 痛点：审计列（create_time/update_time/create_by）走 MetaObjectHandler 运行时填充是 MP 项目标配，而预览把 fill 列当普通列给 `?` 占位（EntityResolver.kt:202-219 读 fill 只用于分组排序、BatchOperationConverter.kt:433-435 只在 insertBatchSomeColumn 模板里静默剔除 fill=UPDATE 列）——运行时有值、预览看不到，「预览=运行时」的核心承诺在 fill 列上失真；且该剔除语义对用户完全不可见。
- 形态：预览参数区对 fill 列加「自动填充」角标+可填模拟值（复用 AUDIT 分组与 BatchColumn 勾选列形态）；进阶档：PSI 扫描项目内 MetaObjectHandler 实现类的 strictInsertFill/strictUpdateFill 调用，静态推导填充来源（`LocalDateTime.now()` → 标注 now()）。
- 规模 M（角标+手填模拟值可先做 S 档）；基建复用=TenantLineEnhancer 的 INSERT 列追加先例（BatchOperationConverter.kt:452-464 同形）+EntityResolver fill 读取。
- 竞品零对位（推断）：同类插件均无 MetaObjectHandler 静态感知；这是 §2.3 盘点出的 MP 拦截器仿真唯一缺位——补齐即 MP 生态独占叙事闭环。
- 前提 V72：MP 3.5.x fill API 三形态（strictInsertFill/setFieldValByName/metaObject.getValue）静态可识别面；多 Handler 共存冲突语义；fill 列默认勾选态变化对既有 CRUD 测试的回归面。

### R49 Wrapper 链布尔条件求值探镜

- 痛点：XML 条件已有真/假/未求值三态标注（R30），Wrapper 链布尔条件（`.eq(condition, …)` 首参）只有无反馈勾选框（ConditionToggle.kt:9-27）——用户分不清「我勾的」还是「引擎猜的」，两条链路体验不对称。
- 形态：复用 ExpressionEvaluator 分级策略（ExpressionEvaluator.kt:40-54，字面量/变量追踪/方法调用/前缀运算已全覆盖）静态求值布尔实参，条件行尾轻量标注，UI 照抄 xmlConditionOutcomeLabels 形态（SqlPreviewPanel.kt:4181-4209）。
- 规模 S~M；红线全兼容；竞品零对位（推断）。
- 前提 V73：ConditionToggle.flagSource 的来源方法全集与布尔重载识别率；MP condition 缺省 true 语义下的文案误导风险。
