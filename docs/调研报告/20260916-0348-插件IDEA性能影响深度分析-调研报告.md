## 1. 总结论

**维持结论：默认配置下插件对 IDEA 性能影响可忽略；这 48 个新提交无一引入常驻开销、周期任务或插件自有线程，其中 T-PerfSweep2 六项全部按意图落地，是本系列五轮以来首次出现的净改善轮。** 新增代码审读后得 1 个中低危发现（分桶路由每行现场编译正则，一行可修）与 4 个低危项（§5），均非常态高成本，无一构成「会带来性能问题」级别的缺陷。

支撑结论的四个增量事实：

1. **常驻面零变化、常驻成本净减**：plugin.xml 本轮改动仅 groupWeight 钉序（T-SettingsOrder）、更新检查注释对齐（T-PerfSweep2-06）、errorHandler 注释与版本/changeNotes 文案；13 个 lineMarkerProvider 与 4 个 completion contributor 计数未动（grep 复核），快速路径红线依旧守住（§3.1）。全局红线盘点 Thread.sleep 实点 7→6（调度器 drain sleep 随 T-PerfSweep2-05 消除），周期调度/Alarm/PSI 树监听维持 0（§4.4）。
2. **唯一新增后台设施挂在平台共享池上，插件自有线程数维持 2 条**：T-FeedbackBatch2 的 500ms 防抖复用 `AppExecutorUtil.getAppScheduledExecutorService()`（`IdeErrorReportSubmitter.kt:112`），不新建线程、无需 dispose，闲时零成本；插件自建线程仍只有反馈错峰调度器（daemon 单线程，`PendingReportScheduler.kt:30-32`）与 SqlLogAutoSaver 落盘线程两处（§4.2/§4.4）。
3. **上轮六个发现点全部收敛且经二遍实证**：EDT 每拍 O(全史) 文档拷贝、响应体无上限、批量附件无界组装、exec 缓存槽项目关闭残留、调度器占线程拒新、注释漂移——六项修法与立项意图一致，其中 01/03/04 直接消除了三处 EDT 重复分配/残留面（§3.2）。
4. **历史热点治理痕迹全部原样在位**：预热 60ms 预算、控制台退避轮询、正则提常量惯例、指纹 LRU 128 条等逐项回验未退化（§3.1/§3.3/§4.1）。

## 4. 新增子系统审计

### 4.1 日志链路（并发分桶 +232、原始时间 +85 新文件、搜索增强、ListParamRenderer 新 151 行）

- **并发分桶机制（7d23c1d 修参数错挂）**：按线程 token 分桶的独立状态机——`ThreadBucket` 状态机 + LinkedHashMap 桶表 + fail-open 回退桶，桶数上限 64、超限冲刷空闲桶防膨胀。无锁无 synchronized，仍依赖 filter 回调单线程假设（EDT）。`feed()` 每行先路由 `bucketFor` → `extractThreadToken`，**此处每行现场 `Regex(...)` 编译级别关键词正则，是本轮唯一实质热路径退化点（§5.1）**；其余新增（THREAD_BRACKET/PURE_DIGIT 已预编译且只扫级别前后 35 字符窗口、pendingLogLine 每语句一个引用、closePending 遍历 ≤64+1 桶）均温和。出证：`JdbcTemplateLogParser.kt:70-73`（feed 逐行路由）、`:203-216`（bucketFor+淘汰）、`:442`（maxParseLength=20000）、`:445`（64 桶上限）、`:230`（每行正则）。
- **原始时间记录与显示切换（51eb01a）**：结构正确——捕捉时只暂存日志行引用（`pendingLogLine`），语句闭合时每条目一次 `LogTimestampParser.parse` 并存进条目（`JdbcTemplateLogParser.kt:111`、`:157`/`:275`，MyBatis `:118`，Hibernate `:221`）；显示切换只换 Long 来源重新 format（`SqlLogPanel.kt:1529-1532`），零回推零全量重解析；格式化发生在可见单元格渲染（`SqlLogPanel.kt:1679`、`HistorySqlLogPanel.kt:703`），惰性 O(可见行)。LogTimestampParser 本体 5 个 Pattern 全部预编译（`LogTimestampParser.kt:20-31`），仅 SimpleDateFormat 每次尝试新建（`:75`），最坏 5 格式×2 策略匹配——每条目一次，低。
- **搜索行号/时间 + 右键复制（5eeb884）**：200ms 防抖单发 Timer + 销毁 stop 形态不变（`SqlLogPanel.kt:633`/`:1399`、`HistorySqlLogPanel.kt:81`/`:528`、stop `:1327-1328`/`:517-518`）；行号匹配是 Long 精确 equals 零正则（`:161-165`）；时间匹配每条目走一次「读设置 + 新建 SimpleDateFormat」（`:166` → `:1526-1537`，历史页 `:392-398` 同款），条目上限 logMaxCount 默认 200，O(200) 有界（§5.3）；右键复制是 showContextMenu 内即时构建 popup、仅右键时计算剪贴文本，无常驻监听（`SqlLogPanel.kt:1270,1281-1292`、`HistorySqlLogPanel.kt:436,444-453`）。

### 4.2 反馈链路（T-FeedbackBatch2 防抖合并 + T-MarketInternal 整改）

- **防抖合并挂平台共享池，零自有线程**：`IdeErrorReportSubmitter.kt:112` 复用 `AppExecutorUtil.getAppScheduledExecutorService()`（daemon、随应用回收，无 dispose 义务）；trailing 防抖 500ms（每次入队 cancel 重排 `:116-118`，常量 `:208`）+ 自首条 3s 强制兜底（`:117`，常量 `:211`）。flush 后 EDT 构建单个对话框（`:171-192`），复合 consumer 每 flush 分配一次把同一结果回放本波各平台簇（`:141-143`），逐次 submit 增量仅一个 filter 列表 + 一个 PendingCall 小对象（`:98-105`）。

## 5. 发现点与建议（1 中低 + 4 低，按优先级）

> 五项已立项收敛：`docs/开发计划/20260916-0651-T-PerfSweep3-性能五项收敛-开发计划.md`（T-PS3-01~05，与全分支功能全景审计报告 §7 O-23 同源立项；建议随最近的功能分支合流窗口实施）。

1. **【中低】分桶路由每行现场编译正则**（`JdbcTemplateLogParser.kt:230`）：`feed()` 每行先走 `bucketFor`（`:71`→`:203`）→ `extractThreadToken` 首行 `Regex("""\b(DEBUG|TRACE|INFO|WARN|ERROR)\b""").find(line)`——**每行一次 Pattern.compile + 无级别关键词行（续行/堆栈/普通输出）全行扫描**，发生在 EDT 捕捉回调上；高吞吐控制台下随行数线性累积分配压力。同文件 `:287` 注释自证本项目 T-PerfSweep F2「正则提常量」惯例，companion 里 `:452-:512` 九条正则均已提常量，唯此条漏网。建议：提为 companion 常量，一行改动。
2. **【低】防抖队列条数无上界**（`IdeErrorReportSubmitter.kt:73`、`:115`）：`pendingCalls` 无条数上限，时间维度有 trailing 500ms + 3s 兜底双保险（`:117`、`:208`、`:211`）但同一波「报告全部」簇数不限，窗口内等量累积 PendingCall（持有事件与堆栈文本引用）至 flush。到达源是用户单次动作、现实有界。建议：enqueue 加队列长度上限（如 64 条提前置 delayMs=0），一行封死理论边界。
3. **【低】搜索时间匹配每条目新建 SimpleDateFormat**（`SqlLogPanel.kt:166` → `:1526-1537`，`HistorySqlLogPanel.kt:392-398` 同款）：每次防抖搜索对每条目执行「读设置 + new SimpleDateFormat + format」，O(logMaxCount=200) 有界、EDT 一次，量级毫秒内。建议：把格式化片段缓存到条目（设置变更时失效）或面板级复用 formatter（EDT 单线程可安全复用）。
4. **【低·连续三轮在册】重放守卫 stamp 变化全文档拷贝**（`SqlLogConsoleBridge.kt:380`、`:388-395`）：stamp 未变走缓存，但文档一变仍 `getText.invoke(doc)` 整串拷贝后 `lineSequence().firstOrNull()`，O(全史) 分配形态未变（捕捉开启时的常规拍路径）。建议：照 T-PerfSweep2-01 手法改 `getCharsSequence`，首行只需读 `[0, 首个\n)` 区间片段。
5. **【低·连续三轮在册】WrapperCache 无自动淘汰**（`psi/WrapperCache.kt:41`）：ConcurrentHashMap 无容量上限、无失效清理，键含文件+锚点+签名、值含模型对象，长会话缓慢增长。单项量级有界（每条为单次预览产物），但三轮未清账。建议：容量上限 + LRU 淘汰，或按项目挂 Disposer 关闭时清空。

上述均不动摇总结论：1 有明确的「每行一次编译」量级与一行修法，2~3 是用户动作触发的有界长尾，4~5 是连续在册的已知有界遗留。
