# 插件 IDEA 性能影响深度分析（调研报告）

**创建时间**：2026-09-14
**文档定位**：回答一个问题——SQL Visualizer 会不会拖慢 IDEA。逐文件审读 master 工作树（50d3fb9）全部性能敏感链路：daemon 快速路径、EDT 热路径、轮询与定时器、线程模型、缓存与内存滞留、启动期开销，全部结论带 文件:行 出证。文中行号以 2026-09-14 工作树为准。

**结构说明**：§1 为总结论；§2 为分析范围与方法；§3~§7 按「常驻开销 → 控制台捕获 → 用户触发链路 → 内存 → 启动期」分链路给出证据；§8 为量化估算；§9 为发现点与改进建议（仅 3 个低危长尾项）；§10 为审计覆盖清单。

---

## 1. 总结论

**默认配置下插件对 IDEA 性能影响可忽略；高负载场景（捕捉开启 + 高频 SQL 输出 + 大文件编辑）各热路径均有明确的有界性设计，无阻塞性风险。** 全源码审计后仅发现 3 个低危长尾项（§9），无一构成「会带来性能问题」级别的缺陷。

支撑结论的四层证据：

1. **启动期零开销**：两个 postStartupActivity 在默认配置下双双短路——更新检查默认关（`PluginSettings.kt:151` `autoCheckUpdate=false`），自动监听默认关（`PluginSettings.kt:185` `logAutoCaptureOnStart=false`），即默认启动不产生任何额外线程、定时器或网络请求。toolWindow 由 IDE 惰性创建，用户不打开侧边栏则零成本。
2. **daemon 快速路径纪律**：13 个 lineMarkerProvider 全部锚定窄叶元素类型、O(1) 语法判定、负例即返，无 resolve、无遍历、无索引访问（§3）；这一红线从 M10 起写入 KDoc 并延续至今（`WrapperAnchorDetector.kt:24-26`）。
3. **高频路径治理痕迹完整**：控制台捕获链路存在成体系的 T-Perf/T-LogPerf/T-PerfBatch 治理——轮询指数退避、反射 Method 缓存、组件树遍历短路、UI 刷新置脏合并、磁盘写异步批量、去重键指纹化 + 有界化（§4）。历史上出现过的性能问题均已修复并带回归测试。
4. **线程模型正确**：所有 PSI 重操作（转换/反查/搜索）一律后台线程 + ReadAction，EDT 只做渲染（§5.1）；未发现任何 EDT 上的无界忙等或同步 IO。

## 2. 分析范围与方法

- **范围**：master 工作树全量 `src/main/kotlin/cn/song/mybatisplus/visualizer/`（约 20 个包），以 plugin.xml 注册的常驻扩展点为索引逐链路下钻；`reverse/`、`share/`、`database/`、`xml/`、`psource/` 等纯用户点击触发包做快速路径抽查（§10）。
- **方法**：plugin.xml 扩展点盘点 → 每个常驻扩展点实现文件的快速路径审读 → 全局红线扫描（`javax.swing.Timer`/`Alarm`/`Thread.sleep`/`invokeAndWait`/监听器注册/PSI 强引用缓存/无界集合，grep 全量核对）→ 对发现点回读上下文确认为真实风险而非误报。
- **范围外**：M56 agent 字节码增强代码在 `feature/t-m56-01-agent-base` 分支未合入 master（本地分支清单 `git branch` 实证），且其注入目标是用户应用 JVM 而非 IDE 自身；合入 master 时应另做一轮独立评估。

## 3. 常驻扩展点开销（daemon 与补全热路径）

### 3.1 13 个 lineMarkerProvider：全部守住快速路径红线

daemon 高亮 pass 对 PSI 树每个叶子元素回调各 provider 的 `getLineMarkerInfo`（平台契约，`JpaGutterLineMarkerProvider.kt:49-52` 注释明示），因此这是插件唯一的「代码编辑期间持续付费」的常驻成本。逐个核查结果：

| Provider | 锚点叶类型 | 快速路径成本 | 出证 |
|------|------|------|------|
| SqlGutter（Wrapper 链） | PsiIdentifier/PsiKeyword/new | O(1) 纯语法：parent 链 + `PsiClassType.getClassName()` 文本匹配，不 resolve | `SqlGutterLineMarkerProvider.kt:40-43`、`WrapperLocator.kt:1300-1308` |
| AnnotationSql | 注解 @ token | O(1) 注解名判定 | `AnnotationSqlGutterLineMarkerProvider.kt` |
| XmlSql / PagesXml / HbmNamedQuery | XML 标签 | O(1) 标签名判定 | `XmlSqlGutterLineMarkerProvider.kt` 等 |
| JpaGutter | PsiIdentifier | O(1) 门控后仅在白名单方法名命中时做受限家族判定（注释自述「微秒级 resolve 例外」）；且「调用点反查需 resolve」的形态**刻意不做** gutter | `JpaGutterLineMarkerProvider.kt:43-44,94-100` |
| Jpql / NamedQuery | AT token / 注解 | O(1) 注解名文本判定 | `JpqlGutterLineMarkerProvider.kt:35-45` |
| CriteriaQuery / Hql / CustomDaoHql / JdbcTemplateSql | PsiIdentifier | O(1) 方法名白名单（Set 常量）+ parent 链结构判定 | 各文件 `getLineMarkerInfo` 首段 |
| StringSqlMethod | 方法名 PsiIdentifier | **唯一带遍历的快速路径**：命中方法名后做一次方法体子树结构遍历（零 resolve 主路径），带 200,000 字符护栏 + 家族守卫防双图标 | `StringSqlMethodGutterLineMarkerProvider.kt:85-99,121` |

三个共性护栏进一步压低常驻成本：

- **开关前置**：用户关闭 gutter 图标后逐叶判定直接短路（T-Perf-23，`SqlGutterLineMarkerProvider.kt:41-42`、`HqlGutterLineMarkerProvider.kt:46`）。
- **负例即返**：绝大多数叶子（字符串字面量、括号、关键字等）在首个 `instanceof` 失败处返回，成本为纳秒级类型检查。
- **AnchorDetector 红线**：`WrapperAnchorDetector` KDoc 硬性规定「禁止 PSI resolve、PsiTreeUtil 遍历、文件级扫描」（`WrapperAnchorDetector.kt:24-26`），场景 D 去重用的 `isWrapperVariable` 亦为 O(1) 语法判定（同文件 :204）。

唯一的理论 resolve 触点：场景 B 对变量调用 `variable.type`，`var` 声明的局部变量会触发类型推断——但推断结果落在平台 resolve 缓存，daemon 本身也要为同一变量推断类型，实测代价被缓存吸收，不构成独立成本。

乘数效应评估：13 个 provider × 每叶一次回调，万叶文件的量级约为 10⁵ 次廉价判定/高亮 pass，毫秒级且与 daemon 自身遍历重叠，不构成可感知开销。StringSqlMethod 的方法体遍历使单文件总成本仍为 O(文件大小)（各方法体遍历之和），护栏确保单方法不超 20 万字符。

### 3.2 4 个 completionContributor：仅在补全触发时执行

补全贡献者不常驻付费，Ctrl+Space 触发时才走 `addCompletions`。四者首行守卫：

- WrapperCompletionContributor：`ChainStateDetector.detect` 沿 parent 链回溯链首，无 resolve（`ChainStateDetector.kt:51-66`）；非 Wrapper 链位置完全透传 IDE 默认行为（`WrapperCompletionContributor.kt:29-30`）。
- XmlSqlCompletionContributor：statement 标签定位 + 根标签名 `mapper` 判定（`XmlSqlCompletionContributor.kt:65-69`）；实体解析仅补全触发时执行（plugin.xml:193 注册注释）。
- AnnotationSqlCompletionContributor：字符串字面量判定即返（`AnnotationSqlCompletionContributor.kt:65-75`）。
- SqlCompletionContributor：注册于 SQL 语言，仅预览编辑器场景（IS_PREVIEW_EDITOR 守卫）。

### 3.3 其他常驻注册

- `errorHandler`/`notificationGroup`：无热路径，出错时才回调。
- Settings `applicationConfigurable` × 6：设置页打开时创建，无常驻成本。
- ToolWindow：IDE 惰性机制，未打开不实例化。

## 4. 控制台捕获链路（开启捕捉后的持续成本）

这是插件唯一的持续后台活动。先给结论：**全部成本有界且已治理**，分五层看。

### 4.1 轮询（EDT 定时器）

- 常规轮询 2s 一拍，armed 等待期 500ms 起步指数退避至 2s 封顶（T-LogPerf-01，`SqlLogConsoleBridge.kt:106-141,514-521`）——历史上 100ms 常驻已被修复。
- 每拍 `scanAll` 的反射调用走 ConcurrentHashMap Method 缓存（T-LogPerf-02，`SqlLogConsoleBridge.kt:527-540`）；descriptor→console 缓存命中时短路组件树递归遍历（T-LogPerf-03，`:245-252`），缓存上限 64 条超限整体失效（`:251,516`）。
- 单拍成本：数次已缓存反射调用 + identity map 查找，微秒级。项目停止后轮询保持（armed 重布防语义，`SqlLogManager.kt:404-423`），成本不变。
- 轮询兜底存在的根因是平台兼容：2026.2 起 `RunContentManager` 不再 extends ContentManager，事件监听不可注册（`SqlLogConsoleBridge.kt:21-24`）——轮询是兼容性代价而非设计失误。

### 4.2 控制台 Filter 逐行回调

Filter 随控制台打印逐行回调（通常在 EDT）。单行成本：

- 源码标记前缀判定 + 三解析器 `feed`（各为前缀匹配，不匹配即忽略）+ 重放守卫 stamp 比较（`SqlLogConsoleBridge.kt:326-351,635-676`）。
- 行长由 `maxParseLength`（默认 20000）截断兜底（`SqlLogConsoleBridge.kt:33`）。
- 逐行不读 PluginSettings——配置快照在挂载/设置变更事件时同步（T-LogPerf-04，`:321-322,410-416`）。
- 重放风暴中同 stamp 连续行只付一次行 0 文本拷贝（T-PerfSweep F1 + stamp 缓存，`:386-397`）；混合态分支的最坏情况见 §9 发现点 3。

### 4.3 条目缓冲与去重

- 缓冲上限默认 200 条、超限淘汰最早（`SqlLogEntryBuffer.kt:118-121`、`PluginSettings.kt:439`），内存占用上界明确。
- 去重判定与入队合并进同一 `synchronized(entries)` 临界区——修复过无锁遍历与 EDT 清空并发的 CME 红色报错（T-Perf-06，`SqlLogEntryBuffer.kt:107-135`）。去重为 O(缓冲长度) 线性扫描，n≤200 + 可配置，完成语句级（非逐行），量级可忽略。
- 去重丢弃计数键已指纹化（防原文文本永久驻留，T-Perf-19）并加 4096 键上限淘汰最旧（T-PerfSweep F3，`SqlLogEntryBuffer.kt:52-74,312`）——修复过「十万级去重会话累积百万级键」的无界增长。

### 4.4 UI 刷新（EDT 调度风暴治理）

- 管理器层：置脏 + 单个幂等 flush，数百条 SQL 的风暴合并为数十次轻量刷新（T-Perf-03，`SqlLogManager.kt:471-487`）。
- 缓冲层：内容通知「20 条 + 200ms」双阈值节流，低流量下每条即时、与节流前等价；首条开窗与徽章计数走独立即时通道不被节流切断（T-PerfBatch，`SqlLogEntryBuffer.kt:13-19,287-299`）。
- 面板层：刷新代际 + `lastRendered` 差分基线做增量渲染，旧分批追加链检测代际过期即终止（`SqlLogPanel.kt:280-290`）。

### 4.5 磁盘自动保存

淘汰条目投递 ConcurrentLinkedQueue，专用单守护线程「mpsv-sql-history-autosave」整批一次 flush；写期间新到条目重新调度不丢条（T-Perf-12，`SqlLogAutoSaver.kt:59-90`）。修复过「回调在控制台输出热路径同步 flush 磁盘」的历史问题。单文件 100MB 滚动（`:27`）。

### 4.6 事件监听

项目级仅两处 messageBus 订阅：设置变更（事件驱动刷新，取代逐行同步）与 ToolWindowManagerListener 可见沿判定（轻量字段比较，`SqlLogManager.kt:138-171`）。监听器随服务 Disposable 自动注销，面板侧监听器有命名引用 + removeListener 防累积（T-Perf-15，`SqlLogManager.kt:307-311,454-461`）。

## 5. 用户触发链路（点击/快捷键时才付费）

### 5.1 预览与转换：线程模型正确

统一模式为 `executeOnPooledThread` + `ReadAction.compute` 执行 PSI 重操作，结果经 `invokeLater` 回 EDT 渲染（`SqlPreviewService.kt:1873-1884`）。gutter 点击、方法定义聚合、SQL→Java、CRUD 生成、日志条目反查等入口全部复用该模式（抽查 `SqlGutterLineMarkerProvider.kt:134-140,143-152`、`StringSqlMethodGutterLineMarkerProvider.kt:136-163`）。EDT 上零 PSI 慢操作。

### 5.2 WrapperCache：失效维度完备，淘汰机制缺失（§9 发现点 1）

- 键用 `VirtualFile.url` 字符串 + identityHashCode，不持 PsiFile 强引用（T-Perf-18，`WrapperCache.kt:23-35`）——关闭文件的 PSI 可回收。
- 三维修失效：文件 modificationStamp + resolveVariables 开关 + 表配置签名（`:55-70`），命中时还校验实体文件戳（`SqlPreviewService.kt:193-200`）——设置变更与实体注解变更都能击穿缓存，正确性无虞。
- 唯一缺口：`ConcurrentHashMap` 无容量上限、无自动淘汰，条目只随用户显式「清除缓存」消失（`WrapperCache.kt:41,73`、`PluginCacheManager.kt:25-36`）。增长速率受用户预览点击约束（每次点击至多新增 1 条），非 daemon 自动触发，属低危。

### 5.3 SQL 执行/数据库控制台链路（execute 包，2800+ 行）

- 四处 `javax.swing.Timer` 均为**有界重试/观察窗**：600ms×8 拍结果刷新、1000ms×6 次 script model 稳定探测、8s 单发连接观察、400ms×N 次结果 Tab 重试，全部带代际守卫（generation 不匹配立即 stop 防空转）（`DataSourceSelector.kt:749,1660,2436,2566`）。
- 历史 EDT 忙等已修复（T-Perf-13：`repeat(20){Thread.sleep(20)}` 忙等编辑器实例改为后台轮询，`DataSourceSelector.kt:1156-1183`）。
- 仅在用户执行 SQL 时激活，不常驻。

### 5.4 补全触发链与反查

`WrapperSearchService` 用范围受限的 ReferencesSearch 且约定调用方持 ReadAction（`WrapperSearchService.kt:4-9`）；`PreviewReceiverResolver` 用 `WeakHashMap<PsiFile,...>` 缓存（`PreviewReceiverResolver.kt:75`）——文件可回收。

## 6. 内存与滞留审计

- **无 PSI/编辑器强引用的静态缓存**：全源码 grep 仅 `PreviewReceiverResolver` 一处 PSI 类型缓存且为 WeakHashMap（§5.4）；WrapperCache 键为 url 字符串（§5.2）。
- **条目模型纯字符串**：`LogSqlEntry` 为 rawSql/restoredSql/params/summary 等字符串字段（`LogSqlModels.kt:24-56`），summary 截断展示，缓冲 200 条上界，条目淘汰即自动保存后释放。
- **有界化兜底**：descriptorConsoleCache 上限 64 超限全清（防死引用滞留）；dedupeCounts 上限 4096（§4.3）。
- **监听器生命周期**：服务级订阅挂 Disposable 树（项目关闭自动断开）；面板级监听器命名引用注销（T-Perf-15）；动态插件卸载路径上，更新通知动作显式 expire 防「插件未完全卸载」警告（`StartupUpdateCheck.kt:73-76` 实证注释）。
- **逐行反射句柄**：控制台 Editor/Document Method 在挂载时解析一次缓存（T-PerfSweep F1，`SqlLogConsoleBridge.kt:365-371`），不再逐行 getMethod。

## 8. 量化估算（量级表）

| 场景 | 成本量级 | 依据 |
|------|------|------|
| 默认启动 | 0 额外线程/定时器/网络；gutter 判定随 daemon pass 毫秒级 | §7 |
| 编辑万叶 Java 文件（gutter 开） | ~10⁵ 次纳秒级判定/pass，叠加后仍为 daemon pass 的零头 | §3.1 |
| 捕捉开启、无项目运行（armed） | 每 500ms~2s 一拍微秒级反射扫描（EDT，退避封顶） | §4.1 |

| 长会话内存 | 缓冲/历史/去重键/descriptor 缓存全部有界；WrapperCache 随点击缓慢增长（低危，§9.1） | §6 |

## 9. 发现点与改进建议（均低危，按优先级）

1. **WrapperCache 无自动淘汰**（`WrapperCache.kt:41`）：条目随预览过的锚点只增不减，仅设置页手动清。会话内每次预览新增 1 条、每条持有解析模型（模型本身不持 PsiElement 强引用，实体校验走文件戳），增长缓慢；但极端长会话 + 大量不同锚点预览下无上界。建议：挂文件关闭回调清理该文件条目，或加简单 LRU 上限（如 512 条），并把 `clearAll` 收录表补进 KDoc（现状已收录，`PluginCacheManager.kt:28-35`）。
2. **预览面板预热等待为 EDT sleep-poll**（`SqlPreviewPanel.kt:428-443`）：`awaitPrewarmedTempFile` 在 EDT 上以 `Thread.sleep(PREWARM_POLL_MS)` 轮询等预热线程，有上限预算且预热线程失败时快速降级，属注释明示的有界取舍；极端竞态（预热线程卡在 VFS refresh）下弹窗打开最多阻塞一个预热预算窗。建议：改 `CompletableFuture` 完成回调 + `invokeLater`，消除 sleep-poll 形态。
3. **重放守卫行 0 读取为全文档拷贝**（`SqlLogConsoleBridge.kt:388-397`）：混合态判定需要行 0 文本，现按 stamp 缓存做 `doc.getText()` 全量拷贝后取首行——控制台文档达数十 MB 时单次拷贝可感知，且「尽力而为」缓存无跨线程可见性保证，最坏多算一次。已在 T-PerfSweep F1 把该成本从逐行降到每 stamp 一次，残余风险仅在重放风暴 + 混合态窗口。建议：观察真机即可，若要收敛可改用 `Document.getCharsSequence().lineSequence()` 零拷贝读。
4. （文档微修）plugin.xml:204 的 autoCheckUpdate「默认开」注释与代码默认值漂移（§7）。

上述均不改变「无性能问题」的总结论：1 是增长率受限的内存长尾，2/3 是有界的最坏情形延迟，4 是注释。
