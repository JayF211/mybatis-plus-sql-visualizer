## 1. 总结论

**结论改写：默认配置下插件对 IDEA 的资源型性能影响仍可忽略，但上轮「常驻面零变化、无周期任务、无插件自有线程」的三条红线本轮被 M56 合入打破——插件自有常驻线程 2→4 条、新增一个 5 秒周期巡检、新增一个挂所有控制台的常驻扩展点；空载成本经审读仍属纳秒级，不构成「会带来性能问题」级别的缺陷。** 与此同时，本轮发现了系列六轮以来第一个高危级（交互型）发现点：增强捕获默认开 + 注入确认拒绝不持久化的组合，会让拒绝注入的用户在每次进程启动时挨一次模态弹窗打断。捕捉开启后的常见时序还存在「EP + 桥双路解析」的恒定 ×2 CPU 税（§5.2）。其余发现均为中低/低危有界长尾。

支撑结论的四个增量事实：

1. **常驻面三处扩张，但全部惰性且空载近零**：`consoleFilterProvider` 挂上所有控制台（非捕捉态每行仅一次 volatile 读即返回，`SqlConsoleBridgeFilterProvider.kt:74`）；AgentManager 是项目级惰性服务，首次进程启动/捕捉操作才创建（`RunConfigurationProcessListener.kt:120`、`SqlLogManager.kt:229`），创建后常驻 2 条 daemon 线程 + 每 5 秒一次对空会话表的 filter 扫描（`AgentManager.kt:76`、`:271-278`，纳秒级）；真正付 CPU 的 agent 事件链只在用户同意注入且应用进程运行时存在。
2. **agent 事件消费链的线程模型设计良好**：每会话独立读线程解析（不占 EDT）、`renderParam` 结果经 20 条/200ms 双阈值节流 + 单个幂等 invokeLater 批量进 EDT（`SqlLogEntryBuffer.kt:287-299`、`SqlLogManager.kt:487-498`）、有界 200 条缓冲丢最旧兜背压、落盘走无锁队列 + 专用写线程——没有任何每事件 EDT 同步路径。这套形态在「用户显式同意注入」的前提下是健康的。
3. **上轮六项修复全部在位未退化**：T-PerfSweep2 六修复（extractConsoleError 片段化 `DataSourceSelector.kt:589-597`、响应体 2MB 封顶、批量附件均分、cachedTempPsiFile Disposer 槽 `:3366-3387`、调度器单拍链式、注释对齐）逐一回验原样；预热 EDT sleep-poll 形态亦未变（`SqlPreviewPanel.kt:505-515`）。
4. **上轮五个发现点：1 项已修、4 项仍在（master 口径）**——其中「级别正则每行现场编译」已被 T-AgentDialectLoop 随分桶下沉顺带收敛（正则全部落 `LogThreadRouter` companion，`LogThreadRouter.kt:111`）；「搜索时间匹配 SimpleDateFormat」未修且面扩大到每次搜索 O(全部条目)；WrapperCache、重放守卫、pendingCalls 上界三项原样（§3）。T-PerfSweep3 计划在 **master 未实施**；dev 侧已交付 56aca91（20260917，#2 队列上限 + #3 formatter 缓存落地），随 dev 合流收敛——本报告全部出证以 master ed84f5b 实测为准。

## 4. 新增子系统审计

### 4.1 M56 agent 链路（IDE 侧）

- **线程模型**：两条自建 daemon 单线程池——工作线程 `mps-agent-manager`（attach 串行队列，`AgentManager.kt:66-68`）与巡检线程 `mps-agent-monitor`（`scheduleWithFixedDelay` 5 秒一拍，`:71-76`）；每条 agent 会话另有一条一次性 daemon 读线程 `mps-agent-session-$pid`（`:402-424`）。服务为 `@Service(Service.Level.PROJECT)` + `Disposable`，项目关闭 `dispose()` 里 `shutdownNow` 双池（`:362-370`），messageBus 以 `connect(this)` 挂靠随注销（`:79`）。巡检无会话时每拍只对空表做一次 filter，纳秒级；但服务创建后巡检**无法暂停**（唯一停止点是项目关闭），属常驻面语义变化。
- **attach 触发链与确认闸门**：任意 RunProfile 进程启动都触发 `onProcessAppeared`（`RunConfigurationProcessListener.kt:117-124`，不受 `isModuleBasedLaunch` 门控——该门控只管行号清零）；未确认时走 `requestConsentThenAttach`：invokeLater 到 EDT 弹模态确认框（`AgentManager.kt:121-137`），**同意持久化、拒绝不持久化**（`:130-135` 注释自证「下次运行再询问」）。默认开 + 默认未确认的组合使「拒绝注入的用户」进入每进程一弹的循环（§5.1）。
- **attach 成本**：`Thread.sleep(3000)` 无条件去抖（`:159`，声明的 pendingPids 去抖表 `:64` 从未被使用）+ accept 最长 10s 超时（`:229`），全部排在单线程工作队列上——设置变更任务（shutdownAll/pushDesensitize，`:84-87`）与多个进程的 attach 同线串行，最坏被拖约 13s（功能时效面，不冻结 IDE）。
- **事件流**：读循环解析每事件一次 Gson parse + 逐字段提取（`AgentEvent.kt`）、`toEntry` 参数还原逐字符扫描（`AgentEventAdapter.kt:46-115`）、时间回填走 `logTimeKey` 指纹 + `LogTimeCorrelator.take`（`LogSqlModels.kt:198`）——全部在会话读线程。入队 `SqlLogEntryBuffer.addEntry` 在 `synchronized(entries)` 内做最多 200 条线性去重扫描（`SqlLogEntryBuffer.kt:112-123`、`:197-200`，默认上限 `:302`），与 EDT snapshot() 抢同一把锁——该锁竞争面项目自己在 T-Perf-12 注释里已认知，现状是有界 O(200)，量级可接受。UI 侧经节流 + 幂等 flush 批量进 EDT，无逐条 invokeLater（§1 事实 2）。
- **LogTimeCorrelator**：`object` 单例全局 `@Synchronized`，`LinkedHashMap<键, ArrayDeque>` 容量 512 键 × 单键 ≤8 条、30s 窗口（`LogTimeCorrelator.kt:30/:33/:36`）；桥侧嗅探 put（`SqlLogConsoleBridge.kt:738`）与 agent 线程 take 共享同一把对象锁，接管期两侧高频互斥（临界区均短）。**内存口径与 KDoc 不符**：签名是参数值全文 join（`LogSqlModels.kt:187-188`），单条不限长，大 IN 列表场景 4096 条可达 MB 级，KDoc「数万字节封顶」（`LogTimeCorrelator.kt:29`）失真（§5.5）。
- **杂项**：每次 attach 解压新临时 jar + `deleteOnExit`（`AgentManager.kt:210-220`），文件到 IDE 退出才删且列表随 attach 次数累积；`attachedPids` 项目期只增不减（仅 shutdownAll 清 `:297`）；死代码 `pendingPids`（`:64`）与只写不读的 `lastSeen` 心跳窗口（`:391/:416`，`ONLINE_WINDOW_MS` 未实现）——注释与实现不符，误导后续审计。

### 4.2 捕获通道 EP 化与双轨并存（M56 T-M56-09）

- **EP 常驻面**：`consoleFilterProvider` 无条件注册（`plugin.xml:84-85`），平台对每个 ConsoleView 调一次 `getDefaultFilters`，实例持有独立 `BridgeLineContext`（3 解析器 + 各自路由器，per-console 一次性构造成本）。`applyFilter` 首行是 `if (!manager.capturing) return null`——非捕捉态每行仅一次 volatile 读，这是默认配置下全体控制台的常驻税，可忽略。
- **双轨并存的时序洞（本轮最重要发现）**：设计意图是「EP 首行标志生效后桥轮询挂载停转」，但 EP 首行标志只在 `capturing=true` 后的首行置位（`SqlConsoleBridgeFilterProvider.kt:74-79`），而最常见的「主控制台已存在才点捕捉」时序是 startCapture 先置 `capturing=true` 再 `scanAll` 挂桥 filter（`SqlLogManager.kt:249-253`）——此刻 epActive 必为 false，桥 filter 照挂；`SqlCaptureGate.epActive` 一旦置位也**只挡新挂载、无任何摘除已挂 filter 的逻辑**（`SqlLogConsoleBridge.kt:270-274`，全仓 grep 仅三处引用），桥 handler 内亦无 epActive 短路（`:346-360`）。结果：该时序下每行同时进 EP 与桥双路 `processConsoleLine` + 双 `addEntry`，解析 CPU 恒 ×2，仅靠缓冲去重（默认开，`SqlLogEntryBuffer.kt:49`）保条目不重复——注释宣称的「防双路解析」只对 armed-waiting 时序（捕捉先开、控制台后出现）成立。叠加项：EP 通道无重放守卫（`SqlConsoleBridgeFilterProvider.kt:20-21` 注释自证「降级为直通」），rehighlight 重放风暴时 EP 全量重解析靠去重兜底。另一处重构回退：EP 每行现场读 `PluginSettings...logTimePrefix`（`:80`），桥侧同项早已缓存化（timePrefixCache，`SqlLogConsoleBridge.kt:409-412`）而 EP 未复用。

### 4.3 并发分桶下沉（T-LogParseConc/T-HibConc）

- `LogThreadRouter`（新 221 行）：正则全部预编译（`LogThreadRouter.kt:105/:108/:111`），每行路由 = 整行一次级别关键词 find + 两个 ≤35 字符窗口 substring + 各一次 findAll（`:122-139`），桶上限 64、超限淘汰空闲桶（`:99`、`:86-95`）。无 token 行（MyBatis `==>` 裸行/Hibernate stdout/续行）每行新建 ArrayList 扫最多 64 桶（`:61/:66`）——常数因子级。
- **每行 3× 重复 token 提取**：`processConsoleLine` 把同一行喂给 3 个解析器、各自持有独立路由器（`SqlLogConsoleBridge.kt:693-695`），同一行的 token 提取正则扫三遍——可按行求一次共享，量级低但属白付。
- MyBatis/Hibernate 解析器主体正则全部预编译、分支条件化，新增热路径为 MyBatis 续行每行 `current + "\n" + line` 重建（受 maxParseLength=20000 封顶）；Hibernate 每条裸行过一次 IGNORECASE 锚定 containsMatchIn。无 O(N) 全局扫描回归。

### 4.4 T-UiNative UI 链路

- **渲染热路径**（本轮未新增退化，存量两项最大）：SINGLE_LINE 模式每格重跑 SQL 分词并逐格重建 token→色表（`SqlListFragmentRenderer.kt:52-60` 的 `mapValues`），与每格 new SimpleDateFormat（`SqlLogPanel.kt:1699`）均为上轮既有形态。新增的 SpeedSearch 高亮（6159828）在 meta+SQL 行施加 `applySpeedSearchHighlighting`（`SqlLogPanel.kt:1869-1875`、`HistorySqlLogPanel.kt:788/:793`）——无搜索活动时平台 supply 为 null 即返回，仅打字期间付费，平台惯例形态。
- **列表刷新**：差分增量（头淘汰/插入/尾删）+ 兜底全量重建分批 30 条 + 代际守卫（`SqlLogPanel.kt:1173-1232`），经 manager 置脏 + 单个幂等 flush 合并（`SqlLogManager.kt:482-498`）——流式高频场景无逐条重排。
- **排序选择器**（T-LogSortModes）：排序在 EDT、`sortedBy` 每次比较调 selector（默认 200 条 ≈ 数千次 selector 调用，一次性毫秒内）；其中耗时排序 selector 对无结构化耗时的条目回退 `LogDurationParser.parse` 两次正则全文扫（`SqlLogPanel.kt:1285-1287` → `LogDurationParser.kt:30-53`），桥通道条目命中时点击一次最坏数千次正则扫——EDT 一次性、可接受（§5.6）。
- **剪贴板/颜色**：`UiTextClipboard` 纯平台 CopyPasteManager 写入，无轮询无监听（`UiTextClipboard.kt:19-21`）；CopyFeedback 每次复制一个 1500ms 一次性 Timer（`CopyFeedback.kt:25-33`）；`MpvsUiColors` 全静态 `JBColor.namedColor` 常量、`SqlListTypeColor` 带实例缓存消除同值 repaint——渲染路径无每帧解析。
- **DiagramPanel/Renderer**：布局缓存（T-Perf-24）在位吸收字体度量大头；每帧仍有 `prepareLinesFor` 列表重建、`byIdx` map 重建、每卡片 `BasicStroke` 新建等小分配（`DiagramRenderer.kt:280-289/:323/:368/:583-666`），规模随实体×关系线性，余量低。

### 4.5 执行链（T-ExecDocSync 与既有修复回验）

## 5. 发现点与建议（1 高 + 2 中 + 3 中低 + 4 低，按优先级）

> 建议随第六轮性能 sweep 立项收敛（沿用 T-PerfSweep 代号惯例，建议代号 T-PerfSweep4，任务编号 T-PS4-01~07；其中 T-PS4-06/07 为 T-PerfSweep3 未实施项的并账）。本轮按用户指令仅交付本报告，计划文件待立项指令。

1. **【高·交互打断（非资源型）】增强捕获确认拒绝后，每个进程启动都重复弹一次模态确认框**（`AgentManager.kt:130-135`、`:121-137`；触发面 `RunConfigurationProcessListener.kt:117-124`）：默认配置 enabled=true + confirmed=false，用户在首次弹窗点「取消」后拒绝态不持久化，且 attach 触发不区分主配置（HTTP Client 请求/profiler/测试进程均走 processStarted）——拒绝注入的用户日常开发中每次发请求、每次跑测试都被一次 EDT 模态 DialogWrapper 打断，直到他自行去设置页关闭增强捕获为止。属交互冻结类而非 CPU/内存风险，但它是默认配置可达路径、六轮以来首次出现「高」级发现。建议：拒绝同样持久化（记忆「已拒绝」，设置页可改），或对未确认弹窗加会话级冷却/仅主配置触发——任选其一即可封死。
2. **【中】捕捉开启 × 控制台已存的常见时序下，EP 与桥双路解析恒 ×2**（`SqlLogConsoleBridgeFilterProvider.kt:74-81` + `SqlLogManager.kt:249-253` + `SqlLogConsoleBridge.kt:270-274`/`:346-360`）：epActive 只挡新挂载、不摘除已挂 filter，主控制台已存在的主流时序必然落入双轨，每行两次全流水线解析 + 两次入队指纹计算，靠去重保条目不重；EP 通道还缺重放守卫与 timePrefix 缓存（`:80`）。建议：桥 handler 增加 epActive 短路（一处判空即可），同时 EP 接 timePrefixCache。
3. **【中低】attach 不筛进程类型 + 无条件 3s sleep 串行垄断工作线程**（`RunConfigurationProcessListener.kt:117-124`、`AgentManager.kt:159`、`:229`）：任何 RunProfile 进程都进 attach 队列，每项占 3s sleep + 最长 10s accept；设置变更任务同线排队最坏延迟约 13s；声明的 pendingPids 去抖表（`:64`）从未使用，注释与实现不符。建议：pendingPids 落地去抖，或按 handler 类型/主配置门控触发面。
4. **【中低】agent 事件链现场编译正则**（`AgentEventAdapter.kt:120-125` 每参数两处、`LogSqlModels.kt:167` 每键一次）：违背本项目 T-PerfSweep F2「正则提常量」惯例（同文件 companion 九条均已提常量，唯这两处漏网），发生在会话读线程/去重键 lazy 路径，高吞吐下 GC churn。建议：提 companion 常量，两处各一行。
5. **【中低】LogTimeCorrelator 签名字符串无字节上界 + 全局单锁跨线程共享**（`LogSqlModels.kt:187-188`、`LogTimeCorrelator.kt:29`/`:55-116`）：4096 条容量 × 参数值全文 join 的签名，大 IN 列表场景实际驻留可超 KDoc 宣称的「数万字节」达 MB 级；桥嗅探线程与 agent 会话线程共享同一把对象锁（临界区均短，接管期高频互斥）。建议：签名截断（如 256 字符）+ KDoc 量级口径修正。
6. **【中低·连续两轮在册】搜索按时间匹配逐条目新建 SimpleDateFormat，且触达面扩大**（`SqlLogPanel.kt:1699/:1701`、`filterBySearch :187`、`HistorySqlLogPanel.kt:448`）：T-LogSearchRowTime 的按时间匹配把该成本从「渲染可见行」放大为「每次防抖搜索 O(全部条目)」——默认 200 条毫秒内，logMaxCount 配大后线性放大。建议：formatter 面板级复用（EDT 单线程可安全复用）或条目缓存。
7. **【低·连续四轮在册】WrapperCache 无自动淘汰**（`psi/WrapperCache.kt:41`）：ConcurrentHashMap 无上限无失效，长会话缓慢增长；单项有界但四轮未清账。建议：容量上限 + LRU，或按项目挂 Disposer。
8. **【低·连续四轮在册，口径修正】重放守卫混合态 × stamp 变化全文档拷贝**（`SqlLogConsoleBridge.kt:393-406`、拷贝点 `:400`）：惰性 provider + stamp 缓存已把成本限定为「混合态且文档 stamp 变化」时一次 O(全史) 拷贝取首行（上轮报告描述为每次 stamp 变化，偏宽）。建议照 T-PerfSweep2-01 手法改 `getCharsSequence` 首行片段。
9. **【低】T-PerfSweep3 余项未实施并账（master 口径）**：防抖队列条数无上界（`IdeErrorReportSubmitter.kt:73`/`:111-118`）；重放守卫全文档拷贝（即第 8 条）。dev 侧 56aca91 已修 #2/#3 且声称 #1/#4/#5 前置收口——合流后须以本报告 master 实测为底账逐项复核，防「已修」口径与 master 现状错位（#4 重放守卫拷贝点 `:400` 在 master e7787ca 之后仍未变）。
10. **【低】attach 临时 jar deleteOnExit 累积 + attachedPids 项目期残留**（`AgentManager.kt:210-220`、`:297`）：临时文件到 IDE 退出才删、条目随 attach 次数累积；pid 表项目期只增不减。量级均小，随 T-PerfSweep4 顺手清。

上述均不动摇总结论：第 1 条是交互面且一行可封，第 2 条只在捕捉开启时存在且有单路时序可对照，3~10 为有界长尾。
