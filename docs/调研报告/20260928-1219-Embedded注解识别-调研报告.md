# @Embedded 注解识别调研报告

**创建时间**：2026-09-28 12:19
**问题来源**：用户反馈「目前插件不能正常识别 @Embedded 注解」，要求调研该注解的用法与插件正确识别方案（官方文档 / 官方仓库 / 本地反编译依赖三路交叉）。
**调研方法**：本地 jar 清单实证（MyBatis-Plus 3.5.17 注解包、jakarta.persistence-api 2.2.3 sources）+ Spring Data JDBC 官方文档 + 插件源码逐文件实读 + 仓内测试覆盖盘点。

---

## 一、结论先行

**@Embedded 不是 MyBatis-Plus 的注解。** 本地 `mybatis-plus-annotation-3.5.17.jar`（正是本项目测试基线版本，`build.gradle.kts:98`）全部注解类清单为 15 个：`TableName / TableField / TableId / TableLogic / Version / KeySequence / OrderBy / SqlCondition / IEnum / DbType / FieldFill / FieldStrategy / EnumValue / IdType / InterceptorIgnore`，没有任何 Embedded。网络检索同样未发现 MP 官方支持该注解的任何资料，MP 官方 issue 区对嵌套对象映射长期维持「不内置、用 resultMap/association 或 typeHandler 自行解决」的立场。

`@Embedded` 实际属于两族框架，语义高度相似但细节不同：

| 注解 | 全限定名 | 归属 | 嵌入语义 |
|---|---|---|---|
| `@Embedded` | `jakarta.persistence.Embedded`（旧栈 `javax.persistence`，语义同） | JPA 规范（Hibernate 实现） | 嵌入对象字段展平落宿主表，无隐式前缀 |
| `@Embedded` | `org.springframework.data.relational.core.mapping.Embedded` | Spring Data JDBC | 同上，另有显式 `prefix` 属性 |
| `@EmbeddedId` | `jakarta.persistence.EmbeddedId` | JPA 规范 | 嵌入对象整体作复合主键 |
| `@Embedded.Nullable` / `@Embedded.Empty` | 同上包 | Spring Data JDBC 捷径注解 | 等价 `@Embedded(onEmpty=…)`，列映射语义与裸 `@Embedded` 相同 |
| `@Embeddable` | `jakarta.persistence.Embeddable` | JPA 规范 | 类级标记，标注它的类型即使字段没写 `@Embedded` 也按嵌入语义 |

（Android Room 也有 `@Embedded`，属移动端场景，超出本插件 Java/Kotlin 后端 ORM 范围，仅在命名撞车时需留意。）

**插件现状**：JPA 路径其实已经有一套完整的 `@Embedded` 识别与展平实现（T-J18，含测试），基础场景是工作的。「不能正常识别」的真实缺口在四个面上——Spring Data 专属形态、JPA 规范要求的嵌套点路径覆写、MP 路径完全没有嵌入概念、以及一个已登记的嵌套路径降级边界。详见 §三。

## 二、官方语义（三路交叉核实）

### 2.1 JPA（jakarta / javax persistence，规范原文）

来源：`~/.m2/repository/jakarta/persistence/jakarta.persistence-api/2.2.3/jakarta.persistence-api-2.2.3-sources.jar`（`javax.persistence.Embedded` 源码注释，jakarta 3.x 语义不变；3.1.0 二进制 jar 亦在本地核验）。

要点摘录：

1. **展平语义**：`@Embedded` 标注的持久化字段，其值是 embeddable 类的实例；嵌入对象没有自己的表，其内部字段直接映射为**宿主表的列**。`@Embeddable` 类的字段即使无注解也参与映射（`@Transient` 除外）。
2. **覆写机制**：`@AttributeOverride` / `@AttributeOverrides` 可覆写嵌入类内部字段的列名（repeatable 双形态）。规范明确**覆写的生效层级**：可放在实体类级（针对 @MappedSuperclass 继承或嵌入字段），也可放在嵌入字段上。
3. **嵌套点路径（规范强制形态）**：`AttributeOverride` javadoc 原文——「To override mappings at multiple levels of embedding, a dot (".") notation form must be used in the `name` element to indicate an attribute within an embedded attribute.」规范例 2：

   ```java
   @Embeddable public class Address {
       protected String street;
       protected String city;
       protected String state;
       @Embedded protected Zipcode zipcode;      // 嵌套嵌入
   }
   @Embeddable public class Zipcode {
       protected String zip;
       protected String plusFour;
   }
   @Entity public class Customer {
       @AttributeOverrides({
           @AttributeOverride(name="state",       column=@Column(name="ADDR_STATE")),
           @AttributeOverride(name="zipcode.zip", column=@Column(name="ADDR_ZIP"))  // 点路径
       })
       @Embedded protected Address address;
   }
   ```

   即：覆写嵌套嵌入对象的深层属性时，`name` **必须**写成 `外层字段.内层字段` 的点路径。这是规范要求的唯一写法，不是冷门变体。
4. **Map 元素集合**：`@AttributeOverride` 作用于 Map 时用 `key.` / `value.` 前缀。
5. **无隐式前缀**：JPA 对嵌入列**不加任何隐式前缀**，列名来自嵌入类内部字段的 `@Column` 或隐式命名策略（Hibernate 物理命名策略——Spring Boot 默认驼峰转下划线——对展平列同样生效）。
6. **@EmbeddedId**：嵌入对象整体作主键，内部全部字段列均为主键列，可配合 `@MapsId` 与关联共享主键。

### 2.2 Spring Data JDBC（官方文档）

来源：docs.spring.io《Spring Data JDBC — Mapping》。

要点摘录：

1. 标注 `@Embedded` 的属性「will be mapped to the table of the parent entity, instead of a separate table」——同样是落宿主表。
2. **无隐式前缀**；**显式前缀 opt-in**：「If you need a value object multiple times in an entity, this can be achieved with the optional `prefix` element of the `@Embedded` annotation. This element represents a prefix and is prepended to each column name in the embedded object.」——`prefix` 是同一值对象多次嵌入时的防撞车手段，前缀拼在**每一列**之前。
3. 捷径注解：`@Embedded.Nullable` 与 `@Embedded.Empty` 等价 `@Embedded(onEmpty = USE_NULL / USE_EMPTY)`，是**组合注解**（元注解形态），列映射语义与裸 `@Embedded` 完全一致。
4. `onEmpty`（USE_NULL/USE_EMPTY）只影响「整行列全 NULL 时对象实例化成 null 还是空对象」，属于**读回侧行为，不影响 SQL 文本渲染**，插件无需处理。
5. 没有 `@Embedded` 的嵌套对象引用被视作一对一关联（独立表 + 外键回引列），**不展平**。
6. `@Embedded` 可与 `@Id` 组合形成复合主键。

### 2.3 MyBatis-Plus（官方立场）

1. 本地 jar 全清单无 `@Embedded`（§一已述）——插件测试基线 3.5.17 为准。
2. MP 对实体字段的处理是平铺的：非 static 非 transient 字段默认映射为列，对象类型字段也不会展平（实际项目用 `@TableField(exist = false)` 标记非表字段，或用 typeHandler / resultMap association 处理嵌套结构）。**MP 运行时不存在「嵌入展平」概念**。
3. 含义：写 `@Embedded` 的实体在纯 MP 项目里运行时并不会得到展平行为（MP 会把该字段当普通列 `update_info` 生成 SQL，运行期报错或需 typeHandler）。真实世界里 `@Embedded` 出现在**混合注解实体**上——同一实体同时被 MP 与 JPA/Spring Data 体系使用（老项目 JPA 转 MP、双栈并存、代码生成器产物都是常见形态），此时真实数据库里的列就是展平列。

### 2.4 其他受支持 ORM

Easy-Query 与 xbatis 均无 `@Embedded` 类注解（Easy-Query 的对象→列映射走计算属性/JSON 机制；xbatis 检索不到任何嵌入注解资料）。插件的 `JpaMetadataReader` 对这两个框架的注解常量（EQ8/EQ9/XB 系列）不涉及嵌入。

## 三、插件现状（逐文件实证）

### 3.1 架构：双解析器 + 多 ORM 注解矩阵

- **MP 路径** `psi/EntityResolver.kt`：只读 MP 注解（`@TableName/@TableField/@TableId/@TableLogic/@Version/@KeySequence`），逐字段映射单列。消费方：Wrapper 渲染（`WrapperLocator`）、批量操作（`BatchOperationConverter`）、CRUD 生成（`GenerateCrudSqlFromEntityAction:124`）、实体反查（`EntityClassFinder:37`）、参数解析（`ArgResolver:349`）。
- **JPA 路径** `psi/jpa/JpaEntityResolver.kt` + `psi/jpa/JpaMetadataReader.kt`：覆盖 JPA（jakarta/javax 双包名 + 短名兜底的三轨匹配，`JpaMetadataReader.kt:147-154`）、Hibernate、Spring Data（SD8/SD10）、Easy-Query（EQ8/EQ9）、xbatis（XB 系列）六族注解。消费方：JPQL/HQL/Criteria/Querydsl/EasyQuery 转换器、Spring Data 派生方法与 Specification、Repository gutter。
- **路由**：MP Wrapper 链几乎全走 `EntityResolver`，唯一例外是 xbatis 实体（`WrapperLocator.kt:1287-1291` 显式按 `cn.xbatis.db.annotations.Table` 分流到 `JpaEntityResolver`）。
- **模型**：`model/TableInfo.kt:149-169` 已有 `embedded`（列是否展平自嵌入对象）与 `embeddedParent`（展平列的宿主嵌入字段名）两个字段，T-J18 引入，双路径共用。

### 3.2 JPA 路径已覆盖面（T-J18，已实施）

- `@Embedded / @Embeddable / @EmbeddedId` 识别（`JpaMetadataReader.kt:567-573`，字段标注或字段类型类标注 `@Embeddable` 均命中）。
- 展平：`@AttributeOverride` 覆写 → 内部字段 `@Column` → 驼峰转下划线（`JpaMetadataReader.kt:632-668`）；嵌套 `@Embedded` 递归展平（`:649-653`）；类级 + 字段级覆写合并（`JpaEntityResolver.kt:293-294`）；`@EmbeddedId` 展平列全标主键并进 `compositeIdColumns`。
- 降级：嵌入类型不可解析时回退单列形态，不丢字段（`JpaEntityResolver.kt:297-299`）。
- HQL/JPQL 消费链：属性路径中嵌入段的剥离已实施（`JpaAliasTableResolver.kt:267-273`，`pickTicket.updateInfo.createdTime` → `pickTicket.created_time`）；无别名 HQL 下嵌入段占限定符位的剥离也已实施（O-71 T-02，`:261-266`）。
- 测试：`JpaEntityResolverMappingDeepTest.kt:122`（展平 + @AttributeOverride）、`:161`（@EmbeddedId 复合主键）等，全仓 16 处 `Embedded` 相关断言分布在 4 个测试文件。

### 3.3 缺口（按影响排序）

**G1 Spring Data 专属形态识别不全（SD 常量声明即弃用）**

`JpaMetadataReader.kt:93` 的 `FQN_RELATIONAL_EMBEDDED` 全仓只有声明、零使用。实际行为由 `findFlex` 的**短名兜底轨**决定（`JpaMetadataReader.kt:147-154` 第三轨按 `referenceName` 匹配），由此产生三种命运：

| SD 写法 | PSI 短名 | 现状 | 后果 |
|---|---|---|---|
| `@Embedded`（裸） | `Embedded` | 被 jakarta 轨**误打误撞命中**，按 JPA 语义展平 | 基础场景「碰巧正确」，但 `prefix` 丢失，且无任何测试钉住这个行为 |
| `@Embedded.Nullable` / `@Embedded.Empty` | `Nullable` / `Empty` | **不命中** | 落入普通字段分支，产出 `update_info` 这类**伪单列**（SD 值对象类通常不带 jakarta `@Embeddable`，也不会被 `isNestedEntityOrEntityCollectionField` 拦截） |
| `@Embedded(prefix = "addr_")` | `Embedded` | 命中但前缀被丢弃 | 双嵌入同一值对象时列名撞车 / 列名错，SQL 报 unknown column |

**G2 JPA 嵌套点路径 `@AttributeOverride` 不命中**

覆写键查找只有裸字段名一条路（`JpaMetadataReader.kt:659` `overrides[fieldName]`；嵌套递归时传给下层的覆写清单取自该字段自身的注解且键仍是裸名，`:652`）。规范要求的 `name="zipcode.zip"` 点路径形态（§2.1 第 3 条）无法命中，覆写静默丢失、列名错。类级覆写清单（`JpaEntityResolver.kt:293` 的 `classOverrides`）虽保留原始 name（含点路径），但展平循环同样只按裸名查。

**G3 MP 路径完全没有嵌入概念**

`EntityResolver.kt:139-186` 逐字段单列映射，无任何嵌入分支。混合注解实体（`@TableName` + `@Embedded` 共存）在 Wrapper 预览 / 批量模板 / CRUD 生成里，嵌入对象字段按普通字段产出伪列 `update_info`；`ColumnNameCalibrator` 只做列名校正（`ColumnNameCalibrator.kt:66-76`），既不会展平也不会剔除该伪列。这里存在一个语义抉择：MP 运行时本身不展平（§2.3），插件 MP 路径「跟 MP 运行时」还是「跟真实数据库」——推荐跟真实数据库（与 O-58 校正层的哲学一致：插件目标是产出可执行的 SQL），展平方案见开发计划 D3。

**G4 已知降级边界：嵌套展平列的 fieldName 非完整路径**

`EmbeddedColumnSpec.fieldName` 记录的是最内层字段名（`JpaMetadataReader.kt:612` 自注「非完整路径——嵌套路径为已知降级边界」），`embeddedParent` 只记最外层字段名，HQL 剥离判据也只认首个段（`JpaAliasTableResolver.kt:315-329`）。当前 HQL/JPQL 链已按此闭环，反查（`columnByField` 按内名命中）在常用形态下可用；改为完整路径会牵动既有剥离判据与 16 处测试断言，收益低回归面大，**维持登记不改**。

### 3.4 消费链影响面汇总
