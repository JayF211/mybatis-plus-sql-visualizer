### R60 展示/导出链字面量脱敏（采集侧能力向用户可见面延伸）

- 痛点：SQL 日志/预览/导出里的字面量参数是真实生产数据（手机号/身份证/业务值），用户截图发群、导出 CSV、复制给同事时裸奔；而采集侧其实**已有完整脱敏能力**——agent 侧 `Desensitizer.java:10-30`（敏感关键词+证件/手机号形态双条件，数据不出应用 JVM）+开关 `enhancedCaptureDesensitize`（PluginSettings.kt:494-496，默认关），只是它只护 agent 通道落库前的值，**预览渲染、日志面板、PortableSqlExport/SqlExportService 导出、MCP render_logs 输出四条链路全无脱敏**。
- 形态：主仓侧新增等价 DisplayMasker（agent 是独立源集不能直接引用，规则对齐双条件形态），预览/日志/导出三链统一挂接；设置页单一开关（默认关，与采集开关解耦）；MCP render_logs 是否参与脱敏单独选项（脱敏会降低 AI 诊断价值，默认不脱并在工具描述里声明）。
- 规模 S-M；竞品零对位（推断：DBX/zMyBatis 均无展示侧脱敏）。
- 前提 V112：①Desensitizer 双条件规则的精确语义（关键词表+形态正则）读源码落档，主仓实现与之逐条对齐；②导出链挂点选择（SqlExportService 单点 vs 各 Action 散点）；③脱敏态与原始态的切换交互（面板刷新链路是否已有现成重绘入口）。

### R61 EXPLAIN 执行计划跨次对比（数据底座 dev 已现成）

- 痛点：「加了索引到底有没有变好」「改写 SQL 前后计划差在哪」——现在只能把两次 EXPLAIN 输出并排肉眼比对；全仓 `planDiff|comparePlan` 零命中，两树完全缺失。dev 的 ExplainJsonPlanTree+ExplainPanelChannel（R33 结构化渲染）已把计划变成结构化数据，是五个探查方向里底座最好的一个。
- 形态：EXPLAIN 视图加「与历史对比」动作——选同结构 SQL 的两次 EXPLAIN 结果，树节点对齐 diff（新增/消失节点+cost/rows 变化标注），复用 dev 已有 SqlDiffer 的 UI 形态（IDEA 原生 Diff 外壳）。依赖 R33 回流（master 无 JSON 树），故立项即绑定回流批。
- 规模 M；竞品零对位（推断：DBX EXPLAIN 链无 diff；Database Tools 有计划查看无跨次对比）。
- 前提 V113：①ExplainJsonPlanTree 节点是否有稳定标识可做对齐键（无则先补 id 生成）；②EXPLAIN 结果是否落盘历史（ExplainPanelChannel 生命周期是会话级还是持久）；③Oracle DBMS_XPLAN 文本格式与 MySQL JSON 的统一建模成本（R23 二段式产物形态核对）。

### R62 更新失败可诊断化（通道死亡第三轮的用户侧兜底）
