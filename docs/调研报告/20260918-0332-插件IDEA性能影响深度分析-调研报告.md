## 1. 总结论

**结论改写：默认配置下插件对 IDEA 的资源型性能影响仍可忽略，且本轮交付了系列七轮以来最大一批性能正向收益（预览链 2 秒阻塞消除、历史打开防卡顿）；但资源面新增两条常驻（应用级文档监听 + 防抖调度线程，插件自有常驻线程 4→5），上轮唯一的「高」级交互发现在册未修。本轮新增两条「中」级发现：一条在用户应用 JVM——增强捕获通道每条 SQL 现在付两次全栈捕获，且 fat jar 部署下缓存防合流设计退化为每执行全栈重扫；一条是历史保留上限裁剪的数据安全面——自定义保存目录下用户自有 .sql 文件会被整组静默删除（非性能，审计顺带发现）。** 其余均为中低/低危有界长尾，不动摇总结论。

支撑结论的五个增量事实：

1. **两大正向交付机制属实**：P1 差量快路径命中即返回，不派发不落盘不等 EDT（`DataSourceSelector.kt:3400-3406`，注释自证真机五连预览每次白付 2s）；P2 预热 fire-and-forget，BGT 不再白等 2000ms（`:3160-3162`、接线 `:3411-3414`）；历史读回整读改流式（`SqlLogFileReader.kt:59-63`，滚动阈值 100MB 下内存峰值从文件体量降到单块）+ 历史列表首屏 30 条分批填充（`HistorySqlLogPanel.kt:461-485`）。
2. **常驻面再扩张一条监听一条线程，空载成本仍低**：F5 防抖自动落盘在 `EditorFactory.eventMulticaster` 上装了**应用级 DocumentListener，无 Disposable、装后永不卸载**（`DataSourceSelector.kt:3266-3274`）——此后 IDE 全部编辑器每次文档变更都进一次「volatile 读 + getFile + 路径后缀判定」过滤（`:3279-3283`），纳秒~微秒级；配套新增常驻 daemon 调度线程 `mpv-exec-doc-autosave`（`:3244-3247`），插件自有 Executors 4→5。
3. **上轮十个发现点零修复，全部在册**（§3.1）：T-PerfSweep4 计划（T-PS4-01~08）已立项未实施（`git log -S "T-PS4"` 在 src/main 零命中）；dev 侧 T-PerfSweep3 修复（6bcf1fd）仍未合流。
4. **agent 应用侧栈捕获成本翻倍且缓存设计在 fat jar 下失效**：`StatementHandler.java:124/:137` 每条 SQL 在执行线程 finally 里无条件做两次全栈捕获（locate + StackDigest.build，类头注释 `:18`「只在 execute 取一次」已失真）；`StackLocator.java:186-191` 仅 L1（目录来源）命中才写缓存——全 JAR 来源（fat jar 部署常态）时每条 SQL 重扫全 pool 并逐帧 Class.forName（`:135-143`、`:255`），`:183-185` KDoc「重算频率上界=调用方种类数」论证不成立。
5. **历史保留裁剪的删除面过宽（数据安全）**：`SqlLogAutoSaver.kt:110-124` 对保存目录下**全部** .sql 文件按基名归组、超限（默认 30 组，`PluginSettings.kt:489`）删最旧整组，不做文件名模式过滤——自定义目录（`:171-172` 用户任意路径直用）下用户自有 SQL 脚本可被静默删除；默认目录插件独占不受影响。

## 4. 新增子系统审计

### 4.1 预览/执行链（T-PreviewFast 批次为主体）

- **性能正向四件全部机制属实**：① P1 差量快路径（`DataSourceSelector.kt:3400-3406`）——`execFileContentMatches` 命中即返回，连续同 SQL 预览跳过 EDT 派发/落盘/latch 等待，判据双源（document 文本或 vf 内容）；② P2 fire-and-forget（`:3160-3162`、`:3411-3414`）——预热调用 `waitBudgetMs=0`，BGT 派发后立即返回，超时自愈语义保留给非预热路径（`EDT_EXEC_DOC_SYNC_WAIT_MS = 2000L` `:3152`）；③ P5 落盘去重（`:3141-3146`）——`isDocumentUnsaved` 为假跳过磁盘写，消除无效落盘与 VFS/索引噪音；④ P6 渲染缓存（`SqlPreviewPanel.kt:1480-1486`）——单槽命中直返，吸收挂载回填与参数重渲染的重复 SqlFormatter。T-ExecDocSync3 裸写兜底退役（`:3420-3436`）消灭 File Cache Conflict 模态弹窗及其 invokeLater 链冻结（历史执行卡死放大器），同属正向。
- **【中低】F5 应用级监听裸装不卸载**（`DataSourceSelector.kt:3266-3274`）：`eventMulticaster.addDocumentListener` 用单参重载、无 Disposable，装后永不移除；IDE 全局每次键击/文档变更进 `scheduleExecDocAutosave`——`:3279` 闸门 volatile 读 → `:3280-3283` `FileDocumentManager.getFile` + 路径 endsWith。单项纳秒级但恒驻全程，且命中后仍全量走 getFile+path（可先比对缓存的 document 身份）。这是全局红线「应用级事件监听」族的第一条。
- **【中低】showSql 写点 P4 开闸前提不成立**（`SqlPreviewPanel.kt:1737-1748`）：nativeDoc 分支 `WriteCommandAction { setText }` 自身**无任何落盘动作**，注释「内容刚由本写入落盘」在该调用点未被证实——闸门开掉的是 F5 兜底防抖落盘，formatted 文本滞留 modified-unsaved 直到 IDE 帧保存或下一次 writeVfTextViaDocument。对照 `:3126-3148`：闸门在该处成立是因为同临界区落盘（`:3143-3146`）。正是 T-ExecDocSync2 要消灭的暴露面形态在该分支重新开了一扇小窗（执行一致性面，非性能）。
- **【低】EDT 冷路径新增同步磁盘读**：F4 pre-refresh 收敛在 ReadAction 内 `vf.inputStream.readBytes()` 整读（`:3219-3227`）；P1 无 document 分支同样整读且持 `execFileWriteLock`（`:3397`、`:3555`）；收敛探针成对重复（`:3023-3043`、`:3590-3609`）——单条 SQL 文件、冷路径低频，量级可接受。
- **【低】T-ConsoleDbContext 成本面干净**：`ExecConsoleContext.kt:37-45` 一致即 no-op、失败 runCatching 纯状态回退；每 console 准备/复用至多一次（调用点 `DataSourceSelector.kt:406`、`:1372`）。`switchSchema` 内部是否触发同步 DB 元数据往返未确认（注释仅字节码级断言），留一次 javap 复核。
- **【低】P6 缓存 key 命中路径也做 O(全 SQL) 拼接**（`SqlPreviewPanel.kt:1484`）——远轻于 SqlFormatter 本身，大 SQL 可先比短字段。
- **JOIN 图（低/正向）**：兜底 fit 是有界一次性 Timer（`NativeJoinDiagramSupport.kt:90-93`，`isRepeats=false`、上限 2 次）；enableAutoFit 前移到异步布局触发之前（`NativeJoinDiagramOpener.kt:77`），消除首图不居中的重试布局往返。
- **【低】虚拟外键注册表残留不累积**：dispose 不清注册表是 T-EmbedFkOrder 有意设计（`NativeDatabaseDiagramSupport.kt:99-112` 注释自证真机连线丢失根因），清理=登记前 clear（`:122`）+ 无 JOIN 路径显式回收；但面板 `dispose()`（`SqlPreviewPanel.kt:3019-3036`）未调 `clearRegisteredFk`，最后一张图的条目驻留到下次建图——量级为表名列名字符串，且残留期间 `JoinVirtualFkProvider` EP 可能给用户自开的 Database 图补出旧连线（语义残留）。

### 4.2 SQL 历史全量落盘链（T-SqlHistoryFull / T-HistoryFileRetention）

- **写链形态健康（正向）**：全量化后每条成功入队一次无锁队列投递（`SqlLogEntryBuffer.kt:144` 出口 + `SqlLogManager.kt:454` 接线，风暴期 N 条合并为 1 个写任务），磁盘 IO 全在专用写线程 `mpsv-sql-history-autosave`（`SqlLogAutoSaver.kt:62-76`），CAS 单飞调度 + 整批一次 flush（`:85-98`）；`@Synchronized` 修掉 dispose 与风暴写并发的既有丢条缺陷（2 万丢 9 千→两序不丢，`:78-83` 注释自证压测）。捕获热路径零新增同步成本，无 EDT。
- **【中·数据安全（非性能）】裁剪删除面过宽**：`pruneRetainedFiles`（`:105-125`）对保存目录**全部** .sql 文件按基名归组（`:110-113`，无文件名模式过滤），组数超 maxFiles（默认 30，`PluginSettings.kt:489`）时按组内最新时间戳删最旧**整组**（`:116-124`，`runCatching { f.delete() }`）。默认目录插件独占（`.idea/sql-visualizer/...` `:174`）不受影响；自定义目录用户任意路径直用（`:171-172`），目录下自有 SQL 脚本可被静默删除。修法一行：基名前缀过滤只认本插件命名模式。
- **【低】裁剪无节流**：每非空写批后执行一次全目录 listFiles + 全文件 stat + 排序（`:93-97`、`:110-116`），风暴期批次密集时重复扫同一目录；后台线程 + `@Synchronized` 串行，不卡 UI，量级随目录文件数线性。
- **【低】close 在调用线程同步排水**：设置变更链 `SqlLogManager.kt:448` → `configure`（`SqlLogAutoSaver.kt:160-168`）→ `close`（`:341-349`）→ `drainPendingSync` 同步写批（`:144-151`），调用线程常为 EDT——风暴在途积压大时 EDT 承担一批磁盘写。既有模式被全量写放大，边界场景。
- **读回侧（正向为主）**：`SqlLogFileReader.kt:59-63` 整读改流式（useLines，峰值≈单条 SQL）；历史列表分批填充 + 代际守卫（`HistorySqlLogPanel.kt:461-485`，首屏 30 条立即写、每 30 条 invokeLater 追加、`:475` 代际终止）——「历史打开防卡顿」交付兑现，EDT 只付首屏成本。残留两个低项：parseBlock 每条两个 SimpleDateFormat（`SqlLogFileReader.kt:259/:263`，全程后台线程）；历史搜索防抖后单次 O(全部条目) 且逐条目含 timestampDisplayText（`:448`，EDT，见 §3.1 行 6）。

## 5. 发现点与建议（2 中 + 2 中低 + 6 低，按优先级）

1. **【中·应用侧】增强捕获每条 SQL 两次全栈捕获 + fat jar 下缓存永不命中每执行全量重扫**（`StatementHandler.java:124`/`:137`、`StackLocator.java:109-125`/`:135-143`/`:186-191`/`:255`）：成本落在用户应用 SQL 执行线程，高频 SQL 应用上表现为执行延迟与 CPU 占用双升。建议三件组合：① digest 复用 locate 已取的栈（一次捕获两用）；② 缓存查询前移到 key 算出处；③ fat jar 场景允许 SAFETY 结果按「key + via 标记」入缓存（合流风险用候选列兜底）或给安全网重算加 N 次退避。顺带修正 `:18` 与 `:183-185` 两处失真注释。
2. **【中·数据安全（非性能）】历史保留裁剪对自定义目录全量 .sql 整组删**（`SqlLogAutoSaver.kt:110-124`、目录 `:171-172`、上限默认 30 `PluginSettings.kt:489`）：用户把保存目录指到自有 SQL 脚本聚集处即触发误删，且 `runCatching { delete() }` 静默。建议：归组前按本插件文件名模式（`sql-history-*` / 用户模板渲染结果）过滤，非匹配文件不计数不删除。
