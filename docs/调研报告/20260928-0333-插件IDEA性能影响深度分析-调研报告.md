## 1. 总结论

**结论维持：默认配置下插件对 IDEA 的资源型性能影响可忽略；master 当前发布基线与上轮逐字节一致（零漂移）。** 本轮最有价值的发现不在风险侧而在改善侧：dev 批次 1 把本系列前两轮点名的四个实质热路径敞口全部修掉——F18（gutter 大 CDATA 每 pass 全文正则剥包裹 → O(128 字符窗口)）、F19（gutter 每候选 token 两次设置服务查找 → 一次）、F30（agent「祖先浅帧+更深段全 JAR」形态每事件 at 次 `Class.forName` → per-class 记忆化负缓存）、T-PerfSweep8 4a（ACP 通道每次分发重付 SSE 反射 → volatile 单次缓存），修复形态逐件审计全部干净：无新增线程/Timer/Executors/正则，新驻留状态全部有界（ORIGIN_MEMO ≤512、双台账各 ≤10、SSE 缓存 1 引用），且 String 键不持有 loader 引用、无类加载器泄漏面。本轮新开发现点仅 **F35 一条（微·登记）**；无中高级。

支撑结论的五个事实：

1. **master 零漂移是字节级证明而非抽查**：`git diff cb0ac14..master -- src/main sub-projects` = 0 行，上轮全部红线读数与 F18~F34 锚点数学承袭；红线十三族仍独立重跑了一遍，16 族读数全部与上轮吻合（§3.1，含两处锚行/文件名口径订正）。
2. **dev 批次 1 的 11 个生产文件 diff 逐 hunk 深读**（三路只读子代理本轮未派——增量面 +177 行生产码，主控直读比转述可靠），五件修复的实现与计划回填声明（b97c38b §7.1）逐件对得上，唯一例外是「发现 1/2/3 清零」中**发现 2 的成本面未被触碰**（`McpGateFilterEpBridge.kt` 在 master..dev 零 diff），按代码实况维持 F34② 登记（§3.2 口径注）。
3. **F18/F19 修在平台热路径上**：`getLineMarkerInfo` 对每个 `XML_NAME` token 都会跑，F19 把每 token 两次 `PluginSettings.getInstance()` 砍半；F18 把「自研框架载体几十~几百 KB 大 CDATA 段每高亮 pass 一次全文 unwrapCdata 正则 + 全文 trim」改为前缀窗口扫描，窗口硬上界 128 字符（PREFIX_PROBE_LENGTH 64 + 64 slack）——这是本系列挂账三轮的唯一实质敞口（F18）的落地修复。
4. **F30 修在 agent 每 SQL 事件热路径上**：`ORIGIN_MEMO`（`StackLocator.java:120`）以「loader 身份哈希 + 类名」为键、`Optional` 承载 null 负缓存，负缓存使失败查找也不再重付；健康路径（at==0 直取、名单帧命中）仍零新增分配。
5. **批次内顺手触碰的另外两文件均非性能面**：O-76 全角括号同栈计数是每字符两次常量比较的常数因子（切分器跑在有界 SQL 文本上）；R22 T-01 键扩展把无表名 SQL 的历史参数从「不缓存」改为「规范化指纹键缓存」，新增 O(n) 指纹计算挂在预览渲染去抖路径（500ms debounce），每条微秒级。

## 4. dev 批次 1 前瞻审计（按件）

### 4.1 F18 + F19（87e80dc——XML gutter 高亮 pass 热路径）

**F19（XmlInlineSqlGutterLineMarkerProvider.kt）**：平台对每个候选 token 调 `getLineMarkerInfo` 且无共享短路（KDoc 自证），原形态每 token 两次 `PluginSettings.getInstance()`（detectionEnabled + gutterEnabled 各一）；现合并为 `XmlInlineSqlDetector.gutterFastPathEnabled()`（dev :89-91），单次服务查找取双布尔，私有 `gutterEnabled()` 删除。语义逐字节等价（`xmlInlineSqlEnabled && showGutterIcon`，runCatching 默认 true 同款）。无新增分配，查找次数严格减半。

**F18（XmlInlineSqlDetector.kt firstNonBlankTextPrefix，dev :100-146）**：原形态 `unwrapCdata(text).trim()` 对整段文本（自研框架载体几十~几百 KB）做全文正则 + 全文字符串复制后才 `take(64)`，且挂在每高亮 pass；现混合第三形态——①无 `<![CDATA[` 标记：直读 `trim().take(64)` 零正则；②有包裹：手工指针跳过前导空白/包裹标记（每步 O(1)），内容窗口截到「首个闭合标记前、至多 PREFIX_PROBE_LENGTH+64=128 字符」，仅对窗口做 unwrapCdata；窗口全空白则自闭合标记后继续，找遍段内仍无内容返回 null。**上界论证**：单段扫描代价 O(首个非空内容偏移 + 128)，全文级复制与全文级正则均消失；`close-cut` 语义（短 CDATA 闭合标记截进窗口的历史形态）由「窗口不含闭合」精确保持——计划 B 案「先 take 再剥」会产出错误前缀的边缘用例已由该形态规避（87e80dc 测试 +42 行含边界语料）。语义等价论证（CDATA 段级包裹不出现在首词内部 → 窗口剥包裹与全文剥包裹在首词判定上等价）已写入 KDoc，判定成立。**判定：修复干净，为挂账三轮的唯一实质敞口收口；XML 编辑热路径成本严格下降。**

### 4.2 F29 + F30（653074a——动态注册幂等 + agent 来源记忆化）

**F29（McpToolsetDynamicRegistrar.kt）**：双台账——`definedShells: Map<String, Class<*>>`（dev :47，FQN→Class，define 不可逆故重试复用免撞同 FQN LinkageError）+ `epRegistered: Set<String>`（dev :50，防重复注册）；`registerOnce` 加 `@Synchronized`（dev :70）封 check-then-act 竞态；`registerToolset` 先查 epRegistered 跳过（:98）、`definedShells.getOrPut` 包住 define（:99）、注册成功后记账（:104）。失败重试形态从「整循环永久失败 + 每次项目打开 warn 一条」变为「只补未完成项」。**有界性**：两台账规模上界 = 工具清单 10 条，终态固定；生产访问全部在 @Synchronized registerOnce 内（`registerToolsetForTest` :91 为测试触点不入生产链）。**判定：修复干净，一次性冷路径，无常驻代价变化。**
