## 4. 专项调研：zMyBatis 全仓库深度解剖（本轮重头戏）

### 4.1 身份与最大的反差

**身份**：韩国个人开发者（vendor algorist，两真人账号 luceat-lux-vestra 52 提交 + algorist 9 提交，另有 dependabot 42），Kotlin 单仓三模块（根插件+:core+:mybatis-engine），Marketplace id 30447，2026-04-01 上架至今仅 3 版、110 下载 0 票。依赖 `com.intellij.database`（宿主必须装 Database Tools），依赖真实 `org.mybatis:mybatis:3.5.19`。唯一 action `zMyBatis.Execute`（编辑器右键+运行上下文菜单），无 toolwindow、无 gutter、无 intention。

**最大的反差**：Marketplace 在售的 4 月版（v1，正则启发式求值+错误伪装成 SQL 注释的 error-as-SQL）与仓库 main 上正在进行的完整重写（代号 **Leap**，约 50 个非 dependabot 提交，104 提交总量、主代码 10,424 行、测试 12,813 行——测试比主代码还多 23%）是两个时代的产品。Leap 引入了 admission 门禁+参数契约+全链溯源的架构，但 grep 证实**未接线到任何生产 action**——它是五个月时间写出来的、只有测试能触达的产品。发布纪律极严（CI green 是必要证据非充分审批、qodana fail-closed 门禁、全部 CI action 按 SHA 固定、还有用 Python 测试来测试 CI 策略的元测试），且下版 sinceBuild 从 253 跳到 262，主动放弃 2025.3~2026.1 用户。

### 4.2 旧轨 eval 机制（在售版）

它最聪明的一步：**不自研动态 SQL 解释器，把 SQL 丢给真 Apache MyBatis 跑**——`XMLScriptBuilder.parseScriptNode()` + `getBoundSql(params)`，if/where/foreach/choose/set/trim/bind/OGNL 全部语义与真实运行时天然对齐（MyBatisEvaluator.kt:109-111），自己只做一层「字面量化」：遍历 `parameterMappings` 把每个 `?` 依序换成转义后的字面量（:117-126），foreach 的 `__frch_` 额外参数直接读 `boundSql.getAdditionalParameter`（真引擎已算好）。周边补丁：OGNL 全局注册 LinkedHashMap accessor 补 `map.size/keys`、正则剥 test 属性里的 `#{}`、错误时返回 `-- [MyBatis Plugin Error]` 注释文本而非抛错。交互链：光标定位→XML/注解/Provider 四态识别→参数弹窗（标量单行+对象 JSON 多行，按 `文件::statementId` 记忆）→只读预览（JBTextArea 无高亮）→注入 JdbcConsole 执行——**自己不做结果展示，完全复用 DataGrip 原生结果网格**；控制台按 mapper 文件复用+重启持久化恢复。

### 4.3 新轨 Leap 机制（未发布，但工程极高）

管线哲学是「先证明、后放行、只出结构化产物，证明不了就拒绝」：

- `${}` 原始插值拓扑证明：用 MyBatis 自家 `GenericTokenParser` 证明 raw 值不可能新建/改写任何 `#{}` token（StaticRawSubstitutionAdmission.kt:19-31）；
- foreach 溯源 admission：预算控制（脚本 2MB/节点 65,536/深度 64），拒绝嵌套 foreach、nullable、变量遮蔽、`__frch_` 碰撞，collection 表达式经 OGNL AST 证明「恰好是单个非索引根属性」（ForeachProvenanceAdmission.kt）；
- OGNL AST 白名单：只允许 18 种节点类型，只解析不求值，索引访问/dynamic property/`class` 属性全拒（IsolatedOgnlAstAdmission.kt:21-40）；
- classloader 隔离求值：每次准备新建 `URLClassLoader` 加载独立 MyBatis 跑 `getBoundSql`，因为 MyBatis 会向 shaded OGNL 全局注册 accessor 污染宿主进程（IsolatedDynamicMyBatisPreparation.kt），入参出参限 JDK 类型并深拷贝；
- 参数契约：从 Java mapper 方法签名推断 `ExpectedInputType`（String/整型族/浮点族/Temporal/LIST/MAP/ARRAY），每个参数携带证据链（@Param 别名/占位符/OGNL 表达式/foreach 集合/源文件+区间+版本），**文件改动契约即刻失效**（InputContract.kt:295-344）；用户输入按期望类型严格解码，错误带 offset；
- include/sql 片段跨文件依赖图：namespace 限定引用、歧义检测带候选列表、环检测带路径（XmlStatementSourceGraphResolver.kt，549 行，同样未接线）；
- `${}` 字段的 UX：强制勾选「我理解此值将作为原始 SQL 文本插入」+「Why: …」溯源 tooltip + 明文存储警告（ContractParameterInputDialog.kt）。

### 4.4 威胁评估更新

上轮判断「低，个人项目回坑」维持但需加注：**它的路线不是复刻我们，而是在做「可信执行器」**——交汇点在「执行/预览正确性」，不在可视化调试。七环逐项检查：Wrapper（零代码）、日志捕获+填参（零代码）、agent 字节码增强（零代码）、EXPLAIN 方言矩阵（零代码）、CRUD/回滚生成（零代码）、MCP（零代码）、历史面板/源码跳转（零代码）——它一个环都没有，且 Leap 能力矩阵把范围明确锁死在「XML+Java 注解→执行」。反过来我们也没有「不连库就不能预览」的短板对它形成单点碾压：它求值必须先选数据源/schema、填真实参数，我们的 mock 策略+免库预览是它没有的形态。真正的两个远期风险：一是若 Leap 按 product-contract.md 发版，「执行正确性」口碑会瞬间起来（但它 5 个月不发版 + sinceBuild 跳 262，节奏大概率继续慢）；二是它的 admission/契约设计语言是行业级的（同类思路在 DBX 的 fail-closed 确认流里也出现了），值得作为我们预览可靠性演进的参照系，而不是等它发版。
