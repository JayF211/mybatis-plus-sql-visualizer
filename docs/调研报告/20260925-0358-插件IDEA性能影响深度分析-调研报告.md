### 4.1 O-69 屏蔽规则族（T-SqlSuppress 全链 + O-80 缩放 + 走查返修）

- **【零成本常态】闸门前置**：`SqlLogEntryBuffer.kt:154` `suppressKeys.isNotEmpty()` 短路在 `isFiltered`（`:147`）之后、`synchronized(entries)`（`:168`）之前——无规则时不进锁、不触 lazy；有规则时命中才付 `onSuppressedHit` 归账（ConcurrentHashMap + AtomicInteger，`:89-92`）。MCP 审计通道同闸（`:143`），无旁路。

### 4.2 O-72 通用内嵌 SQL gutter（本轮重点）

- **API 选型**：实现 `getLineMarkerInfo`（`XmlInlineSqlGutterLineMarkerProvider.kt:36`）——与本仓全部既有 gutter provider 同款的逐元素快速 API，非 collect 慢通道；零 resolve、零索引查询、零 PSI search、零文件遍历，243/262 的 SlowOperations 断言面不触。真正的重活（点击转换）在 `previewAsync` 池线程 + `ReadAction.compute`（`SqlPreviewService.kt:2122-2128`）。行标记 pass 自带读锁上下文，provider 未包 ReadAction，正确。
- **逐 token 早退序列**：`XmlToken` → `XML_NAME` → 父 `XmlTag`（`:37-40`）→ 设置双闸 `detectionEnabled()`/`gutterEnabled()`（`:41-42`，关闭即 null，`isSqlCarrierTag` 与文本扫描全不执行）→ `isSqlCarrierTag`（`XmlInlineSqlDetector.kt:36-41`）：有子标签立退（容器标签零成本）→ 认领排除 `isClaimedByKnownStructure`（`:44-54`，mapper 语句/hbm 命名查询/pages 载体**立退零文本读**）→ 才读首个非空文本段：`unwrapCdata().trim()` → `take(PREFIX_PROBE_LENGTH=64)` → 预编译 `\s+` split + uppercase + 6 词 Set 命中（`:57-61`/`:95`/`:27`）。
- **已认领文件上的白跑成本**：平台逐 provider 独立全量调用、无共享短路，mapper.xml 上本 provider 每次高亮 pass 白跑——但主量语句标签在认领排除立退（零文本读），实际支付面 = 每 tag 两次 O(1) 检查 + 2 次设置服务查找 + 无主小标签的 O(文本段) 首词探测；典型 mapper 数百 tag × 微秒级，单 pass 毫秒以下。**实质敞口见 §5-F18**（大 CDATA 段全文正则，与 `XmlInlineSqlDetector.kt:21-22` 自钉的「只探截断前缀、零全文件遍历」红线声明不符）。

## 5. 发现点与建议（2 低·建议修 + 5 低登记 + 4 信息/文档，编号 F18 起承接第十轮系列）

> 第十轮 F1~F17 中六项已随回流兑现销账（§3.1），十一项维持原口径不再重复开出；第十一轮 1/2/3 项由 T-PerfSweep8 承接（已立项未实施）。沿用户定例：本轮仅交付报告，§5 发现点待立项指令后并入 T-PerfSweep9 或随触达批次顺带。

1. **【低·建议修】gutter 快速路径对首个非空文本段全文正则剥 CDATA 后才截断**（`XmlInlineSqlDetector.kt:89-91` + `XmlDirectText.kt:13`/`:22`）：`unwrapCdata(text).trim()` 在 `take(PREFIX_PROBE_LENGTH)` **之前**作用于全文，而 `unwrapCdata` = `(?s)` 正则全文扫描+命中分配——未认领文件里带大 CDATA 的叶子标签（自研框架 SQL 载体正是此形态，几十~几百 KB）**每次行标记高亮 pass 付 O(全文) 正则扫描**，与 `XmlInlineSqlDetector.kt:21-22` 自钉的「只探截断前缀、零全文件遍历」性能红线直接不符（红线判据写的是 `PREFIX_PROBE_LENGTH` 字符）。建议：`if (!text.contains("<![CDATA["))` 走 trim+take 直读，或先 `take(PREFIX_PROBE_LENGTH+32)` 再剥包裹——一行级修复，且应给红线声明补「删掉截断→必红」的反向验证探针。
2. **【低·建议修】gutter 每候选 token 两次设置服务查找**（`XmlInlineSqlGutterLineMarkerProvider.kt:41-42`，`detectionEnabled()` 与 `gutterEnabled()` 各自 `PluginSettings.getInstance()`，后者 `:56-58`）：平台逐 provider 全量跑、无共享短路，14 个 provider 时代本 provider 在每个 XML 文件每次 pass 都付这两次查找（含设置关闭时）。建议：合并为一次读取（一次服务查找取两个布尔）；可与 F18 同批顺带。
3. **【低】屏蔽结构键缺「结构规则存在性」门控**（`SqlLogEntryBuffer.kt:154-159`）：只要存在任意规则（哪怕全部精确口径、结构匹配未开启），每条捕获条目仍会计算一次 `structureKey`（lazy memoized，多一遍 O(n) 字面量参数化扫描 + 一次 StringBuilder 分配）。建议：manager 增设结构键独立集合或 `hasStructureRules` 标志，空则跳过第二查找；有规则 + 高频心跳 SQL 场景量级为每条一次额外扫描。
4. **【低】多选屏蔽逐条 republish**（`SqlLogPanel.kt:1799-1805` → `SqlSuppressRuleManager.kt:187-203`）：N 个不同指纹逐条 `addRule`，每条一次 EDT 上的键集重建 + 监听器遍历；N 通常个位数、键集 ≤500，量级微。建议：bulk `addRules` 单次 republish 收口。
5. **【低】管理对话框渲染每行新建 SimpleDateFormat**（`SqlSuppressManagerDialog.kt:410-411`）：每行每次重绘一次构造（KDoc 以「EDT 专用无线程约束」自辩——线程约束确实不适用，但分配面与本批 PS7-04 刚做的 SDF 缓存化方向相逆）。建议：照 `LogTimestampParser`/`SqlLogFileReader` 的缓存范式统一。
6. **【低·一致性】切分器 NON_BLOCK_BEGIN_TAILS 同段最多 5 次扫描**（`SqlStatementSplitter.kt:355` + `:66-68`）：`any { nextWordIs(...) }` 与 PS7-01 刚消灭的「同段重复扫描」同型；仅 BEGIN 武装候选点触发、O(短段)×5。建议：`nextWordToken` 单次取词进 Set 比对，随下批切分器触达顺带。
