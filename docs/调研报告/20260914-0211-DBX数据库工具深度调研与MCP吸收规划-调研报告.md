## 2. 权限模型

### 2.1 三级模式的真实编码

UI 三档对应两个 bool：**Read only = `read_only:true`；Data read/write（safe_write）= `read_only:false, allow_dangerous_sql:false`；Full access（high_risk_write）= `read_only:false, allow_dangerous_sql:true`**。

核心结构（`F:\code\Database\dbx\crates\dbx-core\src\storage.rs`）：
- `McpGlobalPolicy`（storage.rs:234-258）：`read_only`、`allow_dangerous_sql`、`allowed_connection_ids: Option<Vec<String>>`（None=全部）、`allowed_group_ids`、`allowed_tool_names: Option<Vec<String>>`、`connection_policies`、`group_policies`、`query_timeout_secs`
- `McpConnectionPolicy`（storage.rs:276-310）：每连接读写/高危模式 + `execution_mode_configured` + `execution_mode_policy_version`（版本标记，默认规则视为"上限"而非"覆盖"）+ `database_scope`(All/Selected/None, storage.rs:327-334) + `allowed_databases` + `database_policies`
- `McpDatabasePolicy`（storage.rs:314-325）：每数据库读写/高危

生效模式合成：`effective_database_execution_policy_with_groups`（`crates\dbx-core\src\mcp_policy.rs:126-162`）——全局 → 组 → 连接 → 数据库逐级覆盖；无版本标记的旧规则走 `apply_ceiling`（mcp_policy.rs:164-167）只收紧不放宽；`MCP_EXECUTION_POLICY_VERSION = 1`（mcp_policy.rs:10）。

SQL 执行前校验 `validate_sql_policy`（server.rs:2110-2154），顺序为 fail-closed 链：
1. 非 session 内禁止 USE/持久切库 `SQL_BLOCKED`（2118-2123）
2. 事务语句直接拒绝（2126-2128）
3. **双重写判定**：风险分类器 + 关键字扫描任一命中即算写，防漏判（2129-2139, `MCP_READ_ONLY`）
4. 连接级只读（2140-2145, `CONNECTION_READ_ONLY`）
5. 高危（DDL/危险 SQL）需 `allow_dangerous_sql`（2146-2149, `SQL_BLOCKED`）
6. 生产库保护最终否决（2150-2152, `PRODUCTION_WRITE_BLOCKED`）

Redis 走 `classify_command` 三级（server.rs:1050-1091），Mongo 走 `validate_mongo_command_with_groups`（server.rs:2170-2236，含 runCommand 全面禁用、`$out/$merge` 视为高危写、空 filter 写需高危权限）。

### 2.2 连接白名单

- 存储位置：**`dbx.db` 的 `app_settings` 表（单行 JSON, id=1）里的 `mcp_global_policy` key**（storage.rs:39 常量；load storage.rs:2098-2152；save storage.rs:2154-2174）。表结构见 storage.rs:780（`app_settings`）。HTTP 服务器设置另存 `mcp_http_server_settings` key（storage.rs:40）。
- 校验函数：`policy_allows_connection`（`crates\dbx-core\src\mcp_policy.rs:92-103`）——`allowed_connection_ids: None` = 全部允许；`Some(列表)` = 精确 ID 匹配 **或** 连接所在侧边栏分组路径命中 `allowed_group_ids`（分组树从 `sidebar_layout` 表解析，`connection_group_paths` mcp_policy.rs:48-86）。策略加载失败时整体 fail-closed 报 `MCP_POLICY_UNAVAILABLE`（storage.rs:2151；server.rs:1627-1629），畸形 JSON 也拒绝（storage 测试 storage.rs:6980-7012）。保存时 `normalized()` 强制归一化（去重排序、多条重复规则取合取：任一 read_only 即 read_only、高危需全部允许，storage.rs:418-550）。
- 每个工具调用先 `resolve_connection`（server.rs:1730-1800）：scope 匹配 → 白名单匹配 → 消歧义，拒绝码 `CONNECTION_OUT_OF_SCOPE`。数据库 scope 还检查 SQL 里的跨库限定名（`ensure_sql_database_scope` server.rs:1976-1992，防 `other_db.users` 绕过）。
- 桌面端 bridge 用同一套校验（`src-tauri\src\commands\mcp_bridge.rs:601-748、1069-1136`）。

### 2.3 "中央策略不可被环境变量放大"的编码

关键在 `F:\code\Database\dbx\crates\dbx-mcp\src\backend.rs:54-95`：

```rust
fn legacy_mcp_allow_writes() -> Option<bool> {          // backend.rs:54-60
    match std::env::var("DBX_MCP_ALLOW_WRITES")...{
        "1" | "true" => Some(true), "0" | "false" => Some(false), _ => None } }
fn effective_mcp_policy_with_legacy_allow_writes(state, legacy_allow_writes) -> McpGlobalPolicy {
    let mut policy = state.policy();                     // backend.rs:66-95
    if legacy_allow_writes == Some(false) {              // 只有 =0 有副作用
        policy.read_only = true;  policy.allow_dangerous_sql = false;
        // 并强制 group_policies / connection_policies / database_policies 全部 read_only=true
    }
    policy                                               // Some(true) 完全被忽略
}
```

即：`DBX_MCP_ALLOW_WRITES=1` **没有任何效果**（不能把配置好的只读策略放大）；只有 `=0/false` 仍有效且是"只收紧"——用于旧版 CLI agent 未确认写操作时强制只读（backend.rs:71-75 注释 + 测试 backend.rs:2336-2348，其中 2343 行注释明说 "Configured read_only is a hard upper bound — env var cannot relax it"）。README 安全节（packages/mcp-server/README.md:304）明确了该兼容语义：策略首次保存前 `=0` 保持只读，保存后旧变量被忽略。

配套的 run 级限制环境变量由桌面 AI 聊天内嵌 CLI agent 注入子进程（`crates\dbx-core\src\ai_cli_agent.rs:74-89`）：`DBX_MCP_ALLOW_WRITES`、`DBX_MCP_ALLOW_DANGEROUS_SQL`、`DBX_MCP_SCOPE_CONNECTION_ID(S)/NAME/DATABASE/SCHEMA`、`DBX_MCP_CONFIRMED_WRITE_SQL`。其中：
- `DBX_MCP_CONFIRMED_WRITE_SQL`：用户确认过的具体写 SQL 绑定，单条（server.rs:2071-2078）和批（`confirmed_batch_sql_block_reason` server.rs:2085-2107，脚本含写语句但不是确认的那条即整体拒绝，防"夹带"）双重防重放。
- `DBX_MCP_ALLOW_DANGEROUS_SQL` 不被 dbx-mcp 读取（只被 dbx-cli 的 `dbx query` 读取，crates/dbx-cli/src/main.rs:326-331；以及 Codex/pi 等 CLI 配置生成），MCP 侧高危权限只来自中央策略。

## 3. 数据访问路径

**MCP server 直接读桌面端的 `dbx.db` SQLite 文件，不走 IPC**（数据面）；只有两个桌面 UI 工具走 localhost HTTP bridge。

- 路径解析 `crates\dbx-mcp\src\paths.rs:7-19`：`DBX_DATA_DIR` 非空 → 直接用；否则 `dirs::data_dir()/com.dbx.app`（与桌面端同一 `com.dbx.app` 标识、同一 `dirs::data_dir()` 调用，含 Linux XDG_DATA_HOME）。db 文件 = `<data_dir>/dbx.db`（paths.rs:3,17-19）。
- `main.rs:12-20`：无 `DBX_WEB_URL` 时 `LocalBackend::open(db_path)`（backend.rs:584-601）→ `Storage::open` 直接打开 SQLite，载入 connections + DesktopSettings，构造进程内 `AppState`（含连接池）。
- **耦合点 1（共享存储）**：连接、MCP 策略（app_settings.mcp_global_policy）、侧边栏分组（sidebar_layout）都从同一个 dbx.db 读，且**每次工具调用都重读**（`load_connections` backend.rs:695-705 会把桌面端 UI 的增删改同步进内存缓存并废弃不兼容连接池，`sync_runtime_configs` backend.rs:611-641）。桌面端未运行也能查库。
- **耦合点 2（bridge 端口文件）**：桌面端启动时绑 `127.0.0.1:0` 并把端口写进 `<data_dir>/mcp-bridge-port`（`src-tauri\src\commands\mcp_bridge.rs:14-15、200-287`）；MCP 侧 `LocalBackend::bridge_request` 读该文件后 POST `http://127.0.0.1:{port}`（backend.rs:1006-1021），仅服务 `dbx_open_table`(POST /open-table) 和 `dbx_execute_and_show`(POST /execute-query，桌面执行后 emit `mcp-execute-query` 事件刷新 UI，mcp_bridge.rs:1206-1263)。bridge 请求同样过全套 MCP 策略检查（mcp_bridge.rs:601-1136）。
- **Windows portable 与 `DBX_DATA_DIR`**：桌面端解析顺序 = `DBX_DATA_DIR` 环境变量 > 便携标记（exe 同目录有 `portable.dbx` 且无 `uninstall.exe` 时用 `<exe_dir>/data`）> 默认 AppData（`src-tauri\src\data_dir.rs:37-129`）。Rust MCP 的 paths.rs **只实现了环境变量分支，不会探测 portable 标记**（探测逻辑在 Tauri 壳里，MCP 二进制没有），因此便携版用户必须显式设置 `DBX_DATA_DIR=<exe>\data`（README "Windows portable DBX" 一节，packages/mcp-server/README.md:253-268）。
- **Web 模式**（`WebBackend`，backend.rs:380-575、1024-1041+）：设 `DBX_WEB_URL` 即切换，所有数据经部署的 DBX Web HTTP API：`GET /api/auth/check` → `POST /api/auth/login`（密码 = `DBX_WEB_PASSWORD`，拿 `dbx_session` cookie），策略读 `GET /api/app-settings/mcp-policy`（backend.rs:1026-1033），连接读 `GET /api/connection/list`，执行前 `POST /api/connection/connect`（ensure_connected backend.rs:566-574）；每个请求带 `x-dbx-mcp-request: 1` 头。支持代理/TLS 相关 `DBX_WEB_HEADERS`、`DBX_WEB_CA_CERT` 等（backend.rs:402-463）。
- **桌面端也可内嵌 MCP HTTP 服务**：`src-tauri\src\commands\mcp_http_server.rs`（McpHttpServerState，bearer token 存 `<data_dir>/mcp-http-token` 私有文件 0600 权限而非设置项，storage.rs:336-338 注释），通过 `serve_streamable_http_on_listener` 复用同一 LocalBackend（backend.rs:580-582 `from_app_state`）。

## 4. 传输方式

- **stdio（默认）**：`main.rs:22-27` 用 rmcp `stdio()`，外包 `with_legacy_discovery_fallback`（`crates\dbx-mcp\src\transport.rs:10-65`）：拦截旧版 `server/discover` 自定义请求回 METHOD_NOT_FOUND 而不断开，让新客户端回落到标准 initialize 流程。
- **Streamable HTTP**：`--http`/`DBX_MCP_TRANSPORT=streamable-http`（runtime.rs:44-125）。默认 `127.0.0.1:5225/mcp`；**必须**提供 `DBX_MCP_HTTP_TOKEN` 或 `DBX_MCP_HTTP_TOKEN_FILE`（runtime.rs:153-167）；绑非回环地址需同时满足 `DBX_MCP_HTTP_ALLOW_REMOTE=1` + `--http-allow-remote` + 非空 `DBX_MCP_HTTP_ALLOWED_HOSTS`/`_ORIGINS`（runtime.rs:96-113，且显式 flag 才算数，纯环境变量不够）。实现：axum 路由 + rmcp StreamableHttpService（`crates\dbx-mcp\src\http.rs:21-118`），含 `/healthz`、`/readyz`；鉴权中间件（`crates\dbx-mcp\src\http_auth.rs:64-93`）做 Origin 白名单 + 恒定时间 Bearer token 比较（http_auth.rs:38-51）+ 审计日志；CORS 与鉴权共用同一 origin 谓词，回环模式放行 localhost 任意端口（http.rs:51-65）。
- **Web 模式**：`DBX_WEB_URL` 指向后端 API 时走 stdio 适配（main.rs:12-16）；此外 DBX Web 服务端自身可挂载原生 Streamable HTTP（`DBX_WEB_MCP_TOKEN` 等，由 dbx-web 实现，README:241-251 有说明；本次未深入 dbx-web 源码逐行验证）。
- 每个协议会话新建 `DbxMcpServer`，但 backend 共享、鉴权在 rmcp 之前（http.rs:68-70）。

## 1. DML 写前预览（Preview changes）

**核心文件：`F:\code\Database\dbx\crates\dbx-core\src\dml_preview_sql.rs`（共 599 行，纯函数、零状态）**

### 总体设计（文件头注释 1-13 行有完整说明）
不重建 sqlparser AST，而是**复用 sqlparser 的 `Display` round-trip**：用 sqlparser 解析成 AST 后，只对外层做字符串装配。这样表达式/表名/WHERE 的方言渲染由 sqlparser 保证正确。

- 入口：`build_dml_change_preview_sql`（319-350 行）。输入 `DmlChangePreviewSqlOptions { sql, database_type, identifier_quote, columns }`，输出 `DmlChangePreviewSqlResult { sql, operation, has_new_value_columns, tables }`。
- 方言归一化：`normalize_dialect`（58-69 行）把 30+ 数据库类型映射到 8 种 sqlparser 方言；`parse_statements`（71-83 行）选方言解析。
- 标识符引号：`quote_identifier`（85-98 行）按连接的引号字符（`` ` ``/`"`/`[`）或方言默认值渲染。

### UPDATE 改写：`build_update_preview`（116-211 行）
`UPDATE t SET a = 123 WHERE id = 1` → `SELECT *, 123 AS "a (new)" FROM t WHERE id = 1`

- **`column (new)` 列的生成**（157-160 行）：每个 SET 表达式原样搬运为 `<expr> AS "<列名> (new)"`。别名固定后缀 `" (new)"`。关键洞察（注释 9 行）：SET 表达式在行上下文中按**旧值**求值即得新值，所以 `SET a = a + 1` 也能算对。
- **同列重复赋值**（122-142 行）：取最后一次，但保持首次出现的列序（`set_order` + `set_items` 双数组，按小写列名去重移位）。
- **交错展开模式**（163-197 行）：单表 + 前端传入列清单（ordinal 序）时，投影为「原列, 原列 (new), 下一原列, 其 (new)…」，新值列紧跟原值列；SET 列不在列清单里时追加到末尾（178-182 行兜底）。多表 join 或无列清单时退化为 `*, <追加的新值列>`。
- WHERE/ORDER BY/LIMIT 直接从 AST `to_string()` 拼回（199-210 行）。

### INSERT / DELETE
- `build_insert_preview`（214-283 行）：`VALUES` 多行 → `SELECT 1 AS "a", 'x' AS "b" UNION ALL SELECT …`（每行一个 SELECT，列名来自插入列清单）；MySQL `INSERT … SET` → 单条 SELECT；`INSERT … SELECT` → 直接返回源查询。
- `build_delete_preview`（286-317 行）：`DELETE FROM t WHERE …` → `SELECT * FROM t WHERE …`，保留 USING/ORDER BY/LIMIT。

### “无法安全改写”的判定（全部返回 `Err("Preview is not supported: …")`，`unsupported` 在 108-110 行）
- 非恰好 1 条语句（322-326 行）、非 UPDATE/INSERT/DELETE（348 行）。
- UPDATE 赋值目标不是单列（Tuple，131-133 行）。
- **Postgres `UPDATE … FROM`**（146-154 行）：注释解释——同一目标行可能匹配多行来源，真实 UPDATE 只更新一次，而改写出的 SELECT 会跨连接重复计数，直接拒绝。
- INSERT VALUES 行长度与列清单不符（249-251 行）、VALUES 为空、无 source。
- 解析失败（71-83 行）。错误信息为英文，前端直接 toast，**原语句仍可正常执行**（预览失败不阻塞执行）。

### 前端接线（QueryEditor.vue）
- `requestPreviewChanges`：`F:\code\Database\dbx\apps\desktop\src\components\editor\QueryEditor.vue:1569-1604`。先无列清单调 `api.buildDmlChangePreviewSql` 拿到目标表引用（`tables`），若单表则调 `api.getColumns` 拉列元数据，**第二次调用**传 `columns` 生成交错版本；最后给 SQL 前置注释 `/* dry-run preview */` 并 `emit("executeInNewResultTab", …)` 走正常只读执行路径。

## 对 SQL Visualizer（IntelliJ 插件 / MyBatis SQL 写前预览）的可移植性评估

### 纯算法，可直接移植（语言换成 Java/Kotlin 即可）
1. **DML→SELECT 改写算法**（dml_preview_sql.rs 全文件）——最值得抄。Java 生态有等效的 SQL 解析器：JSqlParser 或 Apache Calcite（MyBatis 自带 `SqlSource`/`BoundSql`，甚至可先拿 boundSql 再解析）。要点全部可平移：外层字符串装配 + AST round-trip、`(new)` 别名后缀、SET 表达式按旧值重求值（`a=a+1` 正确性）、同列去重保序、“交错展开需列元数据”的两阶段流程（先解析拿表引用→查列→重生成）、`UPDATE … FROM`/多语句/元组赋值拒绝清单。对 MyBatis 场景额外利好：`#{}` 参数已在 boundSql 阶段替换，改写输入是合法 SQL。
2. **危险 SQL 判定规则**（sql_risk.rs:144-223）——`statement_is_dangerous` + `predicate_is_obviously_unbounded` 是一套完整的“无界写”静态判定（WHERE 缺失/`1=1`/`a=a`/`LIKE '%'`/含子查询/无列引用），与你插件的 EXPLAIN 诊断天然互补；JSqlParser 可表达同样的 AST 检查。
3. **写语句识别**（query_execution_sql.rs:455-501）——关键词首判 + 注释/字面量剥离 + 方言特判（MySQL 可执行注释、INTO OUTFILE、CTE 包裹写）的分层策略，日志还原场景（判断一条日志 SQL 是否需要还原/预览）直接可用。
4. **Keyless 守卫模式**（data_grid_sql.rs:1572-1576 + useDataGridEditor.ts:1563-1583）——“预览 COUNT 与写语句共用同一 WHERE 字符串，count>1 或取不到即拒绝”这一 fail-closed 设计，可移植为插件对无主键表预览的行数校验。
5. **影响行数预估**（DataGrid.vue:8109-8142）——执行前发 `SELECT COUNT(*) WHERE <同条件>`，带 requestId 防陈旧结果；EXPLAIN 场景可换成 `EXPLAIN` 的 rows 估算，模式相同。
6. **回滚语句反向生成**（new→DELETE 按全行值、deleted→INSERT 原值、dirty→SET 旧值）——纯函数，直接可移植做“生成回滚 SQL”功能。
7. **`${table}` 模板展开 + 快捷键冲突规范化比较**（sqlShortcutActions.ts 全文件，43 行）——Trivial，IntelliJ 的 Action/快捷键体系可借用“规范化后比较 + 与内置 action 集合比对 + 冲突阻断应用”的交互模型。

### 依赖 DBX 架构，不可直接移植（但设计思想可借鉴）
1. **Rust 侧只读强制门**（query.rs 的 `check_read_only_for_connection` 在 7 个执行入口逐一调用）——依赖 `AppState` 连接池与统一执行入口。IntelliJ 插件没有自己的连接层（走 Database 经典 Console/DataSource），等效做法是在插件自己的 SQL 注入点（如 Intention/Before-execution 拦截器）调用等价判定。
2. **写解锁状态机**（write_unlock.rs + readOnlyUnlockStore.ts）——依赖 Rust 进程内 `RwLock<HashMap>` + 后端权威计时 + 前后端双时钟同步。插件可简化为 IDE 级 `PersistentStateComponent`（但注意：持久化解锁窗口会破坏“重启即失效”的安全属性，DBX 特意放内存）。
3. **双实现镜像问题**——DBX 在 Rust 与 TS 各维护一份 sqlRisk/redis 分类器（还有第 4 处 production_safety.rs 正则版）。这是“执行路径在 Rust、UI 在 TS”架构的产物；插件单语言无此问题，应只留一份。
4. **生产库跨库引用正则提取**（productionSafety.ts 的 20+ 正则 + 方言限定名判定）——算法本身可移植，但它依赖连接配置里的 `production_databases` 标记体系与方言表；插件若拿不到“哪个库是生产”的元数据，这条链路无意义，可只借“歧义即命中”原则。
5. **pending changes 的索引寻址快照/undo 栈**——与 DBX 的虚拟滚动网格耦合；插件如果做结果表编辑可用同样结构（`Map<row, Map<col, value>>` 深拷贝快照做 undo 是通用好模式），但 SQL 生成的方言矩阵（30+ 数据库）不必照搬，聚焦 MySQL 即可。

### 一句话结论
dml_preview_sql.rs（改写算法）、sql_risk.rs:144-223（无界写判定）、data_grid_sql.rs 的 guard/count 模式、以及“预览语句与执行语句共用同一 WHERE 字符串”的不变式，四者都是纯算法/纯设计，约占你四个功能所需核心逻辑的 80%；DBX 的安全分层（只读门/解锁窗口/生产标记）则强绑定其 Rust AppState + 前后端双时钟架构，只宜借鉴“持久标志永不翻转、后端为权威、fail closed、歧义即拒绝”这四条原则。

## 5. SQL Visualizer 的 MCP 能力规划（N-12 立项依据）

> **2026-09-14 后续修订**：经 IDEA ACP 与平台原生 MCP 专项调研（`20260914-0317-IDEA-ACP与平台AI原生能力-调研报告.md`），本节「插件内嵌 stdio server」架构不再是一期主轨——平台内置 MCP Server 插件（com.intellij.mcpServer）提供公开的 mcpToolset 扩展点，N-12 改为把三工具注册进平台体系（零 launcher/零端口/零弹窗），自建 stdio 降为可选兜底。本节工具面取舍、权限红线与分期原则仍然有效，保留作设计依据。

> 前提回顾：本插件不做连接管理（复用 IDE 数据源），有「弹窗克制设计红线」。MCP 的定位是把插件的确定性 SQL 能力暴露给 AI agent（ZCode / Claude Code / Cursor 等），让 agent 在写 mapper 前后调用本插件而不是绕过它——把「AI 替代」翻转为「AI 依赖」。用户本机即是 DBX MCP Server 的重度使用者（ZCode 挂全套 dbx 工具），分发模式已被亲身体验验证。

### 5.1 工具面

**P1（最小工具面，2~3 个，全部只读）**

| 工具 | 入参 | 出参 | 价值 |
|------|------|------|------|
| `mpsv_render_sql` | 项目相对文件路径 + 行号（或直接源码片段 + 触发面类型） | 渲染后可执行 SQL + 触发面类型 + 降级说明 | agent 写完 mapper/Wrapper 后即时验证 SQL 形态；本插件 13 类触发面 + 金样矩阵级的渲染正确性是独家供给 |
| `mpsv_schema_context` | 数据源别名 + database/schema + 表名白名单（max_tables 限幅，参照 DBX 默认 8、上限 20） | 紧凑表+列上下文（含注释） | 给 agent 供真实表结构；数据源凭证不出 IDE，MCP 进程拿不到凭据本体 |
| `mpsv_explain` | 数据源别名 + SELECT 语句 | 计划文本 | EXPLAIN 七方言矩阵（含金仓/达梦）是全市场无对应物的能力 |

**P2**：`mpsv_restore_log`（日志片段还原为参数回填 SQL）、`mpsv_recent_executions`（按文件/方法查最近执行记录——复用执行期 SQLVIS-SOURCE 标记数据）、CRUD SQL 与测试资产生成。

**P3（默认永久关闭的写通道）**：若开放写执行，必须继承 DBX 验证过的四原则——中央只读策略是硬上限、客户端环境变量不可放大（DBX 实现：`DBX_MCP_ALLOW_WRITES=1` 完全被忽略，只有 `=0` 能收紧，`backend.rs:54-95`）；用户确认与执行逐字绑定防夹带（`DBX_MCP_CONFIRMED_WRITE_SQL` 单条+批双重比对）；解锁窗口只存内存不持久化（保持「重启即失效」安全属性）；fail closed（解析失败按写处理）。

### 5.2 架构

推荐「IDEA 插件内嵌 stdio MCP server」。IntelliJ 本身是常驻 JVM，不需要 DBX 式独立二进制 + 共享 SQLite 的耦合：MCP 会话在插件进程内直接调 Service 层，数据源凭证、PSI、执行期标记天然可达且不外泄。要点：

- 传输 stdio 起步（与主流 MCP 客户端默认一致）；Streamable HTTP 涉及 token 文件权限、Origin 白名单、恒定时间比较等安全面（DBX 的 `http_auth.rs` 可照抄清单），留 P3。
- 线程规则：MCP 线程调 PSI 必须走后台读队列（ReadAction），渲染属纯计算可同步返回；EXPLAIN 经 IDE 数据源执行走后台线程 + 超时。
- 工具白名单固定：不提供任何连接管理工具（与产品定案一致）；DBX 的「scope 模式自动禁用高危工具、`tools/list` 让 LLM 看不到会被拒绝的工具」策略照搬。
- 审计日志：每次工具调用记 idea.log（或独立文件）——时间、工具、入参摘要、结果状态。
- 零弹窗红线兼容：agent 触发的调用一律不弹确认框，拒绝就返回 MCP error（错误文案给 agent 可读的原因）。

### 5.3 P1 验收标准

1. 三个工具在 ZCode 与 Claude Code 实测可用（真机走查）。
2. 越权用例全拒：UPDATE/DDL/多语句夹带/非白名单数据源，返回结构化错误码（参照 DBX 的 `MCP_READ_ONLY`/`CONNECTION_OUT_OF_SCOPE`/`SQL_BLOCKED` 语义）。
3. IDE 无数据源/项目未索引时明确报错不挂死；会话空闲超时自动回收（参照 DBX 30 分钟过期）。
4. 全流程零主动弹窗；审计日志可查。
5. verifyPlugin 三目标 Compatible，签名护栏按跨版本反射入口登记约定执行。

### 5.4 分期节奏建议

P1 与 2026.9.14 正式版之后的里程碑并行立项；P2 待 P1 真机验证后按用户反馈排序；P3 写通道无限期搁置，除非出现明确的授权写场景需求。风险提示：DBX 的 MCP 工具面是 19 个（含连接管理三件套），本插件 P1 只做 3 个纯只读工具，复杂度约为其十分之一，重点花在「渲染 SQL 的 agent 易读性」上——这是竞品 MCP 做不了的部分。

## 4. AI 生成 SQL 的安全审查

**结论：是纯静态规则审查（sqlparser AST 分类），不是 LLM 自审。** README 说的 "built-in safety checks review AI-generated SQL before it runs" 的实现链路：

- **风险分类** `crates/dbx-core/src/sql_risk.rs:18-24` — `enum SqlRisk { ReadOnly, Write, Ddl, Transaction }`（SELECT/SHOW/DESCRIBE/EXPLAIN/纯读 CTE=ReadOnly；INSERT/UPDATE/DELETE/MERGE/REPLACE/CALL=Write；CREATE/ALTER/DROP/TRUNCATE/GRANT/REVOKE=Ddl；BEGIN/COMMIT=Transaction，agent 一律禁止）。入口 `sql_risk.rs:686` `classify_sql_risk_for_database(sql, database_type)`，用 sqlparser 按方言解析 AST 后 `classify_statement`（sql_risk.rs:69）判定，还有无 WHERE UPDATE、OR 互补谓词等细粒度启发（sql_risk.rs:144-484）。解析失败对写类 fail-closed。
- **权限门** `crates/dbx-core/src/agent_tools.rs:134-159` — `AgentSqlPermissions { allow_writes, allow_dangerous, confirmed_write_sql: Option<String> }`；`confirmed_write_sql_permissions()`（agent_tools.rs:146）fail-closed：生产库、空确认、无具体 SQL 任一条件不满足 → 写权限为 false。`sql_risk_allowed`（agent_tools.rs:202）：Write 需 allow_writes，Ddl 需 allow_dangerous，Transaction 永远 false。
- **拦截时机（agent loop 内）** `agent_loop.rs:473-498`：LLM 若不听话直接调了 execute_query 写语句，`write_requires_confirmation`（agent_tools.rs:214-224，内部调 sql_risk 分类）在**派发到数据库之前**拦截，按是否生产库发 `AgentEvent::WriteSqlConfirmationRequired { sql }`（前端弹确认框，用户确认后带 `confirmed_write_sql` 重新发起请求）或 `AgentEvent::ProductionWriteBlocked { sql }`。
- **确认绑定防漂移**：`src-tauri/src/commands/ai.rs:363-385` 在后端校验确认时的 connection/database/schema 快照与实际目标一致（`verify_confirmed_target`，agent_tools.rs:167-200，快照缺失也拒绝——fail-closed）；执行时 `take_sql_permissions_for_execution`（agent_tools.rs:229-247）**一次性消费**确认授权（SQL 必须与确认串精确匹配，`sql_matches_confirmed_write`，agent_tools.rs:781），之后同 run 内的后续写调用需重新确认。CLI 路径同样经 `DBX_MCP_CONFIRMED_WRITE_SQL` env 传给 dbx-mcp 子进程执行同一校验。
- 辅助：`production_safety.rs` 的 `is_production_database`/`targets_production_database`（ai.rs 命令层 ai.rs:353-358 调用）；执行前 DML 预览另有 `dml_preview_sql.rs`、影响报告 `safety_report.rs:4 generate_safety_report(ImpactReport)`（这是本地 SQL 分析功能，不在 AI 链路上）。
- 换言之：**AI 生成的 SQL 在 Ask 模式下不会自动执行（仅文本），Agent 模式下执行前被静态 SqlRisk 分类 + 用户逐条确认双重把关**。

## 二、精华吸收分析

### P1：可直接平移的核心机制

**1. AI 生成 SQL 的静态安全审查链（最精华）**
- DBX 怎么做（`agent_tools.rs:134-247` + `agent_loop.rs:473-498`）：LLM 生成的 SQL 先过 `SqlRisk` 四级分类（ReadOnly/Write/Ddl/Transaction，sqlparser AST 判定，解析失败 fail-closed）；写需 `allow_writes`、DDL 需 `allow_dangerous`、事务**一律禁止**；写确认绑定三要素（connection/database/schema 快照）+ **SQL 逐字匹配 + 授权一次性消费**（`take_sql_permissions_for_execution`，agent_tools.rs:229-247）——确认过的 SQL 执行一次后授权作废，防会话中途换 SQL 漂移；生产库写直接阻断或强制确认。
- 对 SQL Visualizer：上一轮 MCP 规划里的“逐字确认绑定”在源码层得到完整实现范本。落地形态：插件内建 `SqlRiskClassifier`（JSqlParser 平移 `sql_risk.rs:69-484`，含“无 WHERE 的 UPDATE/恒真谓词/INSERT...SELECT”细则），AI 生成的 SQL **不直接执行、直接进写前预览器**——我们的预览器天然是 AI SQL 的安全落点，这是比 DBX 更顺的架构位。
- 关键提示词规则照抄：`ai.ts:504-506` “写 SQL 先放唯一代码块 + 问句确认 + **确认后原样执行不得改写**”；Ask 模式 “只生成 SQL，不要暗示已执行”。

**2. 结构化技能定义表（prompt 工程的工程化）**
- DBX 怎么做（`aiSkills.ts:16-45`）：每个动作为 `{ id, riskPolicy, contextNeeds, userInstruction, systemRules, outputContract }` 的数据对象，中英双语文案内联；10 个动作各有风险策略、上下文需求声明、输出契约。系统提示分五层装配（基础安全规则/模式/技能/富内容协议/上下文尾注，`ai.ts:286-333`）。
- 对 SQL Visualizer：直接抄成 Kotlin `enum + data class` 表。我们需要的动作集：`generate_mybatis_sql`（NL→mapper 片段）、`explain_sql`、`optimize_sql`、`fix_sql`（吃日志还原的报错）、`convert_dialect`、`restore_incomplete_log`（AI 补全残缺日志——我们的独有场景）。`contextNeeds` 声明让上下文装配按需拉取，不浪费 token。
- schema 注入预算照抄（`ai.ts:574-710`）：默认 50 表×40 列×10 索引×10 外键，超限置 `truncated` 并在提示词里写“不要猜测，让用户 @table 指定”——**预算 + 截断话术**这对组合是防幻觉的关键。

**3. @提及/拖表上下文注入**
- DBX 怎么做（`aiTableMentions.ts` + `AiAssistant.vue:1938-2400`）：光标前 `@token` 触发候选弹层（schema 感知、引号标识符、chip 结构化插入而非文本残留）；对象树右键 "Add to AI"、网格多选行、查询历史条目都能进上下文（`objectBrowserToAiTargets.ts`）；提及表**优先完整加载**列/索引/FK/注释（`loadMentionedTableContext`），其余表才走 50 表兜底。
- 对 SQL Visualizer：编辑器里 `@mapper`/`@table` 提及（PSI 补全 mapper statement 与实体表），右键 mapper statement → "Ask AI to explain"；日志面板选中片段 → AI 分析。上下文 = mapper XML 片段 + 还原 SQL + 表结构（预算内）。

### Provider 抽象的取舍

DBX 用 **enum + match + api_style 三态**（`ai.rs:81-158`），不搞 trait 继承体系；DeepSeek/Kimi/Qwen/Zhipu/MiniMax/Ollama 全部复用 OpenAI 兼容路径，仅按 provider 注入私有字段（如 thinking 开关）。这个“一个兼容路径 + 少量特判”的轻量抽象对 Kotlin 同样成立，比抽象工厂便宜得多。**但对 IDEA 插件，优先核实平台自带 LLM API**（262 平台有 AI Assistant/语言模型基础设施，可 ride 平台的 provider 和额度体系，用户免配 key）——此点**未在本机验证**，列为实现前必查项；自建 provider 层作为兜底方案，结构照 DBX 的 enum 即可。
