### R45 EXPLAIN 执行计划体检（首推）

- 痛点：EXPLAIN 面板解决了「看得见」计划，没解决「读得懂」——type=ALL、key=NULL、filesort/temporary、估算行数与 LIMIT 失配这些红旗对老手一眼见血，对多数用户仍是一屏陌生字段。从「结构化渲染」到「人话结论」差一层，这层正是新手流失点。
- 形态：EXPLAIN 面板加「体检」视图——规则化 checklist（全表扫/未走索引/JOIN 序红旗/临时表与排序/估算行数失配等），每条=判据+中文解释+可执行建议，pass/warn/fail 三态汇总；纯本地规则引擎，零 AI 零遥测零外部调用。
- 规模 S~M；前提 V64（结构化渲染层已抽取哪些字段的核实：MySQL type/key/Extra、PG 节点类型、Oracle PLAN_TABLE 列、DM/金仓等方言差异——规则只能建在已解析字段上；若现状仅文本高亮无字段抽取，则先落一个 M 级解析件再谈规则）。
- 为何本轮成立：EXPLAIN 真机通道+11 方言分发已在（R33 修复后验收）、结构化渲染在册，基建最近、规模最小、红线最干净；与 R34（EXPLAIN 历史化对比）相邻不重叠——R34 比较多次执行的趋势，R45 解读单次计划的健康度。竞品零对位：DBX EXPLAIN 链零增量连续多窗，货架内无人做计划解读。

### R46 执行前 Schema 校验

- 痛点：渲染正确不等于能执行——列名错字、表名漂移、字段改型后旧 SQL 未跟，是动态 SQL 最高频的运行时错误，发现越晚代价越大；现有链路验证「能不能渲染」，不验证「能不能命中 schema」。
- 形态：预览/EXPLAIN 执行前，把渲染产物 SQL 的表/列引用与绑定数据源的 introspection 比对，未知对象红色警示+最接近名建议（did-you-mean）；未绑定数据源自动跳过不阻塞，校验为纯元数据只读。
- 规模 M；前提 V65（插件侧 introspection API 可用面与缓存路径核实；11 方言大小写折叠与引号规则差异——Oracle 大小写双向折叠已有真库实测在册，引号规则不能无条件照搬）。
- 为何本轮成立：数据源绑定+指示行三级化（O-96）刚把「当前会话绑定哪个库」做成一等公民，校验是同一基建的顺延一层；红线对照=只读元数据、调试辅助，非 DB 管理工具化（不做连接/导出/管理动作）。竞品对照：数据库工具有 console 级校验，但插件货架内的 MyBatis 预览链路无人做。

### R47 动态 SQL 分支覆盖报告

- 痛点：动态 SQL 的测试盲区是「从没被任何参数组合触发过的 if/choose/foreach 分支」——本机全绿上线才爆；用户知道试过什么，不知道没试过什么。
- 形态：参数历史会话聚合出节点级触发事实，产出分支覆盖率+「零触发分支」清单，引导用户补参数方案（与参数方案机制闭环）。
- 规模 M（视 V66 探查结果可能降到 S）；前提 V66（参数历史/求值探镜数据结构是否已记录节点级触发事实——与 R43 的 V61 是同一探查件，一次派工两案受益，建议合并派工）。
- 为何本轮成立：历史检索+历史对比+条件求值探镜三件基建在场，只差聚合视图一层；动态 SQL 预览是本插件核心赛道，覆盖报告把「调试工具」升格为「测试辅助」，拉开与全部竞品的位差。竞品零对位。
