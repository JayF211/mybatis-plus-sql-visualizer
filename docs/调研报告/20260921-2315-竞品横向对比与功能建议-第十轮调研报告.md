### 3.2 格局变化的信号

1. **方法学修正一：`searchPlugins` 的 `size=` 参数被服务端静默忽略**。实测传 20/100 都只回 **10** 条，真实生效的分页参数是 `max=`（上限 20，`max≥25` 直接 HTTP 400）。这意味着**历轮（含第九轮）所称「前 20 槽位」实际只有 10 条**——新面孔扫描的覆盖面一直是被砍半的。本轮改用 `max=20` 并追加 `offset=20` 覆盖第 21–40 槽位，扫出 41 个候选（此前口径下会漏掉约一半）。**结论：历史轮次的新面孔结论不作废但覆盖面偏窄，本轮起以 `max=20` 为口径。**
2. **方法学修正二：高位插件的下载计数是批量/延迟刷新的，不是实时值**。本轮 16 个插件呈明显二分：7 个有增量（Log Free +387、MyBatisPlus +154、Free MyBatis Tool +76、Ultra +6、**本插件 +4**、Jtools +1、zMyBatis +1），**9 个两天零增长**——其中包含日下载本应上百上千的 MyBatisX（5,412,277）与 JPA Buddy（6,796,619）。用 `Cache-Control: no-cache` + 随机 query 重抓复核，读数不变，且 `info` 与 `searchPlugins` 两端点一致。**结论：下载增量只对低位插件（万级以下）有参考意义；高位插件应视为「至少 0」，不能据此判定市场停滞。**
3. **断供进入第三周，且贬值速度在加快**。上轮（第九轮）到现在 46 小时，master 又攒下 141 个提交、约十项用户可见改进（增强捕获五条修复 + 空白符开关 + INSERT inlay + foreach 别名 + Oracle 引号 + 串感知拼接 + 回滚 SQL 入口 + 工具栏单行 + 预热预算），**全部只存在于 master**。Marketplace 用户（299 人）与 Gitee 用户都拿不到；本插件增速 +4/日（缓存口径下趋弱），0 票 0 评论第七周。
4. **push 债清零与断供并存，形成清晰反差**。上轮第一风险是「推送债 369 + 断供」双债叠加；本轮推送债清零（唯一完成的出场动作），断供仍在——**说明「动作缺失」型债是可以清的，只差把它排进窗口**。这条对 §11 的优先级建议有直接含义。
5. **zMyBatis 从「接线冲刺」转为「重心转向治理」**（§4）：GitHub 侧两天只有 3 个提交且 100% 是 CI/治理，产品轴停摆；Marketplace 冻结 5.5 个月。上轮「1~2 周量级接近可发货」的判断**需要下修**——不是因为它慢，而是因为它的注意力转移了。
