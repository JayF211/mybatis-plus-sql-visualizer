# IDEA ACP 与平台 AI 原生能力调研报告

日期：2026-09-14（Marketplace/GitHub 数据为当日 API 实测）
调研目标：判断 IntelliJ 插件能否吸收或复用 JetBrains 的 ACP（Agent Client Protocol）能力，打通「IDEA 内 AI agent ↔ 插件能力（MCP/AI 接入）」链路，为 N-12（MCP 能力一期）与 N-14（AI 可选集成）提供修订依据。
验证环境：本机 IntelliJ IDEA Ultimate 262.10315.125（2026.2.1），`C:\Users\USER\AppData\Local\Programs\IntelliJ IDEA\`，直接解包/javap 反编译内置插件。网络为直连，未用本地代理。

核心结论先行：ACP 的"客户端"面（在 IDE 里跑外部 agent）对我们只是场景，不是依赖；真正的抓手是 IDEA 平台内置的 MCP Server 插件（`com.intellij.mcpServer`，253/262 内置、243 可从 Marketplace 装 1.0.30）——它有公开的 `mcpToolset` 扩展点，官方文档明确支持第三方插件注册工具。N-12 应从"插件内嵌 stdio MCP server"改为主轨"注册进平台 MCP Server 体系"，自建 stdio 降级为可选兜底。N-14 的"ride 262 平台自带 LLM API"判断被证伪：平台本体没有任何 LLM API 模块，公开 SDK 文档也没有 LLM API 页面。

## 一、ACP 协议档案

### 1.1 基本盘

- 发起方 Zed，官网 agentclientprotocol.com。JetBrains 2025 年 12 月博客自述：在 Zed 宣布该协议后跟进合作，并把自家内部 Junie 协议并入 ACP，"类似 LSP 之于语言服务器"（https://blog.jetbrains.com/ai/2025/12/bring-your-own-ai-agent-to-jetbrains-ides/）。
- 角色两分：agent（用生成式 AI 自主改代码的程序，通常以 client 子进程运行）与 client（IDE/编辑器，管理环境、用户交互与资源访问）。
- 协议版本：v1 已稳定，v2 为 draft（agentclientprotocol.com/llms.txt 索引可见 protocol/v1 与 protocol/v2 两套文档）。

### 1.2 传输

- 主传输 stdio：client 拉起 agent 子进程，JSON-RPC 2.0 换行分隔，UTF-8，agent 的 stdout 只准写 ACP 消息、日志走 stderr；client 关 stdin 即结束。Streamable HTTP 仅是 draft 提案，自定义传输被允许（https://agentclientprotocol.com/protocol/v1/transports.md）。

### 1.3 方法清单（v1）

Agent 侧必须实现：`initialize`、`session/new`、`session/prompt`、`session/cancel`、`session/update`（通知）；可选：`authenticate`、`session/load`、`session/set_mode`、`logout`。
Client 侧必须实现：`session/request_permission`；可选：`fs/read_text_file`、`fs/write_text_file`、`terminal/create|output|release|wait_for_exit|kill`、`elicitation/create`（https://agentclientprotocol.com/protocol/overview）。

### 1.4 初始化与能力协商

- 协议版本是单个整数（只随破坏性变更递增），client 报最新支持版本，agent 不支持则回退自己最新版，谈不拢 client 应断连并告知用户。
- clientCapabilities：`fs.readTextFile/writeTextFile`、`terminal`、`auth.terminal`、`elicitation`（form/url 模式）、`session.configOptions.boolean`。
- agentCapabilities：`loadSession`、`promptCapabilities`（image/audio/embeddedContext）、`mcpCapabilities.http/sse`、`auth.logout`。双方应交换 `clientInfo`/`agentInfo`（name/title/version）。
- 认证：agent 在 initialize 响应里给 `authMethods` 数组（如 terminal 型认证），需要时 client 调 `authenticate`（https://agentclientprotocol.com/protocol/v1/initialization.md）。

### 1.5 会话与 MCP 通路

`session/new` 参数：`cwd`（必须绝对路径）+ `mcpServers`——client 可以直接向 agent 声明 MCP server 让其连接。传输三种：stdio（agent 必须支持；name/command/args/env）、http（需 agent 宣告 `mcpCapabilities.http`）、sse（可选且已被 MCP 规范弃用）（https://agentclientprotocol.com/protocol/v1/session-setup.md）。`session/load` 可恢复会话并回放全部 `session/update`。

### 1.6 工具调用与权限模型

- 工具调用经 `session/update`（`tool_call` / `tool_call_update`）实时上报，字段含 toolCallId、title、kind、status、content、locations、rawInput/rawOutput。
- kind 分类：read/edit/delete/move/search/execute/think/fetch/other；status：pending/in_progress/completed/failed。
- 权限：agent 执行前可发 `session/request_permission`（请求，非通知），带选项列表，用户选择返回 `outcome: "selected"` + optionId，取消返回 `cancelled`。选项 kind 四值：`allow_once` / `allow_always` / `reject_once` / `reject_always`，客户端可依据用户设置自动放行或拒绝（https://agentclientprotocol.com/protocol/v1/tool-calls.md）。

### 1.7 扩展机制与生态

- 扩展点：`_meta` 字段、下划线前缀自定义方法、初始化时宣告自定义能力。
- RFD 流程：值得关注的两条——mcp-over-acp（给 MCP 加 `"acp"` 传输类型，让工具服务器复用 ACP 连接，现状是 proposal，Rust SDK 的 sacp-conductor 已有桥实现，https://agentclientprotocol.com/rfds/mcp-over-acp.md）；acp-agent-registry（agent 注册表，已 stabilized）。
- 官方注册表：github.com/agentclientprotocol/registry，实测 45 个 agent 目录，含 junie、claude-acp、codex-acp、gemini、cursor、devin、github-copilot、kimi、qwen-code、cline 等。registry 的 hourly cron 自动发现 binary 型 agent 仓库的 GA release（非 draft、非 prerelease、纯数字 tag）。
- 官方 SDK：Kotlin（agentclientprotocol/kotlin-sdk，Maven `com.agentclientprotocol:acp:0.1.0-SNAPSHOT`，JVM 端，client/agent 双侧实现）、另有 Java/Python/Rust/TypeScript（https://agentclientprotocol.com/libraries/kotlin.md）。

### 2.4 自家 agent 与第三方 agent 的承载形态

- Junie：以独立 ACP agent 二进制分发（github.com/JetBrains/junie-acp-release），registry manifest id `junie` v3218.3.0，各平台 zip 启动参数 `--acp=true`；EAP/GA staging/GA 三通道，GA 由公共 registry cron 自动拾取。
- Codex：JetBrains org 下有 codex-acp-releases 仓库（README 404，疑似清空）；平台 ACP 插件里预定义 agent id 集合当前仅含 `"codex"`（javap 反编译 `AcpPredefinedAgentIdsKt`，PREDEFINED_IDS 静态初始化仅一个元素）。
- Claude Code：registry 的 `claude-acp` 条目为 `@agentclientprotocol/claude-agent-acp` npm 包，authors 标注 Anthropic + Zed + JetBrains 三家（registry 仓库 claude-acp/agent.json）。另有 Anthropic 自营的 Claude Code [Beta] IDEA 插件（已停更）。
- 形态结论：JetBrains 没有把第三方 agent 做成"平台内置"，而是 AI Assistant 插件提供 AI Chat 容器 + 平台提供目录/启动 API + registry 提供分发，agent 保持 CLI 二进制形态。

## 三、插件开发者可用面（本次调研最重要结论）

### 3.1 "读"面：贡献 agent 与进程启动（com.intellij.platform.acp，262+）

两个公开扩展点（plugin.xml 原文，本地解包）：

```xml
<extensionPoint qualifiedName="com.intellij.platform.acp.agentsCatalogProvider"
    interface="com.intellij.platform.acp.AcpAgentsCatalogProvider" dynamic="true"/>
<extensionPoint qualifiedName="com.intellij.platform.acp.processLauncherProvider"
    interface="com.intellij.platform.acp.AcpProcessLauncherProvider" dynamic="true"/>
```

javap 反编译接口签名（intellij.platform.acp.jar）：

- `AcpAgentsCatalogProvider.agentsFlow(): StateFlow<List<AcpCatalogEntry>>`——第三方插件可向 agent 目录贡献条目；
- `AcpCatalogEntry`：`getId(): AcpAgentId`、`getDisplayName()`、`getOrigin(): AcpAgentOrigin{LOCAL, EXTERNAL_REGISTRY}`、`resolveStartConfig(Project): AcpAgentStartConfig`；
- `AcpAgentStartConfig`：command/baseArgs/acpArgs/env/args/workingDir——即"怎么拉起 agent 进程"的完整描述；
- `AcpProcessLauncherProvider.createLauncher(Project): AcpProcessLauncher`，`AcpProcessLauncher.startProcess(String, AcpAgentStartConfig, Path, CoroutineScope): AcpServerProcessHandler`（挂起函数）；
- `AcpServerProcessHandler`：`getEelProcess()`（Eel 进程 API）、`isRunning()`、`getTermination(): Deferred<AcpProcessTermination>`、`stopServer()`；
- agent id 体系四类：AcpPredefinedAgentId / AcpRegistryAgentId / AcpRemoteAgentId / AcpCustomAgentId（rawId/fullId，前缀常量 CUSTOM_PREFIX/REGISTRY_PREFIX/REMOTE_PREFIX）；
- `AcpRuntimeOverrides.applyTo(AcpAgentStartConfig)` 支持运行时命令覆盖（用户级自定义启动命令）。

用法判断：这套 API 足以让插件"自带一个 ACP agent"（贡献目录 + 启动配置），但聊天 UI、session/update 渲染、权限弹窗都在 AI Assistant。无 AI Assistant 时，插件理论上可拿 AcpProcessLauncher 自己拉进程 + 用官方 Kotlin SDK 实现 client 侧协议——成本不小，非我们场景。

局限：源码不在公开的 intellij-community（GitHub API 列 plugins/ 目录 98 项，无 platform-acp），API 无公开文档，属于"可反编译参考的半公开面"，252/253 是否已存在该插件未验证（见第六节）。

### 3.2 "写"面：把插件工具暴露给 agent（com.intellij.mcpServer，这才是主抓手）

262 内置 `mcpserver` 插件（`plugins/mcpserver/lib/mcpserver.jar`，本地解包 plugin.xml）注册了 7 个扩展点：

```xml
<extensionPoint name="mcpToolsProvider" interface="com.intellij.mcpserver.McpToolsProvider" dynamic="true"/>
<extensionPoint name="mcpToolFilterProvider" interface="com.intellij.mcpserver.McpToolFilterProvider" dynamic="true"/>
<extensionPoint name="mcpToolset" interface="com.intellij.mcpserver.McpToolset" dynamic="true"/>
<extensionPoint name="mcpProjectPathCustomizer" interface="com.intellij.mcpserver.McpProjectPathCustomizer" dynamic="true"/>
<extensionPoint name="mcpManagedSessionSupport" interface="com.intellij.mcpserver.McpManagedSessionSupport" dynamic="true"/>
<extensionPoint name="elicitationProvider" interface="com.intellij.mcpserver.elicitation.McpElicitationProvider" dynamic="true"/>
<extensionPoint name="projectDependenciesProvider" interface="com.intellij.mcpserver.McpProjectDependenciesProvider" dynamic="true"/>
```

工具声明是注解 DSL。官方 README（intellij-community master `plugins/mcp-server/README.md`）开篇即写明这是"canonical reference for plugin authors — both in-tree and downstream (adding tools from another IntelliJ plugin)"。最小可用面（README 1.1 节）：

```kotlin
class HelloToolset : McpToolset {
  @McpTool
  @McpDescription("Greets the caller by name.")
  suspend fun say_hi(name: String = "world"): String = "Hello, $name!"
}
```
```xml
<extensions defaultExtensionNs="com.intellij">
  <mcpServer.mcpToolset implementation="my.plugin.HelloToolset"/>
</extensions>
```

源码行号出证（intellij-community master）：

- `plugins/mcp-server/src/com/intellij/mcpserver/McpTool.kt` L6-28：`interface McpTool { val isUserConfigurable; val descriptor: McpToolDescriptor; suspend fun call(args: JsonObject): McpToolCallResult }`；L36-50 `McpToolCallResult.text()/error()` 工厂；
- `plugins/mcp-server/src/com/intellij/mcpserver/McpToolset.kt` L12-33：KDoc 全套编写约定（@McpTool/@McpDescription、参数须可序列化、McpExpectedError 表达业务错误、CoroutineContext.project 拿 Project）；L39-50 完整示例；README 2.3 节三个生命周期钩子 `isEnabled()/isExperimental()/alwaysIncluded()`，其中 isExperimental 默认 true，意味着新工具集要显式覆盖为 false 才会进稳定集；
- 注解本体（本地 262 jar 反编译）：`annotations.McpTool(name, title)`、`annotations.McpDescription(description)`、`annotations.McpToolHints(readOnlyHint, destructiveHint, idempotentHint, openWorldHint)`，hint 为三值枚举 UNSPECIFIED/TRUE/FALSE——正是 MCP ToolAnnotations 标准的 IDEA 实现。

版本兼容实测（决定 N-12 双轨策略）：

- 253 分支 Marketplace 包 253.28294.336（updateId 908810，下载解包）：`idea-version since-build="253.28294" until-build="253.*"`，EP 名与 262 相同（mcpToolset/mcpToolsProvider，接口同为 com.intellij.mcpserver.\*）。
- 243~253 通用线 1.0.30（updateId 740652，下载解包）：`since-build="242" until-build="253.*"`，但 EP 完全不同——`<extensionPoint name="mcpTool" interface="org.jetbrains.mcpserverplugin.McpTool"/>`，HTTP handler 形态（`httpRequestHandler implementation="org.jetbrains.ide.mcp.MCPService"`），连接外部 client 需装 mcp-proxy。即老版本有第三方注册面但接口包名、形态都不同。
- 262 内置版依赖仅 intellij.libraries.\* 与 intellij.platform.compose，不依赖 AI Assistant——干净 IDE 装 MCP Server 即可用，无需任何 AI 订阅。

工具过滤与权限（plugin.xml 出证）：`mcp.server.tools.filter` registry key（语法 `-*,+com.intellij.mcpserver.toolsets.general.*,-*.read_file`）、DisallowList/Settings/RegistryKey 四个 mcpToolFilterProvider 实现、Settings 界面 McpToolFilterConfigurable、elicitationProvider 提供 server 向 IDE 用户询问的通路。外部 client 的检测与自动写配置在 `McpClient.kt`（intellij-community master 同路径 clients/ 目录，L59 起 McpClient 抽象类含 configPath/sseUrl/streamableHttpUrl/mcpServersKey），通知 id `mcp.client.detected` / `mcp.client.autoconfigured`（plugin.xml notificationGroup）——IDE 会检测 Claude Code/Cursor/VSCode 等的配置并自动把 IDE MCP server 写进去。

### 3.3 ACP 场景下 agent 的 MCP 配置（路线 A 的可行性）

官方帮助文档（jetbrains.com/help/ai-assistant/acp.html，2026-09-14 实测可访问）：

- 手工加 agent：AI Chat 右上 Add Custom Agent，写 `~/.jetbrains/acp.json`，格式 `{"default_mcp_settings": {}, "agent_servers": {"名字": {"command": "/path/to/agent", "args": ["acp"], "env": {...}}}}`；
- registry 安装：Settings | Tools | AI Assistant | Agents 一键装，自动准备 Node/Python 运行时；ACP agent 不需要 JetBrains AI 订阅；不支持 WSL；
- MCP 两个开关（决定性）：`use_custom_mcp`（默认 true）把用户配置的 MCP servers 传给 agent；`use_idea_mcp`（默认 false）把 IDE 内置 MCP server 的工具暴露给 ACP agent，可用 `idea_mcp_allowed_tools` 收敛为白名单。文档明言 IDE 不会静默共享 MCP 工具。

协议层佐证：`session/new` 本身接受 client 传入的 `mcpServers`（stdio 为 agent 必须支持的传输），即 IDE 侧有能力把任意 MCP server 塞进 ACP agent 会话。

### 3.4 无公开"拦截权限请求"EP

`session/request_permission` 的处理在 AI Assistant 插件内部（本地未装、无源码），platform-acp-plugin 未提供相关 EP。第三方插件想参与权限决策目前无公开机制（未验证项）。

## 四、平台原生 MCP / LLM 能力盘点

### 4.1 MCP：server 侧已是平台一等公民，client 侧归 AI Assistant

- server 侧（见 3.2）：stdio runner（mcpserver.stdio 模块、`McpStdioRunnerClasspath`、`createStdioMcpServerCommandLine`）+ ktor SSE/Streamable HTTP（lib 目录有 ktor-server-sse-jvm.jar）双通道，状态栏 widget、Tools 菜单 Show MCP Tools、headless 启动器（appStarter id="mcpServer"）、OTel trace（registry `mcp.server.ot.trace`）。
- 2025.2 起内置（252 分支 Marketplace 版本自 2025-06-13 出现，与"2025.2 EAP 带 MCP"公告吻合），18M 下载量说明外部 agent ↔ IDE 工具这条链路已是主流用法。
- client 侧（IDE 作为 MCP 客户端消费外部 server）：由 AI Assistant 提供（消费面设置 UI；help 站 MCP 文档页本次 404，未取得第一手，见第六节）。注意 mcpserver 插件 `clients/` 包不是 MCP client，而是"给外部 agent 写 MCP 配置"的工具。

### 4.2 LLM API：无公开可用面

三个独立证据：

1. 干净 262 平台全量搜证：`lib/`、`plugins/*/lib`、`platform-main.jar` 内 grep `com.intellij.core.ai` 零命中，无任何 intellij.platform.ai/llm 模块 jar——LLM 能力不随平台分发。
2. SDK 文档 llms.txt（plugins.jetbrains.com/docs/intellij/llms.txt）全文无任何 AI/LLM/MCP/ACP 页面——第三方插件开发者的公开文档体系里没有 LLM API。
3. 检索无 2025-2026 年间"LLM API 开放"的官方公告；相反 2026-06 Marketplace 出现 15 个窃取 AI provider API key 的恶意插件事件（blog.jetbrains.com/platform/2026/06/marketplace-ecosystem-security-update-malicious-ai-plugins/），JetBrains 对第三方插件碰 LLM key 只会更谨慎。

结论：AI Assistant 的模型（用户登录 JetBrains 账号免 key）不构成第三方插件可依赖的 API；AI Assistant 的"自定义模型"（OpenAI 兼容/Ollama，help: use-custom-models）是终端用户功能而非插件 API。

## 五、与 N-12 / N-14 的衔接：复用 / ride / 吸收三路线对比

### 5.1 路线 A「复用」：外部 agent 经 ACP 跑在 IDEA，agent 用自己的 MCP 配置连我们的 server

- 事实基础：Claude Code 等 agent 保持 CLI 形态，读自己的 MCP 配置（.mcp.json / claude mcp add）；ACP 宿主（AI Assistant）不会清掉这些配置，反而 `use_custom_mcp` 默认 true 会把用户配置的 MCP servers 传给 agent；协议层 session/new 也支持 stdio mcpServers。
- 结论：可行且零 IDE 版本门槛，甚至不需要 IDE 参与（agent 在终端里跑也一样连）。但每家 agent 配置格式不同、要用户手工配置，与 N-12"零弹窗零配置"哲学冲突。
- 可取的增量：做一个低摩擦"接入向导"动作——用户确认后把 mpsv stdio 配置写入 `~/.claude.json`（或提示用户在 AI Assistant MCP 设置里添加），并支持 `~/.jetbrains/acp.json` 的 default_mcp_settings 说明文档。属于锦上添花，不作主轨。

### 5.2 路线 B「ride 平台」：工具注册进平台 MCP Server（建议改为主轨）

- 事实基础：见 3.2。`mcpToolset` EP + 注解 DSL 官方明文支持下游插件；253/262 内置、243 有 1.0.30 旧 EP 可兼容；自动获得 IDE MCP server 的全部承载（端口/传输/状态栏/外部 client 自动配置/工具过滤设置），我们的工具会同时出现在 AI Assistant、Junie、经 `use_idea_mcp` 打开的 ACP agent、外部 Claude Code/Cursor 等所有 MCP client 面前。
- 对 N-12 三工具的映射：`render_sql` / `schema_context` / `explain` 各写一个 @McpTool 方法（或合成一个 SqlVisualizerToolset），`@McpToolHints(readOnlyHint=TRUE, destructiveHint=FALSE, idempotentHint=TRUE)` 即平台原生的"只读"声明；默认只读白名单由 `idea_mcp_allowed_tools` + `mcp.server.tools.filter` 承担，零弹窗目标不变。
- 代价与风险：平台插件为 optional 依赖（`<depends optional="true" config-file="...">com.intellij.mcpServer</depends>`），未装 MCP Server 的环境（如 243 未装 1.0.30）自动降级；老 1.0.30 轨需要一套独立的 `org.jetbrains.mcpserverplugin.McpTool` 适配类（接口不同、无注解 DSL，手写 descriptor），建议仅 243 走这条或干脆 243 不支持（见修订建议）；EP 属平台插件公开面但无 SDK 文档，需跟随版本回归测试。
- 与自建 stdio 的关系：主轨切到平台体系后，"插件内嵌 stdio MCP server"降级为可选兜底（面向不装 MCP Server 插件的老环境或 IDE 之外的场景），一期可直接砍掉，二期再评估。

### 5.3 路线 C「吸收设计」：权限模型与会话语义

- ACP 四值权限（allow_once/allow_always/reject_once/reject_always）与 MCP ToolAnnotations 双轨并存：N-12 只读三工具用 `@McpToolHints(readOnlyHint=TRUE)` 声明；将来若加"写"类工具（如生成文件落盘），吸收 allow_always 白名单设计（首次调用确认一次并记忆），不做每调用弹窗。
- 平台已有 server→IDE 询问通路（elicitationProvider EP），未来需要交互确认时 ride 它，不自建弹窗。
- ACP 的会话/模式/模型选择机制与 N-12 无关（我们无 agent 会话），仅作背景知识。

### 5.4 修订建议汇总

- N-12 修订：主轨从"插件内嵌 stdio MCP server"改为"注册进平台 MCP Server 体系"。262（以及 252/253）用 `mcpServer.mcpToolset` + @McpTool 注解；243 用 Marketplace MCP Server 1.0.30 的 `mcpServer.mcpTool` 旧 EP 写一套薄适配（或明确 243 不提供 MCP 面，写进发行说明）。自建 stdio launcher 从一期范围移除。三工具名保留 mpsv\_ 前缀（命名空间天然隔离，不与平台 toolsets 冲突）。新增强化点：向 README 补"外部 agent 接入指南"（claude mcp add 与 AI Assistant use_idea_mcp 两种姿势）。
- N-14 修订："ride 262 平台自带 LLM API（用户免配 key）"判断被证伪，从方案中删除。保留 OpenAI 兼容单路径 + PasswordSafe 存 key 作为主路径；Platform LLM API 保持观察（等它从 limited access 转公开，短中期不指望）。不建议经 ACP 借外部 agent 做 SQL 理解——渲染/EXPLAIN 是确定性任务，不需要 LLM，N-14 的 LLM 只服务自然语言→SQL 场景。
