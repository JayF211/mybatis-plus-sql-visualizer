# 插件 IDEA 性能影响深度分析（调研报告）

**创建时间**：2026-09-15
**文档定位**：本系列第四轮（前三轮：`docs/性能分析/20260902-0054`、`docs/性能分析/20260910-0345`、`docs/调研报告/20260914-0338`）。回答同一个问题——SQL Visualizer 会不会拖慢 IDEA。本轮性质是**复查 + 增量**：上一轮审计锚点 c4c5f02（2026-09-14 03:38），此后 master 又前进 61 个提交（现行 0844501），src/main 变更 35 个文件、+2725/-721 行，集中在反馈链路（T-FeedbackErr 三轮 + T-FeedbackBatch 批量限流规避）、执行链路（T-ExecSlowOps 线程化、T-ExplainFirstNative/T-ExplainDbl 执行计划）、预览链路（T-PreviewExecDs、T-ListPreviewCopy）。本轮先逐项复核上轮结论是否仍然成立，再对新增代码做同等深度审读，全部结论带 文件:行 出证，行号以 2026-09-15 工作树为准。

## 1. 总结论

**维持并强化上轮结论：默认配置下插件对 IDEA 性能影响可忽略；这 61 个新提交无一引入常驻开销或阻塞路径，反而清退了一条反查搜索路径（WrapperSearchService 整文件删除）。** 新增代码审读后得 1 个中低危发现（错误提取每拍全文档拷贝）与 5 个低危打磨项（§5），均非常态高成本，无一构成「会带来性能问题」级别的缺陷。

支撑结论的四个增量事实：

1. **常驻面零变化**：plugin.xml 本轮唯一改动是根元素加官网 url 属性，扩展点数量与实现类一个未动；13 个 gutter provider 与 4 个 completion contributor 的快速路径红线依旧守住（§3）。
2. **新常驻成本只有一个，且是懒加载 + 闲时零唤醒**：反馈错峰调度器 PendingReportScheduler 是应用级服务，但只在用户批量上报成功后才首次实例化，定时为一次性延时任务（非周期轮询），daemon 线程闲时挂在 DelayQueue 上零 CPU（§4.1）。
3. **线程纪律系统性收紧**：T-ExecSlowOps 把方言 setMapping 等平台重操作归位 EDT、慢 IO 归位后台线程，两段式单向等待（BGT 等 EDT）带 2s 封顶，EDT 永不反向阻塞（§4.2）。
4. **历史热点持续收敛**：上轮低危发现点 2 的预热等待预算从秒级砍到 60ms；逐行热路径的重放守卫、Method 缓存、退避轮询等治理痕迹全部原样在位（§3）。

## 4. 新增子系统审计

### 4.1 反馈链路（T-FeedbackErr ×3 + T-FeedbackBatch，约 +1300 行）

- **PendingReportScheduler：懒加载、一次性延时、闲时零唤醒。** 应用级 `@Service(Service.Level.APP)`，唯一触发点是 BatchSubmitter 首发成功后 `scheduleQuietly`（`BatchSubmitter.kt:40-41`）；`executor.schedule` 单发 720s 延时（`PendingReportScheduler.kt:39`），全包无 scheduleAtFixedRate/WithFixedDelay；专用 daemon 单线程 `sql-visualizer-feedback-queue`（`:24-26`）。空闲时不实例化、实例化后闲时挂 DelayQueue 零 CPU。两处残留见 §5.5。
- **网络全后台。** 常规提交 `executeOnPooledThread`（`FeedbackReporting.kt:41`）+ `invokeLater` 回 EDT；对话框 OK 键在 EDT 只组装不触网；错峰补发在调度器自身线程。连接/读超时各 10s（`FeedbackApi.kt:251-252`）。响应体读取无字节数上限（§5.2）。
- **ErrorReportDialog 无定时器无轮询**：提交流转纯回调（beginSubmitting → 异步 finishSubmitting），重试是用户再点按钮；全文件 grep 无 Timer/sleep/invokeAndWait；监听器全挂对话框自有组件，随窗 GC。
- **错误风暴不放大**：errorReportSubmitter 扩展点只在用户于 Internal Errors 显式点「报告」时回调；先 SHA-256 指纹（≤5 业务帧）查 LRU（128 条，`ErrorFingerprint.kt:16`），命中直接短路不弹框不触网；无 MessagePool 监听、无自动上报。
- **附件构建终值有界、组装瞬时无界**：单份附件 `.take(60_000)` 截断（`ErrorReportComposer.kt:124`），但截断在全文 append 之后且逐条不先截断，组装又发生在 EDT（§5.3）。

**评级：低。** 唯一持续后台活动（错峰补发）是 daemon 线程 + 内存队列（应用退出即弃），空闲零成本。

### 4.3 预览链路（SqlPreviewPanel +142、SqlPreviewService +17）

- **预热等待**：EDT sleep-poll 形态保留但预算 60ms（§3.2），预热线程侧 VFS refresh 失败走 100/200/300ms 后台退避（`:410`），不占 EDT。
- **磁盘生命周期**：exec 临时文件固定 `<project>/.idea/sql-visualizer/exec/mpsql-exec.sql` 覆盖写不膨胀（`:3048-3054`）；预览文件在 `releaseEditor` 与 dispose 时删除（`:1957`、`:419-421`），预热中途取消也补删。
- **内存缓存**：`cachedTempPsiFile` 为进程级单槽 `@Volatile`（`:86`），消费时惰性校验 vf 有效性 + 项目绑定（跨项目拒绝），项目关闭后最多残留一个项目的强引用至下次消费被顶掉——有界但非即时回收（§5.4）。
- **rehost 复查**：800ms 单发延迟复查（`:968`、`:3088`），非轮询。
- **probeConsoleValidity**：每探 4 次反射 + Disposer 检查 + O(1) 服务查找，不读文档不碰 PSI；console prepare 一次，点击执行链不再触发。

**评级：低。**

## 5. 发现点与建议（1 中低 + 5 低危，按优先级）

> 六项已立项收敛：`docs/开发计划/20260915-0820-T-PerfSweep2-第四轮性能复查发现点收敛-开发计划.md`（T-PerfSweep2-01~06）。

1. **【中低】extractConsoleError 每拍全文档拷贝**（`DataSourceSelector.kt:578`）：`doc.getText()` 先整串拷贝再按 baseline substring 截断；600ms 结果刷新定时器（`:776`）与 400ms 结果 Tab 重试定时器（`:2695`，dumb 态最长 100 拍）**每拍**调用。控制台 history 随长会话涨大后，每拍在 EDT 分配 O(全史) 字符串，是本轮新增链路上唯一可感知的最坏情形。建议：改 `getText(baseline, length-baseline)` 片段读取；顺带给 `:2708-2714` 的 debug 日志列表构建加 `LOG.isDebugEnabled` 守卫（当前 debug 关闭也照建）。
2. **【低】响应体读取无上限**（`FeedbackApi.kt:300,302`）：`readBytes()` 与 gzip 解压输出均无字节数上限，仅 10s 超时限时不限量；对端为自家站点 + CDN，属低概率但真实的无界内存面（拦截页/gzip 炸弹）。建议包一层有界 InputStream（1~2MB 封顶），gzip 解压同样限输出。
3. **【低】批量附件 EDT 组装瞬时无界**（`ErrorReportComposer.kt:118-124`、`BatchSubmitter.kt:36`）：`buildString` 先全文 append 全部堆栈、末尾才 `take(60_000)`，逐条不先截断且条数不限附件节；20 条 × 大堆栈病态场景在 EDT 瞬时产生数十 MB 字符操作。典型量级毫秒级，病态时弹窗打开有可感卡顿窗。建议：append 前对每条堆栈先做 per-item 截断（如 8k），或把组装挪到 pooled thread（组装完再交 `executeOnPooledThread` 现有链）。
4. **【低】cachedTempPsiFile 无项目关闭钩子**（`DataSourceSelector.kt:86`）：项目关闭后残留一个项目的 vf+PsiFile 强引用，靠 `isCacheUsable` 惰性校验兜底（下次消费前校验/顶掉），有界但非即时回收。T-PreviewExecDs 已把它从跨项目泄漏收敛为单槽残留，建议再补 ProjectManagerListener/Disposer 置空即闭环。
5. **【低】反馈调度器 drain 占线程 + 静默拒新**（`PendingReportScheduler.kt:38,62-67`）：drain 期间 `Thread.sleep(720s)` 逐条间隔占用唯一调度线程（daemon，零 CPU，性能无害），且此时新 enqueue 被静默丢弃（`:38`）。副作用是内存上界天然受限，但语义上「后续批次被丢」值得留意。建议：改为「发完一条再 schedule 下一条」，既不占线程也让新批次能入队；顺带可在应用 Disposable 注册 shutdown 作规范化收尾。
6. **【文档微修】** plugin.xml:204「开关默认开」注释与 `PluginSettings.kt:151` 默认 false 漂移——上轮已提，本轮仍未修，建议顺手改掉。

上述均不动摇总结论：1 是有拍数上限的最坏情形成本，2~5 是低概率/低量级长尾，6 是注释。
