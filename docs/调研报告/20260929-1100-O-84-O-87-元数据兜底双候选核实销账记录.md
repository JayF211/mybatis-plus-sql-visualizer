## 二、我方现状核实

先给架构层结论，它是两条候选的共同前提：

**我方元数据链不发任何 catalog/system view 查询，元数据唯一来源是 DBN（IntelliJ database 插件）内省出的 DasModel。** 全仓 `src/main` grep `DatabaseMetaData`/`getColumns(`/`getTables(`/`ALL_TAB_COLUMNS`/`information_schema`/`current_schema`/`pg_catalog`/`sys_catalog`，命中全部落在注释、SQL 关键字字典（`SqlKeywords.kt:181/291`）或 DBN API 调用（`JoinVirtualFkProvider.kt:143` 的 `DasUtil.getColumns`），无一处自建 JDBC 元数据查询。取数实现两条：补全/校正链的反射遍历（`DatabaseSchemaResolver.reflectTraversal`，`src/main/kotlin/cn/song/mybatisplus/visualizer/ui/highlight/DatabaseSchemaResolver.kt:657-731`）与 MCP `sqlv_schema_context` 的自建索引（`McpSchemaContextService.scanSource`，`src/main/kotlin/cn/song/mybatisplus/visualizer/mcp/McpSchemaContextService.kt:192-205`）。

这条前提意味着：DBX #111/#120 要防的形态——「我方构造的 schema 限定 catalog 查询在达梦空 schema 下失败或空结果后不降级」——在我方**没有可发生的代码位置**：schema 解析这件事整个被 DBN 承担，我方消费的是它的结果。

### O-87 逐点核实

提案形态拆两半：①「失败**或空结果**均继续降级」的不卡死语义；②「精确→兼容→information_schema」的多来源层级。

| 拆解项 | 我方现状 | 出处（代码可判） |
|---|---|---|
| ①失败不卡死 | 多数据源循环逐个尝试，单源「查不了」不短路后续源、不写负缓存 | `DatabaseSchemaResolver.kt:483-519`（循环 + bail continue）、`:511-514` 注释明示语义 |
| ①空结果继续降级 | 单源确认没有 → 负缓存记 TTL 后**继续看下一个数据源**；全落空时调用方逐维度回落实体注释/推断值 | `DatabaseSchemaResolver.kt:518`（stampNegative 后循环继续）、`:520-529`；`ColumnNameCalibrator.kt:39-40`（降级等价断言：数据源不可用一律原样返回） |
| ①空结果的后台自愈 | 列名校正链未命中投递一次后台预热（冷却窗口 + 在途上限双闸），后续调用取到真值 | `ColumnNameCalibrator.kt:289-333` |
| ②多层级「仲裁」形态 | 列名校正器内部已是三级分层判定：精确命中 → 归一化唯一 → fieldName 归一化唯一，任一步空/歧义即停不改写（宁缺不错） | `ColumnNameCalibrator.kt:228-245`（resolveName 步 1~4）、`:223-226`（歧义即停反例） |
| ②「information_schema」第二来源层 | 不存在，也不该存在：DBN 的 DasModel 本身就是数据库真实内省产物（其内部已含各方言到系统视图的映射），我方再自建 JDBC information_schema 通道等于复制 DBN 的本职，且需按方言写 catalog SQL（达梦要兼容视图），远超小件 | `DatabaseSchemaResolver.kt:9-28`（架构注释）；无任何自建 catalog 查询（本节前提 grep） |

结论：**b**。提案的语义核心（失败/空结果不卡死、分层仲裁、空结果后台自愈）在我方列名校正/补全链逐点已有；提案的字面形态（自建 information_schema 兜底层）插入的前提——我方直连查 catalog——不存在，若强行补是新增一条元数据通道的架构面改动，非小件且无已知真实故障驱动。与 O-84 同理，真机上 DBN 内省对国产库的覆盖质量是唯一残留风险，已由 SmokeTest 通道承接验证。
