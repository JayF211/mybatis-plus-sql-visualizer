# IDEA 性能影响深度分析（2026-09-10 复查）

> 分析基线：2026-09-10，master 299607e（v2026.9.9 后），距上一版《20260902-0054-IDEA性能影响-性能分析》（基线 5cb9190）已落 117 个提交，src/main 241 个源文件全量静态走查。
> 方法：四路并行核查——捕捉链路与日志渲染、daemon 与 PSI 缓存、EDT 与 UI 链路、启动注册与内存驻留。上一版结论逐项复核，期间新增代码（重放守卫、单击预览、行号、rehost 治理等）重点排查。结论均带文件:行号证据，行号为当前工作区快照，后续以符号定位为准。

## 一、总体结论

上一版点名的风险已全部兑现修复：捕捉态常驻 EDT 轮询从每秒 10 拍降到 500ms 起步指数退避封顶 2s，每拍反射查找与组件树遍历经缓存短路压制，逐行配置同步消灭，日志列表 16 秒 EDT 冻结根治。「默认配置零常驻开销」的结论维持不变——两个启动活动默认关、SqlLogManager 是懒服务，不开启捕捉则整个 log 链路一行代码都不跑。

但整体态势发生了两个变化。

其一，09-05 立项的 M54 插件性能红线全面治理（24 任务，docs/开发计划/20260905-1024）在 master 上没有一项以 `fix(perf)` 提交形式落地：计划分支 perf/redline-hardening 不存在，工作区无 T-Perf 提交痕迹。其中 6 个 log 包点位借 T-LogListFreeze04 的日志管线移植搭车进了 master，若干半项被旁支缺陷修复（T-DsCover/T-ExecCopyFix/T-PreviewFlash/T-RefreshDbSteal）顺带覆盖，其余 15 项原样留在 master——gutter daemon resolve、PSI 缓存无界、历史文件 EDT 全量读、参数击键无防抖、schema 全量遍历这些原审查发现全部仍然成立。

其二，期间新代码引入了三个新热点：T-PreviewFlash 的重放守卫在捕捉热路径上做了每行全文档 getText 拷贝（本版新发现的最高优先级项）；CriteriaQuery gutter 成为 daemon 热路径上第二个无预筛 provider；函数体内 Regex 从 17 处涨到 42 处。

风险分级一览：

| 级别 | 组件 | 现象 | 触发条件 |
|------|------|------|----------|

## 三、当前遗留风险

### P1-1 daemon 热路径上的 resolve（T-Perf-02 未落地，且新增一处违规）

daemon 高亮 pass 对打开文件的每个元素回调全部 13 个 lineMarkerProvider（主文件 12 + Kotlin 1，较上一版 8→13）。12 个中 7 个仍是干净的 O(1) 判定，但以下几处把 PSI resolve 与代码块扫描放进了 daemon 热路径：

- CustomDaoHqlGutterLineMarkerProvider.kt:55 对每个方法名 identifier 无预筛直调 locate；CustomDaoHqlLocator.kt:229-230 判定顺序是先跑 4 条 HQL 正则再查 O(1) 的 qualifier 名；PreviewReceiverResolver.kt:47 的 classify 因 Kotlin 实参急切求值，`qualifier.type` 在变量名启发（:75-81）来得及短路之前就已触发引用 resolve。三者叠加，daemon 每趟对项目内每个方法调用执行一遍正则 + resolve。
- CriteriaQueryGutterLineMarkerProvider（本轮新增核查发现）：每个方法名 identifier 直调 locate 全代码块扫描，CriteriaQueryLocator.kt:275 有 `.resolve()`；:159/261/408 函数体内 `setOf(...)` 每叶子分配。
- SqlGutterLineMarkerProvider.kt:34-35 开关判断在锚点判定之后——用户关闭 showGutterIcon 后每个叶子仍先跑完整判定，性能兜底开关失去意义。
- 轻微违规两处：JdbcTemplateSqlGutter 与 StringSqlMethodGutter（后者每方法定义全 body 扫描，有 200k 字符护栏，属已知权衡）。
- 残留分配：HqlGutterLineMarkerProvider.kt:46 与 CustomDaoHqlGutterLineMarkerProvider.kt:53 每叶子新分配 `setOf(...)`。

M54 的修复方案（名字预筛前置、判定顺序反转、classify 按 modificationStamp 缓存）依然适用，未实施。

### P1-2 重放守卫的逐行全文档拷贝（T-PreviewFlash 引入，本轮新发现）

T-PreviewFlash 为修预览闪烁给捕捉链挂了重放守卫（ConsoleReplayGuard），但集成点写法让守卫成本落在了逐行热路径上。SqlLogConsoleBridge.kt:325-333 的 filter 闭包对每行输出调用：

```kotlin
context.replayGuard.decide(endOffset, stampReader(), line, context.line0Reader?.invoke())
```

Kotlin 实参急切求值：`context.line0Reader?.invoke()` 作为实参在每行无条件执行，而它（:374-378）做的是 `doc.getText()`——整个控制台文档的字符串拷贝——再 `lineSequence().firstOrNull()` 取首行。ConsoleReplayGuard.decide:52-70 只在「endOffset 落在 watermark 之前且 stamp 变化」这个罕见的重放场景才需要行 0 文本。同时 `stampReader()`（:368-372）每行重新 `getMethod("getModificationStamp")`，未经 T-LogPerf-02 建立的 Method 缓存。

也就是说，上一版消灭的「逐行固定成本」以一种新形态回来了：捕捉态下每行输出付一次 O(文档大小) 拷贝 + 一次反射查找。长会话控制台输出数十 MB 时，这一项会比它修掉的闪烁问题更重。修复方向小而明确：decide 的行 0 参数改收惰性 lambda（仅在需要时求值）、stampReader 走既有 methodCache、行 0 文本按 stamp 失效缓存。

### P1-3 历史 tab EDT 全量读（T-Perf-05 未落地）

HistorySqlLogPanel 的 refresh（:204-231）在 EDT 对目录内每个 .sql 文件逐行全量扫描计数（SqlLogFileReader.countInFile），选中文件再 `readText()` 整读（SqlLogFileReader.kt:48）；触发点全在 EDT：构造即 refresh（:115-118）、刷新按钮（:82）、点文件（:191-199）。自动保存单文件滚动阈值 100MB（SqlLogAutoSaver.kt:31），长期开启必然长出大文件，届时切历史 tab 即冻结。该面板的渲染器已片段化（T-LogListFreeze04 同款），此子项无碍。

### P1-4 SqlInputEditor EDT 硬抛（T-Perf-07 未落地）

SqlInputEditor.kt:66-67 在字段初始化链（构造点 SqlToJavaPanel.kt:97）EDT 裸调 `PsiFileFactory.createFileFromText`，全文件无 ReadAction 包装。262 平台首次打开「SQL → Java」tab 即硬抛。同类的 SqlPreviewPanel 与 JavaCodeFormatter 均已包 ReadAction，唯独此处遗漏。这一项同时是崩溃项，治理收益最高。

### P2-5 补全与 JOIN 预览的 schema 全量遍历（T-Perf-09 未落地，仅 Ultimate）

DatabaseSchemaResolver.kt:62-66 在 EDT ReadAction 内对每个数据源把 `DasModel.traverser()` 全量物化成 List（:136-142）再筛一张表，无任何 (dataSource, tableName) 缓存。消费方两处高频直调：补全 contributor 每次触发（SqlCompletionContributor.kt:127-128，autopopup 下每标识符字符都可能触发）与 JOIN 预览每表一次（DiagramSchemaEnricher.kt:26）。大库冷缓存时 EDT 冻结可达秒级。附带噪音：每次补全 10~11 条 LOG.info、每次 schema 扫描 2~3 条，全未降 debug。

### P2-6 参数击键路径无防抖（T-Perf-04 未落地）

SqlPreviewPanel 的 renderSql（:1053）同步直调，普通参数/批量列/条件值三路 DocumentListener 每击键触发（:1930-1934，:1688-1692，:1807-1811），foreach 路径每击键两次全量渲染（:1913，:1922）。默认开启格式化时每击键 `SqlFormatter.format` + WriteCommandAction 全文 setText（:1328，:1344）触发全文重分词。detectInClauseParams（:2216-2233）对每个 `?` 复制并大写化整个前缀，O(L×P)。Ognl.kt:75-79 每次求值重新 parse 无表达式缓存。大 SQL + 多参数场景逐键可感知卡顿。

## 四、内存驻留

一项重要更正：变更记录 2026-09-05 曾宣称 T-Perf-19「收藏上限」交付，git diff dev..HEAD 实证 `MAX_FAVORITES=500` 与 evictFavoritesIfNeeded 只存在于 dev 分支（dev SqlHistoryManager.kt:67-73,212），master 的 favoriteEntries（SqlHistoryManager.kt:35，add :56-57）仍无上限不淘汰。T-Perf-19 实际只有指纹化半项进了 master。

无界持有清单（按严重度）：

1. favoriteEntries 无上限（持久化 + 内存双膨胀，dev 已修未移植）。
2. WrapperCache / EntityResolver / JpaEntityResolver 三族缓存无上限且键持 PsiFile 强引用（见 P2-9）。
3. dedupeCounts 键已改 FNV-1a 64 位指纹（LogSqlModels.kt:76,87-94），泄漏面从每条数 KB SQL 原文缩到 16 字符 hex，但条目淘汰后计数仍不随移除、无上限（SqlLogEntryBuffer.kt:85,168-178），十万级去重会话可累积百万级键。

有界缓存运转正常：ParamHistoryCache LRU 50 键为表名+SHA256 前缀；SqlPerfAnalyzer LRU 200（键为 SQL 原文，最坏 MB 级，可接受）；JoinDiagramSnapshotRegistry 32 上限；bridge methodCache 与 descriptorConsoleCache（64 上限 detach 清空）；JoinFkRegistry 无上限但条目小且有 clear 兜底。

生命周期面干净：全项目 6 处 messageBus.connect 全部绑定 Disposable 无一处裸连；SqlLogPanel/SqlPreviewDialog/图编辑器的 Disposer 注册对称；无裸线程、无自建线程池，后台任务全部走平台 pooled 池（15 处 executeOnPooledThread + 5 处 Task.Backgroundable）。

## 五、启动与常驻足迹

plugin.xml 较上一版的变化：lineMarkerProvider 主文件 9→12（新增 JdbcTemplateSqlGutter、NamedQueryGutter、StringSqlMethodGutter，daemon 每 Java 文件多 3 次 O(1) 回调），Kotlin 侧 1 不变；新增可选 depends `com.intellij.diagram` 与两个被动 EP（database.modelRelationProvider → JoinVirtualFkProvider、diagram.Provider → SqlJoinDiagramProvider），Ultimate 下仅打开图时才回调。仍无 Annotator、ExternalAnnotator 与任何索引/stub 注册，不参与索引构建。

默认配置下的常驻足迹为零：两个 postStartupActivity（autoCheckUpdate 与 logAutoCaptureOnStart 均默认关）各做一次设置读取即返回；SqlLogManager 是懒项目服务，未开启捕捉前不实例化，其 EXECUTION_TOPIC 订阅（RunConfigurationProcessListener，自动监听四轮改造新增）也不存在。无常驻线程、无常驻定时器、无常驻监听。

开启捕捉后的常驻开销收敛为一个 EDT swing Timer（500ms 起步指数退避封顶 2s，检测到主控制台切 2s 常规）加挂载控制台上的逐行 Filter。自动监听「被动模式」（processListenerActive）开启设置不再立即 armed、不挂轮询，由 Run 事件驱动——上一版「点过捕捉整个会话 10Hz 常驻」的形态已彻底消失。执行期间的 4 个 transient Timer（600ms/1000ms/400ms 结果轮询与 250ms 设置页高亮）均有代际守卫或拍数上限自停。T-ClickPreview 的 300ms 单击双击区分定时器为一次性（isRepeats=false），每列表实例一个、dispose 停表；T-LogRowNumber 纯序号字段零定时器。

T-RefreshDbSteal 的监听治理已交付且无新增轮询：rehost 监听命名引用 + attach 先移旧 + dispose/detach 显式解绑（SqlPreviewPanel.kt:208,686-761），所有权卫队 consoleAttachedToMe 判定（:650-653），去抖兜底为单发 Timer。

## 七、优化建议（按收益排序）

1. 重放守卫惰性化（P1-2）：decide 行 0 参数改惰性 lambda、stampReader 走 methodCache、行 0 按 stamp 缓存。改动约十行，直接消灭当前捕捉热路径上最大单项成本。
2. M54 第一波 P0 收尾：SqlInputEditor 包 ReadAction（P1-4，兼崩溃修复）、历史 tab 读取后台化（P1-3）、CustomDaoHql/CriteriaQuery gutter 预筛（P1-1）。四项都有精确行号与验收标准在案。
3. dev→master 同步两个已修半项：favorites 500 上限（T-Perf-19）与 attachedConsoles 并发（T-Perf-22），纯移植零设计成本。
4. AutoSaver 批量写（T-Perf-12 余项）：专用执行器 + 去逐条 flush，日志风暴场景收益明显。
5. 其余按 M54 二、三、四波原序推进（T-Perf-04/09 与 T-Perf-18 优先级最高，分别是交互卡顿与长会话内存的主因）。

## 八、验证方法

沿上一版建议：沙盒 attach JFR 或 VisualVM 观察 EDT 事件队列；IDEA 自带 Performance Watcher（idea.log 中 UI freeze / Slow operations 报告）直接量化。针对本版新增项的定向场景：开启捕捉后跑长时间输出应用（控制台累积数十 MB），对比守卫修复前后控制台 flush 速率与 EDT 占用；大 schema 数据源下连续触发补全观察第一次与第二次延迟差（验证 T-Perf-09 缓存收益）；.idea 历史目录放置 100MB 单文件切历史 tab 测冻结时长（T-Perf-05 验收线 500ms）。

M54 计划的整体验收红线（200 条 SQL 流式灌入不掉帧、50KB 动态 SQL 逐键 <50ms、IDE Freezes 报告无本插件新增记录）仍可作为后续每波交付的例行回归项。
