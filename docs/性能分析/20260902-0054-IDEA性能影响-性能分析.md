# IDEA 性能影响深度分析

> 分析基线：2026-09-02，master 分支 8f186cb（v2026.9.2 后），源码 215 个文件全量静态走查。
> 方法：以「常驻开销」为主线，逐项核查 plugin.xml 注册点、定时器、监听器、线程模型与内存驻留，定位会持续占用 EDT 或内存的代码路径。

## 一、总体结论

默认配置下，本插件对 IDE 几乎零常驻开销：两个启动活动默认关闭，daemon 侧扩展全部带 O(1) 守卫，预览与转换全部按需触发、后台执行。持续性的开销集中在一处——SQL 日志捕捉链路：捕捉态全程运行一个 EDT 轮询定时器（未检测到控制台时为 100ms 高频），加上挂在运行控制台上的逐行 Filter 解析。两者都要用户主动开启捕捉后才存在，且有上限兜底，但存在可量化的优化空间，详见第三节与第九节。

风险分级一览：

| 级别 | 组件 | 现象 | 触发条件 |
|------|------|------|----------|
| P1 | SqlLogConsoleBridge 轮询 | armed 态全程 100ms EDT 定时器，每 tick 反射 + 控制台组件树遍历 | 手动点捕捉或开启自动捕捉后，直到点停止 |
| P2 | LogFilterProxyHandler 逐行解析 | 运行中应用每打印一行付一次固定解析成本（EDT） | 捕捉中且有应用在输出 |
| P3 | 8 个 gutter provider | daemon 每个 Java/XML 文件元素多 8 次回调 | 常驻，但回调是 O(1) 判定 |
| 无 | 启动/预览/转换/执行/内存 | 均按需或有界，空闲期零开销 | — |

## 二、启动期

插件注册了两个 `postStartupActivity`，行为均收敛：

- `StartupUpdateCheck`（M28 更新检查）：`autoCheckUpdate` 默认关。开启时走 `Task.Backgroundable` 做网络请求，通知经 `invokeLater`，且应用级单次守卫保证多项目只查一次。不阻塞启动，不进 EDT 主路径。
- `LogStartupCapture`（T-M31.14 自动监听）：`logAutoCaptureOnStart` 默认关。开启时以有界重试（MAX_RETRIES）异步启动捕捉，失败即放弃。

插件没有注册 Annotator、ExternalAnnotator、IndexContributor 或任何 stub/index 扩展，不参与索引构建，也不影响 index/dumb mode 之外的高亮调度。`plugin.xml` 里的 `<depends>` 均为平台内置或 bundled 插件，无额外启动装配负担。

## 三、SQL 日志捕捉链路（唯一的常驻开销来源）

### 3.1 轮询定时器

`SqlLogConsoleBridge` 因 2026.2 平台移除 `addContentManagerListener` 接口而采用轮询兜底（设计上有记录），使用 `javax.swing.Timer`——回调直接在 EDT 执行。进入捕捉态（armed）后轮询全程运行：

- 无主控制台：`FAST_POLL_INTERVAL_MS = 100`，每秒 10 拍。注意 KDoc 写的是「500ms」，常量实为 100ms，注释与代码不一致。
- 检测到主控制台：切换 `POLL_INTERVAL_MS = 2000` 常规轮询。
- 应用停止后回到 armed 态 → 又回到 100ms 快速轮询。也就是说，用户一旦点过「捕捉」（userArmed 持久化），整个 IDE 会话内 10Hz EDT 定时器持续存在，直到手动点「停止」。

每一拍 `scanAll()` 做三件事，成本逐项评估：

1. `hasMainConsole()`：对每个 RunContentDescriptor 反射 `getMethod("getComponent")`、`getMethod("getProcessHandler")` 等——`getMethod` 每次都是全新查找，没有 Method 缓存。单次微秒级，但每拍重复。
2. 描述符循环调 `scanComponent` → `findConsoleView` **递归遍历每个控制台的完整 Swing 组件树**。`attachFilter` 虽然幂等（`attachedConsoles` 命中即跳过），但树遍历在命中判断之前，每拍都做。ConsoleViewImpl 的组件树在大量输出后可达数百节点，若干个旧 tab 叠加，每拍 0.1~1ms 量级。10Hz 意味着 EDT 每 6 帧左右插入一次任务，在低配机或控制台洪峰渲染期会与用户输入/绘制竞争。
3. 状态机判定（主控制台出现/消失），纯比较，可忽略。

优化方向（按收益排序）：

- 快速轮询从 100ms 放宽到 500ms 起步并做线性退避。这个定时器的用途是「尽快挂上新控制台的 Filter」，500ms 的捕获延迟用户不可感知（应用自身启动就要数秒）。
- 反射 Method 对象在 companion 中惰性缓存，消除每拍查找。
- `attachedConsoles` 已覆盖全部描述符中的控制台时直接短路，跳过组件树遍历。
- 注释与常量对齐（100ms 与 500ms 二选一）。

### 3.2 逐行 Filter 代理

`LogFilterProxyHandler` 以动态代理挂到控制台的 message filter 链上，运行中应用的**每一行控制台输出**都会进入 `processConsoleLine`：

- 源码标记 parse（前缀判定）；
- 三个解析器（MyBatis / Hibernate / JdbcTemplate）依次 feed，各自做前缀不匹配快速跳过；
- **每行**调 `ctx.configProvider()` 同步 10 余个解析器配置字段，并再读一次 `PluginSettings.getInstance().state.logTimePrefix`。

执行线程是控制台 flush 线程（通常 EDT）。单行成本微秒级，正常应用日志无感知；但在日志洪峰（循环打日志、数千行/秒）场景下累计开销可观，且与控制台自身渲染叠加。兜底措施已具备：`logMaxParseLength = 20000` 防超长行，非捕捉态不挂 Filter（`attachFilter` 守卫），停止时 `detachAllFilters` 移除代理（失败输出 WARN）。

优化方向：配置同步从「每行」改为订阅 `PluginSettings.SETTINGS_CHANGE_TOPIC`（该 topic 已存在），消除每行两次设置读取与 10 余次字段赋值。

### 3.3 挂载与卸载对称性

`attachedConsoles` / `consoleContexts` 两个 IdentityHashMap 在 `detachAllFilters` 中成对清理，项目关闭经 `Disposable.dispose`（`SqlLogManager : Disposable`）兜底。残留场景只有一种：`removeMessageFilter` 反射失败时 Filter 留在控制台上（有 WARN 日志），此后每行仍进解析器——buffer 已 paused 不入队，但解析成本仍在。概率低，保持现有 WARN 观察即可。

## 四、编辑器 daemon（gutter 图标与补全）

`plugin.xml` 注册 8 个 `lineMarkerProvider`（6 个 JAVA + 2 个 XML）和 4 个 `completion.contributor`。daemon 高亮 pass 会对文件中每个元素回调全部 8 个 provider，这是插件在编辑期的固定足迹，评估如下：

- 全部 provider 遵守 M10 性能红线：`getLineMarkerInfo` 只做 O(1) 纯语法判定（`WrapperAnchorDetector` 锚点判定、标签名判定、注解名判定），零 resolve、零遍历，tooltip 为静态文案。已逐一核对 `SqlGutterLineMarkerProvider` 等实现，未发现违规。
- 值得注意的是这些 provider 均未实现 `collectSlowLineMarkers`，判定全部同步发生在 daemon 线程。当前判定廉价所以无碍，但这是后续迭代必须守住的约束——任何在 `getLineMarkerInfo` 里加入 PSI resolve 的改动都会直接拖慢所有打开文件的 daemon pass。
- 点击后链路正确：PSI 转换经 `previewAsync`（pooled thread + `ReadAction.compute`，已适配 243 平台 EDT 禁慢操作），带 200ms 全局防抖。
- `showGutterIcon` 开关可一键关闭全部 gutter（性能兜底）。
- 4 个补全 contributor 守卫先行（光标位置祖先链 O(1) 判定），实体解析仅在补全实际触发时执行，不通过即 return，不干扰原生补全调度。

## 五、预览与转换链路（按需，无空闲开销）

- `SqlPreviewService`：解析结果经 `WrapperCache` 按文件 + 偏移缓存，缓存维度含表相关设置签名，设置变更即失效——重复预览零 PSI 重算。实体类解析走 `PsiShortNamesCache`（平台索引缓存，非全量扫描）。
- `SqlPreviewPanel`：`EditorFactory.createEditor` 创建的编辑器在 `removeNotify` 释放（防编辑器泄漏）；临时 SQL 文件后台预热（M36.6.1 SlowOperations 治理，EDT 零慢操作）；面板注册到弹窗 Disposer 树，messageBus 连接随 Disposable 级联取消（防 Memory leak detected）。
- 反向转换（SQL→Java）等动作均在 `executeOnPooledThread` 后台执行，EDT 只收结果。

## 六、执行链路（M36，仅 Ultimate 且仅执行期间）

执行相关定时器全部短生命周期、有界：

- 结果 Tab 换入重试：EDT Timer 600ms × 8 拍封顶；
- 旧 Tab 复用判定：`REUSE_ACCEPT_TICKS = 4` 拍；
- 数据源等待：800ms 单次 watch。

执行结束即停止，空闲期零开销。执行期间的开销与原生 Database 控制台自身相当（走同一执行链）。

## 七、内存驻留

- `SqlLogEntryBuffer` 默认 200 条淘汰（`logMaxCount` 可调），`SqlHistoryManager` 默认 200 条（收藏条目例外）。每条 `LogSqlEntry` 持完整 SQL 文本，200 条 × 数 KB 为 MB 级，可控。用户把上限调到极大值时内存随之增长，属配置选择。
- 控制台强引用：`attachedConsoles` 持 console 引用，detach 即清理；无静态 Map 持 project/PSI 引用的泄漏面。
- application 级服务（PluginSettings / SqlHistoryManager）只持配置数据，跨项目共享无泄漏。
- UI 侧一次性 Timer（250/400/1200ms 等）均 `repeats = false`，无累积。

## 八、已知边界（非性能项但相关）

插件动态卸载未完全解决（既有结论存档于 memory）：更新后旧类可能残留在 classloader 中，影响的是「免重启更新」的正确性而非运行时性能，此处仅记录关联。

## 九、验证方法与优化建议汇总

实测验证建议：沙盒内 attach JFR 或 VisualVM 观察 EDT 事件队列（可看到 100ms 周期的轮询任务）；开启捕捉后跑一个循环打印 SQL 日志的 Spring Boot 应用，对比开关捕捉两种状态下的控制台 flush 速率与 IDE 响应；IDEA 自带 Performance Watcher（idea.log 中 `Slow operations` / `UI freeze` 报告）可直接量化。

优化建议按收益排序：

1. 快速轮询 100ms → 500ms 起步 + 退避（P1，消灭常驻 10Hz EDT 负载）。
2. 反射 Method 缓存 + `attachedConsoles` 全覆盖短路（P1，配合上一条把每拍成本压到最低）。
3. 逐行配置同步改为 SETTINGS_CHANGE_TOPIC 订阅（P2，日志洪峰场景收益明显）。
4. 轮询注释与常量对齐（P3，防后续维护误判）。

以上均为捕捉链路的锦上添花，不构成当前版本的阻塞问题。
