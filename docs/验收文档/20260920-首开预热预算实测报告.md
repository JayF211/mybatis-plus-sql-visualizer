## 二、方法：从日志能读出哪些时刻（以及判据）

代码锚点（均在本工作树 master `6e3adce` 上核对）：

| 锚点 | 出处 | 含义 |
|------|------|------|
| `[T-PreviewFast] request→dialog: Nms` | `SqlPreviewService.kt:2067` | 该行打印在**构造 `SqlPreviewDialog` 之前**（`:2094` 打印、`:2095` 构造）。`SqlPreviewDialog.<init>` 第 28 行 `panel = SqlPreviewPanel(project)`，面板构造**末尾**（`SqlPreviewPanel.kt:513-515`）才 `prewarmPreviewTempFile()` → **预热线程启动落在这一行与下一行之间** |

| `[M36] createEditor: len=…` | `SqlPreviewPanel.kt:2520` | `createEditor` 入口；**`scheduleOnce` 的 60ms 计时从这里起算**（`resolvePreviewEditorSource` → `PrewarmAwait.scheduleOnce` → `completeOnTimeout(60ms)`） |
| `[M36] in-memory PSI preview document created` | `SqlPreviewPanel.kt:2682` | 降级链第二级（`fallbackPreviewDocument`）——**出现即代表本次首开走了降级**、且右上角会挂降级横幅 |
| `Reparsing <预览临时文件>` / `Push all on [SqlDialectPusher@…]` | 平台 | `SqlDialectMappings.setMapping` 的副作用（`DialectPreMapping` 的 EDT 段）。**它在预热线程内部、`PsiManager.findFile` 之前**，故出现该行 ⇒ 预热当时**尚未完成**（给出耗时下界） |

预热耗时的**完成**时刻代码里没有日志（`publishPrewarmProduct` 与 `previewTempFile = vf` 均不打点）。本报告用两条**间接**判据补足：

- **下界**：`createEditor` 后 60ms 超时仍未就绪（走降级），且方言映射行出现时预热仍在跑 ⇒ 预热耗时 > 映射行时刻 − 预热启动时刻。
- **上界（本次新增的探针）**：`releaseEditor`（`SqlPreviewPanel.kt:2795`）只在 `previewTempFile != null` 时删除项目内临时文件，而该字段**只在预热线程 `findFile` 成功后**（`:597`）被赋值；「放弃分支」的删除（`:562`）只在预热线程尚未跑到方言映射时发生。故**映射行已出现、关闭面板后文件消失 ⇒ 预热已完成**。探针 `probe.py` 即按此判据：等映射行 → 延时 → 关闭对话框 → 看文件是否还在。

- 三次冷启动首开的预热都**远超 60ms**：最保守的下界分别是 387ms / 995ms / 280ms。

**测不到的部分（如实记录，不编数字）**：

- **预热的真实完成时刻在现有日志里没有任何打点**——`publishPrewarmProduct`（`SqlPreviewPanel.kt:617-623`）只写字段与完成 future，不打日志；成功路径的 `previewTempFile = vf`（`:597`）同样无日志。故上表「已完成」一列只能靠「文件被 `releaseEditor` 删除」这一**间接**判据，且窗口受探针动作（关闭对话框）限制，无法直接读出毫秒数。

  `LOG.info("[M36] prewarm done in ${System.currentTimeMillis() - prewarmStartMs}ms (vf=${vf.name}, psi=${psi.javaClass.simpleName})")`，并在两条 `await.fail` 路径上加同款带原因的收尾行。**该打点只需在预热线程上执行，不碰 EDT，不影响被测量本身**。

## 五、空等期的界面状态（若提高预算，用户会看到什么）

**代码判据（可下结论）**：

- 装配是**回调完成才装配**：冷态下 `resolvePreviewEditorSource` 返回 `false to null`，`createEditor` 直接 `return`（`SqlPreviewPanel.kt:2529`），此时 `editorHolder`（`GridLayout(1,1)` 的 `JBPanel`，`:253`）**没有任何子组件**——编辑器组件与「预览的 SQL 显示在此处…」占位提示都是在 `assemblePreviewEditor` 里才创建/设置的（`:2616` 的 `setPlaceholder(previewEmptyHint)`、`:2624` 的 `editorHolder.add(...)`）。
- 所以等待期编辑区是**纯空面板**：没有占位文案、没有转圈、没有任何进度提示；meta 行、工具栏、参数区已经画好（它们在构造期就建好了）。
- 时序上，`SqlPreviewService.showResult` 是**先构造对话框（含 `showResult` 内的首轮装配尝试）再 `dialog.show()`**（`:2094` 构造、`:2097` 显示），所以「等待期」与「对话框自身首次绘制/淡入」重叠。

**截图佐证（连拍）**：

- `burst2.py`（48fps，锁定编辑区子区域）在 S1 #4：对话框首次可见帧出现在 **18:53:09.308**，而落内存 PSI 在 **18:53:09.271**——**首帧绘制就已有内容**（`build/measure/burst2/f0052_185309342.jpg`），这一拍**没有捕捉到空编辑区**。
- `burst.py`（23fps，整窗）在 S1 #3：`build/measure/burst1/f001_185150665.jpg` 里对话框处于淡入半透明态、编辑区尚无 SQL 文本（meta 行与工具栏已可见）——但该帧同时受淡入影响，**不足以单独作为「空等期」的定证**。

**判断**：在当前 60ms 预算下，等待期基本被对话框自身的构造与首绘（本次实测约 150ms）遮住，用户通常看不到空编辑区；**若把预算提高到 N，空窗就会外露约 N −（首绘耗时，实测约 150ms）**，而编辑区那时是纯空面板。故「提高预算」这一项若实施，**建议同时给编辑区一个轻量占位**（复用 `panel.preview.emptyHint` 或加一句「正在准备预览…」），否则观感是「对话框开了但 SQL 区一片空白」。

## 六、建议

### 6.1 量化结论

- 本环境下 **60ms 预算覆盖 0/7 次首开（含 3/3 次独立冷启动首开）**；要覆盖观测到的首开，预算需 **≥ 约 1.1s**（S3 实测完成上界 1071ms）；只按最保守的下界看，**≥ 1.0s 才勉强越过 S2 的 995ms**。
- 提高预算**不花 EDT 时间**这一判断在代码与实测上均成立：冷态是 `scheduleOnce` 注册后立刻返回（`PrewarmAwait.kt:52-61`），EDT 只在回调里做装配。但实测还给出一个原注释没算到的量：**EDT 派发延迟本身有 49–788ms**（超时回调排队时间），所以「预算 N」对应的用户可见延迟是 **N + EDT 排队**，而不是 N。
- 建议值：**1000ms**（覆盖 S1/S3 的实测完成；对 S2 的 995ms 下界是临界），若希望留余量取 **1500ms**；同时按 §五 补编辑区占位。**这只是三样本、且是负载上界下的估计，不是分布**——正式定值前建议补 §3.2 的打点，在**空闲机**上取 10 次以上首开样本。

### 6.2 更值得做的一件事（有证据支持，但属推断）

方言映射的 EDT 往返出现在**每一次打开**上，而不只是会话首见：S3 会话里 `Push all on [SqlDialectPusher@…]` 出现 **2 组**（首开 19:09:59,689 与复开 19:10:42,664 各一组），原因是 `releaseEditor` 每次关闭都删掉项目内临时文件（`:2795`），下一次预热重建该文件 → **新的 `VirtualFile` 实例** → `DialectPreMapping` 的进程内短路（`previewDialectMappedVf === vf`）与读探测都命中不了 → 重新 `setMapping` + `push all dumb`。而这一步的时刻（+536ms / +1169ms / +395ms）正是三次首开里唯一能定位的预热内部步骤，**也是唯一必须回到 EDT 的步骤**。

因此若目标是「首开不降级」，**比抬预算更有效的是把这一步移出关键路径**（例如让临时文件与其方言映射在面板关闭后存活、或把映射改为不阻塞 `findFile` 的异步侧写）。**注意这是从打点位置做的推断，不是 profiler 结论**——要证实需在预热线程各步骤各加一行耗时打点。
