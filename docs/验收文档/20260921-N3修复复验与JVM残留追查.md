转储里**没有** `Found one Java-level deadlock`，也**没有** `DestroyJavaVM` 线程。

读出来的阻塞链：`WM_CLOSE` → EDT 上 `CloseProjectWindowHelper.windowClosing` → `ApplicationImpl.doExit(:807)` 调 `System.exit` → 因为是在 EDT 上退出的，JVM 就在 EDT 线程里跑应用级关停钩子 → `ApplicationShutdownHooks.runHooks(:114)` 逐个 `Thread.join` 钩子线程 → 卡在 join **`ToolkitShutdown`** 上；而 `ToolkitShutdown` 正停在 AWT 工具包的 native `WToolkit.shutdown()` 里没返回。`main` 则一直停在 `runBlocking`（`Main.mainImpl(Main.kt:84)`）上，所以也没从 `main` 返回。`AWT-Windows` 线程状态正常（还在跑 native 消息泵 `eventLoop`），不是消息泵死了。

**阻塞链上没有任何插件帧**：`ToolkitShutdown` 是 JDK 的（java.desktop），`AWT-EventQueue-0` 停的是 `java.lang.Shutdown`/`ApplicationShutdownHooks` 与平台自己的 `ApplicationImpl`/`CloseProjectWindowHelper`。

### 3.3 禁用插件对照（判归因的关键）

禁用方法（按 AB 报告的方向，但两处都要做，缺一插件照样加载）：

- `config/disabled_plugins.txt` 里的条目**由 Gradle 的 `PrepareSandboxTask` 在每次 `runIde` 时重写**（`PrepareSandboxTask.kt:192` 的 `writeTextIfChanged`），手写文件会被冲掉；必须经任务属性集写入，本工作树临时加 `-PabDisabledPlugins=<插件 id>` 接进去。
- 只做上面一步仍会加载：`runIde` 默认传 `-Didea.required.plugins.id=<被测插件>` 强制加载，须再追加一条同名 `-D` 覆盖（本工作树临时加 `-PabRequiredPlugins=com.intellij.java`）。实测覆盖后进程命令行里该属性只剩一条、值为 `com.intellij.java`。

**禁用是否生效，按日志复核（不是按配置文件推断）：**

```
# 启用臂
Loaded custom plugins: JetBrains AI Assistant (262.9437.276), SQL Visualizer (2026.9.18)

# 禁用臂
Loaded custom plugins: JetBrains AI Assistant (262.9437.276)
Disabled plugins: SQL Visualizer (2026.9.18), JetBrains Ultimate (262.9437.185)
```

即禁用臂里插件确实没加载。

**对照结论：禁用后进程仍然不终止。** 关窗 02:27:59 → `IDE SHUTDOWN` 02:28:02 → 等满 300 秒仍在（`exit_mode=still_alive_after_300s`），转储与启用臂同形（同为 EDT join `ToolkitShutdown`、`ToolkitShutdown` 卡在 native `WToolkit.shutdown`、`main` 停在 `runBlocking`）。

### 3.4 归因判断

残留与插件无关，是平台／JDK 侧的问题。三条依据：

1. **禁用插件后同样残留**（n=1），且两臂转储的阻塞链逐帧一致；
2. 阻塞链上**没有插件帧**——卡住的分别是 JDK 的 `ToolkitShutdown`（native `WToolkit.shutdown`）与平台自己的关停路径；
3. 触发条件是 `System.exit` 在 EDT 上被调用（`CloseProjectWindowHelper.quitApp(:120)`），这与插件是否加载无关。

需要如实划清界限的一条：**`WToolkit.shutdown()` 为什么不返回，本轮没有查到**。转储只能证明它从关停时刻起一直没返回（样本 2 里该线程 elapsed 605.10s，与「关停后经过的时间」吻合），不能证明原因。要定位得往 AWT native 侧走，本轮没做。

## 四、未覆盖与不确定之处

1. **样本量小。** 启用臂 2 次、禁用臂 1 次。禁用臂只等了 300 秒（未做 600 秒档），启用臂等了 300／600 秒两档。两次启用臂读数一致，禁用臂只有单次观测。
2. **「不终止」的时间上界未知。** 最长只观察到 600 秒仍在，不能排除「再等更久会退出」。三轮（含上一轮 120s/300s）都是等满后强杀，没有任何一次观察到自然退出。
3. **`WToolkit.shutdown()` 的阻塞原因未定位**（见 3.4）。没有做 native 侧分析，也没试 `jstack -m`／`jcmd VM.native_memory` 之类的进一步手段。
4. **只测了 WM_CLOSE 这一条退出路径。** 菜单 File → Exit、快捷键退出、关掉工程但不关 IDE 等路径未测。`confirmExit=false` 这个预置本身也只解决「退出流程起不来」，不代表进程能结束。
5. **禁用臂是「已安装但不加载」，不是「未安装」。** 与 AB 报告的 B 臂同一性质；若怀疑「平台仍会读其 plugin.xml 描述符」，需要另做一轮真正卸载的对照。
6. **N3 只验了「空框 Esc 关闭」。** 与上一轮相同，未测「同一实例重复打开」「提交内容后关闭」两条路径；修复的机制正确性由开发计划里的定向单测（含变异实验）保证，本轮只做真机计数。
7. **样本 1 的 `ProgressDialogWrapper` 平台泄漏未归因**（见 2.3）。样本 2 与禁用臂都没有，且样本 1 与另两臂的用户活动不同，本设计无法区分是插件副作用还是 VFS 变更时序。
8. **两臂的沙盒 system 缓存冷热不同**（启用臂 1 首次冷索引，其余为暖）。索引冷热不影响退出路径的判定链。
9. **未在真机上验证。** 全部读数来自沙盒；`confirmExit` 是用户的真实设置项，本轮只证明它在沙盒里能绕开平台缺陷。
