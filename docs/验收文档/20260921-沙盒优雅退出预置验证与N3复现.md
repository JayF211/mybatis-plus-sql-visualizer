## 一、假设与依据

**假设**：沙盒里 IDE 退不掉，是因为退出路径要弹「确认退出」框、而该框自身创建失败；把 `GeneralSettings.confirmExit` 预置为 `false`，退出应能走通。

前一轮的证据（《20260920-IDE启动开销AB实测报告》文末附节）只到「栈指向 `confirmExitIfNeeded`、弹窗创建失败」与「16 次运行 0 次 `IDE SHUTDOWN`」，预置落盘位置是**推断**。本轮先把两处推断坐实，再做 A/B。

### 1.1 `GeneralSettings` 落的就是 `ide.general.xml`（已坐实，非推断）

`com.intellij.ide.GeneralSettings` 的源码不在 ideaIC sources jar 里，但类文件在平台 jar 里。对 262 平台 jar 做 `javap -v`，类级注解常量池给出：

```
#367 = Utf8               ide.general.xml
#380 = Utf8               Lcom/intellij/openapi/components/State;
#382 = Utf8               GeneralSettings
#385 = Utf8               category
#387 = Utf8               SYSTEM
```

即 `com.intellij.ide.GeneralSettings`（在 `intellij.platform.ide.core.jar`，实现 `PersistentStateComponent<GeneralSettingsState>`）带
`@State(name = "GeneralSettings", storages = [@Storage("ide.general.xml")], category = SettingsCategory.SYSTEM)`。
**组件名、选项名、文件名三者与预置写法逐字一致。**

### 1.2 262 的退出条件与「弹框压根不被尝试」的路径（已坐实）

`ApplicationImpl$8.isToBeShown()` 字节码（`intellij.platform.ide.impl.jar`）：

```
invokestatic  GeneralSettings.getInstance()
invokevirtual GeneralSettings.isConfirmExit()Z
ifeq          23
invokestatic  ProjectManager.getInstance()
invokevirtual ProjectManager.getOpenProjects()[Lcom/intellij/openapi/project/Project;
arraylength
ifle          23
```

与 243 源码给的
`GeneralSettings.getInstance().isConfirmExit() && ProjectManager.getInstance().getOpenProjects().length > 0` 一致。

`ApplicationImpl.confirmExitIfNeeded(boolean)` 字节码里的早退分支：

```
7:  iload_0            // isUnsafeExitRequested
11: iload_1            // hasUnsafeBgTasks
17: new ApplicationImpl$8(hasUnsafeBgTasks)     // DoNotAskOption
30: aload_2 / invokevirtual ApplicationImpl$8.isToBeShown()
34: ifne 39
37: iconst_1 / ireturn                          // ← isToBeShown()==false 时直接返回 true，DialogWrapper 根本不构造
```

所以 `confirmExit == false` 时，`confirmExitIfNeeded` 在构造弹窗之前就返回，**不会**走到 `DialogWrapper.show`，也就不会有 peer 创建。

## 二、任务 1：A/B 验证

两臂同一工作树、同一沙盒目录、同一预置配置（`recentProjects.xml` + `trusted-paths.xml` 指向 demo 工程），唯一变量是 `ide.general.xml` 里有没有 `GeneralSettings/confirmExit=false`。A 臂跑完先杀掉本沙盒进程，写入预置并回读确认（`confirmExit_value: "false"`，796 字节），再起 B 臂。

关窗方式：`WM_CLOSE`（`PostMessage` 投给本沙盒 IDE 进程的全部顶层窗口，等同点关闭按钮）。判活只按命令行含 `MPSV-ExitConfirm` 的 java 进程，不碰任何他人进程。

### 2.2 预置是否被 IDE 改写

**没有。** B 臂退出后回读 `ide.general.xml`：796 字节、`confirmExit=false` 原样在，与写入时**逐字节相同**；文件 mtime 停在写入时刻 `01:01:20`，B 臂（01:01–01:05）与任务 2 会话（01:08–01:25）跑完都未变动。即 IDE 既没有抹掉预置、也没有重写该文件。

### 2.3 任务 1 判定

**假设成立。** B 臂满足判定条件：`IDE SHUTDOWN` 出现、`confirmExitIfNeeded` 为 0、peer 错误为 0、`Failed to destruct` 为 0，且主窗口在关窗后立即消失（A 臂窗口则一直挂在屏上）。单变量设计下可归因于该预置；用户可感的差别就是「点关闭后窗口真的关掉了，不再挂在屏幕上」。

**但要如实补一条 B 臂的残留现象**：平台记完 `IDE SHUTDOWN` 之后，**JVM 进程并未终止**——B 臂等 120 秒、任务 2 会话等 300 秒都还在，最后都是强杀。`IDE SHUTDOWN` 这行不是退出前的最后一步日志，而是**已经进入 JVM 关停序列**才打印的：`com.intellij.platform.ide.bootstrap.StartupUtil$setupLogger$1$1` 的字节码里，取到 Logger 之后调
`ShutDownTracker.getInstance().registerShutdownTask(<lambda 捕获该 Logger>)`（`javap -c`：`invokestatic ShutDownTracker.getInstance` → `invokedynamic run:(Lcom/intellij/openapi/diagnostic/Logger;)Ljava/lang/Runnable;` → `invokevirtual registerShutdownTask`），横幅文本就取自该 lambda。所以这行出现意味着 `System.exit` 已被调用、关停任务正在跑，只是**没跑完**。

这条本轮**未归因**：B 臂里插件的 `ParamImportDialog` 从未打开，唯一的 Disposer 泄漏报告来自 JetBrains AI Assistant 自己的 `AI Assistant tool window header`（两条，A 臂无）；因此至少不能归到 `ParamImportDialog` 上，但究竟是平台自身的关停任务被挂住、还是插件别处（MCP/日志线程等）拖住，本轮没有做对照实验（例如禁用插件再退一次），不下结论。

另外顺带排除一个干扰项：B/T2 的关窗后截图里屏中央出现过一个「JetBrains Team Tools User Agreement / IntelliJ IDEA 用户协议」对话框，经窗口归属核查属于 pid 29672（用户自己那个 jbr 17.0.10 的真 IDEA），与本沙盒进程无关；本沙盒「窗口已消失」的判据取的是窗口枚举（本进程可见窗口数 0），不是截图观感。

## 三、任务 2：N3 复现（`ParamImportDialog` Disposer 泄漏）

## 四、未覆盖与不确定之处

1. **`IDE SHUTDOWN` 之后 JVM 不终止，未归因**（见 2.3）。这是本轮最需要后续处置的未解项：预置解决了「退出流程起不来」，但没有得到「进程真的结束」。没做的对照是「禁用插件后同样优雅退出」，因此无法判断残留是平台侧还是插件侧。
2. **每臂各只跑了 1 次**。A 臂的基线复现与上一轮 8/8 的读数一致，B 臂的 `IDE SHUTDOWN` 是单次观测；预置的稳定性（例如是否偶发仍抛 peer 错）没有重复样本。
3. **A/B 之间索引冷热不同**（A 冷启有重索引，B 复用 A 留下的 system 缓存）。索引冷热不影响 `isConfirmExit` 与弹窗创建这两条链，但严格意义上两臂并非完全同条件。
4. **任务 2 未测「同一实例重复打开」与「提交内容后关闭」**：三次都是空框直接 Esc 关闭，没有走 `onConfirm` 回填路径，因此「泄漏是否与提交与否相关」未验证。
5. **`ParamImportDialog` 的泄漏根因未在代码层定位到修法**：本轮只复现与取证，未改源码；`DialogWrapper` 自身是否已被 dispose（若已 dispose 而子 disposable 仍挂在 ROOT 上，修法方向不同）未查证。
6. **未验证预置在真机（用户日常 IDEA 配置）上的行为**：`confirmExit` 是用户的真实设置项，本轮只证明它在沙盒里能绕开这个平台/环境缺陷，不代表应该去改用户设置。
