## 一、改动总览

### 1. T-AcpMcpTransport：ACP 会话 MCP 工具下发修复（SSE 传输绕行）

**缺陷本体**：AI Assistant 的 ACP 会话（Claude Agent）里 agent 工具表没有任何 MCP 服务器——agent 全程只用 `Bash`/`Grep`/`Write`，需要 `sqlv_*` 时自己用 Bash + curl 手工做 MCP 握手。根因在上游 `@agentclientprotocol/claude-agent-acp`（0.66.0 / 0.76.0 / 0.79.0 三版一致）的 `dist/acp-agent.js`：

```js
if ("type" in server && (server.type === "http" || server.type === "sse")) { … }
else if (!("type" in server)) { …stdio… }   // 注释写「有无显式 type 都行」，条件却要求没有 type
```

而 AI Assistant 侧 `com.agentclientprotocol.model.McpServer$Stdio` 标了 `@SerialName("stdio")`，序列化必带 `"type": "stdio"` → 两个分支都不进、**静默丢弃**。IDE 侧逐项排除（设置开关、自定义 MCP 列表、私有 IJ MCP 会话确实创建、stdio 命令实测可跑通）全部无误；对照实验（`codex-acp@1.4.0` 的 stdio schema 无 type 约束，实测带 `type: "stdio"` 亦能解析并通过调用）证明该 bug 是 agent 特有。

**绕行**：同一段代码的 `type === "sse"` 分支实现正确，且 `claude-agent-acp` 的 initialize 响应声明 `mcpCapabilities: { http: true, sse: true }`。经 ml-llm 的 `com.intellij.ml.llm.agents.acp.ideaMcpTransportProvider` EP 注册 provider 返回 SSE，即让 IDE 以 SSE 下发私有 IJ MCP 会话，绕开 stdio 分支。

- **T-AMT-01 EP 注册与可选隔离**：`plugin.xml:101` 新增 `<depends optional="true" config-file="acp-transport-optional.xml">com.intellij.ml.llm</depends>`；新文件 `src/main/resources/META-INF/acp-transport-optional.xml` 内注册 provider。注册形态取 EP 属主 ml-llm 自己的写法（`defaultExtensionNs="com.intellij"` + 点分本地名 `ml.llm.agents.acp.ideaMcpTransportProvider`），与 ml-llm `plugin.xml` 第 5426 行的 `extensionPoint qualifiedName` 逐字对应。ml-llm 不在场时整文件不加载，插件零影响——与既有 `mcp-optional.xml`、`database-optional.xml` 同款隔离手法。

### 2. 泄漏源修复：预热链池线程绑项目生命周期

生产改动单笔提交 `9f4bbb9`，`src/main/kotlin/cn/song/mybatisplus/visualizer/ui/SqlPreviewPanel.kt` **+91/−7**（本轮唯一改生产逻辑的项）。

**问题**：`SqlPreviewPanel` 构造期与 `clear()` 都派发 `executeOnPooledThread` 预热（不 join、不挂 disposable），测试方法返回后池线程才跑，在 `ProjectManagerImpl.closeProject` 的 light 分支造出的 temporarily-disposed 窗口内 `findFile` → 平台把 "Project is already disposed" 记成 ERROR（测试态升格 `TestLoggerAssertionError`），并可能喂出一次注定失败的取服务（`LazyInstanceHolder` 缓存 `CannotInitialize` 后该服务在该项目实例上永久毒化）。

**修法（治本，非守卫）**：

- 取消门挂 `ProjectEx.getEarlyDisposable()`——平台 KDoc 原文即此用途（「In unit test mode light project is not disposed, but this disposable is disposed for each test」）；真机 heavy 关闭路径同样先 `disposeEarlyDisposable()`。项目开始销毁即置 `previewDisposed`，池线程在下一个检查点放弃、**不取服务**；面板 dispose 时 `Disposer.dispose(gate)` 解除登记（不留指向面板的项目树引用）。登记用 `Disposer.tryRegister`（父已销毁时返回 false 不抛）。**取消而非 join**：关闭路径上等待会把在途预热耗时加进用户可感的关闭时间，且平台要求该 Disposable 的 dispose 自包含（getting services is forbidden），本实现只置标志。**未选 `Disposer.register(project, …)`**：light 项目的主 disposable 在片内跨测试方法一直存活（`setTemporarilyDisposed(false)` 只重建 earlyDisposable），挂主树等于整轮不触发。
- `prewarmAbandoned() = previewDisposed || project?.isDisposed == true`：项目侧判据**只作窄缝兜底**（真修法是①让池线程不再比项目活得久）。`SqlPreviewPanel.kt:553` 在紧贴取服务前再判一次（「宁可少取一次服务」）。
- `PsiManager.findFile` 的判据放进 `ReadAction.compute` **内部**（`:565`）——平台读动作会被 `closeProject` 的写动作阻塞、放行时窗口已开，判据放在读动作外面会漏掉这条缝。
- 放弃与真失败分开记账：放弃不置 `prewarmFailed`、不记 WARN（生命周期事件而非预热故障）。

**读数**（同一命令 `./gradlew test` 全量，沙盒 `log-test/idea.log` 按字节偏移取增量切片；行数＝日志行，事件＝5 行/事件）：

| 口径 | 改动前 | 改动后 |
|---|---|---|
| `containerState=disposed temporarily` 行数 | 290（58 事件；事件级首帧归因 58/58 落在 `prewarmPreviewTempFile$lambda`） | **0** |
| `Project is already disposed` 行数 | 290 | **0** |
| `[M36] prewarm FAILED: TestLoggerAssertionError` | 58 | **0** |
| `[M36] prewarm FAILED: AlreadyDisposedException` | 2 | **0** |
| 全量用例读数 | 5372/0/0/6 | 5372/0/0/6（BUILD SUCCESSFUL 6m30s） |
| `ui.SqlPreview*Test` + `CrudSqlPreviewPanelRenderTest` 子集（27 类 382 例）窗口行数 | 25（5 事件，全为预热链） | **0**，382/0/0/0 |

**先红后绿**：定向探针复刻 `closeProject` light 分支的两步（写动作内 `disposeEarlyDisposable()` + `setTemporarilyDisposed(true)`）在预热线程在途时开窗，改动前红（栈与门禁 3971 条同形）、改动后绿。**探针跑完即删、未入库**；独立复核指出该探针读数不可完全复核（详见 §三-1）。另补一条**直读门状态**的探针：面板构造后断言 `prewarmLifecycleGate != null`，再在写动作内调 `disposeEarlyDisposable()`，断言 `previewDisposed` 由 false 变 true——证明门确实触发，而不是挂了个不响的钟。

### 3. T-McpToolNaming：MCP 工具分组与命名收敛
