## 一、背景与验收前置

2026-09-20 验收轮按「先记录、后统一修复」的口径累积了 11 条问题（P1~P8、P11，P9/P10 为本轮复核新发现），本轮统一立项修复并过独立复核。缺陷分布在三条互不相干的链路上：

- **预览面板链路**（P1/P5/P6）：预热产物恒被判「不可用」导致每次打开都降级、调用栈摘要从未进可见行、参数提示态覆写悬停全文；
- **MCP 工具链路**（P3/P4）：参数类型写错时抛内部索引异常、表名匹配跨 schema 把 `mysql.user` 系统表列并进业务表；
- **schema 解析与回滚文案链路**（P7/P7b/P8/P11）：resolver 按名匹配 + 缓存固化污染、内省未完成时误报「表不存在」、回滚告警文案的占位符与键名缺陷。

**环境**：装发行包或 `runIde` 沙盒；MCP 相关项需要 IDE 内置 MCP Server（2025.2+）与一个支持 MCP 的 agent 客户端；回滚相关项需要 XML 预览面板。

## 三、分项验收步骤（真机走查，留人工）

### 3.1 P1 预览不再恒降级（本轮最直观的一项）

> **⚠ 2026-09-20 真机走查订正**：本节步骤 1 的原始预期写错了。**冷启动首开降级是既定设计**——`SqlPreviewPanel.kt:4263` 的 `PREWARM_WAIT_MS = 60L` 注释原文：「60ms：预热线程已就绪（面板再开/热态）立刻命中走 PSI 主路径，**冷启动第一拍直接降级**纯内存编辑器不烧 EDT；预热完成后下次打开即自愈走回 PSI 高亮/补全路径」（T-PreviewSlow F1：把 EDT 同步自旋预算从 2000ms 砍到 60ms，因为干等到 2000ms 会把延迟烧进 UI 线程，真机日志双击→createEditor 达 3.07s）。**P1 要修的是「等索引完成重开也不恢复」**——走查实测该项**已修复**（重开稳定走预热回调主路径、无横幅）。下表步骤 1 按设计口径改写。

| 步骤 | 操作 | 预期 |
|------|------|------|
| 1 | IDE 启动后**首次**双击 mapper 语句打开预览 | **可能出现**降级横幅（冷启动预热未在 60ms 预算内完成，属既定设计，不烧 EDT 的取舍） |
| 2 | 关闭对话框再重开 | **必须无**告警行，且 meta 行正常（走预热回调主路径）——这是 P1 的回归判据 |
| 3 | 在预览编辑器里触发表/列补全 | 补全候选含真实表列（降级模式下只有内存 PSI、无项目内文件上下文）。**注**：走查发现预览编辑器以 viewer 形态创建、`Ctrl+Space` 无补全弹窗，该步骤真机不可执行；同源解析由 §3.4 P4 的 MCP 取数证据覆盖 |

### 3.3 P6 提示态不丢悬停全文

> **⚠ 2026-09-20 真机复核订正两处**：①步骤 1 原先写「清空剪贴板后点导入参数」——**不可达**：入口 `importParamsFromClipboard()` 根本不读剪贴板，且 `ParamImportDialog.doOKAction()` 末句 `if (text.isNotBlank()) onConfirm(text)` 使**空内容直接 return**，提示链路压根不触发（已记为 P13：提交空内容是静默无操作，待产品定夺）。可用的复现是**提交非空但解析为空的内容（如 `{}`）**。②步骤 2 的「首行 / 其后」在 262 上不可见——平台 tooltip 把 `\n` 渲染成空格、呈**单行**，内容都在但呈现为一行拼接。

| 步骤 | 操作 | 预期 |
|------|------|------|
| 1 | 预览面板「更多 → 导入参数」，在对话框里填**非空但解析为空**的内容（如 `{}`）后确定 | 可见 meta 行转红字「⚠ 未识别到有效参数…」，工具栏出现「复制错误信息」按钮（**填空内容提交则无任何反馈，见 P13**） |
| 2 | 悬停该行 | tooltip 里提示文案与基线**都在**（改前提示把 tooltip 整段覆写、调用链丢失）。262 上呈单行拼接 |
| 3 | 再次提交同样内容 | tooltip 不叠加自身（幂等） |
| 4 | 换一条语句重新预览 | 提示态被 `updateMeta` 覆盖，可见行与 tooltip 都回到纯 meta |
| 5 | 提示挂起时把面板拖宽再拖窄 | 提示与复制按钮都不丢（这是 P10 的原始触发路径：复制按钮显隐改工具栏理想宽 → 行重排 → 重算预算） |

### 3.4 P3/P4 MCP 工具入参与跨库匹配

| 步骤 | 操作 | 预期 |
|------|------|------|
| 1 | agent 调 `sqlv_schema_context`，`tables` 传 JSON 数组 `["user"]` | 返回 `[INVALID_ARGUMENT] tables must be a comma-separated string of 1..50 table names (got JSON array).`，**不再是** `Index -1 out of bounds` 之类的内部异常（真机实测文案含 `got JSON array` 形态说明，比本节原先引用的字面更具体） |
| 2 | 同样调一次，`tables` 传空串 / 纯分隔符 / 超 50 个表名 | 一律 `[INVALID_ARGUMENT] tables must contain 1..50 table names (comma-separated).`；`maxTables` / `dataSource` 传数组同样得 `INVALID_ARGUMENT`（`…must be an integer (got JSON array).` / `…must be a data source display name string (got JSON array).`），文案里不含内部异常字样 |
| 3 | `tables: "user"` + `dataSource: "<业务库>@localhost"` | 只返回业务库那张表的列，**不含** `mysql.user` 的系统列（`Host`/`Select_priv`/…），表注释取业务表。对照：不传别名时会命中另一库的同名表，证明别名确实收敛了范围 |
| 4 | 同上但 `tables` 指向一个当前库里没有的表 | 报错文案含「表可能不在当前库」的措辞（实现为英文 `the table may not exist in the data source's current database`，MCP 返回不走 i18n），并附逐源实况 `ds=… targetDb=… modelTables=N indexed=M`。**读法**：`modelTables>0` = 模型读到了；`indexed` = 过滤后仍在范围内的表数——`indexed>0` 说明该源能扫且范围内有表（即「表名确实不存在」），`indexed=0` 且 `modelTables>0` 才是「候选被库名 scope 全过滤掉」（真机实测缺表时各源 `indexed=6/6/10/2`，即前者） |
| 5 | 既有客户端（改版前写好的调用） | 调用方式与返回结构不变：`tools/list` 里 `sqlv_schema_context` 的 `inputSchema` 仍是 `tables{string}` / `dataSource{string}` / `maxTables{integer}` / `projectPath{string}`、`required:["tables"]` |

## 五、已知边界 / 取舍

- **P9 未修（复核新发现）**：`releaseEditor()` 作废预热产物却不重臂 `prewarmAwait`——控制台 attach 后又 detach 且未走 `clear()` 时，同一面板二次装配会走降级链。**直觉修法是错的**：在 `releaseEditor` 里重臂会与 `clear()` 的既有重臂双开，两个预热线程抢 `previewTempFile`，后启动者见字段非空即 `await.fail`，反而把 await 指向失败态、比现状更糟。该生命周期历来是硬仗（T-PreviewFlash / T-PreviewDocLock2 / T-StabilityTail 三轮修补），需专门立项 + 真机验证。触发面窄、降级带诚实横幅，且**非本轮 P1 引入**（P1 修复前该判定恒假、此路径同样降级）。
- **P10 未修（复核新发现）**：参数提示态只写 `metaLabel.text`，不写 `metaLineText`/`metaLineHead`——提示态期间拉伸面板会触发 `applyMetaTruncation()` 用 `metaLineText` 覆盖可见行，提示文字消失而红色前景与复制按钮仍在。既有边界（P6 之前即如此），纯观感。修法已记录：把提示写进 `metaLineHead` 并复位 `lastMetaBudget`。
- **`columnsCached` 行为收窄需产品确认**：多数据源下同名表的补全候选由「各源列并集」改为「首个持有该表的数据源」。若用法依赖主库/影子库并集，需回退该项。
- **DEGRADED 横幅文案仍误导**：称「IDE 索引完成后重新打开预览可恢复完整支持」，而预览链路里没有任何 DumbService 判据。P1 修好后正常路径不再出现该横幅，失败路径仍会显示这句。建议改写为「关闭并重新打开预览可重试」，待产品定文案。
- **P7 的 DBN 反射层未真机验证**：`getDasParent` 祖先链名 = URL 库名这一假设由平台口径佐证，本轮单测用遍历替身驱动，未在真机 DasModel 上跑通。已留诊断抓手：`scan: ds=… targetDb=… modelTables=N indexed=M`（某 DBMS 命名不符会 `indexed=0`，一眼可见）。另：262 平台 `DatabaseTools/lib` 下未找到 `DasObject.class`，`getDasParent` 在 262 的可用性未验证——不可用时按设计 fail-safe 退回按名匹配（不报错、也不限库）。
- **Oracle / PG 的库名解析未验证**：`JdbcUrlDatabase` 对 PG 可取库名，Oracle thin（无 `://`）取不到 → 退回按名匹配（一期口径，不新增失败模式）。
- **`:sql-visualizer-agent:test` 仍不进 `testShards`**：65 例平时不跑，建议并入门禁。
