# IDE 启动开销 A/B 实测报告（装插件 vs 禁用插件）

- 日期：2026-09-20
- 工作树：`F:/code/Java/Gitee/SongRenShuo/mpsv-startup-ab`（分支 `t-startup-ab`，自 master `a1f9c70`）
- 被测工程：`F:/code/Java/Gitee/SongRenShuo/mybatis-plus-sql-visualizer-demo`（未改动其代码）
- 平台：IntelliJ IDEA Ultimate 2026.2.1（IU-262.9437.185），`./gradlew runIde -PgifRecord=true`
- 样本：每臂 8 次，严格交错 A1,B1,A2,B2,…,A8,B8，共 16 次 IDE 启动

## 一、结论

**未观测到可归因于插件的启动开销。**

判据：

1. 五个指标的两臂中位差都在各自臂内的运行间极差之内（|Δ中位| = 0.02 ~ 3.2 s，臂内极差 1.8 ~ 18.6 s）。
2. 同轮次配对的符号检验全部不显著（p = 0.07 ~ 0.73）。
3. 最能隔离插件加载窗的指标——「进程启动 → 项目开始扫描」——两臂中位差仅 **−16 ms**（p = 0.94），几乎完全重合。插件 JAR 加载与扩展点注册就发生在这一段。
4. 结构上插件不可能改变索引工作量：plugin.xml 未注册任何 index / stubIndex / fileType 类扩展点（扩展点全集见第五节）。
5. 实测两臂的索引写入任务数一致（A 臂 27 个、B 臂 26 个），且 B 臂扫描次数更多（42 vs 36）却更早完成。

需要如实记下的一条方向性迹象：扫描之后的三项指标（扫描完成 / 索引任务结束 / 退出 dumb 模式）中位差为 −1.7 ~ −3.2 s（禁用臂更快），未配对的中位差置换检验 p = 0.03 ~ 0.05。**但这条迹象不成立为结论**：它经不起同轮次配对检验（p = 0.07 ~ 0.29），方向上与「B 臂扫描次数更多却更快」矛盾，且找不到任何机制（插件无索引类扩展点，两臂索引写入任务数相同）。按实验设计，差值落在运行间波动内即判为噪声，故不把它报成开销数字。

本设计的分辨率：臂内波动主要由外部 CPU 负载与扫描规模决定（`T_open` 与启动前 CPU 占用率的 Pearson r = +0.88；同一臂不同轮次的扫描规模在 327 / 46799 / 116720 文件之间跳变）。因此**量级在 3 s 以下、特别是亚秒级的插件开销，本设计无法排除**；只能排除「插件让打开工程慢了几秒」这一量级的说法。

## 二、实验设计

### 两臂

| | A 臂（装插件） | B 臂（禁用插件） |
|---|---|---|
| 沙盒 | `build/MPSV-AB-A` | `build/MPSV-AB-B` |
| 启动参数 | `-PgifRecord=true -PabSandbox=MPSV-AB-A` | 同上 + `-PabSandbox=MPSV-AB-B -PabDisablePlugin=<插件 id>` |
| 插件状态 | 已安装且加载 | 已安装但不加载 |

`-PabSandbox` 是本次为隔离临时加在 `build.gradle.kts` 的 `sandboxContainer` 覆盖项，收工后已还原（只提交本报告）。

### 索引缓存隔离

两臂各用独立 `sandboxContainer`，因此各有独立的 `config/`、`system/`、`log/`、`plugins/`：

```
build/MPSV-AB-A/mybatis-plus-sql-visualizer/IU-2026.2.1/{config,system,log,plugins}
build/MPSV-AB-B/mybatis-plus-sql-visualizer/IU-2026.2.1/{config,system,log,plugins}
```

索引在各自的 `system/` 下，不跨臂复用。实验开始前两臂的 `system/` 与 `log/` 均整体删除，故第 1 轮为真冷索引，第 2 轮起为暖索引。没有采用「清索引缓存」的替代方案，因为共享 system 目录时后测臂会白吃前测臂的索引。

### 固定输入状态

每次运行前把 demo 工程的 `.idea` 整体删除并从基线快照还原（基线快照 104 个文件，含插件此前的产物 `sqldialects.xml`、`sql-visualizer/`、`mybatis-plus-sql-visualizer/`）。这样 16 次运行的输入状态逐字节一致，A 臂运行中写入的产物不会累积到下一次。

### 交错与负载记录

顺序为 A1,B1,A2,B2,A3,B3,A4,B4,A5,B5,A6,B6,A7,B7,A8,B8，严格交替，不用「先跑完 A 再跑完 B」。每次运行前用 PowerShell 采样 `Win32_PerfFormattedData_PerfOS_Processor(_Total).PercentProcessorTime` 三次取均值，并统计机器上的 java/idea 进程数。机器上另有并行会话（登记名 `T-GifRec-MCP`）在跑 IDE，未做排他控制，这一点计入波动来源。

### B 臂的禁用方式（含一处必须记录的坑）

只写沙盒的 `config/disabled_plugins.txt` **不生效**。IntelliJ Platform Gradle Plugin 的 `runIde` 会传 `-Didea.required.plugins.id=<被测插件 id>`，该属性使插件被强制加载。首轮试跑（B1，仅写 `disabled_plugins.txt`）插件仍然加载，日志里照样打出 `LogStartupCapture.execute: 触发`，该轮数据作废。

最终做法是两条一起：

1. 在 `prepareSandbox` 的 `doLast` 里把插件 id 写入沙盒 `config/disabled_plugins.txt`（必须在 `doLast` 里写，因为 `prepareSandbox` 每次执行都会把该文件重置为空——根因是 `Jar` 任务的 `outputs.upToDateWhen { false }` 级联，实测）；
2. 在 `runIde` 的 `jvmArgumentProviders` 末尾追加 `-Didea.required.plugins.id=com.intellij.java` 覆盖原值（命令行后者胜），使被测插件不再是「required」，`disabled_plugins.txt` 才生效。

禁用生效的验证：正式 16 次运行中，B 臂日志出现插件类名的次数为 1（仅 JVM options 回显一行），`LogStartupCapture.execute` 一次都没有；A 臂每次都出现，且插件自身日志行数稳定为 2（JVM options 回显 + `LogStartupCapture.execute`）。

两臂唯一的人为差异就是上述 `idea.required.plugins.id` 取值（A 臂为被测插件 id，B 臂为 `com.intellij.java`）。该属性只参与「插件是否 required」的判定，不改变加载集合——两臂日志中「Problems found loading plugins」清单与 Marketplace 更新查询的插件清单逐条一致。

### 两个被排除的环境混淆项

1. **工程信任模态框。** 全新沙盒首次打开该工程会弹 `Trust and Open Project 'mybatis-plus-sql-visualizer-demo'?` 模态框，位置在工程打开之前，无限阻塞且不写任何日志行。首次试跑因此卡了 578 s。参考沙盒 `mpsv-measure-prewarm` 的会话 2 有同款 340 s 停顿，属同一现象。处理：向两臂沙盒预置 `config/options/trusted-paths.xml`。
2. **退出路径在本机 262 沙盒下失败。** `WM_CLOSE` 能触发退出，但 262 的退出路径要弹确认框，本机 `DialogWrapper.show` 创建 peer 失败：`java.lang.InternalError: couldn't create component peer`，进程变僵尸。16 次运行的 `exit_mode` 全部为 `forced`（强杀）。强杀没有破坏索引缓存：第 2 轮起「待索引文件数」降到 0 ~ 65，暖启动成立。为让后台任务（Maven 导入等）跑完再退出，harness 采用「索引结束标记命中后，日志连续静默 20 s」的退出条件。

### 代码层对照（复核上一轮结论）

以下四条经复核成立：

1. `prewarmPreviewTempFile()` 只有两个调用点：`SqlPreviewPanel.kt:525`（面板构造期）与 `SqlPreviewPanel.kt:2476`（`clear()`）。`SqlPreviewPanel` 只由 `SqlPreviewDialog.kt:28` 构造，`SqlPreviewDialog` 只在 `SqlPreviewService.kt:2095` 构造（预览触发路径）。故预热与工程打开无关。
2. 四个 `postStartupActivity` 声明于 `plugin.xml:289/292/295/300`。`StartupUpdateCheck.shouldStartupCheck(autoCheck, alreadyChecked) = autoCheck && !alreadyChecked`，`autoCheckUpdate` 默认 `false`（`PluginSettings.kt:168`）→ 早退；`logAutoCaptureOnStart` 默认 `false`（`PluginSettings.kt:202`）→ `LogStartupCapture` 记一行日志后早退（实测日志确认）；`SqlTemplateShortcutConflictCheck` 读当前键位映射，应用级单次；`OnboardingAnchorTip` 只订阅 `fileOpened`。
3. 补充一条结构性依据（上一轮未提）：`plugin.xml` 未注册任何 index / stubIndex / fileType 类扩展点。`implementation=` 形式的扩展点全集只有 `consoleFilterProvider`、`errorHandler`、`runConfigurationExtension` 与 4 个 `postStartupActivity`。插件不可能改变索引工作量。
4. 实测佐证：16 次运行中 demo 工程 `.idea` 相对基线的 added / changed / removed **全部为 0**，即工程打开阶段插件不写 `sqldialects.xml`、`sql-visualizer/preview/`。这些产物的写入路径 `DialectPreMapping.ensureMapped` 只被 `SqlPreviewPanel`（预览）与 `DataSourceSelector`（执行）调用，都是用户主动触发的路径。因此该混淆项在实际运行中不存在，无需在运行间额外清理。

一处与计时结论无关、仅作记录的观察：沙盒 `plugins/mybatis-plus-sql-visualizer/lib/` 下的运行期 classpath 含 `mybatis-plus-sql-visualizer-2026.9.18.jar` 4.34 MB、`jsqlparser-5.3.jar` 1.26 MB、`commons-math3-3.6.1.jar` 2.21 MB、`jmh-core-1.37.jar` 0.55 MB、`jopt-simple-5.0.4.jar` 0.08 MB。其中 jmh-core / jopt-simple / commons-math3 是 JMH 基准库，出现在插件运行期 lib 下，建议单独确认是否为打包泄漏。

## 六、未覆盖与不确定之处

- **分辨率有限。** 臂内运行间极差 1.8 ~ 18.6 s，主因是外部 CPU 负载与扫描规模波动。本设计能排除的是「插件让打开工程慢了几秒」这一量级；3 s 以下、尤其亚秒级的开销无法排除。
- **只测了「打开工程」这一条路径。** 用户实际触发预热的入口是打开预览对话框，该路径下的预热开销（以及 `SqlDialectMappings` 写入引发的方言重扫）本次未测。
- **每臂只有第 1 轮是冷索引**（无索引缓存 + 首次 Maven 导入），其余 7 轮是暖索引。冷/暖两组的样本量分别是 1 和 7，冷启动的单点数据不足以单独下结论。
- **退出全部是强制结束。** 本机 262 沙盒的正常退出路径会抛 `InternalError: couldn't create component peer`，拿不到干净退出时的日志尾部。这是平台/环境问题，与插件无关，但意味着「退出阶段」的插件开销未覆盖。
- **未做排他控制。** 机器上另有并行会话在跑 IDE，负载未被隔离。已用「交错 + 记录负载 + 负载校正回归」缓解，未消除。
- **B 臂的禁用是「已安装但不加载」**，与「完全未安装」不同（平台仍会读其 `plugin.xml` 描述符）。若要测「未安装」场景需另做一轮。
- 单次运行的墙钟总时长 206 ~ 241 s 含 gradle 构建、settle 等待与退出等待，不作为启动开销指标。

## 附：退出失败根因追查（2026-09-21，用户提示方向后补）

> 本节由主智能体追加。原报告已正确指出「退出路径要弹确认框」，此处补上**平台源码级条件**、

**栈（idea-session-A1.log:1540-1548）**：

```
ApplicationImpl.doExit(:800) → destructApplication(:817) → confirmExitIfNeeded(:1062)
```

**平台源码给的显示条件**（243 sources jar，`com/intellij/openapi/application/impl/ApplicationImpl.java:732`）：

```java
public boolean isToBeShown() {
    return GeneralSettings.getInstance().isConfirmExit()
        && ProjectManager.getInstance().getOpenProjects().length > 0;   // 设置开着 + 有打开的工程
```

即：不是「弹窗没人点」，而是**弹窗自身创建失败**（窗口 peer 已在拆除中）→ `destructApplication`
抛异常 → IDE 停在原地不退出 → 只能强杀。**点击无从谈起。**

**8/8 量化**：`idea-session-A*.log` 的计数呈 8/7/6/5/4/3/2/1（`confirmExitIfNeeded`）与
16/14/…/2（peer 错误）的等差递减，**是快照假象**——三个日志的**末行时间戳完全相同**
（23:57:48），只是起始时间不同，即它们是同一份累积日志在不同轮次拍的快照。真实读数是
**8 轮各 1 次 `confirmExitIfNeeded`、8 轮全部失败、0 次 `IDE SHUTDOWN`**。

两个组件、无 `GeneralSettings` 组件也无 `confirmExit` 键 → 当前用默认值 true）。
