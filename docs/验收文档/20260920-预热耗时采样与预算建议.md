## 二、样本协议

每次打开记全四项：

1. `[M36] prewarm done in Xms` 的 X（核心读数；本轮 16 次全部成功，`prewarm FAILED` 计数 0）；
2. 该次是否降级（日志里出现 `in-memory PSI preview document created` 即降级）；
3. `[T-PreviewFast] request→dialog` 耗时，以及 `createEditor`（被平台频繁异常抑制时改用同一 tick 的 `showSql branch=createEditor`，两者实测差 3~8ms）到降级装配的时间差；
4. 冷启动首开 / 同会话复开。

轮次安排：会话 A（冷启首开 + 复开 5 次）→ 杀沙盒重启 → 会话 B（冷启首开 + 复开 5 次）→ 再重启 → 会话 C（冷启首开 + 复开 3 次）。
每个会话的第一次打开即「IDE 冷启动后的首次打开」，其余为同会话复开。复开之间关闭对话框、间隔 6 秒。

## 四、关于「为什么连复开也降级」——假设判定

任务给出的两个分支里，**表面读数落在第一支**（复开预热耗时普遍 > 60ms：13/13，116~184ms），
但把它归因为「`t-fix-n2` 的每次唯一文件名让每次打开都要新建文件 + 从零解析 PSI，而固定名时第二次能命中已有 PSI/缓存」，
**本轮数据不支持这条因果链**。三条理由：

**1）「每次打开新建文件、从零建 PSI」这一步在改前改后是相同的。**
`releaseEditor` 里的 `previewTempFile?.let { vFile -> java.io.File(vFile.path).delete() }` 在 `20521e2`（t-fix-n2）之前就存在——
它是该提交 diff 里的**上下文行**，不是新增行。也就是说固定名时代关闭预览同样会删掉那个 `mpsql-preview.sql`，
下一次打开同样是「磁盘上没有这个文件 → 重新建 → VFS 重新认 → PSI 从零解析」。唯一文件名并没有增加这一步，这一步本来每次都有。

**2）唯一文件名是与「方言映射改父目录」一起落地的，后者把每次打开都要付的整条开销去掉了。**
本轮三个会话 `Push all [SqlDialectPusher]` 计数都是 0——目录映射命中后连一次 `setMapping` / `push all dumb` 都没发生。
而改前（固定名 + 按文件映射）是**每次打开一组**（上一轮实测报告 S3：2 次打开 2 组 push all，时刻 +536ms / +1169ms / +395ms，
是该报告唯一能定位到时刻、且唯一必须回到 EDT 的预热内部步骤）。所以改后的每次打开工作量**小于**改前，不是大于。

**3）改前代码在重负载下同样复开全降级。**
上一轮实测报告（固定名时代，CPU 72%~99%）里 4 次同会话复开（S1 #2/#3/#4、S3 #2）**全部降级**；
全仓记录里唯一一次「复开走主路径」（走查轮 `_p1_reopen.png` 那次，commit `28d6ed7`）发生在机器较轻的时候，而那一轮的负载没有被记录。

**结论**：复开 > 60ms 是**「每次打开都要在项目内新建一个文件、并让 VFS/PSI 从零认这个文件」这一固有步骤**叠加机器负载的结果，
而不是唯一文件名新引入的代价；固定名时代同一环境下同样过不去（理由 3），且当时还要多付方言映射。
唯一文件名换来的收益（File Cache Conflict 冲突链从构造上消失，本轮 0 次冲突询问）**在本轮没有观测到额外代价**。

**没测到的部分（不编）**：本轮**没有**跑改前版本做同机同负载的 A/B，所以无法完全排除唯一文件名有一点贡献。
唯一一条我没能证伪的候选机制是：固定名时代若面板在预热写回 `previewTempFile` 之前就被关闭，
那个文件不会被删，下次打开会走 `projectPreviewFile()` 的 `existing != null` 分支（复用已在 VFS 里的路径，而非新建）。
这条路径**可能**更快也可能更慢（它要走 `WriteAction` + `FileDocumentManager.getDocument`），本轮无法判定。
要定论需要把 `20521e2` 的父提交放进独立工作树、在**同一台机器同一负载**下重跑同一协议——本轮没做。

## 五、建议预算与依据

### 5.1 直接结论

- 覆盖本轮观测到的**冷启动首开最大值 360ms**，加约 40% 余量 ⇒ **500ms**。
- 500ms 同时覆盖本轮全部 16 次打开（复开最大 184ms，余量 2.7 倍），即在本环境下**能把 16/16 次降级全部转成主路径**。
- 若更在意等待期观感而不追求余量，可退到 **400ms**（覆盖冷启最大 360ms 仅 11% 余量，偏紧，不建议）。

**建议取值：`PREWARM_WAIT_MS = 500L`。**

### 5.2 这个值覆盖不了什么（必须一起说）

上一轮高负载（CPU 72%~99%）下的冷启动首开，预热耗时的**下界**就已经是 280ms / 395ms / 995ms（三次独立冷启动），
最紧一次落在 (280ms, 1071ms]。本轮负载只有 26%~59%，冷启最大 360ms 与那个下界并不矛盾——
它只是说「本轮的负载下 360ms 够用」，**不足以推出重负载下 500ms 也够用**。

所以 500ms 的定位应当写清楚：**它覆盖中低负载下的首开与全部复开，不覆盖重负载下的首开**。
若产品要求「冷启动首开在任何负载下都不降级」，按已有数据需要 ≥1.5s——而这个代价（见 §六）在观感上不可接受，
且它换来的只是「重负载下首开不挂横幅」这一条。我倾向于**不追这个目标**，改为在降级横幅上把「重开即可恢复」讲清楚（横幅文案已在 `423560b` 改到位）。

### 5.3 数据不足之处（沿用上一轮的教训，如实标注）

- **冷启动首开只有 3 个样本**（233 / 239 / 360），最大值 360ms 带偶然性；中位数 239ms 与最大值差了 50%，
  说明这一个分布的尾部还没有被采到。要定 500ms 这个数，建议再补 3~5 次冷启动首开；
  本轮受时间限制没补。
- **负载不是空载**：两个他人会话的 `find` 全盘扫描全程在跑。空载机上数字会更小（结论更保守），重负载下会更大（结论会被推翻）。
  本轮数字只能当「26%~59% 负载下的读数」用。
- 温索引：三个会话都用了复制过来的索引缓存。若用户是在**首次索引**过程中打开预览，预热只会更慢（本轮完全没覆盖这个场景）。

## 六、抬预算的代价：等待期用户看到什么（已实测）

**等待期编辑区是纯空面板**——没有占位文案、没有转圈、没有任何提示，只有底色。
证据：会话 B 冷启动首开的高频连拍（`shots/_b7_f004.png` 等）在对话框出现后的约 550ms 内，
编辑区亮像素计数为 0（`mean=26.35, bright=0`），随后一次性变成有 SQL 的状态。

但**这段空窗是否被用户看见，冷启动与复开完全不同**：

| 场景 | 当前 60ms 预算下的空窗（createEditor→装配） | 是否被看见 |
|------|------------------------------------------|-----------|
| 冷启动首开 | 926 / 614 / 584 ms | **看得见**。连拍实测：对话框窗口在按键后约 1.9s 出现，之后编辑区全空约 550ms 才出现 SQL |
| 同会话复开 | 119~189ms（中位 138ms） | **基本看不见**。按窗口出现时刻对齐的连拍（`_b16_f001.png`，t=128ms）里 SQL 已经渲染完成——装配落在对话框自身首绘的过程中 |

**抬到 500ms 会怎样**（按调度语义推导，不是猜测）：装配的派发时刻 = min(预算, 预热完成) + EDT 排队。
所以

- 冷启动首开：派发从 `+60ms` 挪到 `+233~360ms`。但当前空窗的**主要项是 EDT 排队**（样本 1：60ms 预算 + 866ms 排队 = 926ms），
  抬预算并不会显著拉长它，反而可能因为派发时机挪到 EDT 稍空的时候而更早装配。**这一项代价接近零。**
- 同会话复开：EDT 排队只有约 55~60ms，所以空窗会**多出（预热耗时 − 60）≈ 56~124ms**，
  即从 119~189ms 变成约 175~260ms。仍是亚 300ms 量级，按 §六 的连拍看属于对话框首绘期间的闪现。**这一项代价是可感的轻微拉长。**

两条建议随预算一起提：

1. 抬预算的同时给编辑区一个轻量占位（复用 `panel.preview.emptyHint` 或加一句「正在准备预览…」），
   把「纯空面板」变成「有内容的等待」；否则冷启动首开那 0.5~0.9s 的空窗就是现在这个样子。
2. 顺手核对一下：抬到 500ms 后，冷启动首开的主路径装配会走进 `assemblePreviewEditor` 的
   `WriteCommandAction { d.setText(sql) }` 分支——也就是 N1（写不安全语境）与 N2（File Cache Conflict）
   真正被触达的地方。本轮 16 次全部降级，这两条在本轮同样**没有被触达**（`Write-unsafe` = 0、`MemoryDiskConflictResolver` = 0，
   但这两个 0 只说明「没触发」，不能说明「修好了」，口径同上一轮）。**抬预算是让 N1/N2 的真机验证成为可能的前提。**
