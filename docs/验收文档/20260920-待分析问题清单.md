## P1 预览对话框恒以降级模式打开（内存 PSI）

**✅ 已修（2026-09-20）**（根因与修法见修复计划 §二）

- **现象**：打开 SQL 预览对话框，顶部常驻告警行「预览以降级模式打开（内存 PSI）——本次项目内临时文件不可用，表/列上下文补全受限。IDE 索引完成后重新打开预览可恢复完整支持。」
- **复现**：2026-09-20 沙盒（IU-262.9437.185 + 插件 2026.9.18）实测；等索引完成（`DumbServiceImpl - exit dumb mode` 已出现）后**重开预览仍不恢复**，与告警自述的「索引完成后可恢复」不符。
- **日志**：`SqlPreviewPanel - [M36] in-memory PSI preview document created (len=70)`；
  另有 `DatabaseSchemaResolver: table=role not found in 4 data sources`。
- **影响**：表/列上下文补全受限；告警行会出现在演示动图与用户截图里。
- **待查**：项目内临时文件为何不可用（写权限？路径？与 T-ExecDocSync 的 exec 文件机制同源？）；「索引完成后重开可恢复」这句提示是否成立。

**补充读数（2026-09-22，沙盒 IU-2024.3.7.1）——P1 的残留路径在真实场景被命中**

抬预算到 500ms 之后，「重负载 / 首次索引中的首开」仍会降级，量级比采样时看到的大得多。今早会话（`log/idea.log`，PID 7636）：

- **处置**：立项 `T-PrewarmLateRecover`（[开发计划](../开发计划/20260922-0840-T-PrewarmLateRecover-预览首开降级自动恢复与横幅重试-开发计划.md)）——F1 迟到产物自动换装、F2 横幅「重试」动作覆盖硬失败；**不抬预算**（采样报告 §5.2 已定需 ≥1.5s，代价不可接受）。

## P2 `features/xml-preview.md` 回滚口径与实测不符

**✅ 已修（2026-09-20）**（根因与修法见修复计划 §二）

- **文档现状**（`features/xml-preview.md:82`）：「INSERT 按主键生成 DELETE、UPDATE 还原 SET 原值、DELETE 按 WHERE 重插，弹窗展示并一键复制。」
- **实测（2026-09-20）**：
  - **UPDATE 无法自动生成回滚**——弹窗明说「该语句无法自动生成回滚：UPDATE 原值不可考」，只给「执行快照查询 + 按粘贴结果生成回滚」入口；
  - **SELECT** 直接判「PlainSelect 语句不支持自动回滚」；
  - **INSERT 的逆向不总按主键**——`RoleMapper.insertBatch`（无主键列）生成的是整行等值谓词
    `DELETE FROM role WHERE name = ? AND code = ? AND description = ?`，并附「可能误匹配多行，请先执行 COUNT 自查」。
- **影响**：文档读者按「UPDATE 还原 SET 原值」预期会落空。需按实测口径改写（并同步 en 版）。

## P3 `sqlv_schema_context` 参数类型错时抛内部异常

**✅ 已修（2026-09-20）**（根因与修法见修复计划 §二）

- **现象**：`tables` 传 JSON 数组（`["user"]`）而非契约要求的逗号分隔字符串时，返回
  `MCP tool call has been failed: Index -1 out of bounds for length 0`——**内部索引异常**，
  不是参数校验错误。
- **对照**：`tables` 传空字符串时返回干净的 `[INVALID_ARGUMENT] tables must contain 1..50 table names (comma-separated).`

- **影响**：MCP 客户端类型写错时拿到的是「插件内部崩了」的错误信号，掩盖真实原因，也容易误判为插件缺陷。
- **待查**：平台参数强转后 `tables` 实际落到什么值；校验应前置到取值之后立即做（或在 `split` 前判空）。

## P7 `DatabaseSchemaResolver` 按名匹配 + 列合并 + 缓存固化

**✅ 已修（2026-09-20）**——缓存键进库名维度、同名表只认首个匹配（不再跨表并列）、祖先链须含 URL 库名；`columnsCached` 不再跨数据源并集（**该项需产品确认**，见修复计划 §四）。

## P7b `table=role not found in 4 data sources` 误报

**✅ 已修（2026-09-20）**——遍历 0 张表即判「查不了」（不写负缓存，下次调用重扫），与「遍历过但确实没有」区分开。

- `DatabaseSchemaResolver.kt:321` 仅在 `bailed==0` 时打印；`:394-399` 只在 `getModel()==null` 置 bail——若 model 非 null 但**内省未完成**，遍历 0 张表、bail 仍为 null → 仍打「not found」。
- `role` 是 demo 库 `mp_demo` 里真实存在的表（4 个 datasource 都是本地 MySQL，含 `mp_demo@localhost`）。
- 待查：`:473-477` 的 per-ds `scan` 行里 `tablesScanned` 是否为 0（用于区分「表真不存在」与「模型未内省完」）；若有 30s 负缓存，误报会被固化。

## P11 `rollback.snapshot.columnMismatch` 键在中英 bundle 里都不存在（P8 同类，扫描新发现）

**✅ 已修（2026-09-20）**——两语言补键（带 `{0}` 缺失列名），弹窗不再显示裸键名。

- **发现方式**：修 P8 时写了一次全仓 `RollbackWarning` 站点核对（29 处字面键），扫出这一处**键缺失**。

### P12 极窄面板下 meta 行整行消失（走查发现，已归因非本轮引入）

### P14 「执行快照查询」后回滚弹窗零反馈 + 预览编辑器被快照 SQL 覆写

- **现象**（2026-09-21 真机走查，用户提问原文「点执行快照查询后回滚 SQL 页面没有变化、SQL 预览页面有变化，当前这个状态正确吗」）：预览一条带参数的 UPDATE（参数面板 `user.username=11 / user.password=11 / #user.id=1`）→【回滚SQL】→ 红色横幅「UPDATE 无法自动回滚：原值不可考」→ 点【执行快照查询】→ **回滚弹窗界面零变化**，变化全部出现在预览面板：左侧预览编辑器内容被换成 `SELECT * FROM user WHERE id = 1;`，执行结果落面板控制台网格（1 行 admin/admin，即执行前的真值）。
- **两半现象性质不同**：
  1. **弹窗不自动回填 = 既定设计**。262 程序化 JDBC 快照不可达（`RemoteConnection` 不在本地发行 jar，见 `RollbackSnapshotStore` KDoc 与计划 §六.2），故降级为「用户亲手取 before-image」：`RollbackSqlDialog.runSnapshotQuery()` 只经 `executeAdhocSql` 把结果送进面板控制台网格，回填须用户**复制网格（TSV，首行须为列名）→ 粘贴到弹窗输入框 → 可选填主键列 → 点【按粘贴结果生成回滚】**。但弹窗内**没有任何一句提示**说明这个顺序，空输入框也无占位文案，用户视角等同「按钮点了没反应」。
  2. **预览编辑器被覆写 = 副作用**。`SqlPreviewPanel.executeAdhocSql` 快路径（`:1030-1034`）把本次 adhoc SQL 写进 `nativeEditorDoc`，而预览编辑器**就是**原生控制台编辑器（`onNativeEditorReady`：「释放自研编辑器（原生控制台占据右侧）」）。代码注释自述「回滚执行后下一次 renderSql 会按预览 SQL 同步回来」——【刷新】可恢复，属可逆。
- **连带影响（同一条覆写链，界面前后自相矛盾）**：编辑器内容停在 SELECT 期间，面板上所有按 `nativeEditorDoc` 取数的动作一起走偏——【复制 SQL】复制到的是 SELECT、【回滚SQL】再点一次会去分析 SELECT（→「PlainSelect 语句不支持自动回滚」消息框）、【执行 SQL】执行的是 SELECT；而参数面板仍显示原 UPDATE 的 11/11/1。
- **待定夺（更严重的一支）**：快照的**时序前提在 UI 上不可见**。降级方案要求快照取自正向 DML **执行之前**（弹窗标签只写「快照（执行前数据）」）。若用户在 UPDATE 已执行后才取快照——而现实中最常见的诉求恰是「已经改了，想回滚」——粘贴进来的是 after-image，`revertUpdateFromSnapshot` 会生成 `SET 被改列=新值 WHERE pk=旧pk AND 被改列=新值`：**执行成功但一行未改**，且评级 COMPLETE、绿色横幅「已生成可执行回滚」。是否比对「快照值 == 原语句新值」并在全量相等时拒绝生成（生成器已同时持有 `changedColumns` 与 `newValuesByColumn`，判据现成），需产品定夺。
- **来源**：2026-09-21 用户走查提问（本清单首条来自用户的真机提问，非复核代理发现）。

### P15 服务端 SQL 错误不进面板错误条（语法错一类完全漏检，2026-09-22 用户真机报告）

- **现象**（用户原文「sql预览面板 运行sql有错误 但是面板没有直接显示 只在Output页面显示了，之前的话在sql预览窗口下方位置应该会显示错误原因并可以一键复制的」）：预览面板执行一条 MySQL 语法错 SQL（`FROM "user" t …`，连跑两次），错误原文只出现在控制台 Output 页，面板下方红字 +「复制错误信息」按钮全程没出现。
- **根因（代码实证 + 判据实测）**：服务端错误不以 Java 异常穿过插件链，插件唯一识别手段是 `execute/DataSourceSelector.kt:612-651` `extractConsoleError` 轮询扫描控制台历史文本，判据是 `:654-659` 的 14 条短语词表 `contains`。用户这条报文 `[42000][1064] You have an error in your SQL syntax;` 一条都不含（不是 `syntax error`、SQLSTATE 是数字形态没有 `sqlstate` 词）→ 返回 null → `onError` 从未被调用。判据复刻实测：`ORA-00933`、达梦「无效的表或视图名」、MySQL `Duplicate entry`（1062）、`foreign key constraint`（1451）同样漏检；`Unknown column` / `doesn't exist` / `does not exist` 系命中（历史成功案例全在这一系）。
- **性质**：既有覆盖面缺口（M36.5 期间真机验证过的错误恰好全是 `Unknown column` 系），非本次改动引入的回归。旁证：`docs/变更记录.md:137`（T-ExplainDbl）记录的 `[42000][1064]` 那次，用户看到的是「等待结果超时」提示而非错误原文——同一条漏检路径。
- **漏检后果**：16s 后 `:2946-2978` 落到 `execute.timeout.hint`——把语法错归因成连接/密码问题（归因方向错误）。
- **处置**：立项 **T-ConsoleErrorCoverage**，计划 `docs/开发计划/20260922-0900-T-ConsoleErrorCoverage-服务端SQL错误识别覆盖与面板兜底呈现-开发计划.md`（结构性判据 `[SQLSTATE][errorCode]` + 兜底呈现；先取证再定判据）。
