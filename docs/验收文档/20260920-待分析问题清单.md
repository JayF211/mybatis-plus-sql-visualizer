## P1 预览对话框恒以降级模式打开（内存 PSI）

**✅ 已修（2026-09-20）**（根因与修法见修复计划 §二）

- **现象**：打开 SQL 预览对话框，顶部常驻告警行「预览以降级模式打开（内存 PSI）——本次项目内临时文件不可用，表/列上下文补全受限。IDE 索引完成后重新打开预览可恢复完整支持。」

- **日志**：`SqlPreviewPanel - [M36] in-memory PSI preview document created (len=70)`；
  另有 `DatabaseSchemaResolver: table=role not found in 4 data sources`。
- **影响**：表/列上下文补全受限；告警行会出现在演示动图与用户截图里。
- **待查**：项目内临时文件为何不可用（写权限？路径？与 T-ExecDocSync 的 exec 文件机制同源？）；「索引完成后重开可恢复」这句提示是否成立。

## P2 `features/xml-preview.md` 回滚口径与实测不符

**✅ 已修（2026-09-20）**（根因与修法见修复计划 §二）

- **文档现状**（`features/xml-preview.md:82`）：「INSERT 按主键生成 DELETE、UPDATE 还原 SET 原值、DELETE 按 WHERE 重插，弹窗展示并一键复制。」
- **实测（2026-09-20）**：
  - **UPDATE 无法自动生成回滚**——弹窗明说「该语句无法自动生成回滚：UPDATE 原值不可考」，只给「执行快照查询 + 按粘贴结果生成回滚」入口；
  - **SELECT** 直接判「PlainSelect 语句不支持自动回滚」；
  - **INSERT 的逆向不总按主键**——`RoleMapper.insertBatch`（无主键列）生成的是整行等值谓词
    `DELETE FROM role WHERE name = ? AND code = ? AND description = ?`，并附「可能误匹配多行，请先执行 COUNT 自查」。
- **影响**：文档读者按「UPDATE 还原 SET 原值」预期会落空。需按实测口径改写（并同步 en 版）。

### P9 `releaseEditor()` 后同面板再装配必降级（复核发现，本轮不修）

### N2 预览临时文件触发平台「File Cache Conflict」模态弹窗

**✅ 已修（2026-09-20，分支 `t-fix-n2` / 提交 `20521e2`）**；**「疑似丢预览内容」已证实成立**，本项因此从观感升为**功能**缺陷。

- **修法**：临时文件名由固定 `mpsql-preview.sql` 改为 **`mpsql-preview-<pid>-<seq>.sql`**（每次预热唯一）+ **按面板生命周期回收**（`projectPreviewFile()` 建文件即登记进 `previewTempFilesCreated`，`releaseEditor()` 删本面板创建过的全部）。**带 `pid` 是必需的**：同一项目可被多个 IDE 进程打开，纯序号会跨进程重号，而重号会让「按面板生命周期删除」误删另一会话正在用的文件——等于把冲突换个形式重现。
- **连带改动**：方言映射的身份判定由**文件**改指**父目录**（`previewDialectMappingTarget(vf) = vf.parent ?: vf`），依据是平台源码 `PerFileMappingsBase.getMappingInner → getMappingForHierarchy` 逐级查表、目录映射被其下所有文件继承——这样每轮新文件名不必重做 `setMapping`（否则白付一次 push-all dumb 模式，且 `workspace.xml` 的 `SqlDialectMappings` 状态会按文件路径逐个累积）。
- **「丢内容」为何成立（代码层链路）**：预热把**占位空内容**写盘，而真 SQL 只写进**内存文档**（`assemblePreviewEditor` 的 `d.setText(sql)` + `commitDocument`，该文档**从不** `saveDocument`）。于是固定名下磁盘恒为占位内容、内存文档是「已修改未保存」，平台 `MemoryDiskConflictResolver.beforeContentChange` 三条判据全中；选「Load File System Changes」即 `reloadFromDisk(document)` 把内存换回占位内容（编辑区只剩占位文案，【刷新】才恢复）——与复核观察到的时机完全吻合。唯一文件名后每次预热落在**无任何 document 的全新路径**，冲突链从根上消失。
- **测试**：新增 `SqlPreviewPanelPreviewTempFileTest` 4 例；必跑四类 25 例全绿；扩到整个 `ui` 包 **104 类 / 1110 例 / 0 失败**。变异实验：文件名改回固定值 → 4 例中 3 例转红，随后 sha256 逐字还原。
- **未验证（需真机）**：①**方言映射本身单测不可断言**——`com.intellij.sql.dialects.SqlDialectMappings` 不在测试运行时 classpath（实测 `ClassNotFoundException`），「目录映射生效 → 新文件名 PSI 仍解析为 MySQL」只有代码层依据，**真机须复核补全/注释仍正常**；②真机四条判据（冲突询问 0 / 模态 0 / 内容不丢 / 目录不增长）待收口验证。
- **既有边界（非本项引入）**：面板 `dispose()` 不调 `releaseEditor()`，极端路径下可能残留本面板最后创建的一个文件（**每面板至多 1 个、不随预览次数增长**）；生产正常路径走 `DialogWrapper.dispose → removeNotify → releaseEditor`，已覆盖。

- **现象**：预览时弹模态框「File Cache Conflict — Changes have been made to `…\.idea\sql-visualizer\preview\mpsql-preview.sql` in memory and on disk.」（Load File System Changes / Keep Memory Changes / Show Difference），**抢焦点**使随后的合成点击全部落空。
- **复现**：连续打开两次以上预览（预热线程重写同名项目内临时文件，而编辑器仍持有内存文档）即触发；走查中在 DELETE 预览与 UPDATE 预览两次独立出现。
- **根因**：临时文件名固定为 `mpsql-preview.sql`（`projectPreviewFile()`），每次预热重写同一文件。
- **影响**：真实用户连续预览同样会遇到。建议每次预热用唯一文件名，或写入前先同步 VFS/文档。
- **复核确认（提交 `a617228` 上仍复现，并补上抢焦点的因果实证）**：平台冲突解析器共询问 **3 次**（idea.log 第 1828 / 2180 / 2194 行 `MemoryDiskConflictResolver - reload mpsql-preview.sql from disk?`），屏幕实际弹出模态 **2 次**（第 1 次把「更多」菜单点击整个吃掉）。第 2 次直接坐实「抢焦点」：其后**连续三次**悬停 meta 行都取不到 tooltip，改用「Keep Memory Changes」关掉模态后，**同一次悬停立刻出 tooltip**。
- **可能的连带后果（仅记录，未归因）**：复核中出现一次「新预览打开后 SQL 编辑区只剩占位文案、点【刷新】恢复」，时机紧跟 N2 的冲突询问——怀疑是冲突解析选择「从磁盘重载」把内存文档换成了预热的占位内容（预热文件内容即占位空壳）。若成立，则 N2 不只是弹窗骚扰，还会**丢掉预览内容**；需专门复现确认。

### P12 极窄面板下 meta 行整行消失（走查发现，待定）

- **现象**：宽度扫描 1150/1000/900/800/700/680px——900px 正常（表名在、摘要中段省略，符合 P5 预期）；**680px（AWT 最小宽）时整个 meta 行连同表名消失**，只剩工具栏。
- **根因（代码实证）**：`applyMetaTruncation()` 用 `budget = width − toolbarPanel.preferredSize.width − insets − 16` 再 `coerceAtLeast(MIN_META_BUDGET_PX)`；当对话框宽度小于工具栏理想宽时 BoxLayout 实际分给 metaLabel 的宽度塌到近 0，而代码仍按非零预算算出文本（`ellipsizeMiddle` 对非空输入永不返回空串）——文本被设成可见内容、组件却被挤成 0 宽。
- **待定项**：**尚不确定是否 P5 引入**（P5 让 meta 行文本变长，可能改变 BoxLayout 的收缩分配）。判定方法：在 680px 下对照「有调用栈摘要」与「无摘要」两种语句；走查未做该对照。
- **归因（2026-09-20 复核走查证据后判定：非 P5 引入）**：走查的 680px 失败是在 `UserMapper.xml` 的 `<update>` 上观察到的，而该语句**无调用栈快照**（§3.2 步骤 4 自证 meta 行为纯主体文案）；且同一语句在 **900px 时 meta 行已被中段省略**——说明单是主体文案就已超出预算，行宽是被工具栏吃掉的，与摘要长短无关。故这是**既有的布局挤压**（面板最小宽下工具栏占满、metaLabel 被挤成 0 宽），非本轮 P5 引入。
- **复核加固（提交 `a617228`）**：在 680px 下对照短 meta（`表: role  XML insert: insertBatch`）与长 meta（`表: role  XML select: selectByIncludeFragment`）——**两者都整行消失**，佐证与文本长度无关；同一短 meta 在 760px 可见（中段省略）、820px 可见、900px 完整，即消失发生在 AWT 最小宽这一档。
- **残余未验证**：长 meta 在 760/820px 的表现未测，故「消失阈值是否随文本长度移动」仍未定（要定 P12 的修法边界需补这一组）。
