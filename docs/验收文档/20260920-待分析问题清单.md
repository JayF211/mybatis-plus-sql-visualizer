## P1 预览对话框恒以降级模式打开（内存 PSI）

- **现象**：打开 SQL 预览对话框，顶部常驻告警行「预览以降级模式打开（内存 PSI）——本次项目内临时文件不可用，表/列上下文补全受限。IDE 索引完成后重新打开预览可恢复完整支持。」
- **复现**：2026-09-20 沙盒（IU-262.9437.185 + 插件 2026.9.18）实测；等索引完成（`DumbServiceImpl - exit dumb mode` 已出现）后**重开预览仍不恢复**，与告警自述的「索引完成后可恢复」不符。
- **日志**：`SqlPreviewPanel - [M36] in-memory PSI preview document created (len=70)`；
  另有 `DatabaseSchemaResolver: table=role not found in 4 data sources`。
- **影响**：表/列上下文补全受限；告警行会出现在演示动图与用户截图里。
- **待查**：项目内临时文件为何不可用（写权限？路径？与 T-ExecDocSync 的 exec 文件机制同源？）；「索引完成后重开可恢复」这句提示是否成立。

## P2 `features/xml-preview.md` 回滚口径与实测不符

- **文档现状**（`features/xml-preview.md:82`）：「INSERT 按主键生成 DELETE、UPDATE 还原 SET 原值、DELETE 按 WHERE 重插，弹窗展示并一键复制。」
- **实测（2026-09-20）**：
  - **UPDATE 无法自动生成回滚**——弹窗明说「该语句无法自动生成回滚：UPDATE 原值不可考」，只给「执行快照查询 + 按粘贴结果生成回滚」入口；
  - **SELECT** 直接判「PlainSelect 语句不支持自动回滚」；
  - **INSERT 的逆向不总按主键**——`RoleMapper.insertBatch`（无主键列）生成的是整行等值谓词
    `DELETE FROM role WHERE name = ? AND code = ? AND description = ?`，并附「可能误匹配多行，请先执行 COUNT 自查」。
- **影响**：文档读者按「UPDATE 还原 SET 原值」预期会落空。需按实测口径改写（并同步 en 版）。

## P3 `sqlv_schema_context` 参数类型错时抛内部异常

- **现象**：`tables` 传 JSON 数组（`["user"]`）而非契约要求的逗号分隔字符串时，返回
  `MCP tool call has been failed: Index -1 out of bounds for length 0`——**内部索引异常**，
  不是参数校验错误。
- **对照**：`tables` 传空字符串时返回干净的 `[INVALID_ARGUMENT] tables must contain 1..50 table names (comma-separated).`
  ——说明校验路径存在，但类型不符时没走到。
- **影响**：MCP 客户端类型写错时拿到的是「插件内部崩了」的错误信号，掩盖真实原因，也容易误判为插件缺陷。
- **待查**：平台参数强转后 `tables` 实际落到什么值；校验应前置到取值之后立即做（或在 `split` 前判空）。

## P4 `sqlv_schema_context` 的 `tables` 匹配跨 schema 污染

- **现象**：`tables: "user"`、`dataSource: mp_demo@localhost` 的返回里**同时出现**两套列：
  `mp_demo.user` 的业务列（username/email/first_name/...）与 **`mysql.user` 系统表**的列
  （`Host` / `User` / `Select_priv` / `Insert_priv` / ...）。
- **影响**：agent 拿到的「表结构上下文」混入了权限系统表列，可能据此写出错误 SQL；对表名与系统表重名的场景尤其危险。
- **待查**：`McpSchemaContextService.buildContext` 的表名解析是否限定了当前 datasource 的 schema；是否需要按
  `TABLE_SCHEMA = <datasource 的库>` 过滤。

## P5 预览「meta 行显示调用栈」在 master 上未接通（只进了 tooltip）

- **验收项原文**（`docs/验收文档/20260917-2058-…-验收文档.md` §3.3 判定卡）：「预览 meta 行显示调用栈、悬停见完整链」。
- **实测**：`SqlPreviewPanel.updateMeta` 里 `metaLineText = meta + warningLine`（`:3724`），而可见行 `metaLabel.text` 由 `applyMetaTruncation` 取自 `metaLineText` —— **调用栈摘要从未进入可见 meta 行**，只进了 `toolTipText`。即第 1 步「顶部提示行追加『调用栈: …』」真机走查看不到；第 2 步「悬停见完整链」成立。
- **引入时间**：自 `b117d8c` 引入时即如此（F3 的 `metaLineText` 在 `739588c` 已存在），**非本轮改动所致**。
- **影响**：验收项前半句不成立，文档判定卡**保持未勾选**；已由新测试 `SqlPreviewPanelStackDigestTest#test现状_可见meta行未含调用栈摘要_仅tooltip有` 把该缺口写成可执行断言——一旦接通即转红，强制同步更新测试与判定卡。
- **修法提示**（待立项）：`metaLineText = meta + warningLine + stackText.inlineLine`（一行），但会改变 F3 宽度预算下的可见行长度，属需拍板的取舍。

## P6 参数提示态会覆写 metaLabel.toolTipText（既有边界）

- **现象**：`SqlPreviewPanel.kt:3503-3504` 的参数提示路径会覆写 `metaLabel.toolTipText`。
- **影响**：处于参数提示态时「悬停见完整调用链」可能被覆盖——与 P5 同属「meta 行/悬停」这条链路的既有边界，修复 P5 时应一并确认。
